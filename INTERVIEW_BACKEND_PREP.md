## 0. Самые основы: как вообще работает веб-приложение

### Клиент и сервер

**Браузер (или мобильное приложение)** — клиент. **Backend** — программа на сервере, которая принимает HTTP-запросы и отвечает (часто JSON). Клиент не имеет прямого доступа к вашей базе данных: он говорит только с API.

### Зачем «вход в систему»

HTTP сам по себе **без состояния**: каждый запрос как новый. Чтобы после логина сервер «помнил» пользователя, нужен способ на каждом запросе доказать: «это всё ещё тот же Вася». Варианты:

1. **Сессия в cookie** — сервер хранит сессию в памяти/Redis/БД, в cookie у клиента только небольшой **session id**.
2. **Токен (JWT и др.)** — сервер выдаёт подписанный билет; клиент присылает его в заголовке (например `Authorization: Bearer ...`). Сервер проверяет подпись и срок действия и **не обязан** хранить сессию (но может — если нужен отзыв).

В нашем проекте для API используется **Bearer JWT** (токен в заголовке).

### Что такое API и REST (в двух словах)

**API** — договорённость: какие URL, какие методы (`GET`, `POST`, …), какой формат тела и ответа. **REST** — стиль, где ресурсы идентифицируются URL, а действия — HTTP-методами. У нас это **FastAPI**, который по коду строит **OpenAPI**-описание (удобно для фронта и тестов).

## 2. JWT: объяснение с нуля + как в нашем проекте

### Зачем JWT, если можно «просто id пользователя»

Если клиент пришлёт «я user 5», сервер не знает, не **подделал** ли это кто-то. Нужна **криптографическая гарантия**: данные в токене согласованы с секретом сервера (или с парой ключей). JWT даёт именно это: **payload + подпись**.

### Из чего состоит JWT (три части)

Строка вида `xxxxx.yyyyy.zzzzz`:

1. **Header** — обычно алгоритм (`alg`, у нас HS256) и тип `JWT`.
2. **Payload** — **claims** (утверждения): например `sub` (id пользователя), `exp` (когда протухнет).
3. **Signature** — результат: взяли header и payload, применили алгоритм и **секретный ключ**, известный только серверу (для подписи) и используемый при проверке.

Части кодируют в **Base64URL** (похоже на Base64, удобно для URL). Это **не шифрование**: любой может **декодировать** header и payload и прочитать содержимое. Поэтому в JWT **не кладут пароли и секреты**.

### HS256 простыми словами

**HMAC SHA-256**: из (данные + секрет) получается короткая «слепок-подпись». Кто не знает секрет, не сможет сделать подпись, которая совпадёт. Сервер при каждом запросе **пересчитывает проверку** — если подпись битая или алгоритм не тот, токен отвергается.

**RS256** (другой частый вопрос) — асимметрично: подпись **приватным** ключом, проверка **публичным**. Удобно, когда токены проверяет несколько сервисов без общего секрета.

### Стандартные claims (что означают)

| Claim | Смысл |
|--------|--------|
| **`sub`** | Subject — обычно id пользователя в вашей системе |
| **`iat`** | Issued at — когда выдали токен |
| **`exp`** | Expiration — после этого момента токен недействителен |
| **`iss`** | Issuer — кто выдал (строка-идентификатор вашего auth-сервиса) |
| **`aud`** | Audience — для кого токен предназначен (другая строка) |

**Зачем `iss` и `aud`:** представьте, что у вас два типа клиентов — админка и личный кабинет пациента. Теоретически один и тот же `sub` мог бы совпасть в разных контекстах. **Audience** говорит: «этот токен только для админского API». Если пациентский endpoint принимает только `aud=pacient_app`, чужой токен отсеется. **`iss`** помогает отличить токены от другого окружения или сервиса.

### Жизненный цикл запроса с JWT (как на собесе нарисовать словами)

1. Пользователь вводит логин/пароль → **POST /login**.
2. Сервер проверяет пароль (сравнение с **хешем** в БД), при успехе вызывает **`create_access_token`**.
3. Клиент сохраняет строку токена (память приложения, `localStorage` — спорно с точки зрения XSS; **httpOnly cookie** безопаснее от XSS, но сложнее с CSRF — это тема для углублённого вопроса).
4. Дальше каждый запрос: заголовок `Authorization: Bearer <token>`.
5. Зависимость FastAPI читает заголовок → **`parse_access_token` / `parse_tenant_access_token_for_request_context`** → проверка подписи, `exp`, затем **`iss`/`aud`** по нашим правилам.
6. Из payload достаётся `sub`, `clinic_id`, `type=admin` и т.д. → загружается пользователь из БД при необходимости → строится контекст запроса.

### Как сделано у нас (`src/core/security.py`)

- Алгоритм: **HS256**, ключ **`JWT_SECRET_KEY`**.
- При создании в payload добавляются **`iat`**, **`exp`**, **`iss`** (tenant issuer), **`aud`** (разный для админа и пациента — см. `_infer_tenant_token_audience`).
- **Platform founder** (оператор платформы, не сотрудник клиники): отдельный тип токена **`type=platform_founder`**, отдельные **`iss`/`aud`**, в production — **отдельный секрет** `PLATFORM_FOUNDER_JWT_SECRET`. Зачем: если скомпрометируют «клинический» JWT-секрет, токены основателя всё ещё защищены другим ключом (**снижение blast radius**).
- Декодирование через PyJWT: сначала проверка подписи и обязательных полей; **`iss`/`aud`** дополнительно валидируются функциями `_validate_tenant_iss_aud` / `_validate_platform_founder_iss_aud`.
- Есть флаг **legacy**: старые токены без `iss`/`aud` могли бы ещё работать — для плавной миграции; в новых токенах claims всегда заполняются.

### Короткоживущий токен для SSE

Для **Server-Sent Events** токен иногда передают в query string (браузер так устроен для EventSource). Длинноживущий admin JWT там нежелателен. В проекте для таких случаев выдаётся **отдельный короткоживущий** access — меньше ущерб при утечке из URL/логов.

### Refresh-токены (часто спрашивают на middle/senior)

**Access JWT** короткий: украли — окно атаки маленькое. **Refresh** длинный, но:

- хранят в **httpOnly Secure cookie** или в БД с привязкой к устройству;
- при обновлении access делают **rotation** (старый refresh инвалидируют);
- при компрометации можно **отозвать** конкретный refresh в БД.

У нас в фокусе **access JWT**; «идеальная» схема access+refresh — хороший ответ, если спросят про best practices.

### Stateless и отзыв токена

Плюс JWT: сервер **не обязан** хранить сессию. Минус: пока не истёк **`exp`**, токен формально валиден. Чтобы **отозвать сразу**, нужен **чёрный список**, **версия пользователя в БД** (при смене пароля увеличили version — старые JWT с младшей версией отклоняются), или очень короткий TTL + refresh. В `admin_auth` отмечено, что **revocation** — отдельная задача.

## 3. Аутентификация и авторизация: разница и безопасность

### Два разных слова

- **Аутентификация** — «ты действительно тот, за кого себя выдаёшь?» (пароль, OAuth, второй фактор).
- **Авторизация** — «тебе **разрешено** это действие?» (роли, права, принадлежность к клинике).

Сценарий: JWT валиден (аутентификация ок), но у пользователя нет права `patients.pii.read` → **403 Forbidden**, не 401.

### Пароли: почему не хранить «как есть»

Если БД утечёт, злоумышленник получит пароли. Поэтому хранят **хеш** — одностороннее преобразование с **солью** и **медленным** алгоритмом (чтобы перебор был дорогим). У админов: **passlib pbkdf2_sha256** (`admin_auth.py`).

### Логин админа (логика по шагам)

1. Нормализуется email, берётся IP клиента.
2. **Rate limit** по IP и по email — ограничение числа попыток за окно времени → защита от **брутфорса**.
3. Поиск `AdminUser` в БД, проверка пароля через **`verify_password`**.
4. Проверки «жив ли аккаунт»: не удалён, статус employment, нет ли блокировки организации (например отзыв платформенного биллинга).
5. Вызов **`create_access_token`** с `sub`, `clinic_id`, `type=admin` и отдельным (более коротким) TTL для админов, если так настроено в `settings`.

### RBAC (роли и права)

**RBAC** — Role-Based Access Control. Роль — набор **permissions** (строки вроде `view_reports`, `manage_crm`). У нас:

- матрица и соглашения — `src/application/rbac_matrix.py`;
- при запросе для админа подгружаются роли и permissions в **`RequestContext`**;
- **`require_permissions("code")`** — фабрика зависимости FastAPI: если в контексте нет ни одного из перечисленных прав → **403**.

Так роутер декларативно говорит: «этот endpoint только для тех, у кого есть право X».

### Мультитенантность (одно слово — много смысла)

**Тенант** — клиент SaaS (здесь чаще **клиника**). В JWT у админа есть **`clinic_id`**. Любой запрос к данным клиники должен **фильтроваться** по этому id (или по организации — в зависимости от доменной модели), иначе теоретически можно запросить чужие записи. В проекте это закрепляется кодом и тестами изоляции.

### Platform founder (отдельная линия доверия)

Это не врач и не админ клиники, а оператор **платформы**. Отдельная таблица/логин, **отдельный JWT-секрет**, опционально **TOTP**. Если в production секрет не задан — маршруты основателя отдают **503** с понятным кодом, а не молча используют общий ключ (это сознательное решение безопасности).

## 4. Nginx: что он делает и зачем он вообще нужен

### Проблема без Nginx

Браузеру нужны **два типа ответов**:

1. **Статические файлы** — `index.html`, JS, CSS, картинки (SPA).
2. **Динамический API** — JSON от Python.

Теоретически можно отдавать и то и другое из Uvicorn, но обычно **разделяют**: Nginx отлично раздаёт файлы с диска и кэширует; Python занимается только API.

### Обратный прокси (reverse proxy)

Клиент стучится **на один хост/порт** (например 80). Nginx смотрит на путь:

- **`/`** — отдаёт файлы из каталога со сборкой фронта;
- **`/api/...`** — **перенаправляет** запрос внутрь сети на `backend:8000` и возвращает ответ клиенту как будто сам ответил.

Для backend запрос «приходит» от Nginx, поэтому передают заголовки:

- **`X-Real-IP`** / **`X-Forwarded-For`** — кто реальный клиент (иначе в логах Python был бы только Nginx);
- **`X-Forwarded-Proto`** — `http` или `https` (если TLS терминирует Nginx, приложение должно знать, что снаружи HTTPS);
- **`Host`** — исходный Host.

### Почему `try_files $uri /index.html`

У SPA **одна** точка входа: `index.html`, а маршруты (`/admin/schedule`) рисует уже JavaScript. Если запросить `/admin/schedule` как файл — на диске такого файла нет. **`try_files`** говорит: если файла нет — отдай **`index.html`**, роутер на клиенте разберётся.

### `resolver 127.0.0.11` в Docker

В Docker имя **`backend`** резолвится в IP. Если резолв только при старте Nginx, а контейнер backend поднялся позже, бывают ошибки. **Docker DNS** (`127.0.0.11`) + переменная в `proxy_pass` заставляют резолвить **на каждый запрос** (с кэшем на секунды) — устойчивее при пересоздании контейнеров.

### Что ещё часто делают на Nginx (для собеса)

TLS (сертификаты), gzip/brotli, лимит размера тела, таймауты, rate limit на уровне периметра. В нашем `frontend/nginx.conf` — минимально необходимое для SPA + прокси API.

## 5. База данных: ORM, миграции, слой сервисов

### Зачем ORM (SQLAlchemy)

Писать всё на «голом SQL» можно, но в большом проекте удобнее **объекты Python**, которые мапятся на строки таблиц: меньше ручной склейки полей, типизация, единый стиль запросов. Минус: сложные отчёты иногда пишут сырьём SQL или Core.

### Async-сессии

**Async** — пока приложение ждёт ответа от БД по сети, оно может обрабатывать другие запросы (в рамках event loop), не блокируя поток на каждом I/O. Для высокой конкуррентности это стандартная модель в FastAPI.

### Миграции Alembic (аналогия)

Код версионируют в Git. **Схему БД** тоже нужно версионировать: кто-то добавил колонку — это файл миграции. На пустой базе последовательно применяются все миграции → получается актуальная схема. В Compose контейнер **`migrations`** выполняет `alembic upgrade head` **до** старта `backend`, чтобы приложение не упало из-за отсутствующих таблиц.

### Где живут правила

- **Ограничения БД** — уникальность, внешние ключи (`FOREIGN KEY`), `NOT NULL`: последняя линия защиты целостности.
- **Бизнес-правила** («нельзя записаться на прошлое», «нельзя видеть чужую клинику») — в **application services** и проверках в роутерах/зависимостях, а не только на фронте (фронт можно обойти).

### Soft delete

Вместо физического `DELETE` иногда ставят **`deleted_at`**: запись «скрыта», но история и FK сохраняются. В проекте это встречается в моделях (например админ не удалён навсегда из БД сразу).

### Expand/contract (если спросят про zero-downtime)

Большое изменение схемы делают в два этапа: сначала **добавить** новое (старое и новое поле живут вместе), выкатить код, мигрировать данные, потом **убрать** старое. Так избегают поломки между версиями приложения.

## 6. Redis, Celery, события (коротко и понятно)

### Redis

Очень быстрое key-value хранилище **в памяти** (с опциональной персистентностью). У нас: **лимиты запросов** (счётчики по ключам), инфраструктура для **Celery** (брокер и backend результатов в `docker-compose.yml`).

### Celery

Задача: «отправить письмо», «собрать отчёт» — может идти секунды. Не держим HTTP открытым: кладём задачу в очередь, **worker** забирает и выполняет. **Beat** — планировщик периодических задач.

### In-process event bus

В коде есть шина событий **внутри процесса** API: что-то произошло → вызвались обработчики (CRM, loyalty, …). Это **не Kafka**: для тяжёлого асинхронного — рядом Celery.

## 8. Типичные вопросы на собесе (чуть развёрнутее)

| Вопрос | Как ответить |
|--------|----------------|
| Почему FastAPI? | Современный async-стек, явные типы и Pydantic, автогенерация OpenAPI, удобный DI через `Depends`. |
| Async ORM — зачем? | Запрос к БД — I/O; async позволяет не блокировать обработку других запросов в том же worker. |
| Зачем Redis? | Скорость, атомарные операции для rate limit, очередь Celery. |
| Celery vs шина в памяти? | Шина — быстрые реакции в одном процессе; Celery — вынос тяжёлой работы и расписание. |
| JWT в localStorage и XSS? | XSS может украсть токен; httpOnly cookie лучше против XSS, но нужна защита от CSRF для state-changing запросов. |
| CORS? | Браузер блокирует запросы с «чужого» origin, если сервер не разрешил заголовками; на API настраивают доверенные origin. |

## 10. Технологии глубже (2–3 абзаца там, где есть смысл)

Здесь не справочник «что такое X», а **зачем это на собесе** и **как это стыкуется с реальным стеком**. Про инструменты без особой глубины (например Vite) можно не размазывать — их нет в списке.

### FastAPI и Uvicorn

**FastAPI** — не «ещё один фреймворк ради моды», а сознательный выбор под **typed API**: Pydantic валидирует тело запроса и query-параметры до входа в бизнес-логику, ошибки 422 получаются предсказуемо. Из тех же типов и аннотаций строится **OpenAPI** — это экономит время фронта и QA и показывает на собесе, что вы понимаете контракт API как продукт, а не только как набор функций. **Depends** даёт внедрение зависимостей без глобального состояния: сессия БД, rate limiter, контекст пользователя — всё явно в сигнатуре маршрута.

**Uvicorn** — ASGI-сервер: он держит сеть и отдаёт управление приложению по протоколу ASGI. На собесе полезно сказать, что один worker Uvicorn — один event loop; под высокую нагрузку обычно поднимают **несколько воркеров/процессов** или ставят за ним процесс-менеджер/gunicorn с uvicorn workers — это уже зона деплоя, но вопрос «почему не один процесс на всё» иногда задают.

### PostgreSQL

Реляционная модель хорошо ложится на **SaaS с сущностями и связями**: клиники, пользователи, записи, права, платежи — всё это с **внешними ключами**, уникальными ограничениями и транзакциями **ACID**. На middle/senior часто спрашивают про изоляцию транзакций и индексы: в нашем проекте критично не только «написать запрос», но и не сломать **мультитенантную изоляцию** — фильтрация по `clinic_id` и тесты на утечки между клиниками важнее, чем мода на document-store.

Отдельно в конфиге есть задел под **read replica** (`database_replica_url`) и reporting-сессии с таймаутом — типичный шаг для тяжёлых отчётов без убийства основной базы. Это хороший факт для собеса: «чтение аналитики выносим на реплику, записи — в primary».

### SQLAlchemy 2 и async

**ORM** снимает рутину маппинга строк на объекты и помогает держать единый стиль доступа к данным; **SQLAlchemy 2** делает API более предсказуемым, чем «магия» первых версий. **Async**-сессии с **asyncpg** означают: пока ждём ответа от Postgres по сети, event loop может обрабатывать другие запросы (в рамках одного worker). Важная оговорка для senior-уровня: async не убирает узкие места — тяжёлые запросы и блокировки в БД всё равно нужно **профилировать**; async помогает с **concurrency I/O**, а не с «ускорением SQL в разы».

### Redis в проекте — не только кэш

Redis здесь выполняет **несколько ролей**, и на собесе выигрывает тот, кто это разделяет. Во-первых, **кэш приложения** (расписание, ERP dashboard JSON, справочник профессий) — см. §12. Во-вторых, **rate limiting** — счётчики с TTL в фиксированном окне; при падении Redis лимитер у нас **fail-open** (пропускает запрос), чтобы доступность не убилась из-за кэша — компромисс безопасность/доступность, о котором стоит упомянуть. В-третьих, **краткоживущие данные**: коды OTP для пациентов, OAuth `state`, одноразовые токены на скачивание меддокументов — это не «кэш», а **временное хранилище** с истечением срока. В-четвёртых, **Celery** использует отдельные DB индекса Redis как брокер и backend результатов. Плюс **Pub/Sub** для real-time (например вокруг omni-chat) и **NX + EX** как простой **распределённый lock** в оркестраторе — паттерн «только один исполнитель на ключ».

Итого: Redis — **мультиплексор инфраструктуры**; путать всё подряд с «кэшем» на собесе не стоит.

### Celery

**Celery** отвечает на вопрос: «что делать с работой, которая длится секунды и не должна держать HTTP-запрос открытым». Worker забирает задачи из брокера (Redis), **Beat** запускает периодические задачи по расписанию — это замена многим «кронам на сервере», но с очередью и повторными попытками на уровне воркера. В нашем коде фоновые задачи связаны с доменом (например обновление ERP-витрин и **инвалидация кэша** отчётов после пересчёта). Для собеса: Celery — не замена **in-process event bus**; шина в приложении — для быстрых реакций в том же процессе, Celery — для **выноса тяжёлого I/O и CPU** и ретраев.

### Alembic

Без миграций схема БД живёт «как получится» на каждом стенде. **Alembic** версионирует изменения так же, как Git версионирует код: `upgrade head` приводит пустую или старую базу к актуальной структуре. В Docker Compose job **migrations** выполняется **до** старта API — это защита от гонки «приложение поднялось, а колонки ещё нет». Senior-уровень: для больших таблиц иногда нужны поэтапные миграции (**expand/contract**), чтобы не блокировать продолжительным `ALTER` на миллионах строк.

### Docker Compose

Compose описывает **граф сервисов** (Postgres, Redis, backend, worker, nginx, …), порядок старта и healthcheck’и. Для разработчика это «один способ поднять всё окружение»; для собеса — связь с **идемпотентностью деплоя**: миграции отдельным шагом, секреты из `.env`, образы с фиксированными digest в проде (в комментариях compose это прямо рекомендуется).

### Nginx (дополнение к §4)

В прод-сборке фронта Nginx — **edge**: статика SPA + прокси `/api`. На собесе можно добавить, что TLS чаще всего терминируют на Nginx или балансировщике облака; приложение за прокси должно доверять **`X-Forwarded-*`** только от известных hop’ов (иначе подделка клиентского IP).

### Prometheus / Grafana (коротко)

Метрики — не «украшение», а способ отвечать на вопросы «что сломалось» и «где горит» без ручного копания в логах. В проекте есть счётчики по кэшу ERP, JWT, мультитенантности и т.д. — это показывает зрелость наблюдаемости; детали конфигов в `deploy/`.

## 11. Архитектура: виды подходов и что у нас

### Монолит и микросервисы

**Модульный монолит** — один деплояемый backend, но код разбит на **модули/пакеты** с границами (у нас слои api / application / domain / infrastructure). **Микросервисы** — отдельные деплои, отдельные БД (часто), сеть между сервисами, распределённые транзакции сложнее. Наш проект — **монолит** с чётким внутренним разделением: для собеса это нормальный ответ «мы не усложняли инфраструктуру до десяти репозиториев, но следим за границами модулей и тестируем изоляцию тенантов».

### Слоистая (layered) архитектура

Классика: **presentation → business → data**. В FastAPI «presentation» — роутеры и схемы Pydantic; «business» — сервисы application; «data» — репозитории и ORM. Зависимости идут **внутрь**: API знает о сервисах, сервисы — о интерфейсах домена, инфраструктура реализует эти интерфейсы. Если на собесе спросят «где бизнес-логика» — ответ: преимущественно **не** в роутерах, а в **application services** и правилах домена.

### Гексагональная / порты и адаптеры

Идея: **ядро** (домен) не импортирует Postgres или HTTP; снаружи — **адаптеры** (SQLAlchemy repo, HTTP-клиент к YooKassa и т.д.). В Python это часто смягчено (всё в одном репозитории), но **направление зависимостей** то же: `domain.interfaces` задаёт контракт, `infrastructure` его имплементирует. Это ценный факт: вы не путаете «сущность» с «способом её сохранить».

### Событийно-ориентированная составляющая

**In-process event bus** — обработчики в том же процессе, реакция на доменное событие без немедленного HTTP-ответа клиенту. **Celery** — асинхронная «очередь событий» с персистентностью в брокере и отдельными воркерами. На собесе полезно сказать: «у нас не Kafka между сервисами, потому что сервис один; зато есть разделение **синхронного запроса** и **отложенной обработки**».

### CQRS / read models (лёгкое касание)

Полный CQRS — отдельные модели чтения и записи; у нас **задел** в сторону read replica и кэширования тяжёлых **GET** отчётов — это разговор «мы кэшируем read-модель (JSON дашборда), инвалидируем после пересчёта агрегатов», без заявления, что весь проект построен на CQRS.

## 12. Кэш: виды и что реально есть в dental_booking

### Зачем вообще кэш

База и сеть — дороже, чем память рядом с приложением. Кэш **снижает latency** и **нагрузку на primary** DB. Цена — **согласованность**: данные в кэше могут устареть; нужны **TTL**, **инвалидация** при записи или явные события «данные пересчитаны».

### Где может жить кэш (классификация)

1. **Клиент / браузер** — заголовки `Cache-Control`, ETag; для API с персональными данными часто **отключают** агрессивное кэширование или используют короткий TTL.
2. **CDN** — статика фронта, иногда API на edge; в нашем типичном compose CDN не встроен, но в облаке часто включают перед Nginx.
3. **Reverse proxy** — кэш ответов upstream (в `frontend/nginx.conf` для API кэш не включён — правильно для авторизованного JSON).
4. **Application cache** — приложение само читает/пишет Redis (или in-memory LRU для одного процесса; у нас упор на **Redis**, чтобы кэш был общим для нескольких инстансов API).

### Паттерны на стороне приложения

- **Cache-aside (lazy loading):** приложение сначала смотрит Redis; при промахе читает БД, кладёт в Redis, отдаёт клиенту. Инвалидация — явным `DELETE` ключей при изменении данных (или TTL). **Расписание врача** у нас именно так: `ScheduleService.get_daily_schedule`, ключ `schedule:{doctor_id}:{day}`, TTL **300 секунд**; при бронировании и связанных изменениях вызывается **`invalidate_daily_schedule_cache`** из `BookingService`.
- **Read-through:** логика похожа, но иногда выделяют отдельный слой «всегда через кэш-обёртку». **ERP dashboard** (`erp_report_cache.py`) — чтение JSON из Redis с метриками hit/miss/error, запись с **`setex`** и TTL из настроек (**по умолчанию 60 с**); после обновления витрин Celery вызывает **`invalidate_clinic_erp_report_cache`** — скан ключей по паттерну клиники и удаление (грубая, но простая инвалидация всего кэша отчётов клиники).
- **Write-through / write-behind** — запись одновременно в кэш и БД (или в кэш с отложенной записью в БД); в нашем коде **доминирует cache-aside + явная инвалидация**, write-behind для основных сущностей не используется как паттерн хранения истины.

### Что в Redis у нас НЕ кэш

Чтобы на собесе не смешивать понятия: **счётчики rate limit**, **OTP/state OAuth**, **одноразовые токены**, **брокер Celery**, **pub/sub**, **distributed lock** — это **другие паттерны** на том же движке Redis; их нельзя назвать «кэшем данных домена», хотя технически тоже key-value с TTL.

### Сводка по кэшу данных в проекте

| Что | Где в коде | Паттерн / TTL | Инвалидация |
|-----|------------|---------------|-------------|
| Сетка расписания врача на день | `ScheduleService` | Cache-aside, **300 с** | При изменениях бронирования и т.п. |
| JSON тяжёлых ERP-дашбордов | `erp_report_cache.py` | Read-through + TTL (**60 с** по умолчанию) | После refresh витрин — все ключи клиники |
| Список категорий профессий (staff directory) | `staff_directory_cache.py` | TTL **120 с** (настраивается) | При мутациях справочника |

Настройки включают/выключают ERP и staff-кэш флагами в **`settings`** (`erp_dashboard_cache_enabled`, `staff_directory_cache_enabled`).

## 13. Мини-глоссарий (термины, которые всплывают на собесах)

Коротко: **что это** и **зачем помнить**. Алфавитный порядок по ключевым словам.

| Термин | Простыми словами |
|--------|-------------------|
| **ASGI** | Протокол между **приложением** Python и **сервером** (Uvicorn): как передаются HTTP/WebSocket. Преемник/родственник WSGI, но с **async** и жизненным циклом соединений. FastAPI — ASGI-приложение. |
| **Claim** | Одно поле внутри JWT payload, например `sub` или `exp`. Стандартные claims описаны в спецификации JWT; остальные — ваши доменные (`clinic_id`, `type`). |
| **CORS** | Правила браузера: запрос с сайта A к API на домене B — «кросс-доменный». Сервер отвечает заголовками `Access-Control-*`, разрешая или запрещая. Без CORS фронт на другом origin не прочитает ответ. |
| **CSRF** | Атака: пользователь залогинен на сайте B, злоумышленник заставляет браузер **отправить запрос** на B с куками пользователя. Для **cookie-сессий** защищаются токенами SameSite, CSRF-токенами; для **JWT в Authorization** риск другой (XSS важнее). |
| **DI (Dependency Injection)** | В FastAPI зависимости (`Depends`) создают сессию БД, текущего пользователя, rate limiter — роутер не «достаёт их сам из глобалов», фреймворк **внедряет** готовые объекты. |
| **HMAC** | Семейство схем: **ключ + сообщение → подпись**. HS256 в JWT — это HMAC с SHA-256. Без ключа подпись не воспроизвести. |
| **HS256 / RS256** | **HS256** — один секрет на подпись и проверку (симметрия). **RS256** — подпись приватным ключом, проверка публичным (удобно нескольким сервисам). |
| **JWT** | Подписанный «билет» с claims; клиент носит в заголовке `Authorization: Bearer`. Payload не секретен — нужен HTTPS. |
| **ORM** | Object-Relational Mapping: классы Python ↔ таблицы SQL; запросы строятся через API ORM (SQLAlchemy), а не только рукописным SQL. |
| **OpenAPI** | Машиночитаемое описание API (пути, схемы тел). FastAPI генерирует из типов и аннотаций — из него делают Swagger UI и клиенты. |
| **PII** | Personally Identifiable Information — персональные данные (ФИО, телефон, email). В логах их часто **маскируют** или не пишут. |
| **RBAC** | Role-Based Access Control: доступ через **роли**, роли дают **permissions** (строковые коды прав). У нас `require_permissions("...")` на эндпоинтах. |
| **SaaS** | Software as a Service: один продукт — много клиентов-организаций; изоляция данных между ними — обязательна. |
| **SHA-256** | Криптографическая хеш-функция: из большого входа — фиксированный «отпечаток». В HMAC используется как внутренняя функция; для паролей нужны **медленные** KDF вроде PBKDF2/Argon2, не «голый SHA». |
| **Tenant** | «Жилец» SaaS: одна организация/клиника как изолированный контур данных. У админа в JWT есть `clinic_id` — привязка к тенанту. |
| **TLS / HTTPS** | Шифрование транспорта между браузером и сервером; без этого JWT и пароли видны по сети. |
| **Uvicorn** | ASGI-сервер, который слушает порт и вызывает ваше FastAPI-приложение. |
| **WSGI** | Старый синхронный стандарт Python для веб-приложений; для async-стека чаще **ASGI**. |
| **XSS** | Внедрение скрипта на страницу: может украсть токен из JS-переменной или localStorage. Защита: экранирование, CSP, httpOnly cookies для чувствительных данных. |

## 14. Устный ответ на ~2 минуты: «Опишите авторизацию в вашем проекте»

Ниже текст, который можно **проговорить почти дословно** (≈300–380 слов при спокойном темпе). Подстройте под свой опыт: «я участвовал в…», «мы сделали…».

---

**Вариант монолога**

У нас SaaS для клиник, backend на FastAPI. Я разделяю **аутентификацию** и **авторизацию**.

**Аутентификация:** пользователь доказывает личность. Для админов это email и пароль: пароль не хранится в открытом виде, в базе лежит **хеш** через PBKDF2. На логине мы проверяем учётку, статус, ограничения организации и выдаём **JWT access token** — подписанный HS256 секретом сервера. В токене есть идентификатор пользователя, клиника, тип токена `admin`, плюс стандартные поля **срока жизни**, **issuer** и **audience**, чтобы токен нельзя было перепутать с другим контуром — например с пациентским или с отдельным JWT для оператора платформы. Для платформенного оператора у нас вообще **отдельный секрет** в production, чтобы компрометация клинического ключа не открывала платформенные маршруты.

Дальше каждый запрос к защищённым эндпоинтам идёт с заголовком `Authorization: Bearer`. Middleware и зависимости FastAPI **проверяют подпись и срок**, валидируют issuer и audience, по `sub` подгружают пользователя из базы при необходимости.

**Авторизация** — это уже не «кто ты», а «что тебе можно». После валидации JWT мы строим **контекст запроса**: для админа подтягиваем роли и набор **permissions** из сервиса RBAC. На роутерах используется фабрика зависимостей вроде «нужно право `view_reports` или `manage_crm`». Если права нет — отвечаем **403**, если токена нет или он битый — **401**.

Отдельно у нас **мультитенантность**: админ привязан к **клинике**, идентификатор есть в токене; бизнес-логика и запросы к данным должны **ограничиваться** этой клиникой, чтобы не было пересечения данных между клиентами SaaS.

На периметре логина и чувствительных операций включён **rate limiting** через Redis — чтобы усложнить подбор паролей и злоупотребление API.

Если коротко: **JWT подтверждает личность и контур**, **RBAC и clinic_id определяют, что можно и в каких границах данных**, плюс лимиты и разделение секретов для снижения рисков.
