> **Технический канон:** [PRODUCT_KNOWLEDGE_BASE.md](./PRODUCT_KNOWLEDGE_BASE.md) · маршруты API: [API_V1_ROUTER_MANIFEST.md](./API_V1_ROUTER_MANIFEST.md), [router_surface/INDEX.md](./router_surface/INDEX.md)

---

## Позиционирование

**Dental Booking** — операционная B2B-платформа под стоматологию: маркетинг и запись на сайте, PWA для пациента, админка для расписания, коммуникаций, задач, финансов и маркетинга, единый REST API (`/api/v1`) и изоляция данных по клинике (tenant). Один продукт закрывает цепочку «лид → запись → визит → оплата → повторный визит» без склейки пяти разных сервисов.

---

## Коммерческие условия и цена

В **git-репозитории нет** прайс-листа, пакетов SaaS и лимитов в духе «N пользователей» или «M клиник»: это **внешний** контур (КП, договор, биллинг). Для цифр по подписке и внедрению — только коммерческая служба.

Ниже — не «ёмкость продукта», а **инженерные параметры по умолчанию**, которые можно проверить в коде и при необходимости масштабировать конфигурацией процесса и инфраструктуры (отдельные инстансы API, пулер БД, воркеры Celery, реплика и т.д.).

## Масштаб и нагрузка — объективно по коду

Источник полей по умолчанию: **`src/core/config.py`** (класс `Settings`; переопределение через переменные окружения, см. `.env.example`).

| Тема | Что в коде | Комментарий для заказчика / интегратора |
|------|------------|----------------------------------------|
| **Клиники (tenant)** | Сущность `Clinic`, изоляция данных по `clinic_id`, проверки в `src/application/multitenancy.py` | В прикладном коде **не задан** верхний предел числа клиник в одной инсталляции; сеть из многих точек — это вопрос **развёртывания и БД**, а не захардкоженного «один tenant». |
| **Пул соединений к PostgreSQL** | `db_pool_size=20`, `db_max_overflow=10` | На **один процесс** API-воркера (типичный `uvicorn`) SQLAlchemy по умолчанию даёт до **30** одновременных соединений к БД (20 + overflow). Под нагрузку сети клиник обычно поднимают **несколько реплик** API и/или увеличивают эти переменные осознанно. |
| **Redis** | `redis_pool_size=10` | Пул клиентов Redis на процесс; брокер Celery задаётся отдельно (`celery_broker_url` / `CELERY_BROKER_URL`). |
| **Чтение отчётов с реплики** | `database_replica_url` (опционально), `db_reporting_statement_timeout_ms`, лаг реплики в health | Поддерживается **масштабирование чтения** для тяжёлых GET (см. комментарии в `config.py`, `GET /health/replica` в [OBSERVABILITY.md](./OBSERVABILITY.md)). |
| **ERP / отчёты** | `erp_reports_read_from_aggregate`, витрины, `erp_aggregate_stale_max_seconds` и др. | Тяжёлые отчёты могут идти через **предагрегаты** и fallback на «сырые» запросы при устаревании — это про **стабильность под нагрузкой**, а не про лимит клиник. |
| **Rate limiting** | Отдельные лимиты на auth, admin login, omni send, staff chat, patient chat, AI per clinic и т.д. | Это **защита от злоупотреблений и burst**, а не объявление «максимум пользователей». Значения по умолчанию — в `Settings` в `config.py` (например `rate_staff_chat_send_per_admin_limit`, `rate_admin_omni_send_per_admin_limit`). |
| **Фоновые задачи** | Celery (`celery_broker_url`, `celery_result_backend`) | Пропускная способность очередей — от **числа воркеров** и железа, не зашита одной константой «максимум клиник». |
| **Локальный Compose** | `docker-compose.yml` | Описывает **dev/stage-подобный** стек (Postgres 16, Redis 7, backend, celery, beat, frontend); это **не** спецификация максимальной производственной нагрузки. |

Итог для sales-дискуссии: продукт **изначально мультитенантный** и **не содержит** в репозитории искусственного потолка «одна клиника / пятнадцать сотрудников». Реальная ёмкость — предмет **нагрузочного теста** на целевой конфигурации и коммерческих гарантий (SLA), а не абзаца в markdown.

## Тесты и качество (что есть в репозитории)

- **Pytest:** API (`tests/api/`), сервисы, безопасность, прикладные сценарии — обзор связки «роутер → тесты» в [TESTING_SURFACE.md](./TESTING_SURFACE.md) и в автосводке [router_surface/INDEX.md](./router_surface/INDEX.md).
- **Сквозной сценарий записи и оплаты** зафиксирован в E2E: `tests/e2e/test_booking_to_payment.py` (см. [E2E_TESTING.md](./E2E_TESTING.md)).
- **Фронт:** unit-тесты рядом с страницами (`frontend/src/**/__tests__`), при необходимости Playwright в `frontend/e2e/`.

Это не маркетинговая декларация: при пилоте вы можете запустить тот же `pytest` и убедиться в зелёном прогоне на своём стенде.

## Метрики и эксплуатация (снижение риска простоя)

- Эндпоинты **`/health`**, **`/health/replica`**, **`/health/s3`**, **`/metrics`** (Prometheus) — см. [OBSERVABILITY.md](./OBSERVABILITY.md), реализация в `src/main.py`, доменные счётчики в `src/core/metrics.py` (в т.ч. омниканал, задачи, AI-события — по меткам в коде).
- В репозитории лежат **правила алертов** и **дашборды Grafana**: `deploy/prometheus/`, `deploy/grafana/`.

Для сети клиник это переводится в понятные SLA-обсуждения: не «надеемся», а **снимаем показатели** и реагируем по порогам.

## Два контура коммуникаций (важно для продажи и внедрения)

Путаница здесь стоит денег и репутации; в продукте контуры **разведены** на уровне API и UI.

| Контур | Назначение | API (v1) | Админка (пример URL) |
|--------|------------|----------|------------------------|
| **Чат команды (staff)** | Внутренняя переписка и коллаборация персонала **клиники** | Префикс `/admin/staff` (`admin_staff_collab`) | `/admin/staff-chat` |
| **Omni-чат** | Диалоги с **пациентами** по внешним каналам (омниканал) | Префикс `/admin/omni-chats` и смежные модули | `/admin/omni-chat` |

Пациентский мессенджер в PWA — отдельный контур (`/patient/chat`, UI `/app/chat`). Подробнее: [FEATURE_CHATS_OMNI_PATIENT_STAFF.md](./FEATURE_CHATS_OMNI_PATIENT_STAFF.md). На демо это стоит показать **двумя вкладками подряд**, чтобы заказчик увидел разделение.

## Для кого мы продаём

- **Клиника** с цифровизацией «под ключ»: нужен один вендор на запись, коммуникации и операционку.
- **Сеть** с IT-командой или подрядчиком: нужны API, метрики, предсказуемая архитектура.
- **Интегратор**: готовый стек в Compose, документированные пути и права — меньше сюрпризов на сдаче.
