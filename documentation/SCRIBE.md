# Куда писать открытую продуктовую документацию (SCRIBE)

> **Версия:** 2026-04-03

Документатор (и любой автор продуктовых текстов для **git**) работает **только** в **`documentation/`**. Здесь же лежит материал, который одновременно годится **для клиентов / покупателей** и для **публичного RAG** по репозиторию — **один файл, один смысл, без второй копии** в другом каталоге.

## Канонические пути

См. порядок и смысл слоёв в **[STRUCTURE.md](./STRUCTURE.md)**. Кратко:

| Класс | Путь |
|-------|------|
| Обзор продукта | [PRODUCT_OVERVIEW.md](./PRODUCT_OVERVIEW.md) |
| Питч | [SALES_PITCH.md](./SALES_PITCH.md) |
| База знаний о продукте (поддержка + sales + **единый** текст для RAG в git) | [PRODUCT_KNOWLEDGE_BASE.md](./PRODUCT_KNOWLEDGE_BASE.md) |
| Дерево репозитория | [PROJECT_REPOSITORY_LAYOUT.md](./PROJECT_REPOSITORY_LAYOUT.md) |
| Пользовательские гайды | [USER_DOCS/](./USER_DOCS/) · [USER_DOCS/INDEX.md](./USER_DOCS/INDEX.md) |
| OpenAPI в репозитории | `documentation/openapi.json` (если команда публикует) |

## Как не плодить дубли «RAG vs клиент»

1. **Публично безопасный** контент (что умеет продукт, как пользоваться, ограничения) — **только** в файлах выше. И клиент, и индексатор читают **одно и то же**.  
2. **Секреты, цены переговоров, внутренние решения, черновики волн** — **не** в `documentation/`; ведутся в закрытом хранилище команды. Там **не** дублировать абзацы из `PRODUCT_KNOWLEDGE_BASE.md`: вместо копии — ссылка «канон в репозитории: `documentation/…`».  
3. Если нужен **внутренний** расширенный разбор (углубленный аудит модуля только для штаба), он живёт **вне git** и явно помечается как не для клиента; пересечение с публичным каноном — через отсылки, не через копипаст.

## Правила качества

1. В `documentation/` **не ссылаться** на закрытые деревья и не упоминать внутренние кодовые имена регламентов, которых нет в этом репозитории.  
2. Факты сверять с **кодом** и **тестами**; пробелы помечать явно («уточнить у команды разработки»), без выдумывания.  
3. Не создавать второй файл того же класса вне `documentation/` для публичного канона.

Процедурный канон самой **роли** документатора (чеклисты, стиль) может храниться **только** в закрытом наборе документов команды — он не дублирует содержание `PRODUCT_KNOWLEDGE_BASE.md`.

## Обязательный чек-лист по роутерам (не писать «на глаз»)

Любое описание возможностей продукта, которое опирается на HTTP API, экраны админки/PWA или права, **сначала** проходит по процессу в **[SCRIBE_ROUTER_CHECKLIST.md](./SCRIBE_ROUTER_CHECKLIST.md)**.

Кратко:

1. **Порядок** — строго как `include_router` в `src/api/v1/router.py` (78 модулей); именованный список продублирован в чек-листе.
2. **Для каждого модуля** открыть соответствующий раздел в **[router_surface/INDEX.md](./router_surface/INDEX.md)** (автогенерация): файл роутера, prefix, таблица путей, импорты метрик, pytest-файлы.
3. **Кросс-домены** — Kanban/задачи, чаты (омни / пациент / staff / admin chat), календарь, оплаты: сверять **[FEATURE_KANBAN_AND_TASKS.md](./FEATURE_KANBAN_AND_TASKS.md)**, **[FEATURE_CHATS_OMNI_PATIENT_STAFF.md](./FEATURE_CHATS_OMNI_PATIENT_STAFF.md)**, **[FEATURE_CALENDAR_SCHEDULE.md](./FEATURE_CALENDAR_SCHEDULE.md)**, **[FEATURE_PAYMENTS_FINANCE.md](./FEATURE_PAYMENTS_FINANCE.md)**.
4. **Тесты** — не утверждать покрытие без проверки; отправная точка **[TESTING_SURFACE.md](./TESTING_SURFACE.md)** и списки в INDEX.
5. После правок в `src/api/v1/routers/` или `router.py` — выполнить `python scripts/generate_router_surface_docs.py` и закоммитить обновлённый `documentation/router_surface/INDEX.md`.

**Запрещено:** добавлять в `USER_DOCS` или в питч новые «фичи» без прохождения чек-листа для всех роутеров, от которых сценарий зависит.
