## 1. Назначение

`/admin/tasks` — единый production-канбан исполнения задач клиники:

- поток задач по стадиям (ручные + AI + системные);
- контроль нагрузки команды (WIP);
- контроль времени (SLA/Aging);
- управляемые переходы (workflow rules);
- прозрачный след изменений (audit trail).

---

## 2. UI и взаимодействие

### 2.1. Layout

- Единый канбан без бокового контекста, с жестким выравниванием колонок.
- Отдельный компактный фильтр/свимлейн: **«Ждут моего подтверждения»**.
- Быстрые фильтры: исполнитель, приоритет, срок (`все/сегодня/просрочено`).
- Bulk-панель: массовая смена статуса для выбранных карточек.

### 2.2. Карточка задачи

- Поля: title, приоритет, срок, исполнитель, AI-mark (если применимо).
- Состояния:
  - `blocked` (визуально + бейдж + причина в деталях);
  - `overdue` (SLA просрочено);
  - `aging` (долго в работе, по порогу).
- Контролы:
  - drag-handle для мыши;
  - checkbox для bulk;
  - клавиатурный перенос `Alt+ArrowLeft/Right`.

### 2.3. Колонки и статусы

- Базовые статусы: `open`, `in_progress`, `on_hold`, `review`, `done`, `cancelled`.
- Дополнительные статусы из API поддерживаются динамически.
- Для каждой колонки отображаются:
  - счетчик задач;
  - WIP (`текущее/лимит`, если лимит задан);
  - SLA overdue;
  - Aging 48h+.

### 2.4. Модалки/детали

- Центрированные модалки (`GlassModal`) как единый стандарт оболочки.
- В деталях задачи обязательны workflow-контролы:
  - `blocked / blocked_reason`;
  - `done checklist` (подтверждение критериев завершения).

## 3. Kanban Hardening Pack (обязательный минимум)

### 3.1. WIP-лимиты

- Лимиты задаются по колонкам.
- При превышении:
  - колонка выделяется как перегруженная;
  - перенос новых карточек в колонку блокируется (кроме внутренних перестановок).

### 3.2. Сортировка внутри колонки

- Поддерживается drag-drop на позицию внутри колонки.
- Порядок карточек хранится как rank-map на фронте (локально) до появления серверного `rank/order` контракта.

### 3.3. Правила переходов

- Переход в `done` разрешен только если:
  - отмечен checklist завершения;
  - задача не в `blocked`.
- Нарушение правил показывает понятное сообщение и отменяет переход.

### 3.4. SLA / Aging

- SLA overdue: просрочка по `due_at`.
- Aging: превышение порога длительности жизненного цикла задачи (например, 48h+ от `created_at`).
- Метрики показываются на уровне колонки.

### 3.5. Blocked state

- Задача может быть заблокирована вручную.
- Для blocked хранится причина (`blocked_reason`).
- blocked-задачи нельзя закрывать в `done`.

### 3.6. Bulk и быстрые фильтры

- Bulk: выбрать несколько карточек и массово применить статус.
- Быстрые фильтры обязательны на уровне страницы:
  - assignee;
  - priority;
  - due segment.

### 3.7. Audit trail

- Любое перемещение между статусами фиксируется в журнале:
  - `task`, `from`, `to`, `timestamp`.
- Пока отсутствует backend-аудит endpoint — журнал хранится в UI-сессии.

### 3.8. Keyboard accessibility

- Доступность без мыши обязательна:
  - фокус на карточке;
  - перевод между соседними колонками по hotkeys.

## 4. API-контракт и текущие ограничения

### 4.1. Используемые endpoints

- `GET /v1/admin/tasks`
- `POST /v1/admin/tasks`
- `PATCH /v1/admin/tasks/{id}` (status)
- `POST /v1/admin/tasks/{id}/claim`
- `GET/POST /v1/admin/tasks/{id}/comments`

### 4.2. Временная фронтовая компенсация до backend-расширения

- `rank/order`, `blocked`, `blocked_reason`, расширенный workflow-аудит пока не закреплены в API.
- До фиксации backend-контракта используется UI-local storage/session для:
  - порядка карточек;
  - blocked/checklist состояния;
  - audit-ленты.

## 6. Критерии приемки

- Канбан выровнен, карточки не «лесенкой».
- Все модалки задач открываются по центру.
- Кнопки/действия в модалках всегда доступны по скроллу.
- DnD работает между всеми этапами и внутри этапа.
- Переходы в `done` валидируются правилами.
- WIP/SLA/Aging/Blocked/Bulk/Audit/Keyboard работают без регрессий.
