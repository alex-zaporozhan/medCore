АРХИТЕКТУРА И ПРИНЯТЫЕ РЕШЕНИЯ
==============================

МОДУЛЬНЫЙ МОНОЛИТ И СЛОИ
-------------------------

Один основной backend-процесс и отдельные процессы фоновых воркеров и планировщика. Зависимости направлены от HTTP-границы к домену; инфраструктурный код реализует контракты домена и не протекает в обратную сторону.

  Слой              Роль
  ----------------  ----------------------------------------------------------------------------------------------------------------------------------------
  HTTP / API        Маршруты версии API, внедрение зависимостей, проверка прав, маппинг в DTO. Порядка девяноста модулей маршрутов по зонам:
                    администратор клиники, пациент, публичный контур, платформа, владелец сети.

  Application       Бизнес-правила, оркестрация сценариев, публикация доменных событий. Порядка семидесяти сервисных модулей плюс
                    вспомогательные компоненты: блокировки, движки расчётов, кэширование.

  Domain            Модель данных ORM и абстракции репозиториев. Порядка ста шестидесяти сущностей.

  Infrastructure    Реализации репозиториев, задачи очереди, клиенты внешних API, доступ к Redis и объектному хранилищу, realtime.

Точка входа процесса связывает жизненный цикл приложения, middleware, метрики и подписку обработчиков на внутреннюю шину событий.


СОБЫТИЯ
-------

  • Внутрипроцессная шина — обработка побочных эффектов в том же runtime (CRM, финансы, лояльность, задачи,
    маркетинговая атрибуция). Не заменяет гарантированную доставку между процессами.

  • Transactional outbox — запись намерений в БД в одной транзакции с доменными изменениями и последующая
    надёжная доставка воркерами (вебхуки платежей, провижининг платформы). Управляется флагами окружения.


МУЛЬТИТЕНАНТНОСТЬ И ДОСТУП
--------------------------

  • Клиника — первичный тенант данных; идентификатор присутствует в сущностях и в токенах административного контура.

  • Организация (сеть) — уровень холдинга; биллинг, каталог тарифов и entitlements завязаны на организацию.

  • RBAC — единая матрица атомарных прав (порядка полусотни кодов) и ролей; изменения сопровождаются миграциями данных
    и регрессионными проверками соответствия HTTP-операций матрице.

  • Ответы при отсутствии прав — в части сценариев используется сокрытие ресурсов (например 404 вместо 403),
    чтобы не раскрывать идентификаторы чужих тенантов.


ИДЕНТИЧНОСТЬ
------------

Три контура JWT (HS256) с разными наборами claims, временем жизни и секретами:

  • администратор клиники;
  • пациент;
  • высокопривилегированная роль платформы с отдельным секретом в продакшене и проверками на старте.

Issuer и audience для тенантных токенов настраиваются конфигурацией.


ПЛАТЕЖИ И ВЕБХУКИ
-----------------

  • Раздельные секреты и политики для пациентских платежей и для биллинга платформы.

  • На старте в production проверяется непересечение секретов и соблюдение минимальных политик для вебхуков.


КОНКУРЕНТНОСТЬ В РАСПИСАНИИ
---------------------------

Запись в один слот врача сериализуется advisory lock в PostgreSQL по ключу из даты, времени и врача. Отдельный
advisory-контур для тяжёлого пересчёта финансовых агрегатов, чтобы не блокировать операционную запись.


ОТЧЁТНОСТЬ И НАГРУЗКА НА БД
----------------------------

  • Опциональная read replica для тяжёлых чтений с отдельным таймаутом операторов SQL.

  • Кэш агрегированных JSON для ERP-панели в Redis с настраиваемым TTL.


КЛИЕНТСКОЕ ПРИЛОЖЕНИЕ
---------------------

Один production-бандл SPA покрывает все зоны продукта. Запросы к API идут под общим префиксом; в режиме разработки
проксируются на backend.


МАСШТАБИРОВАНИЕ
---------------

  • Горизонтальное масштабирование API при общем Redis и идемпотентных вебхуках и outbox.

  • Независимое масштабирование воркеров очереди.

  • Реплика для чтения и лимиты времени на reporting-сессиях.

  • Точечный вынос bounded context в отдельный сервис возможен; границы фиксируются в архитектурных записях о коммерции
    и смежных областях.


НАБЛЮДАЕМОСТЬ
-------------

Десятки серий метрик на эндпоинте Prometheus; десятки правил алертинга; несколько готовых дашбордов Grafana
с провижинингом источников данных.


ПЛАНИРОВАНИЕ И ДОРОЖНЫЕ КАРТЫ
-----------------------------

Исторические пакеты доменного проектирования и волн QA сохранены как архив намерений и не определяют поведение
системы в поставке; приоритет у кода и актуальных архитектурных записей внутри репозитория.
