ОБЕСПЕЧЕНИЕ КАЧЕСТВА И ТЕСТИРОВАНИЕ
====================================


ИНСТРУМЕНТЫ
-----------

  • pytest с асинхронным режимом и сессионным циклом событий для стабильности больших наборов.

  • В процессе — HTTP-тесты против ASGI-приложения без отдельного серверного процесса для основной массы API.

  • Playwright — браузерные сценарии критичных пользовательских потоков; в CI поднимается production-сборка frontend и при
    необходимости отдельный процесс API за прокси preview.

  • Лимит времени на тест — предотвращение зависаний на долгих SSE, блокировках и сетевых таймаутах; длительная инициализация
    сессии БД не обрезается тем же лимитом.

ЖИЗНЕННЫЙ ЦИКЛ ДАННЫХ В ТЕСТАХ
------------------------------

  1. Режим тестирования откладывает инициализацию пула БД до фикстуры сессии.

  2. Задаётся DSN тестовой базы; при отсутствии — явный отказ с понятным сообщением.

  3. Однократно на сессию накатывается схема миграциями до последней ревизии.

  4. Очистка всех таблиц с каскадом только если имя базы содержит признак тестового контура; при необходимости принудительно
     завершаются чужие сессии на этой базе.

  5. Сидирование минимальной клиники: врач, услуга, пациент, финансовые дефолты, две роли администратора (владелец с полным
     набором прав и врач с ограниченным), учётная запись платформенной роли, восстановление строк каталога SaaS после очистки.

  6. HTTP-клиент создаётся на приложении с контролируемым поведением при необработанных исключениях внутри стека.

Вспомогательные сценарии: логин администратора, врача, пациента через одноразовый код из Redis, логин платформенной роли,
прямой доступ к сессии ORM для сервисных тестов.


МАРКЕРЫ И ВОРОТА
----------------

  • Критический путь — короткий набор для merge-gate; в строгом CI отсутствие браузера или БД приводит к падению job, а не к
    молчаливому пропуску.

  • Регрессия платежей, персональных данных, чатов — тематические подмножества для выборочного прогона.

  • Безопасность — явная маркировка чувствительных сценариев.

  • Интеграция с Redis — пропуск, если брокер недоступен или отключён флагом.

Отчёт JUnit для ворот критического пути проверяется скриптом: ноль пропусков, ноль ошибок и сбоев, хотя бы один успешный тест.


СОГЛАСОВАННОСТЬ RBAC
--------------------

Канон прав живёт в одном модуле матрицы. При изменении прав или маршрутов поддерживается синхронизация: автоматическая сверка
инвентаря эндпоинтов с матрицей и регрессионный тест, не допускающий расхождений.


ТИПОВЫЕ РИСКИ ЛОКАЛЬНОГО ПРОГОНА
--------------------------------

  • Исчерпание пула соединений PostgreSQL при параллельном запуске API и полного набора тестов на один инстанс — снизить
    параллелизм или поднять лимит соединений.

  • Блокировка очистки таблиц из-за открытой сессии вне pytest — закрыть сторонние клиенты к тестовой базе.

  • На Windows — выбор политики event loop для совместимости Playwright и asyncio.


ЦЕННОСТЬ ДЛЯ ЗАКАЗЧИКА
----------------------

Автоматизированный контур закрывает: контракт API и права доступа, финансовые и платёжные ветки, изоляцию мультитенантности,
устойчивость фоновой доставки, публичный UI-критический путь, статические артефакты мониторинга. Объём и слойность тестов
отражают зрелость продукта как коммерческого SaaS для стоматологических сетей и одиночных клиник.
