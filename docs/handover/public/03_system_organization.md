# Организация системы по смыслу

Описание без привязки к дереву файлов: как смысловые части складываются в целостный продукт.

## Поверхность API

Версионированный REST-слой сгруппирован по ролям вызывающей стороны. Публичные маршруты отделены от аутентифицированных; платформенные операции изолированы от клинического админа. Общие зависимости: сессия БД, контекст тенанта, проверка матрицы прав, ограничение частоты запросов.

## Прикладная логика

Сервисы инкапсулируют сценарии: запись на приём, расписание, CRM и воронка, задачи и канбан, документооборот, лояльность, маркетинг и атрибуция, omnichannel и AI-ассистенты, склад и касса, зарплаты, отчётность ERP, настройки клиники и сети, биллинг SaaS. DTO отделяют контракт API от внутренних структур. События публикуются в шину и в outbox там, где нужна гарантия после коммита.

## Модель данных и доступ

Сущности отражают мультитенантность (клиника, организация), финансовые и медицинские сущности, коммуникации, каталог услуг и прайс, платформенный каталог продуктов и entitlements. Репозитории инкапсулируют SQL; интерфейсы позволяют подменять реализацию в тестах.

## Интеграции и фон

Клиенты внешних API изолированы в инфраструктурном слое. Задачи очереди выполняют длительные операции, ретраи outbox, уведомления и сверки. Хранилище файлов — пресайны и загрузки через S3-совместимый API.

## Клиентское приложение

Маршрутизация по зонам продукта; общий клиент HTTP; хуки для доменной логики UI. Сборка оптимизирована под PWA и разделение чанков по зонам навигации.

## Автоматизация поставки

Контейнеры backend и frontend; compose-стек для полного контура на одной машине; отдельный шаг миграций перед подъёмом приложения. Скрипты и workflow CI описывают прогон тестов, аудит зависимостей, публикацию образов и альтернативный корпоративный pipeline.

## Документация и решения

Внутренние ADR фиксируют контракты вебхуков, outbox, реплики для отчётов, политики резервного копирования и др. Продуктовые обзоры описывают состояние возможностей относительно кода.

## Трассировка сценария «от запроса к данным»

1. HTTP-обработчик проверяет аутентификацию и права.
2. Сервис оркестрирует транзакцию, доменные правила и побочные эффекты.
3. Репозиторий выполняет запросы к PostgreSQL.
4. При необходимости публикуется событие или запись outbox; воркер доводит асинхронную часть до конца.
