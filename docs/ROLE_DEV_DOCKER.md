## ROLE_DEV: протокол по Docker и инфраструктуре

Этот документ — «правильные мозги» @DEV для работы с Docker, Dockerfile, docker‑compose и деплоем через реестр. Он дополняет общие правила из `DOCKER_DEPLOY_PROTOCOL.md` и применим не только к текущему проекту.

---

### 1. Общие принципы

- **Образы собираются в CI, а не на проде.**
  - Продакшен‑серверы по умолчанию только тянут и запускают образы (`pull + up -d`), а не строят их.
- **Один источник истины для образа.**
  - Backend и frontend имеют закреплённые имена образов и тегов; менять их можно только осознанно и консистентно (Docker Hub + compose + CI).
- **Никаких секретов в образах и Git.**
  - Пароли/токены не прошиваются в Dockerfile и не коммитятся в репозиторий.
  - Всё чувствительное — через переменные окружения, `.env` (локально) и secrets (CI/CD).
- **Минимальные, воспроизводимые образы.**
  - Меньше слоёв, фиксированные базовые образы, понятная команда запуска.

---

### 2. Dockerfile: безопасный и предсказуемый

Когда @DEV создаёт или правит Dockerfile, он следует таким правилам:

1. **Выбор базы**
   - Использовать официальные образы (например, `python:3.11-slim`, `node:20-alpine`, `nginx:alpine`).
   - По возможности пиновать мажор/минор версию, а не просто `latest`.

2. **Слои и кэш**
   - Отдельный слой для зависимостей:
     - backend: `COPY requirements.txt .` → `RUN pip install ...`
     - frontend: `COPY package*.json` → `RUN npm ci`
   - Затем `COPY . .` и команды сборки; это ускоряет rebuild при мелких изменениях кода.

3. **Multi‑stage build**
   - Первый этап: сборка (npm build, компиляция).
   - Второй этап: минимальный runtime (nginx, slim‑python и т.п.) с копированием только артефактов (`dist`, `app/`, бинарники).

4. **Без секретов и конфигов продакшена**
   - Не копировать `.env` в образ.
   - Не прописывать пароли/URL прямо в `ENV` внутри Dockerfile.

5. **Пониженные привилегии (когда возможно)**
   - Не запускать приложение под `root`, если это не требуется (создать пользователя и `USER appuser`).

6. **Порт и команда запуска**
   - Явно указывать `EXPOSE` для внутреннего порта.
   - Использовать один прозрачный `CMD` или `ENTRYPOINT`, без сложных shell‑конструкций.

---

### 3. docker-compose: контракт для окружения

Подход @DEV к `docker-compose.yml`:

1. **Каждый сервис — отдельный контейнер**
   - `backend`, `frontend`, `db`, дополнительные воркеры и т.п.

2. **Имя образа + (опционально) сборка**
   - Продакшен‑compose:
     - всегда указывает `image: <registry>/<repo>:<tag>`;
     - `build:` может остаться для локальной разработки, но деплой в прод опирается на образы из реестра.

3. **Порты**
   - Формат `ВНЕШНИЙ:ВНУТРЕННИЙ`.
   - Внутренний порт должен совпадать с `EXPOSE` и реальным портом приложения.
   - Внешние порты согласованы с nginx/инфраструктурой.

4. **Переменные окружения**
   - Для базы: `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`.
   - Для приложения: `DATABASE_URL`, `ALLOWED_ORIGINS`, `SECRET_KEY` и т.п.
   - Чувствительные значения можно вынести в `.env` рядом с compose и подключать через `env_file`, если это согласовано с @LEAD.

5. **Устойчивость**
   - Для критичных сервисов: `restart: unless-stopped` или аналог.
   - `depends_on` и healthchecks для корректного старта (например, backend ждёт, пока `db` станет `healthy`).

6. **Сетевые настройки и тома**
   - Использовать named volumes для данных БД.
   - При необходимости — отдельные сети, чтобы не светить базу наружу.

---

### 4. .env и секреты

@DEV придерживается следующего протокола:

- В репозитории:
  - только `.env.example` с фейковыми значениями и комментариями.
  - `.env` добавлен в `.gitignore`, если не оговорено иначе.
- В CI (GitHub Actions):
  - все реальные секреты (`DOCKERHUB_TOKEN`, токены к внешним сервисам) хранятся в **Secrets**.
- На VPS:
  - секреты передаются либо через `docker-compose.yml` (как сейчас), либо через `.env` на сервере, который не коммитится.

---

### 5. Деплой через реестр

Когда @DEV настраивает деплой, он стремится к схеме:

1. **CI**:
   - собирает образы (`docker build` / `docker/build-push-action`);
   - пушит в реестр (Docker Hub, GHCR) под фиксированными тегами;
   - **пересобирает только те образы, которые реально затронуты изменениями в коде**:
     - если изменились файлы в `backend/**` — пересобирается только backend‑образ;
     - если изменились файлы в `frontend/**` — пересобирается только frontend‑образ;
     - если менялись только доки/инфраструктурные файлы вне этих папок — шаги сборки можно пропустить.
2. **Сервер**:
   - `docker login` под сервисным аккаунтом;
   - `docker compose pull`;
   - `docker compose up -d`.

Prod‑сервер не должен зависеть от локальных билдов разработчика.

---

### 6. Как @DEV использует этот протокол в проекте

- Перед созданием/изменением Dockerfile или `docker-compose.yml`:
  - перечитывает этот файл и `DOCKER_DEPLOY_PROTOCOL.md`;
  - проверяет, что новая схема не нарушает:
    - единый реестр образов;
    - отсутствие секретов в коде;
    - предсказуемые теги образов.
- При сомнениях:
  - фиксирует предложение в Markdown (новый протокол/изменения);
  - согласует с @LEAD / @ARCH;
  - только потом меняет конфигурацию.
