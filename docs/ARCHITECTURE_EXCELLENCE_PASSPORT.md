# ARCHITECTURE_EXCELLENCE_PASSPORT — паспорт целевой архитектуры (10/10)

> **Роли:** @ARCH (проектирование и инварианты) · @QA_ARCH (доказательства, риски, DoD) · @LEAD (приоритет и приёмка).  
> **Назначение:** единый **универсальный** ориентир **нефункциональной** зрелости: безопасность, износостойкость, мультитенантность, эксплуатация, дисциплина поставки.  
> **Паспорт vs факты проекта:** здесь — нормы и чеклисты для любого продукта; **конкретные KPI, baseline и цели** конкретной команды ведите в `docs/NONFUNCTIONAL_SCORECARD.md` (или эквиваленте по конвенции репозитория).

**Как пользоваться:** @ARCH сверяет новые решения с разделами **3.1, 4–12, 15** до фиксации в `docs/artifacts/ARCH_*.md`. @QA_ARCH использует **§3 (включая 3.1), §13–§15** и чеклист **§14** как расширение к `.cursorrules` и DOMAIN_STANDARDS.

## 1. Зачем этот документ

**Проблема без единого языка:** NFR и «коммерческая зрелость» легко трактовать по-разному, если критерии размазаны по чату и старым заметкам.

**Риск расхождения ожиданий и факта:** фактическая дисциплина поставки (CI, образы, миграции) меняется со временем — её нужно сверять с **`docs/DOCKER_INFRA_PASSPORT.md`**, **`docs/MIGRATION_UPGRADE.md`** и актуальным workflow в `.github/workflows/`, а не с устаревшими допущениями.

Этот паспорт **фиксирует критерии целевой зрелости (ориентир 10/10)** и **матрицу упущений**, чтобы @ARCH и @QA_ARCH проверяли одну и ту же плоскость; измеримые цели команды — в `docs/NONFUNCTIONAL_SCORECARD.md`.

## 4. База данных и модель данных (10/10)

**Мультитенантность**

- Каждая бизнес-сущность с изоляцией по клинике/арендатору: явный `clinic_id` / `tenant_id`, составные индексы `(tenant_id, …)`.
- Запрет «забыть фильтр»: критичные read/write проходят через слой, где tenant обязателен (конвенция в коде + негативные тесты).

**Целостность**

- Уникальные и частичные индексы там, где бизнес-инвариант (слоты, идемпотентность, «одна активная запись»).
- Внешние ключи и каскады осознанны; soft delete не ломает ссылочную целостность (или явная политика «архив»).

**Миграции**

- Правило **expand → deploy → contract**: сначала добавляем nullable/новые колонки и dual-read, потом переключаем код, потом удаляем старое.
- Каждая миграция с осмысленным `downgrade`; деструктивные шаги — отдельным релизом после выключения чтения старых полей.
- В идеале: **отдельный шаг** «alembic upgrade» в релизе, а не только «при старте контейнера» без контроля (для 10/10 — контролируемый job / runbook).

**Резерв и восстановление**

- Регулярный backup (логический/физический), **проверенный restore** (RPO/RTO задокументированы, drill зафиксирован).
- Шифрование бэкапов at rest — если требование среды/заказчика.

**Эволюция**

- Индексный аудит по топовым запросам; slow query budget; при росте — read-replica / партиционирование как осознанный ADR, не «случайно».

## 5. Транзакции, события, очереди (10/10)

**Синхронный путь**

- Явные границы транзакций для цепочек «бронь → оплата → завершение → побочные эффекты».
- `SELECT … FOR UPDATE` (или эквивалент) на конкурируемых ресурсах: слоты, кассы, списание пакетов, claim задач.

**Асинхронный путь**

- Паттерн **outbox / transactional outbox** (или эквивалент): запись в БД и постановка в очередь атомарны по смыслу; нет сценария «запись есть — события нет» без компенсации.
- **Идемпотентность** consumer’ов: `idempotency_key`, `source_event_id`, дедупликация.
- **Dead-letter / poison queue**: политика изоляции, ручной разбор, метрики.

**Celery**

- `autoretry_for`, лимиты попыток, классификация ошибок (transient vs permanent).
- Метрики: lag, age задач, retry rate, финальные провалы.

**Деньги, аудит, согласованность**

- Цепочки с движением денег / касс / пакетов: где возможно — **сверка** (reporting vs операционные таблицы) или периодическая reconciliation-job; расхождения — алерт.
- **Неизменяемый или append-only след** для чувствительных админских действий (кто, когда, что; хранение достаточное для расследования и комплаенса — уровень фиксирует @LEAD).

**Отчётные витрины (предагрегаты ERP) — ориентир для 8.5+**

- **Переносимый канон (NFR, слои, PK, паритет, DoD, маппинг на scorecard):** `docs/TEMPLATE_ERP_REPORTING_VITRINES.md` — использовать в любом проекте; не привязан к артефактам `docs/artifacts/`.
- **Реализация в этом репозитории** (таблицы, эпик 026, таски, связь с Engine L2): `docs/artifacts/ARCH_DEV_ERP_VITRINES_026.md`, `docs/artifacts/ARCH_DEV_ERP_VITRINES_026_TASKS.md`; контекст L2 — `docs/artifacts/ARCH_PERF_ENGINE_L2_DEEP_2026.md` §6–8.
- **Инварианты:** не ослаблять tenant/RBAC; суммы в ответе API должны **согласовываться** с «сырым» эталоном при паритете или при умышленном fallback; **наблюдаемость** — lag, `empty_vitrine` / `stale_range`, логи fallback; **откат** — feature-flag / settings без миграции в emergency.
- **Нефункциональный контекст (черновик/аудит этого репо):** `docs/artifacts/NONFUNCTIONAL_AUDIT_NEXT.md` §5 (витрины), §5.2 (выборочная сверка), §6.1 (кардинальность метрик).
- **Плоскость UI** (что показывать пользователю при `aggregate_stale` и т.п.) — не здесь, а в `docs/TECH_PASSPORT_FRONTEND_UI_LOGIC.md` (раздел про владельческие отчёты).

## 6. Внешние интеграции и AI (10/10)

- Единая политика: **timeout, retry с backoff+jitter, circuit breaker** где уместно; не блокировать event loop бесконечными ожиданиями.
- Ошибки — в **едином envelope** (см. контракт в ARCH), без утечки стека наружу.
- **AI:** лимиты токенов/стоимости, fallback, логирование без сырого PII, метрики success/timeout/provider_error/retry.

---

## 7. Безопасность и мультитенантность (10/10)

- RBAC-матрица + **негативные** тесты на запрещённые действия.
- **Cross-tenant** тесты: нельзя получить чужие данные ни через API, ни через job, ни через «утечку» в join.
- Webhook’и (платежи, мессенджеры): подпись, защита от replay, идемпотентность обработки.
- Supply chain: скан зависимостей и образов; секреты только из секрет-хранилища; ротация.
- Security headers, CORS, CSRF — по профилю админки/PWA (ADR).
- **Привилегированный доступ** (support / «войти от имени»): только с явной политикой, TTL, двухфактором по регламенту и **полным аудитом**; без «тихих» обходов tenant.
- **Злоупотребления:** базовый контур — rate limit, бот-защита на публичных формах, учёт подозрительных паттернов (ADR при росте угроз).

## 8. Наблюдаемость и эксплуатация (10/10)

- Структурированные логи: `trace_id`, `clinic_id`, актор, операция, результат; маскирование PII.
- Метрики Prometheus + **алерты**: error budget, lag очередей, saturation БД/Redis, внешние зависимости.
- Распределённая трассировка (OpenTelemetry) на критичных цепочках — целевое состояние 10/10.
- Runbook’и: P1/P2, эскалация, **game day** (отказ Redis, БД, AI).
- **Каталог сервисов и зависимостей** (кто от кого зависит: БД, Redis, провайдер AI, платёжка, мессенджеры) — чтобы за время инцидента не выяснять архитектуру с нуля.

---

## 9. Производительность и ёмкость (10/10)

- Baseline p50/p95/p99 по **согласованному** списку API; отдельно read / write / AI.
- Нагрузочные сценарии (k6/Locust и т.д.) + **регрессионный** порог (хотя бы nightly).
- Профиль пулов соединений, concurrency воркеров, память Redis; план деградации при перегрузке.

---

## 10. CI/CD и дисциплина поставки (10/10)

- **PR / main:** линт + тесты backend, сборка + тесты frontend; блокировка при критичных находках SCA/secret scan.
- Образы: тег **`git sha`** (обязательно), политика для `latest`.
- Нет «релиза без тестов в CI»; нестабильные тесты = дефект процесса.
- CD: хотя бы **staging** с smoke + ручной gate на prod (или полная автоматизация — ADR).

---

## 11. Frontend и контракт с API (10/10)

- Четыре состояния UI (Loading / Empty / Error / Success) на всех пользовательских списках.
- Контракт ошибок и типов согласован с backend; при смене API — версия или feature-flag + период совместимости (ADR).
- **Доступность (a11y):** целевой уровень (например WCAG 2.1 AA для ключевых потоков) задаётся в ADR; критичные действия — с клавиатуры, видимый фокус, осмысленные подписи.
- **Клиентская матрица:** какие браузеры/режимы официально поддерживаются (и что считается best-effort) — зафиксировано, чтобы @QA_ARCH не спорил с ветром.

## 12. Что часто упускают даже в хороших дорожных картах (добавление к архивным документам)

| Тема | Зачем |
|------|--------|
| **Реестр ADR** | Решения не теряются в чатах; связь «почему так в БД». |
| **Политика версионирования и deprecation API** | Как объявляем поломку, сроки, совместимость клиентов. |
| **Feature flags / kill switch** | Быстро гасить рискованные ветки без отката схемы. |
| **FinOps / лимиты AI** | Стоимость и токены как управляемый бюджет, не сюрприз. |
| **Право на удаление / анонимизация (GDPR-подобное)** | Процедуры и технические хуки, если PII в системе. |
| **Контрактные тесты API** | Схема ответов не «плывёт» молча между сервисами/клиентом. |
| **Версионирование расширений БД** | pg_trgm и др. — зафиксированы в миграциях/доке. |
| **Единый rate limiting** | На публичных и чувствительных ручках. |
| **Доказательства, а не намерения** | KPI и drill хранятся рядом с кодом (отчёты, артефакты QA). |
| **SLO vs внешний SLA** | Внутренние бюджеты ошибок ≠ обещания клиенту; развести в документации. |
| **Политика обновления зависимостей** | Renovate/Dependabot, pinning, лицензии — без «никогда не обновляем». |
| **Локализация и часовые пояса** | Если продукт мультиязычный/мультирегиональный — единый контракт дат (UTC+IANA). |
| **Периодический pen-test / security review** | Хотя бы регламент под коммерческий контур. |

## 15. Доказательства качества: тесты и регрессия (10/10)

- **Пирамида:** unit на доменную логику; integration на БД/транзакции/репозитории; e2e или контрактные тесты на критичные user journeys (запись, оплата, завершение визита — по профилю продукта).
- **Критичные инварианты** (double-booking, идемпотентность webhook, tenant isolation) — покрыты **автотестами**, а не только ручной регрессией.
- **Контракт API** (OpenAPI/схемы + проверка в CI или consumer-driven) — согласован с фронтом.
- **Flaky tests:** политика нулевой терпимости к постоянно падающим тестам; карантин только с владельцем и сроком.
- **Тестовые данные и изоляция:** нет случайного запуска интеграционных тестов против прод-БД.
