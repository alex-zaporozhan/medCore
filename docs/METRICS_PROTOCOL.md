# 📊 METRICS_PROTOCOL — Контроль грамотности метрик

> **Назначение:** единый протокол проверки того, что метрики в системе не просто существуют, но считают именно то, что должны считать — корректно, согласованно и доказуемо.  
> **Не дублирует:** `ARCHITECTURE_EXCELLENCE_PASSPORT.md` (нормы зрелости) и `NONFUNCTIONAL_SCORECARD.md` (целевые KPI). Этот документ — **как проверить**, а не **что должно быть**.

**Роли и зоны ответственности:**

| Роль | Зона |
|------|------|
| @PRINCIPLE | Корректность определения метрики до кода: grain, формула, временные границы |
| @QA_ARCH | Корректность реализации: инструментация, согласованность UI и бэкенда, отсутствие двойного учёта |
| @ARCH | Архитектура сбора: где и как метрика пишется, какой стек наблюдаемости; контроль кардинальности и схем событий |
| @LEAD | Приоритизация: какие метрики критичны для текущего этапа продукта |

---

## 1. ЧЕТЫРЕ СЛОЯ МЕТРИК

Каждый слой имеет свои риски и свой протокол проверки.

### Слой 1 — Бизнес-метрики (Business KPIs)
**Что это:** показатели результата бизнеса. Выручка, конверсия, LTV, churn, NPS.  
**Кто владеет:** @BIZ формулирует, @ARCH проектирует источник данных, @PRINCIPLE проверяет формулу.  
**Главный риск:** метрика посчитана, но считает не то — например «выручка» включает отменённые платежи.

### Слой 2 — Продуктовые метрики (Product Events)
**Что это:** события внутри продукта. Количество броней, статусы задач, использование функций, воронки.  
**Кто владеет:** @ARCH проектирует event schema, @DEV инструментирует, @QA_ARCH проверяет.  
**Главный риск:** событие пишется в неверный момент (до commit, а не после), или дублируется при retry.

### Слой 3 — Технические метрики (Observability)
**Что это:** latency, error rate, availability, queue lag, DB connections.  
**Кто владеет:** @ARCH выбирает стек (Prometheus/OTel), @DEV инструментирует, @OPS настраивает алерты.  
**Главный риск:** метрика есть, но алерт настроен неверно или порог не согласован с SLO; либо взрыв кардинальности ломает сбор или стоимость.

### Слой 4 — Метрики качества данных (Data Quality)
**Что это:** согласованность витрин с операционными таблицами, отсутствие «потерянных» записей, корректность агрегатов.  
**Кто владеет:** @PRINCIPLE проверяет до кода, @QA_ARCH проверяет в реализации.  
**Главный риск:** отчёт и операционный экран показывают разные числа для одного периода.

## 2. ПРОТОКОЛ ОПРЕДЕЛЕНИЯ МЕТРИКИ (до кода)

Запускается @PRINCIPLE при наличии Gate G4 (агрегат / отчёт / KPI).  
Чеклист §2.2 и карточка §2.1 должны быть выполнены **до merge кода**, который пишет метрику или строит отчёт. Карточка может появиться раньше финального `ARCH_*.md` (например в `PRINCIPLE_FINDINGS_*.md` или ADR) — см. §2.4.

### 2.1. Карточка метрики (обязательный артефакт)

Для каждой метрики — одна карточка. Без заполненной карточки метрика не идёт в разработку.

```markdown
## МЕТРИКА: [Название]

**Слой:** [Бизнес / Продукт / Технический / Данные]
**Владелец:** [роль или модуль]
**ID реестра:** [M-XX — после выделения строки в METRICS_REGISTRY.md]

**Определение:**
- Что считаем: [существительное — что именно является единицей подсчёта]
- Условие включения: [какие записи попадают в числитель]
- Условие исключения: [что явно не считается — отменённые, soft-deleted, тестовые]
- Знаменатель (если дробная): [что в основании]

**Временные границы:**
- Период: [день / неделя / месяц / произвольный диапазон]
- Граница: [[start, end) или включительно с обеих сторон]
- Таймзона: [UTC / локаль тенанта — и где конвертация]

**Источник данных:**
- Таблица(ы): [список]
- Grain строки источника: [одна строка = что]
- JOIN'ы: [если есть — риск умножения строк]
- Tenant-фильтр: [обязательный фильтр по clinic_id / tenant_id] **или** «глобальная метрика без tenant» + краткое обоснование

**Деньги (если применимо):**
- Валюта и правило конвертации (если несколько валют)
- Нетто / брутто, учёт налогов — что именно в числителе

**Приближённый подсчёт (если применимо):**
- Sampling, агрегаты OTel и т.п. — да/нет; сравнимость с OLTP-агрегатом (обычно «не сравнивать напрямую»)

**Техническая привязка (для слоёв Продукт / Технический):**
- Каноническое имя: [имя серии Prometheus / тип product event]
- Labels / поля события: [перечень]; **без PII и секретов** (см. §3.3) — или ссылка на ADR с исключением

**Согласованность:**
- Соответствует ли операционному экрану: [да / нет / частично — объяснение]
- При расхождении — источник правды: [операционный экран / витрина / оба синхронизированы]

**Инварианты:**
- [ИНВ-NN] формулировка — нарушение → эффект
```

### 2.2. Чеклист @PRINCIPLE перед передачей в @ARCH

- [ ] Определение не содержит слов «обычно», «как правило», «примерно» (кроме явно помеченного приближённого подсчёта в карточке)
- [ ] Условие включения и исключения явно перечислены (включая soft-deleted, отменённые, тестовые)
- [ ] Временные границы однозначны: тип границы зафиксирован
- [ ] Таймзона: либо всё в UTC, либо явное место конвертации — не «где-то в UI»
- [ ] Нет риска умножения строк при JOIN
- [ ] Для мультитенантных агрегатов tenant-фильтр обязателен; для глобальных метрик на карточке зафиксировано «без tenant» и обоснование
- [ ] Для метрик с деньгами: возвраты, сторно, частичные оплаты, валюта и нетто/брутто — учтены явно
- [ ] Метрика согласована с операционным экраном или расхождение задокументировано
- [ ] Для product events и полей аналитики: нет необоснованной передачи PII/секретов; отклонения только через ADR (§3.3)
- [ ] Для технических метрик: @ARCH подтвердил допустимую кардинальность набора labels (или зафиксирован план ограничения)

### 2.3. Реестр (M-XX), единственность смысла и привязка к коду

- **Одна бизнес- или продуктовая семантика** («броней создано за день», «выручка за период») → **одна строка** в `docs/artifacts/METRICS_REGISTRY.md` и **один** `M-XX`. Повторный отчёт с тем же смыслом расширяет ту же карточку/реестр, а не создаёт параллельное определение без ID.
- **Строка в реестре** выделяется до или вместе с карточкой; статус может быть 🟡 до прохождения Вектора 10.
- **В реализации обязательна трассировка к M-XX:** комментарий или константа рядом с инструментацией; в Grafana — `M-XX` в названии панели, описании или теге дашборда; в схеме события — поле документации или ссылка на карточку. Цель: по коду и дашборду найти единственное определение в реестре.
- **Изменение формулы или смысла** при том же «удобном» имени в коде — по §4.1 (часто новый `M-YY` или явная версия события).

### 2.4. Где хранится карточка

Допустимые места (в столбце «Карточка» реестра — путь и якорь):

- `docs/ARCH_*.md`
- `docs/PRINCIPLE_FINDINGS_*.md`
- `docs/adr/*.md` или иной ADR в репозитории

@QA_ARCH сверяет реализацию с карточкой по ссылке из реестра, а не только с `ARCH_*.md`.

## 3. ПРОТОКОЛ ПРОВЕРКИ РЕАЛИЗАЦИИ (после кода)

Запускается @QA_ARCH как **Вектор 10 — Metrics Integrity** (дополнение к 9 существующим векторам).

### 3.1. Вектор 10 — Metrics Integrity

**Применяется когда:** модуль содержит агрегаты, отчёты, дашборды, счётчики событий или технические метрики.

**Корректность подсчёта:**
- [ ] Метрика совпадает с карточкой (ссылка из `METRICS_REGISTRY.md`): условия включения/исключения соблюдены в запросе
- [ ] В реализации и дашборде указан или иначе однозначно прослеживается **M-XX** из реестра
- [ ] Временные границы реализованы точно как определены: `>=` и `<` или `<=` — по карточке
- [ ] Таймзона: конвертация в одном месте, не размазана между бэком и фронтом
- [ ] JOIN не умножает строки: есть GROUP BY или DISTINCT там где нужно
- [ ] Для таблиц со **soft delete** в схеме — явное исключение удалённых (`deleted_at IS NULL` или принятый эквивалент); для таблиц без soft delete пункт не применяется
- [ ] Для мультитенантных агрегатов tenant-фильтр в каждом запросе; для глобальных метрик — соответствие карточке «без tenant»

**Доказуемая согласованность слоёв:**
- [ ] Зафиксирован **набор для сверки:** тестовые tenant_id / период / ожидаемые числа (фикстура, скрипт или чеклист в PR)
- [ ] Число на дашборде совпадает с операционным экраном и/или эталонным SQL за тот же период — проверено на этом наборе
- [ ] Если витрина — проверена на соответствие raw-таблице за тот же период
- [ ] При наличии кэша — инвалидация происходит при изменении исходных данных

**Технические метрики:**
- [ ] Counter / histogram / gauge соответствуют типу метрики в карточке; для SLO по latency — согласованы тип (например histogram) и то, как из него читается квантиль / error budget (см. `NONFUNCTIONAL_SCORECARD` или ADR)
- [ ] Counter инкрементируется ровно один раз на событие (нет дублирования при retry)
- [ ] Событие пишется после успешного commit, не до
- [ ] Для метрик в разрезе тенанта — метка `tenant_id` / `clinic_id` в labels; для глобальных — на карточке зафиксировано отсутствие tenant
- [ ] Алерт настроен и порог согласован с NONFUNCTIONAL_SCORECARD или ADR

**Продуктовые события:**
- [ ] Event пишется в правильный момент жизненного цикла (не при создании формы, а при сохранении)
- [ ] Нет дублирования события при идемпотентном retry (ключ идемпотентности, dedup на стороне потребителя — по карточке)
- [ ] Event содержит достаточно контекста: tenant_id, actor_id, timestamp, entity_id (или эквивалент по карточке)
- [ ] Соблюдение §3.3 (PII, кардинальность полей)

### 3.2. Красные флаги метрик (автоматический 🔴)

- Метрика на экране и в отчёте расходятся для одного периода без задокументированной причины
- `COUNT(*)` без учёта soft delete **на таблице, где колонка soft delete предусмотрена схемой**
- Агрегат по деньгам без учёта возвратов, сторно или без явной валюты/нетто на карточке
- Дата фильтруется без учёта таймзоны
- JOIN без GROUP BY на таблице один-ко-многим
- Метрика пишется до `session.commit()` — данные могут не сохраниться, а счётчик уже увеличен
- Мультитенантный Counter / бизнес-агрегат без tenant-фильтра или без tenant label там, где они требуются карточкой
- Реализация или дашборд **без** привязки к `M-XX`, хотя метрика в реестре
- В labels Prometheus или в измерениях событий — **PII, сырой свободный текст, токены, секреты** без ADR
- Высококардинальные labels (например `user_id`, `email`, необbounded строки) без явного согласования @ARCH + @OPS

### 3.3. Наблюдаемость: PII и кардинальность

**PII и секреты:** в именах серий, labels и в payload product events не допускаются персональные данные, контактные поля, сырой пользовательский ввод, API-ключи и токены. Допустимы стабильные внутренние id (entity_id, tenant_id), перечисления и низкокардинальные классификаторы. Исключения только с оформленным ADR и оценкой риска.

**Кардинальность:** каждый новый набор labels / измерений события проходит оценку: ожидаемое число уникальных комбинаций, рост во времени. Запрещено добавлять в labels идентификаторы пользователей, заказов и т.п. как измерения по умолчанию. @ARCH согласует с @OPS до merge.

## 4. ПРОТОКОЛ РЕГУЛЯРНОГО АУДИТА

Метрики деградируют при изменении бизнес-логики. Триггеры обязательного пересмотра:

| Событие | Метрики для пересмотра |
|---------|----------------------|
| Добавлен новый статус сущности | Все агрегаты по этой сущности |
| Добавлен возврат / сторно / отмена | Все финансовые метрики |
| Изменена схема таблицы-источника | Все витрины и отчёты с этой таблицей |
| Добавлен новый тип тенанта или роли | Все метрики с tenant-фильтром |
| Изменена таймзона хранения | Все метрики с временными границами |

При срабатывании триггера: @LEAD вызывает @PRINCIPLE для ревизии карточек затронутых метрик.

### 4.1. Изменение определения, исторические ряды и backfill

Если **меняется смысл, фильтр, grain или формула** метрики:

1. Карточка и реестр обновляются; статус метрики — ⚠️ Устарела до завершения процедуры.
2. **Решение по идентичности ряда:**  
   - **Новая метрика** — новый `M-YY` (предпочтительно при несовместимости с прошлыми числами); старый `M-XX` помечается deprecated в реестре при необходимости.  
   - **Тот же M-XX** — только если определение уточняется без изменения смысла для прошлых периодов; иначе новый ID.
3. **Витрины и отчёты:** при исправлении ошибки в SQL/ETL — план backfill или явное ограничение «корректно с даты D» задокументированы в карточке или ADR.
4. **Дашборды и алерты:** обновляются в том же изменении или отдельной задаче со ссылкой на M-XX/M-YY; при разрыве ряда — подпись на дашборде или release note.

## 5. РЕЕСТР МЕТРИК ПРОЕКТА

Хранится в `docs/artifacts/METRICS_REGISTRY.md`. Создаётся @ARCH при первом появлении метрик, обновляется при каждом изменении. **Выделение нового `M-XX`** — без коллизий (следующий свободный номер); при сомнении согласовать с @ARCH.

**Структура:**

```markdown
# METRICS_REGISTRY — [Название проекта]
> Версия: [дата]

| ID | Название | Слой | Источник | Техн. имя / событие | Владелец | Статус | Карточка |
|----|----------|------|----------|---------------------|----------|--------|---------|
| M-01 | Выручка за период | Бизнес | finance_transactions | — / отчёт SQL | @BIZ | ✅ Проверена | ARCH_*.md §... |
| M-02 | Броней создано | Продукт | bookings | event `booking_created` | @DOMAIN | ✅ Проверена | PRINCIPLE_FINDINGS_*.md §... |
| M-03 | p95 latency /bookings | Технический | Prometheus | `http_request_duration_seconds` | @OPS | 🟡 Алерт не настроен | ARCH_*.md §... |
| M-04 | Активных тенантов | Бизнес | clinics | — | @BIZ | 🔴 Нет карточки | - |
```

**Статусы реестра:**
- ✅ Проверена — карточка есть, Вектор 10 пройден, согласована с операционным экраном (или расхождение задокументировано)
- 🟡 Частично — карточка есть, реализация не проверена или есть известный gap
- 🔴 Нет карточки — метрика используется без формального определения (блокер)
- ⚠️ Устарела — триггер ревизии сработал или смена определения по §4.1, требует пересмотра
- 🪦 Deprecated — метрика заменена другим M-YY; не использовать в новых дашбордах
