## GATE-2 — РАЗРАБОТКА ЗАВЕРШЕНА

**Когда проверяется:** после отчёта @DEV о выполнении всех to-dos в DEV_PROMPTS.

### Блокеры:
```
□ Все to-dos в DEV_PROMPTS отмечены ✅ в отчёте @DEV
□ Нет незакрытых TODO / заглушек без явного решения @LEAD «не делать»
□ Миграции применены, команды выполнены
□ Код не содержит «...», «# rest of code», неполных блоков
□ Все async-блоки имеют try/catch (не пустой)
□ invalidateQueries вызван после каждой мутации
□ Отчёт @DEV содержит: что сделано / что отложено / почему
```

### Симптомы галочки от @DEV (немедленный стоп):
- "Готово, осталось только..." → **не готово**
- Отчёт без перечисления всех to-dos с результатом → **не принимается**
- "Работает на моей машине" без указания команд → **не доказательство**
- Код с TODO без явного решения @LEAD → **блокер**

### Доказательство прохода:
Отчёт @DEV с пунктами 1:1 к DEV_PROMPTS, каждый ✅ или явно отложен с решением @LEAD.

### Реакция при провале:
@LEAD возвращает @DEV: «Продолжай to-dos. Следующий пункт: [N].» Без обсуждения.

- «Мелкие проблемы» не занесены в 🟡 секцию → **нарушение Zero Tolerance**

### Доказательство прохода:

## GATE-4 — КАЧЕСТВО И БЕЗОПАСНОСТЬ

**Когда проверяется:** после GATE-3 🟢.

### Блокеры @QA:
```
□ Критичные user journeys пройдены вручную (список зафиксирован)
□ P0 и P1 из QA_REPORT закрыты — проверено в коде, не со слов @DEV
□ Регрессионные сценарии: CI не зелёный при сломанном критичном пути
□ Тестовые данные изолированы от прода
```

### Блокеры @SEC:
```
□ Секреты: не в коде, не в логах, не в URL
□ RBAC: проверен на уровне API (не только UI)
□ PII: логи замаскированы, нет утечки в ответах
□ Supply chain: зависимости без critical CVE на релизной ветке
□ Rate limiting: на публичных и чувствительных ручках
□ IDOR: чужой tenant недоступен через прямой ID в URL/теле
```

### Симптомы галочки:
- @QA: «Протестировал» без списка сценариев → **не доказательство**
- @SEC: «В целом безопасно» без конкретных проверок → **не принимается**
- CI зелёный, но E2E на критичном пути не запускаются → **дыра**

### Доказательство прохода:
Артефакт @QA с перечнем сценариев + результат. Артефакт @SEC с конкретными пунктами и статусом каждого.

### Реакция при провале:
@LEAD блокирует деплой. Конкретный список P0 → @DEV. Повтор GATE-4 после закрытия.

## GATE-5 — ОПЕРАЦИОННАЯ ЗРЕЛОСТЬ

**Когда проверяется:** перед деплоем в прод / перед пилотом с клиентом.  
**Обязателен начиная с L2.** При L1 (внутренний пилот) — задокументированные риски достаточны.

### Блокеры:
```
□ Деплой воспроизводим: команды задокументированы, @OPS может повторить без разработчика
□ Образы тегированы git sha (не latest без привязки)
□ Backup настроен и restore проверен хотя бы один раз (RPO/RTO зафиксированы)
□ Runbook P1/P2 существует: что делать при падении, кто escalation owner
□ Метрики и алерты: error rate, latency, queue lag — мониторятся
□ Staging smoke прошёл перед прод-деплоем
□ Миграции: порядок выката задокументирован, rollback план есть
```

### Симптомы галочки:
- Runbook есть, но не проверен в drill → **намерение, не факт**
- Restore «настроен» без подтверждённого прогона → **не засчитывается**
- «Задеплоим и посмотрим» → **L0, блокер**

### Доказательство прохода:
Артефакт @OPS с командами деплоя + подтверждённый restore + runbook с named owner.

### Реакция при провале:
@LEAD фиксирует как L1 максимум. Деплой в прод заблокирован до закрытия пунктов.

## GATE-6 — КОММЕРЧЕСКАЯ ГОТОВНОСТЬ (L-ВЕРДИКТ) {#gate-6-commercial}

**Когда проверяется:** перед продажей / пилотом с клиентом / публичным анонсом / запросом «оцени зрелость» / «критический анализ».  
**Жёсткость:** выше стандартных подсказок @QA_ARCH: не смягчать формулировки, не оправдывать объёмом кода то, что не выдерживает прод.

### Мандат @LEAD

- **Цель:** ответить: *можно ли честно продавать и сопровождать продукт в реальной клинике / нагрузке / регуляторике*, а не «демо на ноутбуке».  
- **Не цель:** утешить команду, перечислить фичи ради списка, заменить аудит безопасности юридическим заключением.

### Принципы (жёстче обычного QA)

| Принцип | Смысл |
|---------|--------|
| **Факт, не намерение** | Учитывается только то, что **доказано** тестом, E2E, логом CI, артефактом прогона. «Скоро сделаем» = **не засчитывается**. |
| **Коммерция в центре** | Если разрыв бьёт по деньгам, репутации, данным пациента или SLA — это **P0** в отчёте, даже если «красиво в UI». |
| **E2E — не украшение** | Нет полного прохождения критичного user journey в автоматизации — значит **нет** доказательства готовности цепочки. |
| **Одна дыра не компенсируется** | «Зато тесты на математику» не закрывает отсутствие изоляции tenant на админском API. |
| **Явный вердикт** | В конце: **«к продаже/пилоту готов / не готов / только под NDA и ограничения»** с перечислением **блокеров**. |

### Метод разборки: шесть обязательных блоков отчёта

Отчёт @LEAD должен содержать **все** блоки ниже. Пропуск блока = нарушение протокола.

**3.1. Продукт и ценность** — какие критичные сценарии **обещаны** (roadmap, ТЗ) и что **фактически** работает end-to-end; где **обман ожидания** (UI есть, бэкенд stub, или наоборот).  
**3.2. Архитектура и границы** — дублирование контуров, источник истины; мультитенантность: все пути админа проверены или есть **доказанные** дыры.  
**3.3. Безопасность и данные** — PII, секреты, RBAC, аудит; где **нет тестов** — **неизвестно = риск**.  
**3.4. Надёжность и операции** — backup/restore, деплой, наблюдаемость; без runbook и проверки restore — **не зрелость**.  
**3.5. Качество поставки** — CI: что реально гейтится; зелёный main без **строгих** E2E на критике — **дыра**.  
**3.6. ИИ (если есть)** — fallback, утечки контекста между tenant, стоимость ошибки — отдельно, без маркетинга.

### E2E — строгая сетка {#gate-6-e2e}

Минимум для коммерческой зрелости. Конкретные сценарии проекта дополняются в `tests/e2e/` и артефактах.

| Область | **PASS** | **FAIL** |
|---------|----------|----------|
| **Идентичность и доступ** | E2E: логин админа → доступ только к своей клинике; нет утечки при смене контекста | Обход без теста или только ручная проверка «когда-нибудь» |
| **Бронирование / оплата** (если в продукте) | Полный путь: запись → оплата/статус → отображение в кабинете | Обрыв на sandbox без продовой политики или без автотеста критичного пути |
| **Омниканал** | Отправка/получение в **реальном** канале или документированный контракт с mock + контрактные тесты | «Кнопка есть», сообщение не гарантировано дойти |
| **Мультитенантность API** | Автотесты на изоляцию для **каждого** класса админских роутов с риском | Один тест «на всё» или нет негативных кейсов |
| **Регрессия** | CI падает при нарушении критичного сценария | Зелёный CI при сломаном критичном пути |

**Дополнение:** для каждого критичного journey — **негативные** E2E (отказ оплаты, 401, чужой tenant).  
**Связь с антигалочкой:** галочки в этой сетке при L-оценке = автоматический FAIL (`docs/LEAD_ANTI_CHECKBOX_PROTOCOL.md` §7).

### Шкала вердикта (коммерческая)

| Уровень | Описание |
|---------|----------|
| **L0 — неприемлемо** | Блокеры по безопасности, данным или юридически значимым обещаниям без реализации. |
| **L1 — только внутренний пилот** | Работает в демо; E2E не покрывают прод; нет операционной дисциплины. |
| **L2 — ограниченный пилот с клиентом** | Критичные E2E зелёные; риски задокументированы; есть план инцидентов. |
| **L3 — коммерчески защищаемо** | SLO/backup/безопасность в пределах политики; расширение — масштабирование, а не «доделать базу». |

**@LEAD** обязан назвать уровень **L0–L3** и **не** повышать его без оснований из E2E-сетки выше.

```
□ Все шесть блоков «метод разборки» выше покрыты в отчёте
```

### Протокол реакции на L-вердикт

| Вердикт | Действие @LEAD |
|---------|---------------|
| **L0** | Немедленный стоп. Список блокеров P0 → @DEV/@ARCH. Новый цикл с GATE-2. |
| **L1** | Деплой только во внутренний контур. Создать `MATURITY_UPLIFT_PLAN.md` с шагами до L2. Клиентский пилот заблокирован. |
| **L2** | Ограниченный пилот разрешён. Риски задокументированы. NDA при необходимости. Дата следующего L-review фиксируется. |
| **L3** | Коммерческий деплой разрешён. @LAWYER при необходимости. |

### Симптомы галочки при L-оценке

- L-вердикт без обоснования → **не принимается**
- «Продукт хороший, но...» без L-уровня → **нарушение запретов выше**
- E2E «планируется» или «будет сделано» → **FAIL, не PASS**
- Риски названы, план их закрытия отсутствует → **L1 максимум**

### Definition of Done релиза (единый артефакт) {#gate-6-release-dod}

**Проблема:** DoD задачи закрывается через QA_ARCH (GATE-3); **DoD релиза** раньше приходилось собирать из нескольких документов. **Решение:** один явный чеклист перед коммерческим обещанием или тегом релиза.

Минимум (все пункты должны быть явно ✅ или отмечены «не применимо» с причиной):

| # | Критерий | Источник ворот / артефакт |
|---|----------|---------------------------|
| R1 | Критичные journeys для этого релиза перечислены и проверены (авто или зафиксированный ручной прогон) | GATE-4, QA |
| R2 | Нет открытых 🔴 из QA_REPORT по затронутым модулям | GATE-3 |
| R3 | Соответствие `ARCHITECTURE_EXCELLENCE_PASSPORT.md` / TECH_PASSPORT для затронутого UI — зафиксировано | @QA_ARCH |
| R4 | Мультитенантность и SEC P0/P1 закрыты для затронутых ручек | GATE-4 |
| R5 | Для затронутых экранов — проверка **логики процесса** (`docs/LEAD_PRODUCT_LOGIC_EXCELLENCE.md` §2–3), нет необоснованных мёртвых кнопок | @LEAD / @QA_ARCH |
| R6 | L-вердикт ≥ целевого для типа выката (внутренний / пилот / коммерция) | GATE-6 |
| R7 | Ops: образы по sha, smoke/runbook по политике выката | GATE-5 |

Артефакт: раздел в `docs/ENGINEERING_PLAN.md` или `docs/artifacts/RELEASE_NOTES_*.md` с таблицей R1–R7 — **именованный** DoD релиза, не рассыпной «в голове у @LEAD».

## ПРОТОКОЛ РЕАКЦИИ @LEAD НА ПРОВАЛ ВОРОТ

```
При любом незакрытом блокере:

1. СТОП — цепочка не продвигается
2. ФИКСАЦИЯ — @LEAD называет номер ворот и конкретный незакрытый пункт
3. АДРЕСАТ — конкретная роль получает конкретную задачу (не "разберитесь")
4. ДОКАЗАТЕЛЬСТВО — @LEAD принимает только артефакт, не слова
5. РЕФЛЕКС (автоматически при повторном провале той же ворота):
   ⚡ РЕФЛЕКС:
   1. Кто нашёл: @LEAD (повторный провал GATE-N)
   2. Кто допустил: [@РОЛЬ]
   3. Корневая причина: [одна фраза]
   4. Как не повторить: [правило]
   5. Предложение: добавить в @[РОЛЬ]: "[формулировка]"
```

**Правило повторного провала:** если одна и та же ворота проваливается дважды подряд одной ролью — РЕФЛЕКС запускается автоматически, без запроса пользователя.
