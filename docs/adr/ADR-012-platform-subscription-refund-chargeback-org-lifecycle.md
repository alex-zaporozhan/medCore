# ADR-012: Контур B — возврат, chargeback / спор и жизненный цикл org после «денег назад»

- **Статус:** **Accepted** — нормативная политика и границы решения (LEAD). Реализация state machine, миграций и UI reconcile — **не** считается выполненной этим ADR; вести по [SAAS_STRENGTHENING_MASTER_PLAN.md](../architecture/SAAS_STRENGTHENING_MASTER_PLAN.md) §16.6 шаг 0, §6 и фазам **1b+** / наблюдаемости.
- **Дата:** 2026-04-05  
- **Контекст:** После MVP spine контура B возможна ситуация **успешная оплата → провижининг → активный тенант**, затем **возврат средств** (refund) или **chargeback / спор** у провайдера. Без явной политики возникает класс дефектов: **деньги возвращены — paid-опции и доступ остаются**, **двойной отзыв** при повторной доставке webhook, **молчаливое удаление** org без аудита. Пробел зафиксирован в PRINCIPLE §4.3, МП §6, §16.6 шаг 0, [ADR-011](./ADR-011-platform-subscription-webhook-provisioning.md) (раздел «Шаг 0»). Текущий код: обновление строки платежа + лог-предупреждение при `refunded` при активном intent — **наблюдаемость без доменного отзыва доступа**.

## Решение (победитель)

### 1. Термины (контур B, YooKassa и аналоги)

| Событие | Смысл | Типичный источник истины |
|--------|--------|---------------------------|
| **Отмена до списания** | Платёж не перешёл в устойчивый `succeeded` | Статус платежа провайдера; intent остаётся неактивным / без полноценного тенанта |
| **Refund (возврат)** | Средства возвращены плательщику после `succeeded` | Webhook / pull API провайдера; **идемпотентная** фиксация в `platform_subscription_payments` |
| **Chargeback / dispute** | Оспаривание у эмитента; исход «проигран продавцом» эквивалентен **коммерческому отзыву оплаты** с точки зрения доступа | Политика продукта выравнивается с **refund-плечом** по эффекту на доступ (см. п.3); юридические сроки и бухгалтерия — вне ADR, но **событие в приложении** должно быть однозначным и аудируемым |

### 2. Инварианты (обязательные)

1. **Нет молчаливого `DELETE` Organization / Clinic** из-за возврата или спора. Исключение — отдельный **юридически согласованный** процесс offboarding ([TENANT_OFFBOARDING_AND_EXPORT.md](../operations/TENANT_OFFBOARDING_AND_EXPORT.md)) с **явным** аудитом и сроками retention, не смешиваясь с автоматическим webhook.
2. **Идемпотентность отзыва:** повторное уведомление о том же возврате / финальном исходе спора **не** приводит к повторному массовому удалению строк, **не** дублирует записи аудита с разным смыслом. Использовать монотонные переходы статуса платежа + **детерминированный** эффект на entitlements (см. п.3).
3. **Согласованность денег и доступа:** если продуктовая политика гласит «нет оплаты — нет paid-опций», то при **подтверждённом** refund / проигранном chargeback для платежа, который активировал подписку, **paid entitlements, выданные этим контуром B, должны быть отозваны** (или заменены на явный «базовый / read-only / заблокированный» пресет — выбор пресета фиксируется в модуле биллинга и **§4** каталога). Инвариант: **нельзя** оставлять полный коммерческий доступ при признанном «деньги не у платформы» без явного **ручного** override с аудитом (см. п.5).
4. **Прошлые периоды:** если введена **подписка по периодам** (будущее), отзыв не подменяет факт оплаченного прошлого периода в **бухгалтерском** смысле; ADR регулирует **доступ и продуктовое право пользования**, не бухгалтерские проводки.
5. **Пересечение с импортом и ручным reconcile (§25, §16.6):** действия Основателя после сбоя / импорта **не** обходят п.1–3; каждое критичное изменение entitlements или статуса подписки — **append-only или неизменяемый аудит** (кто, когда, какое событие, ссылка на intent/payment). Повторное использование **тех же** доменных ключей идемпотентности, что у автоматического провижининга, допускается только если документировано в модуле биллинга и не создаёт «тихих» дублей org.

### 3. Политика по умолчанию для уже активированного тенанта (LEAD)

До ввода отдельного продукта «grace period» и сложного биллинга периодов:

- При переходе платежа контура B в **`refunded`** или в эквивалент **«спор проигран / средства изъяты»** (конкретные статусы провайдера — таблица в модуле [platform_subscription_billing.md](../architecture/modules/platform_subscription_billing.md)):
  - **Intent / подписка:** явное состояние уровня приложения (**например** `subscription_suspended` / `billing_revoked` на intent или связанной сущности — выбор поля/таблицы за @ARCH в миграции).
  - **Entitlements:** **отозвать** ключи, выданные из **tariff_snapshot** этого signup (не трогать несвязанные системные исключения без отдельного ADR). Минимум: убрать все ключи кроме явно оговорённого «заглушечного» набора или очистить paid-опции полностью — **как зафиксировано в модуле** после согласования Product.
  - **Organization:** сохраняется для расследований, экспорта, юридических сроков; **блокировка входа** для staff — через существующие механизмы (RBAC / флаг org / гейты), не через необъяснимый 404.
- **Частичный возврат:** не описывается в v1 ADR; требует отдельного продуктового решения (пропорциональный отзыв опций или ручной режим только).

### 4. Связь с ADR-011 и ADR-009

- **ADR-011** остаётся источником разведения A/B, идемпотентности `succeeded`, провижининга вперёд. **ADR-012** задаёт **обратные** и **компенсирующие** переходы после денег назад.
- Критичные шаги отзыва при **replicas ≥ 2** — по [ADR-009](./ADR-009-async-outbox-event-delivery.md) или эквиваленту (outbox / единая очередь), чтобы не было гонки между воркерами и API.

### 5. Наблюдаемость и тесты (DoD реализации)

- Метрики низкой кардинальности: например `platform_billing_payment_lifecycle_total{event="refunded"}`, счётчик **«активный intent при refunded»** до применения отзыва → **0** после (алерт при зависании).
- Автотесты: цепочка `succeeded` → провижининг → `refunded` webhook → entitlements отозваны / статус подписки обновлён; повтор webhook — без двойного эффекта.

## Последствия

- Появятся миграции и код в контуре B и, при необходимости, в гейтах entitlements; обновление OpenAPI внутренних/операторских путей reconcile.
- Кабинет Основателя: сценарии «принудительный отзыв / восстановление после ошибки» должны **соответствовать** п.2–5 и не дублировать бизнес-логику без вызова доменного сервиса.
