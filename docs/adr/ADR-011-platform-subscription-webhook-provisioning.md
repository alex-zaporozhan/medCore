# ADR-011: Платёж подписки SaaS (платформа) — webhook, идемпотентность, провижининг

- **Статус:** Accepted — **MVP spine** (не полное закрытие §16.6 мастер-плана). В коде: `POST /api/v1/platform/billing/webhooks/yookassa`, таблицы `platform_signup_intents` / `platform_subscription_payments`, идемпотентность, провижининг **Organization + Clinic** без первого Владельца/AdminUser и без `organization_entitlements`; нет retry/DLQ/reconcile UI, нет OpenAPI, нет метрик «stuck paid» из §16.6. Полный продуктовый поток — после **go** команды (ARCH/LEAD) и ADR-007 по границе platform/tenant.  
- **Дата:** 2026-04-04  
- **Контекст:** Подписка **организации** на платформу (Владелец → Основатель) — отдельный коммерческий контур от **оплаты пациента→клиника** (например YooKassa в `payment_service`). Повторная доставка webhook и сбой провижининга после успешного списания дают риск дублей организаций и «деньги есть — тенанта нет» ([QA_ARCH ревью](../architecture/SAAS_STRENGTHENING_MASTER_PLAN.md) C1–C2; U-006; тот же документ §6).

## Решение (победитель)

### 1. Разведение контуров

| Контур | Назначение | Правило |
|--------|------------|---------|
| **A. Пациентские платежи** | Существующий продукт | Текущие маршруты и секреты провайдера **не менять** смыслом; тесты U-006 по веткам сохраняются. |
| **B. Подписка платформы** | Оплата тарифа SaaS Владельцем | Отдельный **HTTP path** (префикс `/platform/.../webhooks/...` или эквивалент), отдельный **секрет верификации** webhook, отдельные **настройки** в конфиге. |

Запрещено использовать один и тот же URL и секрет для обоих контуров без явной маршрутизации по типу события, различимой **до** бизнес-логики (чтобы не путать идемпотентность).

### 2. Источник истины до активации

- Заявка на подписку и состояние оплаты хранятся в **БД платформенного контура** (см. ADR-007), не только в Redis.  
- Минимальная сущность: намерение регистрации + выбранный тариф/опции + статус + **идемпотентный ключ платежа** провайдера + TTL для `pending`.

### 3. Идемпотентность

- Повтор webhook с тем же **успешным** платежом **не** создаёт вторую `Organization` и **не** дублирует списание: уникальность по `(provider, provider_payment_id)` или эквиваленту в таблице платежей платформы + проверка состояния машины состояний.

### 4. Провижининг после оплаты

- Переход `paid` → создание/активация `Organization`, первого Владельца, `organization_entitlements` — **в одной транзакционной политике** с retry/outbox по ADR-009 там, где критично.  
- При **ошибке провижининга** после подтверждения оплаты: очередь **retry** с backoff, состояние **dead-letter**, **ручной reconcile** в кабинете Основателя (аудит); без повторного списания при повторе webhook.

### 5. Документация реализации

Детальный контракт состояний, эндпоинтов, переменных окружения и матрица тестов — в [platform_subscription_billing.md](../architecture/modules/platform_subscription_billing.md). **Возвраты, chargeback и отзыв доступа после «денег назад»** — отдельно в [ADR-012](./ADR-012-platform-subscription-refund-chargeback-org-lifecycle.md).

## Последствия

- Миграции Alembic под таблицы платформенного биллинга: **частично внесены** как MVP (см. шапку статуса); дальнейшие миграции (entitlements, первый Владелец и т.д.) — после явного **go** по [SAAS_STRENGTHENING_MASTER_PLAN.md](../architecture/SAAS_STRENGTHENING_MASTER_PLAN.md) §18–§19 и согласования ARCH.  
- Набор **автотестов** на все значимые ветки статусов webhook **B** (аналогично требованиям к A) — **в процессе**; текущие тесты покрывают идемпотентность happy path.  
- Расширение наблюдаемости: метрики «висящий paid без org», «retry exhausted» — целевые до закрытия §16.6.

## Шаг 0 (§16.6 МП — возвраты и смежные контуры)

**Нормативное решение зафиксировано в [ADR-012](./ADR-012-platform-subscription-refund-chargeback-org-lifecycle.md)** (Accepted, LEAD 2026-04-05): инварианты «деньги назад → отзыв paid-доступа», запрет молчаливого удаления org, идемпотентность отзыва, пересечение с reconcile/импортом §25. Детализация статусов провайдера и полей БД — в [platform_subscription_billing.md](../architecture/modules/platform_subscription_billing.md) §12.

Реализация state machine, миграций, метрик и тестов по ADR-012 — **бэклог** (МП §16.6 шаг 0 «код»); текущий **MVP spine** по ADR-011 покрывает успешный `succeeded` + идемпотентность повтора и **не** закрывает полный отзыв entitlements при refund.
