## 1. Проблема и границы

**Проблема:** «сырые» агрегаты по операционным таблицам на произвольном периоде дают недопустимый p95 при росте данных.

**Решение:** слой **витрины** — материализованные строки с заранее выбранной **гранулярностью** (PK), периодический refresh (часто nightly + ручной пересчёт), чтение API с **контролируемым** fallback.

**Вне scope витрины как паттерна:** снимки «как есть» без периода (другой контракт инвалидации); кэш только в Redis без паритета с эталоном — отдельное решение.

---

## 2. Повторяемый каркас слоёв

| Слой | Обязанность |
|------|----------------|
| **Эталон (raw)** | Один согласованный источник семантики сумм/строк: запросы к операционным данным или выделенный reporting-слой. Любое изменение бизнес-смысла — осознанно (ADR), витрина **зеркалит** эталон, а не подменяет его «по-тихому». |
| **Таблица(ы) витрины** | Одна логическая витрина на отчётный срез; PK = выбранная гранулярность; `updated_at`; индексы под фильтр `(tenant_id, …)` и типичный диапазон дат. |
| **Сервис агрегирования** | Refresh за диапазон (часто DELETE + INSERT по ключам окна), вычисление «свежести» по подмножеству строк, участвующих в ответе. |
| **API** | Тот же контракт ответа, что у raw-пути; переключение read-path через feature-flag / settings; метаданные источника и свежести в DTO. |
| **Фон** | Очередь (Celery и аналоги): идемпотентность, ретраи, lookback; ручной `POST` refresh для ops. |
| **Наблюдаемость** | Метрики: lag, пустая витрина, устаревший диапазон, fallback; логи без сырого PII. |

## 3. Гранулярность (PK) — инвариант, не деталь реализации

Витрина хранит строки фиксированной формы. **Нельзя** выбрать PK «как в последнем GROUP BY отчёта», не проверив: ответ API за **любой** допустимый `[date_from, date_to]` должен быть восстановим из строк витрины **без противоречий**.

Типичный **антипаттерн:** агрегат «одна строка на (сущность A, сущность B) на весь интервал запроса». Если пользователь запрашивает разные окна, одна и та же логическая строка соответствует разным суммам — витрина без дополнительного измерения (например **дневной** даты) не кэширует произвольные диапазоны.

**Требование @QA_ARCH:** для каждой витрины зафиксированы PK, доказательство паритета с эталоном на seed-данных и явное решение по «оси даты» (день / визит / период зарплаты и т.д.).

## 4. Свежесть, пустота, fallback

| Ситуация | Ожидаемое поведение (норма 8.5+) |
|----------|-----------------------------------|
| **Свежесть** | `max(updated_at)` по строкам витрины, **входящим в ответ** на конкретный запрос `(tenant, date_from, date_to)` — с тем же предикатом, что и выборка (включая пересечение периодов для отчётов «по периоду зарплаты»). Сравнение с порогом `STALE_MAX` → при превышении read из raw + метка в ответе. |
| **Пустая витрина** | Fallback на raw; метрика `empty_vitrine`; не подменять «ноль» без явного маркера покрытия диапазона. |
| **Откат функционала** | Feature-flag / env: отключить чтение из витрины без обратной миграции в emergency. |

Поля вроде `data_source`, `aggregate_stale`, `aggregate_max_updated_at` — контракт между бэкендом и фронтом; **не** выносить в UI внутренние имена job или таблиц (см. техпаспорт UI).

## 5. Безопасность и деньги

- **Tenant:** каждая строка витрины и каждый запрос с неделимым фильтром арендатора; негативные тесты на IDOR / cross-tenant join.
- **RBAC:** витрина **не ослабляет** права; отдельные permission-контуры (например «владелец» vs «маркетинг») остаются на API.
- **Согласованность с деньгами:** автотесты паритета raw vs витрина; при расхождении — блокер релиза или явный gap с решением @LEAD (как для финансовой сверки в паспорте целевой архитектуры).

## 6. Маппинг на категории NFR (для @QA_ARCH и критики архитектуры)

Увязка с весовой матрицей в `ARCHITECTURE_EXCELLENCE_PASSPORT.md` §3:

| Категория | Что проверить для витрины |
|-----------|---------------------------|
| **Reliability & Resilience** | Идемпотентность refresh; отсутствие «тихой» порчи сумм при частичном сбое; политика retry фоновых задач. |
| **Security & Compliance** | Tenant + RBAC; отсутствие утечки чужого арендатора в отчёте. |
| **Performance & Scalability** | p95 чтения при включённой витрине; бюджет refresh; рост объёма строк при расширении lookback. |
| **Data Integrity & Transactions** | PK и семантика окна; паритет с эталоном; миграции expand → deploy → contract. |
| **Observability** | Метрики lag / empty / stale; алерты по росту fallback; логи причины fallback. |
| **Architecture & Code Quality** | Один эталон raw; явные границы сервиса; отсутствие дублирования бизнес-правил в SQL витрины и raw по-разному без теста. |
| **Delivery Discipline** | Тесты паритета в CI; флаг отката задокументирован в runbook. |

## 7. Чеклист готовности (DoD) для витрины отчёта

- [ ] Зафиксированы PK и ось времени; документирован крайний случай «произвольный период».  
- [ ] Автотест: суммы/строки (в допуске для decimal) = эталон на тех же данных.  
- [ ] Сценарии: пустая витрина, устаревший диапазон — корректный fallback и метаданные ответа.  
- [ ] Негативные тесты tenant/RBAC на read и на фоновый refresh.  
- [ ] Метрики и дашборд/алерты по согласованию с ops.  
- [ ] Runbook: env-флаги, ручной refresh, что делать при расхождении с эталоном.  
- [ ] UI: четыре состояния списка/отчёта; ненавязчивый сигнал при `aggregate_stale` (см. техпаспорт UI).

1. Скопировать этот файл в `docs/` (или принять как внешний стандарт команды).  
2. Добавить **локальный** `ARCH_DEV_*` или ADR: имена таблиц, миграции, эндпойнты, эпик-ID. **Не** копировать из другого репо чужие `ARCH_DEV_ERP_VITRINES_026*` — это привязка к чужому эпику; при необходимости читать как **референс**, не как обязательный файл.
