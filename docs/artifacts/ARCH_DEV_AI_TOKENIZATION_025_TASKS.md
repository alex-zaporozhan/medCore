### 1. Understand — текущая защита ПД и места для токенизации

1.1. **Разобрать существующую политику AI‑безопасности.**  
1.1.1. Изучить `AiSanitizer`, `SafeAiClient`, `AiConfigService` и `ClinicAiSettings`:  
       - как сейчас реализовано `allow_personal_data`;  
       - какие типы ПД уже маскируются (телефон, email и т.п.).  
1.1.2. Связать с `ARCH_DEV_OMNI_POLICY_016.md` и убедиться, что OMNI‑policy уже реализована по соответствующему TASKS‑файлу.

1.2. **Найти места, где AI‑контекст содержит ссылки на сущности.**  
1.2.1. В Orchestrator’е, AI‑tools, Chat AI‑сервисах, отчётах и AI Task Manager’е:  
       - найти, где в контекст/промпт передаются `patient_id`, `booking_id`, `lead_id`, сведения о пакетах/кошельках и т.п.;  
       - определить, где эти ссылки идут как структурные поля, а где — как часть текста.  
1.2.2. Отметить, какие из этих мест будут первыми кандидатами на токенизацию.

### 2. Design‑to‑code — формат токенов и утилиты

2.1. **Определить финальный формат токенов для v1.**  
2.1.1. На основе `ARCH_DEV_AI_TOKENIZATION_025.md` зафиксировать формат:  
       - `PATIENT#<uuid>`, `BOOKING#<uuid>`, `PACKAGE#<uuid>`, `WALLET#<uuid>`, `LEAD#<uuid>` для v1 (прямое кодирование UUID внутри токена).  
2.1.2. Обозначить ограничения:  
       - UUID в токене **не должен** сопровождаться другими ПД (ФИО, телефон и т.п.) при `allow_personal_data=False`;  
       - токены должны быть легко детектируемы регулярным выражением.

2.2. **Спроектировать утилиты генерации/парсинга токенов.**  
2.2.1. Создать модуль (например, `src/application/ai/tokenization.py`) с функциями:  
       - `make_patient_token(patient_id: UUID) -> str`;  
       - `parse_patient_token(token: str) -> UUID`;  
       - аналогичные для Booking/Package/Wallet/Lead.  
2.2.2. Добавить регексы для обнаружения токенов в тексте (отдельные функции/константы).

2.3. **Запланировать (но не реализовывать сейчас) возможность mapping‑таблицы.**  
2.3.1. В комментариях/доках описать, как в будущем можно перейти к схеме с отдельной таблицей `ai_token_mapping` (псевдо‑ID), если появятся более жёсткие требования к ПД.  
2.3.2. Не создавать таблицу на v1, если для текущих требований достаточно UUID‑формата.

### 3. Implement — расширение AiSanitizer и SafeAiClient

3.1. **Научить AiSanitizer распознавать токены.**  
3.1.1. Добавить в `AiSanitizer` поддержку:  
       - детектирования токенов по регексу;  
       - исключения токенов из маскировки ПД (чтобы они не превращались в `[MASKED]`).  
3.1.2. Убедиться, что существующая маскировка телефонов/email сохраняется без изменений.

3.2. **Гарантировать отсутствие ПД при `allow_personal_data=False`.**  
3.2.1. В `AiSanitizer`/SafeAiClient’е дополнительно убедиться, что при `allow_personal_data=False`:  
       - все ПД (телефоны, email, ФИО/адреса по мере поддержки) маскируются;  
       - наружу уходят только токены и «обезличенная» бизнес‑информация.  
3.2.2. При необходимости добавить места расширения для будущего маскирования ФИО/адресов (без немедленного агрессивного включения, если это может сломать текущие сценарии).

### 4. Implement — применение токенизации в AI‑tools и Orchestrator’е

4.1. **Структурированный уровень: токены в полях AI‑tools.**  
4.1.1. В выбранном минимальном наборе AI‑tools (см. `ARCH_DEV_OMNI_REGISTRY_015_TASKS.md`):  
       - заменить явные `patient_id`/`booking_id`/`lead_id` в структурах контекста, передаваемых в AI, на токены;  
       - хранить внутренние id только в доменном контексте (не в текстовом промпте).  
4.1.2. Обеспечить обратное преобразование: при получении ответа AI, содержащего токены, парсить их и мапить обратно в id до вызова доменных сервисов.

4.2. **Текстовый уровень: токенизация внутри сообщений.**  
4.2.1. Там, где в текстовый контекст для AI попадают ссылки на сущности (например, «Пациент Иванов с записью #123»), по возможности заменять их на токены (`PATIENT#uuid`, `BOOKING#uuid`), либо не передавать ПД вообще при `allow_personal_data=False`.  
4.2.2. Использовать функции из `tokenization.py` и возможности `AiSanitizer` для автоматической замены/детектирования токенов в тексте.

4.3. **Избегать принятия бизнес‑решений по «сырому тексту».**  
4.3.1. Там, где AI‑ответы содержат указания действий над сущностями, базироваться на токенах, а не на текстовых описаниях (ФИО, произвольные идентификаторы).  
4.3.2. Если AI вернул только текст без токенов, но требуется действовать на уровне домена, рассматривать это как сигнал/подсказку для оператора, а не автоматическое действие.

### 6. Later — медицинские ПД и даты рождения (SEC roadmap, не реализовывать в v1)

6.1. **Разделить обычные ПД и медицинские ПД.**  
6.1.1. Считать диагнозы, жалобы, результаты анализов и любые данные о здоровье пациента **специальной категорией ПД** (medical PD), отличной от телефонов/email/ФИО/адресов.  
6.1.2. Зафиксировать в `ARCH_DEV_OMNI_POLICY_016.md`, что для medical PD действует более жёсткий режим, чем для «обычных» ПД.

6.2. **Политика для medical PD во внешнем AI.**  
6.2.1. При `provider_type="external"` + `allow_personal_data=False` medical PD (диагнозы, подробности лечения и т.п.) **не должны уходить** во внешний AI ни в явном виде, ни как токены с прозрачной семантикой (`DIAGNOSIS#кариес` и т.п.).  
6.2.2. Допустимы только агрегированные/обезличенные признаки (например, уровни риска/тип кейса), которые нельзя однозначно восстановить до конкретного диагноза.  
6.2.3. Для `provider_type in {"ru_compliant","on_premise"}` можно запланировать отдельный флаг `allow_medical_data` (включение только после отдельного SEC‑review).

6.3. **Будущая модель хранения и токенизации диагнозов.**  
6.3.1. Запланировать отдельную сущность уровня домена (например, `patient_medical_record`/`patient_diagnosis`) с жёстким RBAC и аудитом в базе.  
6.3.2. Для AI контекста использовать не текст диагноза, а код/класс риска (`CASE_TYPE#<uuid>` или `RISK_GROUP#<uuid>`), который мапится на диагноз только внутри клиники.  
6.3.3. Рассмотреть выделение отдельной таблицы наподобие `ai_token_mapping` для medical PD, где псевдо‑ID не позволяют восстановить диагноз извне без доступа к БД клиники.

6.4. **Даты рождения и другие идентификаторы времени.**  
6.4.1. Дата рождения пациента рассматривается как ПД и в сочетании с другими атрибутами (история визитов, суммы, канал коммуникации) может однозначно деанонимизировать человека.  
6.4.2. При `provider_type="external"` + `allow_personal_data=False` точные даты рождения, а также их прямые производные (полный возраст с датой, «родился 01.01.1990» и т.п.) **не должны передаваться** во внешний AI.  
6.4.3. На будущее: вместо точной даты рождения использовать агрегаты (диапазоны возраста, флаги «ребёнок/взрослый/пенсионер») в промптах, если это нужно бизнес‑логике, и рассмотреть добавление мягких регексов/правил в `AiSanitizer` для маскирования дат рождения по аналогии с телефонами/email.
