### 2. Design‑to‑code — модели обязательств и DTO ERP↔Loyalty

       - `ErpLoyaltyObligationMovement`:  
         - поля: `id`, `obligation_id`, `booking_id` (опционально), тип события (`CREATE_FROM_SALE`, `WRITE_OFF_ON_VISIT`, `REFUND`, и т.п.), величина изменения обязательства (в плюс/минус), `clinic_id`, timestamp.  
2.1.2. Определить базовые enum/константы для типов движений и статусов обязательства, чтобы избежать «сырых» строковых значений.

2.2.2. Убедиться, что DTO:  
       - не тянут ORM‑модели напрямую;  
       - содержат только необходимые для ERP/отчётности данные, без ПД (ФИО/контактов).

2.3.1. В application‑слое (например, `src/application/services/erp_loyalty_service.py`) объявить интерфейс/класс `ErpLoyaltyService` с методами:

2.3.2. На этом этапе оставить тела методов минимальными/заглушечными, но задать чёткие сигнатуры и связи с DTO и доменными моделями.

### 3. Implement — создание ERP‑обязательств и движений

3.1. **Реализовать создание обязательства при продаже пакета/депозита.**  
3.1.1. В `ErpLoyaltyService.create_obligation_from_sale` реализовать логику:  
       - на входе получать данные о продаже из Loyalty/продажного сервиса (клиника, пациент/семья, продукт, сумма/номинал, идентификаторы Loyalty‑сущностей);  
       - создавать запись `ErpLoyaltyObligation` с полным исходным номиналом и начальными остатками;  
       - создавать `ErpLoyaltyObligationMovement` с типом `CREATE_FROM_SALE` и ссылкой на соответствующий `LoyaltyOperation`;  
       - возвращать `ErpLoyaltyObligationSnapshot` для использования в ERP‑узле и отчётности.  
3.1.2. Обеспечить, чтобы все создаваемые ERP‑объекты имели корректный `clinic_id` и ссылки на пациента/семью, соответствующие контексту продажи.

3.2. **Интегрировать создание обязательств в поток продажи пакетов/депозитов.**  
3.2.1. В сервисах Loyalty, которые обрабатывают продажу пакетов/депозитов (`LoyaltySaleService`/аналог):  
       - после успешного создания/пополнения кошелька/депозита вызывать `ErpLoyaltyService.create_obligation_from_sale`;  
       - передавать в вызов полный контекст продажи (клиника, пациент/семья, продукт, сумма).  
3.2.2. Убедиться, что в случае отката/ошибки ERP‑создания обязательства:  
       - либо откатывается и операция Loyalty (единая транзакция/согласованный rollback);  
       - либо создаётся Attention/Task о рассинхронизации (будет реализовано в разделе 5).

3.3. **Реализовать регистрацию списаний по визиту.**  
3.3.1. В `ErpLoyaltyService.register_write_off_for_visit` реализовать логику:  
       - на входе получать агрегированную информацию от Loyalty‑write‑off сервиса:  
         - список задействованных пакетов/кошельков, суммы/объёмы списания, связанные `LoyaltyOperation`;  
         - `booking_id` и `clinic_id`;  
       - для каждого затронутого обязательства:  
         - уменьшать остаток в `ErpLoyaltyObligation` на соответствующую сумму;  
         - создавать `ErpLoyaltyObligationMovement` с типом `WRITE_OFF_ON_VISIT` и ссылкой на `booking_id` и `LoyaltyOperation`;  
       - формировать `ErpLoyaltyWriteOffSummary` с новыми остатками и возможными варнингами (недостаточный баланс, попытка переписать уже погашенное обязательство и т.п.).  
3.3.2. Обеспечить валидацию:  
       - запрет списания больше остатка (или чётко задокументированное поведение при попытке overspend);  
       - проверку согласованности `clinic_id` между визитом, обязательством и Loyalty‑объектами.

3.4. **Учёт возвратов и корректировок (по минимуму).**  
3.4.1. Если в бизнес‑логике уже существуют операции возврата/сторнирования по пакетам/депозитам:

3.4.2. Зафиксировать в коде/док‑комментариях, какие кейсы корректировок поддерживаются в v1, а какие остаются в ROADMAP.

### Будущие улучшения ERP‑узла («на потом»)

- **Расширить модель обязательств на кошельки/депозиты.**
  - Текущая реализация покрывает только обязательства по абонементам (`CustomerSubscription`) через `ErpLoyaltyObligation`.
  - В дальнейшем можно добавить отдельные виды обязательств для кошельков/депозитов и увязать их с `Wallet`/потенциальным `LoyaltyDeposit`.

- **Усилить атомарность ERP↔Loyalty по визиту.**
  - В v1 движения по ERP‑обязательствам при списаниях выполняются в режиме best‑effort, без блокировки завершения визита.
  - На следующих итерациях можно сделать критичными ошибки ERP‑обязательств (создание/движения) и синхронизировать rollback между Loyalty и ERP‑узлом.

- **Унифицировать денежную модель обязательств с расчётами `get_liability`.**
  - Сейчас денежный номинал обязательства фиксируется в ERP при продаже и списывается независимо.
  - Можно добавить периодическую сверку с расчётом `get_liability` и настроить авто‑корректировки/Attention при расхождениях за пределами допустимого порога.
