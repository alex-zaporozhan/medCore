### Будущие улучшения ERP‑узла («на потом»)

- **Нормализация статусов отмены.**  
  Текущие коды `cancelled`/`no_show` используются как обобщённые финальные состояния. Арх‑модель предлагает более гранулярные `canceled_by_patient`/`canceled_by_clinic` и служебные статусы. Требуется отдельная миграция данных и рефакторинг мест, где отчёты и метрики завязаны на агрегированные коды.

- **Переход с `pending`/`confirmed` на `scheduled`/`in_progress`.**  
  В текущей реализации `pending` и `confirmed` совмещают несколько состояний жизненного цикла визита. Для полного соответствия ARCH‑модели нужна поэтапная миграция кодов и обновление фронтового словаря, чтобы явно разделить «забронирован, но не подтверждён», «подтверждён» и «в процессе».

- **Расширение state‑machine под ERP‑узел.**  
  Сейчас правила переходов в `BookingStatusService` покрывают только основной happy‑path (`pending/confirmed → completed`, `pending/confirmed → no_show`, отмены). Для глубокой интеграции с ERP‑узлом и Tasks/Attention имеет смысл вынести отдельные под‑состояния для ERP‑обработки (`in_progress`, `error`, `inconsistent`) и связать их с событиями ERP‑узла.

- **Единый источник правды по статусам для отчётов.**  
  Отчётные сервисы и AI‑аналитика сейчас опираются на строковые значения статусов. После стабилизации enum‑модели стоит перевести отчётные вьюхи/репорты на использование нормализованных групп статусов (ожидают/в процессе/финальные/проблемные/отменённые), чтобы избавиться от жёсткого связывания с конкретными строками.
