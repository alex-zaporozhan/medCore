## ARCH_DEV_ERP_REPORTS_012 — владельческая ERP‑отчётность

> DEV_PROMPT_ERP_REPORTS_012 — «владельческая ERP‑отчётность (ERP‑3, ATT‑2)»

---

## 1. Контекст и существующее состояние

### 1.1. Что хочет видеть владелец клиники

На уровне `BUSINESS_PLAN_NEXT.md` и `ARCH_ERP_NEXT.md` владельческая отчётность должна отвечать как минимум на вопросы:

- Сколько денег клиника зарабатывает:
  - в разрезе клиник/кабинетов/врачей;
  - в разрезе услуг/пакетов/источников трафика?
- Сколько стоит фонд оплаты труда и материалы:
  - по визитам/врачам/услугам?
- Каков баланс обязательств по пакетам/депозитам:
  - сколько уже отработано, сколько осталось?
- Какой ROI по каналам привлечения:
  - сколько денег принес каждый источник трафика/кампания?

### 1.2. GAPS ERP‑3 / ATT‑2

По `BACKEND_GAPS_ERP_NEXT.md` и `BACKEND_GAPS_Attribution_NEXT.md`:

- отчёты:
  - частично дублируют расчёты (сложная логика в самих эндпоинтах/ORM‑запросах);
  - не опираются на единый ERP‑узел/обязательства (`DEV_PROMPT_ERP_NODE_010`, `DEV_PROMPT_ERP_LOYALTY_011`);
  - могут плохо масштабироваться (PERF‑2) и быть слабо наблюдаемыми (OBS‑1).
- атрибуция:
  - не всегда связанна с ERP‑данными по деньгам;
  - сложно однозначно ответить, сколько денег принёс конкретный канал/кампания.

### 1.3. Связь с другими артефактами

- `ARCH_ERP_NEXT.md` — определяет, какие данные считаются основой ERP‑отчётности.
- `ARCH_ATTRIBUTION_NEXT.md` — источник правды об источниках трафика/кампаниях.
- `ARCH_DEV_ERP_NODE_010.md` — ERP‑узел завершения визита, формирующий «сырые» ERP‑данные.
- `ARCH_DEV_ERP_LOYALTY_011.md` — обязательства по пакетам/депозитам как ERP‑объекты.
- **`ARCH_DEV_ERP_VITRINES_026.md`**, **`ARCH_DEV_ERP_VITRINES_026_TASKS.md`** — предагрегаты (витрины) для тяжёлых ERP‑отчётов поверх `ErpReportsRepository` (payroll, materials, ROI); не путать с первичным контрактом view‑классов в этом документе.
- `ARCH_DEV_SEC_RBAC_022.md` — ограничения по доступу (особенно к владельческим отчётам).

## 2. Целевое состояние отчётного слоя

### 2.1. Жёсткие инварианты

1. **Отчёты опираются на ERP‑данные, а не пересчитывают бизнес‑логику.**
   - Вся сложная логика движения денег/обязательств реализована:
     - в ERP‑узле завершения визита;
     - в ERP↔Loyalty‑связке;
   - отчётные эндпоинты:
     - используют уже подготовленные ERP‑таблицы/регистры;
     - не дублируют расчёты «на лету» в ORM‑запросах.

2. **Единый источник правды по деньгам.**
   - CRM, отчёты и атрибуция:
     - читают агрегаты из ERP‑слоя;
     - не держат независимые суммы, кроме кэшей/денормализаций, явно синхронизируемых с ERP.

3. **Отчёты масштабируются.**
   - Для тяжёлых отчётов:
     - используются агрегирующие таблицы/материализованные представления/кэши (по согласованию);
     - сложные выборки не блокируют основной OLTP‑контур.

4. **Роли и права доступа соблюдены.**
   - Владелец/управленцы видят:
     - полный объём отчётности;
   - другие роли (доктора, регистраторы, маркетинг):
     - видят только релевантные разрезы/агрегаты без лишней финансовой детализации.

## 3. Архитектурный дизайн отчётного слоя

### 3.1. Отчётные представления поверх ERP‑узла

Предлагаемое разделение:

1. **Факт выручки по визитам**
   - Базовое представление (view/ORM‑модель), условно `ErpVisitRevenueView`:
     - `visit_id`/`booking_id`, `clinic_id`, дата визита;
     - врач/кабинет;
     - суммы по категориям:
       - «живые» деньги (касса/эквайринг);
       - списания из пакетов/депозитов (как отработанные обязательства);
     - ссылки на источники трафика/кампании (через связь с Attribution).

2. **Фонд оплаты труда**
   - Представление `ErpVisitPayrollView`:
     - `booking_id`, врач/участники;
     - начисленная ЗП по визиту (в разрезе ролей/схем).

3. **Склад/материалы**
   - Представление `ErpVisitInventoryView`:
     - какие материалы/в каких количествах были списаны по визиту;
     - стоимость материалов (если доступна).

4. **Обязательства по пакетам/депозитам**
   - Представление `ErpLoyaltyObligationsView`:
     - остатки обязательств по клиникам/пациентам/продуктам;
     - динамика (сколько погашено за период).

Каждое из этих представлений:

- строится поверх «сырых» ERP‑таблиц/регистров, формируемых в `ErpVisitNodeService` и `ErpLoyaltyService` (см. предыдущие ARCH_DEV);
- может быть реализовано как:
  - ORM‑модель, мапящаяся на SQL‑view;
  - или как набор специализированных запросов/репозиториев (если создание view пока избыточно).

### 3.2. Привязка к Attribution

- Для ROI/источников трафика требуется:
  - для каждого визита (и связанных ERP‑записей):
    - иметь связь с конкретным источником трафика и кампанией (см. `ARCH_ATTRIBUTION_NEXT.md`);
  - в отчётном слое:
    - дополнить `ErpVisitRevenueView` полями `traffic_source_id` / `campaign_id`;
    - при необходимости — отдельным представлением `ErpAttributionRevenueView`:
      - агрегирующим выручку по источникам/кампаниям/периодам.

## 4. API и UX владельческой отчётности

### 4.1. Backend API

- В `src/api/v1/routers/admin_reports.py` (и при необходимости смежных роутерах) ввести/нормализовать эндпоинты:
  - `GET /admin/reports/revenue-by-period`:
    - параметры: период, клиника, фильтры по врачу/кабинету/услугам;
    - данные из `ErpVisitRevenueView`.
  - `GET /admin/reports/payroll-by-period`:
    - данные из `ErpVisitPayrollView`.
  - `GET /admin/reports/materials-by-period`:
    - данные из `ErpVisitInventoryView`.
  - `GET /admin/reports/loyalty-obligations`:
    - данные из `ErpLoyaltyObligationsView`.
  - `GET /admin/reports/roi-by-source`:
    - данные из `ErpAttributionRevenueView` (выручка + источники трафика).

- Важно:
  - все эндпоинты:
    - фильтруются по `clinic_id`;
    - защищены корректными пермишенами (`erp.owner_reports.read`, `attribution.reports.read` и т.п., см. `ARCH_DEV_SEC_RBAC_022.md`).

### 4.2. Frontend (кратко)

- Админ‑панель ERP‑отчётности:
  - использует новые API;
  - визуализирует:
    - динамику выручки и ЗП;
    - маржинальность по услугам/врачам;
    - остатки по пакетам/депозитам;
    - ROI по источникам трафика.
- Детальный UX‑план остаётся в зоне фронтовых DEV_PROMPTS/`FRONTEND_GAPS_Admin_NEXT.md`, но:
  - backend‑контракты уже должны быть спроектированы под владельческие сценарии.

## 5. Наблюдаемость и производительность

### 5.1. Performance

- Для тяжёлых отчётов (PERF‑2):
  - при необходимости:
    - ввести агрегирующие таблицы (например, дневные/месячные срезы по клинике/источнику/услугам);
    - либо использовать материализованные представления.
- Все новые запросы:
  - профилировать на реальных/близких к бою объёмах;
  - обеспечить индексы по ключевым полям фильтрации (дата, клиника, врач, источник трафика и т.п.).

### 5.2. Observability

- Для отчётных эндпоинтов:
  - логировать:
    - параметры запросов (агрегировано);
    - время выполнения;
    - ошибки (SQL‑ошибки, таймауты);
  - метрики:
    - латентность по эндпоинтам;
    - частота вызовов;
    - частота таймаутов/ошибок.
