## Цели архитектурного плана (критерии успеха)

План нужен не ради чеклистов, а чтобы фронт оставался **предсказуемым Business OS**:

| Цель | Как проверяется |
|------|-----------------|
| **Единая точка правды по маршрутам и зонам** | Таблицы §2 техпаспорта ≡ `frontend/src/App.tsx`; guard’ы `/admin` / `/app` не обходятся «тихо». |
| **Единый слой HTTP и ошибок** | Новые вызовы через `client.ts`, типы согласованы с бэкендом; нет дублирования 401-логики для пациента. |
| **Единый слой данных** | Query/Mutation в хуках, осмысленные ключи и инвалидация; при смене статусов/DnD — осознанный optimistic. |
| **Приёмка по типу страницы** | Для затронутых экранов — минимум из `docs/DOMAIN_STANDARDS.md` (секция SCHEDULE, CRM, DASHBOARD и т.д. по релевантности); отсутствие обязательного пункта = 🟡 (некритично) или 🔴 (критично для домена) по правилам того же файла. |
| **NFR фронта** | Списки и тяжёлые экраны: четыре состояния UI (Loading / Empty / Error / Success) — `docs/ARCHITECTURE_EXCELLENCE_PASSPORT.md` §11; без «белого экрана» при загрузке там, где ожидаются данные. |

## DoD для PR (фронт, обязательный блок для ревью)

Скопировать в описание PR при изменении UI или маршрутов:

- [ ] Зона (`/admin` / `/app` / …) и guard соответствуют техпаспорту §2.
- [ ] Техпаспорт обновлён, если менялись маршруты или глобальные провайдеры.
- [ ] Типы страниц из `DOMAIN_STANDARDS`: *перечислить* (например SCHEDULE, CRM) — и отметить выполненные пункты **или** отклонение с согласованием LEAD.
- [ ] Списки/таблицы в diff: Loading / Empty / Error / Success (где применимо).
- [ ] `npm test` / CI зелёные; новая логика — тест или краткое обоснование «почему без теста».
- [ ] Не нарушен §7 техпаспорта без эпика.

**QA_ARCH** использует этот блок как первичную матрицу; при отсутствии секции DOMAIN_STANDARDS для затронутых страниц — запрос дополнения или пометка 🟡 с планом.

## Порядок внедрения типовой фичи (чеклист DEV)

Использовать как шаблон для каждого тикета:

1. **Зона:** `/admin` / `/app` / `/` / прочее — согласовано с LEAD.
2. **Маршрут:** запись в `App.tsx` + обновление таблицы в техпаспорте (если менялся публичный маршрут).
3. **API:** метод(ы) в `client.ts`, типы в `types.ts` или рядом с фичей.
4. **Данные:** хук(и) с Query/Mutation и инвалидацией.
5. **UI:** Mantine + каноны из `TECH_PASSPORT_FRONTEND_UI_LOGIC.md`; при затрагивании правой панели — сверка с shell-документом.
6. **DOMAIN_STANDARDS:** для страницы известен тип (SCHEDULE, CRM, …) — пройти релевантный чеклист или зафиксировать отклонение.
7. **Тест:** минимум один тест или обоснование в PR (см. DoD выше).
8. **§7:** не нарушено; если нарушено — эпик и явное согласование.
9. **QA_ARCH:** при готовности к merge — блок DoD в PR заполнен (в т.ч. состояния UI для списков при наличии в diff).
