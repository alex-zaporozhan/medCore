## 1) Принцип

Фронтенд (SPA + PWA) **не заменяет** SLO API, БД и очередей. Программа 8W в основном про **серверную** надёжность и наблюдаемость; фронт вносит вклад через: дисциплину маршрутов, единый клиент, корреляцию запросов, UX при ошибках, и (позже) наблюдаемость в браузере.

## 3) Бэкенд / прокси: приём `X-Request-Id`

Фронт уже отправляет **`X-Request-Id`** на исходящие запросы (`frontend/src/api/client.ts`), если заголовок не задан вызывающим кодом.

**Следующий шаг (отдельная задача на бэкенд/OPS):**

1. **Логирование:** при логировании запроса писать `request_id` из заголовка `X-Request-Id` (или fallback), тот же id — в structured log и в ответ при ошибках рядом с `trace_id`.
2. **Прокси / ingress:** проброс заголовка без обрезки; при генерации id на edge — согласовать с фронтом (кто master: клиент или шлюз).
3. **Приёмка:** по одному инциденту можно найти цепочку: браузерный id → access log → app log (см. Week 5 критерий «полный trace»).

Это **не блокирует** фронт; усиливает Week 5 без изменения контракта API.

## 6) Перформанс «на потом» (фундаментальные направления)

Ниже — не обещания в релизе, а **кандидаты в эпики** после согласования LEAD и привязки к Week 6 (budgets) / Week 8 (evidence). Частично пересекается с §2.

| Направление | Зачем |
|-------------|--------|
| **Code-splitting маршрутов** (`React.lazy` / границы админка vs PWA) | Снять предупреждение Vite о крупном чанке, улучшить TTI на «холодном» входе. |
| **Бюджеты бандла в CI** (`rollup-plugin-visualizer` / лимиты kB по чанкам) | Регрессии размера ловить до продакшена. |
| **Web Vitals (LCP, INP, CLS) на ключевых URL** | Объективная метрика вместо субъективного «тормозит»; связка с Week 8 scorecard. |
| **Prefetch / приоритет загрузки** для 1–2 критичных потоков (запись, лента) | Уменьшить ощущаемую задержку без перегруза сети. |
| **Виртуализация длинных списков** (CRM, логи, история) где уже есть доменная потребность | Стабильный FPS и память на тяжёлых экранах. |
| **Политика `staleTime` / `gcTime` по доменам** в TanStack Query | Меньше лишних запросов при навигации; согласовать с UX «свежести» данных. |
| **Оптимизация ассетов** (изображения витрины/лендинга, шрифты — subset/preload по необходимости) | Меньше байт на first paint. |
| **PWA / SW:** пересмотр `runtimeCaching` при росте API-поверхности | Избежать устаревшего кэша API и лишних сетевых дублей. |
| **Длинные запросы без глобального таймаута** | Оставить как сейчас до эпика; когда появится — **per-hook / per-route** `AbortSignal` + SLA (см. §2). |

Дополнительно: **k6** или нагрузочные сценарии против стенда «фронт + API» — по Week 6, после стабилизации маршрутов.

## 7) Предложения по фундаментальному перформансу («на потом», @QA_ARCH)

Список для бэклога после согласования LEAD; пересечение с §2 и §6 — намеренно (разные уровни детализации).

- **Разделение чанков по зонам** — `React.lazy` + границы по `/admin` vs `/app` vs маркетинг, без смешения критичного и редкого в одном initial chunk.
- **Бюджеты размера в CI** — лимиты kB на main/vendor и порог регрессии; `rollup-plugin-visualizer` / отчёт в артефактах CI.
- **Web Vitals (LCP, INP, CLS)** на 3–5 ключевых URL — снимок в evidence pack (Week 8), не только субъективный «тормозит».
- **Prefetch / приоритет** для 1–2 критичных потоков (запись, лента) — без перегруза сети на слабых каналах.
- **Виртуализация** таблиц и длинных списков (CRM, логи, история) там, где доменная нагрузка уже подтверждена.
- **Политика TanStack Query по доменам** — `staleTime` / `gcTime` не только глобальные из `main.tsx`; согласование с UX «свежести».
- **Ассеты витрины** — форматы изображений, lazy decode, шрифты (subset/preload по необходимости).
- **PWA / SW** — пересмотр `runtimeCaching` при росте API-поверхности; стратегия обновления SW после деплоя.
- **Таймауты и `AbortSignal`** — per-класс запросов (отчёты vs мутации), не глобальный «нож» для всех (см. §2).
- **Контроль main thread** — профилирование long tasks; отложенная гидратация тяжёлых виджетов админки при необходимости.
- **Наблюдаемость перформанса в браузере** — после Week 5 API: выборочный RUM или связка с trace (без дублирования полного OTel из §2 до готовности бэкенда).

## 8) Дополнительные предложения по фундаментальному перформансу («на потом», @QA_ARCH)

Ниже — **ещё** кандидаты в бэклог (дополняют §6–§7; без обязательства срока). Согласование с LEAD; привязка к Week 6 (budgets) / Week 8 (evidence).

| # | Предложение | Комментарий |
|---|-------------|-------------|
| 1 | **Long tasks / main thread** | Профилирование `PerformanceObserver` на критичных потоках (запись, CRM); точечная разгрузка тяжёлых обработчиков. |
| 2 | **Dynamic import тяжёлых библиотек** | Графики, редакторы, карты — только при входе на экран/вкладку, не в initial bundle. |
| 3 | **Контракт списков с бэкендом** | Cursor pagination и верхние границы `page_size` для новых больших таблиц; избегать «подтянуть всё» на клиент. |
| 4 | **INP и тяжёлые фильтры** | Debounce/throttle поиска и фильтров в админке; не блокировать ввод длинными синхронными пересчётами. |
| 5 | **Мемоизация по факту профиля** | `React.memo` / селекторы на границах строк таблицы и колонок Kanban после измерений, не «оптимизация вслепую». |
| 6 | **Web Worker для редких тяжёлых задач** | Только при явном кейсе (большой парсинг CSV на клиенте и т.п.); не дефолт. |
| 7 | **Шрифты и LCP** | Subset, `font-display`, preload только для критичного текста above-the-fold на лендинге. |
| 8 | **HTTP-кэш статики** | Политики CDN для hashed assets (`immutable`); согласовать с деплоем и версией PWA. |
| 9 | **Сценарии «медленная сеть»** | Периодический smoke / k6 + throttling для проверки UX при деградации (связь с Week 6). |
| 10 | **Единая матрица «тяжёлый экран»** | Список экранов из `DOMAIN_STANDARDS` / NFR §11 с обязательным замером Web Vitals перед крупными релизами. |
