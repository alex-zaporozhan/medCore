# DEV Артефакт: “Мини-календарь везде” (roadmap 2026)

## Контекст
Цель дорожной карты: единый UX-подход к календарям в админке (мини-календарь + компактный time-picker + запрет overlap через backend).

## Ограничение по scope на текущую волну
Owner-driven scope для “администраторы не могут создавать собрания на всех” запланирован как отдельная часть в **P6** (см. `DEV_EXECUTION_PLAYBOOK_2026.md` про порядок фаз).
На этой итерации **не реализуем** owner-scope в коде. (Просто учитываем UX/поведение так, чтобы он не блокировал дальнейшую P6-работу.)

### Куда именно “пойдет” owner-scope в P6 (принятое решение)
- “Администраторы” (обычные работники) по умолчанию **не** имеют права создавать групповые события “на всех”.
- Возможность будет задаваться Владельцем в настройках политики конфиденциальности:
  - владелец выбирает, кого из персонала можно считать “руководителем” / кто может создавать групповые события;
  - по умолчанию это будет только Владельцем (т.к. реальных “руководителей” в данных сейчас нет);
  - если владелец захочет — сможет расширить доступ на конкретных администраторов.

## Реализовать сейчас (P1 Staff Core, минимум с приемкой)

### 1) Kanban -> Staff calendar: “В календарь” с auto-open create
Нужно добавить кнопку в **Kanban-карточку задачи** (в `AdminTasksPage`) для создания staff-calendar события:
- клик открывает `AdminStaffCalendarPage` с `task_id` в query;
- дополнительно передаёт флаг `open_create=1`, чтобы страница **автоматически открыла** модалку создания;
- `task_id` в модалке должен быть prefilled (он уже поддержан страницей через `task_id` в query).

### 2) Kanban prefill участников из задачи
Для staff-calendar события поле `participant_admin_ids` должно быть prefilled из задачи.

Правило (простыми словами):
- “Участники задачи” = **реальные люди**, назначенные на задачу.
- В API задачи это соответствует `assignee_ids` (junction) и/или `assignee_id` (legacy одиночный исполнитель).
- `role_assignee` — это “очередь по роли” (не конкретные люди), поэтому для prefill **не используем**.

Точное правило для prefill:
- если `task.assignee_ids` непустой -> используем `task.assignee_ids`;
- иначе если `task.assignee_id` задан -> используем `[task.assignee_id]`;
- иначе prefill пустой список (организатор попадёт в participants сервером).

### 3) Авто-open create: когда и чем предзаполняем
`AdminStaffCalendarPage` при `open_create=1` должен:
- открыть modal создания (режим `create`);
- если у задачи есть `due_at` — предзаполнить дату события (ISO `YYYY-MM-DD`) и скрыть выбор месяца (как при create “из выбранного дня”);
- если у задачи есть assignee’ы и у текущего админа есть право `invite_staff_calendar_participants` — prefill MultiSelect участниками.

## Бэкенд / API
Используем текущие контракты staff calendar:
- `POST /v1/admin/staff/calendar/events` (create)
- `PATCH /v1/admin/staff/calendar/events/{id}` (update)
- overlap возвращается `400` с `detail="Событие пересекается..."` (trace_id может отсутствовать на business-ошибках; UI должен показывать `detail`).

Для prefill задач:
- используем `GET /v1/admin/tasks/{task_id}` (у него уже есть endpoint в `admin_tasks.py`).

## Definition of Done (минимум)
1. В Kanban карточке задачи появляется кнопка “В календарь”.
2. После клика открывается staff calendar create modal с prefilled `task_id`.
3. Если у задачи есть assignee’ы и право `invite_staff_calendar_participants` выдано — MultiSelect участников предзаполнен.
4. Owner-scope в create/patch **не трогаем** (P6 отложен).
