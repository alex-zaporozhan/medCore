## 1. Краткий вывод (состояние «как есть»)

Продукт несёт **зрелые элементы** (разделение контуров платежей, governance секретов на старте, transactional outbox с `dedup_key`, метрики, опциональная read-replica для отчётов, явный RBAC/мультитенантность на уровне приложения). При этом в бэкенде остаются **жёсткие логические и схемные противоречия**, несколько **P0-рисков целостности данных** и систематический **технический долг по асинхронности и границам транзакций**, которые при нагрузке или эволюции статусов бронирования всплывают как инциденты, а не как «краевые случаи».

Проход **QA_ARCH** добавляет фокус на **индустриальные сбои**: деньги и провайдер (YooKassa), семантика HTTP вебхуков (ретраи PSP), порядок внешнего вызова и коммита БД, и **двойной контур CI** (Jenkins как источник релиза vs GitHub Actions как PR-гейт) — там, где «зелёный» PR не гарантирует идентичный сценарий с прод-пайплайном.

Третий проход по признакам **@PRINCIPLE** (`docs/ROLE_PRINCIPLE.md`: SILENT FAILURES, G3 «несколько источников», REPORT grain) добавил **P1-5** и п. **3.12–3.17** (уведомления, EventBus/outbox, брокер, идемпотентность вебхука, логи, replica).

**Четвёртый проход** (раздел 8 ниже) закрывает запрошенный фокус **omnichannel + ERP + импорт** приоритетно для **стабильности каналов/чатов** и **бизнес-инструментов** (G1 state / G4 grain отчётности); сырость фронта вне scope этого файла, но перечислены контракты API, которые фронт обязан честно отражать.

Ниже — аргументированный разбор от «А» (модель данных и инварианты) до «Б» (операционная безопасность и наблюдаемость), плюс блок корпоративной эксплуатации.

## 2. Критические и высокие риски (P0 / P1)

### P0-1. Уникальный ключ слота бронирования против бизнес-логики «слот свободен после отмены»

**Факты в коде и схеме**

- В модели `Booking` задан жёсткий уникальный ограничитель `(doctor_id, appointment_date, appointment_time)` (`ux_bookings_doctor_slot`), без учёта статуса и без `deleted_at` (см. `src/domain/entities/booking.py`).
- Отмена бронирования переводит статус в `CANCELLED`, **не меняя** дату/время и **не выставляя** `deleted_at` (см. `BookingService.cancel_booking` в `src/application/services/booking_service.py`).
- Проверка занятости слота `_ensure_slot_available` **игнорирует** только статус `"cancelled"` и считает слот свободным для новой записи.

**Противоречие**

После отмены запись с тем же `(doctor_id, date, time)` **остаётся в таблице**. Вставка нового бронирования на тот же слот **должна упасть** на уровне БД с нарушением уникального ограничения, хотя прикладная логика считает слот свободным. Это либо **блокировка повторной записи на слот** (функциональный дефект), либо **нестабильное поведение** (если где-то обходят проверку или ловят `IntegrityError` не везде).

**Вердикт PRINCIPLE:** это не «доработка UX», а **нарушение инварианта домена**: либо уникальность должна быть **частичной** (например, только для «активных» статусов), либо отмена должна **освобождать ключ** (смена времени, архивная таблица, soft-delete с исключением из уникальности). Текущая связка — **логически неконсистентна**.

### P0-2. Синхронный HTTP-клиент YooKassa внутри async-потока (блокировка event loop)

**Факты**

- `YooKassaClient` документирован как sync и предполагает использование с executor или из Celery (`src/infrastructure/external_apis/yookassa_client.py`).
- `PaymentService.handle_webhook` и платформенный биллинг вызывают `yookassa.get_payment(...)` **напрямую** из async-кода (`src/application/services/payment_service.py`, `src/application/services/platform_billing_service.py`).

**Риск**

При задержках API ЮKassa или всплеске вебхуков **все воркеры uvicorn** могут простаивать в ожидании I/O, деградируя латентность **всего** API, не только платежей.

**Вердикт:** расхождение между **документацией модуля** и **фактическим использованием** — признак архитектурного долга; для production SaaS это типичный **P0 по SLO**.

**Дополнение QA_ARCH:** тот же sync-клиент вызывается из **`PaymentService.create_payment`** и при **публичном SaaS checkout** (создание intent + `create_platform_subscription_payment` в `platform_billing_service.py`). Любой всплеск трафика на эти ручки масштабирует блокировку event loop **линейно** с числом запросов, а не только с вебхуками.

---

### P0-3. Вебхук платежа: успешный HTTP-ответ при невозможности подтвердить состояние у провайдера

**Факты**

- **Контур A** (`PaymentService.handle_webhook`): при `YooKassaClientError` на `get_payment` логируется исключение и выполняется **обычный `return`** без проброса ошибки (`src/application/services/payment_service.py`).
- Роут `POST /payments/webhook` после вызова сервиса отдаёт **`PaymentWebhookOkResponse` (2xx)** если не было иного исключения (`src/api/v1/routers/payments.py`).
- **Контур B** (`apply_platform_yookassa_notification`): при ошибке `get_payment` — `return None`, затем `handle_platform_billing_webhook_two_phase` всё равно делает **`session.commit()`** и завершается; HTTP-обработчик возвращает успешный ответ (`platform_billing_service.py`, `platform_billing.py`).

**Риск**

Платёжная система часто **прекращает ретраи вебхука** после ответа 2xx. Если в момент вызова API провайдер недоступен или вернул ошибку, **автоматическая доставка «истины» о платеже теряется** до ручной/фоновой сверки. Для бронирования это «запись не подтвердилась при списании»; для SaaS signup — **организация не провижнена при оплаченном интенте** (частично смягчается Celery `retry_due_provisions` / outbox, но это уже операционный долг и задержка time-to-value).

**Вердикт QA_ARCH:** для корпоративного уровня ожидается либо **5xx / повторяемая ошибка** до успешной верификации (с идемпотентностью обработчика), либо явная **очередь reconciliation** с метриками и алертом «webhook acknowledged without provider verify» — текущее «молча 2xx» — **P0 по финансовой согласованности**.

### P1-1. Гонка двух одновременных бронирований одного слота (TOCTOU)

**Факты**

- `_ensure_slot_available` читает список бронирований и решает, свободен ли слот; затем отдельно выполняется `INSERT` (`BookingRepositoryImpl.create` → `flush`).
- Уникальный индекс **частично** защищает от двойной записи, но:
  - при «живых» статусах (не отмена) два параллельных запроса получают один и тот же исход до `flush`;
  - один получит `IntegrityError`, второй — успех; обработка на уровне API/сервиса должна быть **единообразной** и пользовательски понятной (сейчас это не очевидно из слоя сервиса).

**Вердикт:** без явного `SELECT … FOR UPDATE` по ключу слота или без **детерминированной** обработки `IntegrityError` как «слот занят» ответ клиенту будет непредсказуем (500 vs доменная ошибка).

---

### P1-2. Расхождение статусов в проверке слота

**Факты**

- В `_ensure_slot_available` занятость определяется условием `b.status != "cancelled"`.
- В домене объявлен набор расширенных статусов (`canceled_by_patient`, `canceled_by_clinic`, `blocked`, и т.д. в `BookingStatus`).

**Риск**

Бронирование в статусе, который **по смыслу** не должен держать слот (например, отмена с другим литералом), может **блокировать** слот на уровне приложения, хотя по продуктовой модели слот уже «свободен». Это **нестыкуемость enum ↔ бизнес-правил**.

**Уточнение по коду:** в `_ensure_slot_available` сравнение идёт с **строковым литералом** `"cancelled"` (`booking_service.py`); статусы вроде `canceled_by_patient` / `canceled_by_clinic` **не освобождают** слот в этой проверке — при этом уникальный индекс по-прежнему держит строку в таблице, что усиливает конфликт с P0-1 при расширении жизненного цикла.

---

### P1-3. Шифрование секретов клиники от `SECRET_KEY` (ротация и blast radius)

**Факты**

- `encrypt_plaintext` / `decrypt_ciphertext` строят Fernet-ключ от `settings.secret_key` (`src/core/encryption.py`).
- Секреты ЮKassa клиник хранятся зашифрованными этим ключом.

**Риск**

- Смена `SECRET_KEY` **инвалидирует** все сохранённые per-clinic секреты без миграции.
- Компрометация `SECRET_KEY` раскрывает **и сессии/подписи**, и **все платёжные ключи клиник** сразу (большой blast radius).

**Вердикт:** для SaaS с per-tenant секретами ожидаем отдельный **KMS / ключ шифрования данных** (или envelope encryption), не смешанный с «секретом приложения».

---

### P1-4. Создание платежа: сначала внешний провайдер, затем фиксация строки в БД

**Факты**

- В `PaymentService.create_payment` вызывается **`yookassa.create_payment(...)`**, и только после успешного ответа создаётся сущность **`Payment`** и обновляется `booking` (`src/application/services/payment_service.py`).
- Аналогичный порядок при **checkout платформы**: создание платежа в YooKassa, затем запись состояния в БД в том же сценарии (`platform_billing_service.py`, публичный signup).

**Риск**

При падении процесса или БД **после** успешного ответа провайдера и **до** коммита транзакции приложения возможны **«осиротевшие» платежи у провайдера** без связанной строки `payments` / без корректной привязки к брони или intent. Ретраи клиента упираются в **Idempotence-Key = `booking_id`** (см. п. 3.5) — частично защищает от дублей, но не снимает класс инцидентов **reconciliation** и нагрузку на саппорт.

**Вердикт:** для enterprise-потока «деньги» ожидают либо **saga / компенсирующие** шаги, либо идемпотентная запись «ожидающего платежа» в БД до вызова провайдера с последующим доведением статуса — текущий порядок повышает **операционный** риск.

---

### P1-5. Уведомления: «успех» и статус `sent` при фактическом отсутствии доставки (silent failure)

**Факты**

- `send_with_fallback` документирован так: при отсутствии настроенных отправителей и ни одной попытке доставки возвращается **`(True, None)`** — «чтобы не крашить» (`src/application/services/notification_service.py`, ветка `delivered via log only`).
- Celery-задачи уведомлений (`_send_notification_async` в `src/infrastructure/messaging/tasks/notifications.py`) при `success` выставляют запись **`Notification.status = "sent"`**.

**Риск (PRINCIPLE: SILENT FAILURES / G2–G3)**

Операционно и в отчётах выглядит как **успешная коммуникация с пациентом**, тогда как каналов не было или контакты пусты. Для медицинского контура это класс **«тихо не доставили напоминание / подтверждение»** — юридический и репутационный риск сильнее, чем «просто логирование».

**Вердикт:** разделить **техническое завершение задачи** и **бизнес-доставку**: отдельный статус вроде `skipped_no_channel` / `degraded`, метрика и алерт, запрет считать такой исход `sent` без явной политики продукта.

## 3. Средние риски и упущения (P2)

### 3.1. Глобальный singleton Redis-клиент (кроме TESTING)

**Факты:** `get_redis` держит один `_redis_client` на процесс (`src/infrastructure/database/redis_client.py`).

**Риски:** при редком пересоздании event loop, тестах с несколькими loops, горячей перезагрузке — класс проблем «клиент привязан к другому loop». В TESTING создаётся новый клиент на вызов — **асимметрия** поведения test vs prod.

---

### 3.2. Rate limiting: fail-open при ошибке Redis

**Факты:** `RateLimiter.check_or_raise` при любой ошибке Redis пропускает запрос (`src/infrastructure/rate_limiter.py`).

**Торговля:** доступность vs безопасность. Для **логина и вебхуков** это сознательное ослабление периметра при деградации Redis — нужен явный **операционный контракт** (алерты, circuit breaker, жёсткий режим для критичных маршрутов).

---

### 3.3. Расписание в Redis: cache-aside без строгой связки с транзакцией БД

**Факты:** `ScheduleService` кладёт сериализованное расписание в Redis с TTL 5 минут; инвалидация при создании/отмене бронирования best-effort (`src/application/services/schedule_service.py`).

**Риск:** при сбое Redis между коммитом БД и инвалидацией клиент может видеть **устаревшую сетку слотов** до истечения TTL (окно неконсистентности). Для записи на приём это **продуктовый риск**, не только кэш-мисс.

---

### 3.4. JWT: ручная валидация `iss`/`aud` поверх `jwt.decode` с отключенной проверкой

**Факты:** `parse_access_token` отключает `verify_aud` и `verify_iss` в PyJWT и валидирует вручную (`src/core/security.py`).

**Риск:** при будущих изменениях библиотеки или дублировании путей разбора токена выше шанс **расхождения** с канонической семантикой JWT. Режим `jwt_legacy_allow_missing_iss_aud` добавляет **долгий переходный периметр**, который легко забыть выключить.

---

### 3.5. Idempotence-Key в ЮKassa = только `booking_id`

**Факты:** при создании платежа ключ идемпотентности — `str(booking_id)` (`yookassa_client.create_payment`).

**Риск:** повторное создание платежа для той же записи бронирования (повторный клик, ретрай клиента) упрётся в **идемпотентность провайдера**, а не в явную доменную модель «новая попытка оплаты = новый ключ». Это может **блокировать** смену суммы/политики без обходных путей.

---

### 3.6. Outbox: пост-диспетч после commit без гарантии доставки в том же процессе

**Факты:** `get_session_payment_webhook` / `get_session_booking_domain_outbox` коммитят, затем вызывают `dispatch_domain_outbox_batch`; при исключении логируется и полагаются на Celery (`src/api/v1/dependencies.py`).

**Риск:** корректно для outbox-паттерна, но **мониторинг и SLO** на «время от коммита до side-effect» должны быть явными; иначе операционно кажется «всё сохранилось», а downstream **молчит**.

---

### 3.7. Отмена бронирования: локальное время сервера

**Факты:** `cancel_booking` использует `datetime.now()` для сравнения с датой/временем слота (`booking_service.py`).

**Риск:** при несогласованности TZ сервера и бизнес-логики клиники возможны **ошибочные отказы** или разрешение отмены «в прошлом» относительно UTC.

---

### 3.8. Мультитенантность только на уровне приложения

**Факты:** изоляция клиник строится на проверках `clinic_id` и репозиториях; в выборке **нет** Postgres RLS в рассмотренном коде.

**Вердикт:** при ошибке в одном запросе (пропущенный фильтр) риск **cross-tenant утечки** выше, чем при defense-in-depth на уровне БД. Это не баг само по себе, но **упущение глубины защиты** для SaaS с медицинским/PII контуром.

---

### 3.9. Двойной контур CI: Jenkins (релиз) vs GitHub Actions (PR)

**Факты**

- Канон репозитория: **релизные образы и деплой — Jenkins** (`Jenkinsfile`, `CI_CD.md`); в Jenkins для backend зафиксированы шаги вроде `ruff`, узкий `mypy` по файлу, **`pytest`** с `--maxfail=1`.
- Параллельно в `.github/workflows/` включены **другие** workflow (узкий набор тестов + полный suite в `build-and-test-entitlements.yml`, `backend-ci.yml`, release gate и т.д.).

**Риск**

В корпоративной практике это классический **drift quality gates**: PR может быть «зелёным» по одному набору, а релизный Jenkins — остановиться на другом; либо наоборот, локально разработчик ориентируется на GHA, а **боевой** контур не совпадает по флагам окружения, таймаутам, версии Postgres/Redis в job. Для аудита и постмортемов важно иметь **единую матрицу** «что обязательно везде».

---

### 3.10. Celery: изоляция async через новый event loop на задачу

**Факты**

- В `notifications.py` sync-обёртка `_run_async` создаёт **`asyncio.new_event_loop()`** на каждую задачу, выполняет корутину и закрывает loop.
- В `celery_app.conf.update` **не заданы** явно `task_time_limit`, `task_acks_late`, `worker_prefetch_multiplier` и т.п. — поведение по умолчанию зависит от версии Celery и брокера.

**Риск**

- Частое создание loop + сессий БД увеличивает **накладные расходы** и усложняет диагностику утечек при ошибках в сторонних клиентах.
- Дефолты Celery без явной политики — риск **двойной доставки** или потери задач при kill воркера в зависимости от настроек брокера (для денег и уведомлений это должно быть **документированно** и покрыто тестами идемпотентности).

---

### 3.11. JWT: переходный режим `jwt_legacy_allow_missing_iss_aud` по умолчанию `true` в коде настроек

**Факты**

- В `Settings` поле `jwt_legacy_allow_missing_iss_aud: bool = True` (`src/core/config.py`).

**Риск**

При выкатке в production команда может **забыть** выставить `false`, оставив расширенный периметр приема токенов без `iss`/`aud` дольше запланированного. Для корпоративного security review это **явный finding**: дефолт должен быть **fail-closed** для `app_env=production` или подкреплён политикой деплоя/чеклистом.

---

### 3.12. In-process `EventBus` и горизонтальное масштабирование API (PRINCIPLE: G3, несколько источников правды)

**Факты**

- `EventBus` — **один глобальный объект в памяти процесса**; подписчики и публикация не выходят за пределы воркера (`src/application/events/event_bus.py`).
- Согласовано с фундаментальным обзором: при **нескольких репликах** uvicorn событие, опубликованное на реплике A, **неизвестно** реплике B; повтор запроса к другой реплике даёт **недетерминированное** поведение, если бизнес полагался на side-effect в том же процессе.

**Риск**

Любой оставшийся путь «HTTP commit → in-process bus» (или хендлер, создающий **новую** сессию без outbox) воспроизводит **частично применённую** цепочку. Критичные цепочки уже частично вынесены в outbox — остаётся **долг** по полному покрытию и по тестам «multi-worker». См. также `docs/architecture/FUNDAMENTAL_CODE_REVIEW_PRINCIPLE.md`, раздел 2.2.

---

### 3.13. Domain outbox: потолок попыток по умолчанию выключен (`DOMAIN_OUTBOX_MAX_DISPATCH_ATTEMPTS=0`)

**Факты**

- В `Settings` значение по умолчанию **`domain_outbox_max_dispatch_attempts: int = 0`** трактуется как **отсутствие верхней границы** попыток dispatch (`src/core/config.py`, логика `cap > 0` в `domain_outbox_service.py`).

**Риск**

«Ядовитое» событие или постоянно падающий хендлер → **бесконечные** ретраи, шум в логах, нагрузка на БД и воркеры без перевода в явный **DLQ / ручной разбор**. Для корпоративной эксплуатации ожидается явный cap + runbook «что делаем со строками за cap».

---

### 3.14. Celery `task.delay` из HTTP-потока: потеря задачи при недоступности брокера

**Факты**

- В `BookingService` вызовы `send_booking_created_task.delay(...)` / `send_booking_cancelled_task.delay(...)` обёрнуты в **`try/except Exception`** с уровнем `warning` без повторной постановки в outbox (`src/application/services/booking_service.py`).

**Риск**

Кратковременный отказ Redis/RabbitMQ → **запись в БД есть, уведомление не поставлено**, пользователь не увидит ошибки API. Это другой класс **silent failure** (PRINCIPLE), смежный с P1-5: деградация коммуникаций без явного статуса в доменной модели.

---

### 3.15. Вебхук платежа: нет отдельного идемпотентного ключа на уровне HTTP-тела

**Факты**

- Обработка опирается на идемпотентность провайдера и логику сервиса по `provider_payment_id` (см. обсуждение в `docs/architecture/FUNDAMENTAL_CODE_REVIEW_PRINCIPLE.md`, раздел 2.3: уникальный ключ на `payments`).

**Риск**

При расширении веток (частичный возврат, смена суммы, дублирующиеся `notification` от PSP) выше вероятность регрессии **двойного побочного эффекта**, если не зафиксированы тесты «двойной webhook» и не хранится dedup по сырому телу/заголовку там, где это требует политика PSP.

---

### 3.16. Логирование превью сообщений уведомлений

**Факты**

- При отсутствии отправителей в лог пишется **`message_preview`** (первые 80 символов текста) (`notification_service.py`).

**Риск**

В прод-логах (централизованный сборщик) возможна утечка **PII/PHI** из текста напоминаний. Для enterprise-заказчика это типичный finding по **data minimization** в логах.

---

### 3.17. Read-replica: устаревшие чтения для операционных решений

**Факты**

- Reporting-сессии идут на **опциональную реплику** с `statement_timeout` (`get_db_reporting`, `base.py`).

**Риск**

Если фронт или интеграция использует «отчётные» GET для **немедленного** решения после записи на primary (например «проверить баланс/лимит»), возможен **read-your-writes** разрыв. Нужен явный контракт: какие экраны на replica, какие только на primary.

## 4. Архитектурные и «PRINCIPLE»-замечания (качество решений)

1. **Двойные контуры платежей (A/B)** — сильное архитектурное решение; при этом любая **общая утилита** без жёсткого разделения секретов и URL вновь сводит риски (частично нивелировано governance на старте — см. `src/core/payment_webhook_governance.py` и `main.py`).

2. **Слой «сервис + репозиторий»** при глобальном `get_db` с авто-коммитом упрощает CRUD, но размывает границу «одна бизнес-операция = одна транзакция с явным сценарием отката» — важно держать **явные use-case** для денежных и слотовых потоков.

3. **Entitlement enforcement** (`legacy` / `auto` / `strict` в настройках) — типичный rollout-флаг; риск в том, что **поведение одной и той же ручки** зависит от данных организации без явного ответа клиенту «режим X» — усложняет саппорт и регрессию.

4. **Обработчики событий в памяти** (`get_event_bus` при отключенном outbox) vs outbox — два мира; документация ADR помогает, но **кодовые пути** должны оставаться минимальными, иначе тесты покрывают не ту ветку, что в проде.

5. **`get_db` коммитит после каждого запроса**, включая read-only сценарии (`src/infrastructure/database/base.py`): это нормальная схема для FastAPI, но для тяжёлых GET с долгими сессиями увеличивает окно удержания транзакции и нагрузку на primary; отчёты вынесены на `get_db_reporting` — канонично, но **любой** забытый reporting-DSN на записывающем контуре возвращает к риску нагрузки на мастер.

6. **Связка с ролью @PRINCIPLE** (`docs/ROLE_PRINCIPLE.md`): диагностический порядок *STATE MACHINE → MONEY → RACE → TENANT → SILENT → REPORT GRAIN* — блоки **SILENT / G3 / REPORT** дополнены разделом **8** (omnichannel, ERP, импорт). Остаются узкие хвосты: полный перебор всех веток **OmnichannelAIOrchestrator**, всех провайдеров **IntegrationGateway**, полный матричный тест ERP по видам витрин — при необходимости вынести в отдельный тикет/артефакт.

## 7. Заключение от лица техлида

Бэкенд выглядит как **активно развиваемый SaaS-каркас** с сознательными элементами безопасности и выносом критичных событий в outbox. Однако **схема БД бронирований в текущем виде противоречит основному жизненному циклу (отмена → новая запись на слот)**, а **синхронные вызовы платёжного API из async** — это угроза стабильности всей плоскости API. Эти два пункта — не «полировка», а **блокеры зрелости** для позиционирования как надёжного бэкенда под коммерческий SaaS.

Третий блокер уровня **финансовых и юридических** рисков — **успешный ответ вебхука при невозможности верифицировать платёж у провайдера** (контуры A и B): без явной политики ретраев и сверки это превращается в ручной разбор и недоверие к автоматизации.

Документ подготовлен по статическому анализу репозитория; для финальной верификации P0-1 достаточно интеграционного теста: *создать бронь → отменить → создать снова на тот же слот* и зафиксировать ответ БД/ORM. Для **P0-3** — тест или стенд: симулировать `get_payment` → ошибка и убедиться, что PSP/прокси видит **не-2xx** либо что срабатывает **явная** фоновая сверка с метрикой «ack без verify».

Каналы и бизнес-отчёты: см. **раздел 8** и чеклист **раздел 9** (omni / ERP / импорт).

## 8. Четвёртый проход: omnichannel, ERP, импорт (стабильность каналов и бизнес-инструментов)

**Метод:** выборочное чтение `OmnichannelOutboundDispatcher`, `OmnichannelChatService`, `admin_omni_chat`, `omni_pubsub`, `WebchatPushManager`, `ErpAggregateService` / `erp_refresh_lock`, `erp_tasks`, `CsvImportService`, `admin_commerce` (импорт). **PRINCIPLE:** G1 (статусы чата/сообщения/доставки), G3 (HTTP + Redis + in-memory), G4 (агрегаты vs сырые факты), SILENT (201 без доставки).

---

### 8.1. Omnichannel: HTTP 201 и строка в БД при «немой» недоставке (SILENT / G1)

**Факты**

- `POST .../omni-chats/{chat_id}/messages` (`send_admin_omni_message` в `src/api/v1/routers/admin_omni_chat.py`): сначала `append_outbound_message` **персистит** исходящее сообщение и публикует `publish_omni_message_created`, затем вызывается `OmnichannelOutboundDispatcher.dispatch_to_channel`.
- В `dispatch_to_channel` и адаптерах многие отказы — **ранний `return` после логирования** (нет `channel_id`, нет чата/канала, нет `telegram_user_id`, нет токена, пустой текст для Telegram и т.д.) — см. `src/application/services/omnichannel_outbound_dispatcher.py`.
- При неуспехе Telegram после ретраев функция возвращает `False` и **выходит без** установки в метаданных явного финального статуса «FAILED» для всех веток (успех для текста проставляет `delivery_status`/`delivery_channel` только в ветке успешного POST).

**Риск**

Клиент API получает **201 Created** и DTO сообщения; в ленте чата сообщение **существует**, но пациент/виджет мог **не получить** доставку. Это расхождение **ожидания оператора** и **фактического канала** — типичный инцидент «написал — молчит клиент» без явного флага в UI, если фронт не интерпретирует `source_metadata` и не доработан.

**Вердикт:** для корпоративного inbox нужна **единая модель доставки** (pending → sent/failed + причина), а не только успешные ветки; метрика `omni_outbound_dispatch_failed_total` с низкой кардинальностью по причине.

---

### 8.2. Webchat WEB_WIDGET: in-memory long-poll и «DELIVERED» (G3 / масштаб)

**Факты**

- `WebchatPushManager` документирован как **singleton в памяти процесса**; явно предупреждено, что при нескольких инстансах uvicorn long-poll на одном воркере **не увидит** `notify` с другого (`src/application/services/webchat_push_manager.py`).
- `_dispatch_webchat` после `manager.notify(...)` выставляет в `source_metadata` **`delivery_status: DELIVERED`** и делает `flush` — это означает «уведомили ожидающий long-poll в **этом** процессе», а не доставку до браузера end-to-end.

**Риск**

Под балансировщиком с N репликами виджет **нестабилен** без Redis (или иного) fan-out на все воркеры. Текущее `DELIVERED` **переоценивает** гарантию доставки.

**Вердикт:** либо зафиксировать в эксплуатации **строго один** API-воркер для публичного webchat, либо реализовать заявленный в файле переход на **Redis pub/sub по chat_id** (как уже сделано для admin SSE в `omni_pubsub.py`, но это **другой** канал).

---

### 8.3. Redis pub/sub для admin SSE: fail-open (G3)

**Факты**

- `publish_omni_message_created` / `publish_omni_chat_updated` при ошибке Redis логируют **warning** и **проглатывают** исключение (`src/infrastructure/realtime/omni_pubsub.py`).

**Риск**

Админский inbox **не обновится в реальном времени**, хотя HTTP-мутация прошла — снова **silent degradation**; без алерта на частоту `omni realtime publish failed` это выглядит как «глючит фронт».

---

### 8.4. ERP витрины: блокировки и зерно отчёта (G4)

**Факты**

- Ручное/оконное обновление витрин сериализуется **advisory lock на клинику** в транзакции (`src/application/services/erp_refresh_lock.py` + `erp_tasks.refresh_clinic_erp_aggregates_window`).
- Ночной проход и выборочная parity sample — Celery (`erp_tasks.py`); `ErpAggregateService` позиционируется как **идемпотентный refresh** из канонических запросов репозитория.

**Риски (не баги, а эксплуатационные)**

- Между изменением сырых фактов (бронь, оплата, склад) и ночным refresh витрин есть **окно лага**; если UI смешивает «сырьё» и «витрину» на одном экране без подписи, пользователь увидит **расхождение** (G4).
- Сбой ночного таска без жёсткого алерта → длительное **устаревание KPI** при «зелёном» API.

**Вердикт:** явный **SLO** («витрина не старше T часов») + дашборд по `erp_aggregate_*` метрикам и failed nightly.

---

### 8.5. Импорт: CSV расписания vs commerce CSV (G1 / TENANT)

**Факты**

- **`CsvImportService.import_schedule_from_csv`**: при первой ошибке строки — **остановка всего импорта** (`break` + `job.status = "failed"`), MVP-поведение (`src/application/services/csv_import_service.py`). Для части сценариев используется получение «дефолтной» клиники — **предположение single-tenant** в утилите.
- **`admin_commerce`**: импорт остатков/номенклатуры с **обработкой `IntegrityError`** и `try_replay_committed_import` — зрелее для конкуренции (`src/api/v1/routers/admin_commerce.py`).

**Риск**

Два разных уровня зрелости импорта в одном продукте: оператор **теряет весь файл** из-за одной строки в CSV расписания; при этом commerce-поток ближе к enterprise-идемпотентности. Это усиливает ощущение «инструмент сырой» на стороне расписания, если не документировать и не выравнивать UX/API.

---

### 8.6. AI-оркестратор и шлюз провайдеров (хвост для следующего углубления)

**Факты**

- `OmnichannelAIOrchestrator` после `append_outbound_message` вызывает тот же **`dispatch_to_channel`** (`src/application/services/omnichannel_ai_orchestrator.py`); метрики успеха цепочки не разделяют «текст сгенерирован» и «канал доставил».
- `IntegrationGatewayService` нормализует Telegram/WebChat/WhatsApp (MVP) в единый DTO (`src/application/services/integration_gateway_service.py`) — полнота идемпотентности по `external_message_id` на границе провайдера **требует отдельной** таблицы тестов (не выписывалась построчно в этом проходе).

## 9. Чеклист приёмки QA_ARCH (коротко)

1. Слот: отмена → повторная запись на тот же интервал (ожидаемый доменный результат + отсутствие скрытого `IntegrityError` в API).
2. Параллельные два `POST` на слот: один клиент получает доменную ошибку «занято», второй — успех; **нигде** необработанный 500 от уникального индекса.
3. Вебхук A/B: недоступность YooKassa → **не** финальный 2xx без отдельной задокументированной ветки reconciliation **или** повторная доставка вебхука.
4. Создание платежа: обрыв после ответа провайдера → восстановимое состояние (повторный запрос не ломает учёт).
5. Регрессия CI: один документ/скрипт перечисляет **минимальный** набор шагов, которые должны пройти и Jenkins, и GHA для merge в main.
6. Уведомления: сценарий «ни один канал не настроен» → в БД **не** `sent`, либо отдельный статус и метрика; сценарий «брокер недоступен» → повтор или запись в outbox.
7. Два воркера API: событие/outbox обрабатывается предсказуемо (тест или документированное «только outbox+Celery» для критичных цепочек).
8. Omnichannel: сценарий без токена / без `telegram_user_id` → в API и в БД явно видно **не** «успешно доставлено»; фронт показывает ошибку или «ожидает доставку».
9. Webchat: под **двумя** uvicorn-воркерами long-poll получает исходящее сообщение (или задокументирован single-worker + sticky sessions).
10. Redis недоступен: SSE omni не ломает мутации, но есть **алерт** на частоту `omni realtime publish failed`.
11. ERP: после мутации фактов витрина в пределах заявленного SLO; при сбое nightly — видимый индикатор/алерт.
12. CSV import расписания: контракт «всё или ничего» vs commerce import — задокументирован для саппорта и UI.
