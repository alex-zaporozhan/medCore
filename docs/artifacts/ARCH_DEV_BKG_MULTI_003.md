## 1. Контекст и существующее состояние

### 1.1. Multi‑tenant и клиники в архитектуре

- В `ARCH_DECISIONS_NEXT.md` зафиксировано:
  - **Multi‑tenant и RBAC по умолчанию**:
    - все ключевые сущности доменов имеют `clinic_id`;
    - доступ к API в админке ограничен комбинацией `clinic_id` + пермишенов (`require_permissions`).
- В `ARCH_BOOKING_NEXT.md`:
  - домен Booking/Schedule работает **по клинике**:
    - расписание врачей и слоты подвязаны к `clinic_id`;
    - записи (`Booking`) привязаны к конкретной клинике;
    - лист ожидания и предоплата тоже завязаны на клинику.

Multi‑clinic должно быть **первоклассным понятием**:

- у администратора/владельца может быть несколько клиник;
- пациент в PWA должен явно понимать, в какую клинику он записывается;
- любой отчёт/ERP/CRM‑срез строится в явном контексте клиники.

### 1.2. Проблема (GAPS BKG‑3, FPWA‑3)

По `BACKEND_GAPS_Booking_NEXT.md` и `FRONTEND_GAPS_AppPWA_NEXT.md`:

- **Backend (BKG‑3):**
  - логика работы с `clinic_id` в API и сервисах записи/расписания не везде централизована:
    - часть запросов полагается на «текущую» клинику без жёсткого контракта;
    - в некоторых местах риск «случайной» клиники (особенно при наличии нескольких клиник у пользователя).
- **Frontend PWA (FPWA‑3):**
  - выбор клиники в `BookingWizardPage` реализован **неявно**:
    - используется `localStorage` или первая клиника по списку;
    - нет явного шага выбора/подтверждения клиники, особенно важного для multi‑clinic.

Риски:

- пациент может неосознанно записаться в «не ту» клинику;
- при переключении клиник в админке/отчётах возможна путаница контекстов;
- multi‑tenant‑инварианты из `ARCH_DECISIONS_NEXT.md` не полностью соблюдаются.

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_BOOKING_NEXT.md` — жизненный цикл записи, сущности `Clinic`, `Booking`, расписание.
- `ARCH_DECISIONS_NEXT.md` — инвариант multi‑tenant и RBAC.
- `ARCH_DEV_BKG_CORE_001.md` — фасад завершения визита (должен работать строго в рамках `clinic_id`).
- `ARCH_DEV_BKG_STATE_002.md` — унификация статусов Booking (statemachine не должна позволять межклинические «скачки»).
- `ARCH_DEV_SEC_RBAC_022.md` — ревизия RBAC и проверок `clinic_id`.
- `BACKEND_GAPS_Booking_NEXT.md` — BKG‑3.
- `FRONTEND_GAPS_AppPWA_NEXT.md` — FPWA‑3.

## 2. Целевое состояние multi‑clinic‑логики Booking/PWA

### 2.1. Жёсткие инварианты

1. **Явный контекст клиники на всех слоях.**
   - Любая операция, создающая или меняющая `Booking`, работает в явном контексте:
     - `clinic_id` передаётся и валидируется в API;
     - `Booking.clinic_id` никогда не меняется «межклинически» post‑factum.

2. **Единый способ выбора клиники на фронте.**
   - В PWA и админке:
     - клиника выбирается явным UX‑шагом;
     - контекст клиники сохраняется и явно отображается (header/context bar), но **не подменяет** выбор без согласия пользователя.

3. **Фильтрация и валидация по clinic_id на backend.**
   - Все списки:
     - расписание, слоты, waitlist, записи, платежи по визитам —
     - фильтруются по `clinic_id` текущего контекста;
   - при попытке работать с объектом другой клиники:
     - операция отклоняется (403/404) по правилам RBAC/multi‑tenant.

4. **Multi‑clinic не ломает ERP/CRM/Loyalty.**
   - Завершение визита (`BookingCompletionService`) и ERP‑узел:
     - работают только в рамках одной клиники;
     - все созданные ERP/CRM/Loyalty‑объекты несут тот же `clinic_id`.

5. **AI‑слой не может «перепрыгивать» между клиниками.**
   - AI‑tools для Booking (`get_available_slots`, `create_booking`, `cancel_booking`):
     - принимают `clinic_id` как обязательный параметр;
     - Orchestrator формирует контекст только по доступным клиникам данного оператора/пациента.

### 2.2. UX‑инварианты (PWA и админка)

- В PWA:
  - если у пациента есть доступ более чем к одной клинике:
    - wizard записи начинается с шага **«Выбор клиники»**;
    - текущая клиника всегда показана в контекстном блоке (название, адрес/город).
  - если доступ только к одной клинике:
    - шаг выбора может быть пропущен, но контекст клиники всё равно отображается явно.

- В админке:
  - страницы расписания/записей/листов ожидания:
    - имеют явный селектор клиники (или клиника задаётся на уровне аккаунта/ролей);
    - переключение клиники приводит к перезагрузке данных в рамках нового контекста.

## 3. Архитектурный дизайн: backend

### 3.1. API и сервисы Booking/Schedule

Цель: **централизовать работу с `clinic_id`** в домене Booking.

- Проверить и нормализовать следующие роутеры:
  - `src/api/v1/routers/schedule.py`
  - `src/api/v1/routers/bookings.py`
  - `src/api/v1/routers/admin_schedule.py`
  - `src/api/v1/routers/admin_doctor_schedule.py`
  - `src/api/v1/routers/admin_waitlist.py`
  - `src/api/v1/routers/admin_prepayment.py`

Подход:

- Для всех операций чтения:
  - входной параметр `clinic_id`:
    - либо в явном виде в query/path;
    - либо берётся из текущего контекста пользователя (если архитектура уже его предоставляет);
  - фильтрация по `clinic_id` **обязательна** на уровне ORM/репозитория.

- Для операций записи/мутаций:
  - `clinic_id` определяется:
    - либо из тела запроса (создание `Booking`);
    - либо из уже существующего объекта (обновление/отмена), но в обоих случаях:
      - текущий пользователь должен иметь право работать с этой клиникой (см. `ARCH_DEV_SEC_RBAC_022.md`);
  - **запрещено** менять `Booking.clinic_id` после создания записи.

### 3.2. Сервисы домена

- В `BookingService`/`ScheduleService`:
  - явно принимать `clinic_id` в публичных методах:
    - `create_booking`, `list_bookings_for_schedule`, `list_free_slots`, и т.п.;
  - не полагаться на «глобальный» или неявный контекст.

- Для листа ожидания (`QueuePolicy`, `WaitlistEntry`):
  - все операции создания/перевода `WaitlistEntry → Booking`:
    - выполняются только в рамках одной клиники;
    - не допускают ситуаций, когда waitlist одной клиники конвертируется в `Booking` другой.

### 3.3. Связь с RBAC и multi‑tenant

- Сервисы **не подменяют** RBAC:
  - `clinic_id` на уровне сервиса — гарантия правильной выборки/сохранения;
  - права доступа — ответственность слоя API/RBAC (см. `ARCH_DEV_SEC_RBAC_022.md`).

- Там, где уже существует проверка `clinic_id` в сервисах:
  - привести к единому helper’у:
    - например, утилита `assert_entity_belongs_to_clinic(entity, clinic_id)`:
      - бросает доменное исключение при нарушении;
      - логируется как потенциальная попытка межклинического доступа.

## 4. Архитектурный дизайн: frontend (PWA + admin)

### 4.1. PWA `/app` — BookingWizardPage

Исходные GAPS по `FRONTEND_GAPS_AppPWA_NEXT.md`:

- **FPWA‑3:** выбор клиники реализован неявно через `localStorage` + первую клинику.

Целевой UX:

1. **Шаг выбора клиники** (если клиник > 1):
   - компонент типа `ClinicSelectorStep`:
     - список доступных клиник с основными атрибутами (название, адрес/город);
     - выбор сохраняется в state wizard’а и (опционально) в `localStorage` только как **предпочтение**, но:
       - каждый новый wizard всё равно показывает текущий выбор и даёт возможность его сменить.
2. **Контекст клиники в шапке wizard’а:**
   - блок «Вы записываетесь в клинику: <название>»;
   - кликабелен для смены клиники (возврат на первый шаг).
3. **Формирование API‑запросов:**
   - все запросы к backend по слоту/записи используют выбранный `clinic_id`:
     - `GET /schedule/slots?clinic_id=...`;
     - `POST /bookings` с явным `clinic_id`.

### 4.2. PWA `/app` — HistoryPage

- В дополнение к FPWA‑5/6 (словарь статусов и расширенный контекст):
  - фильтры/группировка по клинике:
    - пациент видит, в какой клинике был каждый визит;
    - может отфильтровать историю по клинике (если их несколько).

### 4.3. Admin `/admin` — расписание и записи

- Страницы:
  - `SchedulePage`
  - `AdminBookingsPage`
  - `AdminWaitlistPage`

Цели:

- Явный селектор клиники в верхней части страницы:
  - переключение клиники перезагружает данные через запросы с новым `clinic_id`;
  - текущая клиника отображается в заголовке/context bar.
- Отчёты/агрегаты на этих страницах всегда строятся в явном клініческом контексте:
  - нет «смешанных» списков по всем клиникам без явного выбора.
