## 1. Что у нас сейчас (факт по коду)

### 1.1. Единый enum в БД

Источник правды: `src/domain/entities/booking.py` — класс `BookingStatus` (строковые значения в колонке `bookings.status`, `String(32)`).

**Минимальный набор, который реально используется в продуктовых потоках (создание, оплата, отмена, завершение, отчёты):**

| Код (API / БД)   | Типичное использование |
|------------------|-------------------------|
| `pending`        | Запись создана (ПМП / пациент), часто стартовый статус. |
| `confirmed`      | После оплаты предоплаты / политики «без оплаты» — см. `PaymentService` (автопереход `pending` → `confirmed`). |
| `awaiting_payment` | Промежуточное при сценариях оплаты (есть в UI переходов в админке). |
| `completed`      | Визит завершён (ручные/сервисные методы завершения). |
| `no_show`        | Неявка. |
| `cancelled`      | Отмена (унифицированное `cancelled` в коде; в enum также есть `canceled_by_*` для расширения). |

**Дополнительно в enum заведены** (из `ARCH_DEV_BKG_STATE_002`, часть — «на вырост»):  
`draft`, `scheduled`, `rescheduled`, `in_progress`, `canceled_by_patient`, `canceled_by_clinic`, `blocked`, `maintenance`, `error`, `inconsistent` — **не все из них обязаны отображаться в UI**, но значения уже допустимы на уровне модели.

### 1.2. Где «формально» зашита логика и зачем

1. **`BookingStatusService`** (`src/application/services/booking_status_service.py`) — явная state-machine: **какие переходы разрешены** (например, в `completed` / `no_show` только из `pending` и `confirmed`; в `cancelled` — ещё и из `awaiting_payment`). Любой PATCH статуса из админки проходит через эти правила.
2. **`BookingService`** — доменные проверки: отмена нельзя из финальных статусов, завершение / неявка только из «активных» и т.д.; публикация событий (`make_booking_*_event`).
3. **`PaymentService`** — связка денег и статуса: ожидает подтверждения оплаты vs уже `confirmed`, автоподтверждение при отключённой предоплате.
4. **Отчёты / дашборд** — агрегации по `pending` и `confirmed` отдельно (`report_service`, DTO дашборда).
5. **Интеграции** (CRM, loyalty, ERP-флаги) — часто завязаны на «есть ли `completed`» и т.п.

Итог: бэкенд формален **намеренно**: это контракт API, целостность данных и предсказуемость для оплат, отчётов и интеграций. Смена списка статусов без обновления машины состояний ломает клиентов и аналитику.

## 2. Запрос бизнеса (RU-лейблы) и орфография

Желаемый список (как в ТЗ, уточнённый порядок):

1. **Зарегистрирован** — орфография: **«Зарегистрирован»** (не «Зарегестрирован»).
2. **Подтверждён** — сразу после регистрации: запись/визит подтверждены клиникой (см. ниже связь с кодом `confirmed`). В интерфейсе для «записи» допустима форма **«Подтверждена»** — согласовать с редакцией UI.
3. **Ожидает**
4. **На приёме**
5. **Завершён** (нейтральный/мужской род для процесса приёма; согласовать с редакцией UI.)
6. **Неявка**
7. **Отмена** (короткий существительный для тега/строки; альтернатива — «Отменено» для согласованности с другими экранами.)

Текущий скрин админки (`BookingEntityDrawer`) показывает отдельно *Подтверждена* без явного «Зарегистрирован» — в целевой линейке **«Подтверждён» идёт вторым**, после **«Зарегистрирован»**, что согласуется с доменным `confirmed` после операционного шага `registered`.

## 3. Рекомендация по модели (бизнес + техника)

### 3.1. Два слоя: «операционный» и «планирование»

- **Планирование (онлайн):** пациент записался; клиника может держать запись как «ожидает подтверждения/оплаты» — это сейчас близко к **`pending`** и **`confirmed`** (в т.ч. после YooKassa).
- **Операционный день (ресепшн / кабинет):** пациент **зарегистрирован** в МИС/на ресепшене → запись **подтверждена** клиникой → **ожидает** в зоне ожидания → **на приёме** у врача → **завершён** / **неявка** / **отмена**.

Целевой список из **семи** пунктов описывает **операционную + подтверждение** линейку. Код **`confirmed`** в API остаётся естественной опорой для этапа «Подтверждён» (оплата/политика и отчёты «подтверждено» сохраняются).

### 3.2. Варианты стратегии

| Стратегия | Суть | Плюсы | Минусы |
|-----------|------|-------|--------|
| **A. Только переименование RU** | Коды API не меняем; меняем подписи и цвета. `confirmed` в UI не показываем как отдельный пункт, или переименовываем в «Зарегистрирован» *условно* | Быстро, без миграции БД | Семантика «подтверждена оплатой» смешивается с «зарегистрирован на ресепшене» |
| **B. Новый код `registered` + переходы** | Добавляем `registered` в enum; чёткая матрица: например `pending`/`confirmed` → … → `registered` → `waiting` … | Честная модель для ресепшена | Нужны миграция данных, правила, тесты, обновление оплаты/отчётов |
| **C. Использовать уже существующий `in_progress`** | «На приёме» = `in_progress` (уже в enum), не вводить дубликат | Меньше новых кодов | Нужно включить `in_progress` в state-machine и UI (сейчас в админ-переходах может не участвовать) |

**Практичная рекомендация:** **Вариант B + C в связке:**

- Ввести (или формализовать) **`registered`** под «Зарегистрирован» на ресепшене.
- Следом по смыслу ТЗ — **«Подтверждён»**: маппить на существующий **`confirmed`** (единый код для «клиника подтвердила запись» и сценариев оплаты/политики в `PaymentService`).
- **`Ожидает`** — оставить **`pending`** *или* ввести отдельный `waiting`, только если отличаете «только что зарегистрирован» от «ждёт в очереди»; иначе **достаточно `pending`** с лейблом «Ожидает».
- **`На приёме`** — использовать **`in_progress`** (не дублировать новым значением).
- **`Завершён` / `Неявка` / `Отмена`** — оставить коды **`completed` / `no_show` / `cancelled`**, обновить только RU-лейблы (и согласовать «Завершена» → «Завершён»).
- В UI селекте статусов отображать **порядок**: Зарегистрирован → Подтверждён → … — согласованно с матрицей переходов (§5).

## 4. Черновик соответствия «код → RU (целевое)»

Предлагаемая каноническая таблица для реализации (уточнить на созвоне):

| Код API | RU (отображение) | Группа |
|---------|------------------|--------|
| `registered` | Зарегистрирован | Активные, до кабинета |
| `confirmed` | Подтверждён (альт.: Подтверждена) | Активные; подтверждение клиникой / предоплата |
| `pending` | Ожидает | Активные |
| `in_progress` | На приёме | Активные |
| `completed` | Завершён | Финальные |
| `no_show` | Неявка | Финальные |
| `cancelled` | Отмена | Финальные |
| `awaiting_payment` | Ожидает оплату | Активные (если остаётся в продукте) |

Порядок строк в таблице отражает **целевую цепочку** после введения `registered`: сначала регистрация, затем подтверждение, затем ожидание и т.д. (точный порядок переходов — §5). `awaiting_payment` при необходимости показывают только пока идёт оплата; после успеха обычно уходит в `confirmed`.

## 5. Черновик матрицы переходов (для `BookingStatusService`)

Требуется согласовать с владельцем процесса. Ниже — ориентир:

- В **финальные** (`completed`, `no_show`, `cancelled`) — обычно без выхода назад (как сейчас).
- Из **`in_progress`** — в `completed`, `no_show`, при необходимости `cancelled` (редкий кейс).
- Из **`registered`** — в **`confirmed`** (подтверждение записи после регистрации), далее в `pending` / `in_progress` / `cancelled` по регламенту.
- Из **`confirmed`** — в **`pending`** («ожидает»), **`in_progress`** (на приёме) или **`cancelled`**; не путать с автопереходами из `PaymentService` (`pending` → `confirmed` при оплате) — возможны **две входные ветки** в `confirmed` (онлайн и ресепшн), их нужно явно описать в state-machine.

*Точные рёбра* должны повторить регламент клиники и не противоречить `PaymentService` (нельзя потерять инвариант «оплачено → не в `pending` без отмены»).
