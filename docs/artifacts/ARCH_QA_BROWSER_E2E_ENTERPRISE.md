# Браузерный E2E (Playwright / Cypress / WebDriver): enterprise-канон @QA_ARCH

> **Аудитория:** `@QA_ARCH` (политика, приёмка, метрики), `@ARCH` (ADR и стандарты), `@DEV` (реализация), `@OPS` (CI/CD, окружения, секреты).  
> **Цель:** единая системная рамка для **сквозных UI-проверок в реальном браузере**, сопоставимая с техпаспортом фронта и NFR по качеству, без подмены юнит/интеграционных тестов.  
> **Статус в репозитории (2026-03):** Playwright; **уровень A** + **B-0** (`smoke-public`, `smoke-routes`), CI `e2e.yml`, ADR-006. Логин и API — **B-1+** (`ARCH_FRONTEND_VISUAL_UNIFICATION_AND_E2E_ROADMAP.md`).

## 1) Определения и границы ответственности

### 1.1 Что считается «браузерным E2E»

- Тест выполняется в **реальном браузере** (Chromium / Firefox / WebKit или vendor stack).
- Управление через **автоматизированный драйвер** (Playwright Test, Cypress, Selenium WebDriver и т.д.).
- Сценарий моделирует **путь пользователя** (клики, ввод, навигация), с опциональной проверкой сети/DOM/скриншотов.
- **Не** заменяет: юнит-тесты компонентов, контрактные тесты API, нагрузочное тестирование.

### 1.2 Что E2E не обязан доказывать

- Полное покрытие всех веток бизнес-логики (это слой сервисов и API).
- Корректность расчётов ERP/финансов без изолированных тестов данных и фикстур.
- Безопасность уровня pentest (E2E дополняет, не заменяет SAST/DAST/ручной аудит).

## 2) Сравнение стеков (выбор по enterprise-критериям)

Критерии: **стабильность в CI**, **параллелизм**, **отладка**, **поддержка**, **стоимость владения**, **интеграция с TypeScript/React**.

| Критерий | **Playwright** | **Cypress** | **WebDriver (Selenium 4+)** |
|----------|----------------|-------------|------------------------------|
| Модель выполнения | Процесс Node, мульти-браузер из коробки | Electron + браузер; отдельные ограничения в CI | Стандарт W3C; тяжёлый grid при масштабе |
| Параллель / шардинг | Сильно (workers, projects) | Сильно (с оговорками по плану Cypress) | Сильно при Selenium Grid / cloud |
| Сеть (route interception) | Встроено | Встроено | Через прокси/CDP по месту |
| Trace / отчёты | Trace viewer, HTML report | Dashboard / Cloud (часть платно) | Зависит от обвязки |
| Flake resistance | Высокий auto-wait | Высокий; известны нюансы с `cy` и async | Средний без дисциплины явных ожиданий |
| Кривая обучения (TS/React) | Низкая | Низкая | Средняя |
| Лицензирование | OSS + опционально cloud | OSS + коммерческие фичи | OSS + Grid/облака |

### 2.1 Рекомендация @QA_ARCH для данного репозитория

**Базовый выбор по умолчанию: Playwright Test** — баланс скорости в CI, мульти-браузерности, трассировки и поддержки TypeScript без vendor lock-in в UI-раннере.

**Cypress** — уместен, если команда уже стандартизировала Cypress, нужен единый стиль с существующими тестами в экосистеме или жёсткая интеграция с коммерческим Cypress Cloud (осознанный бюджет).

**WebDriver (Selenium)** — оправдан при **корпоративном mandate** (единый Grid, legacy QA), тестах на специфичных браузерах/политиках или гибриде с мобильными фермами. Для зелёного поля SPA на Vite/React обычно **выше TCO** при том же покрытии.

Фиксация выбора — **краткий ADR** в `docs/artifacts/` или в корне `docs/ADR/` (если появится), с датой и владельцем `@ARCH`.

## 3) Архитектура контура E2E (enterprise-слои)

### 3.1 Пирамида и роль E2E

```
        ┌─────────────┐
        │  E2E (few)  │  ← критические user journeys, smoke по зонам
        ├─────────────┤
        │ Integration │
        ├─────────────┤
        │ Unit / comp │
        └─────────────┘
```

- **E2E:** мало, **медленные**, **дорогие в сопровождении** — только то, что даёт максимум уверенности в регрессах маршрутов, auth и критичных потоков.
- Целевой ориентир: **полный прогон smoke E2E < 10–15 мин** в CI (настраивается с `@OPS`).

### 3.2 Слои внутри набора E2E

| Слой | Назначение | Пример |
|------|------------|--------|
| **Fixture / factory** | Создание пользователей, клиник, токенов через API или БД | `seedE2EClinic()`, `loginAsAdmin(page)` |
| **Page Objects** (или эквивалент) | Инкапсуляция селекторов и действий | `AdminLoginPage`, `BookingWizardPage` |
| **Спеки** | Сценарии Given–When–Then | `admin-smoke.spec.ts` |
| **Reporting** | JUnit/XML, HTML, trace, артефакты в CI | публикация в GitHub Actions / внутренний портал |

Именование и структура каталогов — **одна конвенция на репозиторий** (например `e2e/`, `tests/e2e/`, `frontend/e2e/`); выбор фиксируется в ADR при внедрении.

### 3.3 Привязка к маршрутам (техпаспорт)

- Публичные пути — только **`ROUTE_PATHS`** / `routePaths.ts` (см. `ARCH_FRONTEND_TECH_PASSPORT_DENTAL_BOOKING.md` §2).
- Сценарии E2E **дублируют строки path из канона**, не «магические» URL в десяти файлах: либо импорт констант из общего модуля (если шарится с фронтом), либо единый `e2e/routes.ts`, синхронизируемый с техпаспортом в PR.

## 4) Окружения и данные

### 4.1 Матрица окружений

| Окружение | Назначение | Бэкенд | БД |
|-----------|------------|--------|-----|
| **local** | Разработка спеки | `docker-compose` / локальный uvicorn | миграции + seed скрипт |
| **CI** | Gate на PR | поднять API + БД в job или сервис-контейнер | ephemeral |
| **staging** | Регресс «как прод» | staging API | копия/синтетика по политике OPS |

Правило: **одинаковые переменные** `BASE_URL`, `API_URL`, feature flags — через `.env.e2e` / secrets CI, без хардкода паролей в репозитории.

### 4.2 Тестовые учётные записи и роли

- Отдельные **E2E-пользователи** с минимальными правами под сценарий (admin / patient / при наличии — роли RBAC).
- Пароли — **только** CI secrets или генерация одноразового пользователя через API seed.
- Запрет: продовые учётки и реальные ПИН/телефоны пациентов в автотестах.

### 4.3 Идемпотентность и очистка

- Предпочтительно: **новый контекст** на тест (`beforeEach` reset storage) или изолированный tenant/clinic_id на прогон.
- Документировать политику: truncate vs API cleanup vs отдельная БД на job.

## 5) Надёжность (flakiness) и NFR для E2E

### 5.1 Политика ожиданий

- Предпочитать **ожидания состояния** (locator visible, network idle по смыслу), не фиксированные `sleep`, кроме редких исключений с комментарием и задачей на устранение.

### 5.2 Повторы в CI

- **Retry** только на уровне CI с лимитом (например 1–2 повтора на весь файл или на job), с логированием **flake rate** по тестам.
- Цель: **не маскировать** баги бесконечными ретраями.

### 5.3 Метрики качества набора

| Метрика | Целевой ориентир |
|---------|------------------|
| Flake rate (падения без изменения кода) | < 2% прогонов или трекинг по кварталу |
| Время smoke E2E | Порог в CI, алерт при росте > X% |
| Покрытие критических journey | Список из `DOMAIN_STANDARDS` / продуктовый backlog |

## 6) Безопасность и соответствие

- Скриншоты/trace **не** должны попадать в публичные артефакты с PII без маскирования.
- Секреты только в **GitHub Encrypted Secrets** / Vault; в логах CI — маскирование.
- Для админских сценариев — учёт **RBAC**: не «обходить» guard’ы тестовыми хаками в прод-коде без эпика (см. техпаспорт §7).

---

## 7) CI/CD интеграция (требования к @OPS / @DEV)

1. Отдельный workflow или job `e2e` с **needs** на сборку фронта и подъём API при необходимости.
2. Кэш зависимостей браузера (Playwright browsers) или образ с предустановленными бинарниками.
3. Публикация: HTML report + при падении — trace.zip / видео.
4. Политика веток: **обязательный** или **post-merge nightly** — решает LEAD с учётом стоимости CI.

## 9) Критерии готовности к «первому merge» E2E в репозиторий

- [ ] Выбран стек (ADR) и зафиксирована структура каталогов.
- [ ] Минимум **smoke**: `/`, `/admin/login` (или редирект), `/app` после фиктивного логина пациента — по возможности без реального SMS.
- [ ] Документ `ARCH_QA_BROWSER_E2E_OPERATING_INSTRUCTIONS.md` актуализирован командами запуска.
- [ ] CI job зелёный на `main` не менее N прогонов подряд (порог команды).
