#### Сделано **сверх** исходного списка задач (после QA‑ревью, не были отдельными строками §1–6)

- **Коммит БД перед `BookingCompleted`:** в `BookingCompletionService` после записи визита — `await session.commit()` до публикации события, чтобы подписчики с **отдельной** сессией видели проводки ERP (устранение гонки с `get_db`‑commit в конце запроса).
- **Убрана дублирующая «выручка по визиту» в payload события:** `visit_revenue` в `BookingCompleted` не заполняется из фасада; в `make_booking_completed_event` добавлена пометка deprecated. CRM факт не читает это поле.
- **Единый фильтр income в ERP‑репозитории:** `_income_transactions_for_clinic` для `get_visit_revenue_by_period` и `sum_income_revenue_for_crm_lead` (одно определение «income‑строка» в коде).
- **Автопрогноз при появлении записи:** после `create_lead_for_patient_booking` и при первом `attach_booking` с установкой `primary_booking_id` — вызов `recalculate_estimated_value`.
- **Документация:** блок «Предложения на потом» + синхронизация `BACKEND_GAPS_*`, трекера, `ARCH_AUDIT_NEXT`.

#### Не вошло в v1 (намеренно — сузить scope)

| Элемент | Зачем могло бы понадобиться | Насколько критично в целом |
|--------|-----------------------------|----------------------------|
| **React‑хук / UI для `PATCH .../estimated-value`** | Удобное редактирование прогноза из карточки без Postman. | **Среднее:** API уже есть; хук нужен, когда продукт включает ручной ввод оценки в UI. |
| **Materialized view / SQL‑view income по визиту** | Один и тот же SQL/физика в БД для отчётов и CRM при больших объёмах. | **Среднее/высокое при росте:** на малых данных достаточно ORM + общего фильтра в коде; при нагрузке и дублировании логики — вынести в view. |
| **Таблица «много записей на лид» (или обязательный `lead_id` на всех проводках)** | Когда у сделки несколько визитов без надёжного `lead_id` на каждой транзакции. | **Высокое для сложных циклов сделки:** до тех пор, пока везде проставляется `lead_id`/`booking_id` в ERP, v1 обходится. |

Итог: **всё важное для инварианта «факт в CRM = ERP» в v1 сделано;** три пункта выше — про **UX**, **масштаб/единый SQL** и **модель данных** для сложных сценариев; планировать их в следующих итерациях по продукту и нагрузке.

### 3. Implement — обновление CRM‑логики денег

3.1. **Реализовать методы работы с оценкой и фактом в `LeadService`.**  
3.1.1. Добавить/нормализовать методы:

3.1.2. Важно:  
       - `update_actual_value_from_erp` должен использовать ERP‑слой, а не собственные расчёты по платежам/услугам.

3.2. **Интегрировать обновление `actual_value` с событийным слоем.**

3.2.2. Обработать случаи с несколькими визитами по одному лиду (суммирование фактической выручки).

3.3. **Убрать «локальные» финрасчёты из CRM.**  
3.3.1. Найти и убрать места, где CRM:  
       - сама считает суммы по визитам/платежам без ERP;

3.3.2. Заменить такие участки на чтение из ERP‑представлений или, если необходимо, пометить их как `estimated`/вторичные данные.

### 4. Implement — API и UI CRM по деньгам

4.1. **Обновить CRM‑API так, чтобы он не ломал инварианты ERP.**  
4.1.1. Убедиться, что публичные CRM‑эндпоинты:

4.1.2. При необходимости добавить отдельный API для ручной корректировки `estimated_value` и отдельные строго контролируемые для `actual_value`.

4.2.2. Убедиться, что отчёты по выручке/ROI в CRM используют `actual_value`, согласованный с ERP.

### "На потом" - Предложения на последующие итерации (если не закрыты другими DEV_PROMPT)

- Явная связь лида со **списком** `booking_id` (не только `primary_booking_id`), если проводки ERP не всегда заполняют `lead_id`.  
- Materialized view / SQL‑view для income по визиту, общая для `get_visit_revenue_by_period` и CRM (сейчас общий фильтр `type=income` в коде).  
- Расширенный `estimated_value`: несколько услуг, пакеты, скидки — без смешения с ERP‑фактом.  
- Периодический reconcile‑job: лиды `success` с `actual_value=0` при наличии completed booking (метрика уже есть).  
- Документировать в `ARCH_CRM_NEXT.md` контракт полей `estimated_value` / `actual_value` для аналитики и LTV.

### @QA_ARCH — дополнительные пункты «на потом» (ревью TASK)

- **Наблюдаемость / SRE:** пороги и алерты по `crm_lead_actual_value_erp_missing_fact_total` и по частоте обновлений `actual_value` (аномалии: скачки, нули при ожидаемой выручке); опционально дашборд «CRM ↔ ERP» для клиники.  
- **Идемпотентность и шторм:** при массовых ретраях событий убедиться, что повторные вызовы `update_actual_value_from_erp` не создают лишней нагрузки (уже идемпотентны по сути — зафиксировать в runbook).  
- **Интеграционные тесты:** сквозной сценарий `complete_visit` → commit → `BookingCompleted` → CRM handler → `LeadCard.actual_value` vs сумма `financial_transactions` в той же БД (сейчас слои покрыты unit‑тестами).  
- **Сверка с отчётами:** автоматизированная проверка (nightly или в CI) согласованности агрегатов `report_service` / LTV с ERP‑отчётом по income за период и `clinic_id` (шире, чем один booking).  
- **Аудит ручных правок:** при требованиях COMPLIANCE — не только лог, а запись в `AuditLog` / immutable журнал для `PATCH .../estimated-value` (кто, когда, старое/новое).  
- **Фронт:** хук `useUpdateLeadEstimatedValue` + поле в карточке лида, когда продукт приоритизирует ручной прогноз из Kanban (API уже есть).  
- **Backfill:** одноразовый или периодический пересчёт `actual_value` для исторических лидов после внеднения правил (если в БД есть устаревший кэш).  
- **Безопасность API:** в OpenAPI явно зафиксировать read‑only `actual_value`; при появлении админского override факта (если когда‑либо) — отдельный эндпоинт, роль `manage_finance` + обязательный audit.  
- **Документация для разработчиков:** короткий сценарий в `TESTING_CANON.md` или отдельный `docs/` — как локально воспроизвести «визит завершён → проводка → факт в CRM».  
- **AI / CRM tools:** политика, что инструменты не предлагают «вписать факт» в обход ERP (только прогноз / `estimated` или чтение существующих полей).
