# Архитектура и аудит: отмена записи в расписании

> Артефакт @LEAD / @ARCH по запросу на проверку цепочки «Отменить запись» (расписание). Контекст для @DEV и чек-лист для @QA.

---

## 1. Цель документа

- Описать полный путь от кнопки «Отменить запись» до обновления БД и UI.
- Зафиксировать безопасную и полноразмерную организацию процесса.
- Дать критерии для QA и промпты для @DEV в отдельном документе (`DEV_PROMPTS_SCHEDULE_CANCEL.md`).

## 2. Текущая реализация (путь данных)

### 2.1. Фронтенд (расписание)

| Шаг | Компонент | Действие |
|-----|-----------|----------|
| 1 | `SchedulePage.tsx` | Пользователь кликает по записи в сетке → открывается модалка «Детали записи» (`selectedBooking`). |
| 2 | Модалка «Детали записи» | Кнопка «Отменить запись» видна только при `status !== "cancelled"`, `!== "completed"` **и время слота ещё не наступило** (защита по времени на фронте и в API). По клику: `setPendingCancelBookingId(selectedBooking.id)` и `setSelectedBooking(null)` (закрытие модалки деталей). |
| 3 | Модалка «Подтверждение отмены» | Открыта при `pendingCancelBookingId !== null`. Текст: «Вы действительно хотите отменить запись?» Кнопки: «Нет» (очистить `pendingCancelBookingId`), «Отменить запись» (вызов мутации). |
| 4 | Обработчик «Отменить запись» | `cancelBookingMutation.mutate(idToCancel, { onSuccess, onSettled })`. В `onSuccess`: закрытие модалки, `refetchQueries(["admin-bookings"], ["admin-schedule"])`. В `onSettled`: всегда `setPendingCancelBookingId(null)`. |
| 5 | Хук `useCancelBookingAdmin` | `mutationFn`: `PUT /v1/admin/bookings/{id}/cancel`. `onMutate`: оптимистичное обновление кэша (status → cancelled). `onSettled`: инвалидация `admin-bookings`, `reports-dashboard`, `admin-schedule`. |
| 6 | Данные для сетки | В расписание передаётся `bookingsForGrid = bookings.filter(b => b.status !== "cancelled")`, чтобы отменённые не отображались в ячейках. |

**Файлы:** `frontend/src/admin/pages/SchedulePage.tsx`, `frontend/src/hooks/useAdminBookings.ts`, `frontend/src/admin/components/ScheduleCalendarGrid.tsx`.

### 2.2. Бэкенд (отмена записи)

| Шаг | Слой | Действие |
|-----|------|----------|
| 1 | Роутер | `PUT /api/v1/admin/bookings/{booking_id}/cancel`, `cancel_booking_admin(booking_id, session, current_admin)`. |
| 2 | Сервис | `BookingService.cancel_booking(clinic_id, booking_id)`: проверка ACL (запись принадлежит клинике), запрет отмены при `status in {completed, cancelled}`, **запрет отмены, если время приёма уже прошло** (по серверной дате/времени), установка `status = "cancelled"`, `repository.update(booking)`. |
| 3 | Репозиторий | `BookingRepositoryImpl.update(booking)`: `session.flush()`, `session.refresh(booking)`. Транзакция коммитится в `get_db()` после успешного возврата из эндпоинта. |
| 4 | Кэш расписания | После обновления записи вызывается `schedule_service.invalidate_daily_schedule_cache(doctor_id, appointment_date)`. Ключ Redis: `schedule:{doctor_id}:{date}`. |
| 5 | Побочные эффекты | Очередь: `send_booking_cancelled_task.delay(booking_id)` (уведомление в Telegram и т.д.). Waitlist: `notify_slot_freed(...)` при освобождении слота. |

**Файлы:** `src/api/v1/routers/bookings.py`, `src/application/services/booking_service.py`, `src/infrastructure/database/booking_repo_impl.py`, `src/application/services/schedule_service.py`, `src/infrastructure/database/base.py` (commit в `get_db`).

### 2.3. Расписание (чтение) и кэш

| Элемент | Описание |
|---------|----------|
| Админ-расписание | `GET /api/v1/admin/clinics/{clinic_id}/schedule?date=...&doctor_ids=...` → `ScheduleService.get_aggregated_schedule()`. |
| По врачам | Для каждого врача вызывается `get_daily_schedule(doctor_id, day)`: сначала чтение из Redis (`schedule:{doctor_id}:{date}`), при промахе — `_build_daily_schedule()`. |
| Построение слота | `_build_daily_schedule` загружает записи через `booking_repository.get_for_doctor_on_date()` (без фильтра по status). В цикле слотов: если `booking.status != "cancelled"`, слот помечается занятым и `slot.booking_id = booking.id`. Отменённые в слот не попадают. |
| TTL кэша | 300 с. После `invalidate_daily_schedule_cache` следующий запрос получает промах и пересобирает расписание из БД. |

## 3. Выявленные риски и рекомендации @ARCH

### 3.1. Уже закрыто в текущей реализации

- **Модалка подтверждения** — есть; двойная модалка (детали → подтверждение) решена закрытием «Детали» при открытии «Подтверждение».
- **Закрытие модалки после отмены** — используется `onSettled` для гарантированного сброса `pendingCancelBookingId`.
- **Исчезновение записи в сетке** — передаётся `bookingsForGrid` без `cancelled`; после успеха выполняется `refetchQueries` для `admin-bookings` и `admin-schedule`.
- **Кэш Redis** — при отмене вызывается `invalidate_daily_schedule_cache` для соответствующего врача и даты.

### 3.2. Рекомендации по безопасности и организации

1. **Единый контракт отмены**  
   Отмена из расписания и из страницы «Записи» (`AdminBookingsPage`) используют один и тот же эндпоинт и хук `useCancelBookingAdmin`. Сохранять один источник правды (API + хук) и не дублировать логику.

2. **Транзакция и кэш**  
   Порядок в сервисе: обновление записи в БД → инвалидация кэша расписания. Так при следующем запросе расписания данные в БД уже актуальны. Рекомендуется не менять этот порядок и не выносить инвалидацию до коммита.

3. **Ошибки и откат UI**  
   В хуке при `onError` выполняется откат оптимистичного обновления кэша. На странице расписания при ошибке мутации модалка всё равно закрывается (`onSettled`). При желании можно показывать toast/Alert при ошибке (сейчас только откат кэша).

4. **Страница «Записи»**  
   В `AdminBookingsPage` отмена вызывается без модалки подтверждения (`cancelMutation.mutate(b.id)`). Для единообразия и снижения случайных отмен можно добавить подтверждение и там (по аналогии с расписанием).

## 4. Полноразмерная организация процесса (как и для других действий)

- **Чтение расписания:** один источник — `GET .../schedule` + кэш Redis; фронт — `useAdminSchedule` + при необходимости `useAdminBookings` с фильтром по дате.
- **Изменение записи (перенос):** подтверждение в модалке → `PUT .../reschedule` → инвалидация расписания/записей (уже реализовано в `useRescheduleBookingAdmin`).
- **Отмена записи:** подтверждение в модалке → `PUT .../cancel` → инвалидация кэша расписания на бэкенде + refetch и фильтр `bookingsForGrid` на фронте (реализовано).
- **Завершение записи:** при необходимости — тот же паттерн: подтверждение (если нужно) → API → инвалидация/refetch.

Общее правило: любое действие, меняющее список записей или слоты расписания, должно приводить к инвалидации/refetch соответствующих запросов и, при использовании кэша на бэкенде, к инвалидации этого кэша в той же транзакционной границе (после обновления БД).

## 5. Чек-лист для @QA

- [ ] Расписание: клик по записи → «Детали записи» → «Отменить запись» → модалка «Подтверждение отмены» с текстом «Вы действительно хотите отменить запись?».
- [ ] «Нет» — модалка подтверждения закрывается, запись остаётся.
- [ ] «Отменить запись» — модалка закрывается, запись пропадает из сетки расписания на выбранную дату, слот отображается как свободный.
- [ ] После отмены обновление страницы (F5) — запись не появляется в сетке на эту дату.
- [ ] В разделе «Записи» (админ) отменённая запись отображается со статусом «Отменено» (или не показывается, в зависимости от фильтров).
- [ ] Отмена записи со статусом «completed» или «cancelled» недоступна (кнопка «Отменить запись» не показывается).
- [ ] Отмена записи, время приёма которой уже прошло, недоступна (кнопка не показывается; при прямом вызове API возвращается 400 с сообщением о прошедшем времени).
- [ ] При ошибке сети/5xx: модалка закрывается, при наличии отката кэша запись в списке не переходит в «cancelled» до повторной загрузки.

## 6. Операционные заметки

- **Перезапуск бэкенда/Docker:** после изменений в коде API или сервисов контейнер нужно пересобрать и перезапустить (`docker compose build api && docker compose up -d api`), иначе работает старый образ и запись в БД может не обновляться или кэш — не инвалидироваться.
- **Диагностика «запись не исчезает»:** в DevTools → Network проверить: запрос `PUT .../bookings/{id}/cancel` возвращает 200 и в ответе у записи `status: "cancelled"`; затем запрос `GET .../admin/bookings?date=...` возвращает эту запись уже со статусом `cancelled`. Если PUT даёт 200, а в GET запись всё ещё без `cancelled`, причина на бэкенде (транзакция/кэш). Если в GET приходит `cancelled`, а в сетке запись остаётся — причина на фронте (refetch/фильтр).
- **Если API возвращает 500:** смотреть логи бэкенда (`docker compose logs api --tail 100` или вывод процесса uvicorn). Частые причины: БД или Redis недоступны (запустить `docker compose up -d`), ошибка в коде (traceback в логах). Отмена записи при недоступности Redis больше не приводит к 500 — инвалидация кэша только логируется как warning.

## 7. Статусы completed и no_show (для @BIZ и продукта)

- **completed** в системе выставляется **только вручную**: админ нажимает «Завершить» (или вызывает `PUT .../complete`). Автоматического перехода «время прошло → completed» нет.
- **no_show** тоже только вручную: админ отмечает «Не пришёл» (`PUT .../mark-no-show`).
- **Рекомендуемый сценарий:** если клиент не пришёл, админ до или после времени слота отмечает запись как **no_show**, а не завершает как completed. Тогда запись не блокируется от отмены по статусу; при этом отмена по времени уже запрещена для прошедших слотов (см. п. 2.2).
- **Итог:** запись с прошедшим временем отменить нельзя (защита по времени). Запись со статусом completed отменить нельзя (защита по статусу). Если админ по ошибке поставил completed вместо no_show — в текущей реализации «разблокировать» отмену для такой записи нельзя; при необходимости можно ввести отдельное действие «перевести в no_show» только для записей в статусе completed (по решению продукта).
