**Для кого:** @DEV (исполнитель кода).  
**Кто задаёт контекст:** @LEAD / @ARCH (передают этот документ + при необходимости артефакты из `docs/dev_artifacts/`).

## Точка А (исходное состояние)

- Админка с глобальным Header, светлым сайдбаром, формами в Modal или на отдельных страницах.
- Списки/таблицы при пустых данных или загрузке — пустой экран или полноэкранный Loader.
- В таблицах нет единого ActionMenu (три точки) с действиями по сущности.
- Нет глобального поиска (Spotlight) по Cmd+K.
- Дашборд, чат, расписание, CRM, задачи, финансы, карточки сущностей — без целевой плотности данных и целевых сценариев из техпаспорта.

## Точка Б (целевое состояние)

- Каркас: без Header; тёмный Sidebar с Collapse (260↔80px), группы OPERATIONS / BUSINESS / SYSTEM; светлый Main, контент в Paper; на каждой странице Context Bar (заголовок, при необходимости хлебные крошки + кнопки).
- Все формы создания/редактирования — в Drawer справа; Modal только для подтверждений.
- Пустые списки — Premium Empty State (иллюстрация/иконка, текст, одна кнопка CTA); загрузка — Skeleton по контуру, не Loader; таблицы компактные (Data Density, verticalSpacing="sm").
- В каждой строке таблицы — ActionMenu с действиями (Редактировать, Удалить, контекстные); в карточках сущностей при необходимости — ActionMenu в шапке (Печать, Скопировать, Удалить).

- Дашборд (метрики, Attention Feed с «Взять в работу», таймлайн), при необходимости отдельная страница «Лента внимания» (Feed + My Focus). Аналитика (воронка, drill-down, AI Advisor). Дифференциаторы: Spotlight AI, виджет Revenue Hunter, Retention, Omni-Vault (медиа, Export Builder со Smart Presетами, Full Backup), PWA 2.0; при реализации — Owner Morning Brief и AI Supervisor Summary (бэкенд, Telegram). Всё по `docs/TECH_PASSPORT_FRONTEND_UI_LOGIC.md`, TPF_* и REV_*.

## Как пользоваться этим документом

1. Выполняй **строго по фазам**: 0 → 1 → 2 → 3 → 4 → 5 → 6. Не перескакивай.
2. Внутри фазы выполняй **шаги по порядку** (разделы «Шаги» ниже). Каждый шаг разжёван: что делать, в каком файле, как проверить.
3. После каждого шага ставь галочку в **To-do** фазы. Фазу считай завершённой, когда все to-do отмечены и **Критерий приёмки** фазы выполнен.
4. Если нужны детали кода (примеры, точные пропсы), открывай артефакт: `docs/dev_artifacts/DEV_ARTIFACT_<ID>.md` (указан в начале каждой фазы).
5. Не принимай архитектурных решений сам: если чего-то нет в документе или в артефакте — спроси @ARCH/@LEAD.

## Архитектурные ограничения и правила (соблюдать во всех фазах)

Эти правила заданы в `REV_CRITERIA_IMPLEMENTATION.md` и `REV_ARCH_UI_VALUES.md`; @DEV обязан их соблюдать, не дожидаясь повторения в шагах.

| Правило | Что делать |
|--------|------------|
| **Tenant isolation** | Все запросы в админке — в контексте текущей клиники (`clinic_id` из контекста/токена). Не запрашивать и не отображать данные другой клиники. |
| **Ошибки API** | При ошибке запроса: не молчать. Показать уведомление (toast/notification, Mantine `notifications`). В формах — вывести ошибку валидации под полями или блоком; при критичной ошибке не закрывать Drawer до успешного сохранения или явной отмены. |
| **Оптимистичное обновление** | При drag (календарь, CRM, задачи) и смене статуса: обновить UI сразу; после ответа API при ошибке — **откатить** состояние (например через `onError` + `queryClient.setQueryData` в React Query) и показать toast. Операции должны быть идемпотентными или с `idempotency_key` (см. бэкенд). |
| **Relational Integrity** | Формы не создают «висящих» записей: Task — обязательно `assignee_id`, `due_date`; Transaction — `cashbox_id`, `amount`, `type`, `category`; при создании записи — минимум пациент, врач, слот. Валидация на фронте и бэкенде; при 422 — показать ошибки по полям. |
| **Кэш после сохранения** | После успешного сохранения в Drawer (создание/редактирование сущности) инвалидировать связанные списки (например `queryClient.invalidateQueries` по ключам списков пациентов, записей, задач и т.д.), чтобы данные в таблицах обновились. |
| **Зависимость от API** | Фичи с пометкой «при наличии API» или «при API»: реализовать UI по контракту из `DEV_ARTIFACT_BACKEND_IMPLEMENTATION.md`. **Если эндпойнта ещё нет** — реализовать бэкенд по соответствующей фазе бэкенд-артефакта (B1–B6) и фронт по контракту; не ограничиваться заглушкой, если фича входит в текущую фазу. Заглушка допустима только если задача явно вынесена за рамки фазы или в документе указано «только UI, API позже». Список эндпойнтов и контрактов — в `docs/dev_artifacts/DEV_ARTIFACT_BACKEND_IMPLEMENTATION.md`. |
| **HoverCard при отсутствии summary** | Если API `GET .../summary` для пациента/врача ещё нет — использовать заглушку (например «Загрузка…» по таймауту или минимум имя + «Данные по запросу»); после появления B1 — переключить на реальный запрос с дебаунсом. |

## Шаги (делать по порядку)

### Шаг 1.1. EmptyState и PageSkeleton

- **EmptyState** (`frontend/src/shared/ui/EmptyState.tsx`): добавить пропсы `icon?: ReactNode` (размер 64, dimmed), `action?: { label: string; onClick: () => void }`. Разметка: Stack по центру, сверху иконка (или иллюстрация для Premium Empty State) → заголовок → описание → кнопка. Обратная совместимость: без action/icon — как сейчас. Цель: не пустая таблица, а иллюстрация + понятный текст + одна главная кнопка (Premium Empty States по TPF_MASTER Part V).
- **PageSkeleton:** создать `frontend/src/shared/ui/PageSkeleton.tsx`. Варианты: `variant="table"` (строка заголовков + строки Skeleton по `rows`), `variant="cards"` (2–4 блока height 120px, radius md). Только Mantine `Skeleton`, без Loader.
- **Data Density:** таблицы везде компактные — `verticalSpacing="sm"`, без лишних отступов (REV_RAG_MAP §1, TPF_MASTER 1.3).
- Найти все места с `<Loader />` при загрузке списков/таблиц; заменить на `PageSkeleton` или `DataSkeleton`. В кнопках и формах Loader не трогать.
- **Проверка:** EmptyState с иконкой и CTA рендерится; PageSkeleton отображается при isLoading; полноэкранного Loader при загрузке списков нет; таблицы компактные.

### Шаг 1.2. Drawer вместо Modal для форм

- Составить список всех форм создания/редактирования: пациенты, записи, врачи, услуги, задачи, кассы, шаблоны форм, администраторы и т.д.
- Для каждой: заменить `<Modal>` на `<Drawer position="right" size="lg">` (сложные формы) или `size="md"` (простые). Содержимое и кнопки перенести внутрь Drawer. Modal оставить только для: подтверждений («Вы уверены удалить?», «Сохранить?»); микро-действий в одну кнопку без формы (например «Подтвердить оплату») — по REV_ARCH_UI_VALUES допускается компактный Modal.
- **Проверка:** Все формы сущностей открываются в Drawer справа; подтверждения — в Modal.

### Шаг 1.3. Применить EmptyState и Skeleton на всех страницах со списками

- Пройти по всем страницам с таблицами/списками (пациенты, записи, врачи, услуги, задачи, кассы, формы и т.д.). При `data?.length === 0` рендерить `<EmptyState title="..." description="..." action={{ label: '...', onClick: ... }} />` с осмысленным текстом и одной кнопкой CTA. При `isLoading` рендерить `<PageSkeleton variant="table" />` (или cards).
- **Проверка:** Нет пустого белого экрана при пустом списке; нет полноэкранного Loader при загрузке.

### Шаг 1.4. ActionMenu в каждой строке таблицы

- На каждой странице с таблицей: в каждой строке справа добавить кнопку «три точки» (`ActionIcon` с `IconDotsVertical` или аналог), по клику открывать `<Menu>` с пунктами: минимум Редактировать, Удалить; плюс контекстные (Отправить форму, Перевести в отказ, Скопировать и т.д. по сущности). Список страниц и рекомендуемых пунктов — в `DEV_ARTIFACT_F1_ACTION_MENU.md`.
- **Проверка:** В каждой таблице в строке есть меню с действиями.

### Шаг 1.5. Spotlight (Cmd+K) базовый

- Вверху сайдбара добавить плейсхолдер «Поиск... (⌘K)» (кнопка или инпут-заглушка). По Cmd+K / Ctrl+K открывать компонент Spotlight (`@mantine/spotlight`): пока только навигация по разделам (действия — переход по роутам). Поиск по пациентам/записям — после появления API (Фаза 5).
- Подключить `useHotkeys` в layout: Cmd+K открывает Spotlight, Escape закрывает.
- **Проверка:** Cmd+K открывает Spotlight; можно перейти в раздел; Escape закрывает.

### Шаг 1.6. Zero-Click Context (HoverCard/Tooltip)

- Везде, где отображаются имена пациентов или врачей (таблицы, чат, календарь, CRM, задачи), при наведении показывать мини-карточку: телефон, LTV, следующий визит (если API отдаёт данные). Использовать `HoverCard` или `Tooltip` (Mantine). При отсутствии API — заглушка или запрос по id с дебаунсом.
- **Проверка:** Наведение на имя пациента/врача в списке или карточке даёт контекст без перехода на другую страницу.

### Шаг 1.7. Доступность (Accessibility)

- Критичные кнопки и поля доступны с клавиатуры; фокус не теряется при открытии/закрытии Drawer (REV_CRITERIA_IMPLEMENTATION §3). На ключевых экранах (чат, формы): Escape закрывает Drawer и сбрасывает фокус.
- **Проверка:** Можно выполнить основные действия с клавиатуры; при открытии Drawer фокус внутри него.
