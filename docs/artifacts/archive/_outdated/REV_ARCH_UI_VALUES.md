# REV_ARCH_UI_VALUES — Архитектурные ценности и подходы UI/UX Business OS

> **Префикс REV_** — документы революции операционной системы.  
> **Роль:** @ARCH. Документ отшлифовывает и усиливает ценности, цели и подходы из TECH_PASSPORT_FRONTEND_UI_LOGIC; задаёт паттерны для принятия решений во всех модулях и при согласовании с бэкендом.

**Источники:** `TECH_PASSPORT_FRONTEND_UI_LOGIC.md`, `TPF_MASTER.md`, `REV_RAG_MAP_INNOVATIONS.md`, `ARCH_FRONTEND_BUSINESS_OS_UX.md`, `BUSINESS_LOGIC_V2.md`.

## 1. Цели системы (что мы максимизируем)

### 1.1. Операционная эффективность

- **Минимум кликов до результата:** Любая частая операция (записать клиента, выставить счёт, перевести лида, взять задачу) выполняется без ухода с текущего экрана. Drawer и Action Bar вместо переходов по разделам.
- **Контекст не теряется:** Редактирование всегда в Drawer справа — таблица/календарь/чат остаются в поле зрения. Modal только для подтверждения.
- **Один экран — один пульт:** Dashboard = пульт смены; Чат = пульт коммуникации и записи; CRM = пульт денег. Не размазывать функции по десятку страниц.

### 1.2. Плотность и смысл данных (Data Density + Meaning)

- **Каждый пиксель несёт смысл:** Таблицы компактные; в каждой строке — достаточно информации для принятия решения плюс ActionMenu. Нет «пустых» колонок и декоративных отступов.
- **Обогащённые сущности:** Карточка пациента/записи/врача/услуги — это вкладки с полным набором данных (визиты, финансы, медкарта, коммуникации), а не форма из трёх полей. Уровень Yclients/Bitrix24.
- **Контекст без перехода:** HoverCard/Tooltip на имя пациента/врача даёт телефон, LTV, следующий визит. API должен отдавать эти данные в списках или по запросу summary.

### 1.3. Проактивность и контроль

- **Лента внимания, а не поиск проблем:** Attention Feed выносит «что не так» на первый экран. Кнопки действий на карточках («Предложить листу ожидания», «Открыть чекаут») ведут к решению, а не к «посмотреть потом».
- **SLA и Time-Bomb:** Задачи с дедлайном и временем реакции; визуальное предупреждение (пульсирующая рамка) при превышении порога. Система «пинает» персонал.
- **AI как помощник, не замена:** AI-подсказки в чате, AI-задачи с кнопкой «Принять в работу», Ghost Slots при записи. ИИ снижает рутину, решение остаётся за человеком.

### 1.4. Ощущение скорости и надёжности

- **Zero Latency UI:** Оптимистичные обновления при drag, смене статуса, отправке сообщения. Интерфейс реагирует мгновенно; при ошибке — откат и уведомление. API для таких операций — идемпотентные или с idempotency_key где нужно.
- **Нет «крутилок»:** Skeleton вместо Loader при загрузке. Контур контента виден сразу — снижается когнитивная нагрузка.
- **Premium Empty States:** Пустой список — не пустая таблица, а иллюстрация + текст + одна главная кнопка. Первый вход в раздел не должен вызывать панику «что делать?».

## 2. Паттерны (применять везде, где уместно)

### 2.1. Drawer > Modal

- **Правило:** Создание и редактирование любой сущности — только в Drawer (position right, size lg/md). Modal — только для Confirm/Alert.
- **Где применять:** Задачи, записи, пациенты, врачи, услуги, лиды, кассы, шаблоны форм, настройки сущностей. Уже заложено в TPF_MASTER; при проектировании нового раздела — по умолчанию Drawer.
- **Исключения:** Микро-действия в одну кнопку (например «Подтвердить оплату») могут быть в компактном Modal, если не требуют формы.

### 2.2. ActionMenu в каждой строке

- **Правило:** В каждой строке таблицы справа — кнопка «три точки», открывающая Menu с полным набором бизнес-действий для этой сущности.
- **Где применять:** Все таблицы: пациенты, записи, врачи, услуги, лиды, кассы, задачи, шаблоны форм, кампании, медиа. Действия зависят от сущности: Редактировать, Удалить, Скопировать, Отправить ссылку, Перевести в отказ, Отправить форму и т.д.
- **Бэкенд:** Для каждого действия — явный эндпойнт или комбинация (например «Отправить форму» = GET link + отправка в канал). В ARCH/DEV_PROMPTS указывать контракт.

### 2.3. Relational Integrity форм

- **Правило:** Форма не создаёт сущность без минимально необходимых связей. Task — без assignee и due_date не создаётся; Transaction — без cashbox, amount, type, category не создаётся.
- **Где применять:** Все формы создания: задачи, финансовые операции, при необходимости — записи (пациент, врач, слот). Валидация на фронте и бэкенде; в API — 422 с явными ошибками по полям.

### 2.4. Zero-Click Context (HoverCard/Tooltip)

- **Правило:** Везде, где отображаются имена пациентов или врачей (чат, календарь, CRM, задачи, отчёты), при наведении показывать мини-карточку: телефон, LTV, следующий визит (если применимо).
- **Где применять:** Списки чатов, карточки записей, таймлайн, канбан лидов, таблица задач, отчёты. Если бэкенд не отдаёт summary в списках — запрос по id при hover (с дебаунсом) или отдельный lightweight endpoint.

### 2.5. Spotlight и горячие клавиши

- **Правило:** Cmd+K — глобальный поиск (навигация + поиск пациентов/записей). Cmd+Enter в чате — отправить. Escape — закрыть Drawer/сбросить фокус.
- **Где применять:** Глобально в Layout; в чате дополнительно Cmd+J для фокуса на поиске чатов. В ARCH зафиксировать: поиск пациентов/записей требует GET search или фильтрации существующих API — контракт в TECH_PASSPORT_BACKEND или отдельном API-документе.

### 2.6. Optimistic UI для мутаций

- **Правило:** Для операций drag (календарь, CRM, задачи) и смены статуса одним кликом — обновлять UI до ответа сервера (onMutate в React Query). При ошибке — откат и toast.
- **Где применять:** Расписание (перенос записи), CRM (перенос карточки по этапам), задачи (смена статуса, назначение). Бэкенд: PATCH/PUT идемпотентны или с idempotency_key для платежей/критичных операций.

### 2.7. Три колонки для сложных экранов

- **Правило:** Экран с списком + контентом + контекстом строится как три колонки: список/фильтры (слева), основное содержимое (центр), детали/контекст (справа или Drawer).
- **Где применять:** OmniChat (чаты | переписка | контекст клиента), CRM (фильтры | канбан | Drawer лида), задачи (фильтры | таблица/канбан | Drawer задачи), при необходимости Finance (список | детали кассы/транзакций). Уже заложено в ARCH_FRONTEND_BUSINESS_OS_UX; при добавлении нового «центра управления» — тот же паттерн.

## 3. Применение в модулях (кросс-модульная согласованность)

Ценности и паттерны выше применяются не только там, где явно указано в техпаспорте, но и по смыслу в смежных модулях.

| Модуль | Что усилить из ценностей |
|--------|---------------------------|
| **Dashboard** | Attention Feed с кнопками действий; метрики с динамикой; таймлайн без перехода на полное расписание. |
| **Schedule** | Drag + Optimistic; Ghost Slots; Waitlist как часть экрана; клик по записи → Drawer с вкладками (по TPF_MODULE_ENTITIES). |
| **OmniChat** | Action Bar (Запись, Счёт, Анкета, AI); контекст клиента справа; Zero-Click на имена в других разделах — тот же HoverCard. |
| **CRM** | Суммы на столбцах; Lead Rotting; Drawer с чатом и ссылкой на предоплату; ActionMenu на карточке (не только в таблице). |
| **Tasks** | Relational Integrity (assignee, due_date); AI-пул и «Принять в работу»; Micro-Actions в карточке; Time-Bomb в My Focus. |
| **Finance** | Relational Integrity транзакций; Checkout Hub при завершении визита; техкарты в карточке услуги (вкладка). |
| **Forms** | ActionMenu пациента/записи — «Отправить форму»; в чате — кнопка «Анкета» из того же контракта. |
| **Entities** | Все карточки (Patient, Booking, Doctor, Service) по матрице вкладок; ни одной «короткой» формы. |
| **Analytics/Marketing** | Drill-down из таблицы кампаний в Drawer с пациентами по источнику; AI Advisor как блок с текстовыми инсайтами. |
| **Retention** | AI-сегменты и персональные офферы; воронка кампании до «Оплатили в кассу»; ROI в деньгах. |
| **Omni-Vault** | Медиа-галерея: при наведении — overlay (аватар клиента, иконка канала, дата); клик → Drawer с чатом/визитом. Голосовые: waveform (wavesurfer.js или аналог) + транскрипт. Export Builder без «слепой» выгрузки; Full Backup. |
| **PWA** | Bottom Nav, Next Visit Ticket, EmptyState при отсутствии записи; запись в минимум шагов; Wallet в профиле. |
| **Shell** | Dark Sidebar, Collapse, группы меню, Context Bar на каждой странице, Cmd+K. |

## 4. Согласование с бэкендом (для @ARCH при проектировании)

- **Контракты первичны:** Любое новое UI-поведение из TPF_* или REV_RAG_MAP должно опираться на существующий или спроектированный эндпойнт. В TPF_MODULE_* и DEV_PROMPTS указывать метод и путь.
- **Идемпотентность:** Операции с Optimistic UI (drag, смена статуса лида/задачи) — идемпотентные PATCH/PUT или с idempotency_key для финансов.
- **Tenant isolation:** Все запросы в контексте админки — с clinic_id (из токена или контекста). Не допускать выборки данных другой клиники.
- **Rate и очереди:** AI Command Line, массовый экспорт, полный бэкап — через очереди (Celery) и лимиты; не блокировать HTTP-запрос.
- **Версионирование API:** Путь `/api/v1/`; при ломающих изменениях — новая версия или обратная совместимость по контракту.

## 5. Критерии принятия архитектурного решения по UI

При добавлении новой страницы или фичи проверить:

1. Редактирование/создание идёт в Drawer, а не в Modal (кроме Confirm/Alert).
2. В таблицах есть ActionMenu с релевантными действиями.
3. Пустые состояния закрыты EmptyState с CTA.
4. Загрузка — Skeleton, не полноэкранный Loader.
5. Где есть имена пациентов/врачей — предусмотрен контекст (HoverCard) при наличии API.
6. Операции drag/смена статуса — с оптимистичным обновлением и стабильным контрактом API.
7. Формы не создают «висящих» сущностей (Relational Integrity).
8. Ссылка на соответствующий TPF_MODULE_* или TPF_MASTER в плане реализации.
