## ARCH_DEV_TASKS_MODEL_020 — формализация связи Tasks ↔ AttentionItem

> DEV_PROMPT_TASKS_MODEL_020 — «формализация связи Tasks ↔ AttentionItem (TASK‑1)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль Tasks & Attention в системе

- **AttentionFeed** собирает сигналы из доменов:
  - Booking (no‑show, отмены, переполненное расписание);
  - ERP (ошибки, подозрительные операции);
  - CRM (застой лидов, крупные сделки без движения);
  - Loyalty (низкая активность, истекающие пакеты);
  - Omnichannel/AI (паттерны риска по диалогам, AI‑ошибки).
- **Tasks** превращают эти сигналы в управляемый список действий:
  - конкретный исполнитель/роль;
  - срок/приоритет;
  - связи с доменными сущностями.

### 1.2. Проблема (GAPS TASK‑1)

- По `BACKEND_GAPS_Tasks_NEXT.md` и `ARCH_TASKS_NEXT.md`:
  - связь между `AttentionItem` и `Task`:
    - не формализована как первая‑классная модель;
    - не всегда очевидно, какая задача относится к какому сигналу;
    - статусы задач не всегда отражаются в ленте внимания.
- Риски:
  - шум в AttentionFeed (нескрытые уже обработанные сигналы);
  - дублирующие задачи по одному и тому же событию;
  - отсутствие прозрачной истории «сигнал → задачи → результат».

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_TASKS_NEXT.md` — целевая модель Tasks & AttentionFeed.
- `ARCH_BOOKING_NEXT`, `ARCH_ERP_NEXT`, `ARCH_CRM_NEXT`, `ARCH_LOYALTY_NEXT`, `ARCH_OMNICHANNEL_NEXT`:
  - описывают доменные источники Attention.
- `ARCH_DEV_OBS_CHAINS_023.md` — наблюдаемость по цепочкам.
- `ARCH_DEV_OMNI_REGISTRY_015.md` — tools‑registry и AI‑слой, откуда тоже могут приходить сигналы.

## 2. Целевое состояние связи Tasks ↔ Attention

### 2.1. Жёсткие инварианты

1. **Любой AttentionItem может порождать одну или несколько задач.**
   - Связь `AttentionItem ↔ Task`:
     - явная, хранимая в БД;
     - позволяет увидеть:
       - какие задачи созданы по сигналу;
       - статус обработки сигнала.

2. **Статусы задач влияют на состояние AttentionItem.**
   - Когда все связанные задачи:
     - `done` или `cancelled` — AttentionItem считается «обработанным» (может скрываться/архивироваться);
     - есть активные `open`/`in_progress` — AttentionItem остаётся в ленте как «в работе».

3. **Tasks и Attention используют согласованные статусы и приоритеты.**
   - Статусы задач:
     - `open`, `in_progress`, `done`, `cancelled`;
   - Attention может иметь свой `status`/`state`:
     - `new`, `in_progress`, `resolved`, `archived`;
   - Маппинг между ними зафиксирован и прозрачен.

4. **AI‑генерация задач не ломает доменные инварианты.**
   - AI Task Manager:
     - создаёт задачи только через тот же API/сервисы, что и пользователи;
     - всегда оставляет след в AttentionFeed:
       - «создано AI на основе сигнала X/анализа Y».

## 3. Архитектурный дизайн модели и сервисов

### 3.1. Модель связей

- Вводим явную сущность/таблицу или расширенные поля, например:
  - вариант A (отдельная связь):
    - `AttentionTaskLink`:
      - `id`;
      - `attention_id`;
      - `task_id`;
      - `created_at`;
      - `created_by` (user/AI/system);
  - вариант B (если структура позволяет):
    - поля в `Task`:
      - `attention_id` (nullable);
    - и/или в `AttentionItem`:
      - список/агрегат ссылок на `task_id` (как денормализация).
- Для vNext архитектурно достаточно:
  - обеспечить возможность:
    - от AttetionItem быстро получить все связанные Tasks;
    - от Task — вернуться к источнику Attention.

### 3.2. AttentionFeedService и TaskService

- `AttentionFeedService`:
  - отвечает за:
    - создание AttentionItem’ов по событиям доменов;
    - обновление их статусов/видимости.
- `TaskService` (или аналог):
  - отвечает за:
    - создание/обновление задач;
    - смену статусов/приоритетов;
    - фильтрацию/списки по ролям/клиникам/источникам.
- Новый слой/методы:
  - `TasksAttentionLinkService` (рабочее имя) или расширение существующих:
    - `link_task_to_attention(attention_id, task_id, created_by)`;
    - получение списка задач по Attention;
    - пересчёт состояния Attention по статусам задач.

### 3.3. Состояние Attention на основе задач

- Правила (пример):
  - AttentionItem `status`:
    - `new` — создан, нет задач;
    - `in_progress` — есть хотя бы одна `open/in_progress` задача;
    - `resolved` — все связанные задачи `done`/`cancelled`;
    - `archived` — явно скрыт пользователем/системой (но история сохраняется).
- Пересчёт статуса Attention:
  - триггеры:
    - создание/изменение/закрытие задач, связанных с Attention;
    - явные действия пользователя (например, «отметить сигнал как неактуальный»).

## 4. Источники Attention и типы задач

### 4.1. Классы AttentionItem

- Основные категории (по `ARCH_TASKS_NEXT` и доменам):
  - **Booking / Schedule:**
    - частые no‑show по пациенту/слоту/врачу/клинике;
    - сбои в завершении визитов (ERP/LOYALTY‑ошибки).
  - **ERP / Finance:**
    - ошибки проведения платежей/проводок;
    - подозрительные транзакции/отчёты.
  - **CRM:**
    - лиды без движения (rot);
    - крупные сделки без записей/визитов.
  - **Loyalty:**
    - клиенты с высоким балансом и низкой активностью;
    - истекающие пакеты/депозиты.
  - **Omnichannel & AI:**
    - AI‑ошибки;
    - диалоги, требующие вмешательства человека.

### 4.2. Типы задач и шаблоны

- Для каждой категории Attention:
  - определяем шаблоны задач:
    - заголовок (`title`), описание (`description`);
    - тип исполнителя (`assignee_id`/роль);
    - приоритет и срок.
- Примеры:
  - `NO_SHOW_PATIENT` → задача «Позвонить пациенту, предложить новую запись»;
  - `ERP_SYNC_ERROR` → задача «Проверить проводку ERP для визита #...».

## 5. Интеграция с AI Task Manager (без реализации AI‑части)

### 5.1. Роль AI Task Manager’а

- AI Task Manager (DEV_PROMPT_TASKS_AI_021):
  - анализирует:
    - AttentionFeed;
    - историю задач (что закрывается/игнорируется);
    - доменные метрики (из OBS/CRM/ERP/Loyalty);
  - предлагает/создаёт задачи:
    - в тех же терминах, что и ручные шаблоны;
    - с пометкой `created_by = "ai"` и ссылкой на исходные AttentionItem’ы/метрики.

### 5.2. Ограничения и связь с текущим DEV‑шагом

- В рамках DEV_PROMPT_TASKS_MODEL_020:
  - мы:
    - формализуем модель Tasks ↔ Attention;
    - обеспечиваем API/сервисы для создания/связки задач;
    - настраиваем статусы/приоритеты и логику «resolution».
  - AI‑логика:
    - будет использовать эти же API (через tools‑registry), но проектируется/реализуется отдельно в DEV_PROMPT_TASKS_AI_021.

## 6. Наблюдаемость и аудиторность

### 6.1. Логирование

- Для:
  - создания/обновления AttentionItem;
  - создания/обновления задач;
  - создания связей Attention↔Task;
  - изменения статусов:
    - логируем:
      - `trace_id`, `clinic_id`, инициатор (user/system/AI), тип сигнала, тип задачи, старый/новый статус.

### 6.2. Метрики

- Базовые метрики:
  - количество AttentionItem’ов по категориям и статусам;
  - количество задач по источникам (ручные/AI/системные) и статусам;
  - среднее время до закрытия задач по типам сигнала;
  - доля AttentionItem’ов без задач (сигналы, которые никто не взял в работу).
