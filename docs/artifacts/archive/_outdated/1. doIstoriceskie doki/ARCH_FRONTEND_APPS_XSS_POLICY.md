## ARCH_FRONTEND_APPS_XSS_POLICY — политика XSS и пользовательский контент

Основание: `ARCH_HARDENING_ROADMAP.md` (п. 6), текущая фронтенд‑архитектура (React‑приложения: админка и PWA пациента).

**Цель:** зафиксировать единые правила по работе с пользовательским контентом на фронтенде, минимизировать риск XSS и задать контракты для @FRONTEND/@DEV/@QA.

---

## 1. Классы пользовательского контента

Типы контента, который может содержать пользовательский ввод или текст из внешних источников:

- **Чат‑сообщения**:
  - сообщения пациента и администратора в модуле чата;
- **Описания услуг и маркетинговые тексты**:
  - названия/описания услуг;
  - маркетинговая лента, сторис, промо‑блоки;
- **Прочие текстовые поля**:
  - свободные заметки/комментарии (если появятся в UI);
  - тексты уведомлений/шаблонов, редактируемые админом.

По умолчанию **все эти поля считаются небезопасным пользовательским контентом**.

---

## 2. Базовое правило рендеринга

1. **По умолчанию весь пользовательский текст рендерится как обычный текст**, а не как HTML:
   - в React‑компонентах — через обычный JSX (`<span>{text}</span>`, `<p>{text}</p>` и т.п.);
   - без `dangerouslySetInnerHTML`, `innerHTML`, прямых DOM‑манипуляций.
2. **Любое использование raw‑HTML (включая markdown → HTML)**:
   - запрещено, если не прописано как разрешённое исключение в этом документе;
   - требует обязательной санитизации и unit/UI‑тестов.

---

## 3. `dangerouslySetInnerHTML` и raw‑HTML

### 3.1. Запрещено по умолчанию

**Нельзя** использовать:

- `dangerouslySetInnerHTML` для отображения текстов, пришедших:
  - от пользователя (пациент, админ);
  - из backend API как строка;
  - из внешних систем (интеграции).

**Исключения** (разрешаются только если отдельно описаны ниже и реализованы с санитайзером).

### 3.2. Разрешённые исключения (на будущее)

Если появится функциональность:

- редактируемых HTML/markdown‑текстов (например, блог, статьи, богатый редактор), или
- заранее подготовленных маркетинговых блоков, которые хранятся как HTML,

то:

- перед рендером необходимо:
  - использовать выбранный санитайзер (например, DOMPurify или аналогичную библиотеку);
  - ограничить список тегов и атрибутов до безопасного подмножества (см. ниже).

**Пример белого списка (ориентировочно):**

- теги: `p`, `br`, `strong`, `em`, `ul`, `ol`, `li`, `a`, `span`, `h1`–`h4`;
- атрибуты: `href` (без `javascript:`), `title`, `target` (`_blank` с `rel="noopener noreferrer"`).

Конкретный список должен быть зафиксирован при внедрении такой фичи.

---

## 4. Санитизация при поддержке HTML/markdown (будущий уровень)

Если будет принято решение поддерживать markdown/HTML:

- выбрать библиотеку (например, DOMPurify) и оформить её использование в одном месте (утилита/хук, а не разрозненный вызов по коду);
- настроить:
  - **строгий режим** (запрет `style`, `on*`‑атрибутов, `iframe`, `script`, `object`, `embed`, `form`, `input` и т.п.);
  - фильтрацию `href/src` (только `https`, `mailto`, `tel` при необходимости).
- внедрить unit‑тесты:
  - проверка, что `<script>`/`onerror=`/`javascript:` и подобные конструкции не проходят через санитайзер.

До внедрения такого решения весь пользовательский контент должен отображаться только как текст.

---

## 5. Требования к тестам

Для компонентов, рендерящих пользовательский текст, @FRONTEND должен:

- добавить unit/UI‑тесты с "опасными" строками:
  - `"<script>alert(1)</script>"`;
  - `"<img src=x onerror=alert(1) />"`;
  - `"<a href='javascript:alert(1)'>link</a>"`;
- убедиться, что:
  - текст отображается как строка (экранированная) или отфильтрован санитайзером;
  - скрипты не исполняются.

---

## 6. Выход для цепочки

- Этот документ задаёт **XSS‑политику для всех фронтенд‑частей** продукта:
  - базовое правило "всё как текст";
  - запрет `dangerouslySetInnerHTML` без явного описания и санитайзера;
  - требования к будущей поддержке HTML/markdown;
  - ожидания по тестированию со стороны @FRONTEND/@QA.
- В контексте `DEV_PROMPTS_HARDENING_SECURITY_AND_AI.md` (фаза B.3) @DEV/@FRONTEND должны:
  - инвентаризировать компоненты с пользовательским контентом;
  - удалить/ограничить raw‑HTML там, где он не разрешён;
  - добавить тесты на XSS‑кейсы.
