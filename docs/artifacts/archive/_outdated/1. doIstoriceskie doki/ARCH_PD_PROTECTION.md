## ARCH_PD_PROTECTION — защита ПД (ФЗ‑152 и международные сценарии)

Основание: `ARCH_HARDENING_ROADMAP.md` (п. 7), текущая архитектура (`ARCH_DENTAL_BOOKING_01_DB_AND_STRUCTURE.md`, `ARCH_CHAT_PATIENT_ADMIN.md`, `ARCH_AI_IMPLEMENTATION.md`, `ARCH_AI_POLICY.md`, `ARCH_ENVIRONMENTS.md`), реализация `src/core/encryption.py`, `src/core/config.py`, AI‑санитайзер.

**Цель:** описать, где и как хранятся и обрабатываются персональные данные (ПД), как работают шифрование и бэкапы, какие внешние каналы используются, и как встроить требования ФЗ‑152 при сохранении возможности международного развёртывания (EU/US‑клиенты, внешние AI‑провайдеры типа Google/Claude).

---

## 1. Классификация данных и регуляторные режимы

### 1.1. Классы данных

- **Персональные данные (ПД)**:
  - пациент: ФИО, телефон, email, дата рождения, история записей, тексты чата, заметки;
  - администратор/врач: ФИО, email, служебный телефон.
- **Платёжные данные (не держим "сырые")**:
  - идентификаторы платежей (YooKassa и др.), суммы, статусы;
  - номера карт/СVV **никогда не хранятся** в системе — обрабатываются только плательщиком (YooKassa).
- **Технические данные**:
  - логи, метрики, токены интеграций, настройки клиники.

### 1.2. Режимы развёртывания

Вводим флаг в конфигурации (семантически, реализация — в `Settings`):

- `data_residency_mode: "ru_fz152" | "intl_flexible"` (название можно уточнить при внедрении).

Режимы:

- **`ru_fz152`** (по умолчанию для проектов в РФ):
  - основная БД и "первичный сбор" ПД — на территории РФ;
  - внешние AI‑провайдеры могут использоваться только с **жёсткой санацией** и по согласованному перечню;
  - при интеграциях с зарубежными сервисами ПД либо анонимизируются, либо не передаются.
- **`intl_flexible`**:
  - размещение БД и бэкапов — по договорённости с клиентом (EU/US/др.);
  - допускается хранение и обработка ПД в выбранном регионе;
  - допускается использование зарубежных AI‑провайдеров (Google, Anthropic/Claude и т.п.) при соблюдении политики санации и договоров обработки ПД (DPA).

Этот флаг влияет на **разрешённость конкретных интеграций** и конфигурацию AI, но не отменяет общие требования по шифрованию/логам.

## 2. Где живут ПД и бэкапы

### 2.1. Основная БД

Сущности с ПД (неполный список):

- `patients` (телефон, ФИО, email, ДР, история согласий);
- `bookings` (привязка к пациенту, дата/время, услуга, заметки);
- `chat_messages` (тексты сообщений пациента/админа);
- `notifications` (телефон/email пациента, текст уведомления);
- `clinic`, `doctors`, `admins` (данные персонала).

Требования:

- **encryption-at-rest** на уровне инфраструктуры:
  - диски (volume) БД должны быть зашифрованы средствами провайдера (LUKS, cloud‑encrypt, etc.);
  - доступ к БД ограничен по сети (VPC/VPN, firewall).
- Доступ к БД:
  - только из backend‑приложения и управляемых админ‑инструментов;
  - прямые подключения извне (BI‑инструменты) должны быть оформлены отдельными договорами и ограниченными аккаунтами.

### 2.2. Бэкапы

Политика бэкапов:

- **Что бэкапим:**
  - основную БД;
  - файлы миграций/конфигурации (не ПД, но важно для восстановления).
- **Куда:**
  - в режиме `ru_fz152`:
    - хранилище бэкапов (object storage) располагается в РФ или у провайдера, имеющего право работать с ПД граждан РФ;
  - в режиме `intl_flexible`:
    - регион выбирается по договорённости (EU‑DC, US‑DC и т.п.).
- **Шифрование:**
  - бэкапы должны быть зашифрованы (GPG/KMS/шифрование бакета);
  - ключи шифрования хранятся отдельно (KMS, Vault).
- **Retention:**
  - рекомендуемый срок хранения:
    - по умолчанию 30–90 дней (конкретика — по договору с клиникой);
    - отдельные долговременные архивы (год+) — только при явном запросе и с отдельным обоснованием.

Удаление:

- при удалении/анонимизации записей ПД в "боевой" БД:
  - старые бэкапы физически могут содержать ПД до истечения retention‑периода;
  - это должно быть явно отражено в политике и договорах;
  - по запросу клиента возможна принудительная зачистка конкретных бэкапов (опция с повышенной стоимостью/узким SLA).

## 3. Шифрование и ключи

### 3.1. Шифрование чувствительных значений в приложении

Уже есть модуль `src/core/encryption.py`, использующий:

- KDF на базе `sha256(secret_key)` → ключ для Fernet;
- функции:
  - `encrypt_plaintext(plain: str) -> str | None`;
  - `decrypt_ciphertext(cipher: str | None) -> str | None`.

Назначение:

- шифрование **секретов интеграций и служебных ключей** (например, YooKassa secret, токены API сторонних сервисов).

Требования:

- использовать этот механизм для хранения:
  - платёжных секретов;
  - токенов Telegram‑бота;
  - любых внешних API‑ключей (включая Google/Claude и др.), если они сохраняются в БД.
- не использовать его для "массового" шифрования всей пациентской информации — это задача инфраструктурного шифрования на уровне дисков/таблиц.

### 3.2. Шифрование "на диске" и "в полёте"

- **В полёте (transport):**
  - весь трафик между клиентами и backend — по HTTPS;
  - соединения backend ↔ БД/Redis по возможности также шифровать (TLS к БД/Redis, если поддерживается провайдером).
- **На диске (at rest):**
  - шифрование volumes для БД и бэкапов средствами провайдера;
  - шифрование object storage для бэкапов.

Управление ключами:

- `secret_key`, `jwt_secret_key`, ключи для шифрования бэкапов и т.п.:
  - хранятся в менеджере секретов (Vault, Secrets Manager, KMS), а не в репозитории;
  - доступ к ним ограничен по принципу минимально необходимых прав.

## 4. Где ПД покидают систему

### 4.1. AI‑интеграции

Основание: `ARCH_AI_IMPLEMENTATION.md`, `ARCH_AI_POLICY.md`.

Текущая позиция:

- все вызовы внешнего AI проходят через `SafeAiClient` и `AiSanitizer`;
- **телефоны, email, ФИО и другие ПД не должны уходить во внешний AI**:
  - они заменяются маркерами (`[PHONE]`, `[EMAIL]`, `[NAME]` и т.п.);
  - тексты чатов/заметок подвергаются санации перед отправкой.

Политика по режимам:

- `ru_fz152`:
  - по умолчанию AI‑провайдеры за границей РФ должны использоваться только на обезличенных данных;
  - в настройках клиники/окружения:
    - список разрешённых провайдеров и регион их размещения;
  - `AiSanitizer` должен гарантировать, что в payload нет прямых ПД.
- `intl_flexible`:
  - допускается использование облачных AI‑провайдеров (OpenAI, Google, Anthropic/Claude и т.п.) в регионах, согласованных с клиентом;
  - даже в этом режиме **санитизация ПД остаётся включённой по умолчанию**;
  - возможен флаг "ослабления" санации для on‑prem/частных моделей по решению @SEC/@LAWYER.

Заглушки/возможности:

- в конфиге AI следует заложить возможность:
  - выбора провайдера (`ai_provider_type = "none" | "ru_local" | "openai" | "google" | "anthropic" | "custom"`);
  - ограничения регионов (`ai_provider_region = "ru" | "eu" | "us" | ...`).
- при недопустимом сочетании (`ru_fz152` + провайдер без DPA/без санкционированного региона) — AI‑функционал должен работать только в fallback‑режиме (см. `ARCH_AI_FAILOVER`).

### 4.2. Email/SMS/мессенджеры

Внешние каналы:

- **SMS** (например, SMSC.ru):
  - уходят номер телефона и текст сообщения;
  - в тексте не должно быть избыточных ПД (например, полных ФИО в открытом виде);
- **Email**:
  - email‑адрес пациента;
  - текст напоминаний/подтверждений (без лишних медицинских деталей, по договорённости с клиникой);
- **Telegram/мессенджеры**:
  - `telegram_chat_id`/идентификатор аккаунта пациента;
  - текст сообщений/уведомлений.

Политика:

- минимизация ПД в содержимом сообщений:
  - например, "Здравствуйте, ваша запись в клинику на дату/время подтверждена" вместо детализированных медицинских диагнозов;
- фиксация факта и объёма ПД, уходящих во внешние системы, в бизнес‑документации и договорах.

Хранение во внешних системах:

- по умолчанию:
  - система хранит минимум технической информации о доставке (статус, идентификатор сообщения, дата/время);
  - содержимое сообщений может храниться в логах/таблицах `notifications` но только столько, сколько необходимо для работы/аудита.
- Retention:
  - настройка срока хранения записей в `notifications` (например, 6–12 месяцев) и/или обрезка текста до безопасного минимума.

## 5. Ответственность и зона контроля при внешних AI‑провайдерах

Технически система:

- реализует санацию ПД перед внешними AI‑вызовами (SafeAiClient + AiSanitizer);
- предоставляет конфигурацию, позволяющую:
  - выбрать тип и регион AI‑провайдера;
  - полностью отключить внешних AI или работать только в fallback‑режиме;
- обеспечивает шифрование секретов и защищённый транспорт до границы своей инфраструктуры.

При этом:

- ответственность за:
  - выбор конкретного AI‑провайдера (Google, OpenAI, Anthropic/Claude и др.);
  - подписание с ним договоров обработки ПД (DPA, SCC и т.п.);
  - корректную юридическую оценку трансграничной передачи ПД;
лежит на стороне владельца инстанса/клиники и/или интегратора, а не на самой системе как программном продукте;
- архитектурно мы **открываем техническую возможность** подключения внешних AI‑провайдеров, но не гарантируем их внутреннюю безопасность и не несём ответственности за утечки, произошедшие:
  - внутри инфраструктуры AI‑провайдера;
  - по причине некорректной юридической настройки отношений с ним.

Эта оговорка должна быть отражена в юридических документах (см. зону ответственности @LAWYER).

## 6. Логи и обезличивание

Связано с `ARCH_ENVIRONMENTS.md`.

Политика:

- Никаких "сырых" ПД в логах:
  - телефоны и email должны маскироваться;
  - коды SMS/пароли/токены не должны логироваться.
- Уже реализованный `AiSanitizer` и прочие утилиты должны:
  - уменьшать риск утечки ПД в логи при отладке AI.

Примеры:

- **допустимо**:
  - `"+7***1234"` вместо полного номера;
  - `"user***@example.com"` вместо полного email.
- **недопустимо**:
  - `"phone=+79001234567"` в логах;
  - `"code=123456"` в логах авторизации.

## 7. Удаление и ретенция данных

### 6.1. Сроки хранения

Зависят от бизнес‑требований и законодательства, но базовые рекомендации:

- история записей и чатов:
  - хранится столько, сколько необходимо для работы клиники и урегулирования конфликтов (например, 3–5 лет);
- технические логи:
  - 30–180 дней;
- таблица `notifications`:
  - 6–12 месяцев.

Конкретные значения должны быть согласованы с клиникой и зафиксированы в договоре.

### 6.2. Право на забвение / удаление ПД

Если клиент/пациент требует удаления:

- в основной БД:
  - либо полное удаление строки (soft‑delete + очистка/анонимизация чувствительных полей);
  - либо анонимизация (сохранение агрегированных данных без идентификаторов).
- в бэкапах:
  - ПД могут сохраняться до истечения retention‑периода;
  - при строгих требованиях возможна отдельная процедура зачистки бэкапов (дорогая операция, оговаривается отдельно).

## 8. Выход для @DEV, @OPS, @SEC, @LAWYER

- **@DEV**:
  - использовать `src/core/encryption.py` для хранения ключей/секретов;
  - не добавлять новые места, где ПД уходят во внешние системы или логи, без учёта этой политики;
  - поддерживать `AiSanitizer` и строгую санацию текстов перед внешним AI.
- **@OPS**:
  - обеспечить encryption‑at‑rest для БД и бэкапов;
  - настроить регионы хранения данных в соответствии с `data_residency_mode`;
  - управлять retention‑политикой и доступом к логам/бэкапам.
- **@SEC**:
  - периодически ревьюить карту потоков ПД;
  - одобрять/блокировать новые интеграции (AI/мессенджеры) с точки зрения ПД;
  - вести реестр соглсований (DPA, ФЗ‑152 и др.).
- **@LAWYER**:
  - использовать этот документ как основу для формализации:
    - Политики обработки ПД;
    - Соглашений с клиниками и иностранными клиентами;
    - DPA/Standard Contractual Clauses при передаче ПД в другие юрисдикции.
