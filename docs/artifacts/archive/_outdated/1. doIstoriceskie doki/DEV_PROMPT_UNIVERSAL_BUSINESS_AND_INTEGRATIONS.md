## Этап 1. Тип бизнеса и роли специалистов (универсальный бизнес)

**Цель:** Сделать продукт пригодным для стоматологий, клиник и салонов красоты без форка кода, с возможностью добавлять свои типы бизнеса и ролей специалистов.

### 1.1. Backend: поля и миграции

1. **Клиника (`clinics`):**
   - Добавить колонку `business_type TEXT NOT NULL DEFAULT 'stomatology'`.
     - Использовать строковые значения: `stomatology`, `clinic`, `beauty_salon`, `barbershop`, `other`.
   - Добавить колонку `business_type_custom_name TEXT NULL`.
     - Логика: если `business_type = 'other'` и `business_type_custom_name` не пустой — в UI показывать это имя (например, «Барбершоп+тату»).

2. **Доктор/специалист (`doctors`):**
   - Добавить колонку `specialist_role TEXT NOT NULL DEFAULT 'doctor'`.
     - Разрешённые значения: `doctor`, `nurse`, `master`, `therapist`, `other`.
   - Добавить колонку `specialist_role_custom_name TEXT NULL`.
     - Если `specialist_role = 'other'` и заполнено поле — использовать его как отображаемое название роли.

3. Обновить соответствующие entity и DTO:
   - `src/domain/entities/clinic.py`, `src/application/dto/clinic_dto.py`;
   - `src/domain/entities/doctor.py` (или аналогичная сущность врача), DTO для врача.

4. Миграции:
   - Отдельная Alembic-миграция, без изменения уже существующих данных.

### 1.2. Backend: API и контракты

1. В админских эндпоинтах получения/обновления клиники и врача:
   - Пропустить через API новые поля `business_type`, `business_type_custom_name`,
     `specialist_role`, `specialist_role_custom_name`.
   - Валидация: `business_type` и `specialist_role` — одно из допустимых значений или `other`.

2. В публичных эндпоинтах (пациентское PWA) использовать только уже сформированные строки
   (например, `display_specialist_role`), чтобы фронт не размазывал бизнес-логику:
   - Добавить в DTO врача поле `display_role: str` (формируется на backend:
     - если `specialist_role = 'doctor'` → «Врач»,
     - `master` → «Мастер»,
     - `nurse` → «Медсестра»,
     - `other` + custom → custom,
     - fallback — «Специалист»).

### 1.3. Frontend: формы и тексты

1. **Админка — настройки клиники:**
   - В разделе настроек добавить селект «Тип бизнеса»:
     - Опции: Стоматология, Клиника, Салон красоты, Барбершоп, Другое.
     - При выборе «Другое» показывать текстовое поле «Свой тип бизнеса».
   - Отправлять и показывать данные через эндпоинт клиники.

2. **Админка — карточка врача/специалиста:**
   - Добавить селект «Роль специалиста»:
     - Опции: Врач, Медсестра, Мастер, Терапевт, Другое.
     - При «Другое» — поле «Своя роль специалиста».

3. **PWA пациента и админка:**
   - Там, где отображаются врачи/специалисты («Записаться к врачу», списки), использовать поле `display_role` из API, а не хардкод «врач».
   - Термины «Пациент» vs «Клиент», «Приём» vs «Визит» — на этом этапе можно оставить как есть либо завязать на `business_type` с помощью простого словаря в конфиге фронта (без сложной i18n).

### 1.4. Тесты

- Unit-тесты на сборку DTO (display_role) и обновление/чтение новых полей.
- Smoke-тесты API клиники и врача: получение/обновление с новыми полями.

## Этап 2. Отчёт по специалистам и администраторам (ежемесячный)

**Цель:** Дать владельцу простой управленческий отчёт без полноценного модуля зарплат:
кто сколько работал и сколько принёс выручки.

### 2.1. Backend: модель данных и агрегаты

1. **Специалисты (врачи/мастера):**
   - Базироваться на существующих сущностях:
     - рабочие часы/расписание врачей;
     - `bookings` (записи) с длительностью слота и суммой (предоплата/выручка).
   - Для выбранного периода (месяц):
     - посчитать количество **дней**, в которые у специалиста были рабочие слоты или завершённые записи;
     - оценить **часы работы** как сумму длительностей записей (или слотов) — для простоты без учёта перерывов;
     - посчитать суммарную выручку по оказанным услугам (можно использовать сумму `prepayment_amount` и/или отдельные поля по завершённым услугам, см. текущую модель).

2. **Администраторы:**
   - На первом шаге — без сложного учёта «чек-ина/чек-аута»:
     - считать **дни активности** как дни, в которые администратор создавал или изменял записи;
     - возможно, ввести упрощённую таблицу `admin_activity_log` (admin_id, clinic_id, date, actions_count), заполняемую по событиям.
   - Часы можно оставить за скобками или оценивать грубо (например, фиксированное рабочее время клиники * дни активности).

3. Разработать сервис `report_service` (если ещё не покрывает эти кейсы) с методом:
   - `get_staff_monthly_report(clinic_id, year, month)` → DTO с данными по специалистам и администраторам.

### 2.2. API и DTO

- Новый эндпоинт админки, например:
  - `GET /api/v1/admin/reports/staff-monthly?clinic_id=...&year=...&month=...`
  - Ответ: список записей по специалистам и список по админам (отдельные массивы или один с меткой роли).

### 2.3. Frontend

- В `/admin/reports` добавить вкладку/секцию «Специалисты и администраторы»:
  - фильтры: месяц/год;
  - таблицы: ФИО, роль, дни работы, часы (если считаем), выручка (для специалистов).

### 2.4. Тесты

- Smoke-тесты API отчёта (200, корректная структура).
- Unit-тесты агрегатов (на небольшом наборе seed-данных).

## Этап 4. Чат + внешние мессенджеры + история для AI

**Цель:** Оставить внутренний чат как базу и добавить возможность писать клиенту в «привычный мессенджер» из нашей админки, при этом сохранять историю в БД.

Опираться на `BIZ_CHAT_MESSENGERS_AND_AI.md` и текущий `ARCH_CHAT_PATIENT_ADMIN.md`.

### 4.1. Модель данных

1. Расширить существующую модель чата **или** добавить отдельную таблицу, в зависимости от решения ARCH (предпочтительно — расширить):
   - добавить в `chat_messages` поле `channel TEXT NOT NULL DEFAULT 'internal'`
     - значения: `internal`, `telegram`, `whatsapp`, `vk`, `email`, и т.д.
   - добавить поле `external_id TEXT NULL` — идентификатор сообщения во внешнем канале (если есть).
2. Для входящих сообщений из мессенджеров предусмотреть связь с пациентом (по chat_id/phone и т.п.).

### 4.2. Интеграции по каналам (минимальный объём)

1. **Telegram:**
   - уже используется для уведомлений — расширить бот, чтобы принимать входящие сообщения и пробрасывать их на наш backend (webhook).
   - добавить endpoint для Telegram webhook, который создаёт/обновляет запись в истории сообщений (channel = `telegram`).

2. **WhatsApp/VK:**
   - на этом этапе можно ограничиться только отправкой (если нет готового безопасного API / договора).
   - предусмотреть структуру данных и интерфейс, но интеграцию в коде делать за флагом/заглушкой.

### 4.3. UI админки

- В окне чата:
  - рядом с полем ввода — селектор канала отправки (по умолчанию `internal`, если у пациента есть telegram_chat_id — можно предлагать Telegram).
  - в ленте сообщений — отображать и помечать канал (например, иконкой).

### 4.4. Подготовка к AI

- Гарантировать, что все сообщения (внутренний чат + внешние каналы) лежат в одном/согласованных формате в БД (patient_id, direction, channel, body, timestamps), чтобы позже можно было строить витрину для анализатора без изменений схемы.

## Этап 5. Web Push в PWA

**Цель:** Сделать нормальные push-уведомления в PWA (новые сообщения в чате, новости клиники) без платных сервисов, согласно `ARCH_WEB_PUSH_CLARIFICATION.md`.

### 5.1. Backend

1. Генерация и хранение VAPID-ключей (пара public/private) и их выдача фронту.
2. Таблица `patient_push_subscriptions` (patient_id, endpoint, keys, created_at, updated_at).
3. Endpoint `POST /api/v1/patient/push-subscription` для сохранения/обновления подписки.
4. Утилита для отправки push (например, на базе `pywebpush`), используемая из:
   - событий «новое сообщение в чате»,
   - событий «новый пост/сторис» (по желанию).

### 5.2. Frontend (PWA)

1. Service Worker уже есть для PWA — расширить его для приёма push и отображения уведомлений.
2. В UX:
   - При первом **открытии чата** или **ленты** — показать диалог «Включить уведомления, чтобы не пропускать ответы и новости?» и запросить разрешение через `Notification.requestPermission`.
   - После разрешения — получить `PushSubscription` и отправить на backend.
3. В настройках профиля добавить блок «Уведомления» с возможностью повторно запросить разрешение/отключить подписку.

### 5.3. Тесты

- Интеграционный smoke-тест: создание подписки и попытка отправки push (без проверки доставки до браузера).
