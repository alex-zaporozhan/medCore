# BIZ_DISCOUNTS_PRICING_RULES — Скидки и ценообразование

> Роль: @BIZ  
> Контекст: Dental Booking — SaaS для клиник и салонов. Уже есть базовая модель скидок (таблица `discounts` и применение при оплате предоплаты), но владельцу нужно:
> - видеть **цену со скидкой сразу в мастере записи**;
> - задавать **комбинированные условия** скидок (например, «услуга X только для первого визита»);
> - быть уверенным, что скидка реально зафиксирована в БД, а не только «красиво отображена».

---

## 1. Контекст и цели

### 1.1. Как сейчас

- Цена услуги (`services.price`) — базовая, **без учёта скидок**.
- Скидки (`discounts`) применяются в `PaymentService` только на сумму **предоплаты** перед оплатой в YooKassa:
  - пациент может видеть старую цену в мастере записи;
  - при выключенной предоплате скидки фактически не задействуются.

### 1.2. Что хочет владелец

- Клиент (пациент) должен видеть **реальную цену со скидкой** на шаге выбора услуги и на шаге подтверждения.
- Скидка должна:
  - быть **зафиксирована в записи или платеже** (чтобы потом не спорить «мы вам обещали 20%»);
  - не пересчитываться задним числом при изменении настроек скидок.
- Нужны **комбинации условий**, не только «по услуге» или «первый визит» по отдельности:
  - «−20% на услугу Удаление зуба для первого визита»;
  - в будущем — комбинации с врачом, периодом, особыми акциями.

## 2. Сценарии применения скидок (MVP)

### 2.1. Скидка по услуге

- **Контекст:** админ создаёт скидку `service` на конкретную услугу (например, «Удаление зуба −20%»).
- **Ожидание:**
  - В мастере записи пациент видит цену **с учётом скидки** (и, по желанию, зачёркнутую старую цену).
  - В записи и/или платеже зафиксированы:
    - `base_price` (старая цена),
    - `discount_amount`,
    - `final_price`.

### 2.2. Скидка «первый визит» + услуга

- **Контекст:** клиника даёт скидку только тем, кто приходит **в первый раз**, и только на конкретную услугу (например, «Первое отбеливание −30%»).
- **Ожидание:**
  - Если у пациента **нет завершённых (`completed`) визитов** в этой клинике — он видит цену со скидкой.
  - Если пациент уже был, скидка на ту же услугу **не применяется**.
  - В отчётах владелец видит, какую выручку принесла конкретная first-visit‑скидка.

### 2.3. Одновременное действие нескольких скидок

MVP‑решение нужно зафиксировать явно:

- Вариант A: применяем **только одну** (например, самую «сильную» по % или с высшим приоритетом).
- Вариант B: позволяем **комбинировать** (сначала first_visit, затем service, и т.п.).

@BIZ должен выбрать вариант для MVP и обосновать:

- **Реком. старт:** Вариант A (одна скидка на запись), чтобы не ломать голову админам и пациентам.

## 3. Правила определения «первого визита»

Предлагаемый стандарт (подтвердить или скорректировать):

- Пациент считается **первичным в клинике**, если:
  - в таблице `bookings` **нет записей** с:
    - `clinic_id = текущая клиника`,
    - `patient_id = этот пациент`,
    - `status IN ('completed')`.
- Отменённые (`cancelled`) и no-show (`no_show`) **не считаются завершёнными визитами**.
- При переносах/повторов:
  - если первый визит отменён/не состоялся — скидка first_visit может примениться к следующей успешной записи (нужно явно описать, так это или нет).

## 4. UX‑требования

### 4.1. Для пациента (PWA)

- На шаге **выбора услуги**:
  - показывать **старую и новую цену**, если скидка есть:
    - пример: `1 000 ₽ → 800 ₽ (скидка 20%)`;
  - если активна только «первый визит» — можно подсветить текстом «Скидка при первом визите».
- На шаге **подтверждения**:
  - повторить итоговую цену + пояснение:
    - «Скидка: −200 ₽ (20% на первый визит)».

### 4.2. Для администратора

- В карточке записи и/или платеже:
  - видно, какая скидка применена (`discount_name`),
  - видно `base_price`, `discount_amount`, `final_price`.
- В отчётах (MVP‑минимум):
  - количество записей, где была применена скидка типа `first_visit`;
  - суммарный объём «списанных» скидок по клинике/периоду.

## 5. Комбинации условий (что разрешаем в MVP)

@BIZ должен утвердить таблицу **разрешённых комбинаций** (для MVP) и явно отметить «не делаем сейчас».

Пример структуры:

| Комбинация                          | Статус в MVP | Комментарий                     |
|-------------------------------------|--------------|---------------------------------|
| `service`                           | ✅           | Базовый кейс                   |
| `first_visit`                       | ✅           | Скидка на первый визит         |
| `service ∧ first_visit`            | ✅           | Ключевой кейс сейчас           |
| `service ∧ doctor`                 | ✅/❌        | По решению, если нужно         |
| `period`                            | ✅/❌        | Общие акции по времени         |
| `service ∧ first_visit ∧ doctor`   | ❌           | Слишком сложно для MVP         |
| `несколько скидок одновременно`    | ❌ (MVP)     | Обсуждается отдельно           |
