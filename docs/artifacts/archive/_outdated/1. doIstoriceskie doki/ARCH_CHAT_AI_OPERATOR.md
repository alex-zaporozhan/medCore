## ARCH_CHAT_AI_OPERATOR — AI‑оператор для чата и клиентов

**Проект:** Dental Booking System MVP  
**Режим:** SAAS  

---

### 1. Цели и ограничения

**Цель:** дать администратору и владельцу помощника, который:

- быстро **суммаризирует диалоги** с клиентом;
- предлагает **варианты ответов** в чате;
- помогает понять контекст отношений с клиентом (частота, выручка, конфликты).

**Жёсткие ограничения v1:**

- AI **никогда сам не отправляет сообщения клиенту** — только предлагает варианты.
- Все вызовы AI проходят через backend, нет прямых ключей на фронте.
- При ошибках/таймаутах AI интерфейс продолжает работать (fallback: «без подсказок»).

---

### 2. Основные сценарии

#### 2.1. Суммаризация диалога

- В админском чате есть кнопка «Суммаризировать».
- Вызов:
  - backend собирает последние N сообщений по `conversation_id` (например, 50–100, с обрезкой длинных).
  - шлёт их в AI‑сервис с указанием:
    - типа бизнеса;
    - ролей (Врач/Мастер и т.п., из `business_lexicon`);
    - языка (RU).
- Ответ:
  - короткий текст 3–6 предложений:
    - что происходило в диалоге;
    - на что жаловались;
    - есть ли незакрытые вопросы.

#### 2.2. Подсказка ответа

- В форме ввода сообщения админа есть кнопка «Предложить ответ».
- Вызов:
  - backend берёт:
    - несколько последних сообщений (контекст),
    - краткую информацию о клиенте (кол‑во визитов, выручка, флаги),
    - необязательное «намерение» (если админ выбрал: извиниться/пригласить/проинформировать).
  - шлёт промпт в AI.
- Ответ:
  - 1–3 варианта коротких ответов на естественном русском:
    - без агрессии;
    - без мед. рекомендаций (если нет мед. лицензии);
    - с вежливым тоном.
- Админ выбирает вариант → может отредактировать → отправляет как обычное сообщение.

#### 2.3. Анализ клиента

- В карточке клиента есть блок «AI‑обзор».
- Вызов:
  - backend подготавливает агрегаты по клиенту:
    - число визитов, средний чек, суммарная выручка;
    - количество отмен/no‑show;
    - наличие конфликтов/жалоб;
    - выдержки из чата (по необходимости).
  - AI формирует:
    - краткий профиль («ходит каждые 3–4 мес., любит скидки, 1 жалоба за год»);
    - подсказку «что сделать сейчас» (пригласить, извиниться, промо и т.п. — только текст для человека).

---

### 3. Архитектура интеграции

#### 3.1. Сервисный слой

В слое application выделяется сервис, например:

```python
class ChatAiService:
    def __init__(self, settings: Settings): ...

    async def summarize_conversation(self, clinic_id: UUID, conversation_id: UUID) -> str: ...

    async def suggest_reply(self, clinic_id: UUID, conversation_id: UUID, admin_id: UUID) -> list[str]: ...

    async def analyze_patient(self, clinic_id: UUID, patient_id: UUID) -> PatientAiInsight: ...
```

`PatientAiInsight`:

- `summary: str`
- `risk_flags: list[str]`
- `next_best_action: str | None`

#### 3.2. Взаимодействие с внешней AI‑моделью

- Внутри `ChatAiService`:
  - собирается контекст (текст/агрегаты);
  - формируется промпт (с указанием ролей и ограничений по тону/темам);
  - вызывается AI‑провайдер (через HTTP‑клиент).
- Параметры:
  - лимит по длине контекста (обрезка старых сообщений);
  - таймаут ответа (например, 5–10 секунд);
  - логирование ошибок без утечки PII (логируем только тип ошибки и ID сущностей).

---

### 4. API для фронтенда

Для v1 достаточно трёх эндпоинтов:

1. `POST /api/v1/admin/chat/conversations/{conversation_id}/ai-summary`
   - Ответ: `{ "summary": str }`.

2. `POST /api/v1/admin/chat/conversations/{conversation_id}/ai-suggest-reply`
   - Тело: опционально `{"intent": "apologize" | "invite" | "info" | ...}`.
   - Ответ: `{ "variants": [str, ...] }`.

3. `GET /api/v1/admin/patients/{patient_id}/ai-insight`
   - Ответ: `PatientAiInsight`.

Авторизация и проверка `clinic_id` — как в остальных admin‑роутах.

---

### 5. UX‑интеграция

- В админском чате:
  - кнопка «AI‑резюме» → вызывает `/ai-summary`, показывает текст над лентой сообщений.
  - кнопка «AI‑ответ» рядом с полем ввода:
    - по клику запрашивает `/ai-suggest-reply`;
    - показывает варианты как кликабельные чипы, подставляющие текст в поле.
- В карточке клиента:
  - блок «AI‑обзор» с:
    - summary;
    - флагами риска;
    - предложением следующего шага.

---

### 6. Безопасность и ответственность

- AI используется **только как подсказка**:
  - финальный текст всегда проверяет и отправляет человек.
- В промптах к модели:
  - явно указываем:
    - не давать медицинских диагнозов и назначений;
    - не обещать то, чего система не может выполнить (скидки, гарантии и т.п.);
    - соблюдение вежливого/нейтрального тона.
- При любой ошибке AI:
  - frontend показывает понятное сообщение («Не удалось получить подсказку, попробуйте ещё раз»);
  - основная функциональность чата не страдает.

---

### 7. Отказоустойчивость AI (failover‑политика)

При любых проблемах с внешним AI (таймауты, 5xx, недоступность провайдера, не сконфигурированный AI) система должна возвращать **пониженный, но рабочий** результат, не ломая основной UX.

#### 7.1. Таблица эндпоинтов и fallback‑поведения

| Функция / эндпоинт                                          | Нормальное поведение                                                                 | Fallback при недоступности AI                                                                                   |
|-------------------------------------------------------------|--------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------|
| `POST /api/v1/admin/chat/conversations/{id}/ai-summary`     | AI даёт структурированное резюме диалога (summary + флаги из `ConversationSummary`) | Локальное heuristics‑резюме: последние N сообщений склеиваются и обрезаются; при ошибке — короткое "без резюме" |
| `POST /api/v1/admin/chat/conversations/{id}/ai-suggest-reply` | AI возвращает 1–3 JSON‑варианта ответа                                              | Возвращается 1–2 простых шаблонных варианта ("Мы вас слышим...", "Давайте подберём время...") или пустой список |
| `GET /api/v1/admin/patients/{id}/ai-insight`               | AI формирует профиль клиента и next_best_action                                    | Локальный расчёт по агрегатам (частота визитов, суммы, no‑show) без AI‑аналитики; при ошибке — пустой insight    |
| `GET /api/v1/admin/ai-reports/conflicts`                   | Возвращаются отчёты на основе `conversation_ai_analysis` с полями из AI            | Если анализ недоступен: пустой список + summary с нулями; UI остаётся рабочим                                    |
| `POST /api/v1/admin/ai-reports/conflicts/reanalyze`        | Запускает батч‑анализ через AI и заполняет `conversation_ai_analysis`              | При недоступности AI безопасно завершает без изменений и логирует проблему; клиент получает 202/200 без падения |

#### 7.2. Принципы реализации failover

- **Поведение по умолчанию:** если `SafeAiClient.is_configured() == False` или вызов AI завершился таймаутом/ошибкой, используется fallback‑ветка.
- **Никаких "голых" 5xx для пользовательских действий**, завязанных на AI:
  - ошибки логируются, но на уровень HTTP возвращается либо успешный ответ с fallback‑данными, либо контролируемый 4xx/5xx с безопасным сообщением;
  - UI должен уметь отобразить "нет резюме / нет подсказок" без краша.
- **Fallback‑алгоритмы должны быть детерминированными и предсказуемыми** (простые правила, локальные агрегаты), чтобы @QA мог их стабильно тестировать.

#### 7.3. Ожидания для @DEV и @QA

- @DEV:
  - в `ChatAiService` и связанных сервисах явно реализовать ветки fallback в соответствии с таблицей выше;
  - при ошибках AI использовать `AiSanitizer`/маскирование, чтобы не увести ПД в логи.
- @QA:
  - в dev‑окружении отключать внешнего AI (пустые ключи/фичафлаг) и проверять, что все перечисленные эндпоинты отрабатывают fallback‑сценарии без 5xx и без поломки UI.
