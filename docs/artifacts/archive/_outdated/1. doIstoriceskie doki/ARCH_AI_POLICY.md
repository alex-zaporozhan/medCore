# Архитектура и политика AI
> Режим: SAAS · Backend: Python 3.11 + FastAPI · Frontend: React + TypeScript · БД: PostgreSQL 15  
> Почему: нужен управляемый, настраиваемый и безопасный AI‑слой для разных типов бизнеса.

---

## 1. Цели AI‑подсистемы

- **Помощь админам**:
  - сводки диалогов (быстро понять суть);
  - варианты ответов (черновики, а не автопилот);
  - обзоры клиентов/пациентов и подсказки по next best action.
- **AI‑коуч по сервису**:
  - анализ типовых конфликтов и жалоб;
  - рекомендации по улучшению скриптов и бизнес‑процессов.
- **Безопасность и ПДн**:
  - запрет прямой утечки ПДн во внешние модели;
  - возможность полностью отключить внешний AI или перейти на on‑prem.
- **Кастомизация под бизнес**:
  - разный системный промпт и режимы для стоматологии, салона красоты, барбершопа и т.д.;
  - настройка тональности, бренда, допустимых тем.

## 2. Уровни возможностей AI (режимы)

1. **Уровень 0 — AI выключен**
   - Все AI‑кнопки на фронте скрыты или показывают, что AI не настроен.
   - Никаких запросов к внешнему провайдеру.

2. **Уровень 1 — Только черновики (по умолчанию)**
   - AI формирует:
     - резюме диалога;
     - варианты ответов;
     - обзоры клиентов/пациентов;
     - аналитические отчёты (в перспективе).
   - Любой текст от AI всегда проходит через человека — отправка клиенту только вручную.

3. **Уровень 2 — Безопасный автоответ**
   - Автоответ разрешён только для “низкорисковых” интентов:
     - расписание, график работы;
     - адрес/как добраться;
     - подтверждение/перенос слота в рамках политик;
     - базовый FAQ, заранее описанный владельцем.
   - Фильтр интентов и бизнес‑правил стоит между AI и отправкой сообщения.

4. **Уровень 3 — AI‑коуч и отчёты**
   - Анализ целых срезов диалогов за день/неделю;
   - отчёты “по конфликтам” и предложения по улучшению процессов;
   - никаких прямых действий от имени админа — только аналитика и рекомендации.

## 3. Модель конфигурации AI (на уровне клиники)

### 3.1. Хранение настройки

На уровне сущности клиники (или отдельной таблицы `clinic_ai_settings`) храним:

- `ai_enabled: bool` — включён ли AI вообще.
- `ai_mode: enum("draft_only","safe_autoreply","analytics_only")`.
- `ai_business_prompt: text` — доп. контекст от владельца:
  - тип бизнеса и услуги;
  - тон общения бренда (формально/дружелюбно/по‑семейному);
  - запрещённые темы;
  - обязательные фразы/дисклеймеры.
- `ai_allowed_intents: list[str]` — список интентов, где разрешён автоответ.
- `ai_autoreply_schedule: optional` — в какие часы автоответ допустим (например, только ночью).
- `ai_provider_profile`:
  - `provider_type: "external" | "on_prem" | "none"`;
  - параметры подключения (базовый URL, модель, ключ) — в защищённых настройках, **не** отдаются на фронт напрямую.

### 3.2. Базовый скелет системного промпта

Системный промпт строится из трёх слоёв:

1. **Глобальный базовый** (прошит в коде, не редактируется владельцем):
   - роль (“ты ассистент администратора клиники/салона”);
   - запреты:
     - не давать медицинских рекомендаций;
     - не обещать скидок/услуг, не указанных явно в контексте;
     - не просить личные данные, которых нет в уже данном тексте.
2. **Бизнес‑специфичный** (автогенерация по `business_type`):
   - словарь терминов (пациент/клиент, врач/мастер и т.п.);
   - типичный сценарий работы бизнеса;
   - допустимый тон.
3. **Клиентский** (`ai_business_prompt`, задаётся владельцем):
   - уникальные особенности конкретной клиники;
   - скрипты приветствий/прощаний;
   - брендинговые требования.

> @ARCH: базовый и бизнес‑слои описать в коде, клиентский — хранить в БД как строку; при генерации промпта конкатенировать их в одном месте.

## 4. Формат ответов AI (JSON‑контракты)

### 4.1. Резюме диалога (conversation summary)

Целевой формат ответа модели:

```json
{
  "summary": "Краткое описание ситуации (2-5 предложений)",
  "sentiment": "negative | neutral | positive",
  "main_issue": "категория проблемы (запись, цена, сервис, врач, оплата, другое)",
  "is_conflict": true,
  "is_resolved": false,
  "suggested_actions": [
    "конкретный следующий шаг администратора",
    "второй шаг (если нужен)"
  ]
}
```

Backend:

- после вызова AI **обязательно**:
  - валидирует JSON по схеме;
  - при ошибке парсинга — пишет в логи и возвращает простой fallback (текстовое summary).

### 4.2. Варианты ответа (suggest reply)

Формат:

```json
{
  "variants": [
    "вариант ответа 1",
    "вариант ответа 2",
    "вариант ответа 3"
  ]
}
```

- Фронтенд использует только текст вариантов.
- Backend может дополнительно ввести флаг `safe_for_autoreply: bool`, если в будущем классификатор/second‑pass проверка будет оценивать безопасность варианта.

### 4.3. Обзор пациента / клиента (patient insight)

Формат:

```json
{
  "summary": "краткий портрет клиента",
  "risk_flags": ["no_show_risk", "churn_risk", "high_value"],
  "next_best_action": "конкретное действие администратора"
}
```

Это уже соответствует модели `PatientAiInsight` — нужно только заставить модель строго отдавать JSON.

### 4.4. Аналитические отчёты по конфликтам (AI‑коуч)

Для отчётов по множеству диалогов:

```json
{
  "items": [
    {
      "conversation_id": "uuid",
      "sentiment": "negative",
      "issue_category": "price",
      "is_resolved": false,
      "admin_mistakes": ["обещал скидку", "не уточнил детали"],
      "business_root_causes": ["непрозрачный прайс", "нет явной политики скидок"],
      "suggested_playbook": [
        "Переписать скрипт ответа на жалобы по цене",
        "Добавить в прайс явные пометки о скидках"
      ]
    }
  ],
  "summary": {
    "total": 12,
    "unresolved_conflicts": 3,
    "top_issue_categories": ["price", "schedule"]
  }
}
```

> @ARCH: эти структуры нужно описать в DTO и документации API, а в промптах явно просить “вернуть строго JSON по этой схеме”.

## 5. Политика ПДн и фильтрации данных

### 5.1. Базовые правила

- Внешнему AI **никогда не отправляются**:
  - ФИО;
  - номера телефонов, email‑адреса;
  - даты рождения, адреса, номера полисов/документов;
  - любые ID, по которым можно легко восстановить личность без БД (например, Telegram @username).
- AI **не имеет** доступа к БД или внутренним API; только к тексту, который ему передаёт наш backend.

### 5.2. Санитайзер (pseudonymization layer)

Перед любым вызовом `AiClient.complete` текст проходит через модуль `AiSanitizer`:

- Задачи:
  - обнаружить и замаскировать:
    - телефоны (`+7...`, любые 10–11‑значные последовательности);
    - email‑ы;
    - возможно ФИО (через простые NER/regexp, с приоритетом на телефоны/e‑mail);
  - заменить реальные данные на стабильные токены:
    - `Пациент_123`, `Администратор_1`;
    - `Телефон: [СКРЫТО]`, `Email: [СКРЫТО]`.
- Архитектура:
  - `AiSanitizer` — отдельный модуль в `src/core/ai_sanitizer.py`;
  - `ChatAiService` и другие сервисы не обращаются к `AiClient` напрямую: только через обёртку `SafeAiClient`, которая внутри вызывает `AiSanitizer`.

### 5.3. On‑prem vs внешний провайдер

- **Внешний провайдер (по умолчанию)**:
  - используется, если настроен `AI_PROVIDER_BASE_URL` и разрешён в политике.
  - все данные проходят через санитайзер.
- **On‑prem / self‑hosted**:
  - архитектурно — тот же `AiClient`, но `base_url` указывает на локальный сервис в контуре клиники.
  - может быть разрешён более мягкий режим (меньше замазываний), но это решение принимается на уровне договора с клиентом и @SEC/@LAWYER.

## 6. Настройки во фронтенде (страница AI‑конфигурации)

### 6.1. Страница “AI и ассистент” в админке

Функционал:

- **Режимы**:
  - переключатель `AI выключен / Только черновики / Безопасный автоответ / Только аналитика`.
- **Промпт и тон**:
  - текстовое поле “Профиль бизнеса и тон” (`ai_business_prompt`);
  - подсказка шаблона:
    - чем вы занимаетесь;
    - как принято обращаться к клиенту;
    - какие фразы/обещания запрещены;
    - что всегда нужно уточнять.
- **Автоответ**:
  - чекбоксы “разрешить автоответ для категорий” (расписание, адрес, FAQ и т.д.);
  - настройки расписания, когда автоответ разрешён (например, ночное время).
- **Провайдер**:
  - статус “AI подключен / не подключен” (без показа ключа);
  - тестовая кнопка “проверить подключение”.

### 6.2. Надёжный RAG‑подход

Для обработки услуг/прайсов/расписания:

- RAG не даёт AI прямого доступа к БД:
  - backend сам выбирает релевантные факты (услуги, цены, политики, расписание) и подмешивает их в промпт в виде текста или структурированного JSON;
  - AI отвечает **только** на основе переданного контекста.
- Конфигурация RAG на фронте:
  - чекбоксы “разрешить AI использовать информацию об услугах / расписании / скидках в ответах”;
  - владельцу не нужно знать детали реализации, только включить или выключить источники контекста.

## 8. Резюме политики

- AI **никогда не действует автономно** без явной настройки и контроля.
- Все действия AI либо:
  - остаются в виде подсказок/отчётов для человека,
  - либо проходят через строгие фильтры интентов и бизнес‑правил.
- Все данные для внешних моделей:
  - проходят через санитайзер ПДн;
  - структурируются в JSON для надёжного анализа и аудита.
