## 2. Приоритеты и фазы внедрения

**Фаза A — Базовая безопасность и предсказуемость (сразу после текущего цикла QA/SEC)**  
- **ARCH_AUTH_SESSIONS**  
- **ARCH_API_GUARDS**  
- **ARCH_RATE_LIMITING**  
- **ARCH_ENVIRONMENTS**

Критерий готовности фазы A:  
- все auth/critical‑эндпоинты описаны и защищены единообразно;  
- dev/stage/prod ведут себя предсказуемо по debug/логам;  
- есть минимальный рабочий rate‑limit на уровне приложения для auth/SMS/AI.

**Фаза B — Процессная безопасность и юридические риски**  
- **ARCH_SECURITY_PIPELINE**  
- **ARCH_PD_PROTECTION**  
- **ARCH_XSS_FRONTEND**

Критерий готовности фазы B:  
- security‑проверки встроены в pipeline и блокируют релиз при критичных/высоких рисках;  
- зафиксированы места хранения и выноса ПД, есть понятная политика для @OPS/@SEC;  
- фронт имеет явный гайд по пользовательскому контенту и XSS.

**Фаза C — AI‑устойчивость и продуктовые SLA**  
- **ARCH_AI_FAILOVER** (как дополнение к существующим AI‑архитектурным файлам)

Критерий готовности фазы C:  
- каждый AI‑эндпоинт формализован с чётким fallback‑поведением;  
- ни один AI‑функционал не даёт "голый" 5xx из‑за внешнего AI.

## 3. ARCH_AUTH_SESSIONS — политика сессий и отзыва токенов

**Цель:** зафиксировать модель сессий пациента/админа и их жизненный цикл без немедленного внедрения сложного механизма отзыва токенов.

**Базовая позиция @ARCH:**
- На ближайший релиз **остаёмся на коротком access‑токене** без refresh‑токена.  
- TTL access‑токена различается по ролям (пример: пациент — 30–60 минут, админ — 15–30 минут, с уточнением в самом ARCH‑документе).  
- Механизм отзыва токенов (token version / blacklist) **описывается как архитектурный паттерн следующего уровня**, но не внедряется немедленно.

**Что должно быть в `ARCH_AUTH_SESSIONS.md`:**
- Модель идентичности:  
  - как patient/admin попадает в токен (минимальный набор клеймов: id, clinic_id для админов, роль);  
  - запрет хранения чувствительных данных в токене.
- Политика TTL для разных ролей с привязкой к рискам.  
- Алгоритм logout / смены пароля / увольнения администратора:  
  - текущее поведение (invalidate на клиенте + ожидание истечения короткого токена);  
  - желаемое поведение следующего уровня (token version в БД/Redis или централизованный blacklist).
- Планируемый паттерн для отзывов: описание схемы таблицы/ключей, не обязательной к немедленной реализации.

**Выход для цепочки:**
- Готовый `ARCH_AUTH_SESSIONS.md` → @DEV получает контракт на генерацию токенов, TTL и обработку основных событий (login/logout/password change/role change).

## 4. ARCH_API_GUARDS — единый слой от IDOR и ACL

**Цель:** убрать разнобой в проверке `patient_id`/`clinic_id`/`owner_id` по всему API и зафиксировать один "правильный" способ.

**Стратегия:**
- Описать единые dependency‑guard’ы (на уровне FastAPI/DRF‑dependency, в зависимости от стека):  
  - `get_current_patient()` — берёт `patient_id` **только из токена**, любые `patient_id` в query/path считаются подозрительными и запрещаются.  
  - `get_current_admin()` — админ всегда привязан к `clinic_id` из токена; все admin‑роуты работают **только внутри своей клиники**.
- Описать шаблон проверки для сущностей:  
  - `load_by_id(...)` → загрузка по ID, затем проверка `clinic_id/owner_id`;  
  - стратегия ответов: 404 (ресурс не существует или скрыт) vs 403 (существует, но доступ запрещён) — с общим правилом, когда что используется.
- Сформировать **чёрный список анти‑паттернов**:  
  - доверие к `patient_id`/`clinic_id` из query/path;  
  - попытки обхода ACL через массовые выборки без фильтрации по клинике.

**Что должно быть в `ARCH_API_GUARDS.md`:**
- Сигнатуры dependency‑guard’ов и описание их поведения.  
- Примеры "правильных" и "неправильных" обработчиков (на псевдокоде).  
- Таблица "роутер → тип guard’а", чтобы @DEV мог пройтись и выровнять все роуты.

**Выход для цепочки:**
- `ARCH_API_GUARDS.md` + чек‑лист роутеров → задача для @DEV по рефакторингу существующих эндпоинтов под единый паттерн.

## 5. ARCH_RATE_LIMITING — защита auth/SMS/тяжёлых эндпоинтов

**Цель:** минимальный, но формализованный rate‑limiting на уровне приложения и рекомендаций по инфраструктуре.

**Стратегия:**
- Определить классы "дорогих" эндпоинтов:  
  - `/auth/send-code` (SMS/email‑коды),  
  - потенциальные платёжные/отчётные маршруты,  
  - тяжёлые AI‑операции (chat summary, suggest reply, AI‑отчёты).
- Ввести минимальную реализацию на уровне приложения:  
  - Redis‑счётчики по ключам `rate:{route}:{ip}` и `rate:send_code:{phone}`;  
  - политика: "N запросов за окно T" с рекомендуемыми значениями (подробно в ARCH‑документе).
- Описать рекомендуемый конфиг для NGINX/Cloudflare:  
  - базовые лимиты per IP/route;  
  - поведение при превышении (429 + заголовки Retry‑After).

**Что должно быть в `ARCH_RATE_LIMITING.md`:**
- Контракт для сервиса/хелпера `RateLimiter` (интерфейс, ожидаемое поведение, ошибки).  
- Рекомендованные лимиты для ключевых эндпоинтов (auth/SMS/AI/отчёты).  
- Схема ключей в Redis и ожидаемый TTL.

**Выход для цепочки:**
- @DEV реализует `RateLimiter` по контракту и оборачивает им критичные эндпоинты;  
- @OPS использует рекомендации для настройки NGINX/Cloudflare.

## 6. ARCH_ENVIRONMENTS — dev/stage/prod и debug/логирование

**Цель:** развести окружения и поведение debug/логов так, чтобы prod был "тихим и безопасным", а dev — удобным для отладки без утечек ПД.

**Стратегия:**
- Описать матрицу окружений: `development`, `staging`, `production`:  
  - включённость debug,  
  - доступность docs/Swagger,  
  - формат ошибок (подробные/краткие),  
  - дополнительные защиты (например, CORS, HSTS).
- Сформулировать политику логирования:  
  - **dev** — можно логировать больше, но без ПД (маскирование телефонов, имён, e‑mail);  
  - **staging** — максимально близко к prod по логам и защите, но можно включать debug‑режим точечно;  
  - **prod** — стектрейсы только во внутренние логи; клиент получает короткое сообщение.
- Задать требования к `.env` для production‑окружения:  
  - обязательно `APP_ENV=production`, `DEBUG=false`,  
  - отключена Swagger‑документация (или защищена),  
  - секреты только из env/secret‑хранилища.

**Что должно быть в `ARCH_ENVIRONMENTS.md`:**
- Таблица "окружение → флаги/поведение".  
- Список ключевых переменных окружения и их значения по умолчанию/ограничения.  
- Рекомендации по раздельным конфигах для backend/frontend (если применимо).

**Выход для цепочки:**
- @OPS настраивает окружения и деплой под эту матрицу;  
- @DEV/@FRONTEND используют единый источник правды для проверки `APP_ENV/DEBUG` и поведения логов.

## 7. ARCH_SECURITY_PIPELINE — зависимости и линтеры безопасности

**Цель:** превратить аудит зависимостей и базовую security‑проверку в формальный шаг перед релизом.

**Стратегия:**
- Определить обязательные инструменты:  
  - `pip-audit` / `safety` для Python;  
  - `npm audit --production` для фронта.  
- Описать, как интерпретируются результаты:  
  - уровни (critical/high/medium/low),  
  - политика: что блокирует релиз, что идёт в backlog (например, всё critical/high по библиотекам на "боевых" путях блокирует релиз).
- Предложить минимальный CI‑pipeline:  
  - шаги для backend и frontend;  
  - форматы отчётов;  
  - критерий "pass/fail".

**Что должно быть в `ARCH_SECURITY_PIPELINE.md`:**
- Таблица "инструмент → команда → где запускается (local/CI)".  
- Политика по уровням уязвимостей.  
- Минимальный YAML‑скелет pipeline (без привязки к конкретному CI‑провайдеру, но с понятными шагами).

**Выход для цепочки:**
- @OPS превращает документ в конкретный CI‑pipeline;  
- @QA/@SEC используют его как чек‑лист перед релизом.

## 8. ARCH_XSS_FRONTEND — политика по пользовательскому контенту

**Цель:** формализовать правила рендера пользовательского контента и минимизировать XSS‑риски.

**Стратегия:**
- Классифицировать пользовательский контент:  
  - чат‑сообщения,  
  - описания услуг,  
  - маркетинговые тексты (лента, сторис).
- Зафиксировать базовое правило:  
  - всё хранится и рендерится как текст;  
  - `dangerouslySetInnerHTML`/raw‑HTML **запрещены по умолчанию**, кроме строго определённых мест, перечисленных в документе.
- Если в будущем появятся markdown/HTML:  
  - выбрать санитайзер (например, DOMPurify/аналог в зависимости от стека);  
  - описать белый список тегов/атрибутов.

**Что должно быть добавлено в `ARCH_FRONTEND_*.md`:**
- Раздел "Политика пользовательского контента и XSS".  
- Список компонентов/экранов, где возможен пользовательский текст, и правила для каждого типа.  
- Рекомендации по unit/UI‑тестам на XSS‑кейсы.

**Выход для цепочки:**
- @FRONTEND и @DEV используют раздел как гайд при добавлении новых полей/экранов с пользовательским вводом;  
- @QA получает набор XSS‑кейсов для регресса.

## 9. ARCH_PD_PROTECTION — ФЗ‑152 на уровне архитектуры

**Цель:** вынести в явный артефакт всё, что относится к хранению/обработке ПД (в т.ч. для ФЗ‑152 и аналогичных требований).

**Стратегия:**
- Описать, где физически должны жить ПД и бэкапы:  
  - основная БД и резервные копии (регион/провайдер, требования по хранению в РФ, если применимо);  
  - шифрование "на диске" и "в полёте".
- Зафиксировать политику бэкапов:  
  - периодичность,  
  - срок хранения,  
  - шифрование/доступ.
- Описать все места, где ПД покидают систему:  
  - AI‑интеграции (с указанием уже реализованной санации/анонимизации),  
  - e‑mail/SMS/Telegram/мессенджеры — какие данные уходят во внешние системы и что там хранится.

**Что должно быть в `ARCH_PD_PROTECTION.md`:**
- Карта потоков ПД (источники → хранилища → внешние каналы).  
- Политика по retention/удалению.  
- Рекомендации для @OPS/@SEC по настройке шифрования и доступов.

**Выход для цепочки:**
- @OPS и @SEC используют документ как референс при аудите инфраструктуры и настройке бэкапов/хранилищ;  
- @BIZ/@LAWYER могут ссылаться на него при подготовке договоров и документов по соответствию.

## 10. ARCH_AI_FAILOVER — политика отказоустойчивости AI

**Цель:** формализовать уже реализованный в коде heuristic fallback и превратить его в стандарт для всех AI‑эндпоинтов.

**Стратегия:**
- Зафиксировать общий принцип:  
  - любой AI‑эндпоинт при недоступности внешнего AI обязан выдавать "пониженный, но рабочий" ответ, а не 5xx;  
  - fallback‑поведение должно быть прозрачным и предсказуемым.
- Перечислить ключевые AI‑фичи:  
  - admin chat summary,  
  - suggest‑reply,  
  - patient AI insight,  
  - AI‑отчёты по конфликтам и др.
- Для каждой фичи сформировать таблицу:  
  - "нормальный режим" (какой внешний AI/модель используется, какие параметры);  
  - "fallback‑режим" (что именно делает система при недоступности внешнего AI: упрощённое правило, сохранение "сырого" текста без анализа, отложенная обработка и т.п.);  
  - сигналы/метрики (как отслеживаем частоту fallback‑режима).

**Что нужно добавить:**
- В `ARCH_CHAT_AI_OPERATOR.md` — раздел с таблицей "AI‑эндпоинт → поведение при отказе AI".  
- В `ARCH_AI_IMPLEMENTATION.md` — технические детали реализации fallback (страты, ретраи, таймауты).

**Выход для цепочки:**
- @DEV синхронизирует текущую реализацию с формализованной таблицей (при необходимости правки);  
- @QA получает понятный чек‑лист для тестирования отказоустойчивости AI (искусственное отключение внешнего AI и проверка ответов).
