# DEV_PROMPTS — Hardening: auth, security, AI

> Основание: `ARCH_HARDENING_ROADMAP.md` (+ будущие `ARCH_AUTH_SESSIONS.md`, `ARCH_API_GUARDS.md`, `ARCH_RATE_LIMITING.md`, `ARCH_ENVIRONMENTS.md`, `ARCH_SECURITY_PIPELINE.md`, `ARCH_PD_PROTECTION.md`, разделы в `ARCH_FRONTEND_*`, `ARCH_CHAT_AI_OPERATOR.md`, `ARCH_AI_IMPLEMENTATION.md`, `ARCH_AI_FAILOVER.md`).  
> Цель: по шагам усилить безопасность/надёжность auth/API/AI без ломки текущего функционала, двигаясь по фазам A → B → C.

---

## 0. Режим работы @DEV

- Работать **по порядку фаз и задач** в этом документе (A → B → C).  
- Перед началом каждой задачи **прочитать соответствующий ARCH‑документ** и свериться с ним.  
- Не изменять публичные контракты API и поведение UI, если это явно не требуется задачей (особенно ответы в ошибочных ситуациях).  
- После каждой крупной задачи:  
  - прогнать unit‑тесты изменённых модулей;  
  - сделать локальный smoke по основным сценариям (auth, ключевые эндпоинты, AI‑фичи).

## ФАЗА A — Auth, guards, rate limiting, окружения

### A.1 — Реализация политики сессий (`ARCH_AUTH_SESSIONS.md`)

**Цель:** привести генерацию и обработку токенов к единой политике TTL и поведения при login/logout/смене пароля, описанной в `ARCH_AUTH_SESSIONS.md`.

**A.1.1 — Обновить модель токена и TTL**

- **Файлы (пример, уточнить по проекту):**
  - `src/infrastructure/auth/jwt_service.py` или аналог (где формируется access‑токен);
  - `src/config/settings.py` / `src/core/config.py` — конфиги TTL.
- **Действия:**
  - Вынести TTL токенов по ролям в конфиг (например, `AUTH_ACCESS_TTL_PATIENT`, `AUTH_ACCESS_TTL_ADMIN`) согласно таблице из `ARCH_AUTH_SESSIONS.md`.
  - Убедиться, что в payload токена используются только необходимые клеймы:
    - `sub` или `user_id` / `patient_id` / `admin_id`;
    - `role`;
    - для админов — `clinic_id` (если так описано в ARCH).
  - Проверить, что **нет** клеймов с ПД (ФИО, телефон, email и т.п.).

**A.1.2 — Централизация создания и валидации токена**

- **Файлы:**
  - сервис токенов (`jwt_service`/`token_service`);
  - dependency‑функции `get_current_patient()`, `get_current_admin()` (см. A.2).
- **Действия:**
  - Убедиться, что все места, где создаётся access‑токен (login/refresh) используют **один** сервис/функцию из `ARCH_AUTH_SESSIONS.md`.
  - Ввести единый метод валидации токена (например, `parse_token()`), который:
    - проверяет подпись и срок действия;
    - возвращает строго типизированную структуру (DTO) с клеймами.

**A.1.3 — Поведение при logout / смене пароля / увольнении админа**

- **Файлы:**
  - эндпоинты авторизации (`/auth/login`, `/auth/logout`, `/auth/change-password`, admin‑управление пользователями);
  - сервисы `AuthService`, `AdminService`/`UserService`.
- **Действия:**
  - Реализовать/уточнить поведение при:
    - `logout` — инвалидировать токен на клиенте (удаление cookie/storage), сервер полагается на TTL;
    - смена пароля — при текущем подходе **не внедрять** version/blacklist, но зафиксировать это в коде через комментарий к месту, где при следующем уровне появится проверка версии (ссылка на `ARCH_AUTH_SESSIONS.md`);
    - увольнение/отключение админа — поведение аналогично: текущие токены истекают сами по TTL.
  - Убедиться, что во всех этих сценариях:
    - не возвращаются лишние данные в ответе;
    - ошибки логируются, но без ПД.

### A.2 — Единые API‑guards и защита от IDOR (`ARCH_API_GUARDS.md`)

**Цель:** убрать разнобой в проверках `patient_id`/`clinic_id`/`owner_id` и использовать единые dependency‑guard’ы.

**A.2.1 — Ввести/обновить dependency `get_current_patient()`**

- **Файлы:**
  - `src/api/dependencies/auth.py` (или аналог);
  - роутеры с patient‑эндпоинтами.
- **Действия:**
  - Реализовать `get_current_patient()` строго по контракту из `ARCH_API_GUARDS.md`:
    - `patient_id` берётся **только** из токена;
    - любые `patient_id` в query/path игнорируются или ведут к ошибке (в зависимости от паттерна в ARCH).
  - Обновить все patient‑роуты:
    - убрать использование `patient_id` из query/path там, где доступен текущий пациент;
    - использовать `current_patient` из dependency.

**A.2.2 — Ввести/обновить dependency `get_current_admin()`**

- **Файлы:**
  - тот же модуль зависимостей;
  - admin‑роутеры (`src/api/v1/routers/admin_*.py`).
- **Действия:**
  - Реализовать `get_current_admin()` по ARCH:
    - чтение `admin_id` и `clinic_id` из токена;
    - возврат объекта/DTO с этими полями.
  - Обновить admin‑роуты:
    - убрать свободный `clinic_id` из запросов там, где он не нужен;
    - использовать `current_admin.clinic_id` для фильтрации/ограничения.

**A.2.3 — Паттерн `load_by_id_with_acl` для сущностей**

- **Файлы:**
  - сервисы сущностей (например, `AppointmentService`, `ServiceService`, `MessageService` и др.);
  - репозитории/DAO.
- **Действия:**
  - Ввести общий хелпер (по ARCH), например:
    - `load_entity_for_clinic(entity_id, clinic_id)` → 404, если `clinic_id` не совпадает или нет доступа;
    - или отдельные методы для owner‑проверок.
  - Заменить ручные проверки в сервисах на вызовы этих хелперов.
  - Соблюдать стратегию 404/403, описанную в `ARCH_API_GUARDS.md`.

**A.2.4 — Чистка анти‑паттернов**

- **Действия:**
  - По чек‑листу из `ARCH_API_GUARDS.md` пройтись по указанным роутерам и:
    - убрать доверие к `patient_id`/`clinic_id` из query/path там, где это запрещено;
    - явно добавить проверки clinic/owner там, где они отсутствовали.

### A.3 — Минимальный rate limiting (`ARCH_RATE_LIMITING.md`)

**Цель:** реализовать минимальный rate‑limiting на уровне приложения для auth/SMS/AI/отчётов, в соответствии с контрактом `RateLimiter`.

**A.3.1 — Реализовать сервис `RateLimiter`**

- **Файл:** `src/infrastructure/rate_limiter.py` (или директория `infrastructure/rate_limiting`).
- **Действия:**
  - Реализовать интерфейс из `ARCH_RATE_LIMITING.md`, например:
    - `check_or_raise(key: str, limit: int, window: int)` → ничего не возвращает при успехе, выбрасывает кастомное исключение при превышении;
    - возможен метод `get_remaining(...)` по контракту ARCH.
  - Использовать Redis‑клиент из уже существующей инфраструктуры (общий connection‑pool).
  - Сформировать ключи в формате `rate:{route}:{ip}` и `rate:send_code:{phone}` по спецификации ARCH.

**A.3.2 — Обернуть критичные эндпоинты**

- **Файлы:**
  - роутер auth (`/auth/send-code`, `/auth/login` и др.);
  - AI‑эндпоинты (chat summary, suggest reply, AI‑отчёты);
  - тяжёлые отчётные эндпоинты.
- **Действия:**
  - В нужных dependency/роутах перед основной логикой вызывать `RateLimiter`:
    - значения `limit`/`window` взять из `ARCH_RATE_LIMITING.md` и/или конфига.
  - При превышении лимита:
    - отдавать 429 (Too Many Requests) в формате, принятом в проекте;
    - при необходимости добавить заголовок `Retry-After`.

### A.4 — Окружения и debug/logging (`ARCH_ENVIRONMENTS.md`)

**Цель:** привести поведение dev/stage/prod к матрице окружений и политике логирования.

**A.4.1 — Конфиги окружений**

- **Файлы:**
  - `src/config/settings.py` / `src/core/config.py`;
  - `.env.example`, dev/stage/prod env‑файлы (если есть).
- **Действия:**
  - Ввести/уточнить переменные:
    - `APP_ENV` (`development`/`staging`/`production`);
    - `DEBUG` (bool);
    - другие флаги из `ARCH_ENVIRONMENTS.md`.
  - Реализовать в коде чтение `APP_ENV` и включение/выключение debug/Swagger/подробных ошибок по матрице из ARCH.

**A.4.2 — Поведение ошибок и логирования**

- **Файлы:**
  - глобальные обработчики ошибок (middleware/exception handlers);
  - конфиг логгера.
- **Действия:**
  - Настроить:
    - в `development` — подробные стектрейсы в ответах только если так разрешено ARCH, но без ПД в логах;
    - в `staging`/`production` — пользователю короткое сообщение, стектрейс только в логи.
  - Убедиться, что формат логов и уровень подробности соответствуют `ARCH_ENVIRONMENTS.md`.

**A.4.3 — Swagger/docs по окружениям**

- **Файлы:**
  - инициализация web‑приложения (где подключается Swagger/OpenAPI UI).
- **Действия:**
  - Включить/выключить Swagger:
    - dev — включён;
    - staging — по решению из ARCH (возможно, ограничен по паролю/IP);
    - prod — выключен или закрыт дополнительной авторизацией.

> **Критерий завершения Фазы A:**  
> - токены и сессии работают по новой политике TTL;  
> - все auth/critical‑эндпоинты используют единые guards и ACL‑паттерны;  
> - ключевые эндпоинты защищены `RateLimiter`;  
> - dev/stage/prod предсказуемо различаются по debug/логам/Swagger.

## ФАЗА B — Security‑pipeline, ПД и XSS

### B.1 — Security‑pipeline для зависимостей (`ARCH_SECURITY_PIPELINE.md`)

**Цель:** подготовить кодовую базу к включению security‑проверок в CI и сделать команды воспроизводимыми локально.

**B.1.1 — Скрипты/команды для Python**

- **Файлы:**
  - `pyproject.toml` / `requirements.txt`;
  - вспомогательные скрипты (`scripts/` или `Makefile`).
- **Действия:**
  - Добавить команды/скрипты для запуска:
    - `pip-audit` или `safety` с параметрами из `ARCH_SECURITY_PIPELINE.md`;
  - Убедиться, что команды:
    - не требуют интерактивного ввода;
    - могут быть запущены как локально, так и в CI.

**B.1.2 — Скрипты/команды для frontend**

- **Файлы:**
  - `package.json`.
- **Действия:**
  - Добавить npm‑скрипт для `npm audit --production` (или команду, указанную в ARCH).
  - Убедиться, что фронт собирается без ошибок при актуальных зависимостях (с учётом договорённостей по `vite-plugin-pwa` и т.п.).

### B.2 — Подготовка к PD‑hardening (`ARCH_PD_PROTECTION.md`)

**Цель:** минимизировать утечки ПД через логи/интеграции и синхронизировать код с картой потоков ПД.

**B.2.1 — Маскирование ПД в логах**

- **Файлы:**
  - логирующие middleware/интерсепторы;
  - места логирования пользовательских данных.
- **Действия:**
  - По карте из `ARCH_PD_PROTECTION.md`:
    - найти места, где в логи могут попадать телефоны/email/ФИО и др. ПД;
    - внедрить маскирование/удаление этих полей перед логированием.

**B.2.2 — Проверка внешних интеграций**

- **Файлы:**
  - интеграции с AI, SMS/e‑mail, Telegram/мессенджеры.
- **Действия:**
  - Свериться с `ARCH_PD_PROTECTION.md` и:
    - убедиться, что во внешние системы не уходят лишние поля (например, полные профили вместо минимально достаточного набора);
    - при необходимости ограничить payload до минимума, описанного в ARCH.

### B.3 — XSS‑политика на фронте (раздел в `ARCH_FRONTEND_*`)

**Цель:** выровнять фронтенд по XSS‑политике и убрать использование raw‑HTML там, где оно не разрешено.

**B.3.1 — Инвентаризация пользовательского контента**

- **Файлы:**
  - компоненты чата, описаний услуг, маркетинговой ленты/сторис;
  - любые компоненты с rich‑text/markdown.
- **Действия:**
  - По списку из ARCH‑раздела XSS:
    - проверить каждый компонент/экран;
    - отметить, где уже используется безопасный рендер (plain text), а где есть потенциальные XSS‑риски.

**B.3.2 — Удаление/ограничение `dangerouslySetInnerHTML`**

- **Файлы:**
  - соответствующие React‑компоненты (`frontend/src/...`).
- **Действия:**
  - В местах, где по политике XSS raw‑HTML запрещён:
    - заменить рендер на текстовый (например, `innerText`/jsx без `dangerouslySetInnerHTML`);
  - В местах, где ARCH допускает raw‑HTML/markdown:
    - внедрить выбранный санитайзер (DOMPurify/аналог);
    - ограничить набор разрешённых тегов/атрибутов по белому списку из ARCH.

**B.3.3 — Тесты на XSS‑кейсы**

- **Файлы:**
  - unit/UI‑тесты фронта.
- **Действия:**
  - Добавить тесты, которые:
    - рендерят компоненты с "опасными" строками (`<script>`, `onerror=`, `javascript:` и т.п.);
    - проверяют, что скрипты **не** исполняются и HTML не интерпретируется там, где это запрещено.

> **Критерий завершения Фазы B:**  
> - есть рабочие команды для security‑сканов зависимостей;  
> - логи и интеграции не выносят ПД сверх карты из `ARCH_PD_PROTECTION.md`;  
> - фронтенд следует XSS‑политике,危险ные места покрыты тестами.

## ФАЗА C — AI‑failover и продуктовые SLA

### C.1 — Формализация AI‑fallback’ов (`ARCH_AI_FAILOVER`, `ARCH_CHAT_AI_OPERATOR.md`, `ARCH_AI_IMPLEMENTATION.md`)

**Цель:** привести код AI‑эндпоинтов в соответствие с таблицей fallback‑поведения, чтобы при недоступности внешнего AI система оставалась рабочей.

**C.1.1 — Синхронизация `ChatAiService` с таблицей fallback’ов**

- **Файлы:**
  - `src/application/services/chat_ai_service.py`;
  - вспомогательные сервисы AI (если есть).
- **Действия:**
  - Для каждого AI‑метода (summary, suggest reply, patient insight, отчёты по конфликтам и др.):
    - явно реализовать ветку "AI недоступен" в соответствии с `ARCH_AI_FAILOVER`:
      - использовать heuristic/local fallback (как описано);
      - не возвращать 5xx из‑за внешнего AI.
  - Убедиться, что логирование ошибок AI не содержит ПД (использовать `AiSanitizer`/маскирование).

**C.1.2 — Обновление AI‑эндпоинтов API**

- **Файлы:**
  - роутеры AI‑эндпоинтов (`src/api/v1/routers/admin_chat_ai.py`, `admin_ai_reports.py` и др.).
- **Действия:**
  - Проверить, что в случае fallback’а:
    - контракты ответов (DTO) соблюдены;
    - фронт не получает неожиданных 500/структур.

---

### C.2 — Тестирование отказоустойчивости AI

**Цель:** гарантировать, что при отключении внешнего AI все AI‑фичи ведут себя в рамках ожидаемых fallback‑сценариев.

- **Действия (ручные/авто):**
  - В dev‑окружении:
    - временно "сломать" доступ к внешнему AI (выключить URL/ключ или настроить мок/фича‑флаг);
    - пройтись по всем AI‑эндпоинтам и UI‑точкам:
      - admin chat summary;
      - suggest reply;
      - patient AI insight;
      - AI‑отчёты по конфликтам.
  - Убедиться, что:
    - UI показывает fallback‑результаты или понятные сообщения;
    - нет "голых" 5xx;
    - в логах фиксируется факт fallback‑режима.

> **Критерий завершения Фазы C:**  
> - каждая AI‑фича имеет чётко реализованный fallback;  
> - отключение внешнего AI не ломает критичный сценарий ни для администратора, ни для пациента.
