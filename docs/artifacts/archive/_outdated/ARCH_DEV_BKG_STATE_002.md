## ARCH_DEV_BKG_STATE_002 — унификация статусов Booking

> DEV_PROMPT_BKG_STATE_002 — «унификация статусов Booking (BKG‑2, FADM‑1, FPWA‑5/6)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль статусов Booking в системе

- Статусы `Booking` — центральный инвариант почти для всех доменов:
  - **Booking / Schedule**: что видно в расписании, какие слоты заняты/свободны.
  - **ERP / Finance**: какие визиты можно проводить в ERP‑узел, что попало в деньги/ЗП/склад.
  - **CRM / Attribution**: что считается «успешной записью», «no‑show», «отменой» и т.п.
  - **Loyalty**: в каких состояниях можно списывать пакеты/депозиты, когда обязательства считаются выполненными.
  - **Tasks / Attention**: какие отклонения (частые no‑show, отмены, зависшие визиты) переходят в сигналы.
- На фронте статусы определяют:
  - цвет/лейблы слот‑карточек и записей;
  - доступность действий («завершить визит», «отменить», «перенести», «вернуть предоплату»);
  - фильтры/счётчики (например, «завершённые», «ожидают визита», «no‑show»).

### 1.2. Проблемы (GAPS BKG‑2, FADM‑1, FPWA‑5/6)

- На backend:
  - статусы могут быть представлены разрозненными строками/константами в разных местах;
  - часть логики использует «сырые» значения (типа `"completed"`, `"canceled"`) без единого enum;
  - переходы между статусами не формализованы (нет явной state‑machine).
- На frontend:
  - где‑то используются прямые строковые статусы из API;
  - нет единого словаря `status_code → label/color/icon/available_actions`;
  - из‑за этого возможны:
    - разные лейблы/цвета для одного и того же состояния;
    - «мертвые» статусы, не покрытые UI‑логикой;
    - сложность обновления UX (каждый экран «рисует» статусы по‑своему).

### 1.3. Связь с другими ARCH/DEV артефактами

- `ARCH_BOOKING_NEXT.md` — жизненный цикл записи, инварианты по статусам.
- `ARCH_ERP_NEXT.md` — какие статусы дают право запускать ERP‑узел и отчётность.
- `ARCH_TASKS_NEXT.md` — какие статусы/переходы рождают Tasks/Attention.
- `ARCH_DEV_BKG_CORE_001.md` — фасад завершения визита, точка перехода в финальные статусы.
- `BACKEND_GAPS_Booking_NEXT.md`, `UX_FLOWS_AND_GAPS_NEXT.md` — конкретные GAPS по статусам и UX‑словам.

## 2. Целевое состояние модели статусов

### 2.1. Жёсткие инварианты

1. **Единый enum статусов Booking.**
   - На backend существует один источник правды, например:
     - `BookingStatus` в доменной модели (`src/domain/entities/booking.py` или отдельный `enums.py`).
   - Все сервисы/роутеры используют только этот enum, а не «сырые» строки.

2. **Явная state‑machine переходов.**
   - Определён и задокументирован набор допустимых переходов:
     - пример (условный, детальная матрица берётся из `ARCH_BOOKING_NEXT.md`):
       - `scheduled` → `in_progress` → `completed`
       - `scheduled` → `canceled_by_patient` / `canceled_by_clinic`
       - `scheduled` → `no_show`
   - Любая смена статуса проходит через централизованный метод/сервис, который:
     - проверяет допустимость перехода;
     - проверяет доменные инварианты (наличие визита, ограничений по времени и т.п.).

3. **Единый «UX‑словарь» статусов.**
   - Отдельный словарь, мэппящий:
     - `status_code` → `label_key` / `default_label`, `color`, `icon`, `priority`, `group` (например, «активные», «финальные», «проблемные»);
   - Используется:
     - на фронте (в PWA и админке);
     - в отчётах/дашбордах;
     - в AI‑подсказках (чтобы AI опирался на те же «человеческие» статусы).

4. **Связь с ERP/CRM/Loyalty инвариантами.**
   - Определён минимальный набор статусов, который влияет на:
     - разрешённость проведения ERP‑операций;
     - включение в отчёты CRM/Attribution;
     - списание пакетов/депозитов.
   - Эти статусы и их значения не меняются без согласования в `ARCH_ERP_NEXT.md` / `ARCH_CRM_NEXT.md` / `ARCH_LOYALTY_NEXT.md`.

5. **Наблюдаемость и проверяемость.**
   - Любой «нестандартный» или ручной переход статуса:
     - фиксируется в логах;
     - для критичных случаев может порождать Attention/Task (например, ручной перевод из `scheduled` сразу в `completed` без ERP‑проводок).

### 2.2. Базовый набор статусов (примерная модель)

> Конкретный перечень и названия уточняются по `ARCH_BOOKING_NEXT.md` и коду, но на архитектурном уровне фиксируем группы.

- **Планирование / до визита:**
  - `draft` (черновик, опционально);
  - `scheduled` (запись подтверждена, визит ожидается);
  - `rescheduled` (перенесено, но ближайшее состояние всё равно «ожидается визита»).
- **Во время визита:**
  - `in_progress` (пациент на приёме).
- **Финальные:**
  - `completed` (визит завершён, ERP‑узел отработал или явно зафиксирована ошибка);
  - `canceled_by_patient`;
  - `canceled_by_clinic`;
  - `no_show` (пациент не пришёл).
- **Особые/сервисные:**
  - `blocked` / `maintenance` (слот занят не пациентом, а служебной блокировкой);
  - `error` / `inconsistent` (редкие ситуации, когда инвариант нарушен и требуется ручная обработка).

### 2.3. UX‑аспекты (цвета/лейблы)

- Статусы группируются для UX:
  - «ожидающие визита» (`scheduled`, `rescheduled`);
  - «в процессе» (`in_progress`);
  - «успешно завершённые» (`completed`);
  - «проблемные» (`no_show`, `error`, `inconsistent`);
  - «отменённые» (`canceled_*`);
- Для каждого статуса задаём:
  - цвет (например, зелёный для `completed`, жёлтый для `in_progress`, красный/оранжевый для проблемных);
  - короткий label (локализуемый ключ) и расширенный tooltip (опционально);
  - набор доступных действий (см. ниже).

## 3. Архитектурный дизайн: enum + state‑machine + словарь

### 3.1. Backend: enum и переходы

- В доменном слое:
  - ввести enum, например:
    - `BookingStatus(str, Enum)` с перечислением всех статусов;
  - обновить ORM‑модель `Booking`, чтобы поле статуса было жёстко привязано к enum.
- В application‑слое:
  - ввести централизованный сервис/утилиту для изменения статуса, например:
    - `BookingStatusService` или методы в `BookingService`:
      - `can_transition(from_status, to_status) -> bool`;
      - `transition(booking, to_status, context)`, который:
        - проверяет допустимость;
        - вызывает связанные доменные операции (где нужно);
        - логирует переход.

### 3.2. Backend: связь с фасадом завершения визита

- `BookingCompletionService` из `ARCH_DEV_BKG_CORE_001.md`:
  - работает с конкретными переходами:
    - `scheduled`/`in_progress` → `completed`;
  - не позволяет:
    - перепрыгивать из неподходящих статусов (`canceled_*`, `no_show`, `completed`) в `completed`;
  - при ошибках ERP/LOYALTY:
    - либо оставляет статус прежним;
    - либо переводит в явный «проблемный» статус (если это согласовано в `ARCH_BOOKING_NEXT.md`).

### 3.3. Frontend: единый словарь статусов

- В общем фронтовом модуле (например, `frontend/src/shared/bookingStatus.ts` или аналог):
  - определить словарь:
    - `BOOKING_STATUS_CONFIG[status_code] = { labelKey, color, icon, group, availableActions }`.
- Этот словарь используется:
  - в PWA (страницы расписания/истории);
  - в админке (расписание, список записей, отчёты);
  - в Omnichannel/CRM (при отображении статусов записей в карточках лидов/пациентов).
- Доступные действия определяются:
  - не только по статусу, но и по ролям/пермишенам (RBAC), однако наличие/отсутствие кнопки на UI не должно ломать инварианты статусов — backend всегда остаётся источником правды.

## 4. Связь с доменами и наблюдаемостью

### 4.1. ERP / Finance

- Только определённые статусы:
  - допускают проведение ERP‑операций (`in_progress` → `completed`);
  - участвуют в отчётности (например, только `completed`, опционально `no_show` для анализа).
- В `ARCH_ERP_NEXT.md` и `DEV_PROMPT_ERP_*` фиксируем:
  - какие статусы считаются «монетизационными»;
  - как они фильтруются в отчётности.

### 4.2. CRM / Attribution

- Статусы определяют этапы воронки:
  - «записан» (`scheduled`), «прошёл визит» (`completed`), «no‑show`, «отменил» и т.д.
- `DEV_PROMPT_CRM_EVENTS_007`:
  - опирается на события смены статусов как триггеры для движения лида по стадиям.

### 4.3. Tasks / Attention

- Определён набор «событий по статусам», которые:
  - порождают Attention/Tasks (частые отмены, высокий процент `no_show`, долгие `in_progress` без завершения).
- `DEV_PROMPT_TASKS_MODEL_020`:
  - использует статусы в качестве источника сигналов, но не дублирует бизнес‑логику статусов.

### 4.4. Логирование и метрики по статусам

- Для ключевых переходов:
  - логировать:
    - `booking_id`, `clinic_id`, `from_status`, `to_status`, инициатор (`user_id` / системный контекст);
  - собирать метрики:
    - количество переходов по типам;
    - долю проблемных статусов (`no_show`, `error`, `inconsistent`).
