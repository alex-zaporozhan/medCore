# DEV_PROMPTS_ALEMBIC_SQUASH — Одна миграция под текущую схему

> Контекст: ARCH_ALEMBIC_MIGRATIONS.md.  
> Исполнитель: @DEV. Выполнять по шагам; после каждого шага проверять команды и при необходимости логи бэкенда.

---

## Цель

- Иметь одну миграцию с полной схемой по текущим моделям (ERP, CRM, лояльность, бумалесс, маркетинг и т.д.).
- Устранить множественные heads и обеспечить стабильный старт бэкенда (`alembic upgrade head` без падений).
- Два варианта: **быстрый** (локально, сброс БД) и **прод** (новая ветка миграций для новых установок / клиента).

---

## Шаг 0. Импорт всех сущностей в env.py

Чтобы `alembic revision --autogenerate` видел все таблицы, в `alembic/env.py` перед `target_metadata = Base.metadata` нужно импортировать все доменные сущности из `src/domain/entities`.

**Сделать:**

- В `alembic/env.py` уже добавлена загрузка всех модулей из `src/domain/entities` через `pkgutil.iter_modules`, чтобы в `Base.metadata` попали все таблицы. При необходимости убедиться, что ни один модуль сущностей не пропущен (исключён только `__init__.py`).
- Проверка: при запуске `alembic revision --autogenerate -m "schema_v2_initial"` против пустой БД (или новой БД) в сгенерированном upgrade() должны появиться все таблицы из кода (clinics, doctors, services, bookings, admins, cashboxes, financial_transactions, loyalty_*, omni_*, и т.д.). Перед autogenerate переменная `DATABASE_URL` (или `.env`) должна быть задана.

Критерий: autogenerate не пропускает таблицы, которые есть в моделях.

## Вариант A — Быстро (локально)

**Условие:** данные в БД можно потерять (например локальная разработка или тестовая БД).

1. Остановить контейнеры: `docker compose down`.
2. Удалить данные БД (чтобы начать с пустой схемы): удалить каталог `pgdata` в корне проекта или создать новую БД и прописать её в `.env` как `DATABASE_URL`.
3. В `alembic/versions/` создать новую миграцию от **пустой** БД:
   - Убедиться, что в env.py импортированы все сущности (шаг 0).
   - Запустить: `alembic revision --autogenerate -m "schema_v2_initial"`.
   - Открыть сгенерированный файл и задать `revision = "schema_v2_initial"` (или короткий ID ≤32 символов), `down_revision = None` (это единственная миграция для новой установки).
4. Для варианта A старые миграции не применять. Либо временно переименовать/переместить папку `alembic/versions` в `alembic/versions_old` и оставить в `alembic/versions` только новый файл с `schema_v2_initial`, чтобы при старте выполнялась только она.
5. Запустить контейнеры: `docker compose up -d`. Проверить логи: `docker compose logs backend --tail 100`. Ожидается: успешное выполнение `alembic upgrade head` и старт uvicorn.
6. Проверить вход в админку (логин).

## Вариант B — Прод (для новых установок и клиента)

**Условие:** сохранить возможность новых установок с одной миграцией; старые файлы миграций не удалять, но новую установку вести от одной ревизии.

1. Выполнить шаг 0 (импорт всех сущностей в env.py).
2. Создать новую миграцию с полной схемой:
   - Временно: отключить или переименовать текущую папку `alembic/versions` (например в `alembic/versions_old`), создать пустую `alembic/versions`.
   - Подключить к приложению пустую БД (новый инстанс или тестовая БД без таблиц).
   - Выполнить: `alembic revision --autogenerate -m "schema_v2_initial"`.
   - В сгенерированном файле задать `revision = "schema_v2_initial"` (≤32 символов), `down_revision = None`.
   - Проверить, что в upgrade() создаются все таблицы (включая alembic_version при необходимости не трогать — Alembic создаёт сам). Колонку alembic_version.version_num при создании таблицы задать длиной не менее 64 (например String(128)), если миграция создаёт таблицу заново.
3. Вернуть структуру миграций для репозитория:
   - Оставить в `alembic/versions` только новый файл `schema_v2_initial` как единственную миграцию для новых установок, либо
   - Перенести старые файлы в `alembic/versions_archive` и в корне оставить только `schema_v2_initial`, чтобы по умолчанию `alembic upgrade head` применял только её.
4. В документации (README или MIGRATION_UPGRADE.md) описать: для новой БД выполнять `alembic upgrade head`; для существующей БД с данными — отдельный сценарий (stamp или ручной апгрейд по ARCH_ALEMBIC_MIGRATIONS.md).
5. Проверка: новая БД → `alembic upgrade head` → все таблицы созданы, бэкенд стартует, логин в админку работает.

---

## Общие требования к ревизии

- Revision ID: короткий, до 32 символов (например `schema_v2_initial`).
- Одна «голова»: для новой установки только одна миграция с `down_revision = None`.
- В docker-compose команда старта бэкенда: `alembic upgrade head && exec uvicorn ...` (или только `alembic upgrade head` перед uvicorn). Не использовать `upgrade heads` до слияния старых веток.

---

## Критерий готовности

- Для новой БД: `alembic upgrade head` применяет одну миграцию и создаёт полную схему.
- Бэкенд-контейнер стартует без падения на этапе миграций.
- Вход в админку (логин) возможен после применения миграции.
