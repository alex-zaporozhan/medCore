## 🧪 QA_AUDIT_NEXT — аудит текущей версии Dental Booking Business OS

> **Роль:** QA_ARCH  
> **Фокус:** фактическое поведение по живому коду и маршрутам, без архитектурных решений.  
> **Источник правды:** backend/ frontend‑код и маршруты (`BUSINESS_*`/`ARCH_*` только как справка).

## 1. Обзор (общие выводы по качеству)

- **Сильные стороны:**
  - Широкий охват доменов уже реализован в коде: расписание и записи, предоплата, омниканал‑чат, CRM‑воронка, ERP (кассы, склад, зарплаты), задачи, лояльность, бумажные формы, отчёты.
  - Frontend для пациента (`/app`) и админки (`/admin`) построен вокруг современных UX‑паттернов (Stepper’ы, таблицы, ContextBar, EmptyState, PageSkeleton и т.п.).
  - Во многих местах состояние загрузки/пустых списков и ошибок явно обработано (`Loader`, `EmptyStateHint`, сообщения об ошибках).
- **Основные проблемы качества (высокий уровень):**
  - **Неполная бизнес‑завершённость** ряда сценариев: AI‑агент заведён на уровне маршрутов и хуков, но фактически заглушка; часть advanced‑сценариев CRM/ERP из V2 не доведена до конца.
  - **Неполная UX‑связность**: в ряде мест таблицы и списки показывают «сырые» статусы (например, статус брони без человеко‑читаемого лейбла), мало «drill‑down» переходов из high‑level вида в детали.
  - **Разнородность UX и дизайна**: новый дизайн (ContextBar, трёхколоночные layout’ы и насыщенные EmptyState’ы) и старые, более простые экраны сосуществуют; цель — везде новый стиль.
  - **AI‑уровень и Enterprise‑фичи (RBAC, Task manager, Attribution)** частично реализованы, но не на уровне «готового Enterprise» (скорее — продвинутый operational tool с мощной базой для роста).

Дальше — детальный разбор по ключевым сценариям пациента и администратора.

## 2. Сценарии пациента

### 2.1. Регистрация/логин и доступ к PWA

**Ожидаемое поведение (Business OS):**
- Пациент видит простой и понятный вход:
  - логин по телефону + SMS‑код или через OAuth;
  - после входа сразу попадает в PWA `/app` с доступом ко всем своим функциям (лента, запись, история, чат, лояльность, формы).
- При неавторизованном доступе к `/app/*`:
  - его перекидывает на `/login` с понятным сообщением;
  - после успешного логина происходит возврат к исходному сценарию (например, если он шёл на `/app/booking`).

**Фактическое поведение (по коду):**
- PWA‑обёртка `AppLayout` проверяет авторизацию пациента:
  - при отсутствии `accessToken` делает `navigate("/login", { replace: true })` (см. `frontend/src/app/layouts/AppLayout.tsx`).
- Отдельные страницы:
  - `/login` → `LoginPage.tsx` (редирект после успешной аутентификации — в `/app`).
  - `/oauth/result` → `OAuthResultPage.tsx` (обработка OAuth‑провайдера).

**GAPS (пациент — логин)**

- **G1 (S2 – UX/flow):** нет явного механизма возврата к исходному маршруту после успешного логина. Сейчас после логина пациент всегда попадает на `/app`, даже если шёл напрямую, например, на страницу записи.  
  *Риск:* дополнительное трение, особенно если PWA предполагается как «маркетинговый туннель» (лендинг → запись).

---

### 2.2. Запись на приём (`/app/booking`)

**Ожидаемое поведение:**
- Линейный wizard:
  1. Выбор клиники (если их несколько) и услуги с прозрачными ценами/скидками.
  2. Выбор врача (фото, ФИО, специализация, рейтинг).
  3. Выбор даты и свободного слота (только доступные слоты).
  4. Подтверждение, оплата (если требуется), понятный результат.
- Уважение политики предоплаты:
  - если включена — обязательный шаг оплаты;
  - если нет — возможность записаться без предоплаты.
- Понятные ошибки:
  - если слоты закончились, нет врачей, не настроена предоплата — человеко‑читаемое сообщение, а не «ничего не происходит».

**Фактическое поведение (по коду `BookingWizardPage.tsx`):**
- Структура wizard’а:
  - Шаги `Stepper`: «Услуга» → «Врач» → «Дата и время» → (опционально) «Подтверждение/Оплата».
  - Выбор клиники не явный на шаге, но клиника вычисляется:
    - из `localStorage("app.selectedClinicId")`, если id есть и присутствует в списке клиник;
    - иначе — первая клиника из `useClinics()`.
- Выбор услуги:
  - список `usePublicClinicServices(clinicId)`; услуги показываются с ценой/скидкой (`base_price`, `effective_price`, `has_active_discount`).
- Выбор врача:
  - `useDoctors({ clinic_id, is_active: true })`;
  - карточки с фоткой, ФИО, рейтингом; фильтрация по `selectedService.doctor_ids`.
- Выбор слота:
  - `useDoctorSchedule(doctorId, dateStr)`, фильтруются `slots` по `is_available`.
- Подтверждение/оплата:
  - `handleConfirm` → `useCreatePatientBooking` + `useCreatePayment`;
  - redirect либо на `/booking/success`, либо на `payment_url` (YooKassa);
  - `handleConfirmWithoutPayment` — для сценария без предоплаты.
- Валидация:
  - `nextDisabled` блокирует переход, если не выбран сервис/doctor/slot/обязательные поля для оплаты.

**GAPS (пациент — запись)**:

- **G2 (S1 – UX/объяснимость):** Wizard не даёт явной информации, **почему** требуется предоплата или нет (есть только `prepaymentEnabled` по настройкам клиники, но нет UI‑объяснения политики).  
  *Риск:* пациент может не понимать, почему иногда нужен платёж, а иногда нет; влияет на доверие.

- **G3 (S2 – многоклиничность/контекст):** текущий выбор клиники завязан на `localStorage` + первую клинику. Нет явного UI‑шага выбора клиники в wizard’е, что усложняет сценарии, когда пациент сознательно записывается в другую локацию/филиал.  
  *Риск:* в multi‑clinic‑сетапе записи могут «случайно» попадать не в ту клинику, где ожидал пациент.

- **G4 (S2 – UX ошибок):** обработка ошибок backend при создании записи/платежа делегирована хукам (`useCreatePatientBooking`, `useCreatePayment`), но в `BookingWizardPage` нет явного UI для показа сообщения об ошибке (toast/alert). В случае неудачи пользователь может увидеть просто «ничего не произошло».  
  *Риск:* ухудшение доверия, особенно при платёжных сценариях.

### 2.3. История записей и отмена (`/app/history`)

**Ожидаемое поведение:**
- Пациент видит:
  - список прошлых/будущих визитов с датой, временем, врачом, статусом, краткими деталями услуги/клиники;
  - возможность отменить предстоящий визит (в рамках правил клиники);
  - понятное отображение статуса (подтверждён, завершён, отменён, no‑show).

**Фактическое поведение (`HistoryPage.tsx`):**
- Используется `usePatientBookings(patientId, accessToken)`; есть:
  - `Loader` при загрузке;
  - текст ошибки при `isError`;
  - `EmptyStateHint` «Нет записей» при отсутствии данных.
- Таблица:
  - Колонки: Дата, Время, Статус, Действия.
  - Значения:
    - дата: `b.appointment_date`;
    - время: строка `appointment_time.slice(0, 5)` или аналог для другого типа;
    - статус: **сырое поле** `b.status` (например, `confirmed`, `completed`, `cancelled`).
  - Кнопка «Отменить»:
    - доступна, если статус **не** `cancelled` и не `completed`;
    - вызывает `useCancelPatientBooking(accessToken)` с `bookingId` + `patientId`.

**GAPS (пациент — история):**

- **G5 (S2 – UX/локализация статусов):** статус брони показывается как сырое поле `b.status` без человеко‑читаемого русского лейбла или цветового кодирования.  
  *Риск:* бизнес‑пользователь и пациент видят технические статусы вместо понятных текстов.

- **G6 (S2 – информативность):** в истории не отображаются врач, клиника, услуга/тип визита — только дата/время/статус.  
  *Риск:* при большом количестве визитов пациенту сложно вспомнить, «куда» эта запись.

### 2.4. Чат пациента (`/app/chat`)

**Ожидаемое поведение:**
- Для пациента:
  - понятный диалог с клиникой, история сообщений, стикеры, отметка прочитанности;
  - явное понимание, что удаление сообщения у него не удаляет его у админа (privacy expectations).
- Для системы:
  - корректная маркировка прочитанности;
  - аккуратные пустые состояния и ошибки.

**Фактическое поведение (`ChatPage.tsx`):**
- Авторизация:
  - если нет `accessToken` или `patientId` → отображается заглушка «Войдите в аккаунт, чтобы писать в чат.».
- Загрузка:
  - `usePatientConversation` (`convData`) + `usePatientChatMessages`;
  - `DataSkeleton` при загрузке беседы;
  - текст «Ошибка загрузки» при `convError`.
- Список сообщений:
  - показывается `EmptyStateHint`, если сообщений нет;
  - сообщения выравниваются по левому/правому краю по признаку `is_mine`;
  - сообщения типа `sticker` рендерятся как картинка по `stickerKeyToUrl`.
- Управление:
  - кнопка «Обновить» инвалидирует кэш сообщений и беседы;
  - пациент может удалять свои сообщения (батон «Удалить»).
  - модалка «Очистить мои сообщения» удаляет все сообщения пациента и явно сообщает, что у администратора они сохраняются.

**GAPS (пациент — чат):**

- В рамках просмотренного кода явных грубых UX‑дыр не обнаружено: есть лоадеры, пустые состояния, понятные тексты.  
  Возможные дальнейшие улучшения (на стыке с ARCH/UX, не жёсткие баги):
  - richer‑мета по визиту/контексту прямо в чате (какой визит, кто врач и т.п.);
  - поддержка вложений (фото/документы), если это целевая фича.

## 3. Сценарии администратора

В этом первом проходе как QA_ARCH зафиксированы верхнеуровневые наблюдения по админке на базе маршрутов и нескольких ключевых страниц; полный детальный аудит каждого модуля будет вынесен в отдельные `FRONTEND_GAPS_*_NEXT` и `BACKEND_GAPS_*_NEXT`. Здесь — только основные проблемы, заметные уже сейчас.

### 3.1. Расписание и записи (`/admin/schedule`, `/admin/bookings`, лист ожидания)

**Ожидаемое поведение:**
- Админ:
  - видит календарь с записями (по врачам/кабинетам);
  - может создавать/переносить/отменять записи;
  - управляет листом ожидания и политиками очередей;
  - видит связку с предоплатой/платежами.

**Фактическое поведение (по маршрутам и кодовым хукам):**
- Имеются отдельные страницы:
  - `SchedulePage.tsx` (операционное расписание),
  - `AdminBookingsPage.tsx`,
  - `AdminWaitlistPage.tsx`,
  - `AdminPrepaymentPage.tsx`.
- Backend:
  - роутеры `schedule`, `bookings`, `admin_schedule`, `admin_waitlist`, `admin_prepayment`, `payments`.
- QA‑уровень в этом артефакте:
  - подтверждает наличие всех необходимых «точек входа» для сценария;
  - детальные UX‑/бизнес‑gaps должны быть выявлены в следующих специализированных артефактах.

**GAPS (админ — расписание/записи):**

- **G8 (S2 – необходимость глубинного теста):** текущий артефакт фиксирует наличие модулей, но не даёт развернутой картины по UX (drag‑and‑drop, фильтры, связка с ERP/CRM). Требуется отдельный QA‑проход `AdminBookingsPage`/`SchedulePage` и связанных сервисов, который выйдет за рамки первичного QA_AUDIT_NEXT.

---

### 3.2. CRM‑воронка (`/admin/sales`)

**Ожидаемое поведение:**
- Kanban‑доска по лидам:
  - колонки стадий с количеством и суммой по лидам;
  - карточки лидов с ключевой информацией (заголовок, сумма, источник, статус);
  - drag‑and‑drop между стадиями с триггером бизнес‑логики;
  - связь с чатами/записями/платежами.

**Фактическое поведение (`AdminSalesPipelinePage.tsx` + `admin_crm.py`):**
- Наличие Kanban‑реализации:
  - drag‑and‑drop с использованием `@dnd-kit/core`;
  - колонки стадий с агрегациями (`leads_count`, `sum_estimated_value`);
  - карточки лидов с источником, оценочной/фактической суммой, статусом, датами.
- Интеграция:
  - кнопка для перехода в чат по `omnichannel_contact_id`.

**GAPS (админ — CRM):**

- **G9 (S2 – автодвижение и связка с Booking/Payments):** V2 предполагает автоматическое создание и движение `LeadCard` по событиям Booking/Payments/Omnichannel. По коду видно ручное управление Kanbanом; степень автодвижения по событиям требует дополнительной проверки. В данном артефакте фиксируется риск несовершенной связки CRM с остальными доменами.  
  *Риск:* CRM остаётся полуручной, а не полностью привязанной к операционной реальности.

### 3.3. ERP (финансы/зарплаты/склад) (`/admin/finance`)

**Ожидаемое поведение:**
- Панель ERP:
  - учёт касс, движений, зарплат, склада в привязке к визитам/услугам;
  - чёткая связь между завершением визита и финансовыми/складскими транзакциями.

**Фактическое поведение (`AdminFinancePage.tsx` + `admin_finance.py` и связанные):**
- Frontend:
  - вкладки: «Кассы», «Транзакции», «Зарплаты», «Склад»;
  - использование `ContextBar`, `PageSkeleton` и таблиц;
  - базовая аналитика (своды по зарплатам, транзакциям, запасам).
- Backend:
  - эндпоинты для касс, транзакций, зарплат, складских операций и liability (аванс по подпискам).

**GAPS (админ — ERP):**

- **G10 (S2–S1 – ERP‑узел завершения визита):** в V2 описан единый транзакционный узел при `Booking.status → completed` (деньги + ЗП + склад). В текущем артефакте QA фиксирует:  
  - наличие ERP‑эндпоинтов и UI;  
  - необходимость глубокого теста бизнес‑цепочки «завершить визит → деньги/ЗП/склад».  
  *Риск:* возможны несогласованности (частично записались деньги, но не списались материалы и т.п.), что критично для Enterprise‑уровня.

### 3.4. Задачи и Attention Feed (`/admin/tasks`, `/admin/attention`)

**Ожидаемое поведение:**
- Единый Task‑центр:
  - задачи от AI, от пользователя, от системных событий (ERP ошибки, follow‑up по чатам);
  - удобная фильтрация, статусы, приоритеты, привязка к пациенту/визиту.

**Фактическое поведение (по маршрутам и коду AttentionFeedService):**
- `AttentionFeedService` в backend реально собирает:
  - follow‑up события по чатам;
  - ERP‑ошибки по визитам;
  - retention/loyalty‑gap события.
- `AdminTasksPage.tsx` и `AdminAttentionFeedPage.tsx` (по маршрутам) предоставляют UI‑слой для задач и attention‑ленты.

**GAPS (админ — задачи/attention):**

- **G11 (S2 – AI Task Manager как v2‑фича):** ядро AttentionFeed уже реализовано, но полноценный AI Task Manager (ночной генератор задач) и глубокая интеграция задач со всеми доменами требуют дополнительной проверки и, вероятно, доработка. В этом артефакте QA фиксирует риск недотянутой v2‑функции, а не явных багов в существующем коде.

### 3.5. Omnichannel и AI‑слой (`/admin/omni-chat`, AI Agent)

**Ожидаемое поведение:**
- Оператор:
  - работает в едином Omnichannel, где чаты, CRM‑контекст и AI‑подсказки живут рядом;
  - может использовать AI‑агента для function‑calling (создать запись, предложить слоты, посчитать оффер).

**Фактическое поведение (по `AdminOmniChatPage.tsx`, `AdminLayout.tsx`, `ai_agent.py`, `useAiAgent.ts`):**
- Omnichannel:
  - UI‑страница `AdminOmniChatPage` интегрирована с Omnichannel backend;
  - в `AdminLayout` есть Spotlight и действия, в том числе «Спросить AI».
- AI‑агент:
  - backend: `ai_agent.py` содержит `POST /ai/agent` и `POST /ai/generate-offers`, но оба **заглушки** (статический ответ / пустой список);
  - frontend: `useAiAgent.ts` ожидает `/v1/ai/agent`, но имеет fallback‑заглушку на случай ошибки.

**GAPS (админ — Omnichannel/AI):**

- **G12 (S1 – критический функциональный gap):** AI Agent на уровне маршрутов и хуков присутствует, но фактически не реализует function‑calling и автопилот; это чистая заглушка.  
  *Риск:* несоответствие заявленному позиционированию Business OS с AI‑агентом; по сути AI‑слой сейчас — только аналитика/отчёты, а не операционный агент.

## 4. Приоритизация проблем (S0–S3)

- **S0 — блокирующие для Enterprise‑уровня (не зафиксированы явно в этом первом проходе)**  
  (должны появиться после глубокой проверки ERP‑узла, безопасности и критичных бизнес‑инвариантов).

- **S1 — серьёзные функциональные/продуктовые GAPS:**
  - **G12:** AI Agent — только заглушка, при заявленном Enterprise‑AI‑позиционировании.
  - **G10:** ERP‑узел завершения визита: наличие модулей есть, но нужна верификация полного Unit‑of‑Work.

- **S2 — важные UX/логические проблемы и неполный охват:**
  - **G1:** возврат после логина не сохраняет исходный маршрут (трение при входе).
  - **G2:** непонятность политики предоплаты/оплаты в wizard’е записи.
  - **G3:** неявный выбор клиники при записи (особенно для сетевых клиник).
  - **G4:** отсутствие явного UI‑отображения ошибок при создании записи/платежа.
  - **G5:** сырые статусы в истории визитов (технические vs человеко‑читаемые).
  - **G6:** слабая информативность истории (нет врача/услуги/клиники).
  - **G7:** неполный QA‑охват модулей лояльности и форм в данном артефакте.
  - **G8:** неполный QA‑охват расписания/листов ожидания/связи с CRM/ERP.
  - **G9:** частичная реализованность автодвижения CRM‑лидов.
  - **G11:** недотянутый AI‑Task Manager / Task‑центр.

- **S3 — косметика / улучшения, которые логичнее детализировать в FRONTEND_GAPS/UX_FLOWS:**
  - единообразие стилей по всем страницам/модалкам (старый vs новый дизайн);
  - дополнительные метаданные в чатах, историях, таблицах (путь к Enterprise‑уровню удобства).

## 5. Рекомендации для ARCH (на что обратить внимание)

1. **AI‑агент:** рассмотреть как отдельный критический домен в ARCH_DECISIONS_NEXT — сейчас есть только «скелет»; нужно решить, каким будет минимальный реалистичный v1 function‑calling, который можно реализовать без переписывания пол‑проекта.
2. **ERP‑узел завершения визита:** проверить связку Booking → Finance → Payroll → Inventory по коду и учесть в архитектурных инвариантах и миграционном плане.
3. **Связность CRM/ERP/Omnichannel:** формализовать, какие события (создание контакта, запись, завершение визита, платёж) должны автоматически двигать CRM‑лиды и порождать Attention/Tasks.
4. **UX‑однообразие и человеко‑читаемость:** заложить в архитектурные принципы:
   - единое отображение статусов и бизнес‑сущностей (через словари/мэппинги, а не сырые строки);
   - обязательное наличие расширенных EmptyState/ошибок/лоадеров на всех экранах.
5. **INDI‑режим:** при проектировании vNext учитывать, что реализация будет одиночным разработчиком — важно, чтобы DEV_PROMPTS_NEXT шли маленькими, самодостаточными шагами, не требующими массового переписывания.
