## ARCH_DEV_BKG_ERRORS_005_TASKS — сверх‑детализированные dev‑таски

### 1. Understand — где и как сейчас обрабатываются ошибки записи/платежей

1.1. **Backend: собрать все места обработки ошибок в Booking/Payments.**  
1.1.1. В `bookings.py`, `payments.py`, `admin_prepayment.py`, `BookingService` и платёжных сервисах найти:  
       - блоки `try/except`;  
       - места, где возвращаются ошибки/статусы API (4xx, 5xx);  
       - участки, где ошибки «проглатываются» или сворачиваются в общий 500.  
1.1.2. Составить список типичных ошибок (валидация, занятый слот, ошибки шлюза, таймауты, внутренние проблемы).

1.2. **Frontend: собрать текущее поведение ошибок в PWA и админке.**  
1.2.1. В PWA (`BookingWizardPage`, хуки записи/платежей) и в админке (формы Booking/Prepayment/Payments) найти:  
       - как отображаются ошибки (toast, alert, ничего, общий текст);  
       - какие полевые/общие сообщения сейчас есть.  
1.2.2. Отметить места, где пользователь не получает понятного фидбэка (или вообще не понимает, что произошло).

1.3. **Сопоставить с GAPS и OBS.**  
1.3.1. Связать найденные проблемы с пунктами `BACKEND_GAPS_Booking_NEXT.md` (BKG‑5), `FRONTEND_GAPS_AppPWA_NEXT.md` (FPWA‑4) и `NONFUNCTIONAL_AUDIT_NEXT.md` (OBS‑1/2).  
1.3.2. Зафиксировать, какие именно сценарии ошибок должны быть покрыты структурированным поведением.

### 2. Design‑to‑code — единый формат ошибок и интеграция с trace_id

2.1. **Спроектировать enum и DTO ошибок Booking/Payments.**  
2.1.1. На основе ARCH‑раздела 3.1 определить список кодов ошибок (`BookingErrorCode`), минимум:  
       - `SLOT_UNAVAILABLE`, `PATIENT_NOT_FOUND`, `PAYMENT_FAILED`, `PREPAYMENT_REQUIRED`, `VALIDATION_ERROR`, `SERVICE_UNAVAILABLE`.  
2.1.2. Оформить DTO `BookingErrorResponse` (code, message, details?, trace_id?) в общем DTO‑модуле (например, `booking_dto.py` или близком).

2.2. **Определить маппинг ошибок в HTTP‑коды.**  
2.2.1. Для каждого `BookingErrorCode` определить, какой HTTP‑статус должен возвращаться (обычно 400/409/422 для бизнес‑ошибок, 503/500 для системных).  
2.2.2. Зафиксировать этот маппинг либо в коде (утилита), либо в документации (раздел в ARCH‑файле).

2.3. **Интегрировать `trace_id` в формат ошибок.**  
2.3.1. Включить поле `trace_id` в DTO ошибок, чтобы фронт/поддержка могли по нему найти логи цепочки (совместимо с `ARCH_DEV_OBS_CHAINS_023.md`).  
2.3.2. Убедиться, что `trace_id` всегда присутствует для ошибок, возникающих в рамках критичных цепочек.

---

### 3. Implement — backend: выдача структурированных ошибок

3.1. **Обновить роутеры Booking/Payments для использования DTO ошибок.**  
3.1.1. В `bookings.py`, `payments.py`, `admin_prepayment.py` заменить разрозненную обработку ошибок на единый паттерн:  
       - бизнес‑ошибки → возврат 4xx с `BookingErrorResponse` (code, message, details, trace_id);  
       - непредвиденные исключения → 5xx, но с логированием полного контекста и корректной маскировкой на фронт.  
3.1.2. Переподнять места, где сейчас возвращается общая техническая ошибка, и сопоставить их с конкретными `BookingErrorCode`.

3.2. **Интегрировать trace_id и логирование.**  
3.2.1. В местах, где формируется `BookingErrorResponse`, добавлять текущий `trace_id` из контекста (из OBS‑middleware).  
3.2.2. Логировать для каждой ошибки: `trace_id`, `clinic_id`, тип операции, `error_code`, важные детали (без ПД).

3.3. **Настроить пороги для Attention/Tasks по повторяющимся ошибкам.**  
3.3.1. Определить правила:  
       - N ошибок определённого `BookingErrorCode` по одной клинике/шлюзу за интервал T → Attention/Task;  
       - отдельные «критичные» коды (например, системная ошибка платёжного провайдера) → Attention сразу.  
3.3.2. Реализовать в соответствующем слое (например, в сервисе обработки ошибок/метриках) вызов `AttentionFeedService` при срабатывании порогов.

---

### 4. Implement — frontend: PWA (BookingWizardPage)

4.1. **Обновить хуки записи/платежей для работы с DTO ошибок.**  
4.1.1. В хуках `useCreatePatientBooking`, `useCreatePayment` и аналогичных:  
       - разобрать `BookingErrorResponse` из ответа;  
       - пробросить `code`, `message`, `trace_id` и, при наличии, `details` в компонент‑экран.  
4.1.2. Обеспечить корректную работу `isLoading`/`isError` состояний и предотвратить дабл‑сабмит.

4.2. **Ясно отрисовать ошибки на `BookingWizardPage`.**  
4.2.1. Для разных `BookingErrorCode` определить конкретные тексты и зоны отображения:  
       - `SLOT_UNAVAILABLE` → баннер/alert рядом с выбором времени;  
       - `PAYMENT_FAILED` → баннер/alert рядом с блоком оплаты;  
       - `SERVICE_UNAVAILABLE` → общий верхний alert, возможно, с предложением попробовать позже.  
4.2.2. При ошибке не закрывать wizard и не сбрасывать шаг без действия пользователя; явно показывать, что операция не завершена.

4.3. **Опционально отображать `trace_id` для саппорта.**  
4.3.1. В ошибочном состоянии (например, разворачиваемый блок «Подробности для поддержки») можно показывать `trace_id`, чтобы оператор мог быстро передать его при обращении.

---

### 5. Implement — frontend: админские экраны Booking/Payments

5.1. **Поддержать структурированные ошибки в админке.**  
5.1.1. В админских формах создания/редактирования записей и предоплаты/платежей обновить обработку ответов:  
       - использовать `BookingErrorResponse` для отображения ошибок;  
       - показывать бизнес‑понятные сообщения (аналогично PWA, но с учётом роли оператора).  
5.1.2. Для системных проблем (шлюз недоступен, ERP‑ошибка) показывать явный alert и, при наличии Attention/Task, ссылка/указание на него.

5.2. **Убедиться в консистентности UX между PWA и админкой.**  
5.2.1. Проверить, что одинаковые коды ошибок приводят к схожему по смыслу UX (пусть и с разной формулировкой для пациента и администратора).

### 6. Observe — метрики и тесты по ошибкам записи/платежей

6.1. **Добавить метрики по ошибкам цепочки записи/платежей.**  
6.1.1. В местах формирования ошибок увеличить счётчики по типам (`booking_errors_total{code="..."}{clinic_id="..."}` и т.п.).  
6.1.2. При наличии мониторинга — добавить графики/алерты по наиболее критичным кодам (шлюзы, системные сбои).

6.2. **Покрыть основной набор сценариев тестами.**  
6.2.1. Unit/интеграционные тесты на backend:  
       - успешное создание записи и оплаты;  
       - ошибки: занятый слот, провал платёжного шлюза, ошибки валидации;  
       - проверка, что возвращаются корректные `BookingErrorCode` и HTTP‑статусы.  
6.2.2. Тесты на фронте (по возможности):  
       - что соответствующие сообщения/баннеры отображаются для разных кодов;  
       - что wizard/формы ведут себя предсказуемо (не создают дубликаты, не уходят в неопределённое состояние).

6.3. **Синхронизировать GAPS и документацию.**  
6.3.1. Обновить `DEV_PROMPTS_NEXT.md`, указав статус `DEV_PROMPT_BKG_ERRORS_005`.  
6.3.2. В `BACKEND_GAPS_Booking_NEXT.md` (BKG‑5), `FRONTEND_GAPS_AppPWA_NEXT.md` (FPWA‑4) и, при необходимости, `NONFUNCTIONAL_AUDIT_NEXT.md` (OBS‑1/2) отметить закрытые/уточнённые пункты.

## На потом (@QA_ARCH — предложения)

Рубрика для **следующих итераций** после v1 структурированных ошибок записи/платежей; не заменяет §6 Stabilize, а фиксирует **качество, согласованность с другими эпиками и эксплуатацию**.

1. **Единый словарь кодов с Booking AI tools** — согласовать `BookingErrorCode` / маппинг HTTP с `ARCH_DEV_BKG_AI_TOOLS_006_TASKS` §7.1 (единый слой `booking_ai_errors` или эквивалент), чтобы Orchestrator, tools и PWA опирались на **те же стабильные коды** для аналитики и UI.  
2. **Второй проход по «сырым» ошибкам** — аудит `bookings` / `payments` / `admin_prepayment` на остатки общих 500 / неструктурированных тел без `code` + `trace_id`; вынести в `BookingErrorResponse` по мере обнаружения.  
3. **E2E / контрактные тесты** — API или Playwright: занятый слот / провал шлюза → ожидаемый JSON с `code` и `trace_id` → баннер на `BookingWizardPage`; регресс «wizard не в неопределённом состоянии».  
4. **Метрики и алерты** — дашборд по `booking_errors_total` (или выбранному семейству) с разрезом `code`, `clinic_id` (кардинальность под контролем); алерты на всплески `SERVICE_UNAVAILABLE` и кодов платёжного шлюза.  
5. **Пороги Attention/Task (§3.3)** — если в v1 не введены: дедуп по `(clinic_id, error_code, time_bucket)` и тип Attention/Task по согласованию с `ARCH_DEV_TASKS_MODEL_020` / `AttentionFeedService` (см. также `ARCH_DEV_BKG_AI_TOOLS_006_TASKS` §7.5).  
6. **UX и доступность** — локализация текстов по `code`, A11y для alert/banner, сверка с `UX_FLOWS_AND_GAPS_NEXT` (FPWA‑4).  
7. **OpenAPI и саппорт** — явно описать схему тела ошибки (поля `code`, `message`, `details`, `trace_id`) в OpenAPI; при необходимости короткий runbook для саппорта «как искать по trace_id».  
8. **Документация** — при полном закрытии BKG‑5 обновить `ARCH_AUDIT_NEXT.md` одной строкой про структурированные ошибки booking/payments.
