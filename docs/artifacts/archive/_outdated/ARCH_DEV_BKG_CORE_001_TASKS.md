### 3. Implement — реализация `BookingCompletionService.complete_visit`

3.1. **Реализовать базовый поток `complete_visit`.**  
3.1.1. В методе `complete_visit` реализовать шаги:  
       - загрузка `Booking` по `booking_id`;  
       - валидация `clinic_id` (сравнение с контекстом `actor`);  
       - проверка, что статус находится в допустимом состоянии для завершения (не завершён, не отменён и т.п.).  
3.1.2. При нарушении условий (чужая клиника, неверный статус) возвращать `BookingCompletionResult` с `success=False` и соответствующим `error_code`.

3.2. **Подготовить данные для ERP‑узла и Loyalty.**  
3.2.1. На основе текущих бизнес‑правил (см. `ARCH_BOOKING_NEXT.md`, `ARCH_ERP_NEXT.md`, `ARCH_LOYALTY_NEXT.md`) собрать структуру услуг/позиций, сумм по источникам оплаты, данных для ЗП/склада (заглушечно, если ERP‑узел ещё не реализован полностью).  
3.2.2. Сформировать объекты `ErpBookingCompletionRequest` и `LoyaltyWriteOffRequest` (с временной/упрощённой логикой, если полная ещё не внедрена).  

3.3. **Вызвать ERP‑узел и Loyalty‑слой (через их сервисы/заглушки).**  
3.3.1. В текущей реализации фасад всегда вызывает `ErpVisitNodeService.process_visit_completion`, который адаптирует legacy‑сервис `BookingErpService.process_booking_completed` под новый контракт `ErpVisitNodeRequest/Result`.  
3.3.2. Ошибки конфигурации ERP (`ERPConfigurationError`) приводят к контролируемому отказу фасада: `Booking.status` не меняется, в `booking.erp_error_code` записывается код ошибки, а для владельца/админа создаётся системный `Task`.  
3.3.3. Loyalty‑слой подключён по принципу best‑effort: при ошибках списания фасад не блокирует завершение визита, но возвращает сводку `loyalty_summary` и увеличивает метрики ошибок; для несогласованности ERP/Loyalty‑обязательств (например, `attempt_write_off_more_than_remaining` из ERP‑ноды) создаётся системный `Task` `LOYALTY_ERP_INCONSISTENT_OBLIGATION`.

3.4. **Обновить агрегаты CRM/Attribution и `Booking.status`.**  
3.4.1. После успешного прохождения ERP и Loyalty (без критичных ошибок):  
       - фасад переводит `Booking.status` в `completed` через `BookingStatusService.transition`;  
       - публикуется доменное событие `BookingCompleted` через `make_booking_completed_event` и общий `event_bus` — это минимальный CRM/Attribution‑слой вокруг завершения визита, использующий legacy‑интеграцию, пока отдельный CRM/Attribution‑сервис не выделен.  
3.4.2. В случае ошибок ERP: фасад не изменяет статус `Booking` на `completed`, формирует `BookingCompletionResult` с `success=False` и кодом ошибки, проставляет `booking.erp_error_code` и создаёт системный `Task`; ошибки Loyalty по‑прежнему обрабатываются в режиме best‑effort и не блокируют смену статуса, но попадают в резюме и метрики.
