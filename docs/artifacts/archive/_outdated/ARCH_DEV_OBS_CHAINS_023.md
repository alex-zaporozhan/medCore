## 1. Контекст и существующее состояние

### 1.1. Зачем нам этот файл

- В `NONFUNCTIONAL_AUDIT_NEXT.md` зафиксировано:
  - недостаток логов/метрик по ключевым бизнес‑цепочкам;
  - сложность ответа на вопросы:

  - критичные цепочки прямо названы:

    - `Omnichannel + AI`;
    - `CRM + Attribution`;
    - Tasks/Attention как слой сигналов над ними.

### 1.2. Текущее состояние (по аудиту и коду)

- Есть отдельные логи и метрики на уровне:
  - HTTP‑запросов (стандартные access‑логи/метрики);
  - частей бизнес‑логики (местами логируются ошибки, но не всегда структурировано).
- **Дополнение 2026-03-20:** для **in-process доменной шины** (`EventBus`) при публикации события сбой одного подписчика **не прерывает** вызов следующих; каждый сбой логируется и попадает в счётчик **`domain_event_handler_failures_total`** (`src/core/metrics.py`, метки `event_name`, `handler`). Подробности и ссылка на тесты — в `ARCH_AUDIT_NEXT.md` §4.
- Нет:
  - единых **трейсов** или корреляционных идентификаторов, проходящих через всю цепочку;
  - явной спецификации «какие метрики считаются must‑have для каждой цепочки»;
  - карты цепочек, привязанной к конкретным сервисам/эндпоинтам/таскам.

### 1.3. Связанные ARCH/DEV артефакты

## 2. Целевое состояние наблюдаемости по цепочкам

### 2.1. Жёсткие инварианты

1. **Каждая критичная бизнес‑цепочка описана и трассируема.**
   - Для каждой цепочки есть:
     - схема (последовательность шагов/сервисов/эндпоинтов);
     - единый **correlation_id / trace_id**, который проходит через весь путь;
     - минимальный набор логов/метрик на каждом шаге.

2. **Ошибки и деградации на любом шаге видны как на уровне домена, так и на уровне цепочки.**
   - Ошибка в ERP‑узле на событии `Booking.completed`:
     - видна как:
       - ошибка конкретного сервиса/эндпоинта;
       - и как «обрыв цепочки Booking→ERP/CRM/Loyalty» с привязкой к `booking_id`/`clinic_id`.

3. **Наблюдаемость не раскрывает ПД, но даёт достаточно контекста для диагностики.**
   - В логах/метриках:
     - используем идентификаторы (`booking_id`, `clinic_id`, токены из AI‑слоя), но не ФИО/телефон/e‑mail;
     - значения, связанные с ПД, маскируются или опускаются.

4. **Метрики и логи по цепочкам устойчивы к изменениям реализации.**
   - Обновление внутренней логики (рефакторинг сервисов) не ломает:
     - основную структуру метрик (названия/лейблы);
     - базовые графики и алерты.

### 2.2. Ключевые цепочки

> Список уточняется/расширяется по мере развития системы, но для vNext фиксируем минимум:

1. **Booking → ERP / CRM / Loyalty**
   - Старт:
     - изменение `Booking.status` (обычно `scheduled`/`in_progress` → `completed`);
     - вызов фасада `BookingCompletionService.complete_visit`.
   - Шаги:
     - подготовка данных по услугам/оплате;
     - вызов ERP‑узла;
     - вызов Loyalty‑сервисов;
     - обновление агрегатов CRM/Attribution;
     - финальный статус `Booking`.

2. **Omnichannel + AI**
   - Старт:
     - получение/отправка сообщения в Omnichannel (чат/канал);
     - вызов AI‑оркестратора.
   - Шаги:
     - построение контекста (доменные данные по пациенту/записи/лиду);
     - вызовы AI‑провайдера через SafeAiClient;
     - интерпретация ответа (AI‑tools);
     - возможные изменения в доменах (Booking/CRM/Tasks и т.п.).

3. **CRM + Attribution**
   - Старт:
     - создание лида/контакта;
     - привязка к источнику трафика/кампании.
   - Шаги:
     - движение лида по стадиям (связано со статусами Booking и операциями ERP);
     - запись событий атрибуции;
     - формирование отчётов ROI.

4. **Tasks & Attention как слой сигналов**
   - Старт:
     - события из доменов (ошибка ERP, высокий процент `no_show`, AI‑ошибка, просроченные задачи и т.п.).
   - Шаги:
     - генерация `AttentionItem`/`Task`;
     - изменение их статусов;
     - закрытие/эскалация.

## 3. Архитектурный дизайн: correlation_id, логи, метрики

### 3.1. Correlation / Trace ID

- Вводим единую концепцию `trace_id` (или `correlation_id`), которая:
  - создаётся на входе в цепочку:
    - HTTP‑запрос (при вызове фасада/Omnichannel/CRM‑операции);
    - Celery‑таск (если он инициирует цепочку);
  - передаётся:
    - через контекст запросов/тасков;
    - в параметры логов/метрик;
    - в события Tasks/Attention (чтобы можно было быстро найти связанные логи).
- Технически:
  - используем:
    - либо встроенный механизм трассировки/логгера (если есть APM);
    - либо свой middleware, который добавляет `X-Trace-Id` в запрос/ответ и кладёт ID в контекст.

### 3.2. Структурированные логи

- Для каждого шага в цепочке:
  - логируем:
    - `trace_id`;
    - тип цепочки (`booking_to_erp`, `omni_ai_flow`, `crm_attribution`, `tasks_attention`);
    - ключевые идентификаторы (`booking_id`, `clinic_id`, `lead_id`, `task_id` и т.п.);
    - статус операции (`start`, `success`, `error`) и коды ошибок.
- Логи строятся так, чтобы:
  - по одному `trace_id` можно было собрать весь «путь» через Grep/APM;
  - не требовалось смотреть в десяток файлов/форматов.

### 3.3. Метрики

Для каждой цепочки определяем:

- **Счётчики (counter):**
  - количество запусков цепочки;
  - количество успешных/неуспешных завершений;
  - количество ошибок по категориям (валидация, ERP, AI, таймаут и т.п.).
- **Гистограммы (histogram):**
  - время прохождения цепочки целиком;
  - время ключевых шагов (например, ERP‑узел, AI‑вызов, формирование отчёта).
- **Гейджи (gauge) / производные метрики:**
  - количество «зависших» состояний (например, `in_progress` слишком долго, не закрытые Tasks по критичным Attention).

Названия/лейблы метрик:

- следуют единообразному паттерну:
  - `business_chain_{name}_total`;
  - `business_chain_{name}_errors_total`;
  - `business_chain_{name}_duration_seconds`;
  - `business_chain_{name}_step_duration_seconds{step="erp"|"loyalty"|"ai"|"report"}`.

## 4. Карты цепочек (high‑level)

### 4.1. Booking → ERP / CRM / Loyalty

- **Точка входа:**
  - HTTP‑эндпоинт, вызывающий `BookingCompletionService.complete_visit` (см. `ARCH_DEV_BKG_CORE_001.md`).
- **Шаги и наблюдаемость:**
  1. `BookingCompletionService`:
     - создаёт/получает `trace_id`;
     - логирует `start` с `booking_id`, `clinic_id`, текущим/целевым статусом.
  2. Подготовка данных:
     - логирует ключевые суммы/типы операций (без ПД пациента);
     - метрика `business_chain_booking_erp_step_duration_seconds{step="prepare"}`.
  3. Вызов ERP‑узла:
     - лог `start`/`success`/`error` с `trace_id`, типом операции;
     - метрика для ERP‑шага;
     - при ошибке:
       - статус Booking не меняется или переводится в проблемный;
       - создаётся Attention/Task.
  4. Вызов Loyalty:
     - аналогично ERP‑шагу.
  5. Обновление CRM/Attribution:
     - фиксация факта «успешный визит»;
     - метрики по воронке (связь с `DEV_PROMPT_CRM_MONEY_008`).
  6. Финальный статус:
     - лог `success`/`error` по цепочке;
     - метрика общей длительности цепочки.

### 4.2. Omnichannel + AI

- **Точка входа:**
  - Omnichannel API/вебсокет, инициирующий вызов AI‑оркестратора.
- **Шаги и наблюдаемость:**
  1. Получение сообщения:
     - логируем `trace_id`, `channel`, `direction` (`inbound`/`outbound`).
  2. Построение контекста:
     - лог с указанием типов доменных сущностей (без ПД, с id/токенами).
  3. Вызов AI через SafeAiClient:
     - метрика `business_chain_omni_ai_step_duration_seconds{step="llm"}`;
     - счётчик ошибок по типам (связь с `ARCH_DEV_OMNI_POLICY_016`).
  4. Применение решения:
     - если AI инициирует действия в доменах (создание Tasks, изменение Booking/CRM):
       - лог/метрика для этих доменных операций с привязкой к `trace_id`.

### 4.3. CRM + Attribution

- **Точка входа:**
  - создание лида, фиксация источника трафика.
- **Шаги:**
  1. Регистрация лида:
     - лог `crm_attribution_start` с `lead_id`, `source`, `campaign`.
  2. Движение по стадиям:
     - лог/метрики по переходам (см. `DEV_PROMPT_CRM_EVENTS_007`);
     - *Факт кода (v1 CRM_EVENTS_007):* событийные переходы воронки в `LeadLifecycleService` пишут структурированные логи с `chain=crm_lifecycle`, `step` (в т.ч. `crm_lifecycle_transition`, `resolve_target`, `transition`, `close_lost`), `event_type`, `from_semantic`/`to_semantic`, `trace_id`; счётчики `crm_lead_lifecycle_transitions_total`, `crm_lead_visit_completion_outcomes_total`, `crm_lead_booking_onboarded_total` и др. — см. `ARCH_DEV_CRM_EVENTS_007_TASKS.md` («Выполнено»). Полное выравнивание имён `step` с эталоном таблицы §4 — в «На потом» того же TASKS (**@QA_ARCH**).
  3. Связка с визитами и ERP:
     - использование статусов Booking и ERP‑данных;
  4. Формирование отчётов:
     - метрики по времени и успеху построения отчётов, если они тяжёлые.

### 4.4. Tasks & Attention

- **Точка входа:**
  - генерация Attention/Task из событий доменов.
- **Шаги:**
  1. Создание AttentionItem:
     - лог `attention_created` с `trace_id` исходного события (если есть);
  2. Преобразование в Task:
     - лог `task_created_from_attention`;
  3. Изменение статусов Task/Attention:
     - метрики по времени до закрытия;
  4. Алерты:
     - при зависших критичных задачах.
