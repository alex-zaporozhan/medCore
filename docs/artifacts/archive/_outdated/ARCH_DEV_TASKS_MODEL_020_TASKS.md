### 2. Design‑to‑code — модель связей и статусов

2.1. **Спроектировать модель связи Attention ↔ Task.**  
2.1.1. Выбрать вариант реализации (из ARCH):  
       - отдельная сущность `AttentionTaskLink` (предпочтительно);  
       - или поля `attention_id` в `Task` / агрегат ссылок в `AttentionItem`.  
2.1.2. Описать структуру: идентификаторы, `created_at`, `created_by` (user/AI/system), при необходимости дополнительные атрибуты.  
2.1.3. Спроектировать миграции/обратную совместимость (что делать с уже существующими задачами и Attention).

2.2. **Сформализовать статусы задач и Attention.**  
2.2.1. На основе `ARCH_DEV_TASKS_MODEL_020.md` определить финальный набор статусов:  
       - Task: `open`, `in_progress`, `done`, `cancelled`;  
       - Attention: `new`, `in_progress`, `resolved`, `archived`.  
2.2.2. Уточнить маппинг между ними (когда Attention считается обработанным, когда остаётся в работе).  
2.2.3. При необходимости обновить enum’ы/константы и продумать миграции.

### 3. Implement — backend: сущности и сервисы связки

3.1. **Ввести сущность/поля связи.**  
3.1.1. Реализовать `AttentionTaskLink` (или выбранный вариант) в доменном/ORM‑слое:  
       - добавить таблицу/поля;  
       - написать миграции для БД.  
3.1.2. Обновить DTO/мэппинги, чтобы можно было возвращать/принимать информацию о связанных задачах для Attention (и наоборот).

3.2. **Расширить/создать слой сервисов для связки.**  
3.2.1. Добавить сервис (или методы в существующих):  
       - `link_task_to_attention(attention_id, task_id, created_by)`;  
       - `get_tasks_for_attention(attention_id)`;  
       - `get_attention_for_task(task_id)`.  
3.2.2. Убедиться, что создание связей логирует операции с `trace_id`, `clinic_id`, инициатором (user/system/AI).

3.3. **Реализовать пересчёт статуса Attention на основе задач.**  
3.3.1. В `AttentionFeedService` (или новом сервисе) реализовать логику:  
       - `new` → нет связанных задач;  
       - `in_progress` → есть хотя бы одна задача `open`/`in_progress`;  
       - `resolved` → все связанные задачи `done`/`cancelled`;  
       - `archived` → явное действие пользователя/системы.  
3.3.2. Обновлять статус Attention при:  
       - создании/обновлении задач, связанных с Attention;  
       - изменении статусов задач;  
       - явных действиях пользователей (архивация сигналов).

         - краткую информацию о связанных задачах (количество, статусы, основные заголовки);

4.2.2. При клике на Attention уметь открыть список/Drawer задач, связанных с ним.

4.3. **Фронтенд: AdminTasksPage.**
