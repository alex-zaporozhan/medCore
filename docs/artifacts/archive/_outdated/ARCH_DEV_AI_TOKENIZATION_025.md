## ARCH_DEV_AI_TOKENIZATION_025 — Tokenization‑Layer для AI

> DEV_PROMPT_AI_TOKENIZATION_025 — tokenization‑слой для AI (OMNI‑2, SEC‑1)

---

## 1. Цель и место в общей картине

**Цель:** сделать так, чтобы внешний AI (Claude, OpenAI и т.п.) работал **только с псевдонимами** (`PATIENT#...`, `BOOKING#...`, `PACKAGE#...`),  
а реальные ПД и внутренние связи оставались строго внутри БД и доменных сервисов.

Tokenization‑слой дополняет политику `allow_personal_data` и `AiSanitizer` из `ARCH_DEV_OMNI_POLICY_016.md`,  
усиливая защиту ПД и делая движение данных через AI **обратимо только внутри системы**.

---

## 2. Текущее состояние (исходная точка)

- Имеется:
  - `AiSanitizer` маскирует телефон/e‑mail и умеет работать в режиме pass‑through.
  - `SafeAiClient` гарантирует, что все `messages[n].content` проходят через санитайзер.
  - `AiConfigService`/`ClinicAiSettings` управляют `allow_personal_data` и типом провайдера.
- Нет:
  - единого формата токенов (идентификаторов сущностей для AI);
  - отдельного слоя/сервиса, который:
    - выделяет в тексте ссылки на пациентов/записи/пакеты и заменяет их на токены;
    - умеет по ответам AI, содержащим токены, однозначно вернуть нас к доменным сущностям.

---

## 3. Целевая архитектура tokenization‑слоя

### 3.1. Типы токенов и формат

Вводим **стабильный текстовый формат токенов**, не содержащий ПД:

- Примеры:
  - `PATIENT#<uuid-or-short-id>`
  - `BOOKING#<uuid-or-short-id>`
  - `PACKAGE#<uuid-or-short-id>`
  - `WALLET#<uuid-or-short-id>`
  - `LEAD#<uuid-or-short-id>`
- Требования:
  - токен должен быть **дешёвым для генерации** и однозначно мапиться на внутренний `id` в рамках домена;
  - его можно восстанавливать:
    - либо напрямую из внутреннего UUID (`PATIENT#<uuid>`),
    - либо через маппинг‑таблицы (если выберем отдельные псевдонимы).
  - формат должен быть легко детектируемым в тексте по регулярке (для последующей дешифровки ответов).

### 3.2. Где и как токенизация применяется

Tokenization‑слой логично разделить на два уровня:

1. **Структурированный уровень (AI‑tools):**
   - во многих AI‑вызовах мы формируем structured payload:
     - список уже известных `patient_id`, `booking_id`, `lead_id` и т.п.;
   - здесь токены могут использоваться **в полях**, а не только в свободном тексте:
     - например, `{"patient_token": "PATIENT#<uuid>", "booking_token": "BOOKING#<uuid>"}`.

2. **Текстовый уровень (`AiSanitizer` / SafeAiClient):**
   - в `messages[n].content`:
     - заменяем любые упоминания пациентов/записей, если они появляются в виде текстовых маркеров;
     - гарантируем, что в финальном тексте наружу уходят только токены, а не ПД.

Путь данных:

1. Доменные сервисы формируют структуру (context), содержащую `patient_id`/`booking_id`/и т.п.
2. Перед вызовом AI:
   - Tokenization‑слой:
     - преобразует `id` → `token` и вставляет токены в payload (как structured, так и текстовый контекст);
     - передаёт уже токенизированный payload в SafeAiClient (`AiSanitizer` дополнительно чистит ПД).
3. AI возвращает текст/структуру с токенами.
4. Обратный слой:
   - извлекает токены из ответа;
   - мапит их обратно на внутренние `id`;
   - доменные сервисы используют **только внутренние id**, а не токены.

## 4. Хранение маппинга «токен ↔ сущность»

Есть два подхода (выбрать один в рамках реализации, в зависимости от требований к стабильности токенов):

1. **Прямое кодирование UUID в токене:**
   - формат токена включает реальный UUID, например:  
     `PATIENT#873e7e1f-...`, `BOOKING#4c29...`.
   - Маппинг:
     - не требуется отдельная таблица: доменные сервисы по токену вытаскивают id `split("#")[1]`;
   - Плюсы:
     - просто, не требует доп. хранения;
   - Минусы:
     - UUID сам по себе считается ПД только в том случае, если его можно связать с конкретным человеком;  
       в изоляции это допустимый риск, но важно **никогда не передавать вместе с ним что‑то типа ФИО/телефона/адреса**.

2. **Псевдо‑ID с отдельной токен‑таблицей:**
   - вводим таблицу, например `ai_token_mapping`:
     - `token: str`, `entity_type: str`, `entity_id: UUID`, `created_at`, `expires_at?`;
   - токены могут быть короткими, вроде `PATIENT#A1B2C3` или `BOOKING#K9L0M1`;
   - при отправке в AI:
     - создаём запись(и) в `ai_token_mapping`;
     - подставляем токены в payload;
   - при получении ответа:
     - по токенам вытаскиваем `entity_id`;
   - Плюсы:
     - даже знание токена и базы его значений **не раскрывает** схему id в БД;
   - Минусы:
     - требует управления сроком жизни и очисткой маппинга;
     - усложняет реализацию и добавляет слой хранилища.

Для первой реализации vNext (с прицелом на скорость и прозрачность) можно:

- начать с подхода 1 (UUID в токене),  
  при этом:
  - **жёстко запрещая передачу любых других ПД вместе с токенами** при `allow_personal_data=False`;
  - оставив возможность в будущем перейти к подходу 2 (через дополнительный ARCH_DEV/DEV_PROMPT).

## 5. Встраивание в AiSanitizer и AI‑tools

### 5.1. Расширение AiSanitizer

- Добавить возможность:
  - детектировать токены по регулярке, чтобы:
    - отличать их от обычного текста;
    - не маскировать их как ПД;
  - расширять маскирование:
    - для ФИО/адресов (регексы/словарный подход) — как отдельный этап (в будущем DEV).

### 5.2. Tokenization на уровне AI‑tools

- В `tools_registry`/`ai_tools` (когда он появится по DEV_PROMPT_OMNI_REGISTRY_015, BKG/CRM/Tasks):
  - при формировании контекста для AI:
    - обеспечивать, чтобы:
      - структурные ссылки (`patient_id`, `booking_id`, `lead_id`) переводились в токены заранее;
      - текстовые вставки (история переписки с упоминаниями сущностей) тоже токенизировались, где это возможно.
  - при разборе ответа AI:
    - искать токены, мапить их обратно на сущности;
    - избегать использования «голого текста» для бизнес‑решений, если есть токены.

## 6. Dev‑чек‑лист для DEV_PROMPT_AI_TOKENIZATION_025

**Предпосылки:**  
- DEV_PROMPT_OMNI_POLICY_016 реализован (все AI‑вызовы идут через SafeAiClient/AiSanitizer/AiConfigService).  
- Базовый рефакторинг безопасности/наблюдаемости по SEC/RBAC в работе или завершён.

### Шаги

1. **Спроектировать формат токенов и добавить его в кодовую базу.**
   - Определить константы/утилиты для генерации токенов (`make_patient_token(id)`, `parse_patient_token(token)` и т.п.).
   - Добавить регексы для обнаружения токенов в текстах (вместе с AiSanitizer).

2. **Решить, используем ли на первом этапе прямой UUID или выделенную таблицу.**
   - Для v1:
     - использовать UUID‑основу в токене (`PATIENT#<uuid>`), с акцентом на **строгий запрет** сопутствующих ПД при `allow_personal_data=False`;
   - Описать в комментарии/документе, как перейти к таблице mapping в будущем.

3. **Расширить AiSanitizer для поддержки токенов.**
   - Убедиться, что:
     - токены не маскируются как ПД (иначе ответ AI станет нефункциональным);
     - маскирование телефона/e‑mail остаётся;
     - заложить точки расширения для ФИО/адресов (но без немедленной агрессивной замены, если это может сломать существующие сценарии).

4. **Интегрировать tokenization в AI‑tools/Orchestrator (минимальный набор).**
   - Для первых AI‑tools (например, `get_available_slots`, `create_booking`):
     - убедиться, что:
       - идентификаторы сущностей, фигурирующие в текстовом контексте, переводятся в токены;
       - ответы AI, если ссылаются на пациентов/записи, используют токены, которые можно однозначно мапить обратно.

5. **Добавить тесты на токенизацию/десериализацию.**
   - Тесты для:
     - генерации/парсинга токенов (`make_*_token`/`parse_*_token`);
     - корректности работы AiSanitizer с текстами, содержащими токены и ПД;
     - round‑trip: `id → token → AI → token → id` (без потерь и без утечки ПД).

6. **Задокументировать ограничения и переходный план.**
   - В отдельной секции (можно в этом файле или в `ARCH_DEV_OMNI_POLICY_016`):
     - чётко описать, что:
       - при `provider_type="external"` + `allow_personal_data=False` все ПД убираются, остаются только токены;
       - бизнес‑операции на базе AI‑ответов должны основываться на токенах, а не на текстовых описаниях субъектов;
     - обозначить шаги для возможного перехода на отдельную mapping‑таблицу, если юридические/безопасностные требования усилятся.
