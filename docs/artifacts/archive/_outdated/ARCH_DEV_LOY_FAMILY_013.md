## ARCH_DEV_LOY_FAMILY_013 — FamilyLink и шаринг пакетов

> DEV_PROMPT_LOY_FAMILY_013 — «формализация FamilyLink и шаринга пакетов (LOY‑1)»

### Статус реализации в коде (v1, @QA_ARCH / 2026‑03)

Реализовано **ядро backend**: клинико‑уровневая сущность **`FamilyLink`**, **`FamilyLinkService`**, проверки при списании **подписки** (вместе с существующим **`PackageFamilyLink`**), **`beneficiary_patient_id` / `family_link_id`** на `subscription_usages`, движениях ERP и `wallet_transactions`, передача бенефициара при **завершении визита** (Booking), **`GET /patient/loyalty/history`** с учётом **`can_view_owner_history`** и деталями бенефициара, **списание кошелька** для другого пациента по FamilyLink, **admin API** `/admin/loyalty/family-links`, метрики (отказы, path списания, lifecycle ссылок), unit‑тесты сервисов. Не закрыто: отдельный UI, Omni/CRM, Attention `LOYALTY_FAMILY_RISK`, полная синхронизация GAPS/UX‑доков, интеграционный e2e Booking→ERP, отдельный RBAC‑permission, расширение **`ErpLoyaltyObligation`** бенефициаром — см. **`ARCH_DEV_LOY_FAMILY_013_TASKS.md`** (разделы **«Выполнено»**, **«На потом»**).

## 1. Контекст и существующее состояние

### 1.1. Бизнес‑цепочка и роль FamilyLink

- Домены Loyalty/ERP/Booking в vNext:
  - **Loyalty** хранит продукты (пакеты, депозиты, абонементы), балансы и историю списаний/начислений.
  - **Booking** создаёт визиты, на которых могут списываться услуги/суммы из пакетов/депозитов.
  - **ERP** отражает факт денег/обязательств по визитам и продуктам лояльности.
- **FamilyLink / групповой шэринг**:
  - несколько пациентов (семья/группа) могут использовать:
    - один и тот же пакет/депозит;
    - общий кошелёк/баланс;
  - при этом:
    - права использования зависят от отношений (родитель/ребёнок, супруги, доверенные лица и т.п.);
    - списания должны быть прозрачны и трассируемы по каждому участнику.

### 1.2. Проблема (GAPS LOY‑1 и связанные)

По `BACKEND_GAPS_Loyalty_NEXT.md`, `ARCH_LOYALTY_NEXT.md` и UX‑заметкам:

- Модель семейного/группового использования:
  - не оформлена как **первоклассный доменный механизм**;
  - частично реализована через:
    - неявные связи пациентов;
    - технические флаги в продуктах/кошельках;
    - договорённости на уровне UI.
- Риски:
  - невозможно прозрачно ответить:
    - «кто имеет право тратить этот пакет/депозит?»
    - «чья это операция списания и на какого пациента она повлияла?»
  - потенциальные нарушения:
    - по ПД (родственники видят лишнее);
    - по деньгам (неочевидные долги/обязательства между участниками семьи и клиникой).

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_LOYALTY_NEXT.md` — базовая доменная модель Loyalty (продукты, балансы, кошельки).
- `ARCH_BOOKING_NEXT.md` — как визиты используют Loyalty/ERP.
- `ARCH_ERP_NEXT.md` — отражение обязательств и выручки по пакетам/депозитам.
- `ARCH_TASKS_NEXT.md` — сигналы по рискам лояльности (низкий баланс, неиспользуемые пакеты и т.п.).

- `ARCH_DEV_OBS_CHAINS_023.md` — наблюдаемость цепочек, в т.ч. по лояльности.

## 2. Целевое состояние FamilyLink и шаринга

### 2.1. Жёсткие инварианты

1. **Явная модель FamilyLink.**
   - Связь между пациентами оформлена структурировано:
     - сущность `FamilyLink` (или эквивалент) с типами отношений и правами.
   - Любой доступ к общему ресурсу (пакет/депозит/кошелёк) через FamilyLink:
     - проходит через проверку этой модели.

2. **Общий ресурс принадлежит одной клинике/владельцу.**
   - Пакет/депозит/кошелёк:
     - имеет владельца (основной пациент/контрактное лицо);
     - имеет `clinic_id`;
   - Все операции по шэрингу:
     - не позволяют использовать ресурс вне `clinic_id` и вне ожидаемых отношений.

3. **Права использования задаются явно, а не подразумеваются.**
   - Для FamilyLink‑отношения:
     - храним как минимум:
       - `can_spend_from_shared_wallet` (bool/enum);
       - `can_view_history` (bool/enum);
       - (опционально) `spending_limit` или квоты.
   - Отсутствие явного разрешения → нет доступа.

4. **Каждое списание из общего ресурса трассируемо.**
   - Любая операция списания по пакету/депозиту/кошельку:
     - знает:
       - за кого (конкретный пациент/визит);
       - с какого общего ресурса;
       - по какому FamilyLink‑отношению доступ разрешён.

5. **FamilyLink не ломает существующие доменные инварианты.**
   - ERP остаётся источником правды по деньгам/обязательствам.
   - Booking остаётся источником правды по визитам.
   - Loyalty остаётся источником правды по продуктам/балансам.
   - FamilyLink — слой прав доступа к этим продуктам, а не второй учёт денег.

### 2.2. Основные сценарии

1. **Родитель оплачивает визиты ребёнка из семейного пакета.**
   - Пакет/кошелёк оформлен на родителя.
   - У ребёнка есть FamilyLink с правом «быть бенефициаром» (ему оказывают услуги).
   - При завершении визита:
     - Loyalty списывает из семейного пакета;
     - ERP отражает обязательство по пакету у владельца;
     - история/отчёты ясно показывают, за кого и кем оплачено.

2. **Супруги делят общий депозит.**
   - Депозит оформлен на одного из супругов.
   - Второй — со‑владелец или бенефициар с правом тратить.
   - Лимиты и история видны обоим (по политике, зафиксированной в FamilyLink).

3. **Группа пациентов (например, корпоративный договор).**
   - Общий баланс/пакеты, привязанные к «групповому аккаунту».
   - Каждый участник группы — через FamilyLink или расширенную модель (group link).
   - Права трат/просмотра задаются на уровне группы/ролей внутри неё.

## 3. Архитектурный дизайн моделей

### 3.1. Базовые сущности FamilyLink

На уровне домена Loyalty/CRM:

- `FamilyLink` (рабочее имя):
  - `id: UUID`
  - `clinic_id: UUID`
  - `primary_patient_id: UUID` (владелец/основной пациент)
  - `related_patient_id: UUID` (связанный пациент)
  - `relation_type: Enum` (parent, child, spouse, guardian, other)
  - `can_spend_from_owner_loyalty: bool | Enum`
  - `can_view_owner_history: bool | Enum`
  - (опционально) лимиты/квоты:
    - `spending_limit_total`, `spending_limit_periodic`, `valid_until`
  - служебные поля:
    - `created_at`, `updated_at`, `created_by`, `is_active`

- Дополнительно возможен уровень групп:
  - `LoyaltyGroup`:
    - `id`, `clinic_id`
    - `owner_patient_id` / `account_contact_id`
    - список участников (через отдельную связь).
  - Для vNext достаточно:
    - **семейной пары** `primary_patient` ↔ `related_patient`;
    - и опциональной привязки к группам в будущем.

### 3.2. Привязка Loyalty‑ресурсов к владельцу и бенефициарам

- Продукты/кошельки Loyalty:
  - `LoyaltyWallet` / `LoyaltyPackage`:
    - `id`, `clinic_id`
    - `owner_patient_id`
    - (опционально) `group_id`
  - В истории операций (`LoyaltyTransaction`/`WriteOff`):
    - храним:
      - `wallet_id` / `package_id`
      - `beneficiary_patient_id` (кто получил услугу/benefit)
      - `family_link_id` (если операция основана на FamilyLink)
      - `booking_id` (если списание связано с визитом)

### 3.3. Правила доступа при операциях

- При попытке:
  - списать из пакета/кошелька в пользу пациента `P`:
    - если `P` — владелец ресурса:
      - используем обычные правила Loyalty;
    - если `P` не владелец:
      - ищем актуальный `FamilyLink` или групповую связь:
        - `primary_patient` = владелец;
        - `related_patient` = `P`;
      - проверяем `can_spend_from_owner_loyalty` и (опционально) лимиты.
  - просмотреть историю операций по ресурсу:
    - проверяем:
      - является ли текущий пользователь/его контекст:
        - владельцем;
        - родственником с `can_view_owner_history=True`;
        - сотрудником клиники с соответствующими ERP/Loyalty‑пермишенами.

## 4. Интеграция с Booking и ERP

### 4.1. Завершение визита (Booking → Loyalty → ERP)

- При завершении визита (`DEV_PROMPT_BKG_CORE_001` + `DEV_PROMPT_ERP_NODE_010`):
  - Booking передаёт:
    - `booking_id`, `patient_id`
    - список операций/услуг, где оплата идёт:
      - из пакета/депозита (owner_patient_id может отличаться от `patient_id` визита).
  - Loyalty‑слой:
    - находит соответствующий ресурс (пакет/депозит/кошелёк);
    - проверяет FamilyLink/группу, если владелец ≠ пациент;
    - выполняет списание с сохранением:
      - `beneficiary_patient_id`, `family_link_id`, `booking_id`.
  - ERP‑узел:
    - получает агрегированную информацию:
      - по владельцу ресурса и бенефициару;
      - по типу ресурса (пакет/депозит/кошелёк);
    - отражает обязательства/выручку на уровне владельца (ERP‑контур).

### 4.2. Отчётность и аналитика

- В отчётах ERP/CRM/Loyalty:
  - важно уметь отвечать на вопросы:
    - сколько денег/услуг было потрачено:
      - по владельцу;
      - по каждому бенефициару в рамках семейной связки;
    - как FamilyLink влияет на retention/выручку.
- Архитектурно:
  - модель с `owner_patient_id`, `beneficiary_patient_id`, `family_link_id`:
    - позволяет строить такие отчёты без дублирования балансов:
      - ERP остаётся источником правды по суммам;
      - Loyalty — по балансам и операциям;
      - FamilyLink — по структуре семьи/группы.

## 5. Наблюдаемость и безопасность

### 5.1. Логирование

- Для операций с семейным/групповым шэрингом:
  - логировать:
    - `clinic_id`, `wallet_id`/`package_id`
    - `owner_patient_id`, `beneficiary_patient_id`
    - `family_link_id` (если есть)
    - тип операции (создание/обновление FamilyLink, списание, просмотр истории);
  - без включения ПД (ФИО, телефон и т.п.) в логи.

### 5.2. Tasks & Attention

- Аномальные ситуации:
  - частые отказанные попытки списаний по FamilyLink;
  - неожиданные всплески трат по семейным ресурсам;
  - истекающие пакеты/балансы, к которым привязано много родственников.
- Для них:
  - генерируются `AttentionItem`/`Task` по шаблонам из `ARCH_TASKS_NEXT` и `ARCH_DEV_TASKS_MODEL_020.md`.

### 5.3. Связь с SEC/RBAC

- Операции:
  - управления FamilyLink;
  - создания/редактирования групповых ресурсов;
  - доступа к истории списаний по семейным ресурсам:
    - относятся к чувствительным и:
      - защищаются пермишенами из `ARCH_DEV_SEC_RBAC_022.md`;
      - соблюдают `clinic_id`‑ограничения.
