## 2. Tasks — сервис и API

- [ ] **2.1. Богатый фильтр и DTO для задач**
  - `admin_tasks` сейчас возвращает «сырые» dict без отдельного DTO‑слоя.
  - Хвосты:
    - ввести Pydantic‑DTO для задач и комментариев, чтобы фронт имел стабильный контракт;
    - расширить фильтры (`status`, `assignee`, `role_assignee`, сроки, привязки к доменам) и задокументировать их.

- [ ] **2.2. Контекстная видимость задач**
  - Добавить критерии видимости:
    - врачи видят только задачи, где они исполнитель или `role_assignee="doctor"`;
    - менеджеры/владельцы видят все задачи клиники.
  - Отразить это и на уровне SQL‑запросов, и в тестах (403/404‑сценарии).

- [ ] **2.3. Утилиты `create_task_from_conversation` / доменные фабрики**
  - На данный момент задачи создаются напрямую через `TaskService.create_task`.
  - Нужны удобные factory‑методы:
    - для создания задач из контекста Omnichannel/CRM/ERP (автозаполнение `booking_id`, `patient_id`, `lead_id` и т.д.);
    - чтобы сократить дублирование логики в разных модулях.

## 3. AI Task Generator и системные задачи

- [ ] **3.1. Расширение перечня аномалий**
  - В Celery‑таске `run_ai_task_generator` сейчас собираются только:
    - отменённые визиты;
    - no‑show.
  - Требуется добавить и/или предусмотреть:
    - ERP‑аномалии (нет кассы/политики/склада/остатков);
    - лиды без движения (CRM);
    - другие сигналы из ARCH (например, клиенты с высоким риском оттока).

- [ ] **3.2. Конфигурация на уровне клиники**
  - Сейчас генератор ориентируется на `ClinicAiSettings.ai_enabled`, но:
    - нет явного разделения между «AI‑агент в чате включён» и «AI‑задачи включены».
  - Нужен отдельный флаг/настройка уровня клиники (например, `ai_tasks_enabled`, режим автоматизации), чтобы гибко управлять генерацией задач.

- [ ] **3.3. Формат ответа AI и надёжность**
  - Сейчас ожидается, что LLM вернёт `data["tasks"]` как список.
  - Хвосты:
    - чётко зафиксировать формат (JSON‑контракт) и добавить строгую валидацию (через Pydantic‑модель);
    - добавить тесты на «кривые» ответы и безопасное завершение таски без создания мусорных задач.

## 4. Интеграция Tasks с другими модулями

- [ ] **4.1. Автоматические задачи по событиям (без AI)**
  - Некоторые системные кейсы (ERP‑ошибки, low stock, лиды без движения) пока могут не создавать задачи автоматически.
  - Требуется:
    - убедиться, что все ключевые сценарии из ARCH реально создают задачи через `TaskService` при соответствующих событиях EventBus;
    - если какие‑то обработчики отсутствуют — спроектировать их и добавить.

- [ ] **4.2. Интеграция с OmniChat и AI‑агентом**
  - В текущем коде нет универсальной точки, где AI‑агент или оператор чата создаёт задачи «из разговора».
  - Нужны:
    - API/сервис для создания задач из Omnichannel‑контекста;
    - интеграция в оркестратор AI‑агента для случаев, когда он не может завершить сценарий (создание задач `source="ai_auto"`/`"ai_suggested"`).
