# QA_ARCH — план презентационного наполнения БД (одна клиника, «живой» контур)

> **Цель:** одна команда воспроизведения демо для покупателя: **одна** стоматология (в рамках текущей модели «один логин = одна клиника»), реалистичные ФИО, ~30 пациентов, записи на 3 месяца, лояльность, омниканал, задачи, внимание — без «Демо пациент» и смеси типов бизнеса.  
> **Важно:** цепочка Alembic уже сведена к baseline `schema_v2_initial` + последующие миграции **без** демо-данных; «грязь» была в **скриптах** (`seed_demo_data.py` и т.д.), не в DDL.

### Продуктовый backlog (обязательная доработка)

- **Один логин владельца / админа сети** с переключением активной клиники (или мультивыбор) вместо отдельной учётки на каждый филиал.  
- **Дашборды и отчёты:** фильтр «одна клиника | все клиники сети | выбранный набор» для выручки, задач, омниканала, ERP-витрин — согласовано с RBAC и tenant isolation.  
- До реализации этого эпика презентационный сид остаётся **одноклиническим**, чтобы совпадать с продуктом и PWA (`clinic_id` в конфиге).

---

## 1. Решение по «перестройке миграций»

| Подход | Оценка |
|--------|--------|
| Сквош всех миграций в один новый файл | Риск для существующих БД и веток; не делаем без отдельного ADR. |
| **Новый единый скрипт сидирования** `seed_presentation_showcase` | Рекомендуется: повторяемо, версионируемо, не ломает `alembic upgrade`. |

Итог: **DDL не трогаем**; добавляем **презентационный seed** и при необходимости помечаем старые `seed_demo_*` как legacy в комментариях.

---

## 2. Модель тенанта и вход админов

- В системе **один админ = один `clinic_id`** (JWT крепит клинику). Презентационный сид создаёт **одну** учётку `admin@dentapro.demo` с ролью `owner`.
- Пароль демо выводится в консоль при запуске (константа в коде только для локальной презентации).

**PWA / публичная запись:** один `clinic_id` в конфиге фронта — совпадает с единственной засеянной клиникой.

---

## 3. Данные по клинике (1×)

Поля: `name`, `phone`, `email`, `address`, `business_type=stomatology`, `workday_start/end`, `slot_duration_minutes`, опционально `theme_*`.

Пример нейминга: «Стоматология «Дентал Про» — Центральная клиника». Адрес и телефон — вымышленные, но полные.

---

## 4. Пациенты (~30)

- Уникальный `phone` в рамках клиники (`ux_patients_clinic_phone`).
- ФИО: русские полные имена, разный возраст, email вида `имя.фамилия@mail.example`.
- Без префиксов «Демо», без номеров телефонов как ФИО.

---

## 5. Врачи, услуги, расписание

- По **4 врача** на клинику: терапия, хирургия/имплант, ортодонтия, гигиена — с реалистичными ФИО.
- **10 услуг** (категории therapy/surgery/orthodontics/hygiene/diagnostics) — цены и длительности как в частной практике.
- `service_doctors`: каждый врач ведёт релевантный набор услуг (не «все ко всем», но пересечение для записи есть).
- `doctor_working_hours`: Пн–Сб 09:00–18:00 (чтобы покрыть календарь).

---

## 6. Записи (прошлый / текущий / следующий месяц)

- Диапазон: от **первого дня прошлого месяца** до **последнего дня следующего** от «сегодня» (локальная дата сервера).
- Статусы: в прошлом — преимущественно `completed`; в будущем — `confirmed`/`pending`; часть `cancelled`/`no_show` для правдоподобия.
- Распределение по слотам 30 мин, **без двойных броней** на `(doctor_id, date, time)`.
- `erp_processed=True` для завершённых (чтобы ERP-цепочки не висели «ошибкой» в демо).

---

## 7. Лояльность, семьи, скидки, абонементы

- **Discount:** первый визит −10%; сезонная акция на гигиену; скидка на имплант по направлению.
- **SubscriptionPackage:** 2–3 пакета (например «Гигиена 2 раза», «Профилактика семьи», «Орто-контроль»).
- **CustomerSubscription:** часть пациентов с активными пакетами.
- **FamilyLink:** 3–5 семейных связей (родитель–ребёнок, супруги) на клинику.
- **LoyaltyCampaignSettings:** строка на клинику (уже по схеме БД).

---

## 8. Задачи (Kanban)

- 6–10 задач на клинику: согласование ортопланов, звонок после имплантации, контроль лаборатории, проверка страхового случая, подготовка к OPG.
- Статусы `open` / `in_progress` / `done`, разные `priority`, `assignee_id` = админ клиники, `due_at` в ближайшие дни.

---

## 9. Омниканал (≥6 диалогов)

- Через `IntegrationGatewayService` + разные провайдеры: TELEGRAM, WHATSAPP, VK, WEBCHAT, EMAIL, отдельный чат INSTAGRAM (если поддерживается) или второй сценарий TELEGRAM.
- Тексты — рабочие: перенос, уточнение по оплате, претензия по сроку, согласование КТ, напоминание о профилактике.
- **Не смешивать** в один чат для демо (убрать merge TG+WA из старого `seed_omnichannel_demo`), чтобы в списке было ≥6 **отдельных** диалогов.

---

## 10. Лента внимания (Attention) и «конфликты»

- Сервис `AttentionFeedService` для блока **conflict** использует таблицу **`chat_messages`** (внутренний чат пациент–клиника), а не `omni_messages`.
- План сида: создать **`conversations` + `chat_messages`** с `sender_type=patient` и лексикой жалобы (ключевые слова из `_build_conflict_items`), плюс одно сообщение с `follow_up_at` для блока follow-up.
- Омниканал отдельно остаётся для экрана Omni Chat.

---

## 11. Бизнес-аналитика и отчёты

- Заполнить **завершённые визиты с ненулевой оплатой** (при необходимости — `payments` + связь) для агрегатов ERP; при отсутствии автозаполнения витрин — полагаться на raw-отчёты или запустить фоновые джобы обновления (в плане на будущее: nightly aggregate).

---

## 12. Администраторы и смены

- **Смены администраторов** как отдельная сущность в коде **не найдены**; не сидируем выдуманные смены. В roadmap — отложенная фича.
- ФИО администраторов — полные, должность в `full_name` или в задачах.

---

## 13. AI (Deepseek) — ожидания и проверка

- Код: `AiClient.is_configured()` = наличие `AI_PROVIDER_BASE_URL`; ключ и модель из `.env`.
- Для омниканала по умолчанию `omni_ai_settings.ai_mode=DISABLED` — в сиде выставить **`SUGGEST_ONLY`** на scope BUSINESS для каждой клиники.
- Если в Docker AI «молчит»: проверить `env_file: .env`, сеть до `api.deepseek.com`, лимиты rate limit.


## 15. Критерии «всё показали» (чеклист для презентации)

- [ ] Одна клиника в справочнике, заполненные реквизиты.
- [ ] Расписание и записи на 3 месяца, календарь не пустой.
- [ ] Лояльность: пакеты, подписки, семьи, скидки.
- [ ] Задачи с разными статусами и приоритетами.
- [ ] Omni: ≥6 чатов, осмысленные реплики.
- [ ] Attention: есть follow-up и conflict (через `chat_messages`).
- [ ] Лента promo_posts с опубликованными постами.
- [ ] Вход админа `admin@dentapro.demo` с RBAC owner.
