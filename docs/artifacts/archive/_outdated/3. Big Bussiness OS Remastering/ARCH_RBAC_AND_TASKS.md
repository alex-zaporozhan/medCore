## 🔐 ARCH_RBAC_AND_TASKS — Роли, доступы и задачи

> Роли: @ARCH, @BIZ, @LEAD.  
> Цель: спроектировать домен RBAC (роли и права) и Task Management, включая AI‑генерацию задач, поверх существующих AdminUser/AttentionFeed/Omnichannel.  
> На этом этапе только архитектура, без кода.

---

## 1. Задача и принципы

- **Задача:** отделить уровни доступа (клиника, финансы, CRM, ERP, AI‑модули) и дать системе возможность:
  - назначать задачи людям автоматически (по событиям и анализу AI);
  - контролировать выполнение задач.
- **Принципы:**
  - RBAC **строгий и явный** (никаких «магических» флагов в AdminUser);
  - матрица прав читается из БД и/или конфига, а не из разбросанных `if role == ...`;
  - задачи привязаны к доменам (Booking, Lead, Inventory и т.п.), но домены не зависят от задач.

---

## 2. Модель ролей и прав (RBAC)

### 2.1. Роли верхнего уровня

Базовый набор ролей (минимум для первой версии):

- `Owner` — владелец/собственник:
  - видит и управляет всем, включая финансовые отчёты, ЗП, настройки AI и тарифы.
- `Manager` — управляющий/директор:
  - видит CRM, отчёты, задачи, расписание, но не может:
    - менять глобальные настройки клиники;
    - настраивать зарплатные политики и кассы;
    - менять AI‑провайдера.
- `Admin` — администратор смены:
  - работает с чатами, календарём, очередью, маркетингом, задачами;
  - не видит:
    - детали финтранзакций;
    - суммы ЗП других людей.
- `Doctor` — врач/мастер:
  - видит только:
    - свой календарь;
    - свои задачи;
    - свои пациенты/карточки (без финансовых данных других).

При необходимости можно добавить роли `Accountant`, `Marketer` и др. в дальнейших фазах.

### 2.2. Сущности RBAC

**Role**

- `id: UUID`;
- `clinic_id: UUID | None` (глобальные роли vs специфичные для клиники);
- `code: str` (`owner`, `manager`, `admin`, `doctor`);
- `name: str`;
- `description: str | None`.

**Permission**

- Логический «атом» доступа.
- Примеры кодов:
  - `view_dashboard`, `view_reports`, `manage_clinic_settings`;
  - `view_finance`, `manage_finance`;
  - `view_payroll`, `manage_payroll`;
  - `view_inventory`, `manage_inventory`;
  - `view_crm`, `manage_crm`;
  - `view_tasks`, `manage_tasks`, `assign_tasks`;
  - `view_ai_settings`, `manage_ai_settings`.
- Поля:
  - `id: UUID`;
  - `code: str`;
  - `description: str`.

**RolePermission**

- Связка `role_id` ↔ `permission_id`.

**UserRole**

- Привязка AdminUser/Doctor к ролям.
- Поля:
  - `id: UUID`;
  - `user_id: UUID` (AdminUser / DoctorUser, в зависимости от реализации);
  - `role_id: UUID`;
  - `clinic_id: UUID` (для мультиклиник).

### 2.3. Реализация проверок

- На уровне FastAPI dependencies:

```python
def require_permissions(*permission_codes: str):
    async def dependency(current_admin: AdminContext = Depends(get_current_admin_with_roles)):
        if not current_admin.has_any_permission(permission_codes):
            raise HTTPException(status_code=403, detail="Forbidden")
        return current_admin
    return dependency
```

- Использование:
  - `@router.get("/admin/reports", dependencies=[Depends(require_permissions("view_reports"))])`
  - `@router.post("/admin/payroll/policies", dependencies=[Depends(require_permissions("manage_payroll"))])`

## 3. Модель задач (Task Management)

### 3.1. Сущность Task

**Task**

- Назначение: единица работы для сотрудника.
- Поля (проектно):
  - `id: UUID`;
  - `clinic_id: UUID`;
  - `title: str`;
  - `description: str | None`;
  - `status: str` (`open`, `in_progress`, `done`, `cancelled`);
  - `priority: str` (`low`, `medium`, `high`, `urgent`);
  - `creator_id: UUID | None`; // кто создал
  - `assignee_id: UUID | None`; // кому назначена задача (AdminUser/Doctor)
  - `role_assignee: str | None`; // если задача на роль (например, «любой Admin смены»)
  - `due_at: datetime | None`;
  - `created_at: datetime`;
  - `updated_at: datetime`;
  - `completed_at: datetime | None`;
  - связи с доменами:
    - `booking_id: UUID | None`;
    - `patient_id: UUID | None`;
    - `lead_id: UUID | None`;
    - `inventory_product_id: UUID | None`;
    - `source: str` (`manual`, `ai_suggested`, `ai_auto`);
    - `source_event_id: UUID | None` (ссылка на запись в AttentionFeed/другой сущности).

**TaskComment** (опционально)

- `id: UUID`;
- `task_id: UUID`;
- `author_id: UUID`;
- `created_at: datetime`;
- `text: str`.

### 3.2. Жизненный цикл задач

- Создание:
  - вручную из UI (админ/менеджер/owner);
  - автоматически по событию (см. раздел 4);
  - автоматически через AI Task Generator.
- Изменение:
  - смена статусов (`open → in_progress → done`);
  - переназначение исполнителя;
  - изменение срока.
- Закрытие:
  - по нажатию в UI;
  - автоматически по факту выполнения доменного события (например, выполнен звонок, закрыт лид).

## 4. Источники задач (триггеры)

### 4.1. Система событий

Источник событий — существующий `AttentionFeed` + доменные события:

- отменённые записи;
- пустые окна у врачей;
- лиды без движения;
- низкие остатки материалов;
- ошибки интеграций (Webhook/AI/платежи).

Для RBAC/Tasks важно:

- определить **тип события** и **рекомендованный исполнитель/роль**:
  - «Отменили запись у врача X на завтра» → задача на `Admin` или `Manager` клиники;
  - «Низкий остаток продукта Y» → задача на `Manager`/ответственного за склад;
  - «Лид 7 дней без ответа» → задача на `Admin/Manager` по CRM.

### 4.2. Автоматические задачи без AI

Даже без AI система может создавать базовые задачи:

- отмена записи → задача: «Перезаписать клиента/предложить окно другим»;
- отсутствие PayrollPolicy → задача: «Настроить политику ЗП для врача X»;
- отсутствие Cashbox → задача: «Настроить кассы для клиники».

Это реализуется как:

- обработчики событий домена → создание `Task` c `source="system"`.

## 5. AI Task Generator

### 5.1. Назначение и частота

- Периодический процесс (Celery Beat), например 1 раз в сутки ночью.
- Вход:
  - срез данных за период:
    - отменённые записи;
    - no‑show;
    - пустые окна в расписании;
    - лиды без движения;
    - ERP‑аномалии (низкие остатки, задолженности);
    - `AttentionFeed`.

### 5.2. Поток работы

1. Подготовка датасета:
   - агрегировать «аномалии» и «возможности роста» в структурированном виде:
     - `{"type": "cancellations", "count": 3, "doctor": "...", "clinic": "...", ...}`.
2. Вызов AI:
   - через `AiClient` в режиме «аналитика» (отдельная конфигурация модели);
   - промпт:
     - описание ролей/ограничений;
     - список возможных типов задач (шаблонов);
     - структурированный вход `json`.
3. Ответ AI:
   - ожидается список задач:

```json
[
  {
    "title": "Перезвонить 3 клиентам из листа ожидания врача Иванова на 14:00",
    "description": "Заполнить окно из-за отменённых визитов",
    "priority": "high",
    "role_assignee": "admin",
    "due_at": "2026-03-14T09:00:00",
    "links": { "booking_ids": [...], "patient_ids": [...] }
  },
  ...
]
```

4. Проверка и создание:
   - backend валидирует задачи (формат, связи, дубликаты);
   - создаёт `Task` с `source="ai_auto"`;
   - пишет события в `AttentionFeed`.

### 5.3. Ограничения и безопасность

- AI **не** может напрямую изменять доменные сущности:
  - он только предлагает задачи;
  - сами действия (звонки, изменения статусов, финансы) выполняют люди/сервисы.
- В конфиге клиники:
  - флаг `ai_tasks_enabled: bool`;
  - уровень автоматизации (только предложения vs автоматическое создание задач).

## 6. Связь RBAC/Tasks с другими модулями

- **CRM Kanban:**
  - задачи могут быть привязаны к `LeadCard`:
    - «Связаться с ледом N»;
    - «Закрыть лид как успех/потеря».
- **ERP:**
  - задачи по финансам/складу:
    - «Пополнить склад продуктом X»;
    - «Провести сверку кассы».
- **AI Agent / Omnichannel:**
  - оператор в чате может:
    - создавать задачи прямо из чата (кнопка «Создать задачу»);
  - AI может рекомендовать задачу:
    - «Клиент жалуется, создайте задачу на разбор кейса».

## 7. API и UI‑слой задач

### 7.1. Backend API

Роутер `admin_tasks.py` (проектно):

- `GET /api/v1/admin/tasks`:
  - фильтры: статус, приоритет, исполнитель, дата, доменные связи.
- `GET /api/v1/admin/tasks/{id}`:
  - детали задачи + комментарии.
- `POST /api/v1/admin/tasks`:
  - создание задачи вручную.
- `PATCH /api/v1/admin/tasks/{id}`:
  - обновление статуса, срока, исполнителя.
- `POST /api/v1/admin/tasks/{id}/comments`:
  - добавление комментария.

RBAC:

- просмотр:
  - `Owner`, `Manager`, `Admin` видят задачи своей клиники;
  - `Doctor` — только свои задачи (где `assignee_id` = его ID или `role_assignee="doctor"`).
- управление:
  - создание/назначение задач другим ролям — только для `Owner`/`Manager`;
  - изменение своих задач — для всех, кто назначен.

### 7.2. Frontend

- Новая страница `AdminTasksPage`:
  - список задач (таблица или Kanban по статусам);
  - фильтры по исполнителю/дате/приоритету;
  - быстрые действия (смена статуса, назначение).
- Интеграция:
  - виджет со списком задач на главной (`AdminDashboardPage`) — топ задач на сегодня;
  - виджеты задач в контексте:
    - на странице пациента;
    - в CRM‑лиде;
    - в Omnichannel‑чате.

## 8. Инварианты и контроль

1. **Матрица прав фиксируется явно**: таблица ролей ↔ permissions будет задокументирована и реализована в БД.
2. **Задачи — управленческий инструмент, не «технический лог»**:
   - AttentionFeed остаётся источником сигналов;
   - задачи — только то, что реально должно быть выполнено человеком.
3. **AI‑генерация задач вынесена в отдельный слой**:
   - легко отключается/заменяется;
   - не ломает доменные сервисы.
