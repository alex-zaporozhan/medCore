## DEV_TODOS_CRM_KANBAN_GAPS — хвосты по CRM / Kanban

> Основано на `DEV_PROMPTS_CRM_KANBAN.md` и текущей реализации (доменные сущности, `LeadService`, `lead_event_handlers`, `admin_crm`, `AdminSalesPipelinePage`).

## 1. Backend — доменная логика и события

- [ ] **1.1. Более точное связывание лидов с бронированиями и платежами**
  - Сейчас `handle_lead_on_payment_success` и `handle_lead_on_booking_completed` ищут лиды по `primary_booking_id` среди open‑лидов с лимитом (100).
  - Хвосты:
    - сделать поиск более прямым (например, репозиторный метод `get_lead_by_primary_booking_id`) вместо перебора;
    - продумать поведение, если у лида несколько связанных бронирований/платежей.

- [ ] **1.2. Стратегия стадий и статусов**
  - В `LeadService` и обработчиках событий стадии обновляются минимально (часто с `new_stage_id=None`).
  - Требуется:
    - зафиксировать и реализовать целевую стратегию переходов стадий по событиям (`new` → `booked` → `prepaid` → `success`/`lost`);
    - добавить коды стадий/статусов в конфиг или константы, чтобы не плодить magic‑строки.

- [ ] **1.3. Расчёт `estimated_value` / `actual_value`**
  - `estimated_value`/`actual_value` обновляются точечно и не всегда учитывают ERP/финансы:
    - при `BookingCreated` значение не всегда заполняется на основе стоимости услуги;
    - при последовательности нескольких платежей/визитов по одному лиду суммирование может быть неполным.
  - Нужен единый контракт, как именно CRM опирается на ERP/Finance для фактических сумм (особенно с учётом подписок/лояльности).
