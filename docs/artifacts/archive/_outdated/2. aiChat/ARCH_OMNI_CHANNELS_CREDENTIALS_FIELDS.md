# ARCH: Поля настроек каналов (credentials) по типам мессенджеров

> Как однозначно определить, какие поля нужны для какого мессенджера на странице «Омниканальные каналы», и как добавить новые поля.

---

## 1. Источники истины (как узнать поля «до 100%»)

### 1.1. Бэкенд — потребитель credentials

Ключи хранятся в зашифрованном виде в `omni_integration_configs.credentials_encrypted`. При сохранении фронт отправляет **JSON-строку** в `POST /owner/channels/{id}/credentials` (поле `payload`). На бэкенде эта строка шифруется и сохраняется как есть; при чтении — расшифровывается и возвращается **та же строка**. Кто использует credentials:

| Тип канала        | Где читается | Что ожидается в JSON (ключи) |
|-------------------|--------------|------------------------------|
| TELEGRAM_BOT      | `OmnichannelOutboundDispatcher._dispatch_telegram` | `bot_token` — обязателен для отправки сообщений клиенту |
| TELEGRAM_BOT      | `OmnichannelAIOrchestrator._get_telegram_admin_chat_id` | `admin_chat_id` — опционально, для уведомлений админу (эскалация, черновики AI) |
| TELEGRAM_BOT      | Webhook (integrations_gateway) | Токен для верификации вебхука может браться из env `TELEGRAM_WEBHOOK_SECRET` или из `webhook_secret` в payload |
| WHATSAPP_BUSINESS | Интеграция (нормализация вебхуков) | Обычно: `api_url`, `api_token`, `phone_number_id` (официальный Cloud API) |
| VK_BOT            | VK Callback API / отправка       | `group_id`, `access_token` (токен сообщества с правами сообщений) |
| VIBER_BOT         | Viber Bot API                    | `bot_token` |
| MAX_CHAT          | Кастомный провайдер              | `base_url`, `api_key`, `webhook_secret` (по контракту вашего провайдера) |
| SMS_GATEWAY       | SMSC/другой шлюз                 | `login`, `password`, `sender` |
| EMAIL_INBOX       | IMAP приём почты                 | `imap_host`, `imap_port`, `imap_user`, `imap_password`, `inbox_email` |

**Правило:** Поля для типа канала задаются **двумя местами**:
1. **Фронт** (`AdminOmniChannelsPage.tsx`): тип канала → форма (какие `TextInput` показывать) и объект `payload` при сохранении.
2. **Бэкенд** (диспетчер, оркестратор, интеграции): при чтении `get_integration_secret()` получают строку, парсят `json.loads(raw)` и берут нужные ключи. Добавление нового поля = добавить ключ в payload на фронте + использовать этот ключ в коде бэкенда, который работает с этим каналом.

### 1.2. Официальные API мессенджеров

Чтобы не гадать, а задать поля точно:

- **Telegram Bot API:** https://core.telegram.org/bots/api — для бота нужен `token` (от @BotFather); для отправки в чат админа — `chat_id` (число или строка, можно получить через @userinfobot или из `message.chat.id` в вебхуке).
- **WhatsApp Business Cloud API:** https://developers.facebook.com/docs/whatsapp/cloud-api — нужны Access Token, Phone Number ID, при вебхуках — Verify Token; опционально App Secret.
- **VK Callback API / сообщения:** https://dev.vk.com/api/community-messages — токен сообщества с правом `messages`, `group_id` (или `peer_id`).
- **Viber:** https://developers.viber.com/docs/api/rest-bot-api/ — токен бота.
- **Email (IMAP):** стандартные параметры подключения к почтовому ящику (host, port, user, password).

Итог: для каждого нового типа канала сверяйтесь с **официальной документацией** провайдера и с **кодом бэкенда**, который эти credentials читает (диспетчер, integration_gateway, и т.д.). Тогда набор полей будет однозначным.

## 2. ID чата админа для оповещений (Telegram)

### Зачем

Один чат администратора: личный диалог с ботом или группа, куда бот присылает **личные оповещения владельцу/админу** — как при настройке бота для онлайн-записи (API key + личный ID в Telegram: «записался клиент», «отменился клиент»). В этом проекте то же самое: бот должен знать, **куда слать оповещения админу** (клиент запросил оператора, новый черновик AI; при расширении — новая запись, отмена и т.д.). Раньше использовалось только глобальное значение `TELEGRAM_ADMIN_CHAT_ID` в env; теперь можно задать его в настройках канала TELEGRAM_BOT.

### Один чат vs несколько

- **Один чат админа на клинику/бота:** у одной клиники один канал TELEGRAM_BOT и в нём один `admin_chat_id` — один получатель всех оповещений. Так и задумано.
- **Если каналов несколько:** у каждого канала свой `admin_chat_id` (разные боты или разные чаты). Оповещения по событиям этого канала уходят в его `admin_chat_id`. Для одной клиники обычно один TELEGRAM_BOT и один чат админа.

### Как добавлено

- **Фронт:** В модалке «Настройка ключей: TELEGRAM_BOT» добавлено поле **«ID чата админа (для оповещений)»** (`admin_chat_id`). Сохраняется в том же JSON payload, что и `bot_token`, `webhook_secret`.
- **Бэкенд:**
  - `OmnichannelOutboundDispatcher._dispatch_telegram`: при отправке сообщения **клиенту** по-прежнему используется `contact.external_ids["telegram_user_id"]`; токен бота берётся из credentials (парсинг JSON, ключ `bot_token`).
  - `OmnichannelAIOrchestrator._get_telegram_admin_chat_id`: при уведомлении **админов** сначала читаются credentials канала чата; если в JSON есть `admin_chat_id` — используется он, иначе fallback на `settings.telegram_admin_chat_id`.

Как узнать ID чата: написать боту @userinfobot в нужный чат/группу или взять из вебхука Telegram (`update.message.chat.id`).

## 3. Чек-лист: добавить новое поле для типа канала

1. **Определить ключ и тип:** по документации провайдера и коду бэкенда решить имя ключа (например, `admin_chat_id`) и тип (строка, число).
2. **Фронт (`AdminOmniChannelsPage.tsx`):**
   - Добавить ключ в `CredentialsFormState` и в `initialCredentialsState`.
   - В блоке `if (type === "TELEGRAM_BOT")` (или другой тип) добавить в объект `payload` новый ключ из `credentialsState`.
   - В модалке для этого типа канала добавить `TextInput` (или другой контрол) с подписью и placeholder.
3. **Бэкенд:** В сервисе, который вызывает `get_integration_secret(channel_id)` и использует результат для этого типа канала, после `json.loads(raw)` читать новый ключ из словаря и использовать его (например, для уведомлений или для вызова API провайдера).

Так набор полей на странице и в хранилище остаётся согласованным и однозначным.

## 4. Контракт: отправка и сохранение credentials в бэкенд

### 4.1. Обязательное поведение

Credentials, введённые на странице «Омниканальные каналы» (`/admin/omni-channels`), **должны отправляться в бэкенд и сохраняться**. Цепочка:

1. Пользователь открывает канал → нажимает «Настроить ключи» (или аналог) → открывается модалка с полями по типу канала.
2. Пользователь заполняет поля и нажимает **«Сохранить»**.
3. **Фронт обязан** вызвать `POST /v1/owner/channels/{channel_id}/credentials` с телом:
   - `provider_type` — строка по типу канала (TELEGRAM, WHATSAPP, VIBER, VK, MAX, SMS, EMAIL, OTHER);
   - `scopes` — опционально, можно `null`;
   - `payload` — **строка** (JSON.stringify объекта с ключами по типу канала, см. п. 1.1).
4. **Бэкенд обязан** принять запрос, зашифровать `payload`, сохранить в `omni_integration_configs.credentials_encrypted` (create/update по `business_account_id` + `channel_id`), вернуть `204 No Content`.
5. После успешного ответа список каналов перезапрашивается; у канала выставляется `has_credentials: true`. Сырые ключи в ответах API **никогда не возвращаются** (безопасность).

### 4.2. Ошибки

- При ответе бэкенда 4xx/5xx **фронт обязан** показать пользователю сообщение об ошибке (например, в модалке под формой), не закрывать модалку и не сбрасывать введённые значения, чтобы пользователь мог исправить и повторить сохранение.
- Бэкенд при невалидном запросе возвращает 400/422 с деталями; при отсутствии канала или прав — 404/403.

### 4.3. Проверка

- После нажатия «Сохранить» в модалке ключей: в сетевой вкладке должен уходить `POST .../credentials` с телом; ответ 204; в списке каналов у данного канала статус/бейдж «Подключено» (has_credentials).
- Если запрос не уходит или падает с ошибкой — поведение должно соответствовать п. 4.2 (ошибка видна пользователю).
