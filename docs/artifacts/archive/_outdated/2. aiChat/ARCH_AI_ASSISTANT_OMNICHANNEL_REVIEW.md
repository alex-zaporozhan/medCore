## 2. Что добавить (по приоритету)

### 2.1 Must (критично для продакшена и ARCH)

**Идемпотентность входящих сообщений (раздел 5.2 ARCH)**

- **Где:** `IntegrationGatewayService.handle_inbound_normalized_message` перед `create_inbound_message`.
- **Что:** Проверять по `(chat_id, provider, external_message_id)` (через `source_metadata` или отдельный индекс), что сообщение с таким внешним id ещё не создано. Если уже есть — выйти без создания и без вызова AI (`return` после логирования "duplicate").
- **Зачем:** Двойная доставка вебхука (повтор от Telegram/других провайдеров) не должна создавать дубликаты в БД и не должна повторно дергать AI.

**Фильтрация скрытых сообщений в Admin API**

- **Где:** `GET /admin/omni-chats/{chat_id}/messages` и репозиторий `list_last_messages` / `list_messages_cursor`.
- **Что:** По умолчанию не возвращать сообщения с `ui_hidden = true` (или возвращать с полем `ui_hidden: true` в DTO и явным query-параметром `?include_hidden=true` для модераторов).
- **Зачем:** Соответствие смыслу soft-hide и контролируемому отображению в UI.

### 2.2 Should (важно для полноты и ARCH)

**Эндпоинт выгрузки Audit Log (раздел 7.5 ARCH)**

- **Где:** Новый роутер или расширение Owner API.
- **Что:** `GET /api/v1/owner/audit-log?type=&from=&to=&actor=&limit=` с пагинацией, фильтрами по `action_type`, `actor_type`, диапазону дат. Доступ только для Owner (те же проверки, что у `/owner/channels`).
- **Зачем:** Владелец может проверять действия с ключами и модерацией; требование ARCH.

**Уведомление админов при SUGGEST_ONLY (раздел 3.5 и 4.1 ARCH)**

- **Где:** `OmnichannelAIOrchestrator._suggest_only` после сохранения черновика.
- **Что:** Вызов существующего `NotificationService` (или аналога) — событие вида «новый черновик AI по чату X» для админов клиники (в ленту, email, или in-app в зависимости от того, что уже есть в проекте).
- **Зачем:** ARCH явно указывает `OutboundDispatcher.notifyAdmins` при сохранении черновика, чтобы оператор не пропустил подсказку.

**Детекция запроса живого оператора (раздел 4.2 ARCH)**

- **Где:** `OmnichannelAIOrchestrator.handle_incoming_for_ai` после получения ответа LLM (или до вызова LLM — отдельный шаг).
- **Что:** Простая эвристика по тексту последнего сообщения клиента: ключевые фразы («оператор», «живой человек», «позовите менеджера» и т.п.). При срабатывании: установить `chat.status = WAITING_FOR_OPERATOR`, переключить `ai_mode` чата на `SUGGEST_ONLY` или `DISABLED`, вызвать `notifyAdmins`.
- **Зачем:** Соответствие сценарию 4.2 и ожиданиям пользователей.

### 2.3 Nice (улучшения качества и масштабируемости)

**Данные домена в промпте AI (раздел 3.4 ARCH)**

- **Где:** `LLMClient.generate_reply` (или отдельный шаг сбора контекста в оркестраторе).
- **Что:** Подмешивать в системный/пользовательский промпт краткие факты: название клиники (уже есть), список услуг/прайс (заголовки и цены), «сейчас запись открыта/закрыта» по расписанию. Через существующие сервисы расписания и услуг, без тяжёлых запросов (агрегаты или кэш).
- **Зачем:** Ответы AI становятся привязаны к реальным данным клиники; ARCH это явно требует.

**Ретраи при отправке в Telegram (раздел 5.2 ARCH)**

- **Где:** `OmnichannelOutboundDispatcher._dispatch_telegram` (вызов `httpx`).
- **Что:** При 429/5xx или сетевой ошибке — ограниченное число повторов с экспоненциальным backoff (например, 2–3 попытки), логирование после последней неудачи.
- **Зачем:** Соблюдение rate-limits и устойчивость к кратковременным сбоям провайдера.

**Масштабирование WebchatPushManager (горизонтальное)**

- **Где:** `WebchatPushManager` (in-memory) и long-poll endpoint.
- **Что:** Документировать ограничение: при нескольких инстансах приложения long-poll на одном инстансе не получит событие от диспетчера на другом. Вариант решения: перенос «подписок» и уведомлений в Redis Pub/Sub (один канал на `chat_id` или глобальный с payload `chat_id`).
- **Зачем:** Предсказуемое поведение при масштабировании и деплое в несколько реплик.

## 3. Что изменить (рефакторинг и согласованность)

### 3.1 Контракт Outbound: Message vs DTO

- **Сейчас:** `dispatch_to_channel(message: Message)` принимает доменную сущность; диспетчер сам тянет chat/contact/channel из БД.
- **ARCH:** «sendMessageToProvider(channel_id, OutgoingMessageDTO)» — явный DTO и channel_id.
- **Рекомендация:** Оставить текущую реализацию как есть для MVP. При появлении очередей (Celery/Redis) ввести слой: «Message → OutgoingMessageDTO» в одном месте, воркер вызывает `sendMessageToProvider(channel_id, dto)`. Так проще тестировать и добавлять каналы без доступа к сессии.

### 3.2 Секреты: БД vs внешний vault (раздел 6 ARCH)

- **Сейчас:** Секреты хранятся в БД в зашифрованном виде (`encrypt_plaintext` / `decrypt_ciphertext`).
- **ARCH:** «хранятся во внешнем vault/KMS».
- **Рекомендация:** Для текущего этапа принять явное отклонение в ARCH или в отдельном ADR: «MVP использует шифрование в БД; перед продакшеном — миграция на HashiCorp Vault / облачный KMS». В коде выделить интерфейс `SecretsBackend` (get/set по ключу), реализация «encrypted DB» и позже «Vault» подставляются без смены вызывающего кода.

### 3.3 Owner API: пустой список каналов в GET omni-ai-settings

- **Где:** `owner_omni_ai_settings.get_omni_ai_settings`, условие `scope_id.in_([...]) if channels else False`.
- **Проблема:** При `channels == []` в `where` попадает литерал `False`; в части диалектов/версий это может вести себя неочевидно.
- **Рекомендация:** Явно разветвить: если `not channels`, не добавлять условие по `scope_id` и не выполнять запрос к `OmniAISettings` для CHANNEL (вернуть пустой `channel_items`). Либо использовать «невозможное» условие, например `OmniAISettings.scope_id.in_(select(...).where(False))`, если нужен один общий запрос.

### 3.4 Явная обработка ui_hidden в API сообщений

- **Где:** DTO ответа сообщений (например, `OmniMessageDto`).
- **Что:** Добавить поле `ui_hidden: bool` (и при необходимости `hidden_reason`) в DTO, чтобы фронт мог показывать скрытые сообщения с пометкой (при `include_hidden=true`) или не рендерить их при `include_hidden=false`.

## 5. Вывод

Реализация хорошо закрывает фазы 1–6 DEV_PROMPTS и большую часть ARCH: сущности, поток входящих сообщений, AI-оркестратор, диспетчер, админка и Owner API настроек/каналов. Для продакшена и полного соответствия ARCH стоит в первую очередь добавить идемпотентность вебхуков и явную работу с soft-hide в API сообщений, затем — выгрузку audit-log и уведомления админов при SUGGEST_ONLY; после этого — сценарий «клиент просит оператора» и доработки устойчивости/масштабируемости (ретраи, Redis для webchat push, при необходимости vault).
