## 2. ARCH: Архитектура тестов бэкенда

### 2.1. Слои тестирования

| Слой | Назначение | Где живёт | Зависимости |
|------|------------|-----------|-------------|
| **Unit** | Логика сервисов/домена без HTTP и БД (или с моками). | `tests/unit/` (создать), `tests/services/` (часть). | Минимум: моки session/Redis/SMS. |
| **Integration (API)** | HTTP-запросы к приложению, реальная БД и seed. | `tests/api/`. | `conftest`: init_db, seed_data, client, admin_auth, patient_auth, redis_client. |
| **E2E** | Полные сценарии (auth → booking → payment, фронт-страницы). | `tests/e2e/`. | БД, Redis, при необходимости мок внешних API (YooKassa, SMS). |
| **Security** | Проверки изоляции, отсутствия утечек секретов/ПД, авторизации. | `tests/security/` (создать), часть в `tests/api/`. | Те же фикстуры, что и API; без изменения прод-конфигов. |

### 2.2. Домены и границы

- **Оплаты (Касса):** платежи, webhook, credentials касс (`clinic_payment_gateways`), шифрование, доступ только админа своей клиники. См. `ARCH_PAYMENT_GATEWAYS.md` §5.
- **ПД (персональные данные):** пациенты, врачи, админы, контакты омниканалов; изоляция по clinic_id; отсутствие сырых ПД в ответах ошибок и логах (проверяется тестами/ревью).
- **Чаты:** единый чат (admin), пациентский чат, омниканальные каналы/сообщения; изоляция по клинике и каналу; доступ оператора только к своей клинике.
- **Аутентификация и авторизация:** пациент (SMS), админ (логин/пароль), owner-эндпоинты; rate limit, истечение токена.

### 2.3. Тестовая БД и фикстуры

- БД: `dental_booking_test` (или `DATABASE_URL_TEST`). Перед прогоном — миграции; `seed_data` создаёт одну клинику, админа, врача, услугу, слот (см. `conftest.py`).
- Фикстуры: `admin_auth` и `patient_auth` — через реальный логин; при частых прогонах возможен 429 на admin login — см. раздел QA (улучшения).
- Внешние вызовы: в тестах по возможности мокать SMS, YooKassa, платёжные/email-провайдеры, чтобы не зависеть от внешних сервисов.

### 2.4. Размещение в репозитории

```
tests/
  conftest.py           # общие фикстуры, init_db, seed_data, client, admin_auth, patient_auth, redis
  api/                  # интеграционные API-тесты по роутерам
  services/             # тесты сервисов (с БД)
  domain/               # тесты доменной логики (при необходимости)
  e2e/                  # сценарии запись→оплата, страницы
  security/             # НОВЫЙ: наборы безопасности Касса, ПД, Чаты (см. раздел SEC)
  unit/                 # НОВЫЙ (опционально): чистые unit без БД
```

- **Админ/Owner:** `test_admin_omni_chat.py`, `test_owner_omni_channels.py`, `test_owner_omni_audit.py`, `test_owner_omni_ai_settings.py`, `test_admin_create_doctor_patient.py`, `test_frontend_integration.py`.

- **Справочники и интеграции:** `test_doctors.py`, `test_services.py`, `test_schedule.py`, `test_bookings.py`, `test_integrations_gateway.py`, `test_integrations_gateway_whatsapp.py`, `test_stage1_universal_business.py`.

Полный регресс по оплатам и админским маршрутам описан в `docs/QA_REGRESSION_PAYMENTS_ADMIN.md`.

### 3.2. Улучшения существующих тестов (приоритет для DEV)

1. **admin_auth и rate limit (429)**  
   - **Проблема:** при последовательном запуске многих тестов admin login даёт 429.  
   - **Действие:** в тестовом окружении отключить или сильно ослабить rate limit для `/api/v1/admin/auth/login` (например, через переменную `TESTING=1` или отдельный конфиг), либо сделать фикстуру `admin_auth` с кэшем на сессию (один логин на сессию pytest).

2. **patient_auth и SMS**  
   - **Проблема:** `test_auth_send_code` и e2e с send-code вызывают реальный SMS → 500 при ошибке провайдера.  
   - **Действие:** в тестах мокать `AuthService.send_code` или SMS-клиент так, чтобы код сохранялся в Redis, но SMS не отправлялся; либо в `TESTING=1` не вызывать внешний SMS.

3. **Тесты без авторизации (401)**  
   - **Проблема:** часть тестов в `test_pricing_and_ai.py` и `test_frontend_integration.py` вызывают admin-эндпоинты без `admin_auth` → 401.  
   - **Действие:** добавить в сигнатуры этих тестов фикстуру `admin_auth` и передавать заголовок `Authorization: Bearer <token>` в запросах.

4. **«Чужой» clinic_id в тестах изоляции**  
   - **Проблема:** `test_owner_cannot_access_foreign_channel` использует тот же clinic_id, что и админ (seed).  
   - **Действие:** как в `test_admin_cannot_store_credentials_for_foreign_clinic`: подставлять заведомо чужой UUID (например, `uuid.uuid4()`), чтобы ожидать 404/403.

5. **Фикстура admin_auth — scope session**  
   - Рассмотреть возможность сделать `admin_auth` с `scope="session"` и один раз залогиниться, чтобы снизить число запросов на admin login и избежать 429 при больших прогонах.

### 3.3. Дополнительные наборы (рекомендуемые QA)

- **Регрессия по оплатам:** уже оформлена в `QA_REGRESSION_PAYMENTS_ADMIN.md`. Добавить маркер `@pytest.mark.regression_payments` для части тестов и запуск по маркеру.
- **Регрессия по ПД:** маркер `@pytest.mark.regression_pd` — тесты, которые проверяют доступ к пациентам/врачам только своей клиники и отсутствие ПД в ответах ошибок (см. SEC).
- **Регрессия по чатам:** маркер `@pytest.mark.regression_chats` — тесты admin/owner чатов и patient chat, изоляция по clinic/channel.
- **Дымовой набор (smoke):** минимальный набор после деплоя: health, auth send-code (с моком), один admin-эндпоинт с admin_auth, один платёжный webhook. Оформить в `docs/QA_SMOKE.md` или в одном файле `tests/smoke/`.

## 4. SEC: Наборы тестов безопасности

Ниже — сценарии, которые должны быть покрыты тестами (в `tests/security/` или в существующих `tests/api/` с явной пометкой безопасности). Реализацию выполняет @DEV по этому разделу.

### 4.1. Безопасность уровня «Касса» (платежи и credentials)

- **SEC-K1.** Credentials нигде не возвращаются в API: ответы `GET` по клинике, по платежам, по настройкам не содержат полей `yookassa_secret_key`, `credentials_encrypted` в расшифрованном виде, `payload` с ключами. Тест: запросы от админа своей клиники к эндпоинтам клиники/платежей — в JSON ответа нет строк, похожих на секретные ключи (регулярка или список запрещённых ключей).
- **SEC-K2.** Только админ своей клиники может вызывать `POST /v1/admin/clinics/{id}/payment-gateway/credentials`. Тест: запрос с токеном админа клиники A к `clinic_id = B` (другая клиника) → 404 (или 403). Уже частично есть в `test_admin_payment_gateway_credentials.py`; убедиться, что other_clinic_id действительно чужой.
- **SEC-K3.** Запись в `clinic_payment_gateways` хранит только зашифрованное значение: при чтении из БД поле `credentials_encrypted` не содержит открытого JSON с паролями/ключами. Тест: после upsert прочитать строку из БД и проверить, что в ней нет подстрок из исходного payload (terminal_key, password, secret_key и т.д.).
- **SEC-K4.** Webhook платежей: при необходимости проверки подписи (если появится) — отклонять запросы с неверной подписью. Сейчас webhook может принимать мок payload; если в прод будет проверка — добавить тест «неверная подпись → 401/400».
- **SEC-K5.** Логи: в тестах или ревью убедиться, что в логи приложения не попадают сырые credentials (ни от кассы, ни от омниканалов). При необходимости — тест с подменой логгера и проверкой, что в записанных сообщениях нет секретов.

### 4.2. Безопасность уровня «ПД» (персональные данные)

- **SEC-P1.** Изоляция по клинике: пациенты и врачи доступны только в контексте своей клиники. Тест: админ клиники A не может получить пациента/врача клиники B (подмена ID в URL или query → 404/403).
- **SEC-P2.** Ответы об ошибках не содержат ПД: при 400/404/500 в теле ответа не должно быть подставляемых фрагментов с ФИО, телефоном, email. Тест: вызвать эндпоинт, приводящий к ошибке (например, несуществующий patient_id), и проверить, что в `response.json()` нет телефона/email из seed_data.
- **SEC-P3.** Экспорт/отчёты: при наличии выгрузок (CSV, отчёты) — доступ только для своей клиники и без утечки данных других клиник. Тест: запрос от админа клиники A на отчёт с `clinic_id = B` → 404/403.
- **SEC-P4.** Согласия и хранение: если есть поля consent/ПД — тест на то, что обновление/чтение возможно только владельцем (пациент — свои данные, админ — в рамках своей клиники).

### 4.3. Безопасность уровня «Чаты»

- **SEC-C1.** Админ/оператор видит только чаты своей клиники. Тест: запрос к списку чатов/сообщений с токеном админа клиники A; подмена `clinic_id` в query на клинику B не должна возвращать данные клиники B (пустой список или 403).
- **SEC-C2.** Пациент видит только свои разговоры. Тест: patient_auth клиники A, запрос к сообщениям с подменой conversation_id на разговор другого пациента → 404/403.
- **SEC-C3.** Owner-эндпоинты омниканалов: доступ только к каналам своей клиники (business_account_id = clinic_id текущего админа). Тест: запрос к каналу с другим business_account_id → 404/403. Частично уже в `test_owner_cannot_access_foreign_channel` после исправления «чужого» ID.
- **SEC-C4.** Сообщения и AI: эндпоинты summary/suggest/insight не отдают сырые сообщения других клиник; ответы не содержат ПД из чужих чатов. Тест: вызов с корректным clinic_id и проверка, что в ответе нет идентификаторов/текстов из другой клиники.

### 4.4. Размещение security-тестов

- Создать каталог `tests/security/`.
- Файлы (пример): `tests/security/test_security_kassa.py` (SEC-K1–K5), `tests/security/test_security_pd.py` (SEC-P1–P4), `tests/security/test_security_chats.py` (SEC-C1–C4).
- Либо разместить сценарии в существующих API-тестах с маркером `@pytest.mark.security` и подзаголовком в docstring (например, `SEC-K2`).
- Запуск всех security-тестов: `pytest -m security` или `pytest tests/security/ -v`.
