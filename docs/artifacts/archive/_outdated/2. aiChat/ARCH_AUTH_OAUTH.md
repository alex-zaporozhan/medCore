# ARCH_AUTH_OAUTH

## Цель

Добавить безопасный и понятный для пациента вход через VK и Яндекс, сохранив SMS‑вход как базовый канал. Все методы авторизации в итоге выдают один и тот же тип токена (JWT пациента) и работают c единой моделью `Patient`.

OAuth‑авторизация не заменяет SMS, а дополняет её. Для админки схема авторизации описана отдельно в `ARCH_AUTH_SESSIONS.md`.

---

## Модель данных

### Изменения `Patient`

Добавляем к существующей сущности `Patient` (см. `src/domain/entities/patient.py`) дополнительные поля:

- `vk_id: str | None` — стабильный идентификатор пользователя VK (`id` или `user_id` из VK API, всегда храним как строку);
- `yandex_id: str | None` — идентификатор Яндекс‑аккаунта (`id` из `login`/`userinfo`);
- опционально (если потребуется на UI):
  - `vk_screen_name: str | None` — человекочитаемый ник ВК;
  - `yandex_login: str | None` — логин Яндекса.

Требования:

- поля должны иметь индексы для быстрых поисков: `idx_patients_vk_id`, `idx_patients_yandex_id`;
- в рамках клиники `clinic_id` + `vk_id` и `clinic_id` + `yandex_id` должны быть уникальными (через `UniqueConstraint` или явную проверку перед сохранением);
- телефон остаётся основным идентификатором для SMS‑входа. OAuth‑идентификаторы — дополнительные связки.

Миграция:

- отдельный alembic‑скрипт `add_patient_oauth_ids`:
  - добавляет колонки `vk_id`, `yandex_id` (nullable, `String(255)`);
  - создаёт индексы и уникальные ограничения по (clinic_id, vk_id) и (clinic_id, yandex_id), учитывая `deleted_at` (см. существующий паттерн уникальности).

## Потоки авторизации

### Общие принципы

1. **Единый результат**: после любого успешного флоу бэкенд выдаёт `AuthTokenResponse` с:
   - `access_token` (JWT пациента),
   - `patient_id`,
   - `token_type="bearer"`.
2. **Клиника**: пациент всегда привязан к конкретной клинике (`clinic_id`), как и в SMS‑флоу. OAuth‑вход также работает в контексте «дефолтной» клиники (см. текущую реализацию auth_service; уточнения — в `ARCH_AUTH_SESSIONS.md`).
3. **Безопасность OAuth**:
   - используем параметр `state` как CSRF‑защиту и способ передать желаемый редирект обратно во фронт;
   - храним `state` в Redis с TTL, проверяем при callback’е;
   - не полагаемся на email как единственный идентификатор, всегда храним и проверяем стабильный OAuth‑ID (vk_id/yandex_id).

## VK OAuth — детальный поток

### 1. Старт: `GET /api/v1/auth/oauth/vk/start`

Входные параметры:

- `redirect: str | None` — относительный путь во фронтенде, куда вернуть пользователя после успешной авторизации (например, `/app`, `/app/chat`). Если не задан — используем `/app` по умолчанию.

Шаги:

1. Генерируем случайный `state` (минимум 128 бит энтропии, hex/base64).
2. Сохраняем в Redis:
   - ключ: `auth:vk:state:{state}`;
   - значение: JSON `{ "redirect": redirect or "/app" }`;
   - TTL: 10 минут.
3. Строим URL VK OAuth:

   - `https://oauth.vk.com/authorize` с параметрами:
     - `client_id=settings.vk_client_id`;
     - `redirect_uri=settings.vk_redirect_uri`;
     - `response_type=code`;
     - `scope=email` (минимально достаточно для получения email; при необходимости можно расширить позже);
     - `state={state}`.

4. Возвращаем `302 Redirect` на VK.

Ошибки:

- если `vk_client_id`/`vk_redirect_uri` не настроены — `503 Service Unavailable` с понятным текстом, который фронт может отобразить как «Вход через VK временно недоступен».

### 2. Callback: `GET /api/v1/auth/oauth/vk/callback`

Входные параметры (от VK):

- `code: str`;
- `state: str`;
- возможны `error`, `error_description` — при отмене пользователем.

Шаги:

1. Если пришёл `error`, логируем и отдаём 302 на фронт с статусом ошибки, например:

   - `302 → /app/login?oauth=vk&status=cancelled`.

2. Проверяем `state`:

   - читаем `auth:vk:state:{state}` из Redis;
   - если нет — 400/403 и редирект на `/app/login?oauth=vk&status=state_invalid`;
   - при успешном чтении удаляем ключ (одноразовость).

3. Обмениваем `code` на `access_token` и профиль VK:

   - `https://oauth.vk.com/access_token` с параметрами:
     - `client_id`, `client_secret`, `redirect_uri`, `code`;
   - в ответе ожидаем как минимум:
     - `user_id` (основной ID);
     - `email` (может быть `null`);
     - `access_token` (если понадобится для доп. запросов);
   - при ошибке — логируем и редиректим на `/app/login?oauth=vk&status=provider_error`.

4. Находим или создаём пациента:

   1. Получаем `clinic = _get_default_clinic()` (как в SMS‑флоу).
   2. Ищем пациента по `(clinic_id, vk_id=user_id)`:
      - если найден — используем его;
   3. Иначе, если есть `email` и в будущем появится поле `email` у `Patient` и политика его использования — по решению бизнеса можно добавить дополнительный шаг поиска (опционально, описывается отдельно, сейчас считаем, что email — только вспомогательный атрибут).
   4. Если ни по чему не нашли — создаём нового `Patient`:

      - `clinic_id=clinic.id`;
      - `phone=None` (если нет привязки к телефону, допустимо для чисто OAuth‑пациентов);
      - `vk_id=user_id`;
      - дополнительные поля (ФИО) можно подтянуть из VK, если включены нужные разрешения и это укладывается в политику ПД.

5. Создаём JWT‑токен пациента (как в SMS‑флоу):

   - `sub = patient.id`, `role="patient"`, срок действия как для обычного пациента.

6. Возвращаем **либо** JSON `AuthTokenResponse`, **либо** делаем редирект на фронт:

   - предпочтительный вариант для SPA: `302 → redirect_from_state?oauth=vk&status=ok&token={jwt}&patient_id={id}`;
   - фронт читает параметры, вызывает `login(token, patient_id)` и переводит на нужный экран.

## Yandex OAuth — детальный поток

Поток аналогичен VK, но с эндпоинтами Яндекса.

### 1. Старт: `GET /api/v1/auth/oauth/yandex/start`

Параметры и шаги те же, что и для VK, за исключением URL и scopes:

- OAuth URL: `https://oauth.yandex.ru/authorize`;
- параметры:
  - `client_id=settings.yandex_client_id`;
  - `redirect_uri=settings.yandex_redirect_uri`;
  - `response_type=code`;
  - `state={state}`;
  - `scope=login:email login:info` (минимальный набор для идентификатора и email).

State так же пишем в Redis: `auth:yandex:state:{state}`.

### 2. Callback: `GET /api/v1/auth/oauth/yandex/callback`

Шаги:

1. Обработка `error` аналогично VK.
2. Проверка `state` через Redis (`auth:yandex:state:{state}`).
3. Обмен `code` → `access_token` и профиль пользователя:

   - POST/GET к `https://oauth.yandex.ru/token` с `client_id`, `client_secret`, `code`, `grant_type=authorization_code`;
   - затем запрос профиля, например `https://login.yandex.ru/info` с полученным токеном;
   - из профиля берём:
     - стабильный `id` (используем как `yandex_id`);
     - `default_email` / `emails` при необходимости.

4. Поиск/создание пациента:

   - ищем по `(clinic_id, yandex_id)`;
   - при отсутствии — создаём нового `Patient` с заполненным `yandex_id` и опциональными полями (ФИО, email) в рамках политики ПД.

5. Выдача JWT и редирект во фронт так же, как у VK.

## Политика связывания аккаунтов

### Базовые правила

1. **Один OAuth‑ID → один Patient в рамках клиники**:
   - `(clinic_id, vk_id)` и `(clinic_id, yandex_id)` уникальны;
   - попытка привязать тот же `vk_id` к другому пациенту должна приводить к контролируемой ошибке/разрешению конфликта.

2. **Мульти‑канальный доступ к одному пациенту**:
   - один пациент может иметь одновременно:
     - телефон (SMS‑вход),
     - `vk_id`,
     - `yandex_id`;
   - это позволяет сначала регистрироваться по телефону, а потом «подвязать» соцсети (миграционная логика может быть добавлена позже).

3. **Консервативная стратегия объединения**:
   - на этапе первого внедрения **не выполняем автоматический merge по email/телефону** между аккаунтами, созданными через SMS и OAuth;
   - если бизнес захочет объединять по телефону/email, это должно быть описано отдельной архитектурной заметкой с учётом кейсов дубликатов и ошибок.

### Поведение при существующем телефоне

Сценарий: пациент ранее регистрировался по SMS (есть `Patient` c телефоном), затем приходит через VK/Яндекс.

Базовое решение (MVP уровня безопасности):

- при чистом OAuth‑входе **создаём нового пациента** c `vk_id`/`yandex_id`, не трогая существующую запись по телефону;
- связывание аккаунтов по телефону можно добавить позже через явное действие в личном кабинете («Привязать ВК»), когда пациент уже аутентифицирован и подтвердил действие повторным вводом SMS‑кода.

Это минимизирует риск случайного объединения разных людей, использующих один и тот же номер или почту.

## Обработка ошибок и UX‑редиректы

Фронт ожидает, что все ветки OAuth в итоге приходят на один из трёх сценариев:

1. **Успех** — `redirect?oauth={vk|yandex}&status=ok&token=...&patient_id=...`
2. **Отмена пользователем** — `redirect?oauth={vk|yandex}&status=cancelled`
3. **Техническая ошибка** — `redirect?oauth={vk|yandex}&status=error` (+ возможно `code` для аналитики)

`redirect` хранится в `state` в Redis и не должен напрямую приниматься от пользователя без проверки, чтобы избежать open redirect.

На фронте:

- при `status=ok` вызываем `login(token, patient_id)` и переходим на нужную страницу;
- при `status=cancelled` просто остаёмся на странице логина;
- при `status=error` показываем пользователю общее сообщение: «Не удалось войти через VK/Яндекс. Попробуйте ещё раз или используйте вход по SMS».

## Требования для реализации (@DEV)

1. Реализовать обмен `code→access_token` и загрузку профиля VK/Яндекс в уже созданных callback‑эндпоинтах в `auth.py`.
2. Добавить поля `vk_id`, `yandex_id` (и при необходимости `vk_screen_name`, `yandex_login`) в модель `Patient` и alembic‑миграцию.
3. Реализовать хранение/проверку `state` в Redis с TTL и одноразовостью.
4. Обновить `AuthService` или выделить отдельный `OAuthAuthService`, который:
   - принимает структуру профиля VK/Яндекс;
   - инкапсулирует логику поиска/создания `Patient` и выдачи JWT по правилам выше.
5. Обновить фронтенд так, чтобы он корректно обрабатывал параметры `oauth`, `status`, `token`, `patient_id` на конечной странице редиректа.
