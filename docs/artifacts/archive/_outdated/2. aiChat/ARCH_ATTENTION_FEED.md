## ARCH_ATTENTION_FEED — Лента внимания владельца

**Проект:** Dental Booking System MVP  
**Режим:** SAAS с несколькими клиниками (одна ветка данных на `clinic_id`)  

---

### 1. Цель модуля

Сделать для владельца и старших админов **«панель совести»**, показывающую:

- кому **обещали перезвонить** и не сделали этого;
- кто **давно не был** и теряет привычку ходить;
- где были **жалобы, конфликты, провалы сервиса**.

Это не финансовый отчёт, а **операционный список следующих действий**, который помогает удерживать клиентов и выручку.

---

### 2. Объекты домена

#### 2.1. AttentionItem

Логическая единица ленты — `AttentionItem`:

- `id: UUID`
- `clinic_id: UUID`
- `patient_id: UUID`
- `kind: "follow_up" | "retention_gap" | "conflict"`  
- `title: str` — короткий заголовок для UI.
- `description: str` — пояснение (что произошло и что ожидается).
- `priority: int` — чем больше, тем важнее (1–100).
- `due_at: datetime | None` — когда стоит вернуться к вопросу (для follow_up).
- `created_at: datetime`
- `updated_at: datetime`

**Важно:** на первом этапе **таблицы `attention_items` не создаём**.  
`AttentionItem` — это DTO, собираемое на лету на основе уже существующих данных.

#### 2.2. Источники данных

1. **Follow‑up (обещали перезвонить)**  
   Источник: `chat_messages` + (опционально) поле в `bookings`/`notifications`.
   - Модель:
     - при создании сообщения или действия в админке можно проставить `follow_up_at` и `follow_up_reason` (см. изменение DTO чата).
     - фактически это признак «к этому клиенту нужно вернуться до X».
   - В расчёте ленты:
     - выбираем все открытые follow‑up, у которых `follow_up_at <= now` и нет «закрывающего» статуса (см. 3.2).

2. **Retention gap (давно не были)**  
   Источник: `bookings` + `patients`.
   - Для каждого пациента по клинике считаем `last_visit_at` (по завершённым/подтверждённым записям).
   - Для клиники задаётся **порог ретеншна** (например, 3/6/12 месяцев) — пока достаточно настройки уровня env/конфига или поля в таблице настроек клиники.
   - Клиенты, у которых:
     - `last_visit_at` существует и `now - last_visit_at > retention_threshold`,
     - и при этом они уже приносили выручку (сумма по `bookings` > 0),
     попадают в ленту как `kind="retention_gap"`.

3. **Conflicts (жалобы / сложные клиенты)**  
   Источник: флаги на пациенте и/или теги в сообщениях.
   - Вводим поле/структуру `patient_flags` или отдельную таблицу `patient_flags` (будет детально описано в отдельном ARCH, но для ленты достаточно концепта):
     - флаги: `"conflict"`, `"angry"`, `"no_show_often"`, `"vip"`, и т.п.
   - Клиенты, у которых за последний период:
     - были жалобы (сообщения с тегами `complaint`, `negative_feedback`),
     - и/или установлен флаг `conflict`/`angry`,
     формируют элементы `kind="conflict"`.

### 3. Расчёт ленты

#### 3.1. Сервис AttentionFeedService

В слое application вводится сервис:

```python
class AttentionFeedService:
    def __init__(self, session: AsyncSession): ...

    async def get_feed(self, clinic_id: UUID) -> AttentionFeedRead:
        ...
```

`AttentionFeedRead`:

```python
class AttentionFeedRead(BaseModel):
    follow_up: list[AttentionItemRead]
    retention_gap: list[AttentionItemRead]
    conflicts: list[AttentionItemRead]
```

Где `AttentionItemRead` повторяет структуру `AttentionItem` + базовая информация о пациенте:

- `patient_full_name: str | None`
- `patient_phone: str`
- `patient_tags: list[str]` (VIP, конфликт, и т.п.)

#### 3.2. Правила расчёта по видам

1. **Follow‑up**
   - Берём записи из:
     - `chat_messages` и/или `bookings`, где указан `follow_up_at` и нет признака `follow_up_closed`.
   - Фильтр:
     - `follow_up_at <= now` → высокий приоритет;
     - `follow_up_at > now` → можно не включать в ленту или показывать вторым списком (на будущее).
   - `priority`:
     - базово 80;
     - можно повышать, если клиент VIP или конфликтный (комбинация признаков).

2. **Retention gap**
   - Из `bookings` по клинике собираем:
     - `last_visit_at` и суммарную выручку по пациенту.
   - Фильтр:
     - `last_visit_at` не `NULL`;
     - `now - last_visit_at > threshold` (по умолчанию 6 месяцев).
   - `priority`:
     - пропорционален убыванию выручки и давности (`amount * (now - last_visit)`).
   - Лимит:
     - показываем, например, топ‑50 клиентов по риску.

3. **Conflicts**
   - По `patient_flags` и тегам сообщений выбираем:
     - клиентов, у которых за последние N дней были жалобы/негатив.
   - `priority`:
     - самый высокий (например, 90–100).

### 4. API

Новый админский эндпоинт:

- `GET /api/v1/admin/clinics/{clinic_id}/attention-feed`

Ответ:

```jsonc
{
  "follow_up": [ /* AttentionItemRead[] */ ],
  "retention_gap": [ /* AttentionItemRead[] */ ],
  "conflicts": [ /* AttentionItemRead[] */ ]
}
```

Аутентификация:

- как в других admin‑роутах: токен администратора, `clinic_id` проверяется на принадлежность текущему администратору.

---

### 5. UI-скелет для админки

Размещаем ленту как отдельную вкладку/страницу:

- либо `/admin/attention` (Лента внимания),
- либо секция в `AdminReportsPage`.

Базовый макет:

- три вертикальных блока:
  - **Обещали перезвонить**
  - **Давно не были**
  - **Конфликты**
- каждая карточка:
  - имя + телефон клиента;
  - короткое описание причины;
  - дата/срок (`due_at` или `last_visit_at`);
  - экшены:
    - «Открыть чат»;
    - «Создать запись»;
    - «Отметить выполненным».

---

### 6. Ограничения и следующие этапы

- На первом шаге все вычисления делаются **на лету** через `AttentionFeedService` без отдельной таблицы `attention_items`.
- Если нагрузка вырастет, можно вынести расчёт в фоновую задачу (Celery) и материализовывать ленту в отдельной таблице.
- В будущих итерациях:
  - добавить интеграцию с AI‑оператором (предложение «next best action» для каждого `AttentionItem`);
  - связать ленту с модулем recall‑кампаний (массовые приглашения).
