# ARCH + BIZ: Единый чат — объединение внутреннего и омниканального

> Консультация @BIZ и @ARCH по запросу @LEAD: один интерфейс «Единый чат», внутренние диалоги клиники стекаются в тот же чат, страница «Чат» убрана. Документ задаёт архитектуру и подробный план внедрения в существующий бэкенд и фронтенд.

---

## 1. Позиция @BIZ: зачем один «Единый чат»

### Текущая проблема
- В админке два раздела: **«Чат»** (диалоги с пациентами из PWA/приложения) и **«Омниканальный чат»** (Telegram, WhatsApp, виджет и т.д.).
- Мы позиционируем продукт как **единое окно** для всех каналов связи с клиентом. Два отдельных чата противоречат этому и создают путаницу: куда смотреть, где искать историю.

### Целевая модель
- **Один раздел в админке — «Единый чат».**
- Все входящие сообщения (из приложения пациента, Telegram, WhatsApp, виджет, email и т.д.) попадают в один список диалогов.
- Оператор работает в одном интерфейсе: один список чатов, единая история по контакту, единые AI-режимы и эскалация.

### Выгоды
- Соответствие позиционированию «единый чат».
- Меньше когнитивной нагрузки на администратора.
- Одна точка входа для поддержки и отчётности по переписке.

### Решение
- Убрать отдельную страницу «Чат» в админке.
- Переименовать «Омниканальный чат» в **«Единый чат»** во всём фронтенде.
- Технически: внутренние диалоги (пациент ↔ админ из PWA) должны попадать в ту же омниканальную модель (канал `WEB_APP`), чтобы отображаться в том же списке и том же чате.

## 2. Позиция @ARCH: как технически объединить

### 2.1. Текущее состояние

| Компонент | Внутренний чат («Чат») | Омниканальный чат |
|-----------|------------------------|-------------------|
| Сущности | `Conversation`, `ChatMessage` | `Contact`, `Channel`, `Chat`, `Message` (omni_*) |
| API | `/admin/chat/conversations`, `/patient/chat/*` | `/admin/omni-chats/*`, вебхуки провайдеров |
| Источник сообщений | PWA пациента, ответ админа из «Чат» | Telegram, WhatsApp, виджет и т.д. |
| UI | `/admin/chat` | `/admin/omni-chat` |

### 2.2. Целевая архитектура

- **Единственная точка входа для оператора:** один список чатов и один экран переписки — текущий омниканальный UI (`/admin/omni-chat`), переименованный в «Единый чат».
- **Внутренние диалоги (PWA)** становятся ещё одним «каналом» в омниканальной модели:
  - Тип канала: **`WEB_APP`** (чат из мобильного/веб-приложения клиники, не внешний виджет).
  - На одного пациента (clinic_id + patient_id) — один Contact (с привязкой к Patient через `external_ids.patient_id`), один Chat с `channel_id` = канал типа `WEB_APP`.
- **Два слоя данных (кратко):**
  - **Слой омниканальный (источник правды для «Единого чата»):** `omni_contacts`, `omni_channels` (в т.ч. `WEB_APP`), `omni_chats`, `omni_messages`. В нём живут и мессенджеры, и диалоги из PWA.
  - **Слой внутреннего чата (для PWA пациента):** `conversations`, `chat_messages` — сохраняем для обратной совместимости и для отображения переписки в приложении пациента. Синхронизация: каждое сообщение из PWA дублируется в omni; ответ админа из «Единого чата» по каналу `WEB_APP` дублируется в `chat_messages` и доставляется пациенту (как сейчас).

### 2.3. Канал WEB_APP

- В `omni_channels` добавляется (или уже поддерживается) тип **`WEB_APP`**.
- Один канал `WEB_APP` на клинику (business_account_id): общий для всех диалогов «пациент из приложения».
- Создание: при первом сообщении от пациента из PWA — `get_or_create_channel_for_provider(business_account_id, "WEB_APP")` (и маппинг в сервисе: `WEB_APP` → `WEB_APP`).
- Contact для пациента: `get_or_create_contact` по business_account_id + primary_phone (из Patient), в `external_ids` хранить `{"patient_id": "<uuid>"}` для связи с Patient и с `conversations`/`chat_messages`.

### 2.4. Потоки данных

#### A. Сообщение от пациента (PWA)

1. **Текущий поток (оставить):** `Patient chat API` → `ChatService.send_message_from_patient` → запись в `Conversation` + `ChatMessage`.
2. **Дополнительно (мост в омниканаль):**
   - По `clinic_id` + `patient_id`: найти/создать Contact (по Patient: phone, full_name; `external_ids.patient_id` = patient_id).
   - Найти/создать Channel типа `WEB_APP` для клиники.
   - Найти/создать Chat (contact + channel_id).
   - Создать входящее `Message` (INBOUND, CLIENT, content = body, channel_id = WEB_APP).
   - Опционально: вызвать AI Orchestrator для этого чата (как для других каналов) или по умолчанию оставить `ai_mode=DISABLED` для WEB_APP.

#### B. Ответ админа из «Единого чата» (по каналу WEB_APP)

1. Оператор в UI «Единый чат» отправляет сообщение в чат с `channel_type === "WEB_APP"`.
2. Backend: `OmnichannelChatService.append_outbound_message` + `OmnichannelOutboundDispatcher.dispatch_to_channel`.
3. В диспетчере для `channel_type == "WEB_APP"`:
   - Не вызывать Telegram/WhatsApp.
   - По `chat.contact_id` взять Contact → `external_ids.patient_id` → найти Conversation по (clinic_id, patient_id).
   - Записать сообщение в `chat_messages` (sender_type=admin) и обновить `conversations` (last_message_at, unread_by_patient_count).
   - При наличии механизма push/лонгполла для PWA — уведомить пациента о новом сообщении.

#### C. Ответ админа из старого «Чата» (до удаления страницы)

- После удаления страницы «Чат» этот поток отсутствует; ответы идут только из «Единого чата».

### 2.5. Отображение в «Едином чате»

- Список чатов: только из `omni_chats` (уже так). Чаты с `channel_type === "WEB_APP"` отображаются вместе с остальными; в UI можно показывать бейдж/иконку «Приложение» или «Внутренний чат».
- Сообщения чата: только из `omni_messages` (уже так). Для WEB_APP сообщения подтягиваются из того же omni-репозитория (после моста они там есть).

### 2.6. Обратная совместимость для PWA

- Пациент по-прежнему: получает/создаёт Conversation через `GET/POST /patient/chat/*`, читает сообщения из `chat_messages`, отправляет в `chat_messages`. Никаких изменений контракта для PWA не требуется при внедрении моста.
- Миграция истории: опционально — скрипт, который для существующих `conversations`/`chat_messages` создаёт Contact (по Patient), Chat (WEB_APP), Message (копии в omni_messages). Не обязательно для первого этапа.

### 2.7. Связь Единого чата с БД и мультиклиника

- **Ключ изоляции:** Во всех омниканальных таблицах роль «клиники» играет **`business_account_id`** (в коде он равен `clinic_id` — FK на `clinics.id`). То есть:
  - `omni_contacts.business_account_id` = клиника;
  - `omni_channels.business_account_id` = клиника;
  - `omni_chats.business_account_id` = клиника;
  - `omni_messages` привязаны к чату, чат — к клинике.
- **Пациенты привязаны к одной клинике:** У пациента есть `patient.clinic_id`. Сообщения из PWA идут в `Conversation`/`ChatMessage` с этим `clinic_id`. Мост должен создавать Contact/Chat/Message в омниканале с **`business_account_id = clinic_id`** той же клиники. Тогда диалог пациента клиники «Dental_Booking 2» появится в Едином чате **только у той клиники** (у админов, чей `current_admin.clinic_id` = Dental_Booking 2).
- **Как «принимаются» сообщения с разных клиник:** Каждая клиника изолирована: список чатов в API строится по `business_account_id` (сейчас = `current_admin.clinic_id`). Сообщения из PWA пациента клиники A попадают в omni с `business_account_id = A` и видны только при запросе чатов клиники A. Другие клиники их не видят.
- **Выбор «чат всех клиник» vs «чат клиники №1»:**
  - **Текущая модель:** один админ привязан к одной клинике (`admin_user.clinic_id`). Бэкенд везде использует `current_admin.clinic_id` как `business_account_id`. Выбор клиники в шапке админки (`currentClinicId`) для Единого чата сейчас **не передаётся** в API — список чатов всегда для клиники админа из JWT.
  - **Расширение (опционально):** чтобы админ мог выбрать «чат клиники №1» или «чат клиники №2», нужно: (1) передавать с фронта выбранную клинику (query-параметр `clinic_id` или заголовок `X-Clinic-Id`) в запросы списка/детали чатов; (2) на бэкенде проверять, что у текущего админа есть право видеть эту клинику (пока: `current_admin.clinic_id == requested_clinic_id`; в будущем — таблица доступа админ–клиники); (3) использовать `requested_clinic_id` как `business_account_id` при выборке. Режим «чат всех клиник» потребовал бы либо объединения списков чатов по нескольким `business_account_id` (если у админа несколько клиник), либо отдельной роли «сетевой админ» — вынести в фазу 3 при необходимости.

### 2.8. Что ещё продумать

- **Права доступа:** Сейчас чаты фильтруются по `business_account_id`; при введении выбора клиники в Едином чате нужно явно проверять, что запрошенная клиника доступна текущему админу (один клиник сейчас, в перспективе — список разрешённых клиник).
- **Поиск в списке чатов:** По умолчанию поиск идёт по `Chat.title`; для канала WEB_APP заголовок часто пустой. Имеет смысл расширить поиск на имя и телефон контакта (см. DEV_PROMPTS).
- **Уведомления пациента в PWA:** После того как ответ админа из Единого чата записан в `chat_messages`, желательно уведомить пациента (push или лонгполл), если такой механизм есть в проекте.
- **Миграция старых диалогов:** Существующие переписки в `conversations`/`chat_messages` в Едином чате не видны, пока не выполнен скрипт миграции (создание Contact/Chat/Message по истории). Можно сделать отдельным шагом после стабилизации моста.

## 3. План внедрения (по шагам)

### Фаза 1: Фронтенд — один «Единый чат», убрать «Чат» (без бэкенд-моста)

- **1.1** Переименовать во фронтенде везде «Омниканальный чат» → «Единый чат» (меню, заголовки, плейсхолдеры, подсказки).
- **1.2** Удалить страницу и маршрут `/admin/chat` (внутренний чат).
- **1.3** В сайдбаре админки: убрать пункт «Чат», оставить один пункт «Единый чат» (текущий `/admin/omni-chat`).
- **1.4** Бейдж непрочитанных: считать только по омниканальным чатам (например, WAITING_FOR_OPERATOR или unread по omni); убрать использование `useAdminChatConversations` для бейджа в сайдбаре.
- **1.5** Опционально: в «Едином чате» в списке/карточке диалога показывать тип канала (Telegram, WhatsApp, **Приложение**, виджет и т.д.) — уже есть `channel_type`.

**Итог фазы 1:** Пользователь видит один раздел «Единый чат»; старый «Чат» исчезает. Диалоги из PWA пока не попадают в «Единый чат» (для этого нужна фаза 2).

### Фаза 2: Бэкенд — канал WEB_APP и мост PWA → omni

- **2.1** В `OmnichannelChatService.get_or_create_channel_for_provider` добавить маппинг `"WEB_APP"` → `channel_type = "WEB_APP"` (или создать канал при первом использовании).
- **2.2** Сервис «мост» (или расширение `ChatService`): при `send_message_from_patient` после записи в `Conversation`/`ChatMessage` вызывать:
  - get_or_create Contact по Patient (phone, full_name, external_ids.patient_id);
  - get_or_create Channel WEB_APP для клиники;
  - get_or_create Chat(contact, channel_id);
  - create inbound Message в omni.
- **2.3** В `OmnichannelOutboundDispatcher`: для `channel_type == "WEB_APP"` не слать во внешние API; по contact.external_ids["patient_id"] найти Conversation, записать сообщение в `chat_messages`, обновить unread_by_patient_count; при наличии — push/лонгполл для PWA.
- **2.4** (Опционально) Миграция существующих диалогов: скрипт заполнения omni_contacts/omni_chats/omni_messages из conversations/chat_messages для отображения истории в «Едином чате».

### Фаза 3: Доработки (по необходимости)

- Единый счётчик непрочитанных для «Единого чата» (по omni_chats/omni_messages).
- AI-режимы для чатов WEB_APP (по умолчанию DISABLED или SUGGEST_ONLY).
- Очистка: удалить или пометить устаревшим код/роуты `admin_chat.py` и старые эндпоинты `/admin/chat/*` после полного перехода (можно оставить только те, что нужны для AI summary/suggest по conversation_id, если решим сохранить их для WEB_APP по conversation_id из Contact).

## 4. Контракты и риски

- **API пациента** (`/patient/chat/*`): не меняем; PWA продолжает работать с `Conversation` и `ChatMessage`.
- **API админа:** убираем использование `/admin/chat/conversations` и связанных эндпоинтов в UI. Сами эндпоинты можно оставить для обратной совместимости или удалить в фазе 3.
- **Риск:** дублирование сообщений при сбое моста — делать запись в omni идемпотентной (например, по external_message_id = "patient_msg_{chat_message_id}").
