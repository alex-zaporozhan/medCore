## 2. Целевое состояние перф‑слоя

### 2.1. Жёсткие инварианты

1. **Перф‑работа основана на измерениях, а не на ощущениях.**
   - Решения об оптимизациях принимаются:
     - по данным метрик/трейсов;
     - с фиксацией до/после.

2. **Оптимизации не ломают архитектурные инварианты и доменную модель.**
   - Никаких «костылей» во имя перфа:
     - обходящих доменные сервисы;
     - ломающих multi‑tenant/RBAC/AI‑политику.

3. **Ключевые проблемные места идентифицированы и задокументированы.**
   - Есть список «perf spots» с:
     - описанием проблемы (по метрикам);
     - выбранным подходом к оптимизации;
     - статусом (planned/in progress/done).

4. **Оптимизации устойчивы к росту данных.**
   - Там, где ожидается масштаб:
     - используются индексы/пагинация/кэш/фоновая агрегация;
     - поведение на больших объёмах предсказуемо.

5. **Владельцы доменов понимают перф‑ограничения.**
   - Для CRM/ERP/Omnichannel:
     - есть зафиксированные «границы разумного»:
       - по объёму данных на один запрос;
       - по времени ответа (SLO/SLA).

## 3. Архитектурный подход к PERF_SPOTS

### 3.1. Шаг 1 — Идентификация проблемных мест

- Используя:
  - метрики из `ARCH_DEV_OBS_CHAINS_023.md`;
  - APM/трейсинг (если есть);
  - реальные/синтетические нагрузки;
- выделяем **конкретные**:
  - эндпоинты;
  - запросы к БД;
  - участки цепочек;
  - компоненты фронта,
которые:
  - стабильно замедляют систему;
  - или «лопаются» на больших объёмах данных.

Примеры:

- CRM:
  - `GET /crm/leads/kanban`:
    - долгие запросы с множеством join’ов и без индексов;
    - тяжёлый payload по каждому лиду.
- ERP/Attribution:
  - `GET /admin/erp/reports/...`:
    - полные агрегации за год по всем клиникам;
    - отсутствие предагрегации/кэша.
- Omnichannel:
  - цепочки с несколькими последовательно вызываемыми LLM‑запросами;
  - отсутствие параллелизма/тайм‑аутов.

### 3.2. Шаг 2 — Классификация и приоритезация

- Классы perf‑проблем:
  - **Данные/запросы к БД**:
    - N+1;
    - отсутствие индексов;
    - избыточные поля/джойны.
  - **Бизнес‑логика/алгоритмы**:
    - неоптимальные циклы;
    - пересчёт одних и тех же агрегатов on‑the‑fly.
  - **Сетевые вызовы/AI**:
    - длинные цепочки без параллелизма;
    - отсутствие тайм‑аутов/ретраев.
  - **Фронтенд**:
    - рендеринг огромных списков без виртуализации;
    - перегрузка клиента тяжёлыми JSON‑структурами.

- Приоритезация:
  - совмещаем:
    - бизнес‑важность (CRM Kanban и ключевые отчёты — выше);
    - тяжесть проблемы (90‑й/95‑й/99‑й перцентиль);
    - объём усилий на исправление.

### 3.3. Шаг 3 — Выбор архитектурных приёмов

Для точечных мест возможны (по ситуации):

- Индексы/перепроектирование запросов:
  - добавление составных индексов по частым фильтрам (clinic_id, status, assignee, date);
  - выделение «лёгких» проекций для Kanban (без лишних полей).
- Пагинация и лимиты:
  - строгие лимиты;
  - курсорная пагинация;
  - lazy‑loading деталей.
- Кэш/материализованные представления:
  - предагрегация тяжёлых отчётов;
  - периодические пересчёты в фоне.
- Асинхронность:
  - вынос тяжёлых операций в фоновый слой (Celery/таски);
  - немедленный ответ UI с последующей подгрузкой.
- Фронтовые оптимизации:
  - виртуализация списков;
  - мемоизация/разбиение компонентов;
  - снижение размера payload’ов.

## 4. Фокус‑области (high‑level)

### 4.1. CRM Kanban

- Цель:
  - обеспечить приемлемое время загрузки и обновления доски Kanban при:
    - большом числе лидов;
    - активной фильтрации/перетаскивании.
- Арх‑подход:
  - вынести:
    - «Kanban projection» — облегчённое представление лида:
      - только нужные поля (id, основные атрибуты, статус, ответственный, ключевые суммы);
    - использовать:
      - индексы по фильтрам и сортировкам;
      - ограничение числа лидов за один запрос;
      - курсорную/страничную пагинацию для длинных колонок.
  - по необходимости:
    - отдать тяжёлую аналитику/агрегации в отдельные отчётные API.

### 4.2. ERP/Attribution отчёты

- Цель:
  - отчёты «для владельца/маркетинга»:
    - не должны блокировать систему;
    - должны быть предсказуемы по времени.
- Арх‑подход:
  - выделить:
    - слой предагрегированных данных:
      - по дням/клиникам/источникам трафика;
    - фоновый пересчёт:
      - Celery/таски по расписанию;
    - API отчётов:
      - работают по агрегированным таблицам, а не по «сырым» транзакциям каждый раз.
  - минимизировать:
    - применение тяжёлых джойнов в real‑time;
    - возможность запросов «за всё время» без фильтров.

### 4.3. Omnichannel & AI

- Цель:
  - уменьшить время ответа AI‑цепочек до приемлемого уровня;
  - избежать блокировок интерфейсов.
- Арх‑подход:
  - уже в `ARCH_DEV_OMNI_REGISTRY_015`:
    - заложить возможности:
      - параллелизации AI‑шагов;
      - строгих тайм‑аутов и graceful degradation.
  - в рамках PERF_SPOTS:
    - измерить реальное поведение;
    - выявить, какие цепочки требуют:
      - асинхронного режима (ответ позже);
      - упрощения контекста;
      - сокращения числа AI‑вызовов.

## 8. Статус реализации (v1, март 2026)

> Детальный чек‑лист и **«На потом»** — в `ARCH_DEV_PERF_SPOTS_024_TASKS.md`.  
> Глубокий перф (Engine L2) — отдельный артефакт: **`ARCH_PERF_ENGINE_L2_DEEP_2026.md`**.

### 8.1. Сделано в коде (итерация v1)

- **CRM / Kanban**
  - `GET /admin/crm/leads` с параметром **`projection=kanban`**: облегчённые DTO (`LeadKanbanCardDto`) и в репозитории — **`load_only`** по колонкам, нужным доске.
  - Список лидов и **общее количество** по фильтрам — **один round-trip к БД** (`COUNT(*) OVER()`), без отдельного `COUNT(*)` в роутере.
  - Составные индексы по `lead_cards` уже заданы в ORM‑модели (clinic+stage, clinic+status, clinic+created_at).
- **CRM / UI**
  - Хук запрашивает kanban‑проекцию; при **неполной выборке** (`total > len(items)`) показывается предупреждение пользователю.
- **ERP / отчёты**
  - Ограничение длины периода (**до 366 дней**) на диапазонных отчётных эндпоинтах; в теле ошибки — подсказка сократить период или разбить запрос.
- **Наблюдаемость (HTTP)**
  - Гистограмма **`http_request_duration_seconds`** с лейблами **`method`**, **`path`** (предпочтительно шаблон маршрута из `scope["route"]`, иначе нормализованный путь: UUID и числовые сегменты → `{id}`), **`status_class`** (`2xx`…`5xx`).
  - Счётчик **`crm_leads_list_requests_total{projection}`** по режиму списка лидов.
- **Тесты:** юнит‑тесты нормализации пути; API‑тесты Kanban‑проекции и отклонения слишком длинного периода отчёта; сервисные тесты `list_leads` с парой `(rows, total)`.

### 8.2. Не входило в v1 (перенос в Engine L2)

Материализованные предагрегаты ERP, фоновые пересчёты (Celery), пакет виртуализации длинных списков на фронте, курсорная пагинация **по колонкам** Kanban — вынесены в **`ARCH_PERF_ENGINE_L2_DEEP_2026.md`** с обоснованием объёма и рисков.

Расширение витрин на **payroll / materials / ROI** (отдельный эпик): **`ARCH_DEV_ERP_VITRINES_026.md`**, **`ARCH_DEV_ERP_VITRINES_026_TASKS.md`**.
