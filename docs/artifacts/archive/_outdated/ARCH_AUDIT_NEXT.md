## 🔍 ARCH_AUDIT_NEXT — аудит согласованности «код ↔ ARCH ↔ BUSINESS»

> **Роль:** AUDITOR  
> **Фокус:** проверить, что архитектурное видение vNext (ARCH_DECISIONS_NEXT + ARCH_*_NEXT)  
> не противоречит реальному коду и бизнес‑логике, и достижимо без тотальной переписки.

---

## 1. Сводка рисков и несоответствий

1. **Общая согласованность высокая:**
   - Домены в `ARCH_DECISIONS_NEXT` совпадают с тем, как уже структурирован код и `BUSINESS_LOGIC_CURRENT`/`V2` (Booking, Omnichannel, CRM, ERP, Loyalty, Paperless, Tasks, Attribution).
   - Скелеты `ARCH_*_NEXT` корректно описывают то, что реально есть: Booking & Schedule, Omnichannel, CRM, ERP, Loyalty, Paperless, Tasks, Attribution.
   - Принцип «эволюция, а не переписывание» соблюдён — ни один домен не требует выброса текущих сущностей/сервисов.

2. **Ключевые зоны риска vNext:**
   - **AI Agent / Omnichannel tools‑registry:**
     - в коде есть `ai_agent.py` и `useAiAgent.ts`, но оба — заглушки;
     - `ARCH_OMNICHANNEL_NEXT` описывает полноценный Orchestrator + tools‑registry, чего пока нет.
   - **ERP‑узел завершения визита:**
     - ERP‑сущности и UI (`AdminFinancePage`, `admin_finance.py`, inventory/payroll) существуют;
     - `ARCH_BOOKING_NEXT` и `ARCH_ERP_NEXT` вводят жёсткий инвариант «одна транзакция на завершение визита», но сейчас логика разбита и требует консолидации.
   - **Автодвижение CRM‑лидов:**
     - `admin_crm.py` + `AdminSalesPipelinePage.tsx` — ручной Kanban;
     - v1 событийного слоя реализован (`LeadLifecycleService`, шина, `ARCH_DEV_CRM_EVENTS_007`); v1 денег в CRM — `actual_value` из ERP‑income (`DEV_PROMPT_CRM_MONEY_008`); остаётся stale‑job, полнота UTM, ATT/ROI‑отчёты и краевые кейсы «несколько визитов».
   - **UX‑слой как единая система:**
     - `QA_AUDIT_NEXT` фиксирует: статусы/состояния местами отображаются сырыми значениями;  
     - `ARCH_DECISIONS_NEXT` требует «frontend везде отражает бизнес‑смыслы», что повлечёт массовую, но локальную переработку UI.

3. **Риск «архитектура уехала вперёд» минимален:**
   - Все целевые решения опираются на уже существующие сущности и модули;
   - Основные изменения формулируются как «достроить поток» (AI‑слой, ERP‑узел, автодвижение CRM, связка Loyalty/ERP), а не «заменить модель данных».

## 2. Архитектурные решения, которые нужно пересмотреть/уточнить

1. **Жёсткость ERP‑узла (Booking.status → completed):**
   - В `ARCH_DECISIONS_NEXT` это описано как строгий инвариант («либо всё, либо ничего»).  
   - В реальном коде:
     - ERP‑операции и так распределены по сервисам (FinanceService, LoyaltyService, Inventory/Payroll) и AttentionFeed уже умеет фиксировать ошибки (`erp_error_code`).
   - Рекомендация:
     - уточнить в `ARCH_ERP_NEXT` и `ARCH_BOOKING_NEXT` форму реализации:
       - использовать существующий механизм AttentionFeed как «страховку» для частичных сбоев;
       - возможно, не всегда требовать single‑transaction across all ERP‑поддоменов, а документировать допущения (например, раздельные транзакции с компенсирующими действиями).

2. **Глубина AI‑слоя для первой версии:**
   - `ARCH_OMNICHANNEL_NEXT` и `BUSINESS_LOGIC_V2` описывают довольно богатый Orchestrator + множество tools;
   - по `QA_AUDIT_NEXT` AI‑агент сейчас полностью stub, а Omnichannel и так сложен.
   - Рекомендация:
     - в `ARCH_OMNICHANNEL_NEXT` явно зафиксировать **минимально‑жизнеспособный** набор:
       - v1: только `get_available_slots` + `create_booking`, без сложных сценариев отмен/цен/summary;
       - v2+: расширения (`cancel_booking`, `get_patient_summary`, офферы, интеграция с CRM).

3. **Разграничение Tasks vs AttentionFeed:**
   - В `ARCH_DECISIONS_NEXT` указано, что Tasks/Attention — «не дубль бизнес‑логики»;
   - в коде `AttentionFeedService` уже достаточно активно использует domain‑entities и агрегирует много логики.
   - Рекомендация:
     - убедиться, что финальный дизайн Tasks/Attention не начинает хранить «истину» о статусах визитов/пакетов/лидов (только ссылки/выжимки);
     - возможно, разделить ARCH‑описание AttentionFeed на «read‑модель (feed)» и «источник данных (домены)».

4. **Paperless и E‑подпись:**
   - `ARCH_PAPERLESS_NEXT` включает довольно сильные требования по e‑signature, юридическим метаданным и привязкам к визитам;
   - текущая реализация форм (admin_forms/patient_forms) может быть проще.
   - Рекомендация:
     - чётко отметить в `ARCH_PAPERLESS_NEXT`, что e‑подпись — это vNext+ (дополнительный шаг), а не обязательное требование для ближайшего релиза;
     - не блокировать остальные улучшения Paperless необходимостью сразу внедрять полноценный e‑signature стек.

## 3. Рекомендации для ARCH по правкам архитектуры

На основе проверки «код ↔ ARCH ↔ BUSINESS» предлагаются следующие уточнения:

1. **Слоистость ERP‑узла:**  
   - Зафиксировать в `ARCH_ERP_NEXT`:
     - чёткий «фасад» уровня `BookingCompletionService` (или аналог), который координирует вызовы Finance/Payroll/Inventory:
       - но использовать AttentionFeed как «страховку» на случай неполной транзакции;
       - описать пошаговый сценарий миграции от текущих разрозненных вызовов к фасаду.

2. **AI Agent v1 vs v2 в документации:**
   - Внести в `ARCH_OMNICHANNEL_NEXT` раздел «v1 / v2»:
     - v1: небольшой набор безопасных tools, без сложной бизнес‑орканизации;
     - v2: полный Orchestrator, дополнительные инструменты и плотная CRM‑интеграция.
   - Это позволит избежать ощущения «мы не дотягиваем до архитектуры», пока AI‑слой строится по шагам.

3. **Чёткий маппинг между BUSINESS_LOGIC_V2 и ARCH_*_NEXT:**
   - В каждом `ARCH_<DOMAIN>_NEXT.md` добавить микрораздел:
     - «Отношение к BUSINESS_LOGIC_V2»:
       - какие пункты V2 уже покрыты;
       - какие будут реализовываться позже.
   - Это снизит риск расхождения между бизнес‑видением и архитектурой.

4. **UX‑инвариант для статусов/ролей:**
   - В `ARCH_DECISIONS_NEXT` уже есть пункт про единые словари статусов/ролей;
   - стоит добавить:
     - ссылку на `TEMPLATE_DESIGN_UX.md` как на источник UI‑принципов;
     - требование описывать словари статусов в одном месте (например, `status_dicts.ts` / `status_mapping.py`) и не дублировать их по проекту.

## 4. Рекомендации для DEV_PROMPTS_NEXT (пошаговая миграция)

Чтобы минимизировать риск «сломать действующую систему» при движении к vNext, стоит заложить в `DEV_PROMPTS_NEXT` следующие принципы:

1. **AI Agent внедрять итеративно:**
   - Сначала добавить минимальный набор tools (read‑only/простые операции), не меняя существующих endpoint’ов Omnichannel.
   - Только после стабилизации — позволять AI менять состояния (создавать/отменять записи, двигать лиды).

2. **ERP‑узел строить вокруг уже существующего кода:**
   - Выделять фасад постепенно, не вынося логику из сервисов целиком одномоментно.
   - На каждом шаге обеспечивать, что либо и старый, и новый путь дают один и тот же результат, либо старая логика явно выключается через конфиг/флаг.

3. **CRM‑автодвижение в три шага:**
   - Шаг 1: автосоздание `LeadCard` из Omnichannel контактов.
   - Шаг 2: автопереход в «Записан» по событиям Booking.
   - Шаг 3: автопереход в «Успешно завершено»/«Потеряно» по событиям ERP/Booking.

4. **UX‑рефакторинг статус‑слоя как отдельный пакет:**
   - Вынести мэппинги статусов в один модуль и обновить фронт поэтапно:
     - сначала History/Booking/CRM;
     - затем остальные страницы.

5. **Paperless e‑signature отложить в отдельный пакет:**
   - В DEV_PROMPTS выделить отдельный блок для e‑signature, не смешивая его с базовыми улучшениями форм/анкеты.

Эти рекомендации помогут ARCH при формировании `DEV_PROMPTS_NEXT` сделать план миграции безопасным и поэтапным, не выходя за рамки реального кода и бизнес‑ожиданий.
