## ARCH_DEV_OMNI_UI_017 — UX AI‑агента и Omnichannel

## 1. Контекст и существующее состояние

### 1.1. Роль Omnichannel & AI в продукте

По `BUSINESS_PLAN_NEXT.md` и `ARCH_OMNICHANNEL_NEXT.md`:

- Omnichannel — **операционный центр общения** с пациентами/лидами:
  - все каналы (мессенджеры, email, web/PWA‑чат) сводятся в единый UI;
  - оператор видит контекст CRM/Booking/Tasks и действует из одной точки.
- AI‑слой:
  - анализирует диалоги;
  - помогает предлагать слоты, двигать лиды, создавать задачи;
  - в vNext должен быть **явным, управляемым инструментом**, а не «магией».

### 1.2. GAPS по UX и ожиданиям (FO‑1/3, FADM‑4)

По `FRONTEND_GAPS_Omnichannel_NEXT.md` и `FRONTEND_GAPS_Admin_NEXT.md`:

- **FO‑1:** AI‑agent в Spotlight фактически stub:
  - UI выглядит как полноценная фича — пользователь ожидает «умного ассистента»,
  - фактически возвращается заглушка → ломает доверие к AI‑функциям.
- **FO‑2/FO‑3:** контекст CRM/Booking/Tasks в Omnichannel можно усилить:
  - сейчас есть переходы из CRM в Omnichannel, но не везде есть симметричные мостики;
  - нет визуальных индикаторов уровня готовности AI‑функций (beta/stub/prod).
- **FADM‑4:** Omnichannel‑UI:
  - построен на новом дизайне, но AI‑функции и интеграция с другими модулями выглядят «незавершёнными»:
    - Spotlight/AI‑agent без явных лейблов готовности;
    - недостаточно быстрых прыжков к CRM/Booking/Tasks из Omnichannel и обратно.

Риски:

- операторы и владельцы не понимают, какие AI‑функции **реально работают**, а какие нет;
- Omnichannel воспринимается как «ещё один чат», а не как рабочий центр действий;
- сложно постепенно выкатывать новые AI‑фичи без поломки ожиданий.

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_OMNICHANNEL_NEXT.md` — доменная модель Omnichannel & AI.
- `ARCH_DEV_OMNI_POLICY_016.md` — политика ПД и AI‑провайдеров.

## 2. Целевое состояние UX Omnichannel & AI

### 2.1. Жёсткие инварианты

1. **Любая AI‑функция в UI честно отражает свой статус.**
   - Возможные уровни:
     - `stub` — заглушка/демо;
     - `beta` — ограниченная рабочая версия;
     - `prod` — полноценно поддерживаемая фича.
   - Статус виден:
     - в Spotlight/AI‑agent;
     - на кнопках/иконках AI‑действий в Omnichannel.

2. **Omnichannel — рабочий центр, а не только чат.**
   - Оператор:
     - видит ключевой контекст (лид, пациент, запись, задачи);
     - может за 1–2 клика:
       - открыть карточку лида/пациента;
       - создать/просмотреть задачи;
       - перейти к расписанию/истории визитов.

3. **UX Omnichannel опирается на готовность backend‑слоя.**
   - AI‑кнопки и функции в UI:
     - включаются/отмечаются как `beta/prod` **только** после того, как:
       - соответствующий tool зарегистрирован в `tools_registry`;
       - политика ПД (OMNI_POLICY) соблюдена;
       - есть базовая наблюдаемость (OBS‑цепочки).

4. **Пользователь всегда понимает, «кто сделал действие» — человек или AI.**
   - В истории действий/логах Omnichannel:
     - пометка «создано AI» для AI‑инициированных действий;
     - понятная разница между рекомендацией и реально выполненным действием.

## 3. Архитектурный дизайн: фронтенд Omnichannel & Spotlight

### 3.1. Модель статусов AI‑функций

Предлагается ввести конфигурацию уровня фронта (может подтягиваться с backend), например:

```ts
type AiFeatureStatus = "stub" | "beta" | "prod";

interface AiFeatureConfig {
  id: string; // e.g. "omni.spotlight.agent", "omni.tools.suggest_slots"
  label: string;
  status: AiFeatureStatus;
  description?: string;
}
```

- Конфиг может приходить с backend (по клинике/окну фичей) или быть захардкожен на v1 с возможностью миграции.
- UI‑компоненты:
  - Spotlight‑действие «Спросить AI»;
  - AI‑кнопки в Omnichannel (e.g. «Предложить слоты», «Сформировать задачу»);
  - используют этот конфиг для:
    - отображения бейджей (`stub`, `beta`, `prod`);
    - включения/отключения части действий.

### 3.2. Spotlight / useAiAgent

- Текущий hook/компонент `useAiAgent`:
  - должен:
    - знать статус фичи `omni.spotlight.agent`;
    - в режиме `stub`:
      - явно показывать, что это демо/черновик (например, описание + неактивные доменные действия);
    - в режиме `beta/prod`:
      - использовать реальный Orchestrator/tools (когда они появятся по `ARCH_DEV_OMNI_REGISTRY_015`).

- UI‑поведение:
  - `stub`:
    - текст «Функция в разработке» + опционально демо‑ответ;
    - никаких реальных изменений в доменах;
  - `beta`:
    - реальный вызов AI‑функций;
    - бейдж «beta»;
    - подсказка, какие сценарии поддерживаются;
  - `prod`:
    - без дополнительных оговорок, но с доступными логами/историей действий.

### 3.3. Omnichannel‑чат (AdminOmniChatPage)

Цель: усилить связку Omnichannel ↔ CRM/Booking/Tasks в UI.

Основные элементы:

- **Контекстная панель справа/слева**:
  - карточка контакта:
    - базовая информация (имя, телефон, клиника);
  - связанные сущности:
    - активные/последние `LeadCard` (CRM);
    - ближайшие/последние `Booking` (Booking/History);
    - открытые задачи (Tasks).
- **Быстрые действия:**
  - кнопки:
    - «Создать лид» / «Открыть лид»;
    - «Создать запись» / «Открыть расписание» (может вести на admin schedule с предзаполненным фильтром по пациенту/клинике);
    - «Создать задачу» (с предзаполненным контекстом).

Интеграция с AI:

- AI‑предложения:
  - могут появляться в отдельной зоне (e.g. панель «AI‑рекомендации»);
  - но любое действие (создать лид/задачу/запись) подтверждается пользователем кликом.

## 4. Связь с backend‑слоем Omnichannel & AI

### 4.1. Feature‑флаги/конфигурация AI‑функций

Для честного UX нужен источник правды о состоянии AI‑фич:

- Возможные источники:
  - `ClinicAiSettings` (частично);
  - отдельный endpoint конфигурации Omnichannel/AI‑функций, например:
    - `GET /admin/omni/ai-features`:
      - возвращает `AiFeatureConfig[]` по клинике;
  - на v1 можно:
    - описать конфиг статично в коде backend и/или фронта, но архитектурно предусмотреть endpoint.

### 4.2. Интеграция с tools‑registry

- Для AI‑действий, завязанных на tools (после реализации DEV_PROMPT_OMNI_REGISTRY_015):
  - UI‑элементы:
    - должны включаться только если:
      - соответствующий tool зарегистрирован и доступен в текущем контексте (роль/клиника);
      - статус фичи не `stub`.

- Минимальный контракт:
  - `GET /admin/omni/available-tools`:
    - список tool‑id, доступных оператору;
  - UI:
    - пересекает `AiFeatureConfig` и доступные tools,
    - прячет/помечает те, что недоступны.

## 5. Наблюдаемость и QA‑критерии для Omni‑UI

### 5.1. Observability (связь с OBS‑цепочками)

- С точки зрения `ARCH_DEV_OBS_CHAINS_023.md`:
  - Omnichannel+AI‑цепочка должна:
    - логировать:
      - клики по AI‑кнопкам;
      - исход AI‑действий (рекомендации, ошибки, отмены);
    - использовать `trace_id` для связи UI‑действий с backend‑флоу.

### 5.2. QA/UX инварианты (ROLE_QA_ARCH)

- В духе `ROLE_QA_ARCH.md`:
  - AI‑кнопки:
    - имеют hover/active‑состояния;
    - в `stub/beta`‑режимах имеют явные подписи/tooltip’ы (почему ограничены).
  - любое действие:
    - даёт явный фидбек (toast/notification/изменение UI);
    - при ошибке:
      - не ломает весь Omnichannel;
      - даёт оператору понятное объяснение (без «магических» 500).
