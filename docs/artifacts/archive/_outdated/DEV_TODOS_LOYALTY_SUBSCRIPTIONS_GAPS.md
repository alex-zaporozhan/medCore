## DEV_TODOS_LOYALTY_SUBSCRIPTIONS_GAPS — Хвосты по лояльности для @DEV

> Основано на `DEV_PROMPTS_LOYALTY_SUBSCRIPTIONS.md` и фактическом состоянии кода.  
> Цель — зафиксировать все недоделанные/частично реализованные пункты модуля лояльности, чтобы их можно было добивать итеративно.

## 1. Backend — сервисы и доменная логика

- [ ] **1.1. Приоритет между несколькими активными подписками**
  - Добавить в `LoyaltyService` (или отдельный helper) политику выбора подписки, если под один визит подходит несколько активных `CustomerSubscription`.
  - Правила приоритета — по `DEV_PROMPTS_LOYALTY_SUBSCRIPTIONS.md`/`ARCH_LOYALTY_SUBSCRIPTIONS.md` (например: сначала более узкоспециализированный пакет, затем общий баланс; явная стратегия должна быть задокументирована в docstring и/или ARCH).
  - Обеспечить, чтобы выбор был детерминированным (одинаковый результат при повторном вызове).

- [ ] **1.2. Частичное списание и управляемые бизнес‑ошибки**
  - Проверить и при необходимости доработать `use_subscription_for_booking(...)`:
    - явное поведение при попытке частичного списания (если бизнес‑логика его не поддерживает — гарантированно кидать управляемую ошибку, а не молча списывать);
    - выбрасывать отдельные бизнес‑исключения (например, `InsufficientSubscriptionBalance`, `SubscriptionExpired`) с понятными кодами/сообщениями для маппинга в API.
  - Принимать во внимание сценарий, когда одновременно переданы `used_visits` и `used_amount` для разных типов пакетов.

- [ ] **1.3. Защита от гонок в `WalletService`**
  - Сейчас `earn_points`/`spend_points`/`expire_points` полагаются только на транзакцию.
  - Требуется:
    - Добавить защиту от гонок при одновременных операциях по одному кошельку (либо через row‑level locking в запросах к `WalletTransaction`, либо через optimistic locking на `Wallet`).
    - Документировать выбранный подход в docstring сервиса и/или отдельной секции в `ARCH_LOYALTY_SUBSCRIPTIONS.md`.

## 2. Интеграция с Booking / Payments / ERP

- [ ] **2.1. Покупка пакета через платеж и ERP**
  - Связать `LoyaltyService.purchase_subscription(...)` с фактическим процессом оплаты:
    - из обработчика успешного платежа (`PaymentSuccess`/соответствующий event handler) или HTTP‑эндпоинта создать `CustomerSubscription`;
    - связать подписку с `Payment`/`FinancialTransaction` по `payment_id`, как описано в `DEV_PROMPTS_LOYALTY_SUBSCRIPTIONS.md` и ERP‑промпте.
  - Гарантировать идемпотентность: повторная обработка одного и того же платежа не должна создавать дубликаты подписок.

- [ ] **2.2. Использование подписки при записи / подтверждении визита**
  - Внедрить вызов `LoyaltyService.use_subscription_for_booking(...)` в поток обработки бронирования:
    - точка входа: `BookingService` / узел `Booking.completed` / подтверждение записи (по согласованному в ARCH сценарию);
    - помечать `Booking` как «оплачен подпиской» (добавить поле/флаг в сущность и миграцию, если нужно).
  - Проработать поведение при частичной оплате (часть визита пакетом, часть — деньгами), в том числе как это отражается в ERP.

- [ ] **2.3. Оплата баллами и связь с ERP‑выручкой**
  - Реализовать сценарий оплаты визита баллами:
    - использовать `WalletService.spend_points(...)` перед запуском ERP‑узла по бронированию;
    - передавать в ERP/Finance фактическую сумму с учетом списанных баллов, чтобы не допустить «удвоения» выручки (выручка только по оплаченным деньгами частям).
  - Обновить `BookingErpService`/финансовый слой так, чтобы они корректно учитывали операции по кошельку и не создавали лишних доходных транзакций.
  - Добавить тесты, покрывающие кейс «часть суммы списана баллами, часть оплачена деньгами».
