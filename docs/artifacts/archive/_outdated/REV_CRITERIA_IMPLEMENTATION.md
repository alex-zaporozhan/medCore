# REV_CRITERIA_IMPLEMENTATION — Критерии внедрения UI/UX революции

> **Префикс REV_** — документы революции операционной системы.  
> **Назначение:** Критерии, по которым супер-эффективно внедряются элементы из TECH_PASSPORT_FRONTEND_UI_LOGIC и REV_RAG_MAP. Обеспечивают стабильность бэкенда, приоритизацию и чек-листы.

**Входы:** `REV_RAG_MAP_INNOVATIONS.md`, `TECH_PASSPORT_FRONTEND_UI_LOGIC.md`, `BUSINESS_LOGIC_V2.md`, `ARCH_FRONTEND_BUSINESS_OS_UX.md`.

---

## 1. Ось: стабильность бэкенда

Каждое новое UI-поведение должно либо использовать существующие контракты, либо иметь явно описанный контракт.

| Критерий | Описание | Проверка |
|----------|----------|----------|
| **Контракт первичен** | Новый экран/действие опирается на существующий или спроектированный эндпойнт (см. FUNCTIONAL_MAP_CURRENT, TECH_PASSPORT_BACKEND). | В TPF_MODULE_* или DEV_PROMPTS указан точный метод и путь. |
| **Идемпотентность** | Операции, по которым делается Optimistic UI (drag, смена статуса), должны быть идемпотентными или с `idempotency_key`. | В ARCH_* или API-спеке зафиксировано. |
| **Tenant isolation** | Все запросы в контексте админки содержат `clinic_id` (из токена или контекста). | Не тянем данные другой клиники. |
| **Rate и лимиты** | AI Command Line, экспорт, массовые действия — учтены лимиты и очереди (Celery). | В ARCH указаны ограничения. |

## 2. Ось: приоритизация внедрения

Порядок внедрения минимизирует блокировки и даёт быстрые визуальные победы.

| Приоритет | Блок | Зачем первым | Зависимости |

| **P0** | Drawer вместо Modal для всех созданий/редактирований | Универсальный закон; снижает когнитивную нагрузку. | Существующие CRUD API. |
| **P0** | EmptyState + Skeleton везде | Убирает «пустые белые экраны» и спиннеры. | Существующие GET. |
| **P1** | ActionMenu в каждой строке таблицы | Data Density + быстрые действия без перехода. | Точечные эндпойнты (cancel, copy, send link). |
| **P1** | Optimistic UI для календаря и CRM (drag) | Ощущение «нулевой задержки». | PUT/PATCH с чётким контрактом. |
| **P1** | Spotlight (Cmd+K) — навигация + поиск по пациентам/записям | Pro-ощущение; ускоряет работу. | GET search или фильтрация существующих списков. |
| **P2** | Обогащённые карточки сущностей (Patient, Booking, Service, Doctor) по вкладкам | Глубина данных без «пустых» форм. | Расширение GET by id (вложенные коллекции). |

| **P3** | Checkout Hub, техкарты, кассы | ERP-контроль. | Transactions, consumables, cashbox. |

| **P5** | PWA 2.0: Bottom Nav, Next Visit Ticket, Stories, Wallet | Лицо для пациента. | Существующие patient API + лояльность. |

## 3. Ось: качество внедрения (чек-лист на фичу)

Перед признанием фичи «готовой» пройти чек-лист.

- [ ] **Закон Drawer/Modal:** Редактирование только в Drawer; подтверждения в Modal.
- [ ] **Relational Integrity:** Формы не создают «висящих» записей (обязательные поля по RAG MAP).
- [ ] **EmptyState:** При пустом списке показывается EmptyState с CTA.
- [ ] **Загрузка:** Нет полноэкранного Loader; есть Skeleton по контуру.
- [ ] **Действия в строке:** В таблице есть ActionMenu с релевантными действиями.
- [ ] **Контекст по наведению:** Где есть имена пациентов/врачей — HoverCard/Tooltip с полезной информацией (если API отдаёт).
- [ ] **Горячие клавиши:** Если экран ключевой (чат, форма) — Escape закрывает Drawer/сбрасывает фокус.
- [ ] **Оптимистичное обновление:** Где есть drag или смена статуса одним кликом — UI обновляется до ответа сервера (и откатывается при ошибке).
- [ ] **Доступность:** Критичные кнопки и поля доступны с клавиатуры; фокус не теряется в Drawer.

## 4. Ось: согласование с модулями V2

Внедрение не должно противоречить фазам BUSINESS_LOGIC_V2.

| Модуль V2 | Что из техпаспорта к нему относится | Критерий готовности |
|-----------|-------------------------------------|----------------------|
| AI Agent | AI Suggestions в чате, AI Command Line, AI-задачи, Revenue Hunter | Function Calling и инструменты реализованы; контракты стабильны. |
| CRM Kanban | Воронка, карточки, суммы, Lead Rotting, Drawer чата | LeadCard/LeadStage в БД и API; drag обновляет stage. |
| ERP | Кассы, транзакции, техкарты, Checkout Hub | Cashbox, Transaction, Consumable; завершение визита списывает материалы. |
| RBAC & Tasks | Задачи, исполнитель, SLA, «Задачи от AI» | Task с assignee_id, due_date, source; права по ролям. |
| Loyalty | Digital Pass в PWA (карточки-карты, «Записаться по абонементу»), вкладка «Абонементы» и Family Sharing в Drawer пациента, Auto-Checkout в Checkout Hub, Liability Dashboard («деньги в воздухе»), Wallet/бонусы | Абонементы и пакеты в API; раздел Loyalty в UI; контракт checkout-info + use_subscription_id; liability-эндпойнт. |
| Paperless | Формы, «Отправить форму» из контекста | Шаблоны и отправка ссылки. |
| Attribution | Funnel, таблица кампаний, Drill-down, AI Advisor | UTM → лид → запись → оплата в данных и отчётах. |

## 5. Ось: именование и навигация по файлам

- **REV_*** — революция: карты, критерии, анализ.  
- **TPF_*** — техпаспорт фронтенда: TPF_MASTER, TPF_MODULE_DASHBOARD и т.д.  
- **ARCH_*** — архитектура (существующие + REV_ARCH_UI_VALUES).  
- В DEV_PROMPTS и планах ссылаться на TPF_MASTER или конкретный TPF_MODULE_* как источник правил UI.

## 6. План введения (высокоуровнево)

1. **Фаза 0 (каркас)**  
   Внедрить App Shell по TPF_MASTER (раздел Shell): Dark Sidebar, Collapse, группы меню, Context Bar, убрать Header.  
   Критерий: все админ-страницы открываются в новом каркасе.

2. **Фаза 1 (универсальные законы)**  
   Drawer для всех созданий/редактирований; EmptyState + Skeleton на всех списках; ActionMenu в таблицах.  
   Критерий: ни одна таблица без ActionMenu; ни один пустой список без EmptyState.

3. **Фаза 2 (ключевые экраны)**  
   Dashboard (метрики, Feed, таймлайн); OmniChat (Inbox, Action Bar, CRM Context); Schedule (drag, при необходимости Ghost Slots, Waitlist).  
   Критерий: смена управляется с Dashboard; запись из чата без ухода со страницы.

4. **Фаза 3 (глубина сущностей)**  
   Карточки Patient, Booking, Service, Doctor по матрице вкладок из TPF_MASTER.  
   Критерий: каждая карточка открывается в Drawer с вкладками и без «пустых» форм.

5. **Фаза 4 (CRM, задачи, финансы)**  
   CRM Kanban с суммами и Lead Rotting; Tasks с AI-пулом и My Focus; Finance (кассы, Checkout Hub).  
   Критерий: воронка и задачи работают по сценариям из техпаспорта; финансы проходят через кассу и техкарты.

6. **Фаза 5 (дифференциаторы)**  
   Spotlight + AI Command Line; AI Revenue Hunter виджет; Retention (AI Segments, офферы); Omni-Vault (медиа, экспорт, бэкап); PWA 2.0.  
   Критерий: по отдельным DEV_PROMPTS и приёмочным сценариям.

---

*Использование: при планировании спринта брать блок из REV_RAG_MAP → проверить по этому документу (приоритет, стабильность API, чек-лист) → ссылаться на TPF_MASTER или TPF_MODULE_* в задаче.*
