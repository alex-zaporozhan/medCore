# ARCH_ALEMBIC_MIGRATIONS — Стратегия миграций БД

> Роли: @ARCH, @DEV, @LEAD.  
> Цель: зафиксировать текущую схему БД одной миграцией (squash), устранить множественные heads и перезапуски бэкенда, задать два сценария — быстрый (локально) и прод (передача клиенту).

---

## 1. Текущая проблема

- **43 файла миграций**, разросшаяся цепочка от `cae7fd450d09` с множеством ветвлений.
- **8 heads** в Alembic: `x1y2z3a4b5c7`, `ai_tasks_enabled_0001`, `b1c2d3e4f5g6`, `add_patient_oauth_ids`, `loyalty_0003_booking_paid_by_subscription`, `marketing_attr_0001_visit_attributions`, `paperless_0001_digital_forms_and_signatures`, `shift_demo_4d`. При старте контейнера `alembic upgrade heads` неоднозначен или падает.
- Часть ревизий с длинными ID (например `c3d4e5f6g7h8_erp_finance_inventory` — 34 символа) упиралась в `alembic_version.version_num` VARCHAR(32); добавлена миграция `expand_alembic_ver_64`, но множественные heads остаются.
- Система сильно изменилась (ERP, Kanban/CRM, лояльность, бумалесс, маркетинговая атрибуция и др.); актуальное состояние схемы задаётся **моделями в коде**, а не историей миграций.

---

## 2. Желаемое состояние

- **Одна линейная история** для новых установок: одна начальная миграция «полная схема по текущим моделям».
- **Короткие revision ID** (≤32 символов), чтобы не зависеть от ограничений `alembic_version`.
- Для **существующих БД с данными** — явный сценарий: либо продолжать старую цепочку до слияния, либо один раз пометить состояние как применённое (stamp) и дальше использовать только новую ветку.

### 2.1. Очистка «кэша» миграций (как pgdata)

Старая история из 43 файлов мешает так же, как залипший pgdata: множественные heads, длинные ID, путаница. **Имеет смысл убрать весь этот кэш.**

- **Вариант 1 — архив:** все текущие файлы из `alembic/versions/` перенести в `alembic/versions_archive/`. Alembic видит только то, что лежит в `versions/`; после переноса папка `versions/` пустая, цепочки и головы обнуляются.
- **Вариант 2 — удаление:** удалить все `.py` из `alembic/versions/` (при необходимости предварительно сохранить папку в git или бэкап).

После очистки в `versions/` остаётся только **одна** новая миграция (полная схема по моделям). Никаких 8 heads и 43 файлов — один чистый старт, как пустая БД после удаления pgdata.

---

## 3. Два сценария

### 3.1. Вариант A — Быстро (локально, для входа и проверки)

**Назначение:** быстро поднять бэкенд и зайти в систему без сохранения текущих данных.

**Шаги:**

1. Остановить контейнеры. Удалить том/данные PostgreSQL (например `pgdata`) или создать новую пустую БД.
2. Старые миграции в `alembic/versions/` не трогать (можно позже архивировать). Добавить **одну новую** миграцию с коротким revision ID (например `schema_v2_initial`), которая создаёт **все таблицы** по текущим моделям (через `alembic revision --autogenerate` при пустой БД или ручной перенос из `metadata`).
3. В `alembic_version` для новой установки будет одна запись — эта ревизия.
4. В `docker-compose` / команде старта бэкенда по-прежнему: `alembic upgrade head` (или `heads` после слияния). Для варианта A допустимо временно заменить команду на `alembic upgrade <revision_id>` до слияния.

**Ограничение:** данные в текущей БД теряются. Подходит только для локальной разработки/проверки.

---

### 3.2. Вариант B — Прод / передача клиенту

**Назначение:** чистая история миграций для новых инсталлов и для поставки клиенту.

**Принципы:**

1. **Одна «начальная» миграция** (single baseline) с полной схемой, соответствующей текущим доменным моделям (ERP, CRM, лояльность, бумалесс, маркетинг и т.д.). Revision ID короткий, например `schema_v2_initial` (≤32 символов).
2. **Новые инсталлы:** только эта миграция: `alembic upgrade head` создаёт всю схему за один шаг.
3. **Существующие инсталлы с данными:**  
   - либо доработать старую цепочку (merge всех heads в одну ревизию, затем одна миграция «полная схема» как следующий шаг),  
   - либо один раз: привести БД вручную/скриптом к целевому состоянию и выполнить `alembic stamp schema_v2_initial`, дальше все изменения — только поверх этой ревизии.
4. **Стандарт ревизий:** все новые миграции имеют `down_revision` и короткий `revision` ID (например `feat_xxx_short`), без длинных суффиксов, чтобы не упираться в длину колонки.

**Артефакты:**

- В репозитории: одна папка/ветка миграций; старые файлы можно перенести в `alembic/versions/archive/` и не подключать к цепочке, либо оставить только новую начальную миграцию и последующие.
- Документация для OPS/клиента: «Для новой БД: `alembic upgrade head`. Для переноса существующей БД — см. MIGRATION_UPGRADE.md».

---

## 4. Технические требования к миграции «полная схема»

- **Источник правды:** SQLAlchemy `Base.metadata` (все модели, наследующие `Base`). В `alembic/env.py` перед `context.configure` должны быть импортированы **все** доменные сущности из `src/domain/entities`, чтобы при `revision --autogenerate` в метаданных были все таблицы.
- **alembic_version:** колонка `version_num` — не короче 64 символов (уже задаётся `version_table_column_type=String(128)` в env.py; при создании таблицы с нуля убедиться, что миграция создаёт её с достаточной длиной).
- **Порядок создания таблиц:** учитывать FK: сначала справочники и независимые таблицы (clinics, admins, …), затем зависимые (bookings, payments, …). Autogenerate обычно генерирует порядок по зависимостям; при ручной сборке — явно задать порядок в upgrade().

---

## 5. Почему бэкенд всё ещё перезагружается

- **Множественные heads:** при `alembic upgrade heads` Alembic может завершаться с ошибкой или применять не все ветки, процесс старта падает → Docker перезапускает контейнер.
- **Исправление:** после появления одной начальной миграции (вариант A или B) и перевода установки на одну голову (`alembic upgrade head`) перезапуски из-за миграций должны прекратиться при успешном применении.
