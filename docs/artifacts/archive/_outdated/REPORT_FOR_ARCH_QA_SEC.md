## 2. Что обработать @ARCH

Ниже — структурированные входы для принятия решений и генерации промптов для @DEV / процессу.

### 2.1 Тестовая БД и стабильность тестов

- **Факт:** 124 теста в ERROR из‑за `database "dental_booking_test" does not exist`.
- **Вопрос к ARCH:** Нужно ли зафиксировать в ARCH_* (или в отдельном ARCH_TESTS / DEV-инструкции) обязательное создание `dental_booking_test` и шаги под Docker/local (например, одна команда `create database` и ссылка из README)?
- **Промпт для @ARCH:**  
  «По отчёту QA: тесты падают из‑за отсутствия БД dental_booking_test. Предложи минимальные изменения в документацию (ARCH или README) и критерий готовности окружения для тестов, чтобы любой разработчик мог поднять тестовое окружение за один шаг.»

### 2.2 RBAC и возврат 401

- **Факт:** Тесты ожидают 401 для защищённых эндпоинтов без авторизации; для части эндпоинтов тесты падают (GET cashboxes, payroll/policies, inventory/transactions, crm/leads, loyalty/policy, forms/templates, attribution/summary, attribution/drill-down, admin/tasks).
- **Вопрос к ARCH:** Является ли единообразный 401 без токена архитектурным контрактом для всех защищённых маршрутов? Если да — где это зафиксировать (ARCH_RBAC или аналог)?
- **Промпт для @ARCH:**  
  «По отчётам QA и SEC: часть RBAC-тестов ожидает 401 без Authorization и не получает его. Сформулируй архитектурное правило: все эндпоинты, защищённые require_permissions / get_current_admin, должны возвращать 401 при отсутствии валидного токена. Дай промпт для @DEV: список эндпоинтов из test_rbac_critical_modules и требование проверить порядок зависимостей и middleware.»

### 2.3 Безопасность и стабильность

- **Факт:** Security-тесты (IDOR, изоляция клиник, шифрование credentials, утечка ПД) не прогонялись успешно из‑за БД; SEC аудит по коду выполнен по 15 Pillars.
- **Промпт для @ARCH:**  
  «По отчёту SEC: после появления тестовой БД нужно гарантировать зелёный прогон tests/security/. Предложи критерий готовности к деплою: все тесты в tests/security/ зелёные; при необходимости дописать в ARCH_* раздел «Безопасность — обязательные проверки перед деплоем» со ссылкой на REPORT_SEC и список security-тестов.»

### 2.4 Функционал и интеграции

- **Факт:** QA P20-доп (зрелость интеграций) не заполнен по результатам прогона; интеграции перечислены в ARCH_* (ERP, платёжки, Telegram, omni и т.д.).
- **Промпт для @ARCH:**  
  «По отчёту QA: Pillar P20-доп (интеграции) не проверен. Обнови таблицу «Статус интеграций» в актуальном ARCH_*.md: для каждой интеграции укажи статус (полный flow / заглушка) и что должно быть проверено перед релизом (в т.ч. security-тесты и smoke).»

### 2.5 Критерии стабильной работы системы

- **Промпт для @ARCH:**  
  «По сводному отчёту QA+SEC сформируй краткий чек-лист «Критерии стабильности и безопасности перед релизом» для этого проекта: (1) тестовое окружение и прогон pytest, (2) smoke и критические E2E, (3) прогон tests/security/, (4) RBAC 401 по списку критичных эндпоинтов, (5) проверка секретов и rate limiting. Формат: маркированный список с ответственным (DEV/QA/OPS) и ссылками на REPORT_QA и REPORT_SEC.»
