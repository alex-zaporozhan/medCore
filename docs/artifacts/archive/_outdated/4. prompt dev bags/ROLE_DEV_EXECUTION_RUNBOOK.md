## ROLE_DEV_EXECUTION_RUNBOOK — как @DEV выполняет архитектурные промпты

> **Цель:** минимизировать решения со стороны @DEV.  
> @ARCH/@LEAD принимают архитектурные решения, @DEV строго исполняет сценарий.

---

### 1. Что читать перед началом любой задачи

1. **Определить DEV_PROMPT.**  
   - Открыть `docs/artifacts/DEV_PROMPTS_NEXT.md`.  
   - Найти актуальный `DEV_PROMPT_xxx` по приоритету/зависимостям (@ARCH/@LEAD укажут, с какого начинать).

2. **Найти связанный ARCH_DEV и TASKS.**  
   - Открыть `docs/artifacts/ARCH_DEV_COVERAGE_NEXT.md`.  
   - По `DEV_PROMPT_xxx` найти `ARCH_DEV_xxx.md`.  
   - Для этого же ID использовать файл мелких задач `ARCH_DEV_<ID>_TASKS.md` (пример: `ARCH_DEV_OMNI_POLICY_016_TASKS.md`) в `docs/artifacts/`.

3. **Понять архитектуру.**  
   - Внимательно прочитать `ARCH_DEV_xxx.md` целиком: контекст, целевое состояние, инварианты, dev‑чек‑лист.

4. **Рабочий сценарий для @DEV.**  
   - Работать **только** по задачам из `ARCH_DEV_<ID>_TASKS.md` и/или dev‑чек‑листу в конце `ARCH_DEV_xxx.md`.  
   - Не добавлять новые крупные задачи от себя без согласования с @ARCH.

---

### 2. Алгоритм выполнения одной dev‑таски

Для каждой задачи из `ARCH_DEV_<ID>_TASKS.md`:

1. **Прочитать формулировку.**  
   - Убедиться, какие файлы/слои перечислены (DTO, сервисы, роутеры, тесты, OBS).

2. **Найти и изучить код.**  
   - Открыть указанные файлы (например `application/services/...`, `api/v1/routers/...`, `domain/entities/...`).  
   - Понять текущее поведение, не меняя архитектуру.

3. **Внести изменения строго по слоям:**
   - DTO/модели (если указаны).  
   - Application‑сервисы (главная логика).  
   - Роутеры/API (только перечисленные в ARCH_DEV/задаче).  
   - OBS: логи/метрики/Attention — если задача это требует.

4. **Написать/обновить тесты:**
   - Для каждого жёсткого инварианта, затронутого задачей.  
   - Позитивные и негативные сценарии, описанные в ARCH_DEV.

5. **Прогнать тесты (минимум локально) и зафиксировать результат.**

6. **Обновить статус задачи:**
   - Отметить её выполненной в таск‑трекере и/или ссылкой на PR.  
   - В `ARCH_DEV_<ID>_TASKS.md` статус можно не править — это артефакт @ARCH, но в описании PR указать, какие пункты файла закрыты.

Переходить к следующей dev‑таске **только после** завершения всех шагов выше для текущей.

---

### 3. Чего @DEV делать не должен (без @ARCH)

@DEV **НЕ**:

- Не меняет каркас архитектуры домена:
  - не создаёт новые домены/крупные сущности без явного описания в `ARCH_DEV_xxx.md`;
  - не меняет публичные контракты API за пределами перечисленных в ARCH_DEV/DEV_PROMPT.

- Не трогает без прямого указания:
  - RBAC/permissions и проверки `clinic_id`;  
  - глобальную политику безопасности/SEC;
  - общую политику AI (кроме задач, прямо описанных в соответствующем ARCH_DEV).

- Не «улучшает как кажется лучше»:
  - никакого рефакторинга вне контекста задачи;
  - никаких новых фич поверх сценария без отдельной задачи и решения @ARCH.

Если реализация задачи приводит к изменениям, которые явно выходят за пределы описанного в `ARCH_DEV_xxx.md`/`*_TASKS.md`, @DEV останавливается и обращается к @ARCH.

---

### 4. Когда @DEV обязан позвать @ARCH

Позвать @ARCH (через комментарий в таске/PR/чат), если:

1. **Нет ответа в артефактах.**  
   - Поведение, контракт или формат данных не описаны ни в `ARCH_DEV_xxx.md`, ни в `DEV_PROMPTS_NEXT.md`, ни в `DEV_ARTIFACT_*`.

2. **Есть несколько архитектурных вариантов.**  
   - Например: разные способы кеширования, новые связи между доменами, изменение статуса жизненного цикла.

3. **Нарушается инвариант.**  
   - Для выполнения задачи нужно осознанно нарушить/пересобрать один из инвариантов, описанных в ARCH/REV/SEC документах.

4. **Требуется новый публичный API.**  
   - Если текущих эндпоинтов недостаточно, и нужен новый контракт, — это решение @ARCH, не @DEV.

---

### 5. Git‑ветки и PR с точки зрения @DEV

- **Ветка на DEV_PROMPT.**
  - Имя: `feature/dev-prompt-<id>` (пример: `feature/dev-prompt-omni-policy-016`).

- **Один PR — ограниченный набор задач.**
  - В описании PR:
    - указать `DEV_PROMPT_xxx`, `ARCH_DEV_xxx.md`, `ARCH_DEV_<ID>_TASKS.md`;
    - перечислить пункты из `*_TASKS.md`, которые закрывает PR;
    - коротко описать, какие инварианты затронуты и как они покрыты тестами/OBS.

- **@DEV не сливает ветки самовольно.**
  - Слияние/релиc — после ревью @ARCH/QA по чек‑листам.

---

### 6. Связь с фронтовыми промптами

- Для фронтенда:
  - Основной сценарий: `docs/artifacts/DEV_PROMPTS_NEXT.md` (фичи) + `DEV_PROMPTS_FRONTEND_BACKEND_UNLOCK.md` (раскрытие бэкенда).  
  - Устаревший `DEV_MASTER_PROMPT.md` использовать **только как пример стиля**, задачи из него **не** включать в текущий план.

@DEV всегда исходит из текущих `DEV_PROMPTS_*`, `ARCH_DEV_*` и связанных `DEV_ARTIFACT_*`.  
Любое расхождение или устаревший документ — повод спросить @ARCH/@LEAD, а не придумывать решение.
