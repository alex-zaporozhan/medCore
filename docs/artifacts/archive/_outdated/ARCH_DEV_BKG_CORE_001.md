## ARCH_DEV_BKG_CORE_001 — ERP‑фасад завершения визита

> DEV_PROMPT_BKG_CORE_001 — «ERP‑фасад завершения визита (BKG‑1, ERP‑1)»

---

## 1. Контекст и существующее состояние

### 1.1. Бизнес‑цепочка

- Запись (`Booking`) проходит путь:
  - создана / подтверждена;
  - пациент пришёл / не пришёл;
  - оказаны услуги, проведена оплата / списание из пакета / депозита;
  - визит завершён, деньги/материалы/лояльность отражены в ERP/CRM.
- Сейчас части этой логики размазаны по:
  - сервисам Booking/ERP/Loyalty;
  - роутерам (`bookings`, `admin_finance`, возможные вспомогательные эндпоинты);
  - фронтовым формам завершения визита и оплаты.

### 1.2. Проблема (gap BKG‑1 / ERP‑1)

- Нет единой точки, которая:
  - атомарно проводит завершение визита;
  - гарантированно вызывает ERP‑узел, Loyalty, CRM‑агрегации;
  - даёт чёткий контракт «успех/ошибка» для UI и последующих доменов.
- Из‑за этого:
  - возможны расхождения между Booking.status и фактом проведения денег/списаний;
  - сложно отследить, где именно «сломался» поток (нет наблюдаемого фасада);
  - ERP‑узел и DEV_PROMPT_ERP_NODE_010 не на что опереться как на единый вход.

### 1.3. Связь с другими ARCH/DEV артефактами

- `ARCH_BOOKING_NEXT.md` — инварианты статусов и жизненного цикла `Booking`.
- `ARCH_ERP_NEXT.md` — путь денег/материалов, ERP‑узел завершения визита.
- `ARCH_LOYALTY_NEXT.md` — списания/обязательства по пакетам/депозитам.
- `ARCH_TASKS_NEXT.md` / `ARCH_OMNICHANNEL_NEXT.md` — Attention/Tasks при сбоях.
- `ARCH_DEV_ERP_NODE_010.md` (планируется) — внутренняя реализация ERP‑узла.

## 2. Целевое состояние фасада завершения визита

### 2.1. Жёсткие инварианты

1. **Единая точка входа.**
   - Любое изменение `Booking.status → completed` в проде проходит через один доменный сервис фасада:
     - `BookingCompletionFacade` (рабочее имя) в `src/application/services/booking_service.py` или отдельном модуле.

2. **Атомарность по доменам.**
   - В рамках одной транзакции/юнита работы фасад:
     - проверяет, что `Booking` находится в допустимом статусе для завершения;
     - вызывает ERP‑узел (деньги, ЗП, склад);
     - вызывает Loyalty‑слой (списания/обязательства);
     - обновляет агрегаты/события для CRM/Attribution (минимально необходимый набор);
     - фиксирует финальный статус `Booking`.
   - Если любая из критичных частей не проходит:
     - транзакция откатывается;
     - фронт и внешние слои видят контролируемую ошибку.

3. **Явный контракт фасада.**
   - Метод фасада возвращает структурированный результат, например:
     - `BookingCompletionResult` c полями:
       - `success: bool`;
       - `booking_id`, финальный статус;
       - `erp_summary` (сводка по деньгам/материалам);
       - `loyalty_summary` (списания/балансы);
       - `warnings: list[str]`;
       - `error_code`/`error_message` (при неуспехе).

4. **Инварианты multi‑tenant и RBAC.**
   - Все операции фасада выполняются в рамках:
     - `clinic_id` записи;
     - проверенных прав вызывающего пользователя/системного контекста.
   - Фасад не даёт обойти проверки из `DEV_PROMPT_SEC_RBAC_022`:
     - вызывается только из роутеров с корректными `require_permissions(...)`;
     - дополнительно проверяет принадлежность сущностей к `clinic_id`.

5. **Наблюдаемость по умолчанию.**
   - Каждый вызов фасада:
     - логируется с ключевыми параметрами (booking_id, clinic_id, суммы, исход);
     - при критичных ошибках создаёт Attention/Task по шаблону из `DEV_PROMPT_TASKS_MODEL_020`.

### 2.2. Границы ответственности фасада

- **Фасад делает:**
  - проверяет возможность завершения визита по текущему состоянию `Booking` и связанных сущностей;
  - собирает входные данные для ERP/LOYALTY/CRM;
  - orchestration: вызывает соответствующие доменные сервисы и обрабатывает их результат;
  - управляет транзакцией и финальным состоянием `Booking`.

- **Фасад не делает:**
  - не содержит бизнес‑правил ERP/LOYALTY/CRM внутри себя;
  - не знает о деталях UI (тексты для пользователя — задача слоя представления);
  - не обходит RBAC/clinic‑ограничения;
  - не пишет напрямую в БД в обход доменных сервисов.

## 3. Архитектурный дизайн фасада

### 3.1. API фасада (черновой контракт)

- Место размещения (предложение):
  - `src/application/services/booking_service.py`:
    - класс/сервис `BookingCompletionService` или метод в существующем `BookingService`.

- Предлагаемый интерфейс:

```python
class BookingCompletionResult(BaseModel):
    success: bool
    booking_id: UUID
    final_status: str
    erp_summary: dict | None = None
    loyalty_summary: dict | None = None
    warnings: list[str] = []
    error_code: str | None = None
    error_message: str | None = None


class BookingCompletionService:
    async def complete_visit(
        self,
        booking_id: UUID,
        *,
        actor: UserContext,
        session: AsyncSession,
    ) -> BookingCompletionResult:
        ...
```

- `UserContext` берётся из текущей модели аутентификации:
  - должен содержать `user_id`, `clinic_id`, роли/пермишены.

### 3.2. Поток внутри `complete_visit`

1. Загрузка `Booking` по `booking_id` + валидация `clinic_id` и статуса.
2. Подготовка структур для ERP‑узла:
   - список оказанных услуг/позиций;
   - суммы по источникам (кэш, эквайринг, пакет, депозит и т.п.);
   - данные для ЗП и склада (грубый контур, детали в `ARCH_DEV_ERP_NODE_010`).
3. Подготовка данных для Loyalty:
   - какие пакеты/депозиты должны быть списаны;
   - контроль балансов и статусов обязательств.
4. Вызов ERP‑узла:
   - единый метод, например `erp_node.process_booking_completion(...)`;
   - ожидание результата, обработка ошибок.
5. Вызов Loyalty‑сервиса:
   - методы списания/обновления обязательств;
   - фиксация результата.
6. Обновление агрегатов CRM/Attribution (минимально необходимый набор, без тяжёлых отчётов).
7. Обновление `Booking.status` и связанных полей (например, фактическое время визита, суммы).
8. Формирование `BookingCompletionResult` и возврат.

### 3.3. Интеграция с ERP‑узлом и Loyalty

- Фасад опирается на явные контракты:
  - ERP:
    - `ErpBookingCompletionRequest` / `ErpBookingCompletionResult`;
  - Loyalty:
    - `LoyaltyWriteOffRequest` / `LoyaltyWriteOffResult`.
- Эти контракты будут детализированы в `ARCH_DEV_ERP_NODE_010` и `ARCH_DEV_ERP_LOYALTY_011`, но уже сейчас:
  - должны быть оформлены как отдельные DTO в `src/application/dto/erp_finance_dto.py` и аналогичных модулях;
  - не должны тянуть за собой прямые ORM‑модели в API фасада.

## 4. Изменения в API и слоях приложения

### 4.1. Backend API

- Обновить роутеры:
  - `src/api/v1/routers/bookings.py`
  - `src/api/v1/routers/admin_finance.py`
- Основные изменения:
  - операции, которые сейчас:
    - напрямую меняют `Booking.status` на `completed`;
    - вызывают ERP/финансовые операции кусочно;
  - должны быть переведены на вызов фасада:
    - `result = await booking_completion_service.complete_visit(...)`.

- Контракты API:
  - возвращать клиенту агрегированный ответ на основе `BookingCompletionResult`;
  - гарантировать, что при ошибках:
    - статус `Booking` не переходит в `completed`;
    - клиент получает осмысленный код/сообщение;
    - критичные сбои приводят к Attention/Task.

### 4.2. Frontend (high‑level)

- Фронт‑формы завершения визита/оплаты (Admin + PWA):
  - ориентируются на новый контракт API:
    - не пытаются по отдельности дергать ERP/LOYALTY;
    - ожидают единый результат «визит завершён» либо контролируемую ошибку.
- Детальный фронтовый план будет зафиксирован в соответствующем `FRONTEND_GAPS_*_NEXT.md` и DEV‑тасках, но важно:
  - минимизировать количество шагов/кликов для оператора;
  - показывать состояние выполнения (индикатор «проводим визит…»);
  - явно отражать частичные неуспехи (например, ERP‑узел недоступен, визит не завершён).

## 5. Наблюдаемость и ошибки

### 5.1. Логирование

- В `BookingCompletionService`:
  - логировать:
    - `booking_id`, `clinic_id`, инициатора (`user_id/role`);
    - суммы/типы операций (без деталей ПД пациента);
    - исход (успех/ошибка, коды ошибок).

### 5.2. Attention/Tasks

- При критичных ошибках (например, ERP недоступен, неконсистентные данные):
  - создавать `AttentionItem`/`Task` с привязкой к:
    - `booking_id`, `clinic_id`;
    - типу проблемы (ERP_FAILURE, LOYALTY_MISMATCH и т.п.);
  - интеграция согласуется с `DEV_PROMPT_TASKS_MODEL_020`.

### 5.3. Метрики

- Ввести базовые метрики:
  - количество попыток завершения визита;
  - доля успешных/ошибочных завершений;
  - распределение типов ошибок (ERP, Loyalty, валидация и т.п.);
  - время выполнения фасада.
