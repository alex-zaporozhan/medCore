## UX_FLOWS_AND_GAPS_NEXT — ключевые флоу и UX‑дыры

> **Фокус:** верхнеуровневые пользовательские сценарии (пациент + админ)  
> и явные UX‑gaps, выявленные по коду и QA‑аудиту.

---

## 1. Пациентские сценарии (`/app`)

### 1.1. Логин → PWA

**Флоу:**  
`/` → кнопка «Приложение пациента» → `/login` → логин (телефон/SMS или OAuth) → `/app`.

**GAPS:**
- **UX-1:** не сохраняется исходный маршрут (если пользователь шёл на `/app/booking`, после логина его всегда кидает на `/app`).

### 1.2. Быстрая запись (`/app/booking`)

**Флоу:**  
`/app` → нижняя навигация «Запись» → `BookingWizardPage`  
→ шаги: Услуга → Врач → Дата/время → (опционально) Подтверждение/оплата → `/booking/success`.

**GAPS:**
- **UX-2:** не объяснена политика предоплаты (почему иногда нужно платить, иногда нет).
- **UX-3:** выбор клиники происходит «за кадром» через `localStorage` и первую клинику, без явного шага выбора.
- **UX-4:** в случае ошибок API при создании записи/платежа нет явного пользовательского сообщения (может казаться, что «ничего не произошло»).

### 1.3. История и отмена визита (`/app/history`)

**Флоу:**  
`/app` → верхняя навигация/меню «История» → `HistoryPage` → таблица визитов, кнопка «Отменить».

**GAPS:**
- **UX-5:** статус посещения показывается сырым значением (`confirmed`, `completed`, `cancelled` и т.п.), без перевода/цветового кода.
- **UX-6:** в списке нет врача/услуги/клиники — только дата/время/статус.

### 1.4. Чат с клиникой (`/app/chat`)

**Флоу:**  
`/app` → нижняя навигация «Чат» → `ChatPage` → просмотр/отправка сообщений, наклейки.

**GAPS:**
- Явных критичных UX‑дыр в рамках первого прохода не выявлено; интерфейс учитывает лоадеры, ошибки и пустые состояния.

### 1.5. Лояльность и формы (`/app/loyalty`, `/app/forms`)

**Флоу:**  
`/app` → «Лояльность» / «Формы» → соответствующие страницы.

**GAPS:**
- **UX-7:** требуется отдельный детальный аудит (что именно видит пациент: баланс, пакеты, историю, статусы форм), чтобы привести к уровню Enterprise SaaS.

## 2. Админские сценарии (`/admin`)

### 2.1. Расписание и записи

**Флоу:**  
`/` → «Войти в Business OS (админка)` → `/admin/login` → `/admin`  
→ `/admin/schedule` (сетка расписания)  
→ `/admin/bookings` (таблица записей)  
→ `/admin/waitlist` (лист ожидания)  
→ `/admin/prepayment` (политики предоплаты).

**GAPS:**
- **UX-8:** текущий аудит не детализирует drag&drop, фильтры, визуальные статусы, связку с ERP — требуется отдельный фронтовый аудит модулей расписания/записей.
- **FADM-2 (частично снято на backend, 2026‑03):** лист ожидания приведён к единому сервису и предсказуемым правилам (`WaitlistService`, статусы, конвертация в запись, панель на расписании с фильтром активных заявок); **остаётся продуктовый UX** — сильнее связать `/admin/waitlist` и `/admin/schedule` (единый контекст клиники/врача/дня, меньше ощущения «отдельного острова»). Подробности: `ARCH_DEV_BKG_WAITLIST_004.md` §8, `ARCH_DEV_BKG_WAITLIST_004_TASKS.md` («На потом»).

### 2.2. CRM‑воронка (`/admin/sales`)

**Флоу:**  
`/admin` → «CRM & Sales» → `AdminSalesPipelinePage` (Kanban).  
Из карточки лида возможен переход в Omnichannel‑чат.

**GAPS:**
- **UX-9:** требуется описать полный UX (фильтры, поиск, навигация из лида к визиту/оплате/пациенту) и выровнять его под Enterprise‑уровень (Kanban как центр продаж, а не только визуальный список).

### 2.3. Omnichannel и AI

**Флоу:**  
`/admin` → «Chat & AI» → `AdminOmniChatPage`;  
Spotlight «Спросить AI» в `AdminLayout` вызывает `useAiAgent` (stub).

**GAPS:**
- **UX-10:** с точки зрения пользователя, заявлен AI‑агент, но фактически он отвечает заглушкой; это создаёт рассинхронизацию ожиданий и поведения.

### 2.4. ERP‑панель (`/admin/finance`)

**Флоу:**  
`/admin` → «Finance» → `AdminFinancePage` → вкладки «Кассы», «Транзакции», «Зарплаты», «Склад`.

**GAPS:**
- **UX-11:** нужно проверить, насколько прозрачно отображена связь «визиты → деньги → ЗП → склад» и есть ли drill‑down из ERP в конкретные визиты/пациентов/лиды.

### 2.5. Лояльность, формы, маркетинг, задачи, отчёты

**Флоу (сводно):**  
`/admin/loyalty`, `/admin/forms`, `/admin/marketing`, `/admin/recall`, `/admin/retention`, `/admin/attention`, `/admin/tasks`, `/admin/reports`, `/admin/attribution`, `/admin/omni-ai-settings` и др.

**GAPS:**
- **UX-12:** требуется единый фронтовый аудит модулей админки:
  - унификация дизайна (новый UI везде, без «старых» окон);
  - консистентность status‑лейблов и ключевых показателей;
  - удобные переходы между связанными доменами (например, из отчёта → конкретные визиты/лиды/пациенты).

## 3. Кросс‑UX инварианты, вытекающие из флоу

1. **Статусы и роли в UI всегда человеко‑читаемые и цвето‑кодированные.**
2. **Любая критичная операция (запись, оплата, завершение визита, действия в CRM) имеет:**
   - явный лоадер;
   - явное сообщение об ошибке;
   - понятный результат/подтверждение.
3. **Любой high‑level экран (отчёты, ERP, CRM, AttentionFeed) должен позволять drill‑down в первичные сущности.**
4. **Нигде не должно остаться экранов в «старом дизайне» — все страницы и модалки приводятся к гайду из `TEMPLATE_DESIGN_UX.md`.**
