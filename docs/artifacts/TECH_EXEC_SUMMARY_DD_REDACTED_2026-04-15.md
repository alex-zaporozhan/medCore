# Техническое резюме (обезличенная версия для внешних LLM / третьих сторон)

Здесь **по возможности не указываются пути в репозитории, внутренние имена скриптов и файлов**. **Секретные значения не приводятся**; имена переменных окружения в вашей среде трактуйте как обобщённые ручки конфигурации.

**Зачем этот документ.** Ниже — не маркетинг, а скелет того, *как устроена система*: где проходят границы тенантов, где риск гонок и как его прижимают, почему фоновые задачи и outbox не «дополнение», а часть модели надёжности, и как фронт и AI вписаны в ту же картину без отдельного микросервисного зоопарка. Архитектурный ярлык здесь — **модульный монолит**: один основной сервис развёртывания с чёткими слоями (API → приложение → инфраструктура), а не распределённый граф из десятков независимых релизов.

## 1. Данные и изоляция мультитенантности

**Логика проекта.** Продукт одновременно обслуживает **несколько клиник** и при этом может группировать их в **организации** (сеть, холдинг, SaaS-аккаунт платформы). Операционная «единица дня» для врача и админа — клиника; финансово-продуктовые и платформенные вещи часто живут на уровне организации. Такое разделение позволяет и изолировать данные по месту оказания услуг, и не дублировать всё (справочники, биллинг, права на сеть) на каждую точку.

**Модель**

- **Тенантность по клинике** по умолчанию: в контексте аутентифицированного администратора есть **идентификатор клиники**; доменные сервисы **проверяют принадлежность сущности клинике** перед изменениями (бронирования, расписание и смежные потоки).
- **Уровень организации / сети** добавляет второе измерение: биллинг, entitlements и базы знаний на уровне организации завязаны на **организацию**. Кросс-клинический доступ админов **явно ограничен** (та же организация **и** повышенная «сетевая» роль); иначе ответы **в духе 404/403**, чтобы снизить перебор чужих тенантов.
- **Структурированные HTTP-ошибки** при запрете кросс-клинического доступа включают стабильный **код ошибки**, метаданные сущности и **корреляцию / trace id**, если доступно.

Смысл ответов **404 там, где «чужая» клиника** — не только безопасность, но и **снижение утечки факта существования** идентификаторов между тенантами: клиенту сложнее отличить «нет объекта» от «объект есть, но не ваш». Структурированное тело ошибки нужно интеграторам и саппорту: по коду и `trace_id` можно сопоставить запись в логах без раскрытия лишних полей в тексте «403 Forbidden».

**Масштаб реляционной модели (оценочно, статический анализ)**

- Порядка **~160 таблиц в ORM** (подсчёт объявлений имён таблиц по дереву бэкенда).
- Порядка **~160 модулей доменных сущностей**, согласованных с персистентностью.
- **Высокие двузначные** числа ревизий миграций (схема эволюционировала множеством инкрементов).

**RBAC**

- Порядка **~50 атомарных кодов прав** в **одном каноническом матричном описании** (сидирование в БД; задокументированная процедура добавления прав и синхронизации с миграциями).
- В рантайме: **роли и права на пару пользователь + клиника** через отдельный сервис поверх репозитория.
- **Сотни** проверок на уровне маршрутов (декораторы / зависимости) по админ-API.
- В персистентности: **права, роли, связи роль–право, связи пользователь–роль, опциональные пер-юзер гранты, аудит**.

**Почему RBAC такой гранулярный.** В медицинском и финансовом контексте недостаточно роли «админ»: одному пользователю нужен доступ к расписанию, другому — к ПДн пациента, третьему — только к складу без кассы. Канонический список прав синхронизируется с БД, чтобы **один источник правды** для сидов, миграций и проверок на маршрутах; «сотни» точек проверки — следствие большой поверхности админ-API: каждый чувствительный эндпоинт явно декларирует минимальный набор прав, а не полагается на соглашения в сервисах.

## 2. Масштаб бэкенда и архитектуры

**Логика разрезания.** HTTP-слой тонкий: валидация входа, аутентификация, RBAC, маппинг в DTO. Тяжёлая логика — в **сервисах приложения** и **домене**; доступ к БД и внешним системам — через репозитории и адаптеры. Это классический **гексагональный / чистый** уклон без отдельного деплоя на каждый bounded context: модули граничат по пакетам и соглашениям, а не по сетевому процессу.

**HTTP API**

- Порядка **~490** обработчиков маршрутов FastAPI (подсчёт декораторов на версионированных HTTP-роутерах).
- Порядка **~90** модулей роутеров для публичной, админской и платформенной поверхности.
- Порядка **~560** исходных файлов Python в пакете приложения.

**Основные библиотеки**

- **FastAPI / Starlette / Uvicorn**, **SQLAlchemy 2 + асинхронный драйвер PostgreSQL**, **Alembic**, **Pydantic v2**, **клиенты Redis**, **Celery (Redis)**, **HTTPX**, **Prometheus client**, **JWT**, **SDK Telegram-бота**, **AWS SDK**, **cryptography**, **TOTP**.

**Фоновые задачи**

- В Celery зарегистрировано **порядка дюжины** пакетов задач: уведомления, пакетные AI-задачи, лояльность, дайджесты для владельца, уборка экспортов/бэкапов, агрегаты ERP, обслуживание CRM, напоминания коллаборации, **повторы SaaS-биллинга**, **диспетчер транзакционного outbox**, **сверка платежей**.
- Расписание beat: **от субминутных до суточных** интервалов (примеры: **30 с** слив outbox, **5 мин** напоминания персонала, **15 мин** напоминания пациентам, **ночные** окна ERP, **часовые/суточные** проходы AI, **биллинг** — retry и TTL).

**Зачем Celery и Redis в связке.** Запрос HTTP должен **быстро завершаться**; всё, что может тормозить (рассылки, тяжёлые пересчёты, повторные попытки к внешнему API, ночные свёртки) выносится в воркеры. Redis здесь — и **брокер очереди**, и (отдельно от Celery) хранилище для **лимитов**, **кэшей сессий**, **pub/sub** между репликами API. Разные периоды beat отражают **разную критичность по времени**: outbox и биллинг ближе к real-time SLA, ERP-ночник — к пакетной аналитике.

**Транзакционный outbox**

- **Outbox в PostgreSQL** с **идемпотентной вставкой** по **ключу дедупликации** (в одной транзакции с изменением доменного состояния, где так задумано).
- **Асинхронная доставка** планировщиком воркера; **метрики и gauge** для очереди, возраста, ошибок и лимитов попыток диспетчера.
- **Флаги** в конфигурации для вебхука платежей, провижининга SaaS, событий жизненного цикла бронирования, размера батча и максимума попыток диспетчера.

**Идея outbox в двух словах.** Классическая проблема: «запись в БД прошла, а публикация события / вызов шины — упал» → **потеря побочного эффекта** или двойная доставка при ретраях. Outbox решает это так: **в той же транзакции**, что и бизнес-изменение, в таблицу кладётся строка «событие к отправке» с **дедуп-ключом**; отдельный воркер потом читает очередь и доставляет наружу. Идемпотентность по ключу защищает от **повторной обработки** при сбоях между коммитом и диспетчером. Флаги конфигурации позволяют **поэтапно включать** outbox на отдельных контурах (платежи, SaaS, бронирования) без «большого взрыва» релиза.

**Контроль конкурентности**

- **Транзакционные advisory locks PostgreSQL** сериализуют изменения **по слоту врача** и **обновление ERP** на клинику, снижая гонки.
- **Блокировка на уровне строк** задокументирована как минимум для одного сценария **конверсии листа ожидания**.

**Почему advisory lock, а не только уникальный индекс.** Уникальность по полям слота ловит часть коллизий, но **гонка «два клиента на один слот»** и «перенос + запись в ERP» лучше сериализуются **явной точкой упорядочивания** в БД: advisory lock дёшево привязывается к **логическому ключу** (врач + время слота, клиника для ERP) без отдельной таблицы блокировок и работает **в рамках транзакции**. `SELECT … FOR UPDATE` на конкретной строке листа ожидания — другой приём для сценария «только один поток конвертирует запись в бронь».

**Масштабирование чтения**

- Опциональный **DSN read-replica** для отчётных сессий с поддержкой **statement timeout**.

**Смысл read-replica + таймаута.** Тяжёлые отчёты — типичный источник **долгих запросов** и конкуренции с OLTP. Вынос чтения на реплику (если она заведена в инфраструктуре) **разгружает мастер**; `statement_timeout` на отчётной сессии ограничивает «забытые» запросы, чтобы один дашборд не держал соединения пула бесконечно.

## 3. Фронтенд и UI/UX

**Логика клиента.** Один фронтовый билд обслуживает **несколько «зон» UX**: публичный/пациентский контур (запись, PWA), развёрнутая **админка** клиники, маркетинг и **платформенный** кабинет. Маршрутизация на стороне браузера разводит эти зоны; к API они ходят с разными токенами и префиксами версии API на бэкенде.

**Стек**

- **React 18**, **Vite 6**, **TypeScript 5.x**, **React Router 6**, **Mantine 7**, **TanStack Query 5**, библиотека drag-and-drop, **Vitest**, **Playwright**.

**Грубые оценки UI (одно SPA-дерево)**

- Порядка **~150** файлов TSX всего.
- Порядка **~75** страничных компонентов (без колокейтед-тестов).
- Порядка **~25** общих UI-примитивов; остальные экраны — в зонах админки и маркетинга.

**PWA**

- **Включена** стандартным **плагином PWA для Vite** и **Workbox**: манифест, иконки, скриншоты, ярлыки, стратегии offline / navigate fallback, кеширование хэшированных ассетов.
- По статическому просмотру бэкенда **не видно полноценных WebSocket-эндпоинтов**; «реалтайм» опирается на **HTTP long-poll** и **Redis pub/sub**.

**Почему так сделано с «реалтаймом».** WebSocket удобен, но требует **липких сессий**, прокси с апгрейдом, отдельного мышления про переподключение. Long-poll проще внедрить за **обычным балансировщиком HTTP**; wake через Redis позволяет **нескольким репликам API** будить ожидающий запрос на той машине, где висит соединение, без общего in-memory состояния между процессами.

**Состояние**

- **Серверное состояние** в основном через хуки **TanStack Query**; отдельного «глобального Redux» как основного слоя не выделяется.

**Почему TanStack Query в центре.** Для админки и PWA доминируют **запрос–ответ к API**: кэш, инвалидация, повтор при ошибке и дедупликация запросов даётся библиотекой из коробки. Глобальный стейт минимален: то, что не серверное (например, выбранная клиника в UI), живёт в **локальном контексте** или памяти маршрута, без тяжёлого Redux-дерева.

## 4. AI и интеграции

**Логика AI в продукте.** Внешняя LLM — **заменяемый провайдер** (OpenAI-совместимый контракт), а не зашитый вендор. Критично не «ум модели», а **границы**: что уходит наружу, в каком виде, и кто может включить передачу персональных данных. Поэтому цепочка «санитайз → HTTP-клиент» и отдельные тесты на санитайз — часть **модели угроз**, а не косметика.

**AI**

- Вызовы провайдера идут через **HTTP-клиент** к **настраиваемому OpenAI-совместимому** эндпоинту chat-completions.
- **Обёртка** прогоняет **санитайзер** по исходящему тексту до внешнего вызова; отдельный модуль санитайза и тесты к нему.
- **Крупный сервис-оркестратор** для поведения омниканал-ассистента; **реестр инструментов** в стиле бронирование / CRM / задачи.
- Админ-чат использует тот же путь построения **«безопасного клиента»**.

**RAG (retrieval)**

- **Текстовая база знаний на организацию** с поиском в границах **идентификатора организации**.
- Режимы поиска: **подстрока ILIKE (по умолчанию)**, **FTS PostgreSQL** (tsvector + GIN при включении), **гибрид**; явное **экранирование wildcards** для пользовательских фрагментов.
- В комментариях к коду отмечена **векторная** фаза как отдельное будущее развитие.

**Что RAG здесь означает на практике.** Это не обязательно «эмбеддинги + векторная БД»: в текущей фазе это **организационно изолированный текстовый корпус** и поиск по нему (подстрока или полнотекст PostgreSQL). Смысл для интегратора: **контур ответственности** — знания привязаны к организации, запросы не смешивают чужие KB; гибридный режим позволяет **подтянуть recall FTS**, а если индекс пуст — откатиться на ILIKE. Векторный этап в комментариях заявлен как **следующий шаг**, не как обязательная часть текущей поставки.

**Сторонние точки касания (неполный список)**

- Интеграция с **платёжным / эквайринговым провайдером** для контура пациента и **SaaS-платформы**, включая вебхуки и задачи сверки.
- **Telegram** для уведомлений / каналов омниканала.
- **Объектное хранилище**, совместимое с S3 API.
- Опциональное **конвертное шифрование** с **облачным KMS**.
- Интеграция **бота / капчи** (виджет класса Turnstile на вебе).
- Отправка почты по **SMTP**.
- В стеке аутентификации и тестах фигурируют потоки **OAuth**.

**Как читать блок интеграций.** Платёж и мессенджер — **денежный и коммуникационный** периметр; S3-совместимое хранилище и KMS — **данные в покое**; капча и rate limits (на бэкенде, не перечислены здесь детально) — **злоупотребления публичными эндпоинтами**. Вместе это типичный **enterprise-пластырь**: не только «фича работает», но и «можно эксплуатировать в чужом облаке с политиками».

## 5. Наблюдаемость, QA, деплой

**Логика качества.** Тесты и CI устроены **слоями**: быстрые и узкие ворота на каждый PR (линт, аудит зависимостей, выборочные сценарии), полный прогон тяжёлого дерева, отдельные **ворота критического пути** с junit-артефактом (чтобы явно видеть «зелёный минимум» для M&A), плюс проверки **не кода, а артефактов эксплуатации** (JSON дашбордов, YAML алертов) — чтобы дрифт документации и мониторинга ловился так же, как регрессия в API.

**Тесты**

- Порядка **~800** собранных кейсов **pytest** в основном дереве тестов.
- Смесь **HTTP API**, **сервисной интеграции**, **core/security**, **application/domain**, **небольшого числа браузерных E2E**, плюс **валидация артефактов** (например JSON дашбордов и YAML правил алертинга).
- В pytest есть **маркеры**: критический путь, регрессии (платежи, ПДн, чаты), security, интеграционные тесты с Redis.
- Фронт: порядка **~25** модулей unit-тестов; **несколько** спецификаций Playwright во фронтовом пакете; в CI возможны браузерные тесты против **статического preview-сервера**.

**Артефакты наблюдаемости**

- Конфигурация **Prometheus** плюс **несколько десятков** правил алертов: свежесть ERP, здоровье платежей/вебхуков, очередь outbox, биллинг платформы, всплески security, ошибки embed/RAG, сигналы злоупотреблений patient-auth, «застывший» логический бэкап и т.д.
- **Несколько JSON-дашбордов Grafana** и пример конфигурации Alertmanager.
- Внутри процесса модуль метрик объявляет **100+ инструментов Prometheus** (counter, histogram, gauge) с **нормализацией шаблонов путей** для контроля кардинальности лейблов.

**Зачем столько метрик и алертов.** В монолите узкие места сдвигаются: сегодня это очередь outbox, завтра — всплеск 5xx на бронировании. **Широкая инструментировка** даёт SRE возможность **разделить симптом и причину** без немедленного чтения кода. Нормализация путей в лейблах — осознанный приём против **взрыва кардинальности** (UUID в метке каждого запроса убьёт Prometheus). Алерты завязаны на **бизнес-смысл** (ERP, платежи, безопасность), а не только `cpu > 80%`.

**Деплой и CI**

- Стек **Docker Compose**: **PostgreSQL 16**, **Redis**, job миграций, настраиваемые теги образов бэкенда/фронта, воркеры/beat; опциональный **профиль observability** для стека метрик.
- **Два Dockerfile** (монолит API + образ со статическим SPA).
- **GitHub Actions**: несколько workflow — полные/слойные ворота тестов бэкенда, **проверка обвязки entitlement-роутов**, **аудит ORM-колонок тенанта**, **junit-ворота критического пути**, **релизные ворота по тегам версий**, опциональная **публикация в registry**, **сухая сборка образов**, **проверка ссылок в документации**, **ручной DR-restore drill**, **сканирование контейнеров**.
- **Корпоративный контур** описан отдельно: релиз в духе **Jenkins + GHCR** (детали — во внутренней CI-документации, здесь не дублируются).

**Два контура поставки — не противоречие.** Публичный SaaS-ориентированный путь (образы в общедоступном registry, ручной или теговый push из CI) соседствует с **корпоративным** (приватный registry, Jenkins). Для интегратора это сигнал: продукт **не заточен под один хостинг**, а допускает и «один VPS», и «закрытый контур с GHCR».

## Одна фраза для покупателя (по-прежнему факты, без путей)

Один развёртываемый **модульный монолит на Python** с **явными границами клиники и организации**, **десятками гранулярных прав RBAC**, **сотнями HTTP-маршрутов**, **~160 реляционными таблицами**, **outbox + блокировками БД для надёжности**, **широким использованием Celery/Redis**, **поставляемыми артефактами Prometheus/Grafana/Alertmanager** и **сотнями автотестов**, включая браузерные и проверки цепочки поставок в CI.
