## ARCH_DEV_TASKS_AI_021 — AI Task Manager и автогенерация задач

> DEV_PROMPT_TASKS_AI_021 — «AI Task Manager и автогенерация задач (TASK‑2)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль AI Task Manager’а

- По `ARCH_TASKS_NEXT.md` и `DEV_PROMPTS_NEXT.md`:
  - Tasks/Attention — единый слой сигналов и действий по доменам (Booking/ERP/CRM/Loyalty/Omnichannel).
  - AI Task Manager:
    - помогает операторам:
      - находить приоритетные задачи;
      - автоматически подсказывать/создавать задачи по событиям/паттернам;
    - **не должен** создавать шум и ломать доменные инварианты.

### 1.2. База из DEV_PROMPT_TASKS_MODEL_020

`ARCH_DEV_TASKS_MODEL_020.md` уже зафиксировал, что:

- связь `AttentionItem` ↔ `Task`:
  - явная, хранимая в БД;
  - статусы задач влияют на состояние AttentionItem;
  - есть модель статусов/приоритетов и сервисы связки.
- AI и ручные задачи используют **одни и те же** модели/сервисы/статусы.

DEV_PROMPT_TASKS_AI_021 строится поверх этого:

- добавляет **AI‑уровень анализа и генерации**;
- но не меняет базовую модель Tasks/Attention.

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_DEV_TASKS_MODEL_020.md` — фундамент Tasks↔Attention.
- `ARCH_DEV_OMNI_REGISTRY_015.md` — общий tools‑registry и AI Orchestrator.
- `ARCH_DEV_OMNI_POLICY_016.md` и `ARCH_DEV_AI_TOKENIZATION_025.md` — политика AI/ПД и токенизация.
- `ARCH_DEV_OBS_CHAINS_023.md` — наблюдаемость цепочек, включая Tasks/Attention.
- Доменные ARCH:
  - `ARCH_BOOKING_NEXT`, `ARCH_ERP_NEXT`, `ARCH_CRM_NEXT`, `ARCH_LOYALTY_NEXT`, `ARCH_OMNICHANNEL_NEXT` — источники сигналов.

## 2. Целевое состояние AI Task Manager’а

### 2.1. Жёсткие инварианты

1. **AI создаёт/обновляет задачи только через те же сервисы, что и пользователи.**
   - Никаких прямых записей в БД в обход TaskService/AttentionFeedService.
   - Используются:
     - доменные методы и API, описанные в `ARCH_DEV_TASKS_MODEL_020`.

2. **Каждая AI‑задача имеет прозрачное происхождение.**
   - В модели Task:
     - `created_by: Enum("manual", "ai", "system")`;
     - `source_attention_id: UUID | None`;
     - (опционально) `ai_reason: str`/`ai_payload: JSON` (без ПД, с токенами).

3. **AI‑логика не обходит RBAC и доменные ограничения.**
   - AI‑контекст оформлен как техническая роль/пермишен по `ARCH_DEV_SEC_RBAC_022`.
   - Любые «действующие» задачи:
     - не дают AI сделать больше, чем может человек с соответствующей ролью;
     - требуют подтверждения оператором, если так решено бизнес‑логикой.

4. **AI‑уровень управляем и наблюдаем.**
   - Владелец/менеджер может:
     - включать/выключать классы AI‑задач;
     - видеть статистику:
       - сколько задач предложил AI;
       - сколько было принято/отклонено;
       - насколько они полезны (примерно).

5. **AI‑шум минимизируется, а не переносится на людей.**
   - AI Task Manager не должен:
     - засыпать операторов множеством мелких/дубликатных задач;
   - вместо этого:
     - агрегировать сигналы;
     - предлагать осмысленные «пакеты» задач;
     - учитывать историю (что уже делалось/игнорировалось).

## 3. Архитектурный дизайн AI‑уровня

### 3.1. Основные компоненты

Предлагаемая разбивка (логические сервисы, не обязательно отдельные классы):

- `AiTaskAnalyzer`:
  - потребляет:
    - AttentionFeed (новые/открытые сигналы);
    - историю Tasks (что создано, что закрыто, что игнорируется);
    - доменные метрики (по необходимости, через OBS‑слой).
  - строит **кандидаты задач**:
    - список предложений: «что имеет смысл сделать».

- `AiTaskGenerator`:
  - на основе кандидатов:
    - решает, что именно создать в виде Tasks;
    - уважает настройки по шуму/приоритетам;
    - взаимодействует с Tools‑registry/AI Orchestrator при необходимости.

- `AiTaskSettings`:
  - пер‑клинические настройки:
    - какие классы AI‑задач разрешены;
    - пороги чувствительности/шумов;
    - флаги вроде:
      - `ai_tasks_enabled`;
      - «требуется подтверждение перед созданием задач» (human‑in‑the‑loop).

### 3.2. Потоки данных

1. **Сбор контекста:**
   - периодический или по событию процесс:
     - извлекает свежие AttentionItem’ы (например, severity high/medium);
     - извлекает историю задач по этим Attention/доменным объектам;
     - (опционально) тянет метрики из OBS‑слоя.

2. **Анализ (AiTaskAnalyzer):**
   - группирует сигналы:
     - по пациенту/врачу/клинике/типу проблемы;
   - применяет эвристики/правила (и/или LLM) для:
     - определения, есть ли смысл действия;
     - составления черновое описание задачи (title/description).

3. **Генерация (AiTaskGenerator):**
   - фильтрует кандидаты по настройкам:
     - отключённые классы задач → игнорируются;
     - превышение лимитов задач в день/на объект → объединение/отказ.
   - создаёт Tasks:
     - через TaskService;
     - с `created_by="ai"` и ссылкой на Attention/доменные сущности.

4. **Доставка и UX:**
   - задачи появляются в обычном списке Tasks;
   - по ним можно фильтровать:
     - «AI‑предложения»;
     - «требуют подтверждения» (если реализовано).

## 4. Интеграция с Omnichannel & AI‑слоем

### 4.1. AI‑оригинальные сигналы

- Помимо доменных событий (Booking/ERP/CRM/Loyalty), источником могут быть:
  - анализ диалогов Omnichannel (по `ARCH_OMNICHANNEL_NEXT`, `ARCH_DEV_OMNI_REGISTRY_015`);
  - AI‑анализ CRM/ERP‑данных.
- Эти сигналы:
  - приходят в виде AttentionItem’ов с типами:
    - `AI_CONVERSATION_RISK`, `AI_SUGGESTED_ACTION`, и т.п.;
  - уже должны проходить через:
    - `SafeAiClient` + `AiSanitizer`;
    - tokenization‑слой (`ARCH_DEV_AI_TOKENIZATION_025`).

### 4.2. Tools‑registry и повторное использование AI‑инфраструктуры

- Для собственно AI‑аналитики в Task Manager’е:
  - используется общий tools‑registry (`ARCH_DEV_OMNI_REGISTRY_015`):
    - LLM‑вызовы идут через Orchestrator;
    - запросы/ответы используют токены вместо ПД.
- AiTaskAnalyzer может быть реализован как:
  - один или несколько AI‑tools в registry:
    - например, `analyze_attention_for_tasks`;
  - вызываемый из Celery/планировщика.

## 5. Наблюдаемость, SEC/RBAC и контроль шума

### 5.1. Роли и пермишены

- По `ARCH_DEV_SEC_RBAC_022.md`:
  - вводится техническая роль/пермишен:
    - `ai.tasks.manage` (для настройки AI Task Manager’а);
    - `ai.tasks.run` (для выполнения фоновых задач).
- AI‑процессы:
  - выполняются от имени технического контекста с минимально необходимыми правами:
    - доступны только нужные слои доменов (Tasks/Attention/чтение метрик);
    - не могут напрямую изменить ERP/Booking/CRM/Loyalty без задач/человеческих действий (кроме специально оговоренных сценариев).

### 5.2. Логирование и метрики

- Логирование:
  - создание AI‑задач:
    - `task_id`, `attention_id`, `clinic_id`, тип задачи, инициатор (`created_by="ai"`), краткая причина;
  - отклонение/игнорирование кандидатов (для анализа шума);
  - изменения настроек AiTaskSettings.
- Метрики:
  - количество сгенерированных AI‑задач по типам/доменам;
  - доля задач, переведённых в `done/cancelled` против оставленных бесконечно `open`;
  - доля задач, которые операторы явно пометили как «бесполезные/спам» (если UI это позволяет).

### 5.3. Контроль шума и UX

- Бизнес‑уровнем/настройками определяется:
  - лимиты:
    - задач в день на клинику/пациента/врача по AI‑инициативам;
  - классы задач, включённые/выключенные для AI;
  - необходимость ручного подтверждения:
    - AI предлагает draft‑задачи, оператор подтверждает/отклоняет.
