## 1. Сводка: что уже есть (факт по коду)

| Область | Реализовано | Комментарий |
|--------|-------------|-------------|

| **AI** | `ai_mode` на чате + `OmnichannelAISettingsService` scope CHAT; `omnichannel_ai_orchestrator` | Границы LLM/tenant — см. `ARCH_PHASE_03_OMNI_CHAT_2026.md`. |
| **Админ API** | Список, деталь, сообщения (cursor `after`/`before`), скрытие, смена AI | Cursor на бэке есть; без догрузки «раньше» в UI оператор **не видит** полную историю при лимите — **Must:** P0-B в DEV_PROMPTS. |
| **Фронт** | `AdminOmniChatPage`: 3 колонки, фильтры, инспектор CRM/формы/AI, быстрая запись, хоткеи, polling списка **5s** | Реалтайм ленты нет (Should: SSE); VIP/оплата — **заглушки** до появления данных в API (§7.3). |

**Вывод:** ядро данных **готово** к unified inbox. Критический путь качества — **OutboundPolicy** (§3), **аудит отправки** (`sender_admin_id`), **полная история в UI** (`before` + merge), затем **SSE** и **очередь/SLA**.

## 2. Целевая стратегия (3 опоры)

1. **Conversation kernel** — один `omni_chats` на открытый диалог с контактом (см. инвариант §10); история только в `omni_messages`; канал — атрибут сообщения и правила доставки.  
2. **Channel execution layer** — адаптеры провайдеров; **исходящая политика обязательна** (§3); ретраи и идемпотентность на границе провайдера.  
3. **Agent workstation** — очередь слева, лента + composer по центре, контекст справа; обновления: **SSE** при готовности, **polling** как fallback (уже есть для списка).

## 3. OutboundPolicy — алгоритм (Must, не «магия»)

Цель: **пациент получает ответ в том канале, откуда ожидает**, если не выбран явно другой.

**Вход:** `chat_id`, тело `POST .../messages` с полями `content`, опционально `reply_channel_id` (UUID).

**Шаги:**

1. Загрузить `chat` с `business_account_id` = `current_admin.clinic_id` (иначе **404** `Chat not found`).  
2. **Явный канал:** если `reply_channel_id` задан — загрузить `OmniChannel` с `id = reply_channel_id` и `business_account_id` = clinic; если не найден или не та клиника — **400** с `detail` (не путать с 404 по чату). Проверить тип канала **допускает исходящие** (тот же критерий, что у `OmnichannelOutboundDispatcher` для данного типа); иначе **400**.  
3. **Явный канал не задан:** вычислить **default_reply_channel_id**:  
   - последнее сообщение в чате с `direction = INBOUND` и `actor_type = CLIENT`, сортировка `created_at DESC`, взять `channel_id`;  
   - если такого нет (только исходящие/AI) — взять `chat.channel_id`;  
   - если и его нет — **409 Conflict** с понятным `detail` (код стабильный, например `OMNI_REPLY_CHANNEL_UNRESOLVED`): «не определён канал для ответа; настройте канал или передайте reply_channel_id».  
4. Создать `omni_messages` с `channel_id = выбранный`, `sender_admin_id = current_admin.id` для `HUMAN_ADMIN`.  
5. Вызвать `OmnichannelOutboundDispatcher.dispatch_to_channel(msg)` с этим `channel_id`.

**Таблица HTTP (единая для API и тестов):**

| Ситуация | Код |
|----------|-----|
| Чат не найден или чужая клиника | **404** |
| `reply_channel_id` невалиден, не той клиники, или канал не исходящий | **400** |
| Нельзя вычислить канал (шаг 3, нет ни default, ни `chat.channel_id`) | **409** |
| Успех | **201** + тело `OmniMessageDto` с `channel_id` / `channel_type` / `sender_admin_id` |

**Проверка «реально работает»:** интеграционный тест в CI: два канала в одном чате (два inbound с разным `channel_id`) — ответ без `reply_channel_id` создаёт сообщение с `channel_id` последнего **CLIENT** inbound и диспатчер вызывается с ним (при необходимости mock провайдера — но разрешение канала и FK tenant обязаны быть реальными).

**OpenAPI / DTO:** обновить схемы и строчные описания ручки — @QA_ARCH проверяет соответствие §3.

## 4. Архитектура бэкенда (целевая)

### 4.1. Границы модулей

```
[Ingress webhooks] → (сегодня: существующие обработчики) → OmnichannelChatService
                                                              ↓
                                                    Message + channel_id
                                                              ↓
                                              OutboundPolicy (§3)  ← Must: выделить в один вызываемый модуль/функцию
                                                              ↓
                                         OmnichannelOutboundDispatcher
```

**Цель эволюции:** выделить **InboundPipeline** (dedup, структурные логи, correlation_id, **без `content` в INFO**) — не блокер P0, но не смешивать с OutboundPolicy в одном «комке».  
**OutboundPolicy** — один модуль с вычислением `channel_id` + валидация; вызывается только из `send_admin_omni_message` (и при необходимости из тестов).

### 4.2. Данные (эволюция)

| Изменение | Назначение | Критерий «готово» |
|-----------|------------|-------------------|
| `omni_messages.sender_admin_id` FK → admin_users | Аудит «кто отправил» | В **ответе** POST и в GET сообщений (или отдельное поле в DTO); фронт — инициалы/метка при наличии данных |
| `SendOmniMessageRequest.reply_channel_id` optional | Явный выбор канала | UI показывает канал до отправки; тело запроса и ответ согласованы с OpenAPI |
| `omni_chats.assignee_admin_id` | Очередь | **Реально:** PATCH + фильтр «мои» + отображение в списке (P1-B) |
| `first_operator_reply_at` | SLA | Предпочтительно: вычисление в отчётах по первому `HUMAN_ADMIN` после первого `CLIENT` — без лишней колонки до нагрузки |

Индексы под очередь: после появления `assignee_admin_id` — частичный индекс по `(business_account_id, assignee_admin_id, status)` (уточнить имена колонок в миграции).

### 4.3. API

- `POST /admin/omni-chats/{id}/messages` — тело: `content`, опционально `reply_channel_id`; ответ **201** с полным `OmniMessageDto` включая `channel_id`, `channel_type`, `sender_admin_id`.  
- `GET .../messages` — контракт курсора без изменений; фронт **обязан** использовать **`before`** для истории (P0-B).  
- `PATCH /admin/omni-chats/{id}` — при появлении assignee/status; **RBAC** — §5.  
- **SSE** `GET /admin/omni-chats/events` (или `/stream`): §6.

### 4.4. Наблюдаемость

- Счётчик: `omni_outbound_failures_total{channel_type}` при ошибке диспатчера (если ещё нет — добавить в рамках P0-A/P1 по возможности).  
- Латентность первого ответа оператора — отчётно позже; не блокирует P0.

## 5. Безопасность и RBAC (обязательно в реализации)

| Действие | Минимальное правило |
|----------|---------------------|
| Список/чтение чатов клиники | Через `current_admin.clinic_id` |
| Отправка сообщения | Тот же контур; **не** логировать `content` в application **INFO** (допускается маска в debug) |
| `reply_channel_id` | Строго `channel.business_account_id == clinic_id` + исходящий тип канала |
| PATCH assignee / смена статуса | Явное право; зафиксировать в `application/rbac_matrix.py` при реализации P1-B |
| SSE | Тот же JWT/cookie что и REST; **не** передавать текст сообщения в событии |

**Rate limiting (обязательный hardening после P0-A):** на `POST .../messages` — лимит с **429** и стабильным `detail` (например 30/мин на админа или политика проекта). Реализация: существующий `src/infrastructure` rate limiter, если есть; иначе — отдельная подзадача сразу после зелёных тестов P0-A (не откладывать «на потом» без записи в бэклог с датой). Цель @LEAD: снять риск злоупотребления и DoS с учётной записи.

## 6. Контракт realtime (SSE) — «Should», но конкретно

**Не галочка:** клиент после события **подгружает** актуальные данные через существующий GET, merge без дублей по `message.id`.

- Событие (JSON): `{ "type": "message.created", "chat_id": "uuid", "message_id": "uuid", "clinic_id": "uuid" }` (без `content`).  
- Клиент: `invalidateQueries` для ключа сообщений открытого чата и при необходимости список чатов.  
- Fallback: при ошибке `EventSource` — polling ленты открытого чата 10–15 с и/или кнопка «Обновить» — зафиксировать в UI.

## 7. Архитектура фронтенда

### 7.1. Слои

- **Shell** — полная высота вьюпорта, flex, `minHeight: 0`.  
- **Данные** — React Query; лента: **стабильный merge** по `message.id`, хронологический **asc**, при подгрузке `before` — не терять позицию скролла без необходимости (UX).  
- **Composer** — показывает **куда уйдёт ответ** (default по политике или выбранный `reply_channel_id`); после отправки bubble в ленте согласован с `channel_type`.

### 7.2. Что не считаем «готово»

| Фича | Не галочка |
|------|------------|
| Подгрузка истории | Оператор дочитывает **начало** треда при N > limit; нет дубликатов id при merge |
| Канал отправки | Виден **до** отправки; совпадает с лентой после ответа |
| Макросы (Could) | Шаблоны из API, вставка в поле, RBAC на список |

### 7.3. VIP / оплата

До полей в CRM/API — не включать «живые» фильтры; disabled + tooltip или скрыть (согласовано с BIZ).

## 9. Must / Should / Could (с критериями приёмки)

| Приоритет | Поставка | Критерий «реально работает» |
|-----------|----------|-----------------------------|
| **Must** | OutboundPolicy + `sender_admin_id` + DTO/OpenAPI | CI: тест двух каналов + tenant на `reply_channel_id`; UI показывает канал отправки |
| **Must** | История `before` + merge | Ручная проверка + отсутствие дублей; линтер зелёный |
| **Should** | SSE + fallback | Сообщение без F5; без PII в событии; fallback не ломает ленту |
| **Should** | assignee + PATCH + «мои» | Сохранение, фильтр, тест изоляции клиники |
| **Could** | Макросы, маршруты legacy | По DEV_PROMPTS |

**Критерий @LEAD для коммерческого обещания омника:** Must-строки закрыты **в коде и тестах**, не только в документе; строка E2E «омниканал» в `docs/LEAD_PRODUCT_GATE_PROTOCOL.md` (GATE-6, E2E-сетка) — PASS только при реальной доставке или задокументированном mock + контрактных тестах (политика проекта).

## 10. Риски и рабочие решения

| Риск | Решение / статус |
|------|------------------|
| **Несколько OPEN чатов на один контакт** | **Целевой инвариант:** не более **одного** открытого (`OPEN`/`IN_PROGRESS` — уточнить по enum в коде) чата на пару `(business_account_id, contact_id)`. Реализация: уникальный частичный индекс в БД **или** атомарная проверка в `get_or_create_chat` + тест на гонку. Если в прод-данных уже есть дубликаты — отдельная задача миграции/сверки **до** массового enterprise. |
| **Legacy `admin/chat` vs omni** | Явные подписи в `routePaths`, меню, README; не смешивать код в одном PR без задачи (см. DEV_PROMPTS P2). |
| **Нагрузка SSE** | Один поток на сессию админа, heartbeat, disconnect при unmount / уходе со страницы. |
| **Отсутствие rate limit** | Закрывается hardening сразу после P0-A (§5). |
