# QA_ARCH — критерии поиска бизнес- и логических упущений

Документ задаёт **оси** и **слои**, по которым команда (или LLM-прогон) систематически ищет разрывы между ожидаемым поведением продукта/рынка и тем, что реализовано в коде, данных и процессах.

Использование: для каждой ячейки матрицы задавать вопрос «есть ли сквозной сценарий, метрика, контракт, политика и владелец процесса?». Ответ «нет» или «только вручную/в демо» = кандидат в упущение.

---

## 1. Оси (по типу ценности)

| Ось | Вопросы-фильтры |
|-----|-----------------|
| **Выручка / монетизация** | Есть ли путь от лида до оплаты (SaaS, пациент, B2B)? Что блокирует чек? Есть ли upsell/cross-sell в продукте? |
| **Привлечение и онбординг** | Как новый арендатор/клиника попадает в систему без ручных скриптов? Есть ли self-service, SLA, письма, статусы? |
| **Удержание и доверие** | Напоминания, продление, dunning, прозрачность статусов подписки, смена владельца/плана. |
| **Операционная эффективность** | Сколько ручных шагов у саппорта/основателя? Есть ли очереди, DLQ, ретраи, runbook? |
| **Соответствие и риски** | ПДн, мед. контекст, оферта, согласия, аудит действий, хранение логов без PII. |
| **Безопасность и мошенничество** | Секреты webhook, rate limit, идемпотентность, принцип наименьших привилегий, разделение контуров A/B. |

## 2. Слои (по месту в системе)

### 2.1. Публичный маркетинг и лендинг

- Обещания в UI/копирайте vs реальные API (например: «на email придёт…» при отсутствии отправки).
- Формы без бэкенда или с частичной валидацией.
- Каталог тарифов: источник правды (БД vs статика), расхождение цен.

### 2.2. Контур саморегистрации арендатора (SaaS / B2B)

- Публичная регистрация: email/телефон, верификация, выбор плана, оплата, создание org/clinic/admin.
- Закрытая регистрация: от имени платформы (инвайт, ручное создание, импорт).
- Состояния жизненного цикла: `pending_payment` → `active` → `suspended` / `revoked` — видимость для клиента.

### 2.3. Идентичность и роли

- Разделение: платформа (founder), владелец бизнеса (owner), персонал, пациент.
- Нет ли «тихих» эквивалентов (например, все админы равны без RBAC)?
- Смена владельца, восстановление доступа, блокировка.

### 2.4. Данные и мультитенантность

- Границы tenant: `organization_id`, `clinic_id`, утечки в отчёты и кэш.
- Сущности без владельца или с дефолтами, опасными в проде.

### 2.5. Интеграции и каналы

- Внешние провайдеры (оплата, мессенджеры, email): что при неуспехе? Заглушки, stub, «первый clinic_id».
- Webhook: верификация секрета, повторная доставка, дедупликация.

### 2.6. Асинхронность и надёжность

- Outbox, Celery, DLQ: есть ли действие для оператора при `dead_letter`?
- Идемпотентность платежей и провижининга.

### 2.7. Наблюдаемость и поддержка

- Метрики/алерты по критическим воронкам (оплата, провижининг, webhook).
- Корреляция `trace_id`, аудит админских действий.

### 2.8. UX завершения сценария

- Экран после оплаты: следующий шаг (установить пароль, войти).
- Ошибки с понятным кодом для саппорта vs «что-то пошло не так».

## 3. Чек-лист «красных флагов» в коде

При просмотре репозитория искать:

- Комментарии **`MVP`**, **`stub`**, **`TODO`** на критическом пути.
- Ветки **`if not configured`** для секретов в проде (например пустой webhook secret).
- Логи вида **«deliver via secure channel»** без вызова доставки.
- **Один захардкоженный** `business_account_id` / «первый clinic» в интеграции.
- **Отсутствие** Celery-задачи / outbox-события там, где пользователю обещано письмо или пуш.
