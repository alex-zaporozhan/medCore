## ARCH_DEV_CRM_MONEY_008 — источник правды по деньгам в CRM

> DEV_PROMPT_CRM_MONEY_008 — «источник правды по деньгам в CRM (CRM‑2, ERP‑3)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль денег в CRM

- CRM‑воронка должна показывать:
  - **оценочную выручку** (сколько потенциально принесут активные лиды);
  - **фактическую выручку** (сколько денег реально дошло до ERP по завершённым визитам);
  - **маржинальность и LTV** по пациентам/клиентам/кампаниям.
- По `ARCH_CRM_NEXT.md` и `BUSINESS_PLAN_NEXT.md`:
  - CRM не должна становиться вторым контуром финансового учёта;
  - она опирается на **ERP‑слой** как единственный источник правды по деньгам.

### 1.2. Проблема (GAPS CRM‑2 / ERP‑3 / ATT‑2)

- По `BACKEND_GAPS_CRM_NEXT.md`, `BACKEND_GAPS_ERP_NEXT.md`, `BACKEND_GAPS_Attribution_NEXT.md`:
  - логика расчёта `estimated_value`/`actual_value` в CRM:
    - частично реализована локально;
    - не всегда явно связана с ERP‑узлом и отчётным слоем;
  - атрибуция ROI (`ATT‑2`) зависит от консистентности CRM‑/ERP‑данных;
  - владельческая отчётность (ERP‑3) опирается на ERP‑узел, но CRM должна читать эти же данные, а не пересчитывать их.

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_CRM_NEXT.md` — модель воронки и денег в CRM.
- `ARCH_ERP_NEXT.md` — ERP‑модель денег/обязательств.
- `ARCH_ATTRIBUTION_NEXT.md` — маркетинговая атрибуция.
- `ARCH_DEV_BKG_CORE_001.md`, `ARCH_DEV_ERP_NODE_010.md`, `ARCH_DEV_ERP_LOYALTY_011.md`, `ARCH_DEV_ERP_REPORTS_012.md`:
  - задают ERP‑узел завершения визита, связь с Loyalty и отчётный слой.
- `ARCH_DEV_CRM_EVENTS_007.md`:
  - описывает автодвижение лидов по событиям (в т.ч. завершение визита).

## 2. Целевое состояние денег в CRM

### 2.1. Жёсткие инварианты

1. **ERP — единственный источник правды по фактическим деньгам.**
   - `actual_value` в `LeadCard` и агрегаты CRM:
     - рассчитываются/обновляются на основе ERP‑данных (узел завершения визита, транзакции, отчёты);
     - не пересчитывают денежную бизнес‑логику на стороне CRM.

2. **CRM хранит оценочную выручку как «прогноз», а не как деньги.**
   - `estimated_value`:
     - может базироваться на:
       - корзине услуг/предложений;
       - тарифах/прайсе;
       - данных о предыдущих визитах;
     - но всегда размечена как оценка, не влияющая на ERP‑учёт.

3. **Связь лид ↔ визиты ↔ ERP‑транзакции однозначна.**

- Для каждого `LeadCard`:
  - известно:
    - какие `Booking`/визиты с ним связаны;
    - какие ERP‑транзакции относятся к этим визитам;
    - какую фактическую выручку/маржу они дали.

4. **CRM и владельческая отчётность показывают согласованные суммы.**
   - Данные по выручке и ROI:
     - в CRM‑воронке;
     - в отчётах ERP/Attribution;
     - должны совпадать в пределах одинаковых фильтров/периодов/клиник.

## 3. Архитектурный дизайн: связка CRM ↔ ERP ↔ Attribution

### 3.1. Модель связей

- В `LeadCard`:
  - уже есть/добавляются поля:
    - `patient_id`, `booking_id` (основной визит) или коллекция связанных визитов;
    - `estimated_value`, `actual_value`;
    - `source`, `utm_*`, `campaign_id` (для атрибуции).
- Связь с ERP:
  - через:
    - `booking_id` → ERP‑узел → `FinancialTransaction`/`ErpVisitRevenueView`;
    - дополнительные поля/таблицы, если визит разбивается на несколько транзакций.

### 3.2. Расчёт и обновление `estimated_value`

- Источники оценки:
  - прайс/услуги, выбранные на этапе лида/предварительной записи;
  - тип пакета/предложения (если лид касается пакета/абонемента).
- Логика:
  - может быть реализована в `LeadService`:
    - как отдельный метод «пересчёт оценки»;
  - важно:
    - не использовать её для построения ERP‑отчётов;
    - чётко маркировать в UI как прогноз/оценка (не факт).

### 3.3. Расчёт и обновление `actual_value`

- Триггер:
  - `LeadEventVisitCompleted` (см. `ARCH_DEV_CRM_EVENTS_007.md`);
  - с привязкой к `booking_id`.
- Процесс:
  - через `ErpVisitRevenueView` (ARCH_DEV_ERP_REPORTS_012):
    - запрашивается фактическая выручка по визиту(ам), связанным с лидом;
  - `LeadService`:
    - обновляет `actual_value` и, при необходимости, дополнительные агрегаты по лиду;
    - может хранить историю изменений (для аналитики).

### 3.4. Связь с Attribution/ROI

- Для ROI по лидам/кампаниям:
  - используются те же ERP‑представления, что и для владельческой отчётности;
  - CRM:
    - читает агрегаты по `campaign_id`/`source`;
    - отображает их в Kanban/карточках лида и отчётах.

## 4. Наблюдаемость и согласованность

### 4.1. Логирование и метрики

- При обновлении `estimated_value`/`actual_value`:
  - логируем:
    - `lead_id`, `clinic_id`, предыдущее и новое значение;
    - источник изменения (событие визита, ручная корректировка и т.п.);
    - `trace_id` (связь с цепочкой Booking→ERP→Reports).

### 4.2. Проверки согласованности

- Периодические проверки/скрипты:
  - выборка лидов, где:
    - `actual_value` в CRM отличается от суммы ERP‑транзакций по связанным визитам;
  - отчёт для владельца/админа (или внутренний мониторинг) о расхождениях.

## 6. Факт реализации v1 (зафиксировано в коде)

> Детальный чек‑лист по пунктам — в `ARCH_DEV_CRM_MONEY_008_TASKS.md` (в т.ч. раздел **«Статус реализации v1»** и **«На потом»**).

Кратко по архитектуре:

- **`actual_value`:** сумма строк `financial_transactions` с `type=income` и (`lead_id` = лид **или** `booking_id` в наборе primary + визит из события). Данные читает `ErpReportsRepository.sum_income_revenue_for_crm_lead`; обновление — `LeadService.update_actual_value_from_erp` (после визита, после `PaymentSuccess`, без дельт по сумме платежа в CRM).
- **`estimated_value`:** прогноз; авто с цены услуги по `primary_booking_id` при создании лида из записи / первом attach; ручной ввод — `PATCH /admin/crm/leads/{id}/estimated-value`.
- **События:** `BookingCompleted` публикуется **после** `session.commit()` фасада завершения визита; поле `visit_revenue` в payload не используется для CRM (deprecated).
- **Наблюдаемость:** лог `crm_lead_actual_value_from_erp`, метрики `crm_lead_actual_value_erp_*` и тесты согласованности с visit‑revenue.

Сверх первоначального списка задач (после QA): общий фильтр income в репозитории, коммит до шины, отключение дублирующей выручки в событии, UI‑подсказки по нулевому факту, обновление GAPS/DEV_PROMPT/трекера.
