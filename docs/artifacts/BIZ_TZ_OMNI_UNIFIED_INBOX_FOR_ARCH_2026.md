## 1. Продуктовая модель (обязательно учесть в архитектуре)

### 1.1. Unified inbox: «из многих — в одно»

Пациент может писать клинике **через разные мессенджеры и каналы** (Telegram-бот, виджет сайта, веб-PWA и т.д.). Для администратора **все обращения одного контакта/диалога** должны сходиться в **одно окно переписки** в админке: оператор не переключается между «отдельными приложениями каналов», а ведёт **одну нить разговора**, понимая **откуда пришло каждое сообщение** (метка канала, при необходимости — технический контекст доставки).

**Бизнес-смысл:** снижение времени ответа, отсутствие потерянных сообщений между каналами, единая история для CRM и споров («что обещали пациенту»).

### 1.2. Что не смешиваем без явного правила

- **Один бизнес-диалог** = один поток в UI, но **канал каждого сообщения** остаётся видимым в данных и UI (иконка/подпись), чтобы не путать ограничения канала (например, длина текста, вложения).
- **Разные люди** — разные диалоги; привязка к **пациенту/лиду** в правой панели — источник истины для «запись, задача, форма».

## 2. Цели и KPI (для приоритизации архитектурных решений)

| Цель | KPI (пример) | Зачем @ARCH |
|------|----------------|-------------|
| Скорость ответа | Время до первого ответа оператора (по рабочим часам) | Очереди, уведомления, деградация при нагрузке |
| Полнота контекста | % диалогов с привязанным `patient_id`/`lead_id` | Модель данных инспектора, интеграции |
| Предсказуемость канала | Доля ошибок доставки/таймаутов по каналам | Идемпотентность, ретраи, статусы |
| Удержание оператора | Среднее время на типовое действие (запись из чата) | UX-паттерны, шорткаты, модалки без ухода |

## 3. Персоны и сценарии (Must для «здорового» коммерческого чата)

### 3.1. Оператор клиники (основной пользователь)

- Видит **список диалогов** с приоритетом: неотвеченные, VIP, риски оплаты (когда есть данные).
- Открывает **один диалог** — видит **единую ленту** сообщений с **пометкой канала** на каждом сообщении или группе.
- Отвечает **в тот канал, который политика считает ответным по умолчанию** (или выбирает канал, если продукт это допускает) — **бизнес-требование: не отправлять «в никуда»**.
- Без ухода из экрана: **запись**, **задача**, **анкета/форма**, переход в CRM/расписание.

### 3.2. Руководитель / Owner

- Видит **агрегаты** по каналам и SLA (не обязательно в том же UI, но метрики должны быть согласованы с моделью событий).
- Нужна **аудит-пригодность**: кто ответил, когда, через какой канал.

### 3.3. Пациент (вне админки)

- Ожидает ответ **в том мессенджере, где написал**, если не переключён на другой канал осознанно — **бизнес-ограничение для @ARCH:** маршрутизация исходящих по каналу и консистентность с inbound.

## 4. Процессы (бизнес-правила для отражения в архитектуре)

1. **SLA-first:** диалоги с нарушением целевого времени первого ответа должны быть **визуально выделены** в списке (уже есть задел — «неотвеченные»; расширение — по таймерам SLA).
2. **Эскалация:** перевод на другого оператора / роль — **политика клиники**; в архитектуре — **учёт назначения и аудита**.
3. **Риски:** VIP и платёжные аномалии — **фильтры/бейджи** при наличии данных; не блокируют единое окно, но **меняют приоритет в списке**.
4. **Макросы и быстрые ответы** — **Could/Should** для коробки; для @ARCH — **расширяемый composer** и хранение шаблонов без жёсткой привязки к одному каналу.
5. **Теги темы диалога** — для отчётности и маршрутизации; модель — **не ломать единую ленту**.

---

## 5. Нефункциональные ожидания (коммерческий «здоровый» минимум)

- **Мультитенантность:** данные чата не пересекаются между клиниками (уже заложено в продукте — @ARCH подтверждает границы).
- **Соответствие ожиданиям enterprise:** предсказуемые состояния диалога, доставка/прочитано **по возможностям канала**, без «ложных галочек».
- **PII:** не логировать содержимое переписки в открытые логи; доступы по RBAC — согласно политике клиники.
