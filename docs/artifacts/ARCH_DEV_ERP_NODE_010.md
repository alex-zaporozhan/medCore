## ARCH_DEV_ERP_NODE_010 — ERP‑узел завершения визита

> DEV_PROMPT_ERP_NODE_010 — «оформление ERP‑узла завершения визита (ERP‑1, ERP‑3)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль ERP‑узла в цепочке

- Базовая бизнес‑цепочка (см. `ARCH_BOOKING_NEXT.md`, `ARCH_ERP_NEXT.md`, `BUSINESS_PLAN_NEXT.md`):
  - `Booking` создан → подтверждён → пациент пришёл;
  - оказаны услуги, рассчитана стоимость, выбраны источники оплаты (касса/эквайринг/пакет/депозит и т.п.);
  - визит завершается (`Booking.status → completed`);
  - ERP фиксирует:
    - **деньги** (выручка по визиту, разрезы по услугам/источникам/каналам);
    - **ЗП** (начисления исполнителям);
    - **склад** (списание материалов).
- DEV_PROMPT_BKG_CORE_001 вводит фасад завершения визита (узел Booking↔ERP↔Loyalty/CRM).  
  Этот файл фокусируется на **внутреннем ERP‑узле**, который будет вызван из фасада.

### 1.2. Проблема (GAPS ERP‑1 / ERP‑3)

- Сейчас логика движения денег/материалов:
  - частично реализована в `erp_finance`‑сервисах, частично — в других модулях;
  - не оформлена как единый «узел завершения визита»;
  - может быть размазана по нескольким вызовам / транзакциям.
- Из‑за этого:
  - сложно гарантировать консистентность между:
    - статусом `Booking`,
    - финансовыми записями (транзакции, платежи),
    - начислениями ЗП и складскими движениями;
  - отчёты (ERP‑/владельческие, CRM/Attribution) рискуют опираться на неполные/рассинхронизированные данные.

### 1.3. Связь с другими артефактами

- `ARCH_ERP_NEXT.md` — описывает домены ERP: финансы, ЗП, склад, отчётность.
- `ARCH_DEV_BKG_CORE_001.md` — фасад завершения визита, единая точка входа `BookingCompletionService`.
- `ARCH_DEV_OMNI_POLICY_016.md` / `ARCH_DEV_SEC_RBAC_022.md` — рамка безопасности и политик (RBAC, ПД/AI).
- Будущие:
  - `ARCH_DEV_ERP_LOYALTY_011.md` — обязательства по пакетам/депозитам как ERP‑объекты;
  - `ARCH_DEV_ERP_REPORTS_012.md` — владельческая ERP‑отчётность.

## 2. Целевое состояние ERP‑узла

### 2.1. Жёсткие инварианты ERP‑узла

1. **Единый вход для завершения визита в ERP.**
   - Один доменный сервис/интерфейс уровня application:
     - условно `ErpVisitNode` / `ErpBookingCompletionNode`;
     - вызывается _только_ из фасада `BookingCompletionService` (см. `ARCH_DEV_BKG_CORE_001.md`).

2. **Цельный взгляд на деньги/ЗП/склад.**
   - На вход ERP‑узел получает **агрегированный контекст визита**:
     - список оказанных услуг/позиций;
     - стоимость по каждой услуге/позиции;
     - разрез по источникам оплаты (кэш/эквайринг/пакет/депозит/discount и т.п.);
     - данные для ЗП (исполнители, доли, схемы начисления);
     - потреблённые материалы (для склада).
   - На выходе:
     - единый результат с идентификаторами созданных ERP‑объектов (транзакции, проводки, начисления, складские движения);
     - сводка для отчётности и CRM.

3. **Атомарность на уровне ERP‑инвариантов.**
   - Деньги, ЗП и склад обрабатываются **как один узел**, а не как три несвязанных вызова:
     - либо все необходимые ERP‑действия по визиту зафиксированы;
     - либо узел возвращает контролируемую ошибку, а фасад откатывает транзакцию.

4. **Минимальная публичная поверхность.**
   - Внешние (по отношению к ERP‑модулю) слои:
     - не создают напрямую ERP‑объекты (касса, проводки, начисления и т.п.);
     - всегда идут через ERP‑узел/явные сервисы ERP‑домена.

5. **Подготовка к отчётности.**
   - ERP‑узел:
     - пишет данные в структуры, достаточные для владельческих отчётов (VISIT → MONEY/PAYROLL/STOCK);
     - не строит тяжёлые агрегаты сам, но обеспечивает корректную, нормализованную базу для `DEV_PROMPT_ERP_REPORTS_012`.

### 2.2. Границы ответственности

- **ERP‑узел делает:**
  - валидацию входных данных (структура/согласованность сумм, допустимость схем начисления);
  - расчёт внутренних ERP‑объектов (движение денег/ЗП/склада);
  - запись этих объектов в БД в рамках транзакции фасада;
  - возврат результата в виде DTO.

- **ERP‑узел не делает:**
  - не управляет статусом `Booking` (это ответственность фасада Booking);
  - не пишет напрямую в CRM/Attribution (только готовит данные для них);
  - не обходит RBAC/clinic‑ограничений (работает в рамках `clinic_id`, переданного фасадом);
  - не реализует логику Loyalty (пакеты/депозиты) — только учитывает её результаты, синхронизация с Loyalty будет в `DEV_PROMPT_ERP_LOYALTY_011`.

## 3. Архитектурный дизайн ERP‑узла

### 3.1. API ERP‑узла (черновой контракт)

- Application‑слой, например `src/application/services/erp_node_service.py`:

```python
class ErpVisitNodeRequest(BaseModel):
    booking_id: UUID
    clinic_id: UUID
    visit_date: datetime
    services: list[ErpVisitServiceItem]  # услуги/позиции
    payments: list[ErpVisitPaymentItem]  # источники оплаты
    payroll_inputs: list[ErpVisitPayrollInput]  # данные для ЗП
    inventory_items: list[ErpVisitInventoryItem]  # материалы


class ErpVisitNodeResult(BaseModel):
    success: bool
    finance_ids: list[UUID] = []
    payroll_ids: list[UUID] = []
    inventory_ids: list[UUID] = []
    warnings: list[str] = []
    error_code: str | None = None
    error_message: str | None = None
```

- Сами DTO `ErpVisitServiceItem`, `ErpVisitPaymentItem`, `ErpVisitPayrollInput`, `ErpVisitInventoryItem` оформляются в:
  - `src/application/dto/erp_finance_dto.py` (и при необходимости соседних DTO‑модулях),
  - **без утечки ORM‑моделей наружу**.

- Сервис:

```python
class ErpVisitNodeService:
    async def process_visit_completion(
        self,
        request: ErpVisitNodeRequest,
        *,
        session: AsyncSession,
    ) -> ErpVisitNodeResult:
        ...
```

### 3.2. Внутренняя структура ERP‑узла

Внутри `ErpVisitNodeService` выделяем под‑сервисы/компоненты:

1. **FinanceProcessor**
   - Принимает список сервисов и платежей.
   - Создаёт/обновляет:
     - финансовые транзакции по визиту;
     - при необходимости — проводки в регистрах доходов/расходов (если такие структуры уже есть/появятся).
2. **PayrollProcessor**
   - Рассчитывает ЗП на основе `payroll_inputs`:
     - привязка исполнителей к услугам;
     - схемы начисления (процент с выручки, фикс и т.п.), определённые в ERP‑настройках.
3. **InventoryProcessor**
   - Обрабатывает список расходованных материалов:
     - списания со склада по номенклатуре/количеству;
     - контроль остатков, возможные предупреждения (низкий остаток и т.п.).

Каждый из этих компонентов:

- реализуется как отдельный класс/сервис в ERP‑слое (`erp_finance`, `payroll`, `inventory`);
- не знает о `Booking` как таковом — только о `booking_id`/`clinic_id` и бизнес‑параметрах.

### 3.3. Поток внутри `process_visit_completion`

1. Базовая валидация запроса:
   - проверка, что суммы по услугам и платежам согласованы;
   - проверка, что `clinic_id` и `booking_id` согласуются с контекстом (по данным, переданным фасадом).
2. Вызов `FinanceProcessor`:
   - создание/обновление основных финансовых объектов;
   - сбор идентификаторов и предупреждений.
3. Вызов `PayrollProcessor`:
   - расчёт и запись начислений;
   - сбор идентификаторов и предупреждений.
4. Вызов `InventoryProcessor`:
   - списания со склада;
   - сбор идентификаторов и предупреждений.
5. Формирование `ErpVisitNodeResult`:
   - если один из под‑процессоров вернул критичную ошибку:
     - помечаем `success=False`, выставляем `error_code`/`error_message`;
     - фасад завершения визита откатывает транзакцию на своём уровне.
   - если всё прошло, но есть неблокирующие предупреждения (например, низкий остаток склада):
     - `success=True`, но `warnings` заполняются для Attention/Tasks и оператора.

## 4. Изменения в слоях ERP‑домена

### 4.1. Application‑слой

- Ввести новый сервис:
  - `ErpVisitNodeService` (или аналогичное название);
  - определяющий публичный контракт ERP‑узла для `BookingCompletionService`.
- Перенести/нормализовать существующую разрозненную логику:
  - из `erp_finance_service.py` и других ERP‑сервисов;
  - в Finance/Payroll/Inventory‑подкомпоненты, вызываемые через `ErpVisitNodeService`.

### 4.2. Domain/infra‑слой

- Убедиться, что:
  - сущности ERP (транзакции, начисления, складские движения) оформлены так, чтобы:
    - можно было однозначно связать их с `booking_id` и `clinic_id`;
    - по ним можно строить владельческую отчётность (в будущем `DEV_PROMPT_ERP_REPORTS_012`).
- При необходимости:
  - добавить недостающие поля/связи (например, `booking_id` или ссылку на «визит»);
  - ввести дополнительные доменные сущности/таблицы, не забивая логикой отчётов текущие таблицы платежей.

## 5. Наблюдаемость и ошибки ERP‑узла

### 5.1. Логирование

- В `ErpVisitNodeService`:
  - логировать:
    - `booking_id`, `clinic_id`;
    - суммы по визиту (агрегировано, без ПД пациента);
    - факт создания/обновления ключевых ERP‑объектов;
    - ошибки и предупреждения под‑процессоров.

### 5.2. Attention/Tasks

- При критичных ошибках:
  - формировать `AttentionItem`/`Task` типа `ERP_VISIT_FAILURE` (совместно с `DEV_PROMPT_TASKS_MODEL_020`);
  - включать:
    - ссылку на `booking_id`, `clinic_id`;
    - краткое описание причины (например, `ERP_FINANCE_WRITE_ERROR`, `ERP_PAYROLL_MISMATCH`).
- При неблокирующих предупреждениях:
  - либо включать их в тот же Attention‑поток (с меньшей критичностью),
  - либо логировать как метрики/варнинги для последующего анализа.

### 5.3. Метрики

- Базовые метрики ERP‑узла:
  - количество вызовов `process_visit_completion`;
  - доля успешных/ошибочных вызовов;
  - распределение ошибок по типам (finance/payroll/inventory/validation);
  - время выполнения узла;
  - при необходимости — разрезы по клиникам.
