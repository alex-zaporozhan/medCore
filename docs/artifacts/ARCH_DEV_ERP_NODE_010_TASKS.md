## ARCH_DEV_ERP_NODE_010_TASKS — сверх‑детализированные dev‑таски

### 1. Understand — где сейчас живёт ERP‑логика завершения визита

1.1. **Собрать места, где создаются/обновляются ERP‑объекты по визиту.**  
1.1.1. В модулях ERP (финансы, ЗП, склад — например, `erp_finance_service.py`, payroll/inventory‑сервисы) найти операции, явно связанные с визитом/`booking_id`.  
1.1.2. Выписать, какие сущности создаются/обновляются при завершении визита: финансовые транзакции, начисления ЗП, складские движения.

1.2. **Понять, как эти операции связаны с `Booking.status → completed`.**  
1.2.1. Сопоставить найденные ERP‑операции с контекстом фасада `BookingCompletionService` (см. `ARCH_DEV_BKG_CORE_001.md` и реализацию по `ARCH_DEV_BKG_CORE_001_TASKS.md`).  
1.2.2. Определить, какие ERP‑вызовы уже идут через фасад, а какие выполняются «в обход» (из других сервисов/эндпоинтов).

1.3. **Сопоставить с GAPS.**  
1.3.1. Открыть `BACKEND_GAPS_ERP_NEXT.md` (ERP‑1, ERP‑3), `BACKEND_GAPS_Booking_NEXT.md` (в части завершения визита) и `NONFUNCTIONAL_AUDIT_NEXT.md` (PERF‑2, OBS‑1).  
1.3.2. Для каждого gap указать, какие найденные участки ERP‑кода к нему относятся, и какие будут перекрыты формированием ERP‑узла.

### 2. Design‑to‑code — DTO и каркас ERP‑узла

2.1. **Оформить DTO входа/выхода ERP‑узла.**  
2.1.1. В `src/application/dto/erp_finance_dto.py` (или близком DTO‑модуле):  
       - создать `ErpVisitNodeRequest` и `ErpVisitNodeResult` по образцу из `ARCH_DEV_ERP_NODE_010.md`;  
       - создать вспомогательные DTO: `ErpVisitServiceItem`, `ErpVisitPaymentItem`, `ErpVisitPayrollInput`, `ErpVisitInventoryItem`.  
2.1.2. Убедиться, что DTO не содержат ORM‑модели и оперируют только агрегированными данными визита.

2.2. **Объявить интерфейс `ErpVisitNodeService`.**  
2.2.1. В application‑слое (например, `src/application/services/erp_node_service.py`) объявить класс `ErpVisitNodeService` с методом  
       `process_visit_completion(request: ErpVisitNodeRequest, session: AsyncSession) -> ErpVisitNodeResult`.  
2.2.2. Пока реализовать метод как заглушку/скелет (без логики Finance/Payroll/Inventory), но с базовой структурой результата.

2.3. **Спроектировать внутренние под‑процессоры.**  
2.3.1. На уровне дизайна (комментарии/архитектурный раздел в коде) разложить `ErpVisitNodeService` на 3 компонента:  
       - `FinanceProcessor` (деньги),  
       - `PayrollProcessor` (ЗП),  
       - `InventoryProcessor` (склад).  
2.3.2. Определить их интерфейсы (методы/параметры), не реализуя пока детально бизнес‑логику.

### 3. Implement — реализация ERP‑узла (Finance/Payroll/Inventory)

3.1. **Реализовать базовый поток `process_visit_completion`.**  
3.1.1. В `ErpVisitNodeService.process_visit_completion` реализовать шаги:  
       - базовая валидация структуры `ErpVisitNodeRequest` (согласованность сумм, наличие `clinic_id`, `booking_id`);  
       - инициализация/вызов внутренних процессоров (пока можно часть из них реализовать шаг за шагом);  
       - сбор результатов и предупреждений;  
       - формирование `ErpVisitNodeResult` (success/warnings/error_code/error_message).

3.2. **Реализовать FinanceProcessor.**  
3.2.1. В ERP‑слое (например, модуль финансовых сервисов) создать `FinanceProcessor`, который:  
       - принимает список услуг/позиций и платежей (`ErpVisitServiceItem`, `ErpVisitPaymentItem`);  
       - создаёт/обновляет финансовые записи по визиту (транзакции, проводки и т.п.);  
       - возвращает список идентификаторов финансовых объектов и, при необходимости, варнинги.  
3.2.2. Перенести существующую логику проведения денег из текущих ERP‑сервисов в этот процессор, минимизируя дублирование.

3.3. **Реализовать PayrollProcessor.**  
3.3.1. В ERP‑слое создать `PayrollProcessor`, который:  
       - принимает `ErpVisitPayrollInput` (исполнители, услуги, схемы начисления);  
       - рассчитывает суммы ЗП в соответствии с действующими правилами;  
       - создаёт/обновляет записи начислений в БД.  
3.3.2. Перенести текущую логику начисления ЗП по визиту в этот процессор.

3.4. **Реализовать InventoryProcessor.**  
3.4.1. В ERP‑слое создать `InventoryProcessor`, который:  
       - принимает `ErpVisitInventoryItem` (материалы, количество);  
       - выполняет списания со склада, обновляет остатки;  
       - формирует предупреждения (например, низкий остаток).  
3.4.2. Перенести текущую логику списания расходников по визиту в этот процессор.

### 4. Integrate — связать ERP‑узел с фасадом и доменной моделью

4.1. **Связать `ErpVisitNodeService` с `BookingCompletionService`.**  
4.1.1. В `BookingCompletionService.complete_visit` (фасад завершения визита):  
       - на основе текущего `Booking` и связанных данных (услуги, платежи, исполнители, расходники) сформировать `ErpVisitNodeRequest`;  
       - вызвать `ErpVisitNodeService.process_visit_completion(request, session)`;  
       - обработать `ErpVisitNodeResult` (success/ошибка/варнинги).  
4.1.2. Убедиться, что ERP‑узел вызывается именно из фасада, а не напрямую из роутеров или других доменов.

4.2. **Дооформить привязки ERP‑сущностей к визиту.**  
4.2.1. Проверить ERP‑сущности (финансовые, ЗП, склад) на наличие `booking_id` и `clinic_id`.  
4.2.2. При необходимости добавить недостающие поля/связи, чтобы:  
       - можно было однозначно связать записи с конкретным визитом;  
       - в будущем строить владельческую отчётность (ERP‑узел → отчёты).  
4.2.3. Убедиться, что изменения не ломают существующие сценарии чтения/отчётности (миграции/дефолты продумать отдельно, если нужны).

5.1.2. При ошибках/исключениях фиксировать `error_code`/`error_message` на уровне ERP‑узла (без ПД пациента).

5.2. **Интегрировать критичные ошибки с Tasks/Attention.**

5.2.2. Для неблокирующих варнингов (например, низкий остаток склада) — либо логировать их как варнинги, либо создавать Attention с низким приоритетом.

5.3. **Добавить метрики ERP‑узла.**

## 7. Будущие улучшения ERP‑узла («на потом»)

> Эти пункты выходят за рамки базовой реализации DEV_PROMPT_ERP_NODE_010, но логично продолжают развитие ERP‑узла и должны быть вынесены в отдельные DEV‑таски.

1. **Выделить реальные Finance/Payroll/Inventory‑процессоры.**
   - Вынести из `BookingErpService` отдельные реализации:
     - `FinanceProcessorImpl` (оборачивает `FinanceService`),
     - `PayrollProcessorImpl` (оборачивает `PayrollService`),
     - `InventoryProcessorImpl` (оборачивает `InventoryService`).
   - Переписать `ErpVisitNodeService` так, чтобы он:
     - больше не вызывал напрямую `BookingErpService`, а работал только через процессоры;
     - собирал агрегированный контекст визита в DTO (`ErpVisitServiceItem`, `ErpVisitPaymentItem`, `ErpVisitPayrollInput`, `ErpVisitInventoryItem`);
     - вызывал процессоры и собирал реальные `finance_ids` / `payroll_ids` / `inventory_ids`.

2. **Обогатить `ErpVisitNodeRequest` фактическими данными визита.**
   - В `BookingCompletionService` добавить полноценную сборку:
     - списка услуг/позиций и их стоимости;
     - фактических платежей по визиту (кэш/эквайринг/пакеты/депозиты/скидки);
     - исполнителей и их ролей для ЗП;
     - расходников и складских данных.
   - Передавать эти данные в ERP‑узел через `ErpVisitNodeRequest`, чтобы узел работал не только по `booking_id`, а на полном контексте визита.

3. **Усилить валидацию внутри ERP‑узла.**
   - Реализовать проверки:
     - согласованности сумм между услугами и платежами;
     - допустимости схем начисления ЗП;
     - непротиворечивости `clinic_id`/`booking_id` с контекстом фасада.
   - Ввести отдельный класс ошибок в `ErpVisitNodeResult` с кодами `VALIDATION_*` и обработкой их на уровне фасада (без фиксации `Booking.completed`), отличая валидационные ошибки от конфигурационных/технических.

4. **Ввести специфичный тип Attention‑элемента для ERP‑узла.**
   - Добавить `kind="erp_visit_failure"` (или аналогичный) в `AttentionItemRead`.
   - Явно маппить `booking.erp_error_code` и ошибки ERP‑узла на подтипы:
     - `ERP_FINANCE_*`, `ERP_PAYROLL_*`, `ERP_INVENTORY_*`, `ERP_VALIDATION_*`.
   - Использовать эти типы в `AttentionFeedService` и `TaskService` для приоритизации и фильтрации проблемных визитов, сохраняя в описании задачи краткое объяснение проблемы без ПДн.

5. **Разнести visit‑DTO по модулям.**
   - Финансовые структуры (`ErpVisitServiceItem`, `ErpVisitPaymentItem`) — оставить в `erp_finance_dto.py`.
   - Payroll‑структуры (`ErpVisitPayrollInput`) — перенести в `erp_payroll_dto.py`.
   - Inventory‑структуры (`ErpVisitInventoryItem`) — перенести в `erp_inventory_dto.py`.
   - Сделать `ErpVisitNodeRequest`/`ErpVisitNodeResult` тонким агрегатором, импортирующим эти типы.

6. **Расширить тестовое покрытие ERP‑узла.**
   - Добавить интеграционные тесты с реальной БД для `ErpVisitNodeService`:
     - успешное завершение визита с деньгами/ЗП/складом;
     - негативные сценарии по каждому домену (нет кассы, нет payroll‑политики, нет склада, недостаток остатков склада и т.п.).
   - Проверить сквозные инварианты:
     - корректная запись `booking.erp_error_code`;
     - отсутствие перехода `Booking.status` в `completed` при `ErpVisitNodeResult.success=False`;
     - наличие релевантных Attention/Tasks и метрик.
