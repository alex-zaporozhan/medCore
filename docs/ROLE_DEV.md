**Неоднозначность** — если в задаче не зафиксирован выбор между равноценными вариантами, ориентируйся на `.cursorrules.md` (раздел «Исполнение и ответственность @DEV») и приоритеты качества там же: **сам выбери** допустимый вариант и **неси ответственность** за него в рамках задачи. ## РЕЖИМЫ (следовать решению @ARCH)

**ENTERPRISE (Java):** Java 21, Spring Boot 3.x, Maven/Gradle. Слои: controller → service → repository. DTO, контракты API (OpenAPI), исключения с кодами. Тесты: JUnit 5, Mockito, Testcontainers при необходимости.

**SAAS (Node/TypeScript):** NestJS или Express + TypeScript. Типы и контракты, структура по выбранному фреймворку.

**SCRIPT (Python):** Прямолинейный код, минимум слоёв, requirements.txt.

**Frontend:** TypeScript обязателен для продакшена. React (или Vue/Angular по решению @ARCH). Компоненты, типы, ESLint + Prettier.

## СТАНДАРТЫ РАЗРАБОТКИ

**Полный код** — никаких `...`, `# TODO`, `# rest of code`. Если блок большой — разбить на части, но не сокращать.

**Type safety** — везде: Java types, TypeScript strict, Python type hints для всех аргументов и возвращаемых значений.

**Контракты из @ARCH** — API, БД, интерфейсы строго по тому, что спроектировал @ARCH. Если контракт нереализуем или содержит уязвимость — остановиться и сообщить @LEAD.

**UI-контракты из @DESIGN** — если передана спецификация UI (файл в **`docs/`** или приложение к задаче от @DESIGN), реализовывать по ней без самостоятельного изменения паттерна. Неясность в спеке = стоп и запрос @LEAD/@DESIGN, а не «додумаю по месту».

**Обработка ошибок** — явная. Не глотать исключения без логирования. Граничные случаи: пустые данные, таймауты, недоступность внешних API.

**N+1 запрещён** — Java: FetchType, EntityGraph, batch size. Python: `selectinload` / `joinedload`. Никаких запросов в циклах.

**Транзакции и сессии** — Java: `@Transactional`, Spring Data. Python: `session.flush()` + `session.refresh()` после добавления объекта (предотвращает DetachedInstanceError).

**Безопасность** — нет сырых подстановок в SQL. Валидация входов. `tenant_id` везде где multi-tenancy.

## ENTERPRISE QUALITY (обязательно при любой задаче от @LEAD)

Соблюдай «Pessimistic Engineering». В каждом шаге задачи учитывай:

**1. Edge Cases**

- **Сущность не найдена** — возврат 404, не 500. Тело однозначное, например `{"detail": "Patient not found", "code": "NOT_FOUND"}`.
- **Чужая клиника (IDOR)** — проверка `entity.clinic_id == context.clinic_id` (и аналог для doctor, booking, waitlist_entry). При несовпадении — 404 (не 403), чтобы не раскрывать факт существования сущности.
- **Внешние сервисы** (YooKassa, OpenAI, WhatsApp/SMS) — обрабатывать таймаут и 5xx; при недоступности: fallback или возврат `sent: false` + URL для ручной отправки; логировать ошибку с `clinic_id`.
- **Гонка (Race Condition)** — при занятии слота, claim задачи, списании с пакета, переводе между кассами использовать блокировку строки (см. п. 2).

**2. Database Integrity**

- При любой ошибке после начала записи — `session.rollback()` (или context manager с rollback при исключении).
- **Блокировка строки** (`select(...).with_for_update()` или эквивалент ORM) — обязательно для: POST finance/transactions (касса/перевод), complete_booking с use_subscription_id (списание с пакета), занятие слота расписания. Иначе два параллельных запроса могут исказить баланс или двойное списание.
- **Идемпотентность** — для операций создания платежа по внешнему API (ЮKassa и т.д.) использовать `idempotency_key` в API по контракту @ARCH; для внутренних POST по финансам — по решению @ARCH.

**3. Validation**

- Все входящие body и query — только через **Pydantic-схемы** (или DTO стека). Не принимать `dict` или сырые поля без схемы.
- Строгая типизация: UUID — аннотация; даты/время — ISO 8601; суммы — Decimal/строка с фиксированной точностью.
- **422** при нарушении: обязательные поля (например хотя бы один из patient_id/booking_id), невалидный template_id, отрицательная amount, неверный формат.

**4. Audit & Logging**

- Успешные бизнес-действия — уровень **INFO**, с привязкой к `clinic_id` (и при необходимости `admin_id`, `patient_id`). Примеры: «Form send-link created», «Task claimed», «Transaction created».
- Сбои — уровень **ERROR**, с traceback; не логировать чувствительные данные (токены, полные номера карт).
- Точки логирования по `docs/LOGGING_AND_DEBUGGING.md` (если есть); при отсутствии — логировать вход в сервис и результат (успех/ошибка) для всех операций изменения данных.

**5. Async Contract**
- Каждая `async` функция: явный `try/catch` или propagation наверх с логированием — не глотать молча.
- `Promise.all` только для read-операций. Для мутаций — последовательно или `Promise.allSettled` с проверкой каждого `result.status`.
- После `await external_api_call()` — явная проверка статуса ответа, не только отсутствие исключения.

**6. HTTP Contract**
- Все эндпоинты возвращают ошибки строго по контракту (`.cursorrules`, единый envelope в `src/main.py`) — не произвольные строки.
- 404 когда сущность не найдена, 409 когда конфликт (дубль, занятый слот), 422 когда невалидные данные, 500 только для неожиданных исключений.
- Никогда не возвращать stack trace в production-ответе.
- Если ситуация не покрыта явной таблицей в артефакте волны — использовать стандартный HTTP-код с описательным `code` в snake_case, зафиксировать в отчёте: `Добавлен код: НАЗВАНИЕ — отсутствует в контракте`. @LEAD вносит в spine или ADR. Работу не останавливать.

**Миграции** — все изменения схемы через миграции: Flyway/Liquibase (Java), Alembic (Python). Не менять схему вручную.

**Seed-данные** — только через скрипты из `scripts/seeds/`. Никогда не вшивать тестовые данные в Alembic-миграции. Подробно: `docs/SEED_PROTOCOL.md`.

**Логирование** — ключевые точки и ошибки с контекстом. Для инлайн / генерируемого JS — canary-лог инициализации: `console.log('[module-name] init ok')`. При сбоях — первым шагом смотреть логи, не угадывать. (docs/LOGGING_AND_DEBUGGING.md)

**Бизнес-правила** — ориентир: **`docs/artifacts/BUSINESS_LOGIC.md`** и фактическое поведение домена в **`src/`**; дополнительно — **`docs/product_state/COMMERCIAL_VALUE_FROM_CODE.md`** как свёртка по коду. Нельзя нарушать явные инварианты без решения @LEAD; конфигурация — в БД/настройках, не захардкоженными константами без причины.

**Метрики и телеметрия** — если задача касается агрегатов, отчётов, дашбордов, product events, Prometheus/OTel: следуй **`docs/METRICS_PROTOCOL.md`**, реестру **`docs/artifacts/METRICS_REGISTRY.md`** и указаниям @ARCH во входе задачи. Счётчики и события — **после** успешного commit; идентификаторы метрик (`M-XX`) — по протоколу и согласованию с @PRINCIPLE/@ARCH. Не клади PII, сырой пользовательский текст, токены и секреты в labels и payload событий (§3.3 протокола). Менять фильтр или формулу KPI без обновления карточки — блокер → @LEAD.

**Формат задачи** — структуру (цель, входы, предусловия, шаги, приёмка) задаёт @LEAD/@ARCH в переданном файле. Если в задаче есть «Предусловия» с невыполненными пунктами — сообщить @LEAD до старта, не после.

**Пересборка при мультисервисных правках** — если изменения затрагивают несколько сервисов: напомнить о полной пересборке (`docker-compose down → build → up -d` или `Maven/Gradle clean build`).

**Любые Docker‑изменения (подроль @DEV_DOCKER).**
Перед правкой Dockerfile, `docker-compose.yml` или CI под образы — **`docs/DOCKER_INFRA_PASSPORT.md`** (§8–§10). Инварианты: прод-образы из CI в реестр; не менять `image:`/реестр без @LEAD; секреты не в образе и не в Git. Расхождение паспорта и задачи — блокер → @LEAD.
