# ARCH: Платёжные кассы (payment gateways) — поля, одна vs несколько

> Как устроена страница «Касса» (/admin/payment-gateway), какие поля нужны для популярных касс в РФ и в мире, одна касса или несколько.

---

## 1. Одна касса или несколько

**По закону (РФ):** для онлайн-оплаты можно использовать несколько платёжных агрегаторов (ЮKassa, Тинькофф, Сбер и т.д.). Ограничение не «одна касса на юрлицо», а то, что каждый платёж идёт через выбранный в момент оплаты провайдер; фискализация (54-ФЗ) обеспечивается самим агрегатором. То есть **несколько касс одновременно — допустимо** (например, ЮKassa для карт + другой для СБП).

**В продукте сейчас:** у клиники одно поле `payment_gateway` (enum: yookassa | sber | tinkoff | custom) и **одна активная касса** для потока предоплаты: все создания платежей идут через выбранный шлюз (сейчас реализован только ЮKassa). То есть **активна всегда одна касса** для данного сценария (предоплата при записи).

**Расширение «несколько касс»:** можно сделать так: клиника настраивает **несколько** платёжных шлюзов (список с credentials), а при создании платежа выбирается один — например, «касса по умолчанию» или выбор по способу оплаты (карта / СБП / и т.д.). Это уже доработка: отдельная модель/таблица или JSON с массивом настроек касс + поле «касса по умолчанию». В текущей версии оставляем **одну активную кассу** на клинику; в настройках она **видна и выбираема** (выпадающий список или карточки касс с переключателем «использовать по умолчанию»).

**Итог:** юридически можно несколько; в интерфейсе можно показывать список популярных касс и дать возможность **выбрать одну активную** (как сейчас). Позже — добавить хранение нескольких настроенных касс и выбор одной как активной для предоплаты.

## 2. Источники истины по полям

- **Бэкенд:** какие поля клиники и DTO используются для оплаты (сейчас: `payment_gateway`, `yookassa_shop_id`, `yookassa_secret_key_encrypted`). Новый провайдер = новые поля в клинике или отдельная таблица `clinic_payment_gateways` с JSON credentials.
- **Официальная документация** каждого провайдера — единственный источник «100%» набора полей (см. раздел 3).

## 3. Популярные кассы — поля и описания

Ниже поля, которые реально требуются API провайдеров для приёма платежей (create payment, get status). Список можно вынести в DEV-промпт и в подсказки на странице «Касса».

### 3.1. ЮKassa (РФ)

- **Документация:** https://yookassa.ru/developers
- **Поля:** `shop_id` (идентификатор магазина), `secret_key` (секретный ключ).
- **Где брать:** Личный кабинет ЮKassa → Настройки → Идентификатор магазина и Секретный ключ.

### 3.2. Тинькофф (РФ) — Tinkoff Pay / Tinkoff EACQ

- **Документация:** https://www.tinkoff.ru/kassa/dev/payments/
- **Поля:** `terminal_key` (идентификатор терминала), `password` (пароль от терминала; выдаётся в ЛК).
- **Примечание:** для приёма платежей на сайте обычно используется EACQ API (payment form или REST).

### 3.3. Сбербанк (РФ) — SberPay / Sberbank Business API

- **Документация:** зависит от продукта (SberPay, эквайринг и т.д.); обычно: `userName`, `password` (логин/пароль API) и часто `token` или отдельные ключи для сценария.
- **Поля (типовые):** логин (userName), пароль (password); для части сценариев — merchant_id, api_key. Точный набор — по выбранному API в документации Сбербанка.

### 3.4. Robokassa (РФ)

- **Документация:** https://docs.robokassa.ru/
- **Поля:** `merchant_login`, `password1` (пароль #1), `password2` (пароль #2 для проверки результата). Опционально: тестовый режим (отдельный пароль).

### 3.5. Stripe (мир)

- **Документация:** https://stripe.com/docs/api
- **Поля:** `secret_key` (Secret key из Dashboard), опционально `publishable_key` (для клиентской формы). Для серверного создания платежей достаточно Secret key.

### 3.6. PayPal (мир)

- **Документация:** https://developer.paypal.com/docs/api/overview/
- **Поля:** `client_id`, `client_secret` (из приложения в PayPal Developer Dashboard). Для production — Live, для тестов — Sandbox.

### 3.7. Своя / Custom

- Только человекочитаемое **название** (например, «PayPal», «Своя интеграция») без сохранения ключей в системе; оплата ведётся вне продукта.

## 4. Текущая реализация и куда расширять

- **Сейчас:** страница «Касса» — выбор одной платёжной системы (Select) и блок полей только для ЮKassa (Shop ID, Секретный ключ). Сбер/Тинькофф в списке, но полей и бэкенда нет.
- **Цель:** для каждой кассы из списка показывать **все нужные поля** с подсказками (description), как на странице омниканальных каналов; активная касса — одна (выбранная). При добавлении нового провайдера: поля на фронте + бэкенд (хранение credentials, вызов соответствующего клиента в `PaymentService`).

Детальные тексты подсказок и placeholder’ы для полей — в `DEV_PROMPTS_PAYMENT_GATEWAYS.md`.

## 5. Архитектура хранения credentials платёжных касс

### 5.1. Принципы

- **Одна активная касса на клинику** остаётся как сейчас: поле `clinics.payment_gateway` (`yookassa` / `sber` / `tinkoff` / `robokassa` / `stripe` / `paypal` / `custom`).
- **ЮKassa** уже хранится на уровне клиники полями:
  - `clinics.yookassa_shop_id`
  - `clinics.yookassa_secret_key_encrypted`
  и используется напрямую в `PaymentService` через `_yookassa_client_for_clinic`.
- Для остальных провайдеров (и полей «Идентификатор» / «Ключ» для `custom`) нужно хранить credentials в **зашифрованном виде**, с возможностью расширения под несколько касс в будущем.
- Набор полей по провайдеру **определяется фронтом** (страница «Касса») + реализацией клиента в `PaymentService` (по аналогии с омниканалами).

### 5.2. Выбранная схема хранения (этап 1)

Этап 1 решает задачу: **хранить credentials для одной активной кассы на клинику**, без реализации create payment для новых провайдеров (только хранение и последующее чтение из одного места, когда появится интеграция).

Новая сущность:

- Таблица `clinic_payment_gateways`:
  - `id` (UUID, PK)
  - `clinic_id` (FK → `clinics.id`, indexed)
  - `gateway` (String(32)) — код кассы (`yookassa`, `tinkoff`, `sber`, `robokassa`, `stripe`, `paypal`, `custom`)
  - `credentials_encrypted` (Text, nullable) — зашифрованная JSON-строка с полями по провайдеру
  - `status` (String(32), default `PENDING`) — для health-check (PENDING / OK / ERROR / REVOKED и т.п., по аналогии с omni-интеграциями)
  - `created_at`, `updated_at` (timestamps с server_default / onupdate)
  - опционально: `created_by`, `updated_by` (UUID администратора), для аудита
- Уникальный ключ: `(clinic_id, gateway)` — на клинику не более одной записи на конкретный тип кассы.

Шифрование:

- Использовать те же утилиты, что и для ЮKassa и omni-интеграций: `encrypt_plaintext` / `decrypt_ciphertext` из `src.core.encryption`.
- В таблице хранится **только зашифрованная строка** с JSON; структура JSON определяется фронтом и описана в DEV-промпте.

### 5.3. API-контракт (этап 1)

Добавляется отдельный админский endpoint (аналог owner-омни-credentials):

- `POST /v1/admin/clinics/{clinic_id}/payment-gateway/credentials`
  - **Кто вызывает:** админ из `/admin/payment-gateway` (текущая страница «Касса»).
  - **Тело запроса:**
    - `gateway` — строка, совпадает с `clinics.payment_gateway` (например, `"tinkoff"`, `"sber"`, `"robokassa"`, `"stripe"`, `"paypal"`, `"custom"`).
    - `payload` — строка, результат `JSON.stringify` объекта с полями по провайдеру (см. DEV-промпт).
  - **Поведение:**
    - По `(clinic_id, gateway)` ищется/создаётся запись в `clinic_payment_gateways`.
    - `payload` шифруется и кладётся в `credentials_encrypted`.
    - `status` переводится в `PENDING` (до прохождения health-check, который появится позже).
    - Возвращается `204 No Content` при успехе.
  - **Безопасность:**
    - Только админ текущей клиники (как и другие admin-роуты).
    - Сырые credentials не отдаются наружу; дальнейшее чтение будет только из бэкенд-сервисов (например, будущий `TinkoffClient`, `SberClient` и т.д.).

На этом этапе **`PaymentService` продолжает работать только с ЮKassa** и не использует `clinic_payment_gateways`. Как только появится реализация других провайдеров, она будет читать credentials **только из этой таблицы**, не добавляя новых колонок в `clinics`.

### 5.4. Структура JSON `payload` по провайдерам (guideline для DEV-промпта)

Фронт при сохранении формирует объект по активной кассе и сериализует его в строку:

- `yookassa` — **пока не используем** новый сторедж (остаёмся на полях клиники):
  - хранение shop_id / secret_key остаётся в `clinics.yookassa_*`, чтобы не ломать существующий код.
- `tinkoff`:
  - `terminal_key`
  - `password`
- `sber`:
  - `userName`
  - `password`
- `robokassa`:
  - `merchant_login`
  - `password1`
  - `password2`
- `stripe`:
  - `secret_key`
  - `publishable_key` (опционально)
- `paypal`:
  - `client_id`
  - `client_secret`
- `custom`:
  - `identifier` — произвольный идентификатор/логин
  - `key` — секретный ключ/пароль

Имена ключей синхронизируются с DEV-промптом и кодом будущих клиентов платёжных систем.

### 5.5. Будущее расширение: несколько касс на клинику

Текущая архитектура допускает расширение до **нескольких настроенных касс**:

- `clinic_payment_gateways` уже поддерживает несколько строк на клинику с разными `gateway`.
- Можно будет:
  - хранить в таблице все подключенные кассы (ЮKassa, Тинькофф, Сбер и т.д.);
  - добавить в `clinics` поле `default_payment_gateway_id` или использовать текущее `payment_gateway` как «тип по умолчанию»;
  - в `PaymentService.create_payment` выбирать клиента по полю `gateway_id`/типу и credentials из `clinic_payment_gateways`.

Эти изменения — отдельный этап (отдельный DEV-промпт), после стабилизации хранения credentials для одной активной кассы.
