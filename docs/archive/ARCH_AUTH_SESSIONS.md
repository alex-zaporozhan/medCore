## ARCH_AUTH_SESSIONS — политика сессий и токенов (пациент/админ)

Основание: `ARCH_HARDENING_ROADMAP.md` (раздел 3), текущая реализация `src/core/security.py`, `src/application/services/auth_service.py`, `src/api/v1/routers/admin_auth.py`, фронтовый клиент `frontend/src/api/client.ts`.

**Цель:** зафиксировать единую модель сессий и токенов для ролей *пациент* и *админ*, описать политику TTL и текущее поведение при login/logout/смене пароля/увольнении, а также зафиксировать паттерн будущего отзыва токенов (token version / blacklist) без обязательства немедленной реализации.

---

## 1. Модель идентичности и клеймы токена

### 1.1. Общие принципы

- Используем **один тип токена — access‑token** формата JWT (HS256), без refresh‑токена на текущем уровне.
- JWT хранится **на клиенте**:
  - пациент — в `localStorage` (ключи `dental_booking_patient_token`, `dental_booking_patient_id`);
  - админ — в `localStorage` (ключ `dental_booking_admin_token`).
- Токен **не содержит персональных данных**:
  - никаких ФИО, телефонов, email, дат рождения и т.п.;
  - только идентификаторы и роль.

### 1.2. Клеймы пациентского токена

Генерация: `AuthService.verify_code()` → `create_access_token(...)` в `src/core/security.py`.

Обязательные клеймы:

- `sub`: строковый UUID пациента (`str(patient.id)`).
- `role`: строка `"patient"`.
- Служебные клеймы (добавляются автоматически в `create_access_token`):
  - `iat`: время выпуска токена (UTC).
  - `exp`: время истечения токена (UTC).

Запрещено добавлять в токен:

- `phone`, `full_name`, `birth_date` или любые другие ПД пацента.
- `clinic_id` — привязка пациента к клинике делается по БД по `sub`, а не через клейм.

### 1.3. Клеймы админского токена

Генерация: `admin_login()` в `src/api/v1/routers/admin_auth.py` → `create_access_token(...)`.

Обязательные клеймы:

- `sub`: строковый UUID администратора (`str(admin.id)`).
- `clinic_id`: строковый UUID клиники администратора (`str(admin.clinic_id)`).
- `type`: строка `"admin"` (разделение на типы токенов).
- (опционально на будущем уровне) `role`: `"owner" | "admin" | ...` — при появлении ролей внутри админов.
- Служебные:
  - `iat`: время выпуска;
  - `exp`: время истечения.

Запрещено добавлять в токен:

- `email`, `full_name` или любые другие ПД админа.

### 1.4. Парсинг и использование клеймов

- Для админов уже реализован dependency `get_current_admin` в `admin_auth.py`, который:
  - читает Bearer‑токен из заголовка `Authorization`;
  - декодирует JWT, проверяет `type == "admin"`;
  - извлекает `sub` и по нему подгружает `AdminUser` из БД.
- Для пациентов на уровне API **не должно быть прямого чтения `sub`/`role` из токена в хендлерах**; вместо этого на следующем шаге (ARCH_API_GUARDS) вводится единый dependency `get_current_patient()`.

## 2. Политика TTL для разных ролей

### 2.1. Общие требования к TTL

- Токен должен быть **достаточно короткоживущим**, чтобы:
  - минимизировать риски при компрометации клиентского устройства или XSS;
  - при смене пароля/увольнении/изменении прав долгоживущие токены не сохраняли доступ на недели.
- TTL **настраивается через конфиг** (`src/core/config.py`), а не захардкожен в коде.

### 2.2. Пациентский токен

Рекомендуемая политика:

- Конфиг‑ключ: `jwt_access_token_expire_minutes_patient: int` (новое поле в `Settings`).
- Значение по умолчанию: **60 минут**.
- Аргументация:
  - пациент работает с приложением эпизодически, 1 час — комфортное "окно" без постоянных пере‑логинов;
  - при потере/компрометации устройства риск ограничен этим окном + возможностью вручную выйти (очистка токена на клиенте).

Реализация:

- В `AuthService.verify_code()` при вызове `create_access_token` использовать `expires_delta`, вычисляемый на основе `jwt_access_token_expire_minutes_patient`.

### 2.3. Админский токен

Рекомендуемая политика:

- Конфиг‑ключ: `jwt_access_token_expire_minutes_admin: int` (новое поле в `Settings`).
- Значение по умолчанию: **20 минут**.
- Аргументация:
  - админ работает из браузера на рабочем месте; более короткий TTL уменьшает окно злоупотребления в случае, если админ отошёл и не заблокировал ПК;
  - перезаход раз в 20 минут приемлем с учётом чувствительности админской панели.

Реализация:

- В `admin_login()` при вызове `create_access_token` использовать `expires_delta` на основе `jwt_access_token_expire_minutes_admin`.

### 2.4. Поведение при истечении токена

- Backend:
  - при попытке использовать истёкший токен JWT‑библиотека выбрасывает ошибку, хендлеры возвращают 401/403 в соответствии с текущей политикой (`Недействительный или истёкший токен` и т.п.).
- Frontend:
  - для админов:
    - при 401 на `/v1/admin/*` клиент `frontend/src/api/client.ts` очищает админский токен и редиректит на `/admin/login`;
  - для пациентов:
    - при 401 на `/v1/patient/*` клиент очищает пациентский токен/id и редиректит на `/login`.

## 3. Поведение при logout / смене пароля / увольнении администратора

### 3.1. Logout (пациент)

Текущее поведение:

- Мобильный/PWA‑клиент реализует logout как:
  - очистка токена и `patient_id` в локальном хранилище (`PATIENT_TOKEN_KEY`, `PATIENT_ID_KEY`);
  - переход на `/login`.
- Backend при этом не хранит состояние сессий, полагаясь на TTL токена.

Требования:

- Все публичные клиенты (`app`, PWA) должны использовать **единый logout‑механизм**:
  - не держать дополнительные "кеши" токенов;
  - после очистки токена все запросы к `/v1/patient/*` должны приводить к 401 и перенаправлению на страницу логина.

### 3.2. Logout (админ)

Текущее поведение:

- `AdminAuthGuard` на фронте:
  - решает доступ к `/admin/*` страницам по наличию `ADMIN_TOKEN_KEY` в `localStorage`.
- При logout (кнопка выхода в админке):
  - выполняется очистка `ADMIN_TOKEN_KEY`;
  - пользователь редиректится на `/admin/login`.
- Backend также полагается на TTL токена; состояния сессий нет.

Требования:

- Единый UI‑паттерн:
  - logout **всегда** вызывает очистку `ADMIN_TOKEN_KEY` и редирект на `/admin/login`;
  - никаких "мягких" logout без явной очистки токена.

### 3.3. Смена пароля администратора

Текущее поведение:

- Явного эндпоинта смены пароля может не быть; смена учётных данных происходит через административные операции.
- Даже если пароль изменён, уже выданные JWT‑токены действуют **до истечения TTL**, так как сервер не хранит отдельный "version" и не проверяет его при валидации токена.

Требования текущего уровня:

- Не внедрять version/blacklist прямо сейчас, но:
  - явно **задокументировать** это ограничение;
  - в коде в местах смены пароля оставить комментарий‑якорь к этому документу для будущей доработки.
- TTL админского токена (20 минут) считается достаточным компромиссом до введения server‑side механизма.

### 3.4. Увольнение/отключение администратора

Текущее поведение:

- При пометке `AdminUser.deleted_at` или изменении статуса в БД:
  - `get_current_admin` при следующем запросе по истечении TTL перестанет находить администратора → 401.
- Пока токен не истёк, владелец токена технически сохраняет доступ.

Требования текущего уровня:

- Отключение админа должно:
  - немедленно скрывать его из UI и списков (где это применимо);
  - блокировать выдачу новых токенов (login) для его учётки (по email).
- Уже выданные токены продолжают действовать до TTL; это допуск текущего уровня, который будет устранён при внедрении token version/blacklist.

## 4. Паттерн следующего уровня: token version / blacklist

Эта секция описывает **архитектурный паттерн**, который не обязателен к немедленной реализации, но должен учитываться при проектировании кода сейчас (чтобы не ломать контракты позже).

### 4.1. Вариант 1 — token version в БД

Идея:

- Для каждой учётки пользователя (пациент/админ) хранить целочисленный `token_version`.
- При выпуске токена:
  - в payload добавлять клейм `ver` (current `token_version`).
- При валидации токена:
  - после декодирования JWT прочитать `ver` из клейма;
  - прочитать `token_version` из БД;
  - если `ver != token_version` → токен считается отозванным (401).

События, при которых увеличивается `token_version`:

- смена пароля администратора;
- принудительный logout всех сессий (security‑инцидент, изменение прав/роли);
- при необходимости — смена критичных настроек аккаунта.

Схема (пример для админа):

- Таблица `admin_user` уже существует:
  - добавить поле `token_version: int NOT NULL DEFAULT 1`.
- Логика:
  - при создании админа → `token_version = 1`;
  - при событии "invalidate all tokens" → `token_version += 1`.

### 4.2. Вариант 2 — централизованный blacklist в Redis

Идея:

- При необходимости принудительно отозвать конкретный токен (или набор токенов):
  - добавить его `jti` (id токена) или `sub` в чёрный список в Redis.
- При валидации токена:
  - после декодирования JWT проверить наличие ключа `blacklist:<type>:<id>`:
    - `type` — "admin" / "patient";
    - `id` — `sub` или `jti` в зависимости от схемы.
- TTL для ключа:
  - равен времени оставшейся жизни токена (или чуть больше), чтобы не накапливать бесконечный список.

Технические требования:

- Для реализации blacklist по `jti` нужно:
  - при выпуске токена генерировать клейм `jti` (UUID токена);
  - при logout all / смене пароля/увольнении:
    - помечать нужные `jti` как отозванные, либо использовать комбинацию `sub`+`issued_before`.

### 4.3. Выбор подхода для Dental Booking

Рекомендация:

- Для админов:
  - базовый механизм — **`token_version` в БД**:
    - простая схема, хорошо интегрируется с уже существующей авторизацией;
    - удобно "обнулять" все сессии админа/клиники при инцидентах.
- Для пациентов:
  - на текущем уровне достаточно короткого TTL + клиентского logout;
  - при появлении массовых требований к отзыву токенов пациентов — возможно расширение механизма `token_version` и на них.

На текущем этапе:

- Код следует писать так, чтобы:
  - в местах генерации токена **было очевидное место для добавления `ver`/`jti`**;
  - в dependency `get_current_admin`/`get_current_patient` была понятная точка, где можно будет добавить проверку `token_version`/blacklist.

## 5. Конкретные требования к коду для @DEV

1. **Конфиг TTL по ролям**
   - Добавить в `Settings` (`src/core/config.py`) поля:
     - `jwt_access_token_expire_minutes_patient: int = 60`;
     - `jwt_access_token_expire_minutes_admin: int = 20`.
   - Обновить вызовы `create_access_token` для пациента и админа через явный `expires_delta`.

2. **Клеймы токенов**
   - Пациент:
     - гарантировать, что payload содержит только `sub`, `role="patient"` + служебные `iat/exp`.
   - Админ:
     - гарантировать, что payload содержит `sub`, `clinic_id`, `type="admin"` + `iat/exp`;
     - не добавлять email/ФИО/иные ПД.

3. **Logout на фронте**
   - Пациент:
     - убедиться, что все места logout вызывают очистку `PATIENT_TOKEN_KEY` и `PATIENT_ID_KEY` + редирект на `/login`.
   - Админ:
     - убедиться, что все места logout вызывают `clearAdminToken()` + редирект на `/admin/login`.

4. **Якорные точки для будущего token version**
   - В местах смены пароля админа и отключения учётки оставить комментарий вида:
     - `# ARCH_AUTH_SESSIONS: здесь в будущем будет increment token_version / отзыв токенов`.
   - Не реализовывать сам механизм в этом цикле hardening, но не мешать его добавлению.

Этот документ является источником правды для всех изменений сессий и токенов в рамках hardening‑фаз, описанных в `DEV_PROMPTS_HARDENING_SECURITY_AND_AI.md` (секция A.1).
