# Интеграции: 1С, qMS, Битрикс24 — как реализовать

> Запрос владельца: сделать прямые интеграции вместо только CSV. Цель — дать клиенту стабильность «внутри продукта», без зависимости от посредников (Albato и т.п.).

---

## 1. Почему сейчас только CSV

- **1С:** У каждой клиники своя конфигурация 1С и разный доступ к API. Универсальный «из коробки» обмен без доступа к серверу клиента возможен только через файлы (CSV/XML). Прямой REST API 1С требует, чтобы на стороне клиента был поднят HTTP-сервис (1С как REST-сервер) и открыт доступ — это настраивает клиент или интегратор.
- **qMS, Битрикс24:** В MVP приоритет был на записи, оплате, напоминаниях; интеграции с внешними CRM/МИС оставлены как заглушки в админке.

---

## 2. 1С: как реализовать обмен по API

**Варианты:**

| Вариант | Описание | Кто настраивает |
|--------|----------|------------------|
| **CSV (текущий)** | Импорт расписания врачей из CSV; экспорт закрытых записей в CSV. Клиент или 1С-специалист настраивает обмен файлами (папка, по расписанию). | Клиент / интегратор 1С |
| **REST API 1С (исходящий от нас)** | Наш backend вызывает 1С клиента по HTTP. В 1С должна быть опубликована REST-точка (например, «Получить расписание», «Принять оказанные услуги»). Мы отправляем GET/POST на URL + учётные данные, которые вводит клиник в настройках. | Клиент открывает в 1С веб-сервис и даёт нам URL + логин/пароль или токен |
| **REST API 1С (входящий к нам)** | 1С клиента по расписанию вызывает наш API (например, `POST /api/v1/integrations/1c/visits` с данными об оказанных приёмах). Мы принимаем JSON и обновляем записи/выручку. | Клиент настраивает в 1С исходящий обмен на наш URL |

**Рекомендация для плана:**

1. **Оставить CSV** как режим по умолчанию (работает без доступа к 1С).
2. **Добавить режим «1С API»** в настройках интеграции клиники:
   - Поля: `1c_base_url`, `1c_api_key` (или логин/пароль), переключатель «Использовать 1С API вместо CSV».
   - Backend: модуль `Integrations1C` с методами `fetch_schedule()` и `push_completed_visits()`. Контракт API 1С (формат запросов/ответов) описать в отдельном документе или согласовать с типовой конфигурацией (например, 1С:Медицина или типовой обмен для стоматологии).
3. Реализацию вести через @ARCH (контракт API, безопасность хранения учётных данных, повтор при сбоях).

## 3. qMS (МИС для стоматологии/клиник)

**Что такое qMS:** Медицинская информационная система (СП.АРМ), используется в 300+ клиниках. Интеграции с 1С, Парус, контакт-центрами, гос. системами (ЕГИСЗ, ФЭР и т.д.) заявлены на сайте производителя. Публичного REST API для сторонних систем в открытом доступе нет.

**Как реализовать:**

- Запросить у СП.АРМ описание API или протокола обмена (файлы, веб-сервисы) для синхронизации расписания и оказанных услуг.
- Если API/обмен есть — добавить в настройках клиники тип интеграции «qMS» и модуль по аналогии с 1С (URL, ключ, контракт обмена).
- Если производитель даёт только файловый обмен — реализовать парсер их формата (вместо/в дополнение к нашему CSV).

**План:** В бэклог заложить задачу «Интеграция qMS» с шагом 1 — запрос к производителю (документация/доступ к тестовому стенду). Дальше — по контракту от @ARCH.

## 4. Битрикс24: как реализовать

**Механика Битрикс24:**

- **Входящий вебхук:** В Битрикс24 создаётся «Входящий вебхук» (Приложения → Разработчикам). Выдаётся URL вида `https://[портал].bitrix24.ru/rest/[user_id]/[code]/`. Любой HTTP-запрос на этот URL с методом в теле выполняет метод REST API (например, `crm.lead.add`, `crm.deal.add`).
- **Исходящий вебхук:** Битрикс24 может отправлять события на наш URL (новый лид, изменение сделки) — мы принимаем webhook и, при необходимости, создаём запись или обновляем данные.

**Что мы можем делать:**

| Действие | Реализация |
|----------|------------|
| Создавать лид/сделку в Битрикс24 при новой записи | При подтверждении записи (patient + booking) вызывать `crm.lead.add` или `crm.deal.add` с полями (имя, телефон, комментарий, сумма). URL и код вебхука хранить в настройках клиники (`bitrix24_webhook_url`). |
| Синхронизировать контакты | При создании/обновлении пациента опционально вызывать `crm.contact.add`/`crm.contact.update`. |
| Принимать события из Битрикс24 | Наш endpoint `POST /api/v1/integrations/bitrix24/webhook` принимает тело от Битрикс24; при событии «новая заявка с формы» можно создавать запись у нас (если заявка содержит дату/услугу). |

**Рекомендация:**

1. В настройках интеграции добавить блок «Битрикс24»: поле «URL входящего вебхука», чекбокс «Создавать лид при новой записи».
2. Backend: сервис `Bitrix24Client` с методом `create_lead(phone, name, comment, amount)` — вызов `crm.lead.add` по документации Битрикс24 REST API.
3. Опционально: при создании записи админом/пациентом вызывать этот метод асинхронно (Celery), чтобы не блокировать ответ.
4. Исходящий вебхук (Битрикс24 → мы) — отдельная задача, если понадобится двусторонняя синхронизация.

Детальный контракт (поля лида, обработка ошибок, тесты) — в зоне @ARCH.

## 5. Стабильность «только внутри» vs посредники

- **Через посредников (Albato и т.п.):** Клиент настраивает сценарии в стороннем сервисе; обмен идёт через их инфраструктуру. Плюс — быстрое подключение без нашей разработки под каждую конфигурацию 1С/Битрикс. Минус — зависимость от третьей стороны, подписка, лимиты.
- **Внутри нашего продукта:** Мы реализуем прямые вызовы 1С/Битрикс24 по контракту. Стабильность того же масштаба возможна при условии:
  - мы документируем и поддерживаем один или несколько типовых контрактов (например, «1С: типовой обмен для стоматологии», «Битрикс24: лид при записи»);
  - клиент или его интегратор настраивает свою 1С/Битрикс под этот контракт (открывает URL, создаёт вебхук).
  То есть «стабильность внутри» = предсказуемый, версионируемый контракт с нашей стороны + чёткая инструкция для клиента. Масштаб (много разных конфигураций 1С) мы не покроем без партнёрства или посредников; покрываем типовые сценарии.
