## ARCH_ENVIRONMENTS — окружения, debug и логирование

Основание: `ARCH_HARDENING_ROADMAP.md` (п. 4), текущая реализация `src/core/config.py`, `src/core/logging.py`, `src/main.py`, клиент `frontend/src/api/client.ts`.

**Цель:** зафиксировать матрицу окружений (`development` / `staging` / `production`), поведение debug/Swagger/ошибок и политику логирования, чтобы:

- dev был удобен для разработки, но без утечек ПД в логи;
- staging максимально имитировал prod по защите и логам;
- prod оставался "тихим и безопасным" для внешнего пользователя, а подробности уходили только во внутренние логи.

---

## 1. Матрица окружений

Базовые значения в `Settings` (`src/core/config.py`):

- `app_env: str` — `"development" | "staging" | "production"` (по умолчанию `"development"`).
- `debug: bool` — общий флаг для FastAPI и ряда фич.

### 1.1. Таблица поведения по окружениям

| Окружение      | `app_env`     | `debug`       | Swagger (`/docs`, `/redoc`)           | Ошибки в ответах клиенту                               | Логи                               |
|----------------|---------------|--------------|----------------------------------------|--------------------------------------------------------|------------------------------------|
| Dev            | `development` | `true`       | Включены, без доп. защиты             | Более подробные, но без стектрейсов и ПД               | Подробные, допускаются DEBUG‑логи |
| Staging        | `staging`     | `false` или `true` точечно | Включены, но доступны только по VPN/базовой auth | Короткие сообщения, без стектрейсов                    | Как в prod, но можно повышать детализацию |
| Prod           | `production`  | `false`      | Отключены (либо за базовой auth/IP‑фильтром) | Только короткие сообщения ("Внутренняя ошибка сервера") | Структурированные JSON‑логи без ПД |

**Правило:**  
`app_env` определяет "режим окружения", `debug` — конкретные включения dev‑фич (но в `production` `debug` всегда должен быть `false`).

## 2. Поведение backend‑приложения

### 2.1. FastAPI‑приложение

Сейчас:

- `FastAPI(..., debug=settings.debug, docs_url="/docs", redoc_url="/redoc", ...)` в `src/main.py`.

Требуемое поведение:

- В `production`:
  - `settings.app_env == "production"`;
  - `settings.debug == False`;
  - `docs_url` и `redoc_url`:
    - либо `None` (Swagger отключён полностью),
    - либо защищены дополнительной авторизацией/ограничением по IP (на уровне NGINX/Cloudflare).
- В `staging`:
  - по умолчанию `debug == False`;
  - Swagger включён, но доступ ограничен (VPN, basic‑auth, IP‑whitelist).
- В `development`:
  - `debug == True`;
  - Swagger открыт.

Рекомендуемый подход:

- в `main.py` вычислять фактические `docs_url`/`redoc_url` в зависимости от `settings.app_env`;
- при необходимости добавить переменную окружения `enable_swagger_in_production: bool = False`, но по умолчанию она **False**.

### 2.2. Обработка ошибок и формат ответов

Backend уже возвращает:

- для 4xx: бизнес‑ошибки с деталями (оставляем);
- для 5xx: возможно, подробные стектрейсы (нежелательно для prod).

Frontend‑клиент (`frontend/src/api/client.ts`) уже:

- для 5xx пытается "обрезать" traceback и заменить на короткое сообщение `"Внутренняя ошибка сервера (500)..."`

Требования:

- На уровне backend:
  - в `production` и `staging`:
    - глобальные exception‑handlers не должны отдавать стектрейсы/внутренние детали;
    - тело ответа для 5xx должно быть коротким (код + короткое описание), без SQL‑запросов и трейсбеков.
  - в `development`:
    - можно включать более подробные сообщения, но по возможности:
      - не слать сырые стектрейсы во внешний мир (достаточно сокращённых описаний, фронт всё равно нормализует их);
      - основная диагностика — по логам.

## 3. Политика логирования

### 3.1. Текущая реализация

`src/core/logging.py`:

- лог‑уровень берётся из `settings.log_level` (по умолчанию `"INFO"`);
- формат логов:
  - `"json"` → `JSONFormatter` со структурированным выводом;
  - иначе — текстовый формат `"%(asctime)s - %(name)s - %(levelname)s - %(message)s"`.

### 3.2. Требования по логам и ПД

**Общее правило:**  
Ни в одном окружении в логи не должны попадать "сырые" ПД (телефоны, email, ФИО, коды подтверждения и т.п.) без маскировки.

Разница по окружениям:

- Dev:
  - допустимы более подробные бизнес‑контексты;
  - ПД должны быть **замаскированы** (например, `+7***1234`, `user***@example.com`);
  - можно использовать текстовый формат логов.
- Staging:
  - формат логов как в prod (JSON, `INFO`/`WARNING`/`ERROR`);
  - ПД замаскированы;
  - уровень DEBUG включается только временно для расследования, и всё равно без "сырого" вывода ПД.
- Prod:
  - только структурированные JSON‑логи;
  - минимум DEBUG/INFO, акцент на `INFO`/`WARNING`/`ERROR`;
  - никакого логирования кодов SMS, паролей, access‑токенов и т.п.

### 3.3. Переменные окружения для логирования

В `Settings` уже есть:

- `log_level: str = "INFO"`;
- `log_format: str = "json"`.

Требования:

- Для `production`:
  - `log_format=json`;
  - `log_level=INFO` или `WARNING` (по решению @OPS/@SEC).
- Для `development`:
  - допускается `log_format=text` для удобства локальной отладки;
  - `log_level=DEBUG`/`INFO`.
- Для `staging`:
  - как в prod (`json` + `INFO`), чтобы ловить реальные проблемы.

## 4. Переменные окружения backend

### 4.1. Ключевые переменные

Минимальный набор (расширяется по мере внедрения других ARCH‑документов):

- `APP_ENV` → `app_env`:
  - `"development"` / `"staging"` / `"production"`;
- `DEBUG` → `debug`:
  - в `.env` как `true`/`false` (Pydantic сам сконвертирует);
- `SECRET_KEY` → `secret_key`;
- `DATABASE_URL` → `database_url`;
- `REDIS_URL` → `redis_url`;
- `CORS_ORIGINS` → `cors_origins`;
- `JWT_SECRET_KEY` → `jwt_secret_key`;
- `JWT_ALGORITHM` → `jwt_algorithm`;
- `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` → `jwt_access_token_expire_minutes` (или разделённые поля для ролей, см. `ARCH_AUTH_SESSIONS.md`);
- AI‑конфиг:
  - `AI_PROVIDER_BASE_URL`, `AI_PROVIDER_API_KEY`, `AI_PROVIDER_MODEL`, `AI_TIMEOUT_SECONDS`;
- Logging:
  - `LOG_LEVEL`, `LOG_FORMAT`.

### 4.2. Требования к `.env` для production

В production‑окружении:

- `APP_ENV=production`;
- `DEBUG=false`;
- `LOG_FORMAT=json`;
- `LOG_LEVEL=INFO` (минимум).

Секреты:

- значения `SECRET_KEY`, `JWT_SECRET_KEY`, `AI_PROVIDER_API_KEY`, пароли к БД и Redis:
  - должны храниться **не в репозитории**, а в `.env` на сервере или в менеджере секретов (Vault, AWS Secrets Manager и т.п.);
  - `.env` на prod не должен попадать в репозиторий/артефакты сборки.

## 5. Окружения frontend

Хотя основной фокус — backend, важно, чтобы frontend:

- знал, в каком окружении он работает (через переменные сборки, например `VITE_APP_ENV`);
- корректно обрабатывал ошибки:
  - не показывал пользователю сырые сообщения об ошибках backend (traceback, SQL);
  - использовал уже реализованную нормализацию ошибок в `frontend/src/api/client.ts`.

Рекомендации:

- В `development`:
  - можно отображать более подробные сообщения в dev‑консоли, но не в UI для конечного пользователя;
  - включить dev‑индикаторы (например, бейдж "DEV" в UI).
- В `staging`/`production`:
  - показывать только пользовательски‑дружелюбные сообщения;
  - детали смотреть по логам и tracing‑системам.

## 7. Выход для @DEV и @OPS

**Для @DEV:**

- привести `main.py` и обработку ошибок к этой матрице:
  - учесть `app_env` и `debug` при включении Swagger и форматировании ошибок;
  - убедиться, что фронтовый клиент не получает стектрейсы.

**Для @OPS:**

- настроить отдельные `.env`/секреты для dev/stage/prod;
- убедиться, что:
  - prod‑окружение запущено с `APP_ENV=production`, `DEBUG=false`, `LOG_FORMAT=json`;
  - доступ к Swagger на prod (если включён) ограничен внутренним периметром;
  - логи собираются централизованно (ELK/CloudWatch/иное) и не содержат ПД.
