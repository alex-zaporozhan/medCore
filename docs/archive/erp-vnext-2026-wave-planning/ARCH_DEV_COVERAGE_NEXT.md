## 11. Процесс реализации ARCH_DEV_* в код

Этот раздел фиксирует единый повторяемый процесс, по которому команда/агенты превращают `ARCH_DEV_*` в код и позволяют безопасно возобновлять работу при потере контекста.

### 11.1. Управление потоком задач (что и в каком порядке делаем)

- **Источник правды по порядку:** используем приоритеты и зависимости из `DEV_PROMPTS_NEXT.md` (разделы 2–3):
  - сначала P0 (OMNI_POLICY_016, SEC_RBAC_022, BKG_CORE_001, ERP_NODE_010 и т.д.),
  - затем P1, P2, P3 с учётом цепочек зависимостей.
- **Epic/feature на DEV_PROMPT:**
  - для каждого `DEV_PROMPT_xxx` создаётся один epic/feature в таск‑трекере;
  - в описании epic/feature указываются ссылки:
    - на соответствующий блок в `DEV_PROMPTS_NEXT.md`,
    - на `ARCH_DEV_xxx.md`,
    - на связанные `BACKEND_GAPS_*_NEXT.md` / `FRONTEND_GAPS_*_NEXT.md` / `NONFUNCTIONAL_AUDIT_NEXT.md`.
- **Файлы с мелкими dev‑тасками:**
  - для каждого `ARCH_DEV_xxx.md` создаётся файл мелких задач:
    - имя: `ARCH_DEV_<ID>_TASKS.md` (пример: `ARCH_DEV_OMNI_POLICY_016_TASKS.md`);
  - этот файл содержит 3–10 атомарных dev‑тасок в логическом порядке:
    - аналитика → модели/DTO → сервисы → роутеры → тесты → логи/метрики/OBS;
  - именно по этим файлам удобно поднимать работу в новом контексте и запускать по одной задаче в реализацию кода.

### 11.2. Подход к реализации для каждого ARCH_DEV_xxx

Для любого `ARCH_DEV_xxx` используется один и тот же цикл:

1. **Стадия “Understand” (аналитика, без кода):**
   - прочитать `ARCH_DEV_xxx.md`, связанные `ARCH_*_NEXT.md` и соответствующие GAPS;
   - зафиксировать локальный план (какие файлы/контракты трогаем, какие инварианты нельзя сломать);
   - при необходимости уточнить файл `ARCH_DEV_<ID>_TASKS.md`.
2. **Стадия “Design‑to‑code” (скелет):**
   - вносить только структуры и контракты:
     - DTO в `application/dto/*`,
     - интерфейсы/классы сервисов с `...` внутри,
     - enum/словари, не ломающие текущие вызовы;
   - крупные изменения всегда делать инкрементально (новые методы/эндпоинты, фиче‑флаги, мягкие переключатели).
3. **Стадия “Implement” (логика + тесты):**
   - реализовать бизнес‑логику строго по разделам 2–3 `ARCH_DEV_xxx.md`:
     - сначала центральный фасад/узел/orchestrator,
     - затем интеграции с соседними доменами;
   - вместе с логикой добавлять/обновлять тесты для всех жёстких инвариантов и критичных сценариев из GAPS.
4. **Стадия “Integrate” (API, UI‑контракты):**
   - обновлять только явно перечисленные в `ARCH_DEV_xxx.md` роутеры/публичные API;
   - по возможности сохранять обратную совместимость:
     - через новые версии/контракты,
     - через адаптеры/фасады, пока фронт не обновлён.
5. **Стадия “Observe” (логи, метрики, Attention/Tasks):**
   - реализовать раздел «Наблюдаемость и ошибки» из `ARCH_DEV_xxx.md`:
     - структурированные логи,
     - метрики (количество, ошибки, latency),
     - привязка критичных ошибок к Tasks/AttentionFeed.
6. **Стадия “Stabilize” (долги и документация):**
   - удалить/сжать временные обходы и legacy‑ветки, оставшиеся под фиче‑флагами;
   - обновить статусы:
     - в `DEV_PROMPTS_NEXT.md` (статус DEV_PROMPT),
     - в соответствующих `BACKEND_GAPS_*_NEXT.md`/`FRONTEND_GAPS_*_NEXT.md`,
     - при необходимости — в `ARCH_AUDIT_NEXT.md`.

### 11.3. Организация работы команды / агентов

- **Git‑ветки:**
  - ветка создаётся на DEV_PROMPT, а не на случайный тикет:
    - формат имени: `feature/dev-prompt-<id>` (пример: `feature/dev-prompt-omni-policy-016`);
  - в ветке допускается несколько PR, но каждый PR закрывает ограниченный набор задач из `ARCH_DEV_<ID>_TASKS.md`.
- **PR‑шаблон:**
  - ссылки на `DEV_PROMPT_xxx`, `ARCH_DEV_xxx.md`, `ARCH_DEV_<ID>_TASKS.md`;
  - чек‑лист: какие пункты из dev‑чек‑листа `ARCH_DEV_xxx.md` и из файла `*_TASKS.md` закрывает PR;
  - список затронутых инвариантов и краткое описание того, как они покрыты тестами и OBS.
- **Роли ARCH/QA:**
  - ARCH/QA проверяет:
    - соответствие кода инвариантам и целевой модели домена,
    - полноту тестов и наблюдаемости,
    - отсутствие обходов RBAC/`clinic_id`/SEC‑правил;
  - не фокусируется на стиле/мелких деталях реализации, если они не нарушают архитектуру.

### 11.4. Технические практики для спокойной реализации

- **Инкрементальные миграции и фиче‑флаги:**
  - крупные изменения (ERP‑узел, унификация статусов, AI‑Orchestrator) делятся на небольшие релизы;
  - где возможно, используется режим shadow (новый путь работает параллельно и только логирует расхождения).
- **Тесты доменных сервисов:**
  - основной вес тестов — на `application/services/*` и доменный слой;
  - для каждого ARCH_DEV:
    - минимум один тест на каждый жёсткий инвариант,
    - позитивные и негативные сценарии по ключевым бизнес‑цепочкам.
- **Контроль регрессий через OBS:**
  - перед выкладкой новых цепочек добавляются базовые метрики и логи;
  - для каждой задачи фиксируется список ключевых графиков/логов, по которым проверяется выкатка.

## 12. Чек‑лист покрытия ARCH_DEV_*_TASKS

Для каждого `ARCH_DEV_xxx` из таблиц разделов 2–9 должен выполняться следующий чек‑лист по файлам задач:

- **Наличие файла `ARCH_DEV_<ID>_TASKS.md`**
  - Файл существует в `./` с именем по шаблону:  
    `ARCH_DEV_<ID>_TASKS.md` (пример: `ARCH_DEV_BKG_CORE_001_TASKS.md`).
  - В шапке указаны:
    - связанный `ARCH_DEV_xxx.md`,
    - связанный `DEV_PROMPT_xxx` с приоритетом и GAPS.

- **Полный цикл 1–6 внутри `*_TASKS`**
  - Файл содержит разделы:
    - `1. Understand` — аналитика и инвентаризация без правок кода;
    - `2. Design‑to‑code` — DTO, интерфейсы сервисов, контракты;
    - `3. Implement` — реализация доменной логики;
    - `4. Integrate` — роутеры, публичные API, фронт‑контракты (где применимо);
    - `5. Observe` — логи, метрики, Attention/Tasks;
    - `6. Stabilize` — тесты, синхронизация GAPS и ARCH‑артефактов.

- **Атомарность и привязка к коду**
  - В каждом разделе 3–10 подпунктов, которые можно заводить как отдельные задачи в трекере.
  - В подпунктах явно указаны:
    - конкретные модули (`application/services/*`, `api/v1/routers/*`, `application/dto/*`, доменные сущности),
    - связанные GAPS (`BACKEND_GAPS_*_NEXT.md`, `FRONTEND_GAPS_*_NEXT.md`, `NONFUNCTIONAL_AUDIT_NEXT.md`),
    - связи с другими ARCH_DEV (например, фасад завершения визита ↔ ERP‑узел ↔ отчёты).

- **Тесты и OBS в явном виде**
  - В разделе `6. Stabilize` для каждого ARCH_DEV_xxx зафиксированы:
    - типы тестов (юнит/интеграционные) и ключевые сценарии (позитивные/негативные);
    - какие метрики/логи/Attention‑сигналы должны появиться;
    - что именно нужно обновить в `DEV_PROMPTS_NEXT.md`, `BACKEND_GAPS_*_NEXT.md`/`FRONTEND_GAPS_*_NEXT.md`, `ARCH_AUDIT_NEXT.md`.

- **Эталон оформления**
  - В качестве эталона структуры и уровня детализации использовать:
    - `ARCH_DEV_BKG_CORE_001_TASKS.md`,
    - а также уже оформленные `ARCH_DEV_OMNI_POLICY_016_TASKS.md`, `ARCH_DEV_ERP_NODE_010_TASKS.md`, `ARCH_DEV_BKG_STATE_002_TASKS.md`, `ARCH_DEV_ERP_REPORTS_012_TASKS.md`.

Этот раздел служит единым чек‑листом для проверки качества и полноты `ARCH_DEV_*_TASKS` при добавлении новых DEV_PROMPT или ревизии существующих.
