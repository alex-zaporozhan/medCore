## 🎼 ARCH_ORCHESTRATION_PROMPTS — сценарий запуска ролей для апгрейда Business OS

> **Цель:** пошаговый сценарий для запуска всех ролей (QA_ARCH, ARCH, CREATOR, AUDITOR, FRONT/BACK/SEC и др.),  
> чтобы **улучшить существующий код** (а не переписать его с нуля):  
> закрыть баги, логические дыры, дырки в безопасности, привести весь UI к новому дизайну,  
> и в финале получить новый BUSINESS_PLAN + DEV_PROMPTS на рефакторинг/фичи.
>
> **Ключевой принцип:** код — источник правды. Ни одно решение не принимается, пока роль  
> не проверит реальный код/схемы/эндпоинты. `BUSINESS_*` и старые артефакты — только вспомогательная оптика.

---

## 0. Общая рамка процесса

- **Что мы НЕ делаем:**
  - не «выбрасываем» существующий код и не перезапускаем проект с пустого листа;
  - не удаляем файлы «ради красоты», если только сразу не создаётся новый, улучшенный вариант с тем же назначением.
- **Что мы ДЕЛАЕМ:**
  - используем существующий код как фундамент (≈60% готовности);
  - проходим **все слои**: бизнес‑логика → архитектура → безопасность → UX → качество;
  - в конце фиксируем:
    - новый **BUSINESS_PLAN_NEXT.md** (как должен работать продукт);
    - единый **ARCH_DECISIONS_NEXT.md** (принятые архитектурные решения);
    - единый **DEV_PROMPTS_NEXT.md** (упорядоченный список dev‑промптов/тасок по коду).

---

## 1. Порядок запуска ролей (high‑level)

1. **QA_ARCH** — критический аудит фактического продукта:
   - снимает «рентген» багов, UX‑дыр, несоответствий «ожидал → получил».
2. **ARCH (общий архитектор)** — собирает целостное видение:
   - опирается на QA‑аудит + код + текущую бизнес‑логику, формирует архитектурный скелет vNext.
3. **AUDITOR** — проверяет согласованность:
   - нет ли противоречий между кодом, ARCH и BUSINESS; всё ли измеримо и реализуемо.
4. **FRONT_ARCH / BACKEND_ARCH / SEC_ARCH** — детализируют по слоям:
   - фронт (UX+коды страниц), бэкенд (домены/сервисы/эндпоинты), безопасность/перфоманс.
5. **CREATOR** — превращает это в осмысленный **BUSINESS_PLAN_NEXT**:
   - делает нарратив «что за продукт, чем он круче, за счёт чего выигрывает».
6. **ARCH (второй проход)** — готовит **DEV_PROMPTS_NEXT**:
   - разбивает цель на конкретные dev‑шаги, привязанные к файлам и модулям.

Ниже — **конкретные промпты** для каждой роли, с ожидаемым артефактом.

```text

Не реализуй рефакторинг кода и не вноси окончательные архитектурные решения в этом режиме — только фактический аудит и проблемы.  
**Идеи и гипотезы по улучшениям можно помечать как заметки**, чтобы потом ARCH/@LEAD могли их оценить и оформить в ARCH/DEV‑документы.
```

## 4. AUDITOR — проверка согласованности «код ↔ ARCH ↔ BUSINESS»

**Артефакт:** `ARCH_AUDIT_NEXT.md`  
**Фокус:** нет ли расхождений между тем, что описал ARCH, тем, что реально есть в коде, и тем, что ожидает бизнес.

### 4.1. Промпт для AUDITOR

```text
Ты — AUDITOR (архитектурный аудитор) для Dental Booking Business OS.

На входе:
- QA_AUDIT_NEXT.md
- ARCH_DECISIONS_NEXT.md

1. Проверить, что каждое архитектурное решение в ARCH_DECISIONS_NEXT.md реально:
   - либо уже частично реализовано в коде,
   - либо достижимо без тотального переписывания.
2. Найти противоречия:
   - между кодом и ARCH (описано одно, в коде другое);
```

## 7. ARCH — финальный DEV_PROMPTS_NEXT для реализации

**Артефакты:**  
- `DEV_PROMPTS_NEXT.md` — список dev‑шагов по доменам;  
- `DEV_WORKFLOW_GUIDE_NEXT.md` — рабочий контракт для `@DEV` и `@LEAD`, **когда** и **как** согласовывать решения при реализации этих шагов.

**Жёсткий принцип качества:**  
**«Нет GAPS без DEV_PROMPT’а»** — каждый зафиксированный gap (любой важности, включая S3/«косметика»):
- либо получает отдельный DEV_PROMPT (или входит в состав явного DEV‑пакета с ID),
- либо явно помечается как «отложено/закрыто» с обоснованием, и только по решению @LEAD.

Промпт:

```text
Ты снова ARCH, теперь в роли автора dev-плана.

На входе:
- BUSINESS_PLAN_NEXT.md
- ARCH_DECISIONS_NEXT.md, ARCH_*_NEXT.md
- QA_AUDIT_NEXT.md
- BACKEND_GAPS_*_NEXT.md + SUMMARY
- FRONTEND_GAPS_*_NEXT.md + SUMMARY
- NONFUNCTIONAL_AUDIT_NEXT.md

Задача:
1. Сформировать упорядоченный список DEV-промптов/тасок в DEV_PROMPTS_NEXT.md:
   - каждая задача:
     - имеет ID;
     - описывает цель (что меняется для пользователя/домена);
     - привязана к конкретным файлам/модулям (backend+frontend);
     - учитывает ограничения: ничего не ломать, мигрировать пошагово, не выбрасывая существующий код без замены.
2. Разбить задачи на пакеты:
   - Booking/Prepayment/Payments hardening;
   - CRM Kanban & Sales OS;
   - ERP Node (Finance + Payroll + Inventory);
   - Loyalty Engine;
   - Omnichannel & AI Agent;
   - Paperless & Forms;
   - Tasks & Attention Feed;
   - Security & Observability.

Формат DEV_PROMPTS_NEXT.md:
- 1. Принципы реализации (минимум риска, максимум реюза)
- 2. Пакеты задач (каждый пакет — список DEV_PROMPT_xxx с приоритетом)
- 3. Зависимости между задачами (что нужно сделать раньше).
```

Дополнительное требование к CREATOR/@BIZ:  
- при формировании BUSINESS_PLAN_NEXT и при ревью DEV_PROMPTS_NEXT быть **максимально придирчивым** к соответствию:
  - бизнес‑обещаний — коду и архитектуре;
  - каждой зафиксированной проблеме (GAP) — наличию конкретного DEV_PROMPT’а или осознанного решения «не делать» от @LEAD.

## 8. Как мы будем этим пользоваться в INDI‑режиме

- У нас нет Jira/Notion — всё живёт в `./*.md` + коде.
- Мы по очереди запускаем описанные выше роли (через эти промпты), получаем артефакты:
  - сначала `QA_AUDIT_NEXT.md`,
  - затем `ARCH_DECISIONS_NEXT.md` + `ARCH_*_NEXT.md`,
  - затем `ARCH_AUDIT_NEXT.md`,
  - затем `BACKEND_GAPS_*_NEXT.md`, `FRONTEND_GAPS_*_NEXT.md`, `NONFUNCTIONAL_AUDIT_NEXT.md`,
  - затем `BUSINESS_PLAN_NEXT.md`,
  - затем `DEV_PROMPTS_NEXT.md`.
- После этого ты, как единственный dev, реализуешь DEV_PROMPTS по приоритету, а я могу помогать:
  - расшифровывать каждый промпт в конкретные изменения кода;
  - писать/рефакторить код, придерживаясь принятых решений.

Этот файл задаёт **чёткий, документированный план запуска каждой роли**  
и гарантирует, что мы идём **от кода и фактов к Enterprise‑уровню**, а не наоборот.
