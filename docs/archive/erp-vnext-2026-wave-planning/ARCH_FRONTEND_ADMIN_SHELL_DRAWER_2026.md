# ARCH_FRONTEND_ADMIN_SHELL_DRAWER_2026 — оболочка панелей и программа качества админки

> **Статус:** запланировано (черновик для реализации)  
> **Роль-инициатор:** @QA_ARCH  
> **Связь:** `./ARCH_FRONTEND_TECH_PASSPORT_DENTAL_BOOKING.md`, `../../TECH_PASSPORT_FRONTEND_UI_LOGIC.md`, `frontend/src/shared/ui/GlassModal.tsx`

**Назначение документа:** (1) конкретная реализация **`AdminDrawer` + токены** — **фаза A**; (2) **единая «северная звезда»** для ревью уровня лида: логистика, безопасность, удобство и **мягкость** при длительной работе (≈8 ч × 5 дн.); (3) **фазы B–E** и правила **минимизации рисков** — чтобы довести продукт до «твёрдого» состояния без попытки сделать всё одним коммитом.

## 1. Зачем (фаза A — оболочка)

Сейчас в админке смешаны паттерны:

- **`GlassModal`** — центрированное модальное окно с оформлением (blur, тень, фон контента).
- **«Голый» `Drawer` из Mantine** — правая панель без единой оболочки: визуально «резкая полоса», слабая связь с общим дизайн-языком.

**Цель:** выровнять **оболочку** (оверлей, тень, скругления, зона заголовка, отступы контента) для всех выезжающих панелей **без изменения бизнес-логики** открытия/закрытия и состава форм внутри.

---

## 2. Принципы (согласовано с @QA_ARCH)

| Сценарий | Паттерн | Позиция |
|----------|---------|---------|
| Просмотр/редактирование сущности, длинные формы, действие из строки таблицы | Панель-деталь | **Справа** (`Drawer`, `position="right"`) |
| Подтверждения, короткие диалоги, AI «Спросить», быстрые алерты | Модальное окно | **По центру** (`Modal`, в т.ч. `GlassModal`) |

**Не делаем** глобальный перенос всех панелей в центр — это ухудшает типичный admin UX (контекст списка теряется).

**Делаем** единый визуальный язык: одни токены/стили для blur, overlay, тени и контента — и для правой панели, и для центрального модала (где уместно).

## 3. Целевое решение в коде

### 3.1 Компонент `AdminDrawer` (новый)

- Расположение: `frontend/src/shared/ui/AdminDrawer.tsx` (рядом с `GlassModal.tsx`).
- Обёртка над **`Drawer`** Mantine с фиксированными дефолтами:
  - `position="right"`
  - `overlayProps`: согласованная прозрачность и **blur** (как у модалки или чуть сильнее для крупной панели).
  - `styles` / `classNames`: скругление контента слева (`borderRadius` только слева или со всех сторон — зафиксировать в реализации), тень, фон панели (в духе glass или solid — согласовать с паспортом).
  - Заголовок: единый отступ под `title`, при необходимости разделитель под заголовком (через `styles` или обёртку).
- Проброс всех остальных пропсов Mantine `DrawerProps` наружу (`opened`, `onClose`, `size`, `title`, `children`, `trapFocus`, и т.д.), чтобы **не менять** локальную логику страниц.

### 3.2 Выравнивание с `GlassModal`

- Вынести **общие константы стилей** (overlay blur, opacity, boxShadow контента) в `frontend/src/shared/ui/shellPanelStyles.ts` или аналог — импорт в **`GlassModal`** и **`AdminDrawer`**, чтобы не дублировать magic numbers.
- **`GlassModal`** оставить для центрированных сценариев; при необходимости слегка подправить только импорт общих токенов (рефактор без смены API компонента).

### 3.3 Опция «как центр» для одного семейства (опционально)

Если понадобится **один** компонент с переключателем режима:

- Либо `AdminShellPanel` с `variant: "drawer" | "modal"` (внутри — `Drawer` vs `Modal`);
- Либо оставить два публичных компонента **`AdminDrawer`** + **`GlassModal`**, связанные общими стилями (**рекомендуемый минимум** для первого шага).

Деталь выбора — на этапе реализации; артефакт допускает оба варианта при условии **единого визуального языка**.

## 9. Перепроверка @QA_ARCH — улучшения артефакта и реализации

Ниже — что усилить в **документе и в коде**, не меняя уже согласованных принципов §2.

### 9.1 Архитектура компонента

| Тема | Рекомендация |
|------|----------------|
| **Жёсткий `position="right"`** | В `AdminDrawer` зафиксировать `position="right"` в типе (`Omit<DrawerProps, "position">` + константа), чтобы случайно не получить левую панель. Исключения (RTL, другой продукт) — отдельный компонент или явный `unsafe`‑проп, не дефолт. |
| **Слияние `styles` и переопределений** | При `styles={{ content: ... }}` со страницы — **мержить** с дефолтами `AdminDrawer` (а не заменять целиком), иначе потеряем оболочку. Документировать паттерн: `styles={mergeAdminDrawerStyles(passthrough)}` или spread по слоям Mantine. |
| **Публичный API** | Экспорт из `frontend/src/shared/ui/index.ts` рядом с `GlassModal`. Единая точка импорта для админки. |
| **Регрессия импортов** | Опционально: ESLint `no-restricted-imports` — запрет прямого `Drawer` из `@mantine/core` в `admin/**`, разрешён только в `AdminDrawer.tsx` (или в тестах). Снижает «обратное заражение» голым Drawer. |

### 9.2 Визуал и токены

| Тема | Рекомендация |
|------|----------------|
| **Glass vs solid для панели** | Для **длинного** контента чаще читабельнее **непрозрачный** фон панели + лёгкая тень; у `GlassModal` — стекло по центру. В §3.1 явно зафиксировать выбор (не оставлять только «согласовать»): например панель **solid**, модалка **glass** — или оба glass с разной opacity. |
| **`prefers-reduced-motion`** | Учесть в `shellPanelStyles`: слабее blur/анимация или мгновенное появление — доступность и слабые машины. |
| **Скругление** | Mantine `Drawer` — скруглять в первую очередь **внутренний край** (слева у `position="right"`); не ломать `radius` у `Paper` внутри контента. |

### 9.3 Поведение и краевые случаи

| Тема | Рекомендация |
|------|----------------|
| **Два Drawer на одной странице** | Пример: `AdminOmniChatPage` — два независимых `Drawer`. Проверить **z-index** и одновременное открытие (обычно только одно; если оба — Mantine 7 должен поднять последний). Зафиксировать в QA ручной сценарий. |
| **Кастомные хоткеи** | В `AdminOmniChatPage`: `Escape` — закрыть Drawer формы/задачи; **`mod+shift+l`** — переключить свёрнутость правого инспектора (не срабатывает в полях ввода по умолчанию). Убедиться, что порядок обработчиков не ломает закрытие Drawer. Smoke после изменений. Канон: `ARCH_FRONTEND_TECH_PASSPORT_DENTAL_BOOKING.md` §2.2.1. |
| **Семантика «модалка» из Drawer** | Пример: `AdminRetentionPage` — блок с комментарием «Модалка», но разметка — `Drawer`. Оболочку выровнять через `AdminDrawer`; **перенос в центральный Modal** — отдельное продуктовое решение, не блокер для этого эпика. |

## 11. Северная звезда: критерии «твёрдого» админ-продукта (лид / @QA_ARCH)

Цель — не только «красивая полоса», а продукт, который **выдерживает критику** по потокам, безопасности и длительному использованию.

| Измерение | Что проверяем | Зачем раньше казалось «отдельно от оболочки» |
|-----------|----------------|-----------------------------------------------|
| **Логистика** | Порядок разделов, отсутствие дублей смысла, предсказуемый путь «список → деталь → назад», Spotlight как подстраховка | Оболочка не решает **куда** ведёт меню и сколько кликов до задачи. |
| **Безопасность** | RBAC на экранах, нет утечки действий без прав, осознанные модалки на разрушительные операции, ПД не в лишних логах/URL | Визуал не заменяет **политику** и аудит. |
| **Удобство (efficiency)** | Повторяющиеся действия без лишних модалок, понятные primary/secondary, клавиатура где уместно | Power users экономят **секунды × сотни раз в неделю**. |
| **Мягкость (8×5)** | Не «кричит» контрастом и blur без нужды, нет лишнего движения (`prefers-reduced-motion`), читаемые шрифты/плотность, отдых глаз | Иначе «красиво» = **усталость** к пятнице. |
| **Согласованность** | Один язык панелей и модалок (`AdminDrawer` + `GlassModal` + токены) | Иначе лида критикуют за **лоскутное** ощущение. |
| **Ответственность** | Известен владелец слоя, решения задокументированы, регресс не анонимен | Иначе при масштабе команды и пользователей **никто не отвечает** за полоску, которая стоила часа простоя клиники |

**Ответ на вопрос «зачем держать в голове»:** не чтобы **отказаться** от полной цели, а чтобы **не смешивать** в одном релизе: (а) техническую миграцию оболочки, (б) продуктовую перестройку меню, (в) сценарии двух слоёв. Ниже §12 — **как всё запланировать и сделать порциями** без отказа от критериев лида.

## 12. Фазы B–E (после A) — логистика, мягкость, потоки без «большого взрыва»

| Фаза | Фокус | Минимизация риска |
|------|--------|-------------------|
| **A (§3–§6)** | `shellPanelStyles`, `AdminDrawer`, миграция `Drawer`, выравнивание `GlassModal` | Нет смены маршрутов; малые PR; ESLint опционально |
| **B** | Левое меню: группы, порядок enterprise, **одна** политика дублей с «Настройки», перенос «скрыть ленту» из списка разделов | Отдельные PR; сохранить **все** URL; согласовать порядок с @LEAD |
| **C** | Двухслойные сценарии (Drawer + Modal): правила «что закрывается первым», документирование исключений (OmniChat) | Только точечные страницы; ручной QA-чеклист |
| **D** | **Мягкость:** токены blur/contrast под длительную работу; sticky-действия в длинных панелях где больше всего боли (по метрике/опросу) | Feature-flag или постепенное включение; `prefers-reduced-motion` |
| **E** | Безопасность UX: подтверждения на destructive, видимость прав, выравнивание с `ARCH_DEV_SEC_RBAC_022` на экранах | Совместно с бэкендом; не только визуал |

Фазы **B–E** можно вести **параллельно по разным людям**, но не **смешивать в одном PR** с фазой A без необходимости.

При необходимости завести отдельный файл только для **IA меню** (например `ARCH_FRONTEND_ADMIN_IA_2026.md`) — ссылка из фазы **B**.

## 13. Почему не «всё сразу» — и почему это не отказ от цели

- **Один большой PR** (оболочка + меню + потоки + SEC) = высокий риск регрессии, долгий ревью, невозможность откатить частично.
- **Фазы** = каждая даёт **измеримый** результат и возможность **отката**.
- Цель **«твёрдый для лида сайт»** остаётся; этот артефакт **явно включает** критерии §11 и дорожную карту §12; **фаза A — первый безопасный шаг**, не вся работа.

**Минимизация рисков (сводка):** маленькие PR → чеклисты QA по фазе → отдельный трек для меню → не смешивать визуал и IA без согласования @LEAD.

## 14. Протокол @ARCH → @QA_ARCH (меню, потоки, IA)

Когда в рамках этого трека планируется не только оболочка (**фаза A**), но и **перестройка меню / пользовательских потоков** (**фазы B–C и смежное**), артефакт должен пройти **архитектурное усиление** и **проверку качества** по цепочке ниже.

### 14.1 Вклад @ARCH (обязательно до крупных PR по фазам B+)

| Действие | Содержание |

## 15. Enterprise-grade: твёрдость, ответственность, планка «победителя» (@ARCH)

*Контекст масштаба:* продукт рассчитан на **высокую нагрузку и дисциплину эксплуатации**. Даже если **активных админов** в конкретном тенанте меньше «сотен тысяч», **планка качества** для оболочки и навигации — **как у global B2B SaaS** (Stripe, Linear, Notion Admin): иначе долг оператора в 8×5 превращает мелкий дефект в **репутационный и финансовый** риск на уровне организации.

### 15.1 Конкурс решений: «победитель» vs посредственность

| Критерий | Посредственное решение (неприемлемо для enterprise) | **Победитель** (целевой уровень артефакта) |
|----------|---------------------------------------------------|-------------------------------------------|
| **Единый язык** | Каждая страница чуть своим Drawer/модалкой | Один `AdminDrawer` + токены + `GlassModal`; отклонения **документированы** |
| **Ответственность за регресс** | «Сломалось — починим» без владельца | Владелец слоя (**@LEAD** FE / назначенный owner) + запись в журнале §8 |
| **Доступность** | «Mantine сам всё сделает» | Явная цель: клавиатура, фокус, `prefers-reduced-motion`, контраст заголовков панели — **чеклист** перед релизом фазы |
| **Безопасность UI** | Кнопки видны всем; 403 только с бэка | **Fail-closed** по ролям на уровне маршрутов/кнопок в духе `ARCH_DEV_SEC_RBAC_022`; UI не подменяет авторизацию, но **не обещает** недоступное |
| **Наблюдаемость** | Пользователь молча страдает | По возможности: события/метрики открытия панелей и ошибок (согласовать с OBS); не логировать ПД |
| **Эволюция** | Размазать токены по файлам | **Один источник** `shellPanelStyles`; breaking change — **версия + заметка** в CHANGELOG / техпаспорте |
| **Потоки** | Меню как список «что вспомнили» | IA с **критериями** §11–§12 + отдельный IA-артефакт при фазе B; согласование @LEAD |

### 15.2 Архитектурная «твёрдость» (non-functional, фронт)

- **Контракт компонента:** публичный API `AdminDrawer` / токенов — **стабильный**; расширения через опциональные пропсы, не ломая существующие вызовы.
- **Производительность:** тяжёлый blur на overlay — под **бюджет** (не блокировать main thread при открытии; при сомнениях — `prefers-reduced-motion` / упрощённый overlay).
- **Устойчивость:** критичные страницы админки — по возможности **error boundary** вокруг контента панели/страницы, чтобы сбой виджета не валил весь shell.
- **Согласованность с паспортом зрелости:** см. **`../../ARCHITECTURE_EXCELLENCE_PASSPORT.md`** (scorecard, NFR, §про фронт/OBS по возможности).
- **Мультитенантность:** смена клиники не должна оставлять «хвосты» открытых панелей с чужими данными — **закрытие drawer** при смене контекста (явное правило в фазе B/C при работе с `AdminLayout`).

### 15.3 Ответственность (RACI) по фазам

Упрощённая модель; **A** = подотчётный за результат, **R** = исполнитель.

| Деятельность | R | A | C | I |
|--------------|---|---|---|---|
| Фаза A: `shellPanelStyles`, `AdminDrawer`, миграция | @DEV | @LEAD (FE) | @ARCH, @QA_ARCH | @QA |
| Фаза B: IA меню, дубли настроек | @DEV | @LEAD | @ARCH, @QA_ARCH | — |
| Критерии приёмки релиза фазы | @QA_ARCH | @LEAD | @ARCH | — |
| Спор «ломаем ли URL / роль» | — | @LEAD | @ARCH, @QA_ARCH | @DEV |

**Правило:** без **A** в релизе фазы нет «тихого» merge в main для затрагивающих shell изменений.

### 15.4 Безупречность как процесс, не как разовый акт

- **Регрессионный набор:** после фазы A — минимальный список страниц с `AdminDrawer` (entity + 2–3 тяжёлых экрана) в ручном или полуавтоматическом прогоне.
- **Долг:** отклонения от §15.1 (таблица «победитель») заносить в журнал §8 или в техдолг с владельцем — **не накапливать молча**.
