## 1. Контекст и существующее состояние

### 1.1. Роль AI в Loyalty

- По `ARCH_LOYALTY_NEXT.md` и `BUSINESS_PLAN_NEXT.md`:
  - Loyalty‑домен отвечает за:
    - программы лояльности (пакеты, депозиты, бонусы, скидки);
    - балансы и историю списаний/начислений.
  - AI‑слой должен:
    - помогать находить риски/возможности (низкая активность, истекающие пакеты);
    - предлагать кампании удержания/реактивации;
    - работать через Tasks/Attention и Omnichannel, а не напрямую с пациентами.

### 1.2. Проблема (GAPS LOY‑3, TASK‑2, OMNI‑3)

По `BACKEND_GAPS_Loyalty_NEXT.md`, `BACKEND_GAPS_Tasks_NEXT.md`, `BACKEND_GAPS_Omnichannel_NEXT.md`:

- Сейчас:
  - есть базовые механизмы:
    - истечения пакетов/балансов;
    - некоторые маркетинговые/уведомительные сценарии;
  - но:
    - нет единого AI‑уровня, формализующего кампании лояльности;
    - сигналы о рисках активности не всегда оформлены как Attention/Tasks;
    - связь с Omnichannel и AI Orchestrator фрагментарна.

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_LOYALTY_NEXT.md` — доменная модель лояльности.
- `ARCH_TASKS_NEXT.md`, `ARCH_DEV_TASKS_MODEL_020.md`, `ARCH_DEV_TASKS_AI_021.md` — Tasks & AI Task Manager.
- `ARCH_OMNICHANNEL_NEXT.md`, `ARCH_DEV_OMNI_REGISTRY_015.md` — Omnichannel и AI Orchestrator.
- `ARCH_DEV_OMNI_POLICY_016.md`, `ARCH_DEV_AI_TOKENIZATION_025.md` — политика ПД и токенизация.
- `ARCH_DEV_LOY_FAMILY_013.md` — FamilyLink и семейный шэринг (базовый контекст для кампаний).

## 2. Целевое состояние AI‑слоя лояльности

### 2.1. Жёсткие инварианты

1. **AI‑кампании опираются на доменные данные Loyalty, а не на «сырые» SQL/эксели.**
   - Любые решения принимаются:
     - на основе агрегатов/метрик из Loyalty (балансы, активность, истечения);
     - через доменные сервисы, а не прямые запросы.

2. **AI генерирует предложения/задачи, а не выполняет деньги/скидки напрямую.**
   - Скидки/промо/списания:
     - остаются в ответственности Loyalty/ERP и ручных/полуавтоматических сценариев;
   - AI:
     - подсказывает, **кому** и **что** предложить;
     - создаёт Tasks/Attention/Omnichannel‑черновики.

3. **Все AI‑кампании управляются через настройки и RBAC.**
   - Владелец/менеджер клиники:
     - включает/выключает классы кампаний;
     - задаёт лимиты/частоту;
     - не может случайно «запустить спам».

4. **AI‑слой соблюдает SEC/PD политику.**
   - Любые анализы/кампании:
     - проходят через `SafeAiClient` + `AiSanitizer` + tokenization‑слой;
     - не выдают внешнему AI ПД пациентов.

## 3. Архитектурный дизайн AI‑кампаний

### 3.1. Базовые сценарии (MVP‑набор)

Примеры классов кампаний (перечень согласуется с бизнесом):

- **Истекающие пакеты/депозиты:**
  - клиенты с пакетами, срок действия которых заканчивается в ближайшее время;
  - цель:
    - напомнить;
    - предложить визит/продление.

- **Низкая активность при высоком балансе:**
  - клиенты с существенным остатком в пакетах/депозитах, но без визитов за период;
  - цель:
    - напомнить о возможностях пакета;
    - предложить план лечения/акцию.

- **Реактивация «спящих» клиентов:**
  - клиенты без визитов давно, но с историей активности/лояльности.

Каждый сценарий:

- определяется как **кампания** с:
  - правилами отбора;
  - каналами (Tasks/Omni/SMS/e‑mail, если есть);
  - шаблонами действий.

### 3.2. Компоненты

- `LoyaltyCampaignSettings`:
  - per‑clinic конфиг:
    - включённые кампании;
    - лимиты (количество контактов/день, пер‑пациент и т.п.);
    - каналы.

- `LoyaltyCampaignEngine`:
  - собирает кандидатов (списки пациентов) по правилам;
  - взаимодействует с AI:
    - для персонализации сообщений/рекомендаций (опционально);
  - создаёт:
    - Tasks/Attention (для операторов);
    - или черновики Omnichannel‑диалогов.

- `LoyaltyCampaignAnalyzer` (AI‑часть, может быть AI‑tool):
  - помогает:
    - сегментировать клиентов;
    - предлагать тексты/подходы кампаний;
  - работает через Omnichannel AI Orchestrator/registry.

## 4. Интеграция с Tasks & Omnichannel

### 4.1. Tasks/Attention

- Для каждого срабатывания кампании:
  - создаётся:
    - `AttentionItem`/`Task` типа:
      - `LOYALTY_EXPIRING_PACKAGE`;
      - `LOYALTY_HIGH_BALANCE_LOW_ACTIVITY`;
      - `LOYALTY_REENGAGEMENT`;
  - через TaskService и связку по `ARCH_DEV_TASKS_MODEL_020.md`.
- Tasks:
  - содержат:
    - ссылку на пациента (id/токен);
    - суть предложения;
    - приоритет и срок;
    - `created_by="ai"` (если инициатор — AI‑слой) или `system`.

### 4.2. Omnichannel

- При наличии Omnichannel/AI:
  - вместо/в дополнение к задачам:
    - могут создаваться черновики диалогов/кампаний:
      - предварительно сгенерированные AI тексты;
      - токенизированные идентификаторы пациентов.
- Оператор:
  - видит рекомендации;
  - утверждает/редактирует/отклоняет отправку.

## 5. Наблюдаемость, SEC/RBAC и контроль шума

### 5.1. Роли и доступ

- По `ARCH_DEV_SEC_RBAC_022.md`:
  - операции с кампаниями/AI‑слоем лояльности:
    - относятся к чувствительным (маркетинг, массовое воздействие на пациентов);
  - отдельные пермишены:
    - `loyalty.campaigns.manage`;
    - `loyalty.campaigns.run`;
    - (опционально) `ai.loyalty.analyze`.

### 5.2. Логирование и метрики

- Логи:
  - запуск кампаний;
  - количество сгенерированных кандидатов;
  - создание Tasks/Omni‑черновиков;
  - изменения настроек кампаний.
- Метрики:
  - число кампаний и контактов/период;
  - конверсия:
    - отклик (ответы/записи/продления);
    - отмены/жалобы (если есть обратная связь).

### 5.3. Контроль шума и этики

- Настройки и бизнес‑политика определяют:
  - частоту контактов:
    - не более N кампаний/месяц на пациента;
  - фильтры:
    - исключение определённых категорий (например, отказавшиеся от коммуникаций);
  - каналы:
    - не использовать слишком агрессивные каналы без явного согласия.

## 8. Статус реализации (@QA_ARCH / 2026‑03)

**Сделано (MVP правил без LLM):**

- Таблица и сущность **`loyalty_campaign_settings`**, миграции Alembic; DTO и **`default_loyalty_campaign_settings_read`** для GET без побочного INSERT.
- **`run_campaigns_for_clinic`** — три типа задач с `attention_kind`: `LOYALTY_EXPIRING_PACKAGE`, `LOYALTY_HIGH_BALANCE_LOW_ACTIVITY`, `LOYALTY_REENGAGEMENT`; `source="system"`; пороги согласованы с Attention Feed (константы из `attention_feed_service`).
- Лимиты: на клинику/день, на пациента/день, **на пациента/месяц (UTC)**, cooldown по типу; резервирование пациентов между кампаниями в одном прогоне; опционально **не дублировать** expiring‑task, если уже есть SMS `expiring_package` за сегодня.
- Учёт **opt‑out** пациента: `disable_all_notifications`, `disable_reminders` (expiring + high balance), `consent_mailing` (только реактивация).
- Admin API: `GET/PATCH /admin/loyalty/campaign-settings`, `POST /admin/loyalty/campaigns/run`; RBAC `manage_loyalty_campaigns`, `run_loyalty_campaigns` (+ клинико‑скоупные роли в миграции).
- Celery: **`run_loyalty_campaign_engine_all_clinics`** (beat daily); метрики `loyalty_campaign_*`, `loyalty_campaign_batch_errors_total`.
- Частичный индекс по `tasks` для `LOYALTY_%`; вкладка **«Кампании»** в `AdminLoyaltyPage` (настройки + ручной запуск).

**Не сделано / вне текущего MVP (см. также «На потом» в `ARCH_DEV_LOY_AI_014_TASKS.md`):**

- AI‑персонализация (`SafeAiClient`, Orchestrator, `LoyaltyCampaignAnalyzer`), Omnichannel‑черновики, токенизация для кампаний.
- FamilyLink: перенос задач на владельца ресурса — только зафиксировано в коде как ограничение; полная логика — по `ARCH_DEV_LOY_FAMILY_013`.
- Конверсия кампаний в отчётах/OBS, расширенные e2e‑тесты.
