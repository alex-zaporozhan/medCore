### 1. Understand — собрать картину текущего RBAC (без правок кода)

1.1. **Собрать список источников RBAC.**  
1.1.1. Найти реализацию `require_permissions` и перечисления/константы пермишенов (словарь прав, маппинг ролей).  
1.1.2. Найти все вхождения `require_permissions(` по коду.  
1.1.3. Найти все места с ручными проверками ролей/админских флагов: `user.is_admin`, `user.role == "owner"` и т.п.

1.2. **Построить таблицу чувствительных эндпоинтов по доменам.**  
1.2.1. Для роутеров ERP, Loyalty, Tasks/Attention, Attribution, AI‑settings и чувствительных CRM/Booking‑операций выписать: путь, метод, связанный доменный сервис.  
1.2.2. Для каждого такого эндпоинта зафиксировать: текущие `required_permissions` (если есть), наличие/отсутствие ручных проверок ролей, наличие/отсутствие проверок `clinic_id`.  
1.2.3. Сохранить таблицу в отдельный файл (например, `./SEC_RBAC_ENDPOINTS_MAP.md`) или как раздел в `ARCH_DEV_SEC_RBAC_022.md`.

1.3. **Сопоставить найденное с SEC‑/GAPS‑аудитом.**

1.3.3. Отдельно пометить пункты, которые не могут быть закрыты в этом DEV_PROMPT (если такие есть) — с коротким пояснением.

### 3. Implement — нормализация RBAC в коде (по эндпоинтам)

3.1. **Обновить `require_permissions` в роутерах ERP и Loyalty.**  
3.1.1. Для каждого чувствительного эндпоинта ERP (кассы, платежи, проводки, ЗП, склад) установить `require_permissions` строго по матрице (например, `erp.finance.manage`, `erp.inventory.manage`, `erp.payroll.manage`).  
3.1.2. Для эндпоинтов Loyalty (продукты лояльности, кошельки, корректировки) установить соответствующие пермишены (`loyalty.products.manage`, `loyalty.wallets.manage`, `loyalty.adjustments.manage`).  
3.1.3. Удалить ручные проверки `user.is_admin`/`user.role == ...` в этих роутерах, если они дублируют смысл пермишенов.

3.2. **Обновить RBAC в Tasks/Attention и Attribution.**  
3.2.1. В роутерах Tasks/Attention для операций создания/изменения/массового обновления задач и критичных сигналов добавить `require_permissions` (`tasks.manage`, `attention.resolve_critical` и т.п.) по матрице.  
3.2.2. В роутерах Attribution/маркетинговой отчётности добавить пермишены `attribution.reports.read`, `attribution.config.manage` и др. для чтения отчётов и управления конфигурацией.  
3.2.3. Снова убрать ручные проверки ролей, заменяя их на проверку пермишенов.

3.3. **Нормализовать доступ к AI‑настройкам и AI‑операциям.**  
3.3.1. В роутерах, работающих с `ClinicAiSettings` и AI‑конфигами, добавить пермишены `ai.settings.manage` (и при необходимости более тонкие).  
3.3.2. В точках запуска продвинутых AI‑операций (массовые рассылки, bulk‑изменения) добавить соответствующие пермишены (`ai.tools.run_advanced` и др.).  
3.3.3. Убедиться, что AI‑админка и опасные действия доступны только ролям, предусмотренным матрицей (обычно owner/manager/marketing, но не registrar/doctor).

### 4. Integrate — clinic_id и системные/AI‑контексты

4.1. **Жёстко провести `clinic_id` в чувствительных эндпоинтах.**  
4.1.1. Для всех эндпоинтов в таблице чувствительности проверить, что запросы к сущностям всегда фильтруются по `clinic_id` текущего контекста.  
4.1.2. Если фильтрация сделана только на фронте или в роутере частично — перенести/дублировать проверку в доменный сервис так, чтобы она не могла быть обойдена.  
4.1.3. При необходимости ввести helper/утилиту вида `ensure_object_belongs_to_clinic(obj, clinic_id)` и использовать её на пути всех критичных операций.

4.2. **Оформить системные и AI‑роли.**  
4.2.1. Определить в коде отдельную роль/контекст `system_ai` (и, при необходимости, другие технические роли) и явно назначить ей минимальный набор пермишенов из матрицы.  
4.2.2. В Celery‑тасках, AI‑оркестраторе и других фоновых процессах заменить “глобальные” привилегии на этот ограниченный набор прав.  
4.2.3. Проверить, что системный/AI‑контекст не может выполнять действия, которые матрица относит только к `owner`/`manager` и т.п.

### 5. Observe — аудит, логи и проверка RBAC

5.1. **Добавить аудит‑логи для критичных операций.**  
5.1.1. В точках изменения ERP‑объектов (платежи, проводки, ЗП, склад) добавить структурированные логи с: инициатором (user/system), `role`, `permissions`, `clinic_id`, типом операции и результатом.  
5.1.2. Аналогично — в точках операций с пакетами/депозитами и кошельками Loyalty, изменений AI‑настроек, доступа к владельческим ERP/Attribution‑отчётам, массовых изменений Tasks/Attention.  
5.1.3. Убедиться, что логи не содержат ПД (телефонов, email и др.) в явном виде.

5.2. **Покрыть RBAC тестами.**  
5.2.1. Для каждого типа критичной операции написать/обновить тесты, проверяющие:  
       - роль с нужными пермишенами получает 2xx;  
       - роль без нужных пермишенов получает 403/ошибку доступа.  
5.2.2. Добавить тесты на multi‑tenant: операции с объектами другой клиники отклоняются.  
5.2.3. Добавить тесты на системный/AI‑контекст: он может выполнять только те действия, которые ему разрешены матрицей.

## На потом (@QA_ARCH — предложения)

Рубрика для **эволюции и гарантий** после базовой нормализации `require_permissions` и матрицы в `ARCH_DEV_SEC_RBAC_022.md`; не отменяет обязательность проверок на бэкенде.

1. **Расширение матрицы при новых эндпоинтах** — правило: новый чувствительный роут → строка в матрице **до** merge (или явный ADR «временно как owner»), синхронизация с `SEC_RBAC_ENDPOINTS_MAP` / `ARCH_DEV_SEC_RBAC_022.md`.  
2. **UI fail‑closed** — на фронте не показывать действия без права (кнопки/пункты меню), не подменяя серверную проверку; см. `ARCH_FRONTEND_ADMIN_SHELL_DRAWER_2026.md` §15.1, `TECH_PASSPORT_FRONTEND_UI_LOGIC.md` при наличии.  
3. **Периодический аудит расхождений** — скрипт или CI job: сверка списка `require_permissions` / путей роутеров с картой эндпоинтов; падение при «новый роут без записи в карте».  
4. **Immutable audit для критичных мутаций** — если §5.1 не покрывает все кейсы: запись в `AuditLog` (кто, когда, `clinic_id`, тип операции, hash до/после) для платежей, ЗП, ручных корректировок лояльности, смены AI‑настроек — без ПД в теле лога.  
5. **Роли ниже `owner` и отчёты** — явное решение: выдача `erp.owner_reports.read` / `attribution.reports.read` ролям `manager` и др. (сейчас часто только `owner` в seed; см. `NONFUNCTIONAL_AUDIT_NEXT.md` §5, миграция `k7l8m9n0o1p2`).  
6. **Временные делегирования / смена ответственного** — отдельный эпик (вне базового RBAC): time‑boxed permission, согласование с @LEAD.  
7. **Фоновые и AI‑контексты** — регулярный аудит новых Celery‑тасков: не расширять фактические права `system_ai` / технических ролей сверх матрицы §4.2.  
8. **Спецификация вне ARCH** — при стабилизации вынести утверждённую матрицу в `../../SEC_RBAC_SPEC.md` (как предложено в §6.1.2) и дать перекрёстные ссылки из `ARCHITECTURE_EXCELLENCE_PASSPORT.md`, `NONFUNCTIONAL_AUDIT_NEXT.md`.  
9. **Тесты на регресс матрицы** — параметризованные тесты «роль X не имеет permission Y» при добавлении новых пермишенов (генерация из таблицы или snapshot).

**Связь со сводным бэклогом:** `./QA_ARCH_BACKLOG_NA_POTOM_UNIFIED.md` (ID **SR1–SR9** в приложении).
