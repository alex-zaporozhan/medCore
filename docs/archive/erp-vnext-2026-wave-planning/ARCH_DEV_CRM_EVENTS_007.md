## ARCH_DEV_CRM_EVENTS_007 — автодвижение лидов по событиям

> DEV_PROMPT_CRM_EVENTS_007 — «автодвижение лидов по событиям (CRM‑1)»

---

## 1. Контекст и существующее состояние

### 1.1. Роль CRM‑воронки в системе

- CRM‑домен связывает:
  - **Omnichannel** (контакты и диалоги),
  - **Booking** (записи и статусы визитов),
  - **ERP** (деньги по визитам),
  - **Attribution** (источники трафика).
- `LeadCard` отражает движение сделки по стадиям:
  - от первого контакта → до записи/визита → до денег/потери.

### 1.2. Проблема (GAPS CRM‑1, ATT‑1, TASK‑1)

- По `BACKEND_GAPS_CRM_NEXT.md` и `ARCH_CRM_NEXT.md`:
  - автодвижение лидов по событиям других доменов реализовано частично:
    - создание и смена стадий в основном происходят руками через `admin_crm.py` и Kanban;
    - связи «событие в Booking/ERP/Omnichannel → изменение лида» не оформлены как единый слой.
- Риски:
  - воронка зависит от дисциплины пользователей (drag&drop);
  - отчёты по конверсии/ROI не соответствуют фактическим событиям (часть лидов «застывает» на стадиях);
  - сложно запускать AI‑подсказки и задачи по CRM (нет прозрачных событий).

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_CRM_NEXT.md` — целевая модель CRM (воронка, автодвижение, деньги).
- `ARCH_BOOKING_NEXT.md` и `ARCH_ERP_NEXT.md` — статусы визитов и ERP‑узел.
- `ARCH_ATTRIBUTION_NEXT.md` — связка UTM → лид → запись → деньги.
- `ARCH_TASKS_NEXT.md` — задачи по «застывшим» и проблемным лидам.
- `ARCH_DEV_BKG_CORE_001.md`, `ARCH_DEV_BKG_STATE_002.md`, `ARCH_DEV_OBS_CHAINS_023.md`:
  - определяют единый фасад завершения визита, статусы и наблюдаемость по цепочке Booking→ERP/CRM.

### 1.4. Статус реализации (v1 в коде, зафиксировано @DEV; сверка @QA_ARCH)

> Детальный перечень файлов, метрик и инвариантов — **`ARCH_DEV_CRM_EVENTS_007_TASKS.md`** (раздел «Выполнено в коде»); остаточные риски и предложения — там же, рубрика **«На потом»** (в т.ч. блок **@QA_ARCH**).

## 2. Целевое состояние автодвижения лидов

### 2.1. Жёсткие инварианты

1. **Стадии лида определяются событиями доменов, а не только руками.**
   - Для ключевых событий Booking/ERP/Omnichannel:
     - есть предсказуемые правила перехода `LeadStage`.

2. **Автодвижение не ломает ручной контроль.**
   - Пользователь всегда может:
     - вручную скорректировать стадию;
     - зафиксировать исключения (например, «лид закрыт по нестандартной причине»);
   - но система всё равно:
     - записывает и использует исходные события для аналитики.

3. **CRM опирается на единый источник правды по статусам и деньгам.**
   - Статусы визитов — из Booking (через фасад завершения визита и enum статусов);
   - фактические суммы — из ERP‑узла (DEV_PROMPT_ERP_NODE_010/011/012).

4. **Все переходы стадий логируются и наблюдаемы.**
   - Для каждого изменения стадии:
     - фиксируется инициатор (событие/пользователь/AI), причина, прежняя и новая стадия, `trace_id`.

### 2.2. Базовые правила автодвижения (high‑level)

> Конкретные стадии и названия уточняются по `ARCH_CRM_NEXT.md` и конфигурации pipelines, но архитектурно фиксируем паттерны.

- **Создание лида:**
  - триггеры:
    - новый Omnichannel‑контакт без существующего лида;
    - форма заявки/регистрации с маркетинговым source;
  - действие:
    - создаётся `LeadCard` в стартовой стадии (например, `New / Inbox`);
    - связывается с `omnichannel_contact_id`/`patient_id`/utm‑метками.

- **Запись/визит:**
  - триггер:
    - создание `Booking`, связанной с лидом/пациентом;
  - действие:
    - перевод в стадию «Записан» / «Appointment Scheduled».

- **Завершение визита:**
  - триггер:
    - `Booking.status` переходит в `completed` через фасад;
  - действие:
    - перевод в стадию «Win / Успешно»;
    - обновление `actual_value` по ERP‑данным.

- **Отмена/No‑show:**
  - триггеры:
    - `Booking.status` → `canceled_*` или `no_show`;
  - действия:
    - перевод в «Lost / Потерян» (или отдельные подстадии — например, «No‑show»);
    - опциональная генерация задач/attention по правилам Tasks‑домена.

- **Застой/rot:**
  - триггеры:
    - отсутствие событий (новых диалогов, записей, визитов) дольше заданного срока;
  - действия:
    - перевод в стадию «Stale»/«Need Follow‑up»;
    - генерация задач (TASKS_MODEL_020 / TASKS_AI_021).

## 3. Архитектурный дизайн: событийный слой CRM

### 3.1. Событийная модель

- Вводим чёткие доменные события (event‑DTO), например:
  - `LeadEventContactCreated`
  - `LeadEventBookingCreated`
  - `LeadEventVisitCompleted`
  - `LeadEventBookingCancelled`
  - `LeadEventNoShow`
- Источники:
  - Omnichannel (создание контакта/диалога);
  - Booking/ERP (создание записи, завершение визита, отмена, no‑show);
  - системный/AI‑слой (обнаружение застоя).
- События:
  - передаются в слой `LeadLifecycleService` или аналог;
  - не зависят от конкретного транспорта (синхронные вызовы или очередь — решается реализацией DEV).

### 3.2. LeadLifecycleService

- Новый сервис в application‑слое, например `src/application/services/lead_lifecycle_service.py`.
- Ответственность:
  - обработка входящих событий;
  - поиск/создание `LeadCard` по контексту (clinic, contact, patient, booking);
  - определение целевой стадии;
  - переход стадии (через централизованный механизм, аналогичный `BookingStatus` state‑machine).
- Методы (эскиз):
  - `handle_contact_created(event)`
  - `handle_booking_created(event)`
  - `handle_visit_completed(event)`
  - `handle_booking_cancelled(event)`
  - `handle_no_show(event)`
  - `handle_stale_lead(event)`

### 3.3. Связь с LeadPipeline/LeadStage

- Определяем маппинг:
  - `event_type + текущая_стадия` → `новая_стадия`.
- Маппинг:
  - хранится либо в конфигурации (таблица/настройки CRM), либо в коде как словарь по умолчанию;
  - должен быть:
    - прозрачен для администраторов/owner’ов (понимание, как события двигают сделки);
    - пригоден для будущей конфигурируемости.

### 3.4. Интеграция с Attribution и ERP

- При обработке событий:
  - `LeadEventVisitCompleted`:
    - подтягивает ERP‑данные по факту выручки;
    - обновляет `actual_value`, `closed_at`, source/utm для атрибуции.
  - связь с `ARCH_ATTRIBUTION_NEXT`:
    - обеспечивает цепочку `utm` → `LeadCard` → `Booking` → `FinancialTransaction`.

## 4. Наблюдаемость и Tasks/Attention

### 4.1. Логирование

- Для каждого события и перехода стадий:
  - логируем:
    - `trace_id`, `lead_id`, `clinic_id`, `event_type`, `from_stage`, `to_stage`, инициатор;
    - причину (код/описание правила).

### 4.2. Метрики

- Базовые метрики:
  - число лидов, создаваемых по каналам/источникам;
  - частота переходов в «Win»/«Lost» по типам событий;
  - доля «застоявшихся» лидов;
  - среднее время от `New` до `Win`/`Lost`.

### 4.3. Tasks & Attention

- Для проблемных случаев:
  - создание `AttentionItem`/`Task`:
    - лиды, в которых:
      - часто происходят отмены/неявки;
      - долго нет движения (rot);
      - есть значительная оценочная сумма, но нет визитов/денег.
- Связь с `ARCH_TASKS_NEXT`:
  - задачи содержат ссылки на `lead_id`/`booking_id`/`patient_id` и `trace_id`;
  - AttentionFeed показывает CRM‑события в одном потоке с Booking/ERP/Omnichannel.
