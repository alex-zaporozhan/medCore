## 0. Зачем отдельный промпт

После закрытия множества эпиков хвосты лежат в концах **разных** TASK-файлов. Сводный документ **QA_ARCH_BACKLOG_NA_POTOM_UNIFIED** даёт **единую нумерацию ID** для планирования. Этот файл — **как исполнять**: пакетами, с DoD и без раздувания scope.

### 0.1 Философия исполнения (глубокая проработка)

Цель — **не «пройти чеклист любой ценой»**, а **прагматично укрепить продукт**: минимальные, согласованные инкременты, которые снижают риск регрессий и логических дыр **в перспективе**, а не только закрывают формулировку DoD на бумаге.

- **Укрепление ≠ упрощение.** Срезать сложность (например убрать переменные дашборда, секции, документацию в панелях) ради «меньше движущихся частей» **без** анализа рисков — антипаттерн: можно получить «крепкую дубину» без удобства OPS и без предупреждения типовых ошибок (неверный datasource, несогласованные запросы с алертами). Правильный ответ — **явные контракты** (импорт Grafana через `__inputs`, зафиксированные запросы в NFR, согласованность rules ↔ dashboard) и вынесение **слишком тяжёлой** глубины в отдельную фазу: `./QA_ARCH_POST_WAVES_FUNDAMENTALS_BACKLOG.md`.
- **Глубина vs скорость:** если пункт допускает «алерты *или* документ», предпочтителен **полный контур** (метрики с контролируемой кардинальностью + правила + зафиксированные запросы; для OPS — **дашборд как код** в `deploy/grafana/dashboards/`, когда это уместно). Полный L2 perf и тяжёлая инфра — по волнам **W5+**; на текущем этапе — **добросовестно углублять** там, где это реально снижает коэффициент будущих ошибок (hot paths completion/ERP, цепочки OBS, витрины), **без** ломки рабочего кода и без «налепленных» обходов.
- **W1 / W2 вместе:** W1 — наблюдаемость и контроль кардинальности; W2 — **корректность и предсказуемость** витрин ERP (аудит refresh, тесты на краевые суммы, фиксация планов запросов), без обхода эталона `ErpReportsRepository` без ADR.
- **Кардинальность и tenant:** для высокочастотных серий — **`clinic_bucket` / `account_bucket`** (`src/core/prometheus_labels.py`), не сырые UUID в лейблах; детализация по клинике — в **структурных логах**. Остаточные серии с `clinic_id` в лейблах явно помечать в NFR/бэклоге как техдолг.
- **Целостность:** каждый PR должен оставлять систему **в согласованном состоянии** (тесты затронутых модулей, обновление NFR/OpenAPI при изменении контрактов).

## 1. Инварианты (не ослаблять)

- **Multi-tenant:** везде `clinic_id`, проверки принадлежности сущностей.  
- **RBAC:** новые эндпоинты/фоновые job’ы — через матрицу `src/application/rbac_matrix.py` + миграции permissions при необходимости.  
- **ПД / AI:** внешний провайдер + запрет ПД — `SafeAiClient`, токенизация, `ARCH_DEV_OMNI_POLICY_016`.  
- **Корректность ERP:** витрины и CRM-агрегаты не противоречат эталону `ErpReportsRepository` / событиям без явного ADR.
