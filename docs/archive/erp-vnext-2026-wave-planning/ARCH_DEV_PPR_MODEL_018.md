## 1. Контекст и существующее состояние

### 1.1. Роль Paperless в системе

- Paperless‑формы покрывают:
  - согласия на обработку ПД и медицинские вмешательства;
  - договоры/анкеты пациента;
  - внутренние формы (чек‑листы, план лечения и т.п.).
- Связаны с доменами:
  - **Patient** — кто подписывает/заполняет;
  - **Booking/Visit** — по какому визиту/случаю формируется документ;
  - **Loyalty/ERP** (косвенно) — при необходимости подтверждать финансовые/правовые аспекты.

### 1.2. Проблема (GAPS PPR‑2 и связанные)

По `BACKEND_GAPS_Paperless_NEXT.md`, `ARCH_PAPERLESS_NEXT.md` и QA‑заметкам:

- Модели форм:
  - разрозненны, статусы и связи не унифицированы;
  - часть логики «живёт» в UI/легаси‑структурах;
  - сложно однозначно ответить:
    - какие формы обязательны по визиту;
    - какие уже подписаны/в процессе/просрочены.
- Риски:
  - юридические: отсутствие прозрачной истории подписей и статусов по визиту/пациенту;
  - UX: админам/врачам трудно понять, «что ещё нужно подписать/дозаполнить»;
  - интеграции: Paperless не всегда согласован с Booking/Tasks/Attention (нет сигналов о недостающих документах).

### 1.3. Связанные ARCH/DEV артефакты

- `ARCH_PAPERLESS_NEXT.md` — целевой домен Paperless.
- `ARCH_BOOKING_NEXT.md` — жизненный цикл визита.
- `ARCH_TASKS_NEXT.md` — задачи и Attention по пропущенным/просроченным формам.
- `ARCH_DEV_TASKS_MODEL_020.md` — формализация Tasks↔Attention.
- `ARCH_DEV_SEC_RBAC_022.md` — доступ к чувствительным документам (медицинские данные, согласия).

## 2. Целевое состояние моделей Paperless

### 2.1. Жёсткие инварианты

1. **Форма как доменная сущность с понятными статусами.**
   - Базовая сущность (рабочие имена):
     - `FormTemplate` — шаблон формы;
     - `FormInstance` (или `FormSubmission`) — конкретный экземпляр по пациенту/визиту.
   - У `FormInstance` есть статус из конечного набора (см. ниже).

2. **Прозрачные связи с пациентом/визитом.**
   - Любая форма, относящаяся к пациенту/визиту:
     - явно ссылается на:
       - `patient_id`
       - `booking_id` / `visit_id` (если привязана к визиту)
       - `clinic_id`

3. **Жизненный цикл формы согласован с Booking и юридическими требованиями.**
   - Например:
     - для визита хирургии может требоваться набор обязательных форм до начала лечения;
     - без статуса `signed` по обязательным формам визит не может быть переведён в определённые статусы.

4. **Paperless не дублирует другие домены.**
   - Формы:
     - содержат юридически значимый или операционный контент;
     - **не становятся вторым хранилищем статусов визитов, платежей и т.п.**;
     - вместо этого ссылаются на домены (Booking/ERP/Loyalty) и отражают их состояния в тексте документа.

5. **История изменений и подписей прослеживаема.**
   - Для каждой формы:
     - видно, кто и когда её создал/заполнил/подписал/отозвал;
     - есть audit‑trail с соблюдением требований по ПД.

### 2.2. Статусы форм

Предлагаемый набор статусов `FormInstance.status`:

- `draft` — создана, но не выдана пациенту/на подпись;
- `issued` — выдана/отправлена, ожидание заполнения/подписи;
- `in_progress` — частично заполнена (опционально);
- `signed` — полностью заполнена и подписана (электронно/ручной подписью, по текущей модели);
- `cancelled` — аннулирована до завершения (ошибка, заменена новой версией и т.п.);
- `expired` — просрочена (если есть срок действия формы);
- (опционально) `revoked` — пациент/клиника отозвали согласие.

Важно:

- статусы и их переходы фиксируются в `ARCH_PAPERLESS_NEXT.md` и в этом файле;
- UI и backend используют единый словарь статусов (аналогично `DEV_PROMPT_BKG_STATE_002`).

## 3. Архитектурный дизайн сущностей и связей

### 3.1. Сущности Paperless

Базовый перечень (может быть уточнён при реализации):

- `FormTemplate`:
  - `id: UUID`
  - `clinic_id: UUID` (если шаблоны кастомизируются по клинике)
  - `code: str` (уникальный код формы, например `CONSENT_SURGERY`, `PD_AGREEMENT`)
  - `version: int`
  - `title: str`
  - `description: str | None`
  - `content_schema: JSON` (описание полей / шаблон)
  - `is_active: bool`
  - `created_at`, `updated_at`

- `FormInstance` / `FormSubmission`:
  - `id: UUID`
  - `clinic_id: UUID`
  - `patient_id: UUID`
  - `booking_id: UUID | None`
  - `template_id: UUID`
  - `status: Enum` (см. выше)
  - `filled_data: JSON` (заполненные поля; без лишних ПД, в рамках требований)
  - `signed_at: datetime | None`
  - `expires_at: datetime | None`
  - `created_at`, `updated_at`, `created_by`, `updated_by`

- (опционально) `FormSignature` / `FormAuditEntry`:
  - для точной фиксации подписи/действий:
    - `form_id`
    - `actor_type` (patient/doctor/admin/system)
    - `actor_id`
    - `action` (`issued`, `filled`, `signed`, `revoked`, `cancelled`)
    - `at: datetime`
    - служебный контекст.

### 3.2. Связи с доменами

- С Patient:
  - `FormInstance.patient_id` — обязательное поле для пациентских форм.
- С Booking/Visit:
  - `FormInstance.booking_id` (или `visit_id`) — для форм, связанных с конкретным визитом/услугой.
- С Tasks/Attention:
  - посредством событий:
    - недостающие или просроченные формы → Attention/Tasks.

## 4. Интеграция с Booking, Tasks и UI

### 4.1. Обязательные формы по визиту

- Для типов визитов/услуг (по `ARCH_BOOKING_NEXT.md` и бизнес‑логике):
  - определён набор обязательных шаблонов `FormTemplate`:
    - например:
      - для хирургии: согласие на операцию, согласие на наркоз, согласие на обработку ПД;
      - для диагностики: базовое согласие на ПД и информированное согласие.
- При создании/планировании визита:
  - система может:
    - предусмотреть ожидаемые `FormInstance` (создать `draft` или `issued`);
    - или отметить необходимость их создания (для ручного запуска).

### 4.2. Проверки при изменении статуса визита

- При переводе `Booking` в определённые статусы (например, `in_progress` → `completed`):
  - можно (по бизнес‑решению) требовать:
    - наличие всех обязательных `FormInstance` по визиту в статусе `signed`;
  - если нет:
    - либо блокировать переход;
    - либо создавать Attention/Task на доработку документов.

### 4.3. Взаимодействие с Tasks & Attention

- По `ARCH_TASKS_NEXT` и `ARCH_DEV_TASKS_MODEL_020.md`:
  - создаются Attention/Tasks:
    - при отсутствии обязательных форм к моменту визита;
    - при просрочке форм с ограниченным сроком действия;
    - при отзывах форм (`revoked`) для уже проведённых визитов (для аудит/юристов).

## 5. Наблюдаемость, SEC/RBAC и ПД

### 5.1. ПД и доступ

- FormInstance содержит чувствительные данные:
  - ПД пациента;
  - медицинскую информацию.
- Доступ к формам:
  - регулируется RBAC:
    - по ролям (`doctor`, `registrar`, `owner`, `manager`, `legal`, и т.п.);
    - по `clinic_id`;
  - согласуется с `ARCH_DEV_SEC_RBAC_022.md`.
- При работе AI (в будущем, e‑signature/анализ текстов форм):
  - используются:
    - токенизация/санитайзер по `ARCH_DEV_OMNI_POLICY_016.md` и `ARCH_DEV_AI_TOKENIZATION_025.md`;
    - строгие ограничения по `allow_personal_data`.

### 5.2. Логирование и метрики

- В логах:
  - фиксируются:
    - операции создания/изменения/подписания/отзыва форм;
    - `clinic_id`, `form_id`, `template_code`, `patient_id`/`booking_id` (ID, не ПД);
    - инициатор, тип действия.
- Метрики (минимум):
  - количество форм по статусам (особенно `issued`/`expired`/`revoked`);
  - доля визитов без обязательных подписанных форм;
  - среднее время от `issued` до `signed`.
