## 1. Назначение шаблона

Шаблон фиксирует, как проектировать и собирать операционные экраны, чтобы:
- пользователь решал задачу за 1-3 действия;
- UI был плотным, читаемым и предсказуемым;
- @DEV не додумывал дизайн-поведение по месту.

---

## 2. Admin Design Gate (до разработки)

Перед созданием/изменением admin-экрана обязательно зафиксировать:

```
□ Роль пользователя (кто работает на экране)
□ Главная задача экрана (1 фраза, действие)
□ Тип экрана (Schedule / Finance / CRM / Dashboard / Analytics / Settings / Loyalty)
□ Критичный сценарий А→Б (что пользователь должен завершить без обходов)
□ Ограничения API/данных (ARCH_*.md)
□ UI-режим: локальная полировка или нужен @DESIGN (SPEC/VERDICT)
```

## 3. Базовая композиция admin-экрана

### 3.1. Shell
- Тёмный sidebar для навигации.
- Светлая рабочая зона (`main`) для данных.
- Контекстный бар внутри рабочей зоны вместо тяжёлого глобального header.

### 3.2. Layout
- Данные в приоритете: таблицы/панели/канбан без визуального шума.
- Фон уровня 0: нейтральный светлый.
- Карточки уровня 1: белые с микрограницей.

### 3.3. Никакого global page scroll на тяжёлых экранах
- Для чатов/календарей/канбана: скролл в контентных колонках через `ScrollArea`.
- Sticky заголовки колонок/секций сохраняют контекст при прокрутке.

---

## 4. Решения-паттерны (раз и навсегда)

### 4.1. Drawer vs Modal
- `Drawer`: создание/редактирование сущностей, карточки с вкладками, история.
- `Modal`: только confirm/alert/одно короткое действие.

### 4.2. Таблица vs Карточки vs Kanban
- Таблица: сравнение записей, сортировка, фильтры, >5 полей.
- Карточки: визуальный обзор, <5 полей, мобильный контекст.
- Kanban: статусная прогрессия + drag-and-drop как основное действие.

### 4.3. One Primary CTA
- На экране один главный `primary`.
- Вторичные действия через `default/light/subtle` или `ActionMenu`.

---

## 5. State Spec (обязателен для каждого data-компонента)

```
Loading:
- Skeleton по форме контента
- Критичные кнопки disabled

Empty:
- EmptyState: icon + title + hint + CTA
- Для фильтра "ничего не найдено" — текст без CTA

Error:
- Alert/Toast простым языком
- кнопка "Повторить"
- без stack trace в UI

Success:
- форма сброшена
- Drawer закрыт (если сценарий завершён)
- invalidate/refetch выполнен
```

---

## 6. Data Integrity и UX-инварианты

- В UI не показываем UUID.
- Длинные строки: `truncate` + tooltip/title.
- Деструктивные действия: confirm-диалог.
- Submit во время мутации: `disabled`.
- После мутации: `invalidateQueries`.
- Нет `null.map()` — безопасные дефолты для коллекций.

---

## 7. Визуальные нормы (Crisp SaaS + Swiss Slate / Ink)

- **Канон палитры и токенов:** `docs/ARCH_FRONTEND_UI_LOGIC.md`, `docs/TECH_PASSPORT_FRONTEND_UI_LOGIC.md` (`primary` ink `#1c2e45`, фон `#f4f6f8`).
- Табличный текст не мельче 13px, контент не мельче 15px.
- Плотность таблицы: не менее 12px vertical spacing.
- Иконки без подписи — с tooltip.
- Статусный цвет = смысл (success/warn/error/info) и консистентность.
- Hover/active состояния у всех интерактивных элементов.

## 8. Модульные контракты (минимум)

| Тип модуля | Что обязано быть |
|------------|------------------|
| Schedule | кликабельные слоты, статусы, фильтры врачей, навигация дат |
| CRM | поиск + debounce, карточка клиента, быстрые действия |
| Finance | кассы, транзакции, итоги периода, drill-down |
| Dashboard | KPI + дельты, attention feed, быстрые действия |
| Tasks/Kanban | статусы, assignee, дедлайн, DnD с feedback |
| Settings | ключевые справочники и безопасные ограничения удаления |

Источник проверки: `docs/DOMAIN_STANDARDS.md`.

## 9. Accessibility и Keyboard

- Focus-visible на интерактивных элементах.
- Escape закрывает drawer/modal.
- Tab-порядок не ломает рабочий сценарий.
- Touch target не менее 44x44 на мобильных экранах.

---

## 10. Performance для admin UI

- Анимации только `transform` + `opacity`.
- Списки 1000+ строк: пагинация/виртуализация.
- Debounce для поиска 300-500ms.
- Тяжёлые эффекты blur — точечно, без деградации скролла.
