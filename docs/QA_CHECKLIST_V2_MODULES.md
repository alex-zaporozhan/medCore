## ✅ QA_CHECKLIST_V2_MODULES — Swiss‑level проверка модулей V2

> Роли: @QA, @LEAD, @ARCH, @DEV.  
> Цель: дать чек‑лист, по которому можно объективно подтвердить, что каждый модуль V2 (AI Agent, CRM, ERP, RBAC/Tasks, Loyalty, Paperless, Attribution, Frontend Business OS) работает **как швейцарские часы**, без имитации функциональности.

---

## 1. Как пользоваться чек‑листом

- Для **каждого модуля** V2 пройтись по секциям A–G.
- Если по любой секции результат ниже уровня L3 — модуль **не считается готовым**.
- Для фиксации удобно делать таблицу вида:
  - `Модуль` × `Секция (A–G)` × `Статус (L0–L3)` + короткий комментарий.

---

## 2. Уровни зрелости (ориентир)

- **L0 — Просто чтобы был (fake/стаб)**  
  - Статичный UI/эндпоинты, почти нет реальной логики/данных/ошибок.
- **L1 — Базовый рабочий**  
  - Happy‑path работает, есть БД и миграции, но мало валидаций/тестов.
- **L2 — Продвинутый, но с дырками**  
  - Большинство бизнес‑кейсов реализовано, есть тесты и ошибки, но:
    - слабая интеграция с EventBus/RBAC/AI/отчётами;
    - неполные edge‑кейсы и наблюдаемость.
- **L3 — Swiss‑level / Production‑grade (цель)**  
  - Модуль устойчив, предсказуем, хорошо интегрирован и наблюдаем.

В чек‑листе ниже для @QA важно: **утверждать L3 только при выполнении всех пунктов секции.**

---

## A. Доменные инварианты и данные

- [ ] **Все сущности реализованы по ARCH\_***  
  - Сущности и поля из соответствующего `ARCH_*` существуют в коде (id, clinic_id, статусы, суммы, связи, инварианты).
- [ ] **Инварианты статусов и переходов реализованы**  
  - Статусы не произвольные строки, а ограниченный набор (enum/FSM).  
  - Нельзя получить невозможные состояния (например, `completed` без ERP‑операций).
- [ ] **Multi‑tenancy соблюдён**  
  - Везде есть `clinic_id`; все запросы модулей фильтруют данные по клинике текущего контекста.
- [ ] **Данные не дублируются без причины**  
  - Кэши (`estimated_value`, `actual_value`, LTV и т.п.) могут быть пересчитаны из источника (ERP/Payments).

---

## B. Ошибки и edge‑кейсы

- [ ] **Описан и покрыт перечень бизнес‑ошибок**  
  - Для модуля есть явные коды ошибок (`slot_conflict`, `missing_cashbox`, `insufficient_stock`, `policy_missing`, и т.п.).  
  - Эти коды реально используются в коде и тестах.
- [ ] **Предсказуемое поведение на краях**  
  - Ошибки валидации/конфликтов → читаемое сообщение для пользователя (через UI/ответ API).  
  - Нет «голых» 500 без бизнес‑объяснения.
- [ ] **Контролируемая деградация внешних зависимостей**  
  - При падении AI/платёжного провайдера/storage:
    - модуль выдаёт безопасное сообщение пользователю;
    - логирует техническую ошибку;
    - не оставляет данные в «полупринятом» состоянии.

---

## C. EventBus и кросс‑модульная интеграция

- [ ] **Модуль публикует нужные Domain Events**  
  - При ключевых изменениях (создание/завершение визита, оплата, создание контакта и т.п.) действительно вызывается `EventBus.publish(...)` с нужными payload.
- [ ] **Модуль подписан на релевантные события других модулей**  
  - CRM реагирует на `BookingCreated/Completed`, Payments и Contact.  
  - ERP реагирует на `BookingCompleted`.  
  - Loyalty реагирует на ERP/Payments/Bookings.  
  - Tasks/Attribution реагируют на доменные события согласно ARCH.
- [ ] **Нет жёстких связей, нарушающих архитектуру**  
  - Модуль не импортирует напрямую ORM‑модели других доменов там, где по `ARCH_*` должен использоваться сервис или событие.

---

## D. RBAC и безопасность (включая ПД/AI)

- [ ] **Все критичные эндпоинты закрыты `require_permissions`**  
  - Finance/ERP, CRM, Tasks, Loyalty, Forms, Marketing Attribution, AI‑настройки — все роуты соответствуют матрице `ARCH_RBAC_AND_TASKS.md`.
- [ ] **Проверки прав протестированы**  
  - Есть автоматические тесты:
    - запрос без авторизации → 401;
    - пользователь без нужного `Permission` → 403;
    - с нужным `Permission` → 200 и корректный ответ.
- [ ] **Политика ПД и AI соблюдена**  
  - При `allow_personal_data=False` в payload AI нет ПД (ФИО, телефонов, email, медданных).  
  - Поля с `sensitive=True` (формы/EMR) не утекут в промпты LLM.

---

## E. Тестирование (Unit, интеграционные, e2e)

- [ ] **Unit‑тесты покрывают ключевую бизнес‑логику**  
  - Расчёты (ERP, LTV, Loyalty, Attribution и т.п.) и инварианты проверены юнитами.
- [ ] **Интеграционные тесты покрывают полный сценарий**  
  - Для модуля есть сценарии «из реальной жизни», например:
    - CRM: от Contact → LeadCard → Booking → Payment → Success/Lost.  
    - ERP: от `Booking.completed` до создания всех связанных транзакций.  
    - Loyalty: покупка пакета → использование → истечение/recall.  
    - Paperless: создание шаблона → заполнение → подпись → просмотр/экспорт.  
    - Attribution: utm → VisitAttribution → Lead → Patient → ERP → отчёт.
- [ ] **Фронтенд‑регрессия по ключевым экранам**  
  - Есть базовые UI‑тесты/снапшоты для OmniChat, CRM‑канбана, Finance, Tasks, Loyalty, Forms, Analytics.

---

## F. Наблюдаемость, логи и аудит

- [ ] **Ключевые действия пишутся в аудит/логи**  
  - AI‑инструменты, смена статусов лида/задачи, ERP‑операции, операции экспорта, критичные настройки (AI/финансы) имеют audit‑trail.
- [ ] **Есть базовые метрики**  
  - Количество операций, ошибки по типам, latency критичных операций, минимум — доступны через логи/мониторинг.
- [ ] **Можно ответить на вопросы «кто/что/почему»**  
  - По данным аудита возможно восстановить, кто и когда:
    - изменил статус, создал/отменил визит, подписал документ, запустил экспорт и т.п.

## G. UX / DX и соответствие BUSINESS_LOGIC_V2

- [ ] **Экран решает бизнес‑задачу, а не демонстрирует данные**  
  - Для модуля есть понятные сценарии работы (отображение, фильтры, действия) → пользователь может реально «управлять бизнесом», а не только «смотреть на таблицы».
- [ ] **Состояния UI продуманы**  
  - Loading, empty, error‑состояния реализованы, нет «белых экранов» или неинформативных ошибок.
- [ ] **Модуль соответствует ожиданиям из `BUSINESS_LOGIC_V2.md`**  
  - Реализованные потоки и UI отражают обещанный там функционал (нет over‑promise/under‑delivery).
