# CACHE_STRATEGY — когда и как кэшировать (решение @ARCH)

> **Назначение:** единые критерии введения и смены кэша в системе, чтобы не получить **устаревшие деньги/слоты**, утечки данных между клиниками и «немые» инциденты без метрик.  
> **Решение принимает @ARCH** и фиксирует в `docs/artifacts/ARCH_*.md` / `docs/artifacts/DEV_PROMPTS_*.md`; **@DEV** реализует только описанный контракт.  
> **Связь:** `docs/ARCHITECTURE_EXCELLENCE_PASSPORT.md` (наблюдаемость, целостность данных, производительность).

Это **не** замена Redis как брокеру Celery — речь о **кэше ответов и вычислений**.

---

## 1. Где фиксируется решение

- В архитектурном артефакте или в задаче для @DEV: **что** кэшируется, **ключ**, **TTL**, **инвалидация**, **деградация** при недоступности Redis.
- Любое новое использование серверного кэша в критичном пути — с явной строкой в handoff (см. `docs/ROLE_ARCH.md`, раздел передачи @DEV).

---

## 2. Когда кэш **уместен**

| Критерий | Вопрос |
|----------|--------|
| Частота чтения | Данные читают **значительно чаще**, чем меняют? |
| Допустимая устарелость | Пользователь/бизнес терпит **X секунд/минут** несвежести? |
| Стоимость источника | Запрос к БД или внешнему API **дорогой** (latency, $)? |
| Детерминированность | При том же ключе ответ **одинаков** до смены данных? |

Типичные кандидаты: справочники, агрегаты дашборда (с явным TTL), тяжёлые read-only отчёты, идемпотентные GET при отсутствии строгой realtime-требования.

---

## 3. Когда кэш **неуместен** (или только с особыми правилами)

- **Источник истины для денег и остатков** — не кэшировать как «единственный» ответ без инвалидации по событию.
- **Доступ и авторизация** — не полагаться только на кэш для решения «можно ли видеть сущность».
- **Сильная консистентность** — бронь слота, финальный чек: кэш не заменяет блокировки и констрейнты в БД (см. паспорт §4–§5).
- **Персональные/PII-тяжёлые** данные — только с учётом TTL, ключей с tenant и политики маскирования в логах.

---

## 4. Ключи и мультитенантность

- Ключ **всегда** включает идентификатор арендатора (**`clinic_id`** в этом проекте), если данные изолированы по клинике.
- Именование: предсказуемый префикс (`v1:report:daily:{clinic_id}:{date}` и т.д.), чтобы исключить коллизии и упростить отладку.

---

## 5. TTL и инвалидация

- **TTL** — обязателен; «без срока» только для редких случаев с явным ADR.
- **Инвалидация:** предпочтительно по **событию** (после мутации сущности сбросить затронутые ключи). Только TTL — когда бизнес допускает eventual consistency и риск просчитан.
- При изменении **схемы** кэшируемого объекта — версия в префиксе ключа или полный сброс слоя по регламенту релиза.

---

## 6. Redis vs in-process

| Вариант | Когда |
|---------|--------|
| **Redis** (как сейчас в compose) | Несколько воркеров/реплик API, общий кэш, Celery уже использует Redis. |
| **In-process (LRU)** | Один инстанс, мелкие данные, допустима потеря при рестарте. |

Не дублировать один и тот же смысл в двух уровнях без необходимости; если два уровня — кто «источник правды» при расхождении должен быть описан.

---

## 7. Деградация и stampede

- При недоступности Redis: **прозрачный fallback** на прямой запрос к БД (или отказ фичи с понятной ошибкой) — заранее в задаче.
- **Cache stampede:** для горячих ключей — блокировка пересчёта, single-flight или короткий TTL + фоновое обновление (по решению @ARCH).

---

## 8. Фронтенд (React Query и т.п.)

- Серверный кэш и **клиентский** кэш запросов — разные уровни: после мутаций на бэкенде фронт обязан **инвалидировать** соответствующие query (см. `.cursorrules` / DOMAIN_STANDARDS). @ARCH в задаче указывает, какие списки/ключи на фронте затрагиваются.

---

## 9. Наблюдаемость

- Для внедряемого кэша желательно: счётчики **hit/miss**, опционально latency; при feature-flag кэша — возможность отключить и сравнить метрики (паспорт §8).
