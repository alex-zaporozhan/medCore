# Канон тестирования и проверок качества

**Назначение:** общая рабочая база того, что по канону нужно проверять при проектировании и проведении тестов. Не привязан к конкретному проекту. @ARCH использует этот перечень при проектировании тестов (ARCH_TESTS); @QA сверяется с ним при финальном прогоне; @AUDITOR учитывает при диагностике (типичные причины сбоев).

---

## 1. Кто откуда берёт базу

| Роль | Использование                                                                                                                                             |
|------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| **@ARCH** | При создании ARCH_TESTS (или аналога) — взять категории проверок из этого документа как базу, дополнить под проект (конкретные эндпоинты, фикстуры, E2E). |
| **@QA** | При финальном прогоне — убедиться, что категории из канона покрыты; при необходимости расширить чек-лист под проект.                                      |
| **@AUDITOR** | При диагностике сбоев — перебирать типичные причины, в т.ч. «пустое состояние», валидация, контракт API (см. разделы ниже).                               |
| **@DEV** | При написании тестов — ориентироваться на ARCH_TESTS проекта, который в свою очередь опирается на этот канон.                                             |

## 2. Ключевые типы тестов

При проектировании ARCH_TESTS и при прогоне учитывать:

- **Smoke** — критические эндпоинты и сценарии (health, вход, один основной поток) отвечают/работают после деплоя.
- **Регрессия** — «золотой путь» (типовой сценарий пользователя) проходит после последних изменений.
- **API / интеграция** — запрос → сервис → БД → ответ; контракт (формат, коды ответов); граничные и пустые данные.
- **E2E** — один–два сквозных сценария (например: запись → оплата, создание сущности → отображение в списке).
- **Unit** — по необходимости для сложной бизнес-логики; не обязательны для простых CRUD.  
  *Пример из практики репозитория:* стабильность идемпотентных идентификаторов доменных событий (напр. `booking_event_dedup_id` для CRM/Tasks) — без БД, см. `tests/unit/test_booking_event_dedup.py`.

### 2.1. CI/CD и quality gates

Разделы **§2–§3** задают *что* проверять; **CI** фиксирует *минимальный автоматический барьер* до мержа (зелёный пайплайн ≠ полная замена ручного @QA, но блокирует очевидную регрессию).

- **Фактический пайплайн** в репозитории — всегда сверять с **`.github/workflows/*.yml`** (сейчас: бэкенд **Ruff + pytest** с Postgres/Redis; фронт **`npm run build` + Vitest**; отдельный job **E2E Playwright** после прохождения предыдущих стадий).
- **Политика поставки** (flaky-тесты, образы, миграции, «релиз без тестов») — **`docs/ARCHITECTURE_EXCELLENCE_PASSPORT.md`** (в т.ч. §10), при необходимости **`docs/MIGRATION_UPGRADE.md`**, **`docs/DOCKER_INFRA_PASSPORT.md`**.
- Новый сценарий, отражающий пункт канона (например **§3.1** пустое состояние), по возможности **дублируется тестом** и попадает под CI; иначе риск остаётся на ручном прогоне и @QA_ARCH.

## 3. Категории проверок (базовый перечень)

Ниже — минимальный набор категорий, которые по канону должны быть учтены. Конкретные шаги и приоритеты задаются в ролях (@QA — Pillars, @ARCH — ARCH_TESTS).

### 3.1 Пустое состояние (empty state)

- **Суть:** Ошибки, возникающие естественным образом при отсутствии в БД необходимых данных (нет клиники, пациентов, врачей и т.п.), не должны отдаваться как 500 Internal Server Error.
- **Правило:**
  - В API: при отсутствии обязательных данных возвращать **4xx** (например 404) с **понятным текстом** в `detail`.
  - Тексты для пользователя хранить в одном месте (например `user_messages.py`), не дублировать.
  - На фронте: при отображении ошибки от API показывать текст из `detail` и **универсальную подсказку** в понятных формулировках (без кода — см. ниже).
- **Для клиента — без кода.** Сообщения видят конечные пользователи (не программисты). В текстах **не должно быть** команд, путей, названий скриптов (docker, seed_demo_data и т.п.) — это пугает и непонятно. Нужно: **объяснение, почему ошибка**, и **что сделать по смыслу**, простыми словами. Примеры:
  - «Добавьте первого врача» / «Добавьте первого пациента» / «Добавьте клинику».
  - «Для отчёта нужны минимум врачи, пациенты и хотя бы одна завершённая запись — добавьте их в соответствующих разделах.»
  - «Как только вы добавите нужные данные — ошибка исчезнет.»
  Технические инструкции (seed, команды) — только в документации для администратора/разработчика или в логах, не в UI и не в `detail` ответа API для конечного пользователя.
- **Проверки:** пустая БД после деплоя, отсутствие клиники/врачей/пациентов — приложение не падает с 500; пользователь видит понятное сообщение и подсказку без кода.

### 3.2 Пустые поля и валидация

- Обязательные поля: проверка на бэкенде и в формах; при неверном вводе — понятная ошибка, не падение.
- Граничные значения: пустая строка, слишком длинный текст, спецсимволы — обрабатываются без 500 и без пустого экрана.
- Формы: отмена/назад не сохраняют мусор; при сохранении — явный успех или ошибка.

### 3.3 API и контракты

- Health-check и критические эндпоинты отвечают без 500 при корректном запросе.
- При неверном запросе (невалидные параметры, нет прав) — 4xx с понятным `detail`, не 500.
- Цепочка запрос → сервис → БД → ответ не теряет данные на граничных значениях (пустой список, одна запись, лимиты).

### 3.4 Авторизация и доступ

- Защищённые эндпоинты/страницы без токена/сессии возвращают 401/403 или редирект на логин.
- После входа доступны только разрешённые разделы; выход инвалидирует сессию.
- Нет утечки информации в теле ошибки (например, «пользователь не найден» vs «неверный пароль»).

### 3.5 Данные и объёмы

- Пустые списки/календарь — отображается пустое состояние или сообщение, не падение.
- Большие списки — пагинация или лимиты; нет N+1 на типичных экранах.
- Транзакции: операции создания/обновления атомарны; при конфликте — понятная ошибка, не «битая» запись.

### 3.6 Окружение и конфигурация

- Отсутствие обязательной переменной окружения даёт явную ошибку при старте, а не в рантайме в неочевидном месте.
- Миграции применяются и откатываются без поломки приложения.

## 4. Для @AUDITOR: типичные причины при диагностике

При поиске причины сбоя по слоям (браузер → сеть → сервер → БД) учитывать в числе гипотез:

- **Пустое состояние БД** — нет клиники/пациентов/врачей; эндпоинт ожидает данные и падает. Решение: 4xx + сообщение по п. 3.1 этого канона (без кода в тексте для клиента).
- **Валидация** — неверный формат тела/параметров; сервер должен вернуть 4xx с `detail`, а не 500.
- **Авторизация** — 302 на логин или 401/403 вместо ожидаемого 200.
- **Контракт API** — клиент ожидает поле/формат, которого нет в ответе; проверить OpenAPI/документацию и реальный ответ.
- **Логи** — первым шагом проверить логи сервера и консоль браузера (см. docs/LOGGING_AND_DEBUGGING.md).
