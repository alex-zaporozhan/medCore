# Сценарий нагрузки и честность маркетинга «10k+» (МП §30)

> **Статус:** шаблон прогона для @OPS / @LEAD. Ориентиры N организаций и данных — в [ENTERPRISE_SAAS_SCALE_ENVELOPE.md](../architecture/ENTERPRISE_SAAS_SCALE_ENVELOPE.md).  
> **Связь:** [arch_plan/10_CROSS_CUTTING_SECURITY_ANTISPAM_BRAND_SCALE.md](../architecture/arch_plan/10_CROSS_CUTTING_SECURITY_ANTISPAM_BRAND_SCALE.md) §30.

## Зачем

Публичные формулировки про масштаб (организации, RPS, одновременные пользователи) должны опираться на **зафиксированный прогон** (staging или отчёт с датой), а не на оценку «на глаз».

## Чеклист прогона (минимум)

1. **Контур:** один регион, конфиг как в целевом проде (Postgres, Redis, число реплик API при заявлении multi-replica).
2. **Данные:** N активных организаций, M клиник, объём клиентов/записей согласно сценарию envelope (или явно заниженный smoke).
3. **Нагрузка:** смешанный профиль — логин админа, список записей, создание брони, публичный embed (если включён), webhook-контур B (если в скоупе), критичные read-only отчёты.
4. **Наблюдение:** `http_request_duration_seconds` по `status_class`, p95/p99; `domain_outbox_*` при использовании outbox; ошибки БД в логах; при наличии — метрики §27–§28 (`spam_blocked_total`, `security_*`).
5. **Критерий успеха:** заранее заданные SLO (например из [SLO_CRITICAL_PATHS.md](./SLO_CRITICAL_PATHS.md)) не нарушены в течение окна прогона; либо зафиксированы отклонения и план.
