## 1. Prod-smoke после первого (и каждого значимого) деплоя

Сценарий и критерии: [`DEPLOY_SMOKE.md`](DEPLOY_SMOKE.md).

**При первом прогоне @LEAD дополнительно:**

1. Убедиться, что публичный URL / TLS / DNS соответствуют прод-конфигурации (не dev).
2. Выполнить smoke **с той же стороны, что и клиенты** (интернет → edge → приложение), не только из внутренней сети.
3. Зафиксировать результат: дата, версия образа/тега (лучше SHA из CI), OK/не OK, кто проверил. Достаточно строки в релизном тикете или короткой записи в журнале релизов.
4. При сбое — откат по runbook деплоя; не считать релиз принятым без повторного зелёного smoke.

## 2. Скан слоёв образа в реестре (не то же самое, что Trivy FS в CI)

В репозитории workflow **Trivy FS** лежит в `.github/workflows_disabled/security-trivy.yml` (при включении CI сканируется **файловая система** репозитория). **Слои собранного образа** в Docker Hub / GHCR / другом реестре могут отличаться (базовый образ, копирование файлов, multi-stage build).

**При первом подключении реестра @LEAD:**

1. Включить политику команды: **0 CRITICAL** на тегах, которые едут в prod (как в SME §2.3).
2. Выбрать инструмент: встроенный скан реестра (GitHub Advanced Security, ECR/Azure Defender, отдельный Trivy/Grype job против `registry/...:tag` или digest), главное — **регулярность** и **привязка к тегу SHA**, а не только к `:latest`.
3. Один раз проверить вручную образ, совпадающий с первым прод-выкатом (тот же digest/SHA, что в деплое).
4. Задокументировать, где смотреть отчёт (дашборд, артефакт job, email) и кто эскалирует при CRITICAL.

Автоматизация «скан образа после push» возможна отдельным workflow в репозитории (Trivy `image` + секреты реестра) — пока это на усмотрение @LEAD и политики секретов.
