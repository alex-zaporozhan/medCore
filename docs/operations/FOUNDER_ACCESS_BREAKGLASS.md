# Доступ Основателя платформы: break-glass и смена идентичности (LEAD + OPS + SEC)

> **Связь:** [SAAS_STRENGTHENING_MASTER_PLAN.md](../architecture/SAAS_STRENGTHENING_MASTER_PLAN.md) §1 (C5), §9, §19 п.18; [DR_RUNBOOK.md](./DR_RUNBOOK.md).

## 1. Назначение

Процедуры на случай: потеря 2FA/TOTP, компрометация секрета, необходимость **передать роль Основателя** другому лицу без потери данных тенантов.

Штатное включение TOTP (до break-glass): [PLATFORM_FOUNDER_TOTP_AND_OBSERVABILITY.md](./PLATFORM_FOUNDER_TOTP_AND_OBSERVABILITY.md) §1.

## 2. Роли и допуск

| Роль | Действие |
|------|----------|
| **OPS** | Выполнение шагов по runbook, фиксация в тикете инцидента |
| **SEC** | Утверждение сброса, проверка канала запроса, пост-инцидент |
| **LEAD** | Бизнес-решение о смене Основателя, приёмка после передачи |

Доступ к секретам платформы — только через **secret manager** / vault (не `.env` на проде как единственный носитель).

## 3. Break-glass: восстановление доступа при потере 2FA

**Предусловия:** подтверждённая личность заявителя (внешний канал, договорённость с LEAD).

1. Зафиксировать тикет: кто запрашивает, дата/время, причина.
2. Использовать **офлайн-коды восстановления** или **второй носитель**, если были выданы при онбординге; иначе — контролируемый сброс через OPS:
   - отключить текущий TOTP в приложении: сбросить в БД поля `totp_secret_ciphertext` / `totp_enabled` у строки `platform_founder_users` (миграция/скрипт OPS под тикетом SEC) либо заменить учётную запись Основателя;
   - штатный онбординг TOTP (после входа по паролю, пока 2FA не включена): `POST /api/v1/platform/auth/totp/enroll` → `POST /api/v1/platform/auth/totp/confirm`; вход с 2FA: `POST /api/v1/platform/auth/login` (при необходимости `mfa_token` + `POST .../login/mfa`);
   - принудительно инвалидировать все активные сессии Основателя (истечение JWT + ротация `PLATFORM_FOUNDER_JWT_SECRET` при компрометации).
3. Сменить пароли/ключи API, если есть подозрение на компрометацию.
4. SEC: краткий пост-разбор (что случилось, что усилить).

**Секреты контура B и platform JWT:** хранить `PLATFORM_BILLING_WEBHOOK_SECRET` и (в production) **`PLATFORM_FOUNDER_JWT_SECRET`** отдельно от `JWT_SECRET_KEY` и от секретов пациентских платежей; ротация — по инциденту или политике, с фиксацией в тикете (см. [../architecture/modules/platform_subscription_billing.md](../architecture/modules/platform_subscription_billing.md)).

## 4. Смена идентичности Основателя (передача платформы)

1. **LEAD** письменно утверждает нового ответственного и дату передачи.
2. **OPS** создаёт учётную запись нового Основателя (или переносит привязку) в соответствии с реализацией `/platform/*` (после ADR-007).
3. Старый доступ: отзыв ролей, инвалидация сессий и токенов, ротация **платформенных** секретов (webhook B, интеграции), если старый имел к ним доступ.
4. Аудит: кто выполнил шаги, UUID тенантов не затронуты.
5. Проверка: вход нового Основателя, дашборд, отсутствие доступа у старого.

## 5. Резервный криптографический материал

- Хранить **вне** основного `.env` (отдельный том, vault, офлайн-сейф по политике SEC).
- Регистрация места хранения — в тикете/внутреннем реестре OPS (без PII).
