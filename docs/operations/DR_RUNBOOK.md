# DR_RUNBOOK — резервное копирование и восстановление PostgreSQL

> **Назначение:** закрыть пункты SME `SME_BOX_NFR_CHECKLIST.md` §1.1–1.3 и `ARCH_DATA_MULTITENANT_AND_OPERATIONS_2026.md` §3.  
> **Владелец процедуры:** @LEAD / операции; исполнитель восстановления — дежурный администратор.

## 1. Объекты и RPO/RTO (ориентиры)

| Объект | Метод | RPO (потеря данных) | RTO (время возврата) |
|--------|--------|---------------------|----------------------|
| PostgreSQL (бизнес-данные) | Логический дамп `pg_dump` | Зависит от расписания (см. §2) | Зависит от объёма; целевой ориентир для коробки — восстановление на чистый инстанс за время, зафиксированное после drill |

Redis и очереди Celery после восстановления БД могут потребовать сброса кэша/очередей — см. §5.

## 2. Регулярный backup (1.1)

**Минимум для production / staging:**

1. Расписание: ежедневно (cron или планировщик облака) в окне низкой нагрузки.
2. Команда (пример, подставьте `DATABASE_URL` и путь хранения):

```bash
pg_dump "$DATABASE_URL" -Fc -f "/secure/backups/dental_booking_$(date +%Y%m%d_%H%M).dump"
```

3. Retention: хранить не менее **7** полных дампов (регулируется политикой @LEAD).
4. Проверка: размер файла **> 0**, при возможности — `pg_restore -l` на копии файла.

Секреты подключения — только из секрет-хранилища / `.env` на сервере, не в git.

## 3. Восстановление на новый инстанс (1.2)

**Предусловия:** установлены PostgreSQL совместимой мажорной версии, создана пустая БД (например `dental_booking_restored`).

1. Остановить приложение и воркеры, обращающиеся к БД (чтобы не писать в старую базу).
2. Восстановить дамп:

```bash
pg_restore -d "postgresql://user:pass@host:5432/dental_booking_restored" --no-owner --jobs=4 /path/to/backup.dump
```

3. Применить миграции до актуальной схемы (если дамп старее кода):

```bash
export DATABASE_URL=postgresql+asyncpg://...
alembic upgrade head
```

4. Проверить строку в `alembic_version` — соответствует ожидаемой ревизии для данного релиза.
5. Обновить `DATABASE_URL` / секреты приложения на новую БД, поднять API, Celery, Redis.
6. Smoke: `GET /health` и один read-only сценарий из чеклиста деплоя (например публичное расписание или справочник услуг).

## 4. Restore drill (1.3)

**Минимум:** один успешный учебный прогон на **staging** в квартал (или по регламенту @LEAD). Допустима фиксация того же сценария на **локальном Docker** как проверка воспроизводимости runbook до выноса на staging. **CI:** workflow `.github/workflows/restore-drill.yml` (еженедельно + вручную) — автоматический drill `pg_dump` → новая БД → `pg_restore` → сверка `alembic_version`. Журнал успешных прогонов: [`DR_DRILL_LOG.md`](DR_DRILL_LOG.md).

| Контур | Дата | Результат | Примечание |
|--------|------|-----------|------------|
| GitHub Actions `restore-drill` | см. `DR_DRILL_LOG.md` | OK при зелёном job | Тот же сценарий, что в таблице ниже, на ephemeral Postgres |
| Локальный Docker (`dental_booking_postgres`, БД `dental_booking`) | 2026-03-24 | OK | `pg_dump -Fc` → временная БД `dental_booking_drill` → `pg_restore --no-owner`; сверка `alembic_version` с исходной БД |
| Staging (облако / стенд @LEAD) | *TBD* | — | **Действие @LEAD/ops:** остановить приложение → `pg_dump` с staging → пустая БД → `pg_restore` → smoke (`/health` + один read-only API) → записать дату в `DR_DRILL_LOG.md` |

**Время цикла (локальный drill 2026-03-24):** порядка **1–2 минуты** (без остановки приложения; только БД).

Фиксация: тикет / строка в журнале релизов.

## 5. После restore

- Убедиться, что данные **изолированы по tenant** (`clinic_id`): выборочно сравнить количество клиник и отсутствие «чужих» связей.
- При смене хоста БД — обновить все сервисы, использующие старый DSN.
- Redis: при необходимости `FLUSHDB` для кэша сессий/кодов, чтобы не смешивать состояние со старого контура.
