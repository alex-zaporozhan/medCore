# Кристаллизованные маршруты

> Этот файл создаётся и пополняется системой автоматически.
> Каждый кристалл — это путь от проблемы к решению, пройденный однажды
> и сохранённый чтобы не проходить заново.
>
> Кристаллы не удаляются. Только пополняются и уточняются.
> Инициирует кристаллизацию любая роль после успешного завершения задачи.
> Подтверждает и сохраняет — пользователь.

## Как читать кристалл

```
Условие применения — когда именно этот маршрут работает

Рецепт — минимальный промпт для запуска (быстрый триггер)
Не работает когда — ограничения применимости
```

## CRYSTAL_JS_SILENT_BUTTON

**Задача:** inline JS в кастомной странице не реагирует на действия пользователя

**Условие применения:**
- Кнопка или элемент не вызывает никакого действия при клике
- Нет ошибок в Console (скрипт "молчит")
- Нет POST/запроса в Network при взаимодействии
- Скрипт сгенерирован на бэкенде и вставлен в шаблон через `| safe`

**Путь:**
```
@AUDITOR
  → строит цепочку: клик → обработчик → fetch → сервер → ответ → UI
  → проверяет слой браузера:
      typeof window.[функция] в Console → "undefined"? → скрипт не выполнился
      Elements: скрипт выше DOM-элементов? → race condition
  → находит: скрипт выполнялся до DOM, обращение к null → TypeError до присвоения
@ARCH
  → решение: window.[функция] присваивать в самом начале IIFE
  → инициализацию DOM-зависимых частей — в DOMContentLoaded с fallback
  → try/catch вокруг инициализации чтобы ошибка не ломала кнопку
@DEV
  → реализует по промпту @AUDITOR
  → добавляет canary-лог: console.log("[page-name] init OK")
```

**Рецепт (быстрый триггер):**
```
Проблема: кнопка молчит, нет ошибок, нет запросов.

1. Console: typeof window.[имя_функции] → если "undefined" — скрипт упал до присвоения
2. Elements: найти <script> — он выше или ниже кнопки в DOM?
3. Если выше — скрипт выполняется до DOM → перенести присвоение функции
   в самое начало IIFE, инициализацию — в DOMContentLoaded
4. Добавить try/catch вокруг инициализации
5. Добавить canary-лог в конце init
```

**Не работает когда:**
- Проблема на сервере (POST есть, ответ неверный)
- CSP блокирует inline скрипты (в Console будет явная CSP-ошибка)
- Кнопка в iframe с другим origin

**Источник:** AUDITOR_SCHEDULE_CONSTRUCTOR_BUTTON.md, ARCH_SCHEDULE_CONSTRUCTOR_FIX.md

## CRYSTAL_CALENDAR_MODAL_INLINE_ONCLICK

**Задача:** модальное окно или кнопка в кастомной странице не открывается по клику; клик ведёт себя как навигация (прокрутка, переход).

**Условие применения:**
- Модальное окно/кнопка в кастомной странице не открывается по клику
- Клик приводит к прокрутке вверх или к переходу по ссылке вместо вызова обработчика
- Контент страницы генерируется на бэкенде (шаблон, возможно парсинг/пересборка HTML)

**Путь:**
```
@AUDITOR
  → проверяет наличие onclick в финальном HTML (Elements)
  → проверяет влияние BeautifulSoup / decode_contents на inline-атрибуты
@ARCH
  → решение: не парсить через BeautifulSoup фрагмент без <html> для контента с onclick,
    или не вызывать decode_contents для этого фрагмента; альтернатива — не вставлять
    обработчик через inline onclick, а через скрипт (см. CRYSTAL_JS_SILENT_BUTTON)
@DEV
  → реализует по промпту @ARCH
```

**Рецепт (быстрый триггер):**
```
1. Elements: есть ли onclick на кнопке/элементе в итоговой разметке?
2. Если атрибута нет при наличии его в коде генерации — искать парсинг/пересборку HTML
   (BeautifulSoup, decode_contents) и обойти или изменить способ вставки обработчика
3. Если проблема в порядке скриптов или в роутере — применять CRYSTAL_JS_SILENT_BUTTON
   или решение «скрипт в body»
```

**Не работает когда:**
- Проблема в порядке выполнения скриптов (тогда CRYSTAL_JS_SILENT_BUTTON)
- Блокировка CSP или другой origin

**Источник:** AUDITOR_CALENDAR_MODAL_REPORT.md, ARCH_CALENDAR_MODAL_SOLUTION.md

## CRYSTAL_DOCKER_COMPOSE_ENV_SECRETS

**Задача:** секреты и пароли не должны храниться в docker-compose.yml; контейнеры должны получать их из .env.

**Условие применения:**
- Проект использует Docker Compose
- В compose жёстко прописаны пароли БД или другие секреты (POSTGRES_PASSWORD, SECRET_KEY и т.д.)
- Нужна базовая безопасность: один источник правды для секретов (.env), .env в .gitignore

**Путь:**
```
@LEAD / @OPS / @SEC
  → проверка: в docker-compose нет паролей в открытом виде
  → секреты задаются только в .env; compose подхватывает через env_file и подстановку ${VAR}
```

**Рецепт (быстрый триггер):**
```
1. В docker-compose.yml:
   - В начале файла комментарий: переменные из .env; .env не коммитить.
   - Для сервисов с секретами (postgres, api, celery): не хардкодить пароли.
   - Postgres: environment: POSTGRES_USER: ${POSTGRES_USER:-postgres}, POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-postgres}, POSTGRES_DB: ${POSTGRES_DB:-dental_booking}.
   - Сервисы приложения (api, celery): env_file: - .env; в environment для DATABASE_URL использовать подстановку: postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@postgres:5432/${POSTGRES_DB}.
2. В .env.example добавить POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB и все остальные переменные, нужные контейнерам.
3. .env в .gitignore (уже должно быть).
4. README или DEPLOY: «Скопируйте .env.example в .env и задайте секреты; не коммитьте .env».
```

**Как это работает:**
- Docker Compose при запуске загружает .env из директории с compose-файлом и подставляет ${VAR} в значения при разборе.
- Блок `env_file: - .env` передаёт содержимое .env в контейнер как переменные окружения (переменные из `environment:` имеют приоритет над env_file для тех же ключей).
- Итог: пароли и секреты только в .env; в репозитории только .env.example без реальных значений.

**Не работает когда:**
- Оркестрация не Docker Compose (Kubernetes, ECS — там свои механизмы секретов).
- Нужна обязательная переменная без дефолта: использовать синтаксис ${VAR:?VAR must be set}.

**Источник:** запрос пользователя про безопасность .env и docker-compose (dental_booking, 2026-02).

## CRYSTAL_PORT_CONFLICTS_DOCKER_LOCALHOST

**Задача:** избежать ситуации, когда новый проект не отвечает на localhost, потому что порты или контейнеры уже заняты старыми проектами.

**Условие применения:**
- На `http://localhost:PORT` (например, 8000, 5432, 6379) "ничего не отвечает" или приходит не тот проект.
- На машине уже есть другие проекты с Docker / локальными сервисами.
- Появляются ошибки подключения к БД/Redis, хотя конфиг текущего проекта выглядит корректным.

**Путь:**
```
@OPS / @DEV
  → перед выбором/назначением порта для проекта:
      - проверить, не занят ли порт локальными процессами и контейнерами
      - убедиться, что имена контейнеров и compose-проекты уникальны
  → при проблемах с localhost:
      1. Проверить контейнеры:
         - docker ps            # запущенные контейнеры
         - docker ps -a         # все контейнеры (в т.ч. остановленные)
         - docker-compose ps    # контейнеры текущего проекта
      2. Проверить порты на Windows:
         - PowerShell: Get-NetTCPConnection -LocalPort 8000,5432,6379
      3. Если порт занят чужим проектом:
         - остановить ненужные контейнеры/службы ИЛИ
         - переназначить порты publish в docker-compose.yml текущего проекта
  → зафиксировать конечный набор портов в README проекта.
```

**Рецепт (быстрый триггер):**
```
1. Перед добавлением в docker-compose блока ports:
   - выбрать базовые порты (8000 для API, 5432 для Postgres, 6379 для Redis)
   - проверить занятость:
     PowerShell:
       Get-NetTCPConnection -State Listen | Where-Object { $_.LocalPort -in 8000,5432,6379 }
2. Если порт уже используется:
   - либо остановить старый проект (docker stop ... / docker-compose down в старом каталоге),
   - либо выбрать свободный внешний порт (например, 8001 вместо 8000) и отразить это в README.
3. При "другая" БД или API на localhost:
   - docker ps / docker-compose ps
   - проверить, какой именно контейнер слушает порт (docker inspect или docker ps --format '{{.Ports}}').
4. В README явным текстом указать:
   - какие порты использует проект,
   - команду для остановки/запуска только этого проекта.
```

**Не работает когда:**
- Проблема в самом приложении (ошибка в коде, падение контейнера до старта сервера).
- Порты блокируются корпоративными политиками/фаерволом (нужна диагностика на уровне ОС/сети).

**Источник:** конфликт нескольких проектов на localhost и docker-compose (dental_booking, 2026-02).

## CRYSTAL_FRONTEND_NO_TAILWIND_FOR_PYTHON_SAAS

**Задача:** в Python/FastAPI‑проекте со SPA на React фронтенд ведёт себя нестабильно («молчащие» кнопки, странные перерисовки, расфокусировка), отладка затягивается, а корень проблемы неочевиден, при этом Tailwind используется как основной слой стилизации.

**Условие применения:**
- Бэкенд — Python (FastAPI) в режиме SAAS/MVP.
- Фронтенд — React + TypeScript, Tailwind как главный способ верстки (utility‑классы везде).
- Симптомы UI («кнопка дергает страницу», нет событий/логов, сложность воспроизведения) уже съели заметное время; бэкенд и API‑контракты по тестам работают.
- Команда не специализируется на глубокой фронтенд‑разработке (нет отдельного сильного FE‑инженера, стек поднимает бэкенд‑разработчик).

**Путь:**
```
@AUDITOR
  → фиксирует: API по тестам работает; проблема воспроизводится только в браузере;
    кнопки не дают ожидаемого эффекта, при этом отладка по логам не даёт быстрого решения.

@ARCH
  → принимает, что UI‑слой в текущем виде — тупик по соотношению «затраты/прибыль».
  → решение:
      - оставить React + TypeScript,
      - отказаться от Tailwind как основного способа верстки,
      - перейти на компонентную библиотеку уровня MUI / Ant Design / Mantine
        (готовые кнопки, формы, layout), плюс тонкий слой своих CSS‑правил.
  → для простых проектов на Python SAAS фиксирует правило:
      - Tailwind использовать только для лендингов / статичных страниц
        или при наличии выделенного фронтенд‑разработчика.

@DEV
  → по плану @ARCH:
      1. Убирает Tailwind из сборки (postcss/tailwind.config, классы) или переводит его
         в режим «только для отдельных страниц».
      2. Поднимает выбранную UI‑библиотеку (MUI / Mantine и т.п.).
      3. Переносит критические экраны (админка, пациентское приложение) на готовые компоненты:
         AppBar, Drawer/Sidebar, Form, Button, TextField, Table.
      4. Обновляет ROLE_FRONTEND/TESTING_CANON с указанием новой библиотеки как дефолтной
         для Python SAAS‑проектов.
```

**Рецепт (быстрый триггер):**
```
Если:
  - проект на Python (FastAPI) в режиме SAAS,
  - фронт на React+TS с Tailwind как основной версткой,
  - уже потрачены несколько итераций на странные UI‑баги («кнопка молчит», «страница дергается»),
  - API по тестам работает,
то:
  1. Зафиксировать это как тупик UI‑слоя.
  2. Вызвать @ARCH с прямым запросом:
       «Предложи план миграции на React+TS + компонентную библиотеку без Tailwind
        (минимальная переразметка админки и приложения пациента)».
  3. Принять новый стек как дефолт для похожих Python SAAS‑проектов.
```

**Не работает когда:**
- Проект enterprise‑уровня с отдельной сильной FE‑командой (там Tailwind может быть осознанным выбором).
- Проблема явно в бэкенде/контрактах (тесты падают, POST/ответы некорректны).

**Источник:** текущий проект Dental Booking (долгая отладка «молчащих» кнопок в админке при рабочем API и тестах).
