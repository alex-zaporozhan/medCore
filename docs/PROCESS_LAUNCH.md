# 🚀 PROCESS_LAUNCH — Запуск любого проекта

> Универсальный процесс. Запускай для каждого нового продукта.
> Не пропускай этапы — каждый существует потому что кто-то пропустил.
>
> Состояния сессии, протокол передачи и quality gate — docs/ENGINEERING_PLAN.md.

---

## Фаза 0: Идея (до любого кода)

**Цель:** Понять, стоит ли строить.
```
[ ] Сформулировал идею одним предложением ("Мы помогаем [кому] делать [что] без [боли]")
[ ] @BIZ провёл KILL SIGNAL проверку — все 6 пунктов ОК (или получен вердикт НЕ СТРОИТЬ)
[ ] @BIZ создал MARKET_AUDIT.md — конкуренты с реальными ценами и жалобами, дифференциатор, канал
[ ] Запустил @CREATOR → Pre-flight (LEGAL / MARKET / TECH) прошёл без 🔴
[ ] @CREATOR провёл High-Tech Baseline — определили что берём в MVP
[ ] BUSINESS_LOGIC.md создан и заполнен
```

**Выход:** MARKET_AUDIT.md + BUSINESS_LOGIC.md заполнены. Без MARKET_AUDIT.md — @LEAD не стартует план.

---

## Фаза 1: MVP (минимальный рабочий продукт)

**Цель:** Первый платящий клиент.
```
[ ] MVP из BUSINESS_LOGIC.md реализован (только пункты оттуда)
[ ] Хостинг в РФ (Selectel / Timeweb / Yandex Cloud) если есть ПДн
[ ] Данные в PostgreSQL, не в Google Sheets
[ ] Платёжная система: ЮKassa / Тинькофф / Robokassa
[ ] Уведомления через NotificationService (Telegram + Email fallback)
[ ] Базовая обработка ошибок: try/except + логи
[ ] .env не в git (.gitignore проверен)
[ ] Первый клиент получил демо и дал обратную связь
```

**Выход:** Есть один платящий клиент или явная причина почему нет.

---

## Фаза 2: Стабильность (после первых денег)

**Цель:** Система не падает под реальной нагрузкой.
```
[ ] Retry с экспоненциальной задержкой для внешних API
[ ] Circuit breaker для критичных интеграций (платежи, внешние API)
[ ] Idempotency keys для операций которые нельзя дублировать
[ ] Транзакции БД для атомарных операций
[ ] Celery + Redis для фоновых задач
[ ] Автобэкап БД (минимум раз в сутки)
[ ] Alembic миграции (не менять схему вручную)
[ ] Sentry для ошибок
```

**Выход:** 5 клиентов работают без жалоб на сбои неделю.

---

## Фаза 3: Рост (после product-market fit)

**Цель:** Система выдерживает 10x рост без переписывания.
```
[ ] Prometheus + Grafana или аналог (метрики)
[ ] Структурированные логи (logging с уровнями, не print())
[ ] OpenAPI документация (из FastAPI автоматически)
[ ] Тесты: критические пути покрыты
[ ] Dead Letter Queue для неудачных задач
[ ] Кэширование частых запросов (Redis)
[ ] Горизонтальное масштабирование проверено (stateless сервисы)
[ ] Disaster recovery план задокументирован
```

**Выход:** Система выдержала пиковую нагрузку без ручного вмешательства.

---

## Перед релизом / деплоем (Quality Gate)

**Цель:** Не выпускать в прод критические дефекты и уязвимости.
```
[ ] @QA — финальное тестирование: все P0/P1 закрыты
[ ] @SEC — аудит безопасности: критичные уязвимости закрыты
[ ] @LEAD — явное решение: релиз разрешён
```

Полный чек-лист Quality Gate — docs/ENGINEERING_PLAN.md.

**Выход:** Релиз выполняется после прохождения gate.

---

## После деплоя (до передачи клиенту)
```
[ ] Лицензия и защита: договор/оферта подписан, LICENSE.txt в папке деплоя
    (по запросу — @LAWYER: docs/ROLE_LAWYER.md)
[ ] Коммерческий пакет: COMMERCIAL_PACK_[Проект].md заполнен
    (@BIZ: цена, описание, конкуренты, возражения, ROI)
[ ] Текст для карточки продаж готов (из COMMERCIAL_PACK_*.md)
```

**Выход:** Клиент получает папку только после принятия условий.

## Правила процесса

**Фазы не перепрыгивай.** Нет смысла настраивать мониторинг без первого клиента.

**Чеклист — не галочки ради галочек.** Отмечай только реально сделанное.

**BUSINESS_LOGIC.md — живой документ.** Каждое значимое решение дописывается туда.

**NotificationService — строй с абстракцией:**
```python
class NotificationService:
    async def send(self, user_id: str, message: str, level: str = "info"):
        # Telegram → Email fallback → очередь
        pass
```
30 минут один раз. Страхует от любых блокировок.

## Быстрый старт
```
1. "Мы помогаем [кому] делать [что] без [боли]"
2. @CREATOR → Pre-flight + High-Tech Baseline + BUSINESS_LOGIC.md
3. @LEAD → архитектурное планирование
4. Решение: строить MVP или нет
```

Весь процесс до решения — максимум 2-3 часа.
