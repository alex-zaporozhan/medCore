# TEMPLATE_MODULE_DEV — Стандарт разработки модулей (для @ARCH и новых проектов)

> **Назначение:** Выжимка из техпаспортов и архитектурных ценностей. Используется как эталон при проектировании **любого нового модуля** в текущем и в других проектах.  
> **@ARCH обязан** иметь в виду этот документ при планировании архитектуры модуля и при создании ARCH_* и TPF_MODULE_* (или аналогов).

**Источники (в этом проекте):** `docs/ARCHITECTURE_EXCELLENCE_PASSPORT.md` (NFR и дисциплина поставки), `docs/DOMAIN_STANDARDS.md` (типы страниц и чеклисты), `docs/NONFUNCTIONAL_SCORECARD.md` (KPI команды — если ведётся), `docs/TPF_MASTER.md` (карта модулей / TPF). Устаревшие REV/TECH_PASSPORT-* лежат только в `docs/artifacts/archive/` — **не** использовать как эталон для новой работы.

## 1. Универсальные стандарты (применяются к каждому модулю)

### 1.1. Законы UI (обязательны)

| Стандарт | Правило | Проверка |
|----------|---------|----------|
| **Drawer > Modal** | Создание и редактирование сущностей — только в Drawer (position right, size lg/md). Modal — только Confirm/Alert. | В спецификации модуля явно указано: «форма в Drawer». |
| **ActionMenu в строке** | В каждой строке таблицы/списка справа — кнопка «три точки» → Menu с действиями (Редактировать, Удалить + контекстные). | Для каждого списка перечислены пункты меню и эндпойнты. |
| **EmptyState** | При пустом списке (`length === 0`) — компонент с иконкой, заголовком, описанием и одной кнопкой CTA. | В макете/спеке есть описание EmptyState для каждого пустого состояния. |
| **Skeleton, не Loader** | Загрузка данных — Skeleton по контуру контента. Полноэкранный Loader запрещён. | В разделе «Загрузка» указан Skeleton, не спиннер. |
| **Relational Integrity** | Формы не создают сущности без минимально необходимых связей (напр. Task: assignee_id, due_date; Transaction: cashbox_id, amount, type, category). | В API-контракте и форме перечислены обязательные поля; бэкенд возвращает 422 с деталями. |
| **Zero-Click Context** | Где отображаются имена людей/контрагентов — при наведении HoverCard/Tooltip (телефон, ключевая метрика). | В спеке указано, где применяется; при необходимости — lightweight API для summary. |

### 1.2. Законы API и бэкенда

| Стандарт | Правило | Проверка |
|----------|---------|----------|
| **Контракт первичен** | Каждое действие UI опирается на явный эндпойнт (существующий или спроектированный). В ARCH_* или модульном документе указаны метод и путь. | Таблица эндпойнтов в документе модуля. |
| **Идемпотентность** | Операции с Optimistic UI (drag, смена статуса) — идемпотентные PATCH/PUT или с `idempotency_key` для финансов. | В ARCH зафиксировано. |
| **Tenant isolation** | Все запросы в контексте мультитенанта содержат tenant_id (из токена/контекста). | В контракте и зависимостях указано. |
| **Версионирование** | Путь API с версией (`/api/v1/`). Обратная совместимость при изменениях. | В путях эндпойнтов указана версия. |

### 1.3. Цели системы (что максимизируем)

- **Операционная эффективность:** Минимум кликов до результата; контекст не теряется (Drawer); один экран — один пульт.
- **Плотность и смысл данных:** Компактные таблицы; обогащённые карточки (вкладки), а не формы из 3 полей; контекст без перехода (HoverCard).
- **Проактивность:** Лента внимания с кнопками действий; SLA/Time-Bomb где уместно; AI как помощник (подсказки, пулы задач).
- **Ощущение скорости:** Optimistic UI для мутаций; Skeleton при загрузке; Premium Empty States.

## 2. Типы модулей и обязательные элементы

При проектировании определить тип модуля и применить соответствующий минимум.

### 2.1. Модуль-список (таблица сущностей)

**Примеры:** Пациенты, Записи, Врачи, Услуги, Лиды (таблица), Задачи (таблица), Кассы, Шаблоны форм.

**Обязательно:**

- Страница с таблицей (Data Density: `verticalSpacing="sm"`).
- Context Bar сверху: заголовок + кнопка главного действия (например «Создать задачу»).
- В каждой строке — ActionMenu с набором действий (минимум: Редактировать, Удалить; плюс контекстные).
- Клик «Создать» / «Редактировать» открывает **Drawer** с формой или карточкой (вкладки при обогащённой сущности).
- EmptyState при пустом списке с CTA.
- Загрузка: Skeleton таблицы.
- Эндпойнты: GET list (с фильтрами/пагинацией), GET by id (для Drawer), POST/PUT/DELETE; для каждого пункта ActionMenu — явный эндпойнт или комбинация.

### 2.2. Модуль-карточка сущности (обогащённая)

**Примеры:** Карточка пациента, записи, врача, услуги, лида.

**Обязательно:**

- Открытие в Drawer (position right, size lg).
- Структура: **Header** (аватар/ключевые поля/теги/метрики) + **Tabs** (несколько вкладок с логически сгруппированными данными). Не допускается «форма из 3 полей» для уровня Business OS.
- Вкладки: минимум 2–4 (например [Основное], [История/Связанные], [Финансы], [Заметки]). Каждая вкладка — таблица подтаблиц, формы или контент с привязкой к сущности.
- API: GET by id с вложенными коллекциями или отдельные запросы по вкладкам; PUT/PATCH для редактирования; валидация обязательных связей.

### 2.3. Модуль-пульт (три колонки)

**Примеры:** Чат (чаты | переписка | контекст клиента), CRM (фильтры | канбан | Drawer лида), Задачи (фильтры | канбан/таблица | Drawer задачи).

**Обязательно:**

- Layout: колонка 1 (список/фильтры) | колонка 2 (основной контент) | колонка 3 (детали/контекст или Drawer при выборе).
- В колонке списка — бейджи/индикаторы статуса (например «Ждёт ответа», «AI ведёт»); фильтры-таблетки при необходимости.
- Действия без ухода с экрана: кнопки в контенте или Action Bar (например Запись, Счёт, Анкета в чате) открывают Drawer или компактный Modal.
- Hotkeys: Escape закрывает Drawer; при необходимости Cmd+Enter для отправки, Cmd+J для фокуса поиска.
- Эндпойнты: список с флагами/агрегатами, детали выбранного, действия (создать запись, отправить ссылку и т.д.).

### 2.4. Модуль-дашборд

**Примеры:** Главный дашборд (метрики + лента внимания + таймлайн).

**Обязательно:**

- Верхний ряд: 2–4 виджета-метрики с цифрой и динамикой (% или Sparkline).
- Одна или две колонки контента: лента событий (Attention Feed) с кнопками действий на карточках; при необходимости таймлайн/список «на сегодня».
- EmptyState для пустой ленты.
- Загрузка: Skeleton виджетов и ленты.
- Эндпойнты: агрегаты для метрик, feed (список событий с типами и payload для кнопок).

### 2.5. Модуль с drag-and-drop (канбан/календарь)

**Примеры:** CRM Kanban, календарь записей, задачи (канбан).

**Обязательно:**

- Drag-and-Drop с **оптимистичным обновлением**: UI меняется до ответа сервера; при ошибке — откат и уведомление.
- API: PATCH/PUT с идентификатором и новым состоянием (stage_id, slot и т.д.); операция идемпотентна.
- В шапке колонок/дней при необходимости — агрегаты (сумма, количество).
- Клик по элементу открывает Drawer с карточкой сущности (по типу «модуль-карточка»).
- EmptyState для пустых колонок (или placeholder «Перетащите сюда»).

## 3. Скелет документа модуля (для @ARCH)

При создании нового модуля заполнить документ по следующей структуре. В этом проекте используется префикс `TPF_MODULE_` и связь с `TPF_MASTER`; в другом проекте можно использовать свой префикс (например `MODULE_`, `SPEC_`).

```markdown
# [PREFIX]_MODULE_[NAME] — [Название модуля]

> Связь с мастер-документом и RAG/картой (если есть).

---

## 1. Назначение
Одна-две фразы: зачем модуль, какой пульт/задачу закрывает. «Админ не уходит с экрана, чтобы…».

---

## 2. Структура экрана
- Макет (колонки, блоки). Для списка — таблица + Context Bar. Для пульта — три колонки. Для карточки — Header + Tabs.
- Перечень блоков/компонентов с кратким описанием (что показывается, какие кнопки).
- Где Drawer, где EmptyState, где ActionMenu.

---

## 3. Эндпойнты
| Данные / Действие | Метод/путь | Примечание (обязательные поля, идемпотентность, tenant) |

---

## 4. Правила UI
- Специфичные для модуля (например «Escape закрывает Drawer», «Rich Bubbles для платежей»).
- Ссылка на универсальные законы (Drawer, EmptyState, Skeleton, ActionMenu).

---

## 5. Ссылки
- Страница (путь). Сущности (доменные объекты). Связь с другими модулями.
```

---

## 4. Чек-лист при планировании модуля (@ARCH)

Перед фиксацией архитектуры и передачей в DEV проверить:

- [ ] **Тип модуля определён** (список / карточка / пульт / дашборд / drag-and-drop) и применён минимум из раздела 2.
- [ ] **Drawer для создания/редактирования** заложен; Modal только для Confirm/Alert.
- [ ] **ActionMenu** для каждого списка/таблицы с перечнем действий и эндпойнтов.
- [ ] **EmptyState** описан для каждого пустого состояния.
- [ ] **Загрузка** — Skeleton, не Loader.
- [ ] **Relational Integrity** для форм: обязательные поля перечислены; бэкенд валидирует и возвращает 422 с деталями.
- [ ] **Контракты API** перечислены в документе модуля (метод, путь, тело, коды ошибок).
- [ ] **Optimistic UI** для drag/смены статуса: операция идемпотентна, контракт зафиксирован.
- [ ] **Tenant isolation** учтён в запросах.
- [ ] Документ модуля заполнен по **скелету** из раздела 3 (назначение, структура, эндпойнты, правила, ссылки).

## 5. Примеры-эталоны (в этом проекте)

| Модуль | Документ | Эталон для |
|--------|----------|------------|
| Пульт (три колонки) | TPF_MODULE_OMNICHAT | Чат, операционная среда, Action Bar, контекст справа. |
| Карточка сущности | TPF_MODULE_ENTITIES | Patient, Booking, Doctor, Service — вкладки, без «коротких» форм. |
| Список + CRUD | TPF_MODULE_TASKS, TPF_MODULE_FINANCE | Таблица, ActionMenu, Drawer, EmptyState, Relational Integrity. |
| Канбан | TPF_MODULE_CRM | Столбцы, суммы в шапке, Lead Rotting, Drawer по клику. |
| Дашборд | TPF_MODULE_DASHBOARD | Метрики, Attention Feed с кнопками, таймлайн. |
| Каркас | TPF_MODULE_SHELL | Sidebar, Collapse, Context Bar, Spotlight. |

В другом проекте можно завести свои эталоны по той же структуре (тип модуля → документ-пример).
