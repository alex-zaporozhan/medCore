# Эталон логики продукта (business coherence)

> **Путь:** `docs/LEAD_PRODUCT_LOGIC_EXCELLENCE.md`  
> **Роль:** @CREATOR (пакет на старте) · @DOMAIN_EXPERT (карта процессов) · @LEAD (приёмка «есть ли смысл») · @QA_ARCH (проверка соответствия экрана роли в процессе).  
> **Не заменяет:** `DOMAIN_STANDARDS.md` (типы страниц), `LEAD_PRODUCT_GATE_PROTOCOL.md` (ворота), `ROLE_QA_ARCH.md` (векторы аудита). **Дополняет:** ответ на вопрос *«зачем этот экран в реальном процессе клиники и что оператор должен сделать за 30 секунд»*.

---

## 1. Проблема, которую закрывает этот файл

Машина хорошо делает модалки, сетку и «фичи». Плохо — **самостоятельно** увидеть **процесс**: кто участник, в каком порядке принимаются решения, какие действия обязательны в день, а какие — редкий edge case. Без явной логики получается продукт «много кнопок, мало денег»: декоративный UI, мёртвые действия, отсутствие критичных шагов.

Этот документ — **шаблон эталона логики**: как зафиксировать процесс так, чтобы по нему можно было проверить экран и код, а не «нравится/не нравится».

---

## 2. Артефакт «логика модуля» (минимум)

Для каждого значимого модуля (или группы экранов) в `docs/artifacts/` — отдельный файл или раздел в `BUSINESS_ROUTES.md`:

| Блок | Содержание |
|------|------------|
| **Роль в процессе** | Кто из персонала использует (администратор, врач, владелец). Одна первичная роль на экран. |
| **Триггер** | Что случилось в реальности до того, как человек открыл экран (звонок, no-show, долг, входящее сообщение). |
| **Цель за сессию** | Одна фраза: что должно быть **истиной** после закрытия экрана (запись создана, статус согласован, ответ отправлен). |
| **Обязательная цепочка** | 3–7 шагов в порядке: что **нельзя пропустить** для юридически/коммерчески значимого результата. |
| **Быстрые действия** | Что должно быть доступно **без лишних кликов** (шорткаты, primary CTA, контекстное меню). |
| **Сознательные «нет»** | Что **не делаем** на этом экране (чтобы не раздувать UI); если кнопка есть — она либо ведёт к результату, либо убирается. |

Без этого блока @LEAD не считает модуль согласованным с бизнесом — независимо от прохождения технических ворот.

## 3. Аудит «мёртвые кнопки vs дыры»

Проводит @QA_ARCH или @LEAD по готовому UI (после GATE-2):

| Вопрос | FAIL, если |
|--------|------------|
| Каждая видимая кнопка/пункт меню ведёт к завершённому сценарию с бэкендом? | Есть заглушка, 501, пустой ответ, «скоро» без пометки заглушки согласованной с @LEAD |
| Каждый шаг из §2 «обязательная цепочка» достижим с этого экрана или с явного родителя? | Нужен обход через разработчика или консоль |
| Количество модальных окон на один сценарий | Больше двух без обоснования в ARCH — запах «театра» |
| Дублирующие контуры (два «чата», два расписания) | Нет источника истины в `ARCH_*.md` |

Результат — таблица в `QA_REPORT` или отдельный подпункт: **Logic coherence: 🟢 / 🟡 / 🔴**.

## 4. Связь с @CREATOR

@CREATOR на старте обязан **не только** собрать MARKET_AUDIT и BUSINESS_ROUTES, но и **набросать первый эталон логики** для одного критичного journey (запись / оплата / коммуникация — что объявлено дифференциатором): §2 таблица заполнена хотя бы для одного модуля. Иначе последующий UI неизбежно становится набором экранов без процесса.

---

## 5. Связь с воротами

- **GATE-1:** в `ARCH_*.md` или `DEV_PROMPTS` — ссылка на раздел логики в `BUSINESS_ROUTES.md` / эталоне модуля.  
- **GATE-3:** @QA_ARCH проверяет §3 этого файла там, где применимо.  
- **GATE-6:** при L-оценке «обман ожидания» (UI без процесса) — P0 в слое «Продукт», см. `docs/LEAD_PRODUCT_GATE_PROTOCOL.md` (GATE-6).
