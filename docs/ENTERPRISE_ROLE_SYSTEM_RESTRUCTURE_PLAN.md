# План реструктуризации системы ролей под Enterprise SaaS

> **Приоритет:** HIGH — первичное ревью: **@LEAD**  
> **Черновик / решения слоя знаний:** @QA_ARCH  
> **Статус:** **В РЕАЛИЗАЦИИ** (фаза 1 инфраструктуры знаний зафиксирована в репозитории: `docs/product_state/`, `ENGINEERING_PLAN` §5, PROJECT MEMORY в `.cursorrules`)  
> **Предпосылка:** слой W в `docs/artifacts/` зачищен под RAG (spine + corpus + узкий набор паспортов); политика S — `docs/product_state/README.md`.  
> **Согласование с @SCRIBE:** выходы слоя S — по `docs/ROLE_SCRIBE.md` и `docs/product_state/README.md`; этот файл **не** заменяет `ROLE_SCRIBE`.

---

## A. Решения пользователя и @QA_ARCH (канон смысла)

1. **Корень `docs/` (вне `artifacts/` и `product_state/`)** — канон процесса: `ROLE_*.md`, шаблоны, паспорта, `ENGINEERING_PLAN`, протоколы. **Не раздувать** и **не превращать** в помойку ссылок на временные планы. Массовые правки только по явной задаче пользователя (закон 16 в `.cursorrules`).
2. **Зачистка под «свежий RAG»** — в фокусе **`docs/artifacts/`** (слой W и исторический шум). Цель: модель не подменяет код устаревшими `ARCH_*` / `DEV_PROMPTS_*`.
3. **Отдельный слой S** — **`docs/product_state/`**: продуктовая правда для AI + людей + согласованные снимки (OpenAPI и т.д.), см. `docs/product_state/README.md` (INV-1, INV-6, allowlist).
4. **Инвариант документирования этого плана:** **запрещено** вшивать ссылку на **этот** файл в каждый `ROLE_*.md` как обязательную «навигацию». Временный или эволюционирующий план не должен стать хвостом в канонических ролях. Допустимо: одна строка в `ENGINEERING_PLAN` §5 и в `product_state/README.md` (уже есть). Дальнейшие правки ролей — **точечно** по таблице раздела 5 **после** явного запроса пользователя / задачи @LEAD.
5. **Перед полным удалением содержимого `artifacts/`:** осознанно решить, что переживёт только в git, что требует **3–5 переносов смысла** в канон `/docs` или в сессию @ARCH / @SCRIBE (см. раздел B), и обновить навигацию (`ARTIFACT_MAP` / карта «где правда»).

---

## B. Что не потерять смыслом при зачистке `docs/artifacts/` (матрица @QA_ARCH)

Уровни не про «копировать всё», а про **замену** (код, OpenAPI, `DOMAIN_STANDARDS`, паспорта, `product_state`).

| Уровень | Суть | Действие перед удалением |
|---------|------|---------------------------|
| **A** | Бизнес-карта, IA, намерения продукта | Если в `/docs` нет эквивалента — выжать 1–2 стр. «намерение vs код» или сессия @DOMAIN_EXPERT / @ARCH |
| **B** | Сквозные инварианты (multitenant, NFR gap коробка→SaaS) | Если не покрыто паспортами — один осознанный перенос в канон `/docs`, не надеяться на RAG по сотням страниц |
| **C** | Журналы решений, плейбуки | История команде; для RAG — только с пометкой «контекст», иначе модель оправдывает устаревшее |
| **D** | Очереди: `DEV_PROMPTS_*`, `ARCH_DEV_*`, GAP, бэклоги | Для объективного RAG **вредны** как «канон»; смысл — **git history**; уникальный вывод — редко, можно выписать вручную |
| **E** | Узкие эпики (leads, omni, enterprise staff) | Сохранять смысл только если эпик активен и в коде нет читаемой спеки |

**Риск:** вакуум контракта и навигации после удаления. **Митигация:** SoT API (код, `/openapi.json`, тесты) + карта в `product_state/README.md` + allowlist RAG.

## 0. Оценка @LEAD: система и документ

### 0.1 Сильные стороны текущей системы

- Чёткая цепочка (`ENGINEERING_PLAN`, ворота, Transmission Protocol).  
- Разделение «код пишет @DEV» и ролей-документов.  
- @QA_ARCH как обязательный gate.  
- Паспорта и `DOMAIN_STANDARDS` вне `artifacts/` — слой **P**.  
- @SCRIBE закрывает дыру продукта для слов и дисциплины источников.

### 0.2 Слабое место (корневая причина)

Один каталог `docs/artifacts/` совместил **S-подобные** тексты и **W (хвосты волн)**; индексатор не отличает фазу 2024 от кода → *читаем markdown вместо репозитория*. Исправление — **топология** (P / S / W + политика индекса), а не «ещё один большой ARCH».

### 0.3 Оценка документа (итог)

Диагноз P/S/W и эволюция ролей под Enterprise — 🟢. Явный победитель размещения S — §4.2. Пробелы по GATE-6 и закону 16 закрыты оговорками в §4.4, §8 и разделе A.

## 1. Зачем этот документ

Цель — режим **взрослого SaaS**: нагрузка, безопасность, наблюдаемость, мультитенантность, продаваемость и **одна иерархия источников правды** без смешения W и S в голове модели.

Ограничение: этот текст — **ориентир исполнения**; массовые правки `ROLE_*` и `.cursorrules` вне согласованного scope — только по явному запросу пользователя (закон 16).

### 2.2–2.4 Стек, Grafana, системные документы

## 3. Диагноз (кратко)

| Риск | Митигация |
|------|-----------|
| Индексатор тянет большие `artifacts/*.md` | `.cursorignore`, allowlist в `product_state/README.md` |

**Перед резкой контрактных `ARCH_*`:** зафиксировать SoT API (один выбор). Временной мост ≤ 1 недели с датой снятия — только по решению @LEAD.

## 4. Целевая архитектура знаний

### 4.1 Три слоя

1. **P** — как строим и проверяем: `ROLE_*`, `ENGINEERING_PLAN`, протоколы, шаблоны, паспорта.  
2. **S** — что должно совпадать с деплоем: `docs/product_state/` + машинные снимки.  
3. **W** — хвосты волн: `docs/artifacts/` (`DEV_PROMPTS_*`, `QA_REPORT_*`, черновики); короткий срок жизни, по умолчанию вне «свежего RAG».

### 4.2 Физическое размещение (победитель: вариант B)

| Слой | Где | RAG |
|------|-----|-----|
| **P** | `docs/` (кроме `artifacts/`, `product_state/`) | Высокий для процесса |
| **S** | `docs/product_state/` | Allowlist для «что умеет продукт» |
| **W** | `docs/artifacts/` | Низкий / исключение |

**Мягкий переход:** allowlist может опережать физическое наполнение S; список канонов — только в `product_state/README.md` (INV-1).

### 4.3 RAG «свежий»

- Якорь S: `PRODUCT_KNOWLEDGE_BASE.md` (когда есть) + OpenAPI + код.  
- **INV-3:** W не в allowlist как S без `layer:W` и TTL.  
- Архив `archive/_outdated` — слой H, не смешивать с живым корпусом.

### 4.4 Ворота продукта

`LEAD_PRODUCT_GATE_PROTOCOL.md` (в т.ч. GATE-6). @SCRIBE не заменяет ворота.

### 4.5 Инварианты (INV-1 … INV-6)

Без изменения смысла прежней таблицы в версии 0.5: один путь на класс S; P не подменяет факт продукта; код vs S → код; @SCRIBE с источниками; **INV-6:** реестр M-XX — **ровно один** путь: **`docs/artifacts/METRICS_REGISTRY.md`** (пока не перенесён отдельной задачей в `product_state/` с обновлением `METRICS_PROTOCOL` и всех ссылок).

### 4.6 Разрешение конфликтов

Таблица §4.6 версии 0.5 сохраняется (два файла S → один канон; P vs код → код + правка P по закону 16; @SCRIBE vs OpenAPI → OpenAPI; W vs код → код; Grafana vs описание SLO → запущенная система, затем P).

### 4.7 @PRINCIPLE при смене топологии

Порядок: фаза 0 → 1 → массовая зачистка. Один PR на связку путей. Чеклист для @PRINCIPLE — нумерованный, не размытый «G6+…».
