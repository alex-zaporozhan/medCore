# Внутренний чат персонала: мультитенантность, данные и политика владельца

## Граница тенанта

- **Операционная граница изоляции** — строка `clinics.id` (`clinic_id` в JWT и в строках `admins`, `staff_chat_*`, календаря и т.д.).
- Все запросы к API внутреннего чата выполняются **только в контексте одной клиники**; данные другой клиники не смешиваются на уровне приложения (фильтр по `clinic_id`).

## Видимость между салонами / филиалами

Решение **владельца бизнеса**, нужен ли общий контур персонала между разными точками (разными `clinic_id` в системе), фиксируется в поле:

- `clinics.staff_chat_scope` (строка, по умолчанию `clinic_isolated`).

Значения:

| Значение | Смысл |
|----------|--------|
| `clinic_isolated` | Внутренний чат, комнаты и календарь персонала — **только внутри одной клиники**. Текущее поведение продукта. |
| `network` | **Зарезервировано**: сеть салонов одной сети (общие комнаты между `clinic_id`) — требует отдельной модели «организация / сеть» и миграций; **не включать без эпика**. |

Пока реализовано только **`clinic_isolated`**. Смена режима на `network` не должна молча открывать кросс-клинику — только после явной реализации и миграций.

## Доступ к комнатам (строгая модель)

- Список комнат, сообщения и вложения доступны **только участникам комнаты** (`staff_chat_room_members`), кроме синхронизации общего канала: в **GENERAL** автоматически включаются все активные админы данной клиники.
- **DM** — ровно два участника; приглашения не применяются.
- **GROUP / TASK** — новых участников можно добавлять **только через приглашение** участником комнаты (`POST .../chat/rooms/{room_id}/members`).
- **TASK**-комната создаётся только если вызывающий — постановщик или исполнитель задачи; прочие попадают в комнату **только по приглашению** изнутри.

## База данных и «не путать тенантов»

- Используется **одна** база PostgreSQL, **общая схема**, разделение — колонкой **`clinic_id`** и проверками в сервисном слое (и тестами на изоляцию).
- Альтернативы на будущее (только при нагрузке/комплаенсе): отдельная схема на клинику, отдельная БД на крупного клиента — **не текущий таргет** без ADR.
- Файлы вложений хранятся на диске под путём с префиксом `clinic_id` в каталоге загрузок; метаданные — в строках с `clinic_id`.

## Кэш (Redis)

- Любые ключи кэша, связанные с staff collab, должны включать **`clinic_id`** (и идентификатор сущности), например: `staff_collab:{clinic_id}:...`, чтобы исключить смешение между клиниками.

## Что означает «UI для смены staff_chat_scope» (пояснение)

**Идея:** владелец или супер-админ в **настройках клиники** видит переключатель «Внутренний чат персонала: только эта клиника / (в будущем) сеть салонов».

- **Сейчас:** в БД колонка `clinics.staff_chat_scope` хранит значение по умолчанию `clinic_isolated` — все комнаты и сообщения **только** внутри текущей клиники. Отдельного экрана в админке под этот флаг **ещё нет**: режим меняется только миграцией/SQL до появления эпика с UI и моделью «организация / сеть».
- **Зачем UI:** чтобы владелец **не лез в SQL** и не мог случайно включить `network` до готовности бэкенда; после эпика Enterprise переключатель будет связан с политикой из `ENTERPRISE_STAFF_NETWORK_AND_CHAT_2026.md`.

Пока **нет** UI — это **не баг**, а сознательный этап: сначала данные и документация, потом безопасный интерфейс + `network`.
