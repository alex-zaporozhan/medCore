# Политика версионирования публичного и партнёрского API (LEAD)

> **Связь:** embed / widget / owner-интеграции — [SAAS_STRENGTHENING_MASTER_PLAN.md](./SAAS_STRENGTHENING_MASTER_PLAN.md) §24; префиксы — [backend/api_layer.md](./backend/api_layer.md).

## 1. Принципы

1. **Ломающее изменение** — удаление поля, смена семантики, смена кодов ошибок без обратной совместимости, обязательный новый query/body параметр без default.
2. **Неломающее** — добавление опционального поля, новый endpoint, новое значение enum **если** клиенты игнорируют неизвестные значения.

## 2. Публичные REST-эндпоинты (пациент, виджет, интеграции)

**Победитель решения (LEAD):**

- Префикс версии в пути: `/api/v1/...` — текущая линия; следующая ломающая волна — **`/api/v2/...`** с периодом перекрытия **v1** не короче **6 месяцев** после объявления deprecation, если есть внешние клиенты.
- **Deprecation:** заголовок `Deprecation: true` и `Sunset` (RFC 8594) или документированная дата в OpenAPI; анонс в release notes.

## 3. Webhook (входящие от провайдеров и Битрикс24)

- Версия контракта фиксируется в **URL** (например `/webhooks/yookassa/v1`) **или** явным `event_version` в теле — выбрать один стиль на интеграцию и не смешивать.
- Подпись и идемпотентность обязательны (§6 мастер-плана, ADR-011 для контура B).

## 4. Внутренние админские API

- Версия в пути не обязательна при синхронном релизе фронта и бэка; ломающие изменения — в одном релизе с обновлением SPA.
- Для внешних скриптов клиента — считать **публичными** и применять §2.

## 5. Ответственность

| Роль | Действие |
|------|----------|
| **ARCH** | Ревью PR на ломание контракта |
| **LEAD** | Исключения и сокращение окна deprecation |
| **DEV** | OpenAPI / changelog |
