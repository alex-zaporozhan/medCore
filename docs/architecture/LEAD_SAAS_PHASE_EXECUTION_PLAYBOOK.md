# LEAD: исполнение мастер-плана SaaS (цикл ролей и эпик-срезы)

**Назначение:** снизить хаос при реализации [SAAS_STRENGTHENING_MASTER_PLAN.md](./SAAS_STRENGTHENING_MASTER_PLAN.md): что можно «автоматизировать», какой **размер порции** держать в голове, и **в каком порядке** вызывать @LEAD / @ARCH / @DEV / @QA_ARCH.  
**Связь:** дорожная карта — [§15](./SAAS_STRENGTHENING_MASTER_PLAN.md#saas-sec-15) (в т.ч. **§15b** DoD в том же разделе), ворота — **§19** в том же файле; обзор — [INDEX.md](./INDEX.md), [ARCHITECTURE_SAAS_MASTER_OVERVIEW.md](./ARCHITECTURE_SAAS_MASTER_OVERVIEW.md).

---

## 1. Что можно автоматизировать, а что нет

| Уровень | Что делаем | Ограничение |
|--------|------------|-------------|
| **CI / скрипты** | Тесты, линтеры, проверки миграций, smoke | Не заменяют смысловую приёмку и бизнес-риски. |
| **Чеклисты и промпты** | Один и тот же шаблон на каждый эпик-срез (этот документ) | ИИ всё равно «промахивается», если нет preflight @ARCH и узкого scope. |
| **Ворота релиза** | Явное совпадение с **§15b** и **§19** перед merge в main / перед прод-рекламой | LEAD решает исключения. |
| **Роли** | Не автоматизируются: приоритет, противоречия тарифов/ролей, эскалация | @LEAD остаётся человеком в контуре. |

**Вывод:** «автоматизация» здесь = **дисциплина процесса + CI + повторяемые инструкции**, а не один кнопочный прогон всего мастер-плана.

## 2. Размер порции: фаза целиком или меньше?

**Целую фазу (например всю 1b) за один заход через одного @DEV — не рекомендуется:** слишком большой контекст, накапливаются формальные «галочки» и регрессии.

**Победитель (LEAD):** единица исполнения = **эпик-срез**.

**Эпик-срез** — это порция, для которой одновременно верно:

1. Описана **одной фразой** в заголовке тикета/чата (что меняется в продукте/БД/API).
2. Имеет **явный список файлов/модулей** и границу «не трогаем X».
3. Закрывается **измеримым DoD**: тесты, негативный сценарий, OpenAPI-кусок, миграция с откатом — что уместно по §15b для этой порции.
4. Укладывается в **1–3 итерации** цикла DEV → QA → DEV без «переписывания половины фазы».

Примеры срезов внутри фаз (иллюстрация, не исчерпывающий список):

- **1a:** только fork RLS + негативный тест cross-tenant на один домен; **без** сразу полного UI Основателя.
- **1b:** только провижининг после webhook B для одной ветки статусов; **без** сразу всего лендинга и кабинета. Отдельный срез: **публичный checkout** с `billing_period` + сумма из каталога — [PHASE_FULL_CLOSURE_BACKLOG.md](./arch_plan/PHASE_FULL_CLOSURE_BACKLOG.md) **1b-F5**; не смешивать с срезом «гейт webhook» (**1b-F6** — retry/override).
- **1c:** одна группа маршрутов + строки в [ENTITLEMENT_ROUTER_INVENTORY.md](./ENTITLEMENT_ROUTER_INVENTORY.md); **без** сразу всего меню.

**Весь проект одним запуском** — только как **дорожная карта и приоритизация**, не как один промпт к @DEV.

## 3. Канонический цикл на эпик-срез (победитель процесса)

Порядок **жёстче**, чем «сначала весь код фазы, потом аудит».

| Шаг | Роль | Задача |
|-----|------|--------|
| **0** | **@LEAD** | Утвердить **название среза**, границы, приоритет P0/P1, конфликт с тарифами/ролями (или явное «нет»). Зафиксировать **DoD строки** из §15b, относящиеся к срезу. |
| **1** | **@ARCH** | Preflight: спека/API/миграции/envelope §31 — только то, что **блокирует** этот срез. Выход: «можно резать миграции / публичный контракт» или список открытых вопросов к LEAD. |
| **2** | **@DEV** | Реализация **только** среза; тесты и метрики **в том же PR/ветке**, если они в DoD среза. |
| **3** | **@QA_ARCH** | Аудит по [ROLE_QA_ARCH.md](../ROLE_QA_ARCH.md): риски, формальные галочки, NFR (мультитенант, webhook, cardinality). Выход: **`docs/artifacts/QA_REPORT_*.md`** с приоритетами 🔴🟡🟢. |
| **4** | **@DEV** | Закрыть пункты отчёта; эскалация к @ARCH / @LEAD, если находка **архитектурная** или повторяется после оговоренного числа итераций (см. ROLE_QA_ARCH). |
| **5** | **@QA_ARCH** | Повторная проверка **только** закрытых пунктов и регрессии по срезу; обновление отчёта или короткий «закрыто». |
| **6** | **@LEAD** | Приёмка: соответствие среза формулировке шага 0 и воротам §19 при необходимости. |

**Почему не «@QA_ARCH доработай код по отчёту»:** в репозитории зафиксировано: исправления вносит **@DEV**; @QA_ARCH — инспектор и источник отчёта ([ROLE_QA_ARCH.md](../ROLE_QA_ARCH.md), таблица «Связь с ролями»). Исключение по согласованию **@LEAD** (например микропатч докстринга или одна строка конфига) — явно пометить в PR, чтобы не размывать ответственность.

## 5. Связь с твоим прежним процессом (1 → 2 → 3)

| Твой шаг | Как усилить по playbook |
|----------|-------------------------|
| 1. @DEV весь этап | Заменить на **эпик-срезы** + обязательный **шаг 1 @ARCH** перед кодом для P0/P1. |
| 2. @QA_ARCH отчёт | Оставить; формат — артефакт в `docs/artifacts/`. |
| 3. «QA доработай код» | Заменить на **@DEV по отчёту** + контроль **@LEAD** на эскалации; QA — повторная проверка. |

Так сохраняется твоя идея **«сначала код, потом жёсткий аудит, потом доводка»**, но доводка остаётся в зоне ответственности **@DEV**, что совпадает с ролями в репозитории и уменьшает слепые зоны «аудитор переписал и сам себя принял».

## 6. Минимальный чеклист LEAD перед «go» на код

- [ ] Срез назван и **не** равен «вся фаза», если фаза > одного вертикального шага.
- [ ] Прочитаны **§15b** и **§19** на предмет ворот для этого релиза.
- [ ] Для денег/webhook — явное разделение **контур A vs B** (см. мастер-план **§2c**, **§15c**).
- [ ] Для миграций и публичных API — @ARCH preflight выполнен или зафиксированы открытые риски.
- [ ] После merge — кто обновляет **§2b / overview** (частота: по major SaaS-релизу или quarterly, как в плане).
