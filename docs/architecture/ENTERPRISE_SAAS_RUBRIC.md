# Рубрика критики архитектуры под угол зрения Enterprise SaaS

> **Назначение:** единые оси оценки (**1–14**) и шкала, чтобы отличать «код есть» от «продукт и эксплуатация зрелые». Не юридический и не маркетинговый документ — только инженерные критерии. Оси **13–14** — антиспам и security UX ([SAAS_STRENGTHENING_MASTER_PLAN.md](./SAAS_STRENGTHENING_MASTER_PLAN.md) §27–§28).  
> **Правило трассируемости:** любое утверждение в `docs/architecture/` о поведении системы должно иметь якорь в репозитории (путь к файлу) или пометку «не подтверждено / не проверялось в рантайме».  
> **Операционный перечень пробелов и приёмка LEAD:** [LEAD_ACCEPTANCE_CRITIQUE_AND_GAPS.md](./LEAD_ACCEPTANCE_CRITIQUE_AND_GAPS.md) — пересчёт оценок по осям при major-аудите фиксировать там и здесь (краткая сводка в [ARCHITECTURE_SAAS_MASTER_OVERVIEW.md](./ARCHITECTURE_SAAS_MASTER_OVERVIEW.md)).

## Шкала по каждой оси

| Уровень | Значение | Смысл |
|---------|----------|--------|
| **0** | Отсутствует | Нет модели в коде, нет процесса, или нет артефактов в репо. |
| **1** | Частично | Есть зачатки (таблица, эндпоинт, метрика, тест), но нет сквозного сценария или политики. |
| **2** | Зрелое | Явный контракт, автоматические проверки, наблюдаемость, документированные операционные шаги в репо (runbooks). |

**Как ставить оценку по чек-листу:** посчитать выполненные пункты; **0** — большинство «нет»; **1** — есть основа, но нет автоматизации или политики end-to-end; **2** — почти все «да» с якорями в репо и проверкой в CI или runbook.

Оценка в текстах архитектуры: кратко **0 / 1 / 2** по релевантным осям, без балльной агрегации «в цифру продукта».

## Красные флаги при приёмке (стоп-факторы для слова «Enterprise»)

Если выполняется несколько пунктов без явного ADR «принимаем риск», позиционирование как зрелый Enterprise SaaS **нечестно**:

1. **Нет изоляции тенанта на уровне БД** (RLS или эквивалент) **и** нет отдельного контура platform-operator — только кодовые фильтры по `clinic_id`.
2. **Критичные побочные эффекты** (деньги, CRM, ERP) завязаны на **in-process** EventBus **без** outbox/очереди **и** план масштабирования API >1 реплики без изменения модели.
3. **Webhook оплаты** без набора тестов на **повторную доставку** и без явной идемпотентности бизнес-шага по всем веткам статусов.
4. **Чувствительные токены** админки/пациента только в `localStorage` **без** оценки XSS и без плана смягчения (httpOnly, BFF, CSP).
5. **Health-эндпоинты** отдают наружу внутренние тексты ошибок БД/инфраструктуры.
6. **Основной CI** (unit/integration/security) **отключён** или вынесен вне репозитория **без** документированного обязательного процесса.
7. **Нет runbooks** backup/restore и порядка миграций при инциденте — при том что данные — медицинский/CRM контур.

Детализация по текущему репозиторию: [LEAD_ACCEPTANCE_CRITIQUE_AND_GAPS.md](./LEAD_ACCEPTANCE_CRITIQUE_AND_GAPS.md).

## Оси оценки (1–7), затем 8–12 и 13–14

Ниже — оси **1–7** (ядро SaaS), далее блок **8–12**, затем **13–14** (антиспам и security UX — после оси 12).

### 1. Идентичность и границы тенанта

- Есть ли различие **platform** (вендор SaaS) vs **organization** (клиент) vs **clinic** (единица данных)?
- Кто может **создать** нового тенанта и как исключается смешение данных?
- Единый ли столбец/правило изоляции в запросах (`clinic_id`, `organization_id`, RLS)?

**Факт по текущему репозиторию (проверено по entity и роутерам):** изоляция данных задумана прежде всего на уровне **`clinic_id`**. Сущность **`Organization`** группирует клиники (`Clinic.organization_id`), но отдельной модели **владельца платформы** и потока **self-service регистрации нового бизнеса с изоляцией на уровне платформы** в коде нет. Префикс API **`/owner/`** (`owner_omni_*`) **не** означает отдельный тип пользователя: используется **`get_current_admin`**, область — **`current_admin.clinic_id`** (см. `src/api/v1/routers/owner_omni_channels.py`).

**Чек-лист (да/нет):**

- [ ] Явно смоделирован vendor / platform tenant в коде и JWT.
- [ ] Self-service создание нового бизнес-клиента с изоляцией данных.
- [ ] Все запросы к данным арендатора фильтруются одним правилом; RLS или централизованный policy-слой.
- [ ] Аудит: кто из админов какого тенанта выполнил действие.
- [ ] Документ с матрицей «сущность → столбец тенанта → где проверяется».

---

### 2. Жизненный цикл клиента SaaS

- Self-service signup, провижининг организации/клиник, приглашения админов, отключение (offboarding), экспорт данных.

**Чек-лист:**

- [ ] Регистрация нового арендатора без ручного DDL.
- [ ] Приглашение пользователей и срок жизни инвайта.
- [ ] Offboarding: удаление/архивация данных по политике.
- [ ] Экспорт данных клиента (machine-readable) — API или процедура.
- [ ] Документированные лимиты плана (если применимо).

---

### 3. Безопасность и соответствие

- Хранение секретов, RBAC, аудит привилегированных действий, PII/маскирование, rate limiting, модель угроз для публичных эндпоинтов.

**Чек-лист:**

- [ ] Секреты не в git; шаблон `.env.example` полный; ротация задокументирована.
- [ ] RBAC на всех опасных маршрутах; инвентарь прав сверен с тестом.
- [ ] Rate limit на auth и дорогие POST.
- [ ] PII маскируется в логах/ответах где нужно.
- [ ] Утечки в health/metrics проверены (см. U-001).

---

### 4. Надёжность

- Явные SLO/SLI (в коде или docs), health/readiness, идемпотентность webhooks, поведение при сбое реплики, очереди и повторы (DLQ при наличии).

**Чек-лист:**

- [ ] `/health` vs `/ready` разделены если нужно для K8s (или обосновано одно).
- [ ] Webhook и критичные POST идемпотентны; тесты повторов.
- [ ] Доменные события: либо одна транзакция с основным изменением, либо outbox + повторы.
- [ ] Очередь: DLQ или dead-letter политика для Celery (или эквивалент).
- [ ] SLO записаны (latency, error rate) хотя бы в docs с якорем на метрики.

---

### 5. Наблюдаемость

- Метрики, трассировка (`trace_id`), алерты как код, связь дашборд ↔ метрика; не только «эндпоинт `/metrics` есть».

**Чек-лист:**

- [ ] RED/USE метрики для ключевых путей.
- [ ] `trace_id` в логах и ответах ошибок.
- [ ] Алерты в репо (например Prometheus rules) связаны с runbook или комментарием.
- [ ] Дашборды в репо или ссылка на обязательный внешний артефакт.

---

### 6. Операции

- Миграции, бэкапы, восстановление, версионирование конфигов; мультирегион — только если заявлено.

**Чек-лист:**

- [ ] Alembic линейная история; policy на long-running миграции.
- [ ] Runbook backup/restore Postgres в репо или wiki с URL в README.
- [ ] Runbook отказ Redis/брокера.
- [ ] Версии конфигов/фичефлаги документированы.

---

### 7. Коммерция и биллинг

- Подписки, лимиты плана, metering; если вне кода — явно указать «вне репозитория».

**Чек-лист:**

- [ ] Биллинг **самого продукта** (подписка клиники на SaaS) смоделирован в коде или явно «вне репо».
- [ ] Лимиты плана enforced в API.
- [ ] Платёж пациента (YooKassa и т.д.) отделён концептуально от выручки вендора.

## Оси 8–12 (поставка, фронт, API, BCP, отрасль)

### 8. Поставка и цепочка (CI/CD, зависимости)

- Воспроизводимые сборки: lockfile или эквивалент; скан уязвимостей (SAST/dependency); обязательный зелёный пайплайн на merge.

**Факт по репозиторию (проверка структуры):** в `.github/workflows/` должен быть активный набор проверок; наличие критичных workflow только в `workflows_disabled` снижает ось до **0–1** без внешнего CI (см. U-008). Frontend: `package-lock.json` в репо — плюс к воспроизводимости npm; Python: наличие lock-файла — проверять по факту в корне.

**Чек-лист:**

- [ ] CI гоняет тесты backend на каждый PR/merge.
- [ ] CI гоняет тесты frontend или хотя бы lint+typecheck.
- [ ] Dependency scan (Dependabot, Trivy, Snyk) включён или заменён политикой.
- [ ] Lockfile или зафиксированные версии для прод-сборки.
- [ ] SBOM или экспорт зависимостей для аудита (желательно для уровня 2).

---

### 9. Модель угроз фронтенда

- XSS, CSRF (если cookie-сессии), хранение токенов, CSP, supply chain npm.

**Чек-лист:**

- [ ] Токены не в `localStorage` **или** есть явный risk acceptance и CSP/санитизация.
- [ ] Нет секретов и long-lived service tokens в бандле.
- [ ] Зависимости фронта обновляются; audit `npm audit` в CI (уровень 2).

---

### 10. Управление изменениями API

- Версионирование (`/v1`), deprecation-заголовки, changelog, совместимость клиентов.

**Чек-лист:**

- [ ] Префикс версии зафиксирован (`settings.api_v1_prefix`).
- [ ] Breaking changes процесс: changelog, миграция клиентов.
- [ ] OpenAPI актуален или генерируется.

---

### 11. Непрерывность бизнеса (BCP / DR)

- RTO/RPO цели, резервное копирование, учения восстановления, мульти-AZ — если заявлено.

**Чек-лист:**

- [ ] Документ RTO/RPO или «не заявлено».
- [ ] Процедура restore из бэкапа протестирована (учение) — артефакт дата/результат.
- [ ] DR workflow в CI или runbook (не только disabled без объяснения).

---

### 12. Отраслевые требования (медицина и персональные данные)

- Регламенты хранения медданных, согласия, сроки хранения — **не оцениваются как «есть/нет» без юриста**; ось используется чтобы **не приписывать** репозиторию compliance.

**Чек-лист (инженерный минимум):**

- [ ] Понятно, какие сущности несут мед/PII риск (якоря в `domain/entities`).
- [ ] Шифрование at-rest для вложений/S3 задокументировано в коде/compose.
- [ ] Нет ложных утверждений в docs о сертификации без артефакта.

## Оси 13–14 (антиспам и security UX; мастер-план §27–§28)

Добавлены **2026-04-09** (QA_ARCH цикл 4): отдельно от оси **3** (общая безопасность) и оси **5** (наблюдаемость), чтобы при аудите публичного SaaS не смешивать «RBAC и секреты» с **abuse на входе** и **сигналами вторжения**.

### 13. Антиспам и злоупотребления (публичный вход и чаты)

- Rate limiting и политика для **регистрации / восстановления доступа**, **чат персонала**, **чат клиента** / omni; капча или эквивалент по политике; лимиты контента (длина, ссылки, вложения); наблюдаемость блокировок без взрыва cardinality.

**Связь:** [SAAS_STRENGTHENING_MASTER_PLAN.md](./SAAS_STRENGTHENING_MASTER_PLAN.md) **§27**, **§5** (C3), **§15b** (сквозное усиление).

**Чек-лист:**

- [ ] Лимиты на IP / учётку / организацию на чувствительных шагах auth и на отправку сообщений в чатах.
- [ ] Политика капчи/антибота согласована с продуктом; не только текст в плане.
- [ ] Метрики класса «заблокировано как спам» с **низкой cardinality** (см. ось **5**, M1 в мастер-плане §11).
- [ ] Негативные тесты или ручной сценарий на flood/дубликаты (хотя бы для одного канала).

---

### 14. Утечки в клиенте и реагирование на атакующее поведение

- Ответы API в prod **без** стеков и внутренних путей; маскирование в логах клиента; классификация **security events** (массовые 401/403, сканирование путей, аномальные параметры); метрики и алерты с `runbook_url` (низкая cardinality лейблов).

**Связь:** [SAAS_STRENGTHENING_MASTER_PLAN.md](./SAAS_STRENGTHENING_MASTER_PLAN.md) **§28**, **§11** M1/M6, [PLATFORM_BILLING_ERROR_CATALOG.md](./PLATFORM_BILLING_ERROR_CATALOG.md) как образец стабильных кодов ошибок.

**Чек-лист:**

- [ ] Единый формат публичных ошибок (`error_code` / аналог) без утечки структуры БД и путей файловой системы.
- [ ] Запрет или маскирование секретов и полных токенов в ответах и в клиентских логах по политике.
- [ ] Метрики `security_*` или эквивалент с лимитом лейблов; алерт на всплеск с привязкой к runbook.
- [ ] Для публичных webhook и signup — согласованность с осью **13** и красными флагами (не заявлять «готово» без кода).
